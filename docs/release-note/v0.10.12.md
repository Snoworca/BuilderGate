# BuilderGate v0.10.12

## English

### Fixed

- **With more terminals open than the live-terminal limit, a terminal sometimes stopped showing
  output after a workspace switch.** Typed text and Enter showed nothing, but a reload showed the
  text. This happened with, for example, 40 terminals and the default limit of 32
  (`resourceLimits.workspaceRuntime.maxLiveTerminals`).
  - Cause: above the limit, the browser closes terminals that stay hidden, and it unsubscribes
    their sessions. For each unsubscribe the server sent a `terminal-binary:channel-retired`
    message with the reason `unsubscribed`. The browser did not know this reason, so it cleared its
    whole channel table. After that, it refused the binary output of every other session as an
    unknown channel. It also did not ask the server for the channel table again. The table came
    back only when another terminal opened, so the problem occurred only sometimes.
  - Fix: the browser now treats `unsubscribed` as one session that left, and retires only the
    listed channels. A rollback of the whole binary data plane now sends `codec-epoch-bump`, so
    the browser still clears the table in that case. When output arrives on a channel that the
    browser does not know, the browser asks the server for the channel table again.
  - Checked in a real browser on port 2222 with 40 terminals in 4 workspaces and the limit at 32.
    Before the fix, the terminal stopped showing output in the first or second round of workspace
    switches, and the console showed `binary frame rejected (unknown-channel)`. After the fix,
    72 of 72 checks passed in 3 runs, with no rejected frames. (IR-BGSTAB-001)

- **A prompt sent through MCP sometimes stayed in the agent's input box and was not submitted.**
  Short prompts were submitted, but some long ones were not.
  - Cause: the text and the Enter key were written together. When Enter arrived in the same read
    as a long text, an AI TUI treated it as part of a paste. Also, `message.send` in submit mode
    and the launch command and kickoff of `open_agent` did not send Enter at all.
  - Fix: a submit now writes the text first, waits, and then writes Enter by itself. If the text
    is refused, Enter is not written. (FR-MCP-002 AC-7)

### Added

- **Two MCP settings for the wait before Enter.** In the **MCP Management** window, on the
  **Security** tab:
  - **Wait before Enter**: 150 ms by default, from 0 to 5000.
  - **Extra wait per 1 KB**: 50 ms by default, from 0 to 1000.
  The wait is the base wait plus the extra wait for each started 1 KB, up to 10 seconds. The
  values apply from the next delivery after you save. (FR-MCP-002 AC-8)

### Changed

- **The MCP server instructions now say two more things.** The tools can direct other sessions
  (open terminals, start coding agents, send prompts, read screens). A submit already presses
  Enter, so an agent does not need to send a second message to submit. (FR-MCP-002 AC-9)

## 한국어

### 수정

- **터미널을 실시간 터미널 한도보다 많이 열어 두면, 워크스페이스를 옮긴 뒤 터미널에 출력이 나오지
  않는 경우가 있었습니다.** 글자를 치고 Enter 를 눌러도 화면에 아무것도 나오지 않았고, 새로고침하면
  친 글자가 보였습니다. 예를 들어 터미널 40개를 기본 한도 32
  (`resourceLimits.workspaceRuntime.maxLiveTerminals`)로 쓸 때 나타났습니다.
  - 원인: 한도를 넘으면 브라우저는 오래 숨겨진 터미널을 닫고 그 세션의 구독을 해제합니다. 서버는 구독
    해제마다 `terminal-binary:channel-retired` 메시지를 이유 `unsubscribed` 로 보냈습니다.
    브라우저는 이 이유를 몰라서 채널 표 전체를 비웠습니다. 그 뒤로는 다른 모든 세션의 바이너리
    출력을 모르는 채널로 보고 버렸고, 서버에 채널 표를 다시 요청하지도 않았습니다. 다른 터미널이
    새로 열릴 때만 표가 다시 채워졌기 때문에 문제가 가끔씩만 나타났습니다.
  - 해결: 브라우저가 `unsubscribed` 를 세션 하나가 빠진 것으로 보고, 메시지에 적힌 채널만
    폐기합니다. 바이너리 데이터 평면 전체를 되돌릴 때는 서버가 이제 `codec-epoch-bump` 를 보내므로,
    그때는 지금처럼 표를 비웁니다. 브라우저가 모르는 채널로 출력이 오면 서버에 채널 표를 다시
    요청합니다.
  - 확인: 2222 포트의 실제 브라우저에서 워크스페이스 4개에 터미널 40개를 두고 한도를 32로 맞춰
    확인했습니다. 수정 전에는 워크스페이스를 한두 바퀴 오가는 사이에 터미널 출력이 멈췄고, 콘솔에
    `binary frame rejected (unknown-channel)` 가 찍혔습니다. 수정 후에는 3회 실행에서 72건 모두
    통과했고, 거부된 프레임은 없었습니다. (IR-BGSTAB-001)

- **MCP 로 보낸 프롬프트가 에이전트 입력창에만 남고 전송되지 않는 경우가 있었습니다.** 짧은
  프롬프트는 전송됐지만, 긴 프롬프트 가운데 일부가 걸렸습니다.
  - 원인: 본문과 Enter 를 한 번에 썼습니다. 긴 본문과 Enter 가 같은 읽기에 실리면 AI TUI 가 Enter 를
    붙여넣기의 일부로 처리했습니다. 또 `message.send` 의 submit 모드와 `open_agent` 의 실행 명령·
    kickoff 는 Enter 를 아예 보내지 않았습니다.
  - 해결: submit 은 이제 본문을 먼저 쓰고, 잠시 기다린 뒤 Enter 를 따로 씁니다. 본문이 거부되면
    Enter 는 쓰지 않습니다. (FR-MCP-002 AC-7)

### 추가

- **Enter 전송 전 대기를 정하는 MCP 설정 두 가지.** **MCP 관리** 창의 **보안** 탭에 있습니다.
  - **Enter 전송 전 대기**: 기본 150ms, 0~5000.
  - **1KB당 추가 대기**: 기본 50ms, 0~1000.
  실제 대기 시간은 기본 대기에 시작된 1KB 마다 추가 대기를 더한 값이며, 최대 10초입니다. 저장한
  뒤의 다음 전달부터 적용됩니다. (FR-MCP-002 AC-8)

### 변경

- **MCP 서버 지침에 두 가지를 더 적었습니다.** 이 도구로 다른 세션을 지휘할 수 있습니다(터미널 열기,
  코딩 에이전트 띄우기, 프롬프트 보내기, 화면 읽기). 또 submit 은 이미 Enter 를 누르므로, 전송하려고
  메시지를 따로 보낼 필요가 없습니다. (FR-MCP-002 AC-9)
