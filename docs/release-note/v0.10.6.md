# BuilderGate v0.10.6

## English

### Faster input with many sessions

- **Typing no longer slows down when dozens of sessions are running.** With many long-running
  sessions (for example Claude Code agents with long scrollback), keystrokes could take seconds
  to appear. The server's main thread was kept busy, so input waited behind it.
  - Cause: for every chunk of output, the server re-processed the whole scrollback of the
    session in three places:
    - Sending an output frame built a full checkpoint (every cell of the scrollback, serialized
      and hashed) only to read two sequence numbers.
    - A diagnostic "shadow comparison" serialized each busy session's whole scrollback and
      replayed it into a fresh terminal at most every 5 seconds per session. One comparison
      takes about 2.5 seconds at 10,000 lines, and nothing in the product uses its result.
    - The output kept since the last snapshot was re-measured and re-cut at its 2 MB limit on
      every chunk.
  - Fix:
    - The output path now reads the two sequence numbers directly.
    - The shadow comparison is off by default. It is controlled by the new
      `terminalAuthority.shadowComparison` setting in the configuration file.
    - The kept output is trimmed only after it grows 25% past its limit.
  - Measured with sessions holding 10,000 lines of scrollback and redrawing every 100 ms:

    | Busy sessions | Before (median keystroke latency) | After |
    |---|---|---|
    | 5 | 2,501 ms | 30 ms |
    | 10 | 4,443 ms (32 of 40 keys took over 5 s) | 29 ms |
    | 30 | — | 32 ms |

    With the shadow comparison turned back on, 10 busy sessions again pushed every keystroke
    past 5 seconds.

### Configuration

- New `terminalAuthority.shadowComparison` (default `false`). Leave it off unless you are
  working on terminal-authority promotion; turning it on brings back the slowdown above.

### Tests

- Added a measurement test for keystroke latency under load (`input-latency-probe.spec.ts`).

## 한국어

### 세션이 많을 때 입력 속도 개선

- **세션이 수십 개 돌아도 입력이 느려지지 않습니다.** 스크롤백이 긴 세션(예: Claude Code 에이전트)이 많으면
  키를 누른 뒤 글자가 찍히기까지 몇 초씩 걸릴 수 있었습니다. 서버의 메인 스레드가 계속 바빠서 입력이 그 뒤에서
  기다렸기 때문입니다.
  - 원인: 출력이 올 때마다 서버가 세 곳에서 그 세션의 스크롤백 전체를 다시 처리했습니다.
    - 출력 프레임을 보낼 때 순번 두 개를 읽으려고 체크포인트 전체(스크롤백의 모든 칸을 직렬화하고 해시)를
      만들었습니다.
    - 진단용 "섀도 비교"가 세션마다 최대 5초에 한 번, 바쁜 세션의 스크롤백 전체를 직렬화해 새 터미널에 다시
      재생했습니다. 1만 줄에서 1회에 약 2.5초가 걸리며, 그 결과는 제품의 어떤 기능도 쓰지 않습니다.
    - 마지막 스냅샷 이후의 출력을 보관하는 문자열을 2MB 상한에서 출력이 올 때마다 다시 재고 잘랐습니다.
  - 해결:
    - 출력 경로는 순번 두 개만 바로 읽습니다.
    - 섀도 비교는 기본적으로 꺼져 있고, 설정 파일의 새 항목 `terminalAuthority.shadowComparison` 으로 켭니다.
    - 보관 문자열은 상한을 25% 넘었을 때만 자릅니다.
  - 측정: 세션마다 1만 줄 스크롤백, 100ms 마다 다시 그리는 조건입니다.

    | 바쁜 세션 | 수정 전 (키 입력 지연 중앙값) | 수정 후 |
    |---|---|---|
    | 5 | 2,501ms | 30ms |
    | 10 | 4,443ms (40회 중 32회가 5초 초과) | 29ms |
    | 30 | — | 32ms |

    섀도 비교를 다시 켜면 바쁜 세션 10개에서 모든 키 입력이 다시 5초를 넘었습니다.

### 설정

- 새 항목 `terminalAuthority.shadowComparison` (기본값 `false`). 터미널 권한 승격 작업을 하는 경우가 아니면
  꺼 두십시오. 켜면 위의 지연이 다시 생깁니다.

### 테스트

- 부하 상태의 키 입력 지연을 재는 측정 테스트를 추가했습니다(`input-latency-probe.spec.ts`).
