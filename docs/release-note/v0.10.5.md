# BuilderGate v0.10.5

## English

### Fixed

- **Terminal rendering no longer breaks when switching workspaces.** Moving between workspaces
  could leave a terminal running Claude Code (or another full-screen TUI) garbled: leftover
  lines from an earlier frame and text shifted by a row or a few columns. It stayed that way
  until the browser tab was reloaded.
  - Cause: every time a workspace is shown, the browser asks the server for a screen repair.
    The patch it gets back is the server's current screen, so it already contains all output
    sent before it. The browser wrote that patch straight to the terminal, while output
    received just before it could still be waiting in the browser's write queue. That output
    was then applied a second time on top of the patch. Programs that redraw with relative
    cursor moves, as Claude Code does, then drew every later frame one row off.
  - Fix: the browser now drains its write queue before it applies a screen repair. If the
    queue does not drain, the repair is reported as failed instead of being written over
    pending output.
  - Measured with an Ink-style redrawing TUI in six grid terminals: rapid workspace switching
    broke 18 of 72, 18 of 72 and 8 of 48 screens before the fix, and 0 of 72 (twice) after it.
    Repeated manual repairs broke 6 of 45 and 9 of 75 screens before, and 0 of 60 after.

### Tests

- Added a regression test that switches between grid workspaces while an Ink-style TUI keeps
  redrawing (`terminal-screen-repair-output-order.spec.ts`).
- Fixed two long-failing test suites. Both failures came from the tests, not the product:
  - The terminal render unit tests failed in shells that inherit `NODE_ENV=production`,
    because React's production build has no `act`.
  - The screen-repair resync E2E tests looked for DOM rows that do not exist under the WebGL
    renderer, and they raced against the server's own screen repairs.

## 한국어

### 수정

- **워크스페이스를 전환할 때 터미널 화면이 깨지던 문제를 고쳤습니다.** 워크스페이스를 오가다 보면
  Claude Code 같은 전체 화면 TUI 가 실행 중인 터미널이 깨지는 경우가 있었습니다. 이전 프레임의 줄이
  남거나, 글자가 한 줄 또는 몇 칸 밀렸고, 브라우저를 새로고침해야만 풀렸습니다.
  - 원인: 워크스페이스를 보여 줄 때마다 브라우저가 서버에 화면 수리를 요청합니다. 돌아오는 패치는
    서버의 현재 화면이라, 그보다 앞서 보낸 출력이 이미 모두 들어 있습니다. 그런데 브라우저는 이 패치를
    터미널에 바로 썼고, 직전에 받은 출력 일부는 아직 브라우저의 쓰기 대기열에 남아 있었습니다. 그 출력이
    패치 위에 한 번 더 적용됐습니다. Claude Code 처럼 커서를 상대적으로 옮겨 다시 그리는 프로그램은
    그 뒤 모든 프레임을 한 줄 어긋난 자리에 그렸습니다.
  - 해결: 브라우저가 화면 수리를 적용하기 전에 쓰기 대기열을 먼저 비웁니다. 대기열이 끝내 비지 않으면
    남은 출력 위에 패치를 쓰지 않고 수리 실패로 보고합니다.
  - 측정: Claude Code 처럼 다시 그리는 TUI 를 그리드 터미널 6개에서 돌렸습니다. 빠르게 전환하면
    수정 전에는 72개 중 18개, 72개 중 18개, 48개 중 8개 화면이 깨졌고, 수정 후에는 두 번 모두 72개 중
    0개였습니다. 화면 수리만 반복한 경우 수정 전에는 45개 중 6개, 75개 중 9개였고, 수정 후에는 60개 중
    0개였습니다.

### 테스트

- TUI 가 계속 다시 그리는 동안 그리드 워크스페이스를 전환하는 회귀 테스트를 추가했습니다
  (`terminal-screen-repair-output-order.spec.ts`).
- 오래 실패하던 테스트 두 묶음을 고쳤습니다. 두 경우 모두 원인은 제품이 아니라 테스트였습니다.
  - 터미널 렌더 단위 테스트는 `NODE_ENV=production` 을 상속한 셸에서 실패했습니다. React 프로덕션
    빌드에는 `act` 가 없기 때문입니다.
  - 화면 수리 재동기화 E2E 테스트는 WebGL 렌더러에서는 존재하지 않는 DOM 행을 찾고 있었고, 서버가
    보내는 실제 화면 수리와 경합했습니다.
