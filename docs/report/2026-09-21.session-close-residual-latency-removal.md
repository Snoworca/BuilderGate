# 세션 닫기 잔여 지연 제거 (PERF-BGSTAB-013)

- 날짜: 2026-09-21
- 요구사항: `PERF-BGSTAB-013` — Windows 프로세스 identity 는 WMI 를 거치지 않는다
- 선행: `PERF-BGSTAB-012`, 연구 `docs/research/2026-09-21.session-close-residual-latency.md`
- 관련: `FR-BGSTAB-011` (Wave 2 검증된 프로세스 트리 종료)

## 1. 목표

`PERF-BGSTAB-012` 로 화면에서는 탭이 즉시 사라지게 했지만, 서버는 여전히
Windows 에서 약 5.8초, Linux 에서 약 0.75초를 종료 검증에 썼다. 연구의
A(identity 소스 교체) · B(유예 대기 제거) · C-1(Windows 자손 표본 제거)을 구현한다.

## 2. 결과 (같은 호스트 paired 실측)

실제 프로세스 트리를 띄워 `terminate()` 를 직접 호출한 값이다.
Windows 는 `powershell.exe` 가 자식 `powershell.exe` 를 하나 띄운 트리,
Linux 는 `bash -c 'sleep 120 & sleep 120'` 트리.

| 경로 | 변경 전 | 변경 후 |
|---|---|---|
| **Windows `terminate()`** | 5803 / 5921 / 5763 / 5672 ms | **2325 / 2418 / 2414 / 2110 ms** |
| **Linux `terminate()`** | 753 / 753 / 753 ms | **4 / 2 / 4 ms** |
| Windows identity 조회 1회 | 3.59 / 3.01 / 3.38 s | **313 / 326 / 301 ms** |

두 경우 모두 결과는 동일하다 — `status=completed`, `remaining=[]`,
루트 실제 사망 확인(`rootStillAlive=false`), POSIX 는 leaf-first SIGTERM 3개.

## 3. 무엇을 바꿨나

### A. identity 소스를 WMI 밖으로 (AC-1, AC-2, AC-3, AC-4)

`Get-CimInstance Win32_Process` → `[System.Diagnostics.Process]::GetProcessById(N).StartTime`.

측정으로 확인한 것:

| 방법 | 실측 |
|---|---|
| CIM 전체 열거 | 3.59 / 3.01 / 3.38 s |
| CIM 단일 PID 필터 | 6.08 / 2.46 / 2.16 s |
| `.NET GetProcessById(N).StartTime` | 0.29 / 0.27 s |
| `powershell.exe -NoProfile 'exit 0'` | 0.41 / 0.42 s |

필터를 걸어도 줄지 않고 셸 기동은 0.41초뿐이다 — **비용은 WMI 자체**다.

**좀비 문제 확인.** `GetProcessById` 가 핸들이 열린 종료 프로세스를 살아있다고
오판하면 identity 가 맞아버려 잘못된 kill 로 이어진다. 실측: 우리 쪽 핸들을 쥔 채
`taskkill` 직후 +0ms 부터 CIM 과 `GetProcessById` 가 **둘 다 not-found** 였고
핸들을 놓은 뒤에도 같았다. .NET 은 실행 중 PID 목록으로 판정하므로 CIM 과 같은
생존 의미를 갖는다.

**두 시각은 마지막 자리가 다르다.** 같은 PID 에서
CIM `...8052290Z`(마이크로초) vs .NET `...8052293Z`(100ns).
접두어를 `win32:` → `win32net:` 로 바꿔 세대를 분리했다. 업그레이드 시점에
살아 있던 세션은 구세대 identity를 갖고 있어 불일치 → `skipped-unverified` →
**kill 을 시도하지 않는다.** `FR-BGSTAB-011` AC-2 가 요구하는 안전한 방향이며
재시작하면 사라지는 일회성이다.

**구조적 수정.** 캡처(`readProcessStartIdentity`)와 검증(`queryWindowsProcessInfo`)이
각자 PowerShell 본문을 들고 있던 것을 하나로 합쳤다. 이 쌍의 과거 실패 두 건이
전부 "두 쪽이 어긋남" 이었다 — 한쪽만 깨뜨린 세미콜론 join, 한쪽만 짧았던 타임아웃.
이제 캡처가 검증을 그대로 호출하므로 어긋날 수 없다. 테스트는 두 경로의
`execFile` 인자 배열이 **동일**한지를 단언한다(소스 문자열 매칭이 아니다).

### B. 대기 예산은 상한이지 통행료가 아니다 (AC-5, AC-7)

`gracefulWaitMs` 를 잠들고 나서 확인하던 것을, **먼저 확인하고 남아 있을 때만**
예산이 끝날 때까지 재확인하도록 바꿨다.

- Windows: `taskkill /F` 는 유예를 주지 않는다. 기다릴 대상이 애초에 없었다.
  실측 — `taskkill` 반환 후 루트와 자손 2개가 사라지기까지 **2–7ms**, 6회 중 6회,
  폴링 0회.
- Linux: `terminate()` 753ms 중 **750ms 가 이 대기**였고 실제 작업은 약 3ms.

**유예 의미는 보존된다.** 예산 안에 SIGTERM 으로 죽은 프로세스는 SIGKILL 을 받지 않고,
넘겨 생존하면 승격한다. SRS 전수 확인 결과 이 대기를 *소비*하도록 요구하는 AC 는
없다 — `gracefulWaitMs=750` 은 `FR-BGSTAB-010` AC-1 의 **설정 파싱** 기본값이다.
따라서 승계가 필요 없다.

재확인 간격은 10ms 에서 100ms 로 배수 증가한다. POSIX 의 `inspect` 는 `/proc` 전체를
훑으므로 고정 짧은 간격은 생존 프로세스 하나를 수십 번의 전체 스캔으로 바꾼다.

### C-1. Windows 는 자손을 표본 수집하지 않는다 (AC-6)

`taskkill /T` 가 트리를 걷고, node-pty 의 `kill()` 이 이미 네이티브
`GetConsoleProcessList` 로 콘솔 프로세스를 닫는다. CIM 으로 자손을 세는 것은
이미 하는 일의 두 번째 사본이었다. **POSIX 는 계속 수집한다** — leaf-first
시그널링에 그 목록이 필요하다.

## 4. 비-Windows

사용자 지시에 따라 POSIX 를 명시적으로 확인했다.

- Linux 실제 종료 실측(위 표): 트리 3개 전부 leaf-first SIGTERM, 루트 사망, 2–4ms.
- identity 는 `procfs:<pid>:<ticks>` 그대로, PowerShell 을 부르지 않는다(테스트로 고정).
- 자손 표본, SIGKILL 승격, 예산 상한 모두 테스트로 고정.

**macOS 는 현재 프로세스 트리를 종료하지 못한다.** `readPosixProcessInfo` 가
`/proc/<pid>/stat` 을 읽는데 macOS 에는 `/proc` 이 없어 identity 가 null 이 되고
`inspect` 가 `skipped-unverified` 로 거부한다. 이번 변경이 만든 것이 아니라
`OPS-BGSTAB-017` 로 macOS 빌드를 내기 시작하면서 드러난 선재 결함이다.
현재 동작을 특성화 테스트로 고정해 두었고, macOS 에서 실행해 본 적이 없으므로
코드 경로에 대한 주장이지 실행 증거가 아니다. 검증할 macOS 없이 안전 임계
kill 경로에 미검증 구현을 넣지 않았다.

## 5. 남은 것

**`taskkill` 자신이 이제 가장 큰 항목이다.**

| 측정 | 값 |
|---|---|
| `taskkill /PID N /T /F` | 1.47 / 1.53 / 1.46 s |
| `taskkill /PID N /F` | 1.475 / 1.480 / 1.460 s |
| `taskkill /?` (기동만) | 0.06 s |
| `Process.Kill()` (검증된 PID) | 0.002–0.004 s |

기동은 0.06초인데 kill 이 1.5초다 — **`taskkill` 도 내부적으로 WMI 를 탄다.**
연구 문서가 이것을 0.1초로 추정했던 것이 틀렸다.

`FR-BGSTAB-011` AC-3 이 `taskkill.exe /PID <verifiedRootPid> /T /F` 를 명시적으로
요구하므로 교체에는 승계가 필요하다. AC-3 의 안전 내용(PID 지정, `/IM` 금지,
이름 기반 광역 kill 금지)은 검증된 단일 PID 에 대한 `Process.Kill()` 로 더 좁아지지만,
**보안 결정은 성능 논거만으로 뒤집지 않는다**는 규칙에 따라 별도 판단 사항으로 남긴다.

그 밖에: `no-broad-kill` 가드가 주석을 코드로 읽는다(연구 부록 B-2).
