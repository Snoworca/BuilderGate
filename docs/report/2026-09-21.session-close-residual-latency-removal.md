# 세션 닫기 잔여 지연 제거 (PERF-BGSTAB-013)

- 날짜: 2026-09-21
- 요구사항: `PERF-BGSTAB-013` — Windows 프로세스 identity 는 WMI 를 거치지 않는다
- 선행: `PERF-BGSTAB-012`, 연구 `docs/research/2026-09-21.session-close-residual-latency.md`
- 관련: `FR-BGSTAB-011` (Wave 2 검증된 프로세스 트리 종료)

## 1. 목표

`PERF-BGSTAB-012` 로 화면에서는 탭이 즉시 사라지게 했지만, 서버는 여전히
Windows 에서 약 5.8초, Linux 에서 약 0.75초를 종료 검증에 썼다. 연구의
A(identity 소스 교체) · B(유예 대기 제거) · C-1(Windows 자손 표본 제거)을 구현한다.

## 2. 결과 (같은 호스트 paired 실측)

실제 프로세스 트리를 띄워 `terminate()` 를 직접 호출한 값이다.
Windows 는 `powershell.exe` 가 자식 `powershell.exe` 를 하나 띄운 트리,
Linux 는 `bash -c 'sleep 120 & sleep 120'` 트리.

| 경로 | 변경 전 | 변경 후 |
|---|---|---|
| **Windows `terminate()`** | 5803 / 5921 / 5763 / 5672 ms | **2325 / 2418 / 2414 / 2110 ms** |
| **Linux `terminate()`** | 753 / 753 / 753 ms | **4 / 2 / 4 ms** |
| Windows identity 조회 1회 | 3.59 / 3.01 / 3.38 s | **313 / 326 / 301 ms** |

두 경우 모두 결과는 동일하다 — `status=completed`, `remaining=[]`,
루트 실제 사망 확인(`rootStillAlive=false`), POSIX 는 leaf-first SIGTERM 3개.

## 3. 무엇을 바꿨나

### A. identity 소스를 WMI 밖으로 (AC-1, AC-2, AC-3, AC-4)

`Get-CimInstance Win32_Process` → `[System.Diagnostics.Process]::GetProcessById(N).StartTime`.

측정으로 확인한 것:

| 방법 | 실측 |
|---|---|
| CIM 전체 열거 | 3.59 / 3.01 / 3.38 s |
| CIM 단일 PID 필터 | 6.08 / 2.46 / 2.16 s |
| `.NET GetProcessById(N).StartTime` | 0.29 / 0.27 s |
| `powershell.exe -NoProfile 'exit 0'` | 0.41 / 0.42 s |

필터를 걸어도 줄지 않고 셸 기동은 0.41초뿐이다 — **비용은 WMI 자체**다.

**좀비 문제 확인.** `GetProcessById` 가 핸들이 열린 종료 프로세스를 살아있다고
오판하면 identity 가 맞아버려 잘못된 kill 로 이어진다. 실측: 우리 쪽 핸들을 쥔 채
`taskkill` 직후 +0ms 부터 CIM 과 `GetProcessById` 가 **둘 다 not-found** 였고
핸들을 놓은 뒤에도 같았다. .NET 은 실행 중 PID 목록으로 판정하므로 CIM 과 같은
생존 의미를 갖는다.

**두 시각은 마지막 자리가 다르다.** 같은 PID 에서
CIM `...8052290Z`(마이크로초) vs .NET `...8052293Z`(100ns).
접두어를 `win32:` → `win32net:` 로 바꿔 세대를 분리했다. 업그레이드 시점에
살아 있던 세션은 구세대 identity를 갖고 있어 불일치 → `skipped-unverified` →
**kill 을 시도하지 않는다.** `FR-BGSTAB-011` AC-2 가 요구하는 안전한 방향이며
재시작하면 사라지는 일회성이다.

**구조적 수정.** 캡처(`readProcessStartIdentity`)와 검증(`queryWindowsProcessInfo`)이
각자 PowerShell 본문을 들고 있던 것을 하나로 합쳤다. 이 쌍의 과거 실패 두 건이
전부 "두 쪽이 어긋남" 이었다 — 한쪽만 깨뜨린 세미콜론 join, 한쪽만 짧았던 타임아웃.
이제 캡처가 검증을 그대로 호출하므로 어긋날 수 없다. 테스트는 두 경로의
`execFile` 인자 배열이 **동일**한지를 단언한다(소스 문자열 매칭이 아니다).

### B. 대기 예산은 상한이지 통행료가 아니다 (AC-5, AC-7)

`gracefulWaitMs` 를 잠들고 나서 확인하던 것을, **먼저 확인하고 남아 있을 때만**
예산이 끝날 때까지 재확인하도록 바꿨다.

- Windows: `taskkill /F` 는 유예를 주지 않는다. 기다릴 대상이 애초에 없었다.
  실측 — `taskkill` 반환 후 루트와 자손 2개가 사라지기까지 **2–7ms**, 6회 중 6회,
  폴링 0회.
- Linux: `terminate()` 753ms 중 **750ms 가 이 대기**였고 실제 작업은 약 3ms.

**유예 의미는 보존된다.** 예산 안에 SIGTERM 으로 죽은 프로세스는 SIGKILL 을 받지 않고,
넘겨 생존하면 승격한다. SRS 전수 확인 결과 이 대기를 *소비*하도록 요구하는 AC 는
없다 — `gracefulWaitMs=750` 은 `FR-BGSTAB-010` AC-1 의 **설정 파싱** 기본값이다.
따라서 승계가 필요 없다.

재확인 간격은 10ms 에서 100ms 로 배수 증가한다. POSIX 의 `inspect` 는 `/proc` 전체를
훑으므로 고정 짧은 간격은 생존 프로세스 하나를 수십 번의 전체 스캔으로 바꾼다.

### C-1. Windows 는 자손을 표본 수집하지 않는다 (AC-6)

`taskkill /T` 가 트리를 걷고, node-pty 의 `kill()` 이 이미 네이티브
`GetConsoleProcessList` 로 콘솔 프로세스를 닫는다. CIM 으로 자손을 세는 것은
이미 하는 일의 두 번째 사본이었다. **POSIX 는 계속 수집한다** — leaf-first
시그널링에 그 목록이 필요하다.

## 4. 비-Windows

사용자 지시에 따라 POSIX 를 명시적으로 확인했다.

- Linux 실제 종료 실측(위 표): 트리 3개 전부 leaf-first SIGTERM, 루트 사망, 2–4ms.
- identity 는 `procfs:<pid>:<ticks>` 그대로, PowerShell 을 부르지 않는다(테스트로 고정).
- 자손 표본, SIGKILL 승격, 예산 상한 모두 테스트로 고정.

**macOS 는 현재 프로세스 트리를 종료하지 못한다** (이슈 #118). `readPosixProcessInfo` 가
`/proc/<pid>/stat` 을 읽는데 macOS 에는 `/proc` 이 없어 identity 가 null 이 되고
`inspect` 가 `skipped-unverified` 로 거부한다. 이번 변경이 만든 것이 아니라
`OPS-BGSTAB-017` 로 macOS 빌드를 내기 시작하면서 드러난 선재 결함이다.
현재 동작을 특성화 테스트로 고정해 두었고, macOS 에서 실행해 본 적이 없으므로
코드 경로에 대한 주장이지 실행 증거가 아니다. 검증할 macOS 없이 안전 임계
kill 경로에 미검증 구현을 넣지 않았다.

## 5. 남은 것

**`taskkill` 자신이 이제 가장 큰 항목이다.**

| 측정 | 값 |
|---|---|
| `taskkill /PID N /T /F` | 1.47 / 1.53 / 1.46 s |
| `taskkill /PID N /F` | 1.475 / 1.480 / 1.460 s |
| `taskkill /?` (기동만) | 0.06 s |
| `Process.Kill()` (검증된 PID) | 0.002–0.004 s |

기동은 0.06초인데 kill 이 1.5초다 — **`taskkill` 도 내부적으로 WMI 를 탄다.**
연구 문서가 이것을 0.1초로 추정했던 것이 틀렸다.

`FR-BGSTAB-011` AC-3 이 `taskkill.exe /PID <verifiedRootPid> /T /F` 를 명시적으로
요구하므로 교체에는 승계가 필요하다. AC-3 의 안전 내용(PID 지정, `/IM` 금지,
이름 기반 광역 kill 금지)은 검증된 단일 PID 에 대한 `Process.Kill()` 로 더 좁아지지만,
**보안 결정은 성능 논거만으로 뒤집지 않는다**는 규칙에 따라 별도 판단 사항으로 남긴다.

그 밖에: `no-broad-kill` 가드가 주석을 코드로 읽는다(연구 부록 B-2).

# 부록 — taskkill 교체 (PERF-BGSTAB-014, 2026-09-21)

§5 가 "남은 것" 으로 남겼던 `taskkill` 1.5초를 사용자 승인 하에 교체했다.
`FR-BGSTAB-011` AC-3 의 **도구 지정**을 `PERF-BGSTAB-014` 로 승계했으며,
같은 AC 의 **안전 속성은 유지하거나 좁혔다.**

## A-1. 왜 taskkill 이 느린가

| 측정 | 값 |
|---|---|
| `taskkill /?` (기동만) | 0.06 s |
| `taskkill /PID N /T /F` | 1.46 / 1.53 / 1.46 s (한가할 때) · 2.40 / 2.47 / 2.53 s (부하 중) |
| `taskkill /PID N /F` (트리 없이) | 1.475 / 1.480 / 1.460 s |

기동은 0.06초이고 `/T` 를 빼도 값이 같다 — **비용은 트리 순회가 아니라 WMI 왕복이다.**
전송을 바꿔도 같다: `Get-CimInstance` 2.3–3.1s, `Get-WmiObject` 2.4–3.3s,
raw `ManagementObjectSearcher` 2.5–2.9s. WMI 자체가 느리다.

## A-2. 무엇으로 바꿨나

`CreateToolhelp32Snapshot` 으로 (PID, 부모PID) 쌍을 받아 검증된 루트에서
부모 링크를 따라 자손을 찾고, **leaf-first 로 PID 하나씩** `Process.Kill()` 한다.

**자손 집합이 같은지부터 확인했다.** 3단 트리(powershell → powershell + cmd → timeout,
자손 6개)에서 toolhelp 집합과 `Win32_Process` 집합이 **4회 중 4회 완전히 일치**했다.

AC-3 이 보호하던 것과의 대조:

| AC-3 의 안전 속성 | 교체 후 |
|---|---|
| PID 지정 (`/PID <verifiedRootPid>`) | 유지 — 모든 종료가 숫자 PID, 검증된 루트에서 도달한 것만 |
| `/IM` 금지, 이름 기반 광역 kill 금지 | **좁아짐** — 스냅샷의 실행 파일 이름 필드를 아예 읽지 않는다 |
| `windowsHide` | 유지 |
| `shell: true` 금지 | 유지 |
| — | **추가** — 루트 PID 가 양의 정수가 아니면 스크립트 생성 자체를 거부 |

## A-3. 결과 (동일 조건 paired, 자손 6개 트리)

| | `terminate()` | `terminatedPids` | 자손 생존 | 루트 |
|---|---|---|---|---|
| taskkill | 4693 / 4428 / 5036 / 4628 ms | `[루트 1개]` | 0 / 6 | 사망 |
| toolhelp | **3399 / 3390 / 3036 / 3124 ms** | **`[자손 6 + 루트 = 7개]`** | 0 / 6 | 사망 |

속도 외에 **보고가 정직해졌다.** `PERF-BGSTAB-013` AC-6 으로 Windows 가 자손을
표본 수집하지 않게 되면서 `terminatedPids` 가 루트 하나만 담고 있었는데,
이제 스크립트가 실제로 종료한 PID 를 그대로 보고한다.

## A-4. 기각한 대안 둘 (실측)

- **루트만 종료**: 자손이 살아남는다 — 2개 중 1개, 3회 중 3회.
- **node-pty 의 콘솔 프로세스 목록**: **자손 트리가 아니다.** 살아 있는 conpty
  세션에서 `[조회 에이전트 PID, 셸 PID]` 를 반환했고 실제 자손 2개는 빠졌다.
  이것을 썼다면 프로세스가 조용히 새어 나갔을 것이다.

## A-5. 남은 비용

교체 후 Windows 경로의 약 1.4–1.6초는 kill 스크립트이고, 그중 **약 0.82초가
`Add-Type` 의 C# 컴파일**, 약 0.41초가 PowerShell 기동, 실제 열거·종료는 약 0.2초다.
없애려면 헬퍼 어셈블리를 미리 빌드해 싣거나(패키징된 exe 에서 DLL 을 쓰고 로드하는
경로가 생긴다) 상주 PowerShell 워커를 두어야 한다. **둘 다 보안 표면을 넓히므로
성능만을 이유로 하지 않는다.**

## A-6. 되돌리기

`buildWindowsProcessTreeKillScript` 를 쓰는 `terminateWindowsTree` 한 함수만
`taskkill.exe /PID <root> /T /F` 로 되돌리면 이전 동작이다. `method` 문자열
`windows-verified-tree-kill` 도 함께 되돌려야 한다.

## A-7. 가드가 또 주석을 코드로 읽었다

`no-broad-kill` 가드가 이번에는 "이름을 받는 cmdlet 을 쓰지 않는다" 고 적은
주석의 cmdlet 이름 자체를 위반으로 잡았다. 같은 날 두 번째다(연구 부록 B-2).
주석 문구를 바꿔 해소했고, 근본 수정(주석 제거 후 스캔)은 다른 레인에 이미
구현이 있어 중복 작성하지 않았다.

# 부록 2 — 남긴 것 둘을 닫음 (2026-09-21)

§A-5 와 §A-7 이 남긴 두 항목을 사용자 지시로 처리했다.

## B-1. `Add-Type` 0.82초 — 측정으로 닫음 (변경 없음)

§A-5 는 대안이 보안 표면을 넓힌다는 이유로 미뤘다. 미루기 전에 재지 않은
후보가 하나 있었고, 재보니 **더 나쁘다.**

| 후보 | 실측 |
|---|---|
| `Get-Counter '\Process(*)\ID Process','\Process(*)\Creating Process ID'` | 5991ms / **실패** / **실패** |
| `PerformanceCounterCategory('Process').GetInstanceNames()` | 9178ms (cold) / 133ms (warm) |
| 현행 `Add-Type` + toolhelp | 819ms 컴파일 + 63–78ms 열거 |

성능 카운터 경로는 3회 중 2회가 "카운터 데이터가 잘못되었습니다" 로 실패했다.
WMI 를 피하려다 더 느리고 더 불안정한 것으로 바꾸는 셈이다. **기각.**

남은 두 대안(미리 빌드한 헬퍼 어셈블리, 상주 PowerShell 워커)은 여전히
보안 표면을 넓히므로 하지 않았다. **0.82초는 PowerShell 경로의 현실적 하한이다.**

한 가지 더 검토하고 하지 않은 것: kill 후 검증을 kill 스크립트에 합치면
PowerShell 기동 1회(약 0.35초)를 아낄 수 있다. 하지 않은 이유는 성능이 아니라
**독립성**이다 — 지금 kill 후 검증은 종료를 수행한 주체와 무관한 관측이다.
스크립트가 자기 성공을 스스로 보고하게 만들면 스크립트가 중간에 죽거나
거짓을 말할 때 그것을 잡을 수단이 사라진다.

## B-2. `no-broad-kill` 가드 — 근본 수정 (`OPS-BGSTAB-011`)

가드가 스캔 전에 주석을 제거한다. JS/TS 의 라인·블록 주석과 배치의 `REM`·`::`
을 길이를 보존한 채 공백으로 바꾼 뒤 금지 패턴을 매칭한다.

**문자열과 템플릿 리터럴은 보존한다.** 문자열에 담긴 광역 kill 명령은 산문이
아니라 코드이므로 계속 잡혀야 한다.

주석 제거는 가드를 약화시킬 수 없지만(주석 속 kill 은 kill 이 아니다) 부주의한
제거기는 실제 코드를 지워 **거짓 음성**을 만든다. 그래서 대조군이 안전장치다:

| 대조군 | 기대 |
|---|---|
| `execSync('taskkill /IM node.exe /F')` 등 금지 형태 6종 | 전부 검출 |
| 문자열 안의 `//` 가 뒤 코드를 지우지 않는가 (`'http://x'` + 실제 호출) | 검출 |
| 템플릿 리터럴 안의 `http://` + 실제 호출 | 검출 |
| 같은 문구가 주석일 때 (라인·블록·JSDoc·배치 REM/::) | 미검출 |
| 주석 **다음 줄**의 실제 호출 | 검출, 행 2로 보고 |
| 길이·행 수 보존 | 동일 |

**변이로 양방향 확인했다.** 스캔 대상 `tools/daemon/log.js` 에
`execSync('taskkill /IM node.exe /F')` 를 주입하자 3개 패턴이
`tools/daemon/log.js:107` 로 잡혔고, 같은 문구를 주석으로만 주입하자 5/5 통과했다.
파일은 diff 없이 복구했다.

부수 효과로 **위반 보고에 행 번호가 붙는다.** 이전에는 문자 스니펫만 나와
어디인지 찾아야 했다(CLAUDE.md 가 2026-09-18 에 같은 지적을 남겼다).

그리고 이번 수정으로 `processTreeTerminator.ts` 의 주석 두 곳을 **원래 표현으로
되돌렸다** — 가드를 피하려고 `taskkill`·`node-pty`·`Stop-Process` 를 돌려 말하던
문장들이다. 규칙을 다루는 파일에서 규칙을 모호하게 적게 만드는 압력이 없어졌다.

§A-7 이 "다른 레인에 이미 구현이 있어 중복 작성하지 않았다" 고 적은 판단은
사용자 지시로 뒤집었다. 그 레인의 구현은 다른 가드(`packaged-import-meta-guard`)
를 위한 것이고, 이쪽은 CJS 자체 완결 헬퍼다.
