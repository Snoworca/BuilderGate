# S5-a 정책 키 재귀속 · 정책 단정 보강

## 이슈 설명

설계 SSOT 『`docs/research/binary-comms/06-work-plan.md` #### S5-a.』 의 지시에 따라 fair delivery credit 회계 도메인 전환을 검증하는 테스트 스위트를 보강했습니다. `PERF-BGSTAB-010` AC-4 와 `PERF-BGSTAB-011` AC-8 에서 요구하는 회계 정확성을 재측정하기 전에, 기존 테스트 커버리지를 먼저 확장하는 것이 이번 작업의 범위입니다.

## 문제 원인

`server/src/services/TerminalResourcePolicy.test.ts` 의 policy projection 테스트가 다음과 같은 약점을 가지고 있었습니다.

- 아홉 개 키의 **값**은 모두 대조했으나 **키 집합 자체**는 단정하지 않았습니다. 값 여섯 개만 대조하던 상태는 앞선 커밋 `3bc3111` 에서 이미 해소되었으므로, 이번 커밋이 남긴 구멍은 키 집합과 `source` 두 가지입니다.
- `source` 필드는 빈 문자열이 아닌지만 확인했으므로, 실제 내용이 무엇인지는 검증하지 않았습니다.

그 결과 resolver 에 열 번째 키가 생겨도, `source` 가 엉뚱한 resource limit 으로 귀속되어도 어떤 테스트도 깨지지 않았습니다. 특히 `source` 필드는 회계 기반을 나타내기 때문에 이 검증 누락은 AC-4 와 AC-8 의 재측정 신뢰도를 해쳤습니다.

## 해결 방법

설계 SSOT 의 `[설계결정]` 지시는 번호가 붙은 세 항목입니다. 그중 첫째, 곧 `strategy` 와 `visibilityWeight` 와 `driverWeight` 의 **값**을 `deepEqual` 대상에 추가하는 것은 앞선 커밋 `3bc3111` 에서 이미 이행되었습니다. 따라서 이번 커밋이 이행한 것은 둘째와 셋째입니다.

**키 집합 단정 추가**

```typescript
assert.deepEqual(
  Object.keys(projection).sort(),
  [
    'ackTimeoutMs',
    'bulkSliceBytes',
    'creditWindowBytes',
    'driverWeight',
    'queueMaxBytes',
    'smallOutputBypassBytes',
    'socketSoftGateBytes',
    'strategy',
    'visibilityWeight',
  ],
  signature,
);
```

키가 늘거나 줄면 즉시 red 가 되도록 했습니다.

**source 필드 리터럴 대조**

```typescript
assert.deepEqual(
  Object.fromEntries(Object.entries(projection).map(([key, value]) => [key, value.source])),
  {
    strategy: 'fair-scheduler-decision.json#candidate',
    socketSoftGateBytes: 'resourceLimits.ws.serverBufferedHighWaterBytes',
    bulkSliceBytes: 'resourceLimits.ws.perClientOutputQueueMaxBytes',
    smallOutputBypassBytes: 'resourceLimits.ws.perClientControlQueueMaxBytes',
    visibilityWeight: 'resourceLimits.ws.perClientControlQueueMaxBytes',
    driverWeight: 'resourceLimits.ws.perClientOutputQueueMaxBytes',
    creditWindowBytes: 'resourceLimits.ws.perClientOutputQueueMaxBytes',
    ackTimeoutMs: 'ws.terminal-delivery.ack-timeout',
    queueMaxBytes: 'resourceLimits.ws.perClientOutputQueueMaxBytes',
  },
  signature,
);
```

아홉 개 `source` 를 한 번의 `deepEqual` 로 리터럴 객체와 대조합니다. 모든 기대값은 손으로 적은 리터럴이며, resolver 를 다시 호출하지 않았습니다.

**삭제된 단정**

```javascript
Object.values(projection).every(value => value.source.length > 0)
```

이 줄을 제거했습니다. 새로운 리터럴 단정이 모든 키의 `source` 를 비어 있지 않은 값과 대조하므로 그 조건을 포함하며, 그 위에 값과 키 집합까지 고정합니다.

## TDD 경과

red 를 두 단계로 나누어 확인했습니다.

1. 키 집합 단정만 추가하고 `strategy` 를 의도적으로 빠뜨린 채로 돌려 키 집합 단정이 실패하는 것을 보았습니다.
2. 키 집합을 맞춘 뒤, `source` 리터럴 단정에서 `strategy` 와 `visibilityWeight` 를 틀리게 둔 채로 돌려 source 단정이 실패하는 것을 따로 보았습니다.
3. 둘을 모두 정정해서 green 으로 만들었습니다.

## 재벤치 구성 기록

SSOT 는 재측정에 앞서 한도 구성과 `wsSendMode` 를 고정해 기록할 것을 요구했습니다. 확인한 사실은 다음과 같습니다.

- `server/config.json5` 에는 `serverBufferedHighWaterBytes` · `perClientOutputQueueMaxBytes` · `perClientControlQueueMaxBytes` · `outputCoalesceWindowMs` · `serverBufferedHardLimitBytes` 다섯 키가 하나도 없습니다. 따라서 재발행된 아티팩트의 policy 값은 전부 스키마 기본값에서 유도된 것입니다.
- `server/config.json5:96` 에 `wsSendMode: "safe-send-enforce"` 가 있습니다. 이것은 스키마 기본값인 `direct` 가 아닙니다.
- 기본값에서 `smallOutputBypassBytes` 는 32,768 이므로 40 바이트 청크의 봉투값 356 도 본문값 40 도 모두 임계 아래입니다.
- `server/config.json5` 은 gitignored 이므로 이 전제는 다른 설치본에서 달라질 수 있습니다.

## 아홉 키의 처분 현황

SSOT 의 `PERF-BGSTAB-011` AC-8 은 처분을 다섯 더하기 셋 더하기 하나로 나눕니다.

- 재귀속 대상 세 개(`strategy` · `visibilityWeight` · `driverWeight`)는 앞선 커밋 `3bc3111` 의 authority generation 재발행으로 새 아티팩트에 실렸습니다.
- 바이트 다섯 개 가운데 `bulkSliceBytes` 의 배치 상한 역할은 와이어 바이트 도메인이라 `binary-optin` 이후로 유예됩니다. 나머지는 JSON 상태에서 재측정되었습니다.
- `ackTimeoutMs` 는 값 5,000 그대로입니다.

## 보고만 한 발견

### SSOT 서술의 낡음

`docs/research/binary-comms/06-work-plan.md` 의 `#### S5-a.` 절이 이 스위트를 여섯 키만 대조한다고 기술하고 있으며, `strategy` 와 `visibilityWeight` 와 `driverWeight` 가 회귀 게이트 밖이라고 기재하고 있습니다. 그러나 이 세 키는 앞선 커밋 `3bc3111` 에서 이미 리터럴로 단정되었으므로 그 서술은 현 상태에 맞지 않습니다. 문서 갱신은 이 범위 밖입니다.

### 정책 타입의 중복 아키텍처

정책 타입이 두 벌 존재합니다.

- `server/src/ws/wsSendPolicy.ts` 의 `FairTerminalDeliveryPolicy`
- `server/src/services/TerminalResourcePolicy.ts` 의 `FairTerminalDeliveryPolicyProjection`

이 둘은 구조적으로 같으며, `FairTerminalDeliveryPolicyValue` 도 두 곳에 각각 선언되어 있습니다. SSOT 자신이 이것을 중복 아키텍처 후보로 지목하면서 이번 범위 밖이라고 명시했습니다. 해결은 향후 작업입니다.
