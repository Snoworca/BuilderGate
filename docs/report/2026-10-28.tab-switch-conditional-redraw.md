# 탭 전환 흔들림 수정과 다른 기기 크기 변경 뒤 다시 그리기 (#191)

## 개요

이 보고서는 탭을 전환할 때마다 터미널 화면이 위아래로 흔들리던 문제(#191)를 고친 결과를 기록한다. 작업 중 사용자 확인으로 관련 문제 두 가지가 더 드러났고, 같은 작업에서 함께 고쳤다.

- 요구사항: REL-BGSTAB-058(신설, REL-BGSTAB-050 승계), REL-BGSTAB-011 AC-6(결함 수정)
- 브랜치: `fix/tab-switch-conditional-redraw`(main `b98ab6f7` 기준)
- 작업일: 2026-10-28

## 문제 1: 탭을 전환할 때마다 화면이 흔들림 (#191)

### 증상

탭을 옮길 때마다 터미널 안의 화면(예: Claude Code)이 위아래로 한 번씩 움직였다.

### 문제 원인

- 탭 전환 뒤 자동 다시 그리기(REL-BGSTAB-053 AC-4)가 탭을 옮길 때마다 크기 흔들기(redraw nudge)를 보냈다.
- 크기 흔들기는 PTY를 `rows-1`로 줄였다가 200ms 뒤 `rows`로 되돌린다(REL-BGSTAB-047). 그러면 프로그램이 두 번 다시 그리므로 화면이 움직인다.
- 크기 흔들기가 실제로 필요한 경우는 터미널이 가려져 있던 동안 다른 화면이나 기기가 PTY 크기를 바꾼 경우뿐이다. 이때만 프로그램이 다른 크기에 맞춰 그렸을 수 있다.

### 해결 방법

탭 전환 자동 다시 그리기는 끄지 않았다. 이 기능을 쓰던 사용자에게 동작이 사라지지 않도록, 화면이 어긋났을 수 있을 때만 크기를 흔들게 했다.

- 서버는 PTY 크기를 실제로 바꿀 때마다 그 세션의 구독자에게 `session:resized(cols, rows)`를 보낸다. 같은 크기 요청이나 거부된 요청에는 보내지 않는다. (AC-2)
- 각 터미널은 자기가 최근에 보낸 크기 4개를 기억한다. 그 목록에 없는 크기가 오면 "다른 곳에서 크기가 바뀜"으로 기록하고, 크기를 흔들면 기록을 지운다. (AC-3)
- 탭 복귀와 탭 전환 자동 다시 그리기는 이 기록이 있을 때만 크기를 흔든다. 기록이 없으면 레이아웃 맞춤과 화면 복구만 한다. (AC-4)
- 메뉴의 '화면 다시 그리기', 다시 그리기 단축키, 워크스페이스 전환은 지금처럼 항상 크기를 흔든다. (AC-5)
- REL-BGSTAB-050(탭 보기에서 보일 때마다 크기 흔들기)은 REL-BGSTAB-058로 승계하고 discarded로 바꾸었다.

## 문제 2: 다른 기기에서 크기를 바꾼 뒤 데스크톱으로 돌아와도 바로 다시 그리지 않음

### 증상

아이폰에서 같은 세션의 크기를 바꾼 뒤 데스크톱으로 돌아오면, 다른 탭을 다녀와야만 화면이 바로잡혔다.

### 문제 원인

- 데스크톱의 그 탭은 계속 보이는 상태였으므로, "다시 보이게 됨"을 계기로 하는 다시 그리기가 일어나지 않았다.
- 디버그 기록을 보면 `session:resized`는 데스크톱에 도착했다(`resize_from_elsewhere_recorded`). 그러나 아이폰을 쓰는 동안 데스크톱 창은 포커스를 잃지 않으므로, 처음 넣은 focus·visibilitychange 계기도 발생하지 않았다.

### 해결 방법

창 focus, visibilitychange에 더해, 그 페이지에서 일어나는 마우스 움직임·누르기·키 입력도 "돌아옴"의 신호로 삼았다. 기록이 있으면 터미널이 자기 크기를 다시 보내고 크기를 흔들어 다시 그린다. 기록은 바로 지우므로, 계속 움직이는 마우스가 다시 그리기를 반복시키지 않는다. 사용자가 손대지 않는 화면은 크기를 되돌리지 않으므로, 마지막으로 사용한 화면의 크기가 남는다. (AC-8)

## 문제 3: 아이폰에서 입력한 뒤 데스크톱의 입력과 크기 변경이 모두 거부됨 (REL-BGSTAB-011 AC-6)

### 증상

문제 2를 고친 뒤에도, 아이폰에서 입력한 다음 데스크톱에서 마우스를 움직이면 "입력이 전달되지 않았습니다 n건" 토스트만 뜨고 화면은 다시 그려지지 않았다.

### 문제 원인

사용자가 저장해 준 디버그 기록(세션 `e30ae64c`)에서 순서를 확인했다.

| 시각(UTC) | 기록 |
|---|---|
| 05:46:19.841 | 아이폰 크기 57×16을 "다른 곳에서 바뀜"으로 기록 |
| 05:46:23.808 | 마우스 움직임으로 데스크톱 크기 154×47을 다시 보내고 다시 그리기 시작 |
| 05:46:23.810~24.064 | 서버가 크기 변경 3건을 모두 `invalid-message`로 거부 |
| 05:46:23.818 이후 | 마우스를 움직일 때 터미널 안 프로그램에 보내는 마우스 위치 입력 234건 중 232건을 `target-identity-stale`로 거부 |
| 05:46:24.125 | PTY가 아이폰 크기 그대로여서 화면 복구가 `geometry-mismatch`로 실패 |

- 서버는 세션마다 입력 권한(driver lease)을 한 화면에만 준다. 입력한 화면이 권한을 가져간다.
- 아이폰에서 입력하자 권한이 아이폰으로 넘어갔다. 그러나 데스크톱은 무효가 된 권한을 입력과 크기 변경에 계속 붙여 보냈다.
- 서버에는 권한을 다시 가져오는 재시도 경로가 있었지만, 그 경로는 입력 메시지에 권한이 없어서 서버가 연결 캐시에 저장한 권한을 쓴 경우에만 동작했다. 그런데 실제 브라우저는 `attachRetainedMutationLease`로 입력과 크기 변경에 권한을 항상 직접 붙이므로, 이 경로를 타지 않았다. 크기 변경에는 재시도 경로 자체가 없었다.
- 탭을 옮기면 화면이 새로 등록되면서 권한을 다시 얻으므로, 그때만 바로잡혔다.

### 해결 방법

`server/src/ws/WsRouter.ts`를 고쳤다.

- 입력: 브라우저가 붙인 권한이 `target-identity-stale`로 거부되었고 그 권한이 지금 등록된 화면(같은 viewGeneration)의 것이면, 권한을 다시 가져와 한 번 재시도한다.
- 크기 변경: 같은 조건에서 권한을 다시 가져와 한 번 재시도한다.
- 두 경우 모두 새 권한을 capability 메시지로 브라우저에 알린다. 이전 화면(오래된 viewGeneration)이 보낸 권한은 지금처럼 거부한다.

`WsRouter.ts`는 authority 봉인 소스이므로 build → publish → build 순서로 authority를 다시 발행했다. 새 generation은 `eb3296ec…`이고, 발행 출력의 `codec under measurement`가 `binary`인 것을 확인했다.

## 한계

- 두 기기를 번갈아 쓰면 입력 권한과 PTY 크기가 마지막으로 사용한 화면을 따라 오간다. 이것은 의도한 동작이다.
- 메모리 사용은 코드 구조로만 판단했고 장시간 실측하지 않았다. 추가한 상태는 터미널마다 크기 4개와 참/거짓 값 하나이고, 리스너는 터미널이 떨어질 때 해제된다.
