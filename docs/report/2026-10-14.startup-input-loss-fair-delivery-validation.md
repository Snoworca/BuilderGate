# 페이지를 연 직후 입력이 사라지던 문제 수정 보고서

- 날짜: 2026-10-14
- 요구사항: PERF-BGSTAB-010 (AC-3)
- 관련: 같은 날의 `2026-10-14.binary-channel-retired-unsubscribed.md` 에서 남은 사항으로 기록한 문제

## 1. 이슈

터미널을 많이(40개) 연 상태에서 페이지를 열고 바로 글자를 치고 Enter 를 누르면, 입력이 서버로 가지
않고 사라졌다. 새로고침해도 그 입력은 보이지 않았다.

## 2. 재현

- 2222 포트의 이 체크아웃 서버(WSL), 워크스페이스 4개에 터미널 40개.
- 로그인 직후 터미널이 보이자마자(약 0.4~0.7초) `echo <고유 표식>` 과 Enter 를 입력했다.
- 수정 전: 3회 모두 실패. 보이는 세션이 입력을 받을 수 있게 된 시각은 4.35~4.95초였다. 입력 13개가
  모두 버려졌고, Enter 는 `timeout-enter-safety` 로, 나머지는 `timeout` 으로 버려졌다.

## 3. 원인

1. 브라우저는 연결하자마자 `terminal-delivery:capability` 를 한 번 보낸다.
2. 서버는 이 메시지를 처리하면서 공개된 fair-delivery 증거 산출물을 디스크에서 처음부터 검증했다
   (`validatePublishedFairDeliveryCandidateArtifact`). 파일 탐색, `realpath`, 링크 검사, 해시 계산을
   **동기로** 수행한다.
3. CPU 프로파일로 측정한 결과, 이 검증 한 번에 WSL `/mnt/c` 에서 약 4초가 걸렸다. Windows 에서는
   약 150~175ms 였다. 그동안 서버의 이벤트 루프가 막혀, 이미 준비된 화면 스냅샷 40개도 나가지
   못했다. 구독 처리 자체(`handleSubscribe`)는 21ms 였다.
4. 브라우저는 복원이 끝날 때까지 입력을 큐에 담는다. 큐의 TTL(`inputQueueTtlMs`, 기본 1500ms)이
   지나면 입력을 버린다. 이 TTL 은 오래된 Enter 가 늦게 실행되지 않게 하려는 의도된 안전장치다.
5. 따라서 복원이 1.5초보다 늦어지면 입력이 버려졌다.

## 4. 해결

| 파일 | 변경 |
| --- | --- |
| `server/src/services/TerminalResourcePolicyCanary.ts` | 기본(정준) resolver 로 만든 검증기는 승인 결과를 캐시한다. 키는 runtime policy 다이제스트와 authority 지문이다. 지문은 `current.json` 의 바이트와, 현재 세대 디렉터리의 모든 항목에 대한 `lstat`(mode·size·mtimeNs·ctimeNs·ino)이다. 지문이 바뀌면 디스크에서 다시 검증한다. 거절 결과는 캐시하지 않는다. resolver 를 주입한 경우에는 캐시하지 않는다. |
| `server/src/ws/WsRouter.ts` | `warmFairDeliveryArtifactValidation()` 를 추가했다. capability 처리와 같은 runtime policy 로 검증을 미리 실행한다. |
| `server/src/index.ts` | `WsRouter` 를 만든 직후, 리스너를 열기 전에 위 예열을 호출한다. 승인되지 않으면 경고를 남긴다. |

AC-3(산출물이 없거나 불완전·변조·이탈이면 승격 금지)은 그대로 지킨다. 포인터나 세대 파일을 고치거나,
더하거나, 지우거나, 링크로 바꾸면 지문이 바뀌고 다음 연결에서 다시 검증한다.

입력 큐의 TTL 은 바꾸지 않았다. 큐 만료 시 토스트를 띄우는 것도 하지 않았다. REL-BGSTAB-016 AC-4 가
`observe` 가 아닌 모드에서 그 토스트를 금지하기 때문이다.

## 5. 성능 확인

새 연결 한 번당 서버 이벤트 루프가 막히는 시간이다.

| 환경 | 수정 전 | 수정 후 첫 호출(기동 시 예열) | 수정 후 이후 호출 |
| --- | --- | --- | --- |
| Windows | 150~175ms | 175ms | 약 1.5ms |
| WSL `/mnt/c` | 3.6~4.5초 | 4.5초 | 약 180ms |

첫 호출은 기동 시 예열이 맡으므로, 브라우저 연결은 캐시된 결과를 쓴다. 성능이 나빠지는 경로는 없다.

## 6. 테스트

TDD 로 진행했다. 테스트를 먼저 쓰고, 수정 전에 실패하는 것을 확인했다.

- `server/src/services/TerminalResourcePolicyCanaryCache.test.ts`(신규, 11건)
  - 캐시 재사용, 지문 변경 시 재검증, runtime policy 별 분리, 거절 미캐시, 지문 불가 시 매번 검증.
  - 지문의 안정성, 파일 수정·추가·포인터 변경·링크 교체 시 지문 변경, 포인터 없음.
  - 링크 교체 1건은 Windows 에서 심볼릭 링크 권한이 없어 건너뛰었다.
- `server/src/ws/terminalBinaryRollback.test.ts` — 기동 시 예열 메서드 1건.
- `TerminalResourcePolicyCanary.test.ts` 전체 통과. 기본 검증기가 인자 없는 정준 팩토리의 결과여야
  한다는 구조 가드도 통과한다.
- 서버 모놀리식 러너 533 통과.
- authority 를 재발행했다(build → publish → build, 세대 `4c6d6422…`).

실제 브라우저 확인(2222, 터미널 40개):

| 조건 | 보이는 세션 준비 시각 | 버려진 입력 | 결과 |
| --- | --- | --- | --- |
| 수정 전 3회 | 4.35~4.95초 | 13 | 3/3 실패 |
| 수정 후 3회 | 0.56~0.73초 | 0 | 3/3 통과 |

40탭 워크스페이스 이동 재현(대기 없음)도 2회 48/48 통과, 거절 프레임 0 이다.

## 7. 남은 사항

- `tools/wave3/canary-admission-evidence.test.mjs` 의 GREEN 증거는 이 작업 전부터 낡아 있었다. 이
  작업에서 건드리지 않은 `TerminalResourcePolicy.ts`·`RuntimeConfigStore.ts`·`SessionManager.ts` 의
  해시도 어긋나 있었다. `--regenerate-green` 으로 다시 만들었다. 바뀐 것은 해시와 `capturedAt` 뿐이고,
  판정(`PASS_FAIL_CLOSED_CANDIDATE_UNAVAILABLE`)은 같다. 플래그 없이 다시 돌려도 통과한다.
- 복원이 1.5초를 넘기는 다른 원인(예: 아주 느린 네트워크)이 생기면, 큐 입력은 여전히 알림 없이
  만료될 수 있다. 이를 바꾸려면 REL-BGSTAB-016 AC-4 를 먼저 개정해야 한다.
