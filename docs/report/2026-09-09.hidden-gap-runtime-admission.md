## Change

The existing runtime owns admission and recovery ordering through `admitHiddenDataGap(message, context)`. Context is a separate trusted in-process input, not copied from the incoming message. Current session/connection/installed-view identity and canonical gap fields are checked before mutation. Active capability without an established checkpoint or pending recovery rejects as authority-unavailable. Existing `laterBoundary` and `failClosed` implement the monotonic checkpoint failure boundary; no new epoch allocator or visibility history was added.

Equal or older visibility generations may describe committed loss, including a gap crossing a reveal publication. Future/absent visibility cannot supply a new failure boundary; the runtime retains existing-identity recovery protection. An older epoch boundary is rejected. The owner callback runs before the fresh recovery request. Callback absence rejects with existing recovery protection; callback exceptions remain observable. Successful notification stores one immutable value identity, so exact duplicates during pending recovery do not notify/request again and caller mutation cannot alter the saved identity.

The new optional owner callback has not been connected to production View/Context yet. Existing generic failSession behavior and the separately implemented recoveryAccepted field remain unchanged. The new method is therefore a prepared dependency, not an enabled replacement for raw gap routing.
