# issue #16 항목 5 — 렌더러 수명주기와 사용자 스크롤 (브라우저 절반)

- 날짜: 2026-09-19
- 요구사항: FR-BGSTAB-029
- 범위: 항목 5 의 다섯 시나리오 중 브라우저가 필요한 **넷**. 다섯째(reset/reflow)는
  `docs/report/2026-09-19.issue-16-selection-lifecycle-reset-reflow.md` 가 다룬다.

## 결과 — 넷 다 건전하다

이것을 먼저, 분명히 적는다. 같은 항목의 단위 절반이 결함 셋을 냈으므로, 아무도
반대로 말하지 않으면 **이쪽도 깨져 있으리라는 기대가 공짜로 따라붙는다.** 실측
결과는 반대다.

| 시나리오 | 결과 |
| --- | --- |
| hide/reveal | 선택이 양방향 렌더러 교체를 견딘다 |
| DOM fallback | 이 앱에서 hide/reveal 과 같은 사건이다(아래) |
| WebGL context loss | 선택이 실제 컨텍스트 소실을 견딘다 |
| 출력 중 user-scroll | 파킹된 뷰와 그 위의 선택이 계속 도착하는 출력을 견딘다 |

## 대조군이 없으면 "살아남았다"는 아무 말도 아니다

렌더러가 실제로 교체되지 않았다면 선택이 살아남은 것은 성질에 대한 진술이 아니다.
그래서 각 테스트는 **교체가 일어났음을 구성으로** 먼저 단언한다 — xterm 의 WebGL
렌더러는 `<canvas>` 에 그리고 행 단위 DOM 을 만들지 않으며, DOM 렌더러는 행마다
div 를 만들고 canvas 를 만들지 않는다. 이름이 아니라 그 구조가 렌더러의 정체다.

## 시나리오별 실측

### hide/reveal — 그리고 DOM fallback 은 같은 사건이다

#15 가 **보이는 동안에만** WebGL addon 을 붙이므로, 탭을 숨기면 컨텍스트가 해제되고
그 뷰는 DOM 렌더러로 떨어지며, 되살리면 다시 붙는다. 즉 이 앱에서 hide/reveal 은
양방향 렌더러 교체이고 DOM fallback 은 그 절반이다.

실측: `canvases 3 / domRows 0` → `0 / 28` → `3 / 0`. 선택은 세 지점 모두에서 같은
마커 텍스트를 유지한다.

### WebGL context loss

`WEBGL_lose_context` 로 **실제 컨텍스트를 빼앗는다.** 핸들러가 등록되어 있는지
확인하는 형태의 테스트였다면 한 번도 검증된 적 없는 fallback 위에서 green 이
되었을 것이다.

선택은 살아남는다. 그리고 fallback 이 **빈 화면이 아니라 재도색**이라는 증거로,
WebGL 이 붙어 있는 동안 DOM 에 전혀 없던 마커가 손실 후 DOM 에 나타난다 — 그
등장 자체가 증거이지 잔존물이 아니다.

### 출력 중 user-scroll — 첫 시도가 틀렸고, 그 틀림이 유익하다

처음에는 위로 스크롤한 뒤 출력을 내는 명령을 **타이핑**했다. 화면이 맨 아래로
돌아왔고, 이것은 결함처럼 보인다. 아니다 — `scrollOnUserInput` 이 제 일을 한
것이다. 사용자가 타이핑했으므로 맨 아래로 가는 것이 옳다.

항목 5 가 묻는 것은 **타이핑 없이 출력이 도착하는 동안의** 스크롤이다. 그래서
생산자를 먼저 띄우고 그 뒤로는 아무것도 타이핑하지 않는다. 그러면 뷰는 생산자
이전 출력(`SEED-*` 구간)에 머무르고, 1.5초·3초·5초 동안 계속 도착하는 출력에도
그 자리를 지키며, 그 화면에서 드래그한 선택도 그대로다.

**대조군**: 휠 스크롤이 뷰를 실제로 `SEED-*` 구간으로 옮겼음을 먼저 단언한다.
스크롤이 아무것도 하지 않았다면 그 뒤의 "여전히 파킹되어 있다"는 전부 공허하다.

### bare Enter — 예측을 먼저 적고 측정했다

FR-BGSTAB-029 의 2026-09-19 change note 는 "빈 프롬프트에서 Enter 한 번이면 선택이
사라진다"를 근거로 부분 트림 AC 를 철회했다. 그 관측은 `captureTerminalSelection`
이 생기기 전에 이루어졌고, **같은 날 선택을 엉뚱한 이유로 파괴하는 헬퍼 결함 두
개**가 발견되었다(무조건 클릭, 등록되지 않는 드래그). 즉 철회는 자기 부작용과
제품 동작을 구별할 수 없는 계측기로 내린 관측 위에 서 있었다.

**예측(측정 전에 기록함)**: Enter 는 선택을 지울 것이고, 따라서 철회 사유는 옳다.

**실측**: 빈 프롬프트에서, 경로에 클릭이 하나도 없이, Enter 한 번이 선택을 지운다.
예측대로다. 철회 사유는 유효하며 헬퍼 결함의 산물이 아니다. 되돌릴 것이 없다.

전제 셋을 함께 단언한다 — 이것이 "무언가가 지웠다"를 "Enter 가 지웠다"로 바꾼다.

1. 뷰포트가 안정되어 셸이 idle 이다. 생산자가 도는 중에 보낸 Enter 는 빈 프롬프트의
   Enter 가 아니라 실행 중인 프로그램의 stdin 으로 가는 Enter 다. 이를 위해 생산자
   길이를 30초에서 12초로 줄였다.
2. Enter 직전까지 선택이 살아 있다. 이미 사라진 것을 Enter 탓으로 돌리지 않는다.
3. **클릭 없이 이미 포커스가 있다.** 클릭 자체가 선택을 지우므로, 이 전제를 단언
   하지 않으면 철회를 무효화했던 바로 그 결함이 철회를 검증하는 실험에 다시 들어온다.

## 변이 검증

**14회, 생존 0.** 스크롤 테스트의 셋은 bare Enter 추가로 테스트가 바뀌었으므로
승계하지 않고 **다시 증명했다** — 바뀐 테스트에 대한 옛 kill 은 다른 테스트에 대한
증거다.

| 테스트 | 변이 |
| --- | --- |
| hide/reveal | 숨김 중 선택이 사라졌다고 주장 |
| hide/reveal | reveal 후 기대 선택 텍스트 훼손 |
| hide/reveal | **숨겨진 뷰가 여전히 GPU 컨텍스트를 들고 있다고 주장(교체 대조군 파괴)** |
| context loss | 죽인 컨텍스트 수 하한을 달성 불가능하게 상향 |
| context loss | 컨텍스트와 함께 선택도 죽는다고 주장 |
| context loss | DOM fallback 이 내용을 화면에 올리지 않는다고 주장 |
| user-scroll | **휠 스크롤이 뷰를 생산자 출력에 남겼다고 주장(스크롤 대조군 파괴)** |
| user-scroll | 기대 파킹 행 훼손 |
| user-scroll | 도착하는 출력이 파킹된 선택을 파괴한다고 주장 |
| user-scroll | bare Enter 가 선택을 살려둔다고 주장 |
| user-scroll | **터미널에 포커스가 없다고 주장(클릭 없음 전제 파괴)** |

굵은 셋이 중요하다. 이들은 *주장*이 아니라 **설정 자체가 실패할 수 있는지**를
시험한다. 주장만 변이시키는 스위트는 자신이 무언가를 측정하고 있었는지 말해줄 수
없다.

## 과정에서 나온 것 — 도구가 아니라 판단에 관한 것들

### 게이트를 통과했다는 것은 게이트가 작동한다는 증거가 아니다

2222 에 대한 E2E 게이트를 "established 연결 수가 0" 으로 두었다. 네 번의 실행이
모두 통과했다. 그러나 사용자 브라우저 탭 하나가 `https://localhost:2222` 를 열어
두면 WebSocket 이 무기한 유지되어 그 수는 0 으로 돌아오지 않는다 — 즉 이 신호는
**동료 레인과 사용자를 구별하지 못한다.** 네 번의 통과는 우연히 0 이었던 네
순간이었지, 검사가 건전하다는 증거가 아니었다.

### 안전 검사의 논리곱은 가장 취약한 항만큼만 쓸 수 있다

내 preflight 는 연결 수와 프로세스 존재를 **둘 다** 요구했다. 프로세스 검사는
옳았고 연결 수 검사는 틀렸는데, 논리곱이었으므로 **옳은 검사가 틀린 검사에 가려
졌다.** 안전 검사를 쓸 때의 본능은 조건을 *더하는* 것이지만, 더한 조건 하나하나가
더 많은 안전이 아니라 오작동할 자리 하나씩이다.

### 자기 자신을 매칭하는 pgrep 은 하루에 두 번, 정반대 증상으로 나타났다

명령줄에 패턴 자체가 들어 있는 `pgrep` 검사는 자기 프로세스를 찾는다. 처음에는
**끝나지 않는 watcher** 로 나타났고(상대 레인은 한참 전에 끝나 있었다), 두 번째는
**진행했어야 할 실행을 중단시키는 preflight** 로 나타났다. 증상이 정반대라 누구도
둘을 같은 버그로 묶지 않는다. 그리고 두 번 다 겉보기 동작이 결함이 아니라 미덕으로
읽힌다 — 인내, 그리고 신중.

해법은 더 영리한 패턴이 아니라 **검사기를 자기 결과에서 걸러내는 것**(`| grep -v
pgrep`)이다. 대괄호 트릭(`playwright[ ]test`)은 같은 명령줄 어디에든 리터럴
문자열이 다시 나타나는 순간 무너진다.

### 동시 E2E 충돌

다른 레인이 같은 호스트에서 Playwright 를 돌리는 동안 내가 실행을 시작했고
(게이트에 걸지 않고 값만 출력했다 — 내 잘못), Playwright 가 시작 시 `test-results/`
를 비우면서 **내 실행의 workspace-ownership 레지스트리를 실행 중에 지웠다.** 세
번째 테스트가 `ENOENT … .workspace-ownership/<runId>/run.json` 으로 실패했다 —
단언이 아니라 정리 경로에서. `workers: 1` 은 한 프로세스 안에서만 직렬화하며 프로세스
사이에는 아무 일도 하지 않는다.

그 실패로 workspace 하나가 남았다. **정확한 id 하나**를 읽기 전용 목록에서 회수해
삭제했고, 이름이 내 접두사와 맞지 않으면 **거부만 하는** 가드를 얹었다 — 접두사를
선택자로 쓰면 남의 workspace 를 지우는 길이고, 거부 조건으로 쓰면 안전망이다.
삭제 전후 목록을 남겼다: `Workspace-1` 과 다른 레인의 workspace 는 양쪽 모두에
그대로 있고, 내 것만 사라진다.
