# 라이트 테마 도입 (FR-UIDS-018, FR-UIDS-019, FR-UIDS-020)

## 이슈 설명

- 앱은 다크 테마만 있었다. 라이트 테마를 추가해 달라는 요청이다.
- 앱 내부 셸이 PowerShell 이라, 터미널 색이 어떻게 정해지는지 먼저 검토했다. 가능하다고 판단해 구현했다.
- 요구사항은 `docs/spec/44.ui-design-system.srs.md` 의 FR-UIDS-018(앱 화면, 1144행), FR-UIDS-019(터미널, 1204행), FR-UIDS-020(설정, 1264행)이다. 실행 중 탭 띠가 테마 토큰을 따르도록 FR-UIDS-009 도 맞췄다.
- 결정 사항
  - 앱 화면과 터미널에 라이트 테마를 준다. 다크 화면은 그대로 둔다.
  - 설정 화면에서 다크, 라이트, 시스템 설정 따름 중 고른다. 기본값은 다크이며 헤더 토글은 두지 않는다.
  - 편집기의 주간·야간 기본값은 두 앱 테마 모두에서 주간이다. `docs/spec/41.markdown-editor.srs.md` 의 범위 주석 한 줄을 이에 맞춰 갱신했다.
   - 터미널 변경은 브라우저 쪽에만 둔다. 서버 모드의 보기 속성은 뷰 등록마다 한 번 정해지므로, 새 테마는 새 등록(재접속·새로고침·새 뷰)부터 쓴다.
  - PR 은 마지막에 한 번 만든다.

## 문제 원인 (검토 결과)

- 결론: 가능하다. 다만 CSS 만 바꾸면 입력 글자가 보이지 않으므로 터미널 팔레트도 함께 바꿔야 한다.
- 터미널 글자색은 PowerShell(PSReadLine)이 보내는 ANSI 색 슬롯 번호로 정해진다. 검토 때 관측한 기본 입력 글자는 SGR 37(흰색 슬롯)이다. 실제 RGB 값은 브라우저의 xterm 팔레트가 고른다.
- 기존 다크 팔레트의 흰색 슬롯(#e5e5e5)을 흰 배경에 두면 입력 글자 대비가 1.26:1 이다. 값은 `origin/main:frontend/src/utils/terminalViewAttributes.ts:24` 에서 읽어 이 기록에서 다시 계산했다.
- 앱 CSS 와 인라인 스타일에 토큰이 아닌 색 리터럴이 흩어져 있었다. 3f4eeee9 의 frontend/src diff 에서 색 리터럴이 있던 제거 줄은 116개다. 추가된 줄 중 색 리터럴이 있는 241줄은 전부 `tokens.css` 의 토큰 정의(라이트 블록 포함)다.
- 서버 모드(디버그·시험 전용)의 보기 속성은 뷰 등록마다 한 번 정해진다(MIG-BGSTAB-002). 그래서 그 모드는 새 등록부터 새 테마를 쓴다.

## 남은 한계

1. 흐린 글자 토큰 `--fg-faint`(`#737373`)와 `--fg-dim`(`#6e6e6e`)은 라이트에서 앱 표면 다섯 개(`--bg-app`·`--bg-chrome`·`--bg-surface`·`--bg-raised`·`--bg-panel`) 위 3.98–4.93:1 이다(가장 낮은 곳은 `--bg-chrome` 위 3.98, 4.28). 같은 표면 기준 다크에서는 2.95–3.68:1 로, 처음부터 의도된 저강조 글자이고 FR-UIDS-018 AC-3 의 대상(`--fg`, `--fg-strong`, `--fg-muted`)이 아니다. 라이트 값이 다크보다 대비가 높으므로 그대로 둔다. `LIGHT_TEXT_PAIRS` 는 실제로 그려지는 글자·배경 쌍을 4.5:1 이상으로 검사하며, `--fg-dim` 은 `--bg-panel` 쌍(4.76)으로 들어 있고 `--fg-faint` 는 들어 있지 않다.
2. OSC 색 응답은 이 PC 의 Windows 콘솔 프로그램에 도달하지 않는다. 두 테마 모두 해당하며 기존 결함이다. ConPTY 입력 경로에서 버려지는 것으로 추정한다(미확인).
3. 24비트 배경을 직접 칠하는 외부 AI 코딩 도구 TUI 는 자체 라이트 테마가 필요하다(예: Claude Code 의 `/theme`). Claude Code 메인 화면은 병합 전에 확인했다(아래 추가 확인 절).
4. 열린 편집기 안의 mermaid 다이어그램은 새로고침 전까지 처음 팔레트를 유지한다(편집기 래퍼가 페이지당 한 번 초기화). 편집기 야간 설정이 아니라 앱 테마를 따른다.
5. iOS 홈 화면 띠와 manifest 색은 여전히 다크다.
6. 다른 열린 탭은 새로고침 후에야 변경을 반영한다.
7. 서버 모드의 보기 속성은 뷰 등록 안에서 고정된다. 열린 등록은 재접속·새로고침·새 뷰 전까지 이전 테마의 색 정보를 쓴다(FR-UIDS-019 AC-4). 서버 모드에서는 지금처럼 서버가 CSI ?996n 에 응답하며, 무응답은 기본 모드에만 해당한다.
8. `check:consumer-manifest` 는 이 체크아웃에서 실행하면 실패하며, 이 작업 전에도 같았다. 레거시 매니페스트가 CRLF 로 체크아웃되어 원시 바이트 해시가 어긋나기 때문이다(인덱스의 LF 사본은 기대 해시와 같고, LF 로 읽게 하면 통과한다). 이 작업의 커밋에는 그 파일이 없다.

사용자가 라이트 화면을 직접 확인하다 어둡게 남는 곳 두 군데를 찾았다.

2. **Claude Code 사용자 메시지 줄·diff 줄** — 셀 값을 읽어 보니 Claude Code 기본(dark) 테마가 24비트 배경(#373737, #3d0100, #022800)을 직접 칠한다. 팔레트 교체와 글자색 대비 보정은 이 배경에 닿지 않는다. 결정에 따라 출력 경로는 고치지 않고 README 와 FR-UIDS-019 에 안내를 적었다. Claude Code 의 `/theme` 에서 Light mode 를 고르면 되고(메시지 배경 rgb(240,240,240)), 이 설정은 PC 전역이다. Light mode (ANSI colors only) 는 메시지 배경이 ANSI 흰색이라 이 라이트 팔레트에서 어두운 줄이 되어 맞지 않는다. 리뷰 지적에 따라, Light mode 는 글자를 검게 칠하므로 다크로 돌아오면 Claude Code 도 Dark mode 로 되돌려야 한다는 점과, Auto (match terminal) 는 Windows 에서 동작이 확인되지 않았다는 점을 함께 적었다.

라이트에서 어두운 덩어리를 찾는 화면 검사(9개 화면에서 불투명하고 어두운 배경 요소)에서는 의도한 파란 버튼과 8px 상태 점만 나왔다. 허용 목록과 "테마 무관" 토큰을 다시 훑은 결과와 결정은 아래와 같다.
