# MCP submit 전달의 Enter 분리 (FR-MCP-002 AC-7)

## 이슈

MCP 로 다른 세션의 코딩 에이전트에 프롬프트를 보내면, 가끔 글이 입력창에만 남고 전송되지 않았다.

- 짧은 글("hi")은 저절로 전송됐다.
- 약 2,000자 시험 입력도 한 번은 저절로 전송됐다.
- 다른 긴 프롬프트는 입력창에 남아, 사용자가 직접 Enter 를 눌러야 했다.

## 원인

- `buildergate.terminal.exec` 는 `본문\r` 을 PTY 에 한 번에 썼다(`McpWorkspaceControl.ts`).
- PTY 가 이 입력을 에이전트에 몇 번의 읽기로 나눠 넘기는지는 그때의 타이밍에 달려 있다.
- Enter 가 긴 본문과 같은 읽기에 실리면, AI TUI 는 그 읽기를 붙여넣기로 보고 Enter 를 붙여넣은 내용의 일부로 처리한다.
- 이 원인은 관찰과 맞는 가설이다. 실패한 순간을 직접 관측하지는 않았다.

같은 계열의 결함이 둘 더 있었다. 이 둘은 코드로 확인했다.

- `buildergate.message.send` 의 submit 모드는 Enter 를 아예 보내지 않았다.
- `open_agent` 의 실행 명령과 시작 프롬프트(kickoff)도 Enter 를 보내지 않았다.

## 해결

`server/src/services/submitDelivery.ts` 의 `submitWithSeparateEnter` 가 submit 요청을 두 번에 나눠 쓴다.

1. 본문을 쓴다. 본문 끝의 CR/LF 는 뺀다.
2. 기다린다. 대기 시간은 150ms 에서 시작해 1KB 마다 50ms 씩 늘고, 1초를 넘지 않는다.
3. `\r` 만 따로 쓴다.

실패는 이렇게 처리한다.

- 본문 쓰기가 거부되면 Enter 를 쓰지 않는다.
- Enter 쓰기가 거부되면 "전송됨" 대신 그 실패 코드를 돌려준다.
- Enter 쓰기에는 감사 기록을 다시 남기지 않는다. 전달 한 번에 감사 기록은 한 건이다.
- paste 모드는 바뀌지 않는다.

이 함수를 거치는 경로는 다음과 같다.

- `message.send`, `reply_to_leader`, `terminal.exec` (`createMcpGatewayDelivery`)
- `open_agent` 의 실행 명령과 kickoff (`createMcpAgentInputGateway`)
- sessionKey 가 없는 `execTerminal`

## 한계

- 대기 시간은 경험값이다. 실제 Claude Code 에서의 전송 여부는 자동 시험으로 확인하지 않았다. 구독 계정으로 로그인된 에이전트를 자동화로 조작하면 사내 규정에 어긋나기 때문이다.
- 같은 세션에 두 전달이 대기 구간에서 겹치면 두 전달의 쓰기가 서로 섞일 수 있다. 오케스트레이터는 도구 결과를 기다린 뒤 다음 전달을 보내므로, 순차로 보내는 경우에는 영향이 없다.
