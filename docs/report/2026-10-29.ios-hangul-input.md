# 아이폰에서 한글 조합이 깨지는 문제 수정

## 개요

이 보고서는 아이폰 터미널에서 한글을 입력하면 자모가 분리되어 들어가던 문제를 고친 결과를 기록한다. 작업 중 사용자 확인으로 지우기 키 문제가 하나 더 드러났고, 사용자가 요청한 자모 단위 지우기도 같은 수정으로 해결했다.

- 요구사항: FR-MKB-015(신설, `docs/spec/46.mobile-terminal-keyboard.srs.md`), 타깃 `ios-hangul-input`
- 브랜치: `fix/ios-hangul-input`(main `1ffd12f7` 기준)
- 이슈: #201
- 작업일: 2026-10-29

## 문제 1: 한글 자모가 분리되어 들어감

### 증상

아이폰에서 `안녕하세요`를 치면 터미널에 `ㅇㅏㄴㄴㅕㅇㅎㅏㅅㅔㅇㅛ`가 들어갔다. 안드로이드 사용자에게서는 같은 보고가 없었다.

### 측정

원인을 짐작으로 정하지 않으려고, 이벤트를 화면에 기록하는 진단 페이지를 2222에 임시로 두고 아이폰(iOS 18.7 Safari)에서 측정했다. 진단 페이지는 일반 입력칸, xterm처럼 키 입력을 막는 입력칸, 실제 xterm.js 6.0.0, 수정안을 적용한 xterm을 나란히 두었다.

- 첫 측정 결과는 무효였다. 서버의 CSP(`script-src 'self'`)가 인라인 스크립트를 막아서 기록이 동작하지 않았다. 스크립트를 별도 파일로 옮긴 뒤 다시 측정했다.
- 일반 입력칸과 실제 xterm.js의 이벤트 순서는 같았다. 차이는 xterm이 그 이벤트를 어떻게 처리하는지에 있었다.

### 문제 원인

- iOS 한글 키보드는 조합 이벤트(`compositionstart`/`compositionend`)를 쓰지 않는다.
- 자모마다 `keydown`(`key`=자모, `keyCode` 0)과 `keypress`(`keyCode`=자모 코드 포인트)를 보낸다.
- 앞 글자와 합칠 때는 입력칸에서 앞 글자를 지우고(`deleteContentBackward`) 합친 글자를 다시 넣는다(`insertText "아"`).
- xterm.js는 `keypress`의 자모를 그대로 보내고, 입력칸의 지우기와 다시 넣기는 무시한다(`CoreBrowserTerminal.ts`의 `_keyPress`, `_inputEvent`).
- 안드로이드(Gboard)는 조합 이벤트를 쓴다. 그래서 xterm의 조합 처리 경로를 타고, 문제가 없었다.

### 해결 방법

- 한글 자모 키(U+3131~U+318E, 수식키 없음, 조합 중이 아님, `keyCode` 229가 아님)는 xterm이 처리하지 않게 했다. (AC-1)
- 그 키를 누르는 동안 입력칸이 바뀐 만큼을 터미널로 보낸다. 끝에서 지워진 글자마다 `DEL`(0x7f)을 하나씩 보내고, 이어서 새로 들어온 글자를 보낸다. 이벤트 종류별로 번역하지 않고 키를 누르기 전후의 입력칸 내용을 비교하므로, 어떤 종류의 입력 이벤트가 와도 같은 방식으로 처리한다. (AC-1, AC-2)
- 키를 놓을 때까지 입력칸이 바뀌지 않았으면, 자모를 그대로 보내서 입력을 잃지 않는다. (AC-5)

## 문제 2: 지운 글자에 다음 자모가 합쳐짐

### 증상

첫 수정을 2222에 배치한 뒤 사용자 확인에서 `가` → 지우기 → `나`의 결과가 `가나`였다.

### 문제 원인

- 지우기 키는 xterm이 처리해서 `DEL`을 보내고, 입력칸에는 반영하지 않았다.
- 첫 수정은 그 뒤에 입력칸의 마지막 글자를 코드로 지웠다. 그러나 iOS 키보드는 조합 중인 글자를 자기 안에도 기억한다. 코드로 입력칸을 바꿔도 그 상태는 초기화되지 않았다.
- 그래서 키보드는 여전히 `가`를 조합 중이라고 여기고, 다음 `ㄴ`을 `간`으로 합쳤다.

### 해결 방법

- 입력칸에 이 방식으로 친 한글이 남아 있는 동안에는, 수식키 없는 지우기 키를 xterm이 아니라 iOS 키보드가 처리하게 했다. 키보드가 입력칸을 고친 결과는 문제 1과 같은 방식으로 보낸다. 그러면 키보드의 조합 상태와 터미널 내용이 어긋나지 않는다. (AC-3)
- 입력칸이 비어 있으면 지우기 키는 예전처럼 xterm이 처리한다. (AC-6)
- 다른 경로로 터미널에 입력이 가면 입력칸을 터미널과 맞춘다. xterm이 보낸 `DEL`은 입력칸의 마지막 글자를 지우고, 엔터, 영문, 모바일 키 줄, 붙여넣기, 단축키, 마우스 보고는 입력칸을 비운다. 터미널 질의 응답은 입력칸을 바꾸지 않는다. (AC-4)

## 사용자 요청: 받침만 지우기

사용자는 `각`을 치다가 지우기를 누르면 글자 전체가 지워지는데, 받침만 지울 수 없는지 물었다. 문제 2의 해결로 지우기 키를 iOS 키보드가 처리하게 되면서, 키보드 자체의 자모 단위 지우기가 그대로 동작한다. 이제 `각`에서 지우기를 누르면 `가`가 되며, 이것은 iOS 메모 앱에서 지울 때와 같다. 이 때문에 `가`를 완전히 지우려면 지우기를 두 번 누른다(`가` → `ㄱ` → 빈 칸).

## 리뷰 반영

독립 리뷰를 1회 진행했다. 확실한 결함은 나오지 않았고, 다음 세 가지를 검토했다.

1. 모바일 키 줄(←, Esc 등)을 누른 뒤 iOS 키보드가 이전 글자를 기억하고 합칠 수 있다는 지적이다. 문제 2의 경험상 가능성이 있어 아이폰에서 확인했고, `가` → ← → `ㄴㅏ`와 `가` → Esc → `ㄴㅏ` 모두 정상이었다.
2. 블루투스 키보드가 조합 이벤트를 쓰면서 `keyCode` 229가 아닌 값을 보내면, 조합 중인 글자가 두 번 보내질 수 있다는 지적이다. 실측하지 않았지만 막기 쉬워서, 조합 중인 입력칸 변경은 xterm의 조합 경로에 넘기도록 고쳤다. 테스트를 먼저 추가했다. (AC-6)
3. 입력이 거부되면 입력칸이 터미널보다 앞서 나갈 수 있다는 지적이다. 입력이 막히면 입력칸이 비활성화되어 키보드가 내려가므로, 한계로만 기록한다.

## 검증

- 단위 테스트: `iosHangulInput.test.ts` 14/14. 수정 전에는 모듈이 없어 실패했고, 설계를 바꿀 때도 새 테스트가 먼저 실패하는 것을 확인했다.
- 배선 테스트: `terminalIosHangulInput.test.ts` 7/7. 처음 작성한 6건은 수정 전에 모두 실패했다(0/6). 그중 보호 테스트 2건(질의 응답, keyCode 229)은 테스트 환경에 `InputEvent`가 없어서 실패한 것이었고, 환경을 고친 뒤에는 통과했다(2/6). 나머지 4건은 배선이 없어서 실패했다. 문제 2를 고치면서 지우기 키 테스트를 바꾸고 "입력칸이 비어 있으면 지우기는 xterm이 처리" 테스트 1건을 더해 7건이 되었다.
- 회귀: 터미널 뷰 동작 91/91, 모바일 키보드 83/83, Git 보기 37/37, i18n 가드 통과, 앱·테스트 타입 검사 통과.
- 프런트 단위 테스트 전수: 실패한 파일은 전용 러너에서만 도는 렌더 테스트 목록과 같았다. 마지막 실행에서는 `terminalReplayGuard.test.ts`가 1건 추가로 실패했다. 이 테스트는 5ms 타임아웃과 10ms 대기에 의존하고 이번 변경 코드를 불러오지 않으며, 단독 실행에서는 6/6 통과했다. 그래서 전수 실행 부하에서 생긴 일시적 실패로 판단했다.
- 서버 `TerminalResourcePolicy.test.ts`: 재봉인 전에는 매니페스트 해시 불일치로 2건이 실패했다. 이 변경 없이 돌리면 21/21이었으므로, TerminalView.tsx 수정에 따른 봉인 차이로 확인하고 재봉인했다.
- 아이폰 확인(iOS 18.7 Safari, 2222): `안녕하세요`, `가 아`, `한글abc한글`, `각` + 지우기 → `가`, `가` + 지우기 두 번 + `나` → `나`, 지우기 길게 누르기, 키 줄 ←·Esc 뒤 입력이 모두 정상이었다.

## 기존 실패 (이번 변경과 무관)

- `npm run check:consumer-manifest`: 줄바꿈 문제가 없는 깨끗한 체크아웃에서 main `1ffd12f7`과 이 커밋 `73d52635`이 같은 단언(`terminal-resource-consumer-manifest.test.mjs:846`)에서 같은 값(`e1413f…` 대 `1cf68b…`)으로 실패한다. 이 커밋이 결과를 바꾸지 않았다.
- 이 작업 폴더에서는 같은 검사가 더 앞 단계에서 `d1de37` 대 `1d6dcf`로 실패했다. 그 원인은 코드가 아니라 체크아웃 상태다. `docs/analysis` 아래 약 1,900개 파일이 저장소에는 LF로 있지만 작업 폴더에는 CRLF로 풀려 있고(`git ls-files --eol`의 `i/lf w/crlf`), 레거시 매니페스트의 바이트 해시가 그 때문에 달라진다. 이전 작업(#200)의 보고서도 이 값을 기존 실패로 적었는데, 원인은 같은 줄바꿈 문제였다.
- 정정(2026-10-31): 첫 항목의 846행 실패도 기존 실패가 아니었다. 그 깨끗한 체크아웃에는 서버 빌드(`server/dist`)가 없었다. v0.10.30 릴리스 전에 main `c21625e5`의 깨끗한 worktree에서 `npm --prefix server run build`를 먼저 돌리자 `test:release-pipeline` 전체(`check:consumer-manifest` 포함)가 통과했다.

## 한계

- 입력이 거부되는 순간에 한글을 치면, 입력칸이 터미널보다 앞서 나갈 수 있다(리뷰 3번).
- 블루투스 키보드의 한글 입력은 실측하지 않았다.
- `DEL`로 앞 글자를 지우는 방식이므로, vim 일반 모드처럼 `DEL`을 명령으로 해석하는 곳에서는 한글 조합이 다르게 동작할 수 있다. 사용자가 이 방식을 선택했다.
