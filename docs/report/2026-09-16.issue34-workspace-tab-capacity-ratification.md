# Issue #34 — App.tsx 의 워크스페이스·탭 한도 하드코딩 (비준)

- 이슈: Snoworca/BuilderGate#34 "App.tsx 가 워크스페이스·탭 한도를 하드코딩해 서버 설정과 갈린다"
- 요구사항: FR-BGSTAB-026 (AC-3, AC-4) — Status `implemented`, Stability `evolving` (변경하지 않음)
- 결론: **이슈의 전제는 현재 HEAD 에서 성립하지 않는다.** 코드 수정은 없으며, 이미 적용된 수정의 런타임 증거를 추가했다.

## 이슈 설명

`frontend/src/App.tsx:561` 의 `maxWorkspaces={10}` 과 `:746` 의 `maxTabsPerWorkspace={8}` 이
`server/config.json5` 로 강제되는 서버 한도와 갈린다는 보고. 한 개념에 진입점이 둘이라
한도를 올리면 UI 가 먼저 막고, 내리면 UI 가 허용한 조작을 서버가 거절한다.

## 전제 확인

이슈가 인용한 것은 2026-09-05 조사 시점의 상태다. 그로부터 사흘 뒤 커밋 `da0e347`
(2026-09-08, "fix: 워크스페이스와 탭 UI에 서버 한도 적용") 이 두 상수를 제거했다.
이슈의 전제를 확인한 시점의 HEAD 는 `08fb66d` 였다 — 이 변경의 부모 커밋이며 현재
HEAD 가 아니다. 그 트리에서 `App.tsx` 의 네 곳 (`:606`, `:607`, `:662`, `:842`) 은
모두 `wm.limits.*` 를 읽었고, 이 변경은 제품 코드를 건드리지 않으므로 그대로다.

### 이슈가 제안한 `RuntimeConfigStore` 경로에 대하여

이슈는 두 값이 공개 runtime-config 스냅샷에 포함되는지 확인하지 않았다고 명시했다.
확인 결과 **포함되지 않으며**, `RuntimeConfigStore` 의 키 레지스트리에 아예 등록되어
있지 않다(따라서 `applyScope` 도 없다). 실제 수정은 그 대신 이미 인증된 워크스페이스
엔드포인트를 썼고, FR-BGSTAB-026 AC-5 가 "`/api/runtime-config` 의 허용 필드 계약은
변경하지 않는다" 로 이를 명시한다. `/runtime-config` 가 의도적으로 비인증이라는
#37 의 관찰(`OPS-BGSTAB-004`) 을 고려하면, 두 선택지 중 채택된 쪽이 더 안전하다.
비준 과정에서 이 판단을 뒤집을 근거를 찾지 못했으므로 유지한다.

스냅샷 도착 전 동작에 대한 질문도 이미 규정되어 있다 — AC-4: "수신 전에는 기본값 10·8 을
유지하되 컨트롤을 잠그지 않고, 수신 후 즉시 적용한다." `useWorkspaceManager.ts:175` 의
초기 상수가 그것이며, 갈린 진입점이 아니라 첫 응답까지의 명시된 과도 상태다.

## 한계

1. **이 spec 은 CI 에서 돌지 않는다.** 저장소의 어떤 것도 이 spec 을 위해 서버를
   설정하지 않고, 어떤 기본 스위트도 이것을 실행하지 않는다. 두 한도가
   `RuntimeConfigStore` 키가 아니라 기동 시 한 번 읽히는 값이기 때문에, 실행하려면
   운영자가 `config.json5` 를 바꾸고 서버를 재시작해야 한다. 이것은 **수동 절차 가드**이며
   자동 회귀 커버리지가 아니다. 방치하면 skip 한다.
2. **스크린샷은 `.gitignore` 대상이라 해시만 남는다.** 게다가 spec 이 파일 이름을 실행이
   아니라 설정값으로 짓기 때문에(`issue34-max-workspaces-${값}.png`), r2 재포집이 r1 과
   겹치는 세 경로(`…-workspaces-4`, `…-tabs-3`, `…-tabs-2`)를 덮어썼다. r1 의 그 세 해시는
   이제 어떤 파일과도 일치하지 않으며 이미지는 소실됐다. r1 의 **로그**는 그대로 남아 있고,
   본 증거는 로그이지 스크린샷이 아니다. 자세한 대조표는 분석 README 참조.
3. **`r2-guard-controls.log` 의 첫 포집은 잘려 있었다.** 포집 명령이 각 대조를
   `head -16` 으로 통과시켜 C5 가 4615 바이트에서 중간에 끊겼다. 같은 6/2 설정의 서버를
   새로 띄워 다섯 대조 전부를 잘림 없이 다시 포집해 교체했다 — 현재 8406 바이트,
   `--- [Cn …] ---` 다섯 구획과 각 대조의 `[exit: N]` 이 모두 있고 C1..C5 가
   `1, 1, 1, 0, 1` 이다(skip 인 C4 만 0). 첫 포집이 없었던 것처럼 적지 않기 위해 남긴다.
4. **그 로그는 두 번째 테스트의 제목을 `AC-7` 로 출력한다.** 포집 이후에 `AC-4` 로
   고쳤기 때문이다. 그 테스트가 검증하는 것은 수신한 `maxTabsPerWorkspace` 를 UI 가
   쓰는지(AC-4)이지 시각 보존(AC-7)이 아니어서 라벨을 바로잡은 것이며, 단언은 바뀌지
   않았으므로 기록된 결과는 그대로 유효하다.

## 새로 관찰한 결함 (이슈로 열지 않고 보고)

1. **`maxSessions={32}` 는 같은 결함의 세 번째 사례다.** `frontend/src/App.tsx:663` 이
   전체 세션 한도를 하드코딩하는데, 서버는 `workspace.maxTotalSessions` 를
   `config.json5` 에서 읽어 `WorkspaceService.ts:564` 에서 강제한다(기본 32,
   스키마 범위 1–128). `da0e347` 이 "별도 전체 세션 제한은 유지한다" 로 의도적으로
   범위 밖에 둔 것이며, #34 도 두 값만 지목하므로 이번에 고치지 않았다.
   운영자가 `maxTotalSessions` 를 32 에서 바꾸면 #34 와 완전히 같은 증상이 재현된다.
2. **두 한도는 재시작 범위다.** `RuntimeConfigStore` 키가 아니므로 런타임 변경 수단이
   없고, 기동 시 한 번 읽는다. 클라이언트도 최초 로드 때만 `limits` 를 받는다.
   결함이라기보다 문서화되지 않은 제약이다.
