# Issue #34 — App.tsx 의 워크스페이스·탭 한도 하드코딩 (비준)

- 이슈: Snoworca/BuilderGate#34 "App.tsx 가 워크스페이스·탭 한도를 하드코딩해 서버 설정과 갈린다"
- 요구사항: FR-BGSTAB-026 (AC-3, AC-4) — Status `implemented`, Stability `evolving` (변경하지 않음)
- 결론: **이슈의 전제는 현재 HEAD 에서 성립하지 않는다.** 코드 수정은 없으며, 이미 적용된 수정의 런타임 증거를 추가했다.

## 이슈 설명

`frontend/src/App.tsx:561` 의 `maxWorkspaces={10}` 과 `:746` 의 `maxTabsPerWorkspace={8}` 이
`server/config.json5` 로 강제되는 서버 한도와 갈린다는 보고. 한 개념에 진입점이 둘이라
한도를 올리면 UI 가 먼저 막고, 내리면 UI 가 허용한 조작을 서버가 거절한다.

## 전제 확인

이슈가 인용한 것은 2026-09-05 조사 시점의 상태다. 그로부터 사흘 뒤 커밋 `da0e347`
(2026-09-08, "fix: 워크스페이스와 탭 UI에 서버 한도 적용") 이 두 상수를 제거했다.
이슈의 전제를 확인한 시점의 HEAD 는 `08fb66d` 였다 — 이 변경의 부모 커밋이며 현재
HEAD 가 아니다. 그 트리에서 `App.tsx` 의 네 곳 (`:606`, `:607`, `:662`, `:842`) 은
모두 `wm.limits.*` 를 읽었고, 이 변경은 제품 코드를 건드리지 않으므로 그대로다.

### 이슈가 제안한 `RuntimeConfigStore` 경로에 대하여

이슈는 두 값이 공개 runtime-config 스냅샷에 포함되는지 확인하지 않았다고 명시했다.
확인 결과 **포함되지 않으며**, `RuntimeConfigStore` 의 키 레지스트리에 아예 등록되어
있지 않다(따라서 `applyScope` 도 없다). 실제 수정은 그 대신 이미 인증된 워크스페이스
엔드포인트를 썼고, FR-BGSTAB-026 AC-5 가 "`/api/runtime-config` 의 허용 필드 계약은
변경하지 않는다" 로 이를 명시한다. `/runtime-config` 가 의도적으로 비인증이라는
#37 의 관찰(`OPS-BGSTAB-004`) 을 고려하면, 두 선택지 중 채택된 쪽이 더 안전하다.
비준 과정에서 이 판단을 뒤집을 근거를 찾지 못했으므로 유지한다.

스냅샷 도착 전 동작에 대한 질문도 이미 규정되어 있다 — AC-4: "수신 전에는 기본값 10·8 을
유지하되 컨트롤을 잠그지 않고, 수신 후 즉시 적용한다." `useWorkspaceManager.ts:175` 의
초기 상수가 그것이며, 갈린 진입점이 아니라 첫 응답까지의 명시된 과도 상태다.

C5 의 두 실패는 **서로 다른 두 단언**에서 났고 로그에 전문이 남아 있다.

- 테스트 1 (`spec.ts:93`) — `expect(state.limits).toEqual(...)`: 기대
  `maxWorkspaces: 4, maxTabsPerWorkspace: 3`, 수신 `maxWorkspaces: 6,
  maxTabsPerWorkspace: 2`. 서버는 사실을 말했고 단언 쪽이 틀렸다.
- 테스트 2 (`spec.ts:145`) — `tab 3 is within the configured limit`,
  `Expected: < 400`, `Received: 409`. 세 번째 탭 생성을 서버가 거절했다. 실제 설정된
  탭 한도는 2 이기 때문이다.

C6 은 자리-짝지음(cross-paired) 성질을 **관측**한 것이다. `8 / 10` 은 제거된 두 숫자를
반대 자리에 넣은 쌍이고, 가드는 이것을 통과시킨다. 실행은 브라우저까지 진행한 뒤 C5 와
정확히 같은 두 단언에서 실패한다 — `spec.ts:93` 이 기대 `maxWorkspaces: 8,
maxTabsPerWorkspace: 10` 에 대해 수신 `6 / 2` 를, `spec.ts:145` 가 `Expected: < 400 /
Received: 409` 를 낸다. 어느 실패도 반상수 가드를 언급하지 않는다. 가드가 숫자가 아니라
**자리**를 거부한다는 증거다.

C1 이 **반(反)상수 가드**다. `spec.ts:62-73` 의 `resolveLimits()` 가
`ISSUE34_MAX_WORKSPACES` 가 `10` **이거나** `ISSUE34_MAX_TABS` 가 `8` 일 때
`spec.ts:66` 에서 throw 한다. 그 두 값은 `da0e347` 이 제거한 상수이자
`useWorkspaceManager.ts:175` 의 스냅샷 수신 전 기본값이므로, 그 쌍에서의 통과는
재하드코딩된 `App.tsx` 나 `limits` 를 아예 못 받은 클라이언트로도 만족된다. skip 은
"아무도 이 실행을 설정하지 않았다" 로 읽히는데 10/8 은 증거를 파괴하는 설정이므로 skip 이
아니라 거부를 택했다. C5·C6 은 단언이 반증 가능함을 보인다.

**C1~C3 의 모양이 r2 와 r3 사이에서 바뀌었고, 그것이 재포집의 요점이다.** r2 에서는 그
세 대조가 `Error: No tests found` 로 끝났다 — 가드가 파일 적재 중에 throw 해서 수집이
끝나지 못했기 때문이다. r3 에서는 같은 세 대조가 `2 failed` 를 낸다 — 이 파일의 두 테스트
뿐이고 다른 spec 은 건드리지 않는다. 오류 문구·변수명·exit code 는 두 세대가 동일하고
바뀐 것은 폭발 반경뿐이다. 두 전사가 여기서 어긋나는 것이 수정이 먹혔다는 관측 가능한
증거이지, 둘 사이의 불일치가 아니다.

**가드가 도는 지점.** env 검증(`readLimit`, throw 는 `spec.ts:37`)과 반상수 검사는 둘 다
`resolveLimits()` 안에 있고, 각 테스트가 자기 선두(`spec.ts:85`, `spec.ts:130`)에서
그것을 호출한다 — 모듈 적재 시점이 아니다. 기본 `frontend/playwright.config.ts:7` 이
`testIgnore` 없이 `testDir: './tests/e2e'` 를 두므로 맨 `npx playwright test` 는 이 파일을
같은 디렉터리의 다른 모든 spec 과 함께 적재하고, 적재 중 throw 는 실행 전체의 수집을
깨뜨린다 — 셸에 남은 env export 하나가 무관한 spec 전부를 함께 중단시킨다는 뜻이다.
이렇게 범위를 좁히면 실패는 여전히 하드 실패이되 이 파일 안에 머물고, 수집이 끝난 뒤에
난다. 모듈 적재 시점에 남는 것은 `spec.ts:77-78` 의 `test.skip(UNCONFIGURED, …)` 뿐이며
그것은 skip 만 한다.

**r3 에서 포집하지 않은 것.** 대조군 서버의 pid 와 그 개별 teardown 은 기록되지 않았다.
r2 는 `r2-final-ports.txt` 에 `/proc/108143 after kill: no` 로 그것을 남겼지만,
`r3-final-ports.txt` 는 모든 r3 실행이 끝난 뒤 `node dist/index.js` 프로세스가 남아 있지
않음(`(none)`), WSL 쪽 2221/2222 해제, TCP 2001·2002 가 여전히 PID 30596 으로
`LISTENING` 임만 기록한다. 최종 상태는 기록되었고 개별 pid 는 기록되지 않았다.

1. **이 spec 은 CI 에서 돌지 않는다.** 저장소의 어떤 것도 이 spec 을 위해 서버를
   설정하지 않고, 어떤 기본 스위트도 이것을 실행하지 않는다. 두 한도가
   `RuntimeConfigStore` 키가 아니라 기동 시 한 번 읽히는 값이기 때문에, 실행하려면
   운영자가 `config.json5` 를 바꾸고 서버를 재시작해야 한다. 이것은 **수동 절차 가드**이며
   자동 회귀 커버리지가 아니다. 방치하면 skip 한다.
2. **스크린샷은 `.gitignore` 대상이라 해시만 남는다.** 게다가 spec 이 파일 이름을 실행이
   아니라 설정값으로 짓기 때문에(`spec.ts:114`, `spec.ts:157`), 같은 쌍으로 다시 포집하면
   앞 세대의 이미지가 조용히 덮인다. 실제로 두 번 일어났다 — r2 가 r1 의 세 장을,
   r3 가 r2 의 네 장을 덮었다. 지금 디스크의 값-이름 네 장은 전부 r3 이고,
   `issue34-max-workspaces-5.png` 만 5/2 쌍을 뒤 세대가 쓰지 않아 r1 그대로 남아 있다.
   덮인 이미지는 복구 불가하며, 본 증거는 로그이지 스크린샷이 아니다. 대조표는 분석
   README 참조.
3. **r3 대조군 서버의 pid 와 개별 teardown 은 포집되지 않았다.** `r3-final-ports.txt` 는
   모든 실행 종료 후의 최종 상태(잔존 프로세스 없음, 2221/2222 해제, 2001·2002 는 PID
   30596 으로 불변)만 기록한다. r2 는 그 pid 를 남겼다.
4. **정적 재실행은 r3 세대로 다시 포집했다.** `r3-static-reruns.log` 가 자기 트리
   (`HEAD=c442948` + 미커밋 리뷰 라운드 변경, `git status --porcelain` 인라인)를 밝히며
   26/26·15/15·`tsc exit: 0` 을 기록한다. 다만 그 트리는 여전히 미커밋 상태이며, 로그
   스스로 "다음 커밋이 정확히 이 내용을 고정한다" 고 적고 있다.
5. **`AC-7` 제목 문제는 이제 옛 세대에만 해당한다.** r1·r2 로그는 두 번째 테스트 제목을
   `AC-7` 로 출력한다 — 포집 이후에 `AC-4` 로 고쳤기 때문이다. 그 테스트가 검증하는 것은
   수신한 `maxTabsPerWorkspace` 를 UI 가 쓰는지(AC-4)이지 시각 보존(AC-7)이 아니어서
   라벨을 바로잡았고, 단언은 바뀌지 않았으므로 기록된 결과는 그대로 유효하다. **r3 로그는
   정정된 `AC-4` 를 출력한다.**
6. **`r2-guard-controls.log` 의 첫 포집은 잘려 있었다.** 포집 명령이 각 대조를
   `head -16` 으로 통과시켜 C5 가 4615 바이트에서 중간에 끊겼다. 같은 6/2 설정의 서버를
   새로 띄워 다섯 대조 전부를 잘림 없이 다시 포집해 교체했고(8406 바이트), 그것이 현재
   `raw/` 에 있는 r2 대조군 로그다. 첫 포집이 없었던 것처럼 적지 않기 위해 남긴다.

## 새로 관찰한 결함 (이슈로 열지 않고 보고)

1. **`maxSessions={32}` 는 같은 결함의 세 번째 사례다.** `frontend/src/App.tsx:663` 이
   전체 세션 한도를 하드코딩하는데, 서버는 `workspace.maxTotalSessions` 를
   `config.json5` 에서 읽어 `WorkspaceService.ts:564` 에서 강제한다(기본 32,
   스키마 범위 1–128). `da0e347` 이 "별도 전체 세션 제한은 유지한다" 로 의도적으로
   범위 밖에 둔 것이며, #34 도 두 값만 지목하므로 이번에 고치지 않았다.
   운영자가 `maxTotalSessions` 를 32 에서 바꾸면 #34 와 완전히 같은 증상이 재현된다.
2. **두 한도는 재시작 범위다.** `RuntimeConfigStore` 키가 아니므로 런타임 변경 수단이
   없고, 기동 시 한 번 읽는다. 클라이언트도 최초 로드 때만 `limits` 를 받는다.
   결함이라기보다 문서화되지 않은 제약이다.
