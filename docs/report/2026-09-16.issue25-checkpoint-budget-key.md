# issue #25 — checkpoint snapshot byte 예산을 자체 설정 키로 분리

- GitHub issue: https://github.com/Snoworca/BuilderGate/issues/25
- Requirement: `REL-BGSTAB-023` (신규, target `wave-3`, Status `implemented`, Stability `evolving`)
- 증거: `docs/analysis/2026-09-16.issue25-checkpoint-budget-key/`

## 1. 이슈

Checkpoint snapshot 의 byte 예산(`checkpointMaxBytes`)이 post-checkpoint hold 버퍼의 byte
예산(`postCheckpointMaxBytes`)을 그대로 상속하고 있었다. 서로 다른 두 예산이 production 에서는
하나의 숫자였다.

한쪽을 낮추면 다른 쪽도 같이 낮아지므로, hold overflow 를 재현하려고 값을 낮추면 정상적인
resync checkpoint 까지 "너무 크다" 며 거부되고, 서버가 같은 크기로 재발행 → 클라이언트가 다시
거부하는 루프가 생긴다. 이 루프가 우연히 fault 테스트의 통과 조건을 만족시켜 아무것도 검증하지
못한 테스트가 green 으로 보고된 사고가 실제로 있었다.

### 이슈가 인용한 요구사항 ID 가 틀렸다

이슈는 근거로 `REL-BGSTAB-021` 을 들지만, 그 ID 는
`docs/spec/30.buildergate-stability.srs.md:5721` 의 "A rejected store write rolls back the session
and the tab that addTab created" 가 이미 점유하고 있다. 그리고 `docs/spec/` 전체에
`checkpointMaxBytes` 를 언급하는 요구사항은 **0건**이었다.

기존 ID 를 재사용하거나 재번호하지 않고 **`REL-BGSTAB-023`** 을 새로 할당했다.

### 이슈의 "chunk 는 실패 테스트를 쓸 수 없다" 는 거짓이다

이슈는 chunk 개수 분리를 제외하며 "coordinator 가 이미 독립 처리하므로 실패하는 테스트를 쓸 수
없다" 고 적었다. 독립 평가에서 이것이 거짓으로 확인됐다. `TerminalView.tsx:3521` 이
`postCheckpointMaxChunks` 만 넘기므로 chunk 의 production 결합은 byte 와 **완전히 동일**하며,
같은 형태의 실패 테스트를 똑같이 쓸 수 있다.

chunk 제외 자체는 유지했다(이슈가 정한 범위). 다만 사유를 "TDD 상 불가능" 이 아니라 **범위
결정** 으로 바로잡아 기록했다. 잔존 위험은 그대로 남는다 — 누군가 hold 의 chunk arm 에
도달하려고 `visibleOutputMaxChunks` 를 낮추면 같은 값이 snapshot chunk 상한도 낮춰 resync 루프가
재발한다.

## 4. 해결

### 설계

고정 배수(예: 2배)로 유도하는 방식은 기각했다. SGR 바이트는 cell 수에 비례하지 않아 checkpoint
payload 에 유도 가능한 상한이 없고, 서버는 mint 시점에 수용 가능성을 검사하지 않고 64KiB 단위로
자르기만 한다. 상한을 넘는 상황에서는 운영자가 설정을 올리는 것이 유일한 대응 수단인데, 유도
상수는 그 대응 수단 자체를 없앤다.

**기본값은 4194304** — `visibleOutputQueueMaxBytes` 의 기본값과 같은 수다. 결합된 폴백이 오늘
만들어내던 값과 정확히 일치하므로 effective 동작은 바뀌지 않고 결합만 끊긴다.

### 5.1 consumer manifest 재봉인 (80 → 81)
