# 수정 완료 보고서: IR-BGSTAB-002 — retained state digest 의 codec 무관 canonical 입력과 버전 게이트

## 이슈 설명

`retainedStateDigest` 의 canonical 입력 아홉 필드 중 parser tail 하나가 base64 문자열로 들어가 있었습니다. 이로 인해 데이터 평면 인코딩을 바꾸면 digest 정의가 함께 바뀌어, 같은 상태에 대해 구 클라이언트와 신 클라이언트가 다른 값을 계산하였습니다. 브라우저는 서버와 완전히 별개인 SHA-256 구현으로 이 값을 재계산해 대조하고, 불일치하면 view 를 stale 로 만들며 새 복구 세대를 요구합니다.

이 계약을 규정한 SRS 요구사항이 없었습니다. `docs/spec/` 전체에서 `retainedState` 와 `parserTail` 이 0건이었습니다.

## 문제 원인

parser tail 을 원본 바이트가 아닌 base64 문자열의 형태로 canonical 입력에 포함시킨 것입니다. 데이터 평면 인코딩이 바뀌면 같은 바이트를 다르게 표현하므로, base64 문자열이 변합니다. 그 결과 같은 terminal state 에 대해서도 digest 값이 달라집니다. 또한 canonical 입력의 필드 순서와 커서 좌표가 고정되지 않았고, 버전 게이트가 없어 구·신 양쪽이 서로를 조용히 통과시킬 수 있었습니다.

## 해결 방법

parser tail 을 원본 바이트의 SHA-256으로 치환하였습니다. 커서를 `{x, y}` 두 좌표로 좁혔습니다. canonical 입력의 필드 순서와 mode 순서를 공유 모듈 안에 고정하였습니다. canonical 입력의 버전을 2 로 올리고, 그 버전을 checkpoint 시작 메시지와 확정 메시지에 함께 실었습니다. 브라우저 검증자는 base64 를 디코드해 바이트에서 tail digest 를 만듭니다.

검증자의 반환 타입을 `boolean` 에서 결과 객체로 바꾸어, 모르는 버전이 값 불일치와 구분되는 사유로 수렴하도록 하였습니다.

### 수정된 AC

- **AC-1**: `retainedStateDigest` 의 canonical 입력에는 전송 인코딩에 의존하는 값을 포함해서는 안 된다. base64 문자열, 바이너리 프레임 오프셋, 프롤로그 바이트가 그 예이며, parser tail 은 원본 바이트에서 직접 파생된 인코딩 독립 표현으로만 입력에 들어가야 한다. 정적 계약 테스트가 canonical 입력을 만드는 서버 함수에서 base64 표현을 경유하는 경로가 0개임을 증명해야 하고, 같은 세션 상태에 대해 parser tail 의 base64 표현만 달라져도 digest 가 변하지 않음을 단언해야 한다.

- **AC-3**: 최소 일곱 개의 고정 입력에 대해 기대 digest 를 테스트 안에 hex 리터럴로 적고, 서버 구현과 브라우저 구현과 그 리터럴 셋이 모두 일치함을 단언해야 한다. 고정 입력은 parser tail 이 비어 있는 경우와 ASCII 와 미완성 ANSI 와 CJK 전각과 결합 문자와 ZWJ 이모지와 4바이트 UTF-8 을 각각 포함해야 한다. 기대값을 어느 한쪽 구현을 다시 호출해 만들어서는 안 된다. 서버와 브라우저가 같이 틀리면 통과하는 대조는 이 조항을 만족하지 않는다.

- **AC-5**: canonical 입력의 필드 이름과 개수와 순서, 각 필드의 타입, 그리고 커서 좌표 필드의 키 집합이 서버와 브라우저 양쪽에서 같아야 한다. 어느 한쪽에만 키를 추가하거나 순서를 바꾸면 테스트가 실패해야 하며, 그 판정은 키 배열 자체를 리터럴과 대조하는 방식으로 양쪽 각각에서 이루어져야 한다.

- **AC-6**: canonical 입력의 버전 값이 검증자가 아는 집합에 없으면 검증자는 digest 를 참으로 취급해서는 안 되고, 값 불일치와 구분되는 관측 가능한 사유로 수렴해야 한다. 버전을 아는 값으로 되돌리면 통과함을 같은 테스트가 경계 대조군으로 함께 단언해야 한다.

- **AC-7**: `retainedStateDigest` 가 없는 checkpoint 는 계속 통과해야 하고, checkpoint 시작 메시지와 확정 메시지에서 이 필드의 존재 여부가 항상 일치해야 한다. 한쪽에만 존재하는 경우는 관측 가능한 사유로 거부되어야 한다.

- **AC-8**: 이 Requirement 는 checkpoint 본문 content digest 의 정의, retained active state 의 fnv1a64 digest 정의, 바이너리 프롤로그의 retained state 오프셋 레이아웃과 존재 플래그의 의미론, chunk 회계, 그리고 UI 를 변경하지 않는다.

### 미충족 AC와 사유

- **AC-2**: 데이터 평면 binary 경로가 아직 와이어에 배선되지 않아 두 인코딩으로 어댑터를 호출해 비교하는 것이 성립하지 않습니다. 구조적으로는 canonical 입력에 인코딩 유래 값이 없어 등가가 이미 성립합니다.

- **AC-4**: digest 버전을 선택하는 capability 협상이 선행되어야 합니다. 지금 서버는 협상 없이 v2 만 방출하므로 구 버전 검증자를 선언하는 클라이언트가 존재할 수 없고, 그 상태에서는 실측 자체가 구성되지 않습니다. 협상은 MIG-BGSTAB-002 의 capability 표면 확장을 요구합니다.

## 골든 벡터

일곱 개 고정 입력의 기대 digest 를 hex 리터럴로 적었습니다. 그 값은 어느 구현도 호출하지 않고 계약 문면대로 손으로 조립한 것입니다. 서버 스위트와 프론트 스위트가 같은 리터럴을 공유하므로, 서로 독립인 두 구현과 그 리터럴이 3-way 대조를 이룹니다. 검증 서브에이전트가 저장소 코드를 전혀 쓰지 않은 제3 구현으로 일곱 개를 모두 재현했습니다.

일곱 입력은 빈 tail 과 ASCII 와 미완성 ANSI 와 CJK 전각과 결합 문자와 ZWJ 이모지와 4바이트 UTF-8 입니다.

## 검증 결과

충족한 AC 여섯 개는 다음과 같은 증거를 갖습니다:

- 서버와 브라우저가 같은 canonical 입력을 만들고 같은 hex 리터럴 일곱 개를 공유합니다.
- 그 리터럴은 어느 구현도 호출하지 않고 계약 문면대로 손으로 조립했으며, 검증 서브에이전트가 저장소 코드를 쓰지 않은 제3 구현으로 7/7 을 재현했습니다.
- 뮤테이션으로 확인한 것: 봉투 도메인 복귀, 하한 제거, 커서 축소 제거, 버전 리터럴 변경, tail 을 해시 없이 원문으로, 런타임 게이트 삭제, 사유 축약이 모두 kill 됩니다.
- 핀 파일이 아니어서 대조군은 불필요했습니다.

## 부수 발견사항

### 1. 서버 협상 부재로 인한 fail-closed 동작

서버가 협상 없이 새 버전만 방출하므로, 서버가 갱신된 뒤 아직 새로고침하지 않은 브라우저 탭은 fail-closed 되어 복구를 요구합니다. 데이터가 손상되지는 않으며 새로고침으로 해소됩니다. 협상을 도입하면 사라지는 창입니다.

### 2. Provenance 재발행 불필요

이 digest 를 다루는 파일들은 fair-scheduler provenance 와 terminal resource consumer manifest 어느 핀에도 걸려 있지 않아 재발행 절차가 필요 없었습니다.
