# 워크스페이스 전환 뒤 터미널 렌더링이 한 줄 어긋나는 문제 (REL-BGSTAB-041)

## 이슈

워크스페이스를 오갈 때마다 무작위로 세션 화면이 깨지고, 브라우저를 새로고침해야만 풀렸다.
스크린샷(2026-09-29 19:27)에서 Claude Code 화면 왼쪽에 이전 프레임의 `────` 가 남고 본문이 오른쪽으로
밀렸으며, 상태줄 앞부분(`Opus(H) |`)이 빠진 패널도 있었다. 앱이 생각하는 화면과 xterm 버퍼가 서로 다르다는 신호다.

## 원인

- 화면 수리(screen repair) 패치는 서버 화면의 `repair.seq` 시점 상태이며, 그보다 앞서 보낸 출력을 이미 담고 있다.
- 브라우저는 받은 출력을 출력 스케줄러에 쌓아 두었다가 프레임 예산만큼 나눠 쓰는데, `TerminalView.applyScreenRepair`
  는 패치를 그 대기열을 건너뛰고 xterm 에 바로 썼다.
- 그래서 패치 전에 받았지만 아직 쓰지 않은 출력이 패치 **뒤에** 한 번 더 적용됐다. 상대 커서 이동으로 다시 그리는 TUI
  (Ink / Claude Code)는 이후 모든 프레임을 한 줄 어긋난 자리에 그렸고, 새로고침(서버 스냅샷으로 재구성) 전까지 유지됐다.
- 워크스페이스를 보일 때마다 화면 수리가 요청되므로 전환이 잦을수록 잘 드러났다.

## 측정 (2222, Ink 방식 가짜 TUI 3개 × 그리드 워크스페이스 2개)

| 시나리오 | 수정 전 | 수정 후 |
|---|---|---|
| 빠른 워크스페이스 전환 | 18/72, 18/72, 8/48 깨짐 | 0/72, 0/72 |
| 전환 없이 화면 수리만 반복(휠 클릭) | 6/45, 9/75 | 0/60 |
| 정식 스펙 `terminal-screen-repair-output-order.spec.ts` | 실패(2건) | 통과(0건) |

대조 실험으로 배제한 것: 크기 변화(전환마다 resize 크기 동일, 0/16), 숨김 출력 복구 경로(`write-hidden` 으로 바꿔도 10/72 로 깨짐).

## 해결

`applyScreenRepair` 가 패치를 쓰기 전에 `awaitOutputIdleWithFifoProbe()` 로 출력 대기열이 비기를 기다린다.
끝내 비지 않으면 `screen_repair_apply_rejected(output-not-idle)` 를 남기고 `write-failed` 로 실패를 보고한다
(기존 `screen-repair:failed` 경로).

## 후속: 선재 실패 테스트의 원인과 개선

### `test:unit:terminal-view-behavior` 19건 실패 → 20/20

- 원인: Windows 셸이 설치본에서 `NODE_ENV=production` 을 상속한다. 그러면 `react` 가 프로덕션 빌드를 불러오는데,
  그 빌드는 `act` 를 내보내지 않아 렌더 테스트 전부가 `act is not a function` 으로 실패했다. 제품 결함이 아니다.
- 개선: `frontend/tests/unit/assetStubLoader-register.mjs`(이 스크립트의 `--import` 진입점)에서 `NODE_ENV=production`
  이면 `test` 로 바꾼다. `NODE_ENV=production` 을 상속한 채로 20/20 통과.

### `wave2-screen-repair-resync.spec.ts` AC-4·AC-8 → 10/10, 10/10, 6/6

- AC-4 원인 1: `.xterm-rows` 를 읽는데 WebGL 렌더러에서는 그 DOM 이 없어 10초 타임아웃(#39 와 같은 원인).
  → 행이 없으면 디버그 훅 `captureTerminalText` 로 버퍼를 읽는다(`busy-agent-workspace-bounce.spec.ts` 와 같은 방식).
- AC-4 원인 2: 스크립트로 주입한 화면(마커)은 브라우저에만 있다. 재동기화가 끝난 뒤 클라이언트가 스스로 보낸 워크스페이스 수리
  요청에 서버가 실제 `screen-repair`(seq 26)로 답하면서 마커를 지웠다(5회 중 5회). 제품은 옳게 동작했다.
- AC-8 원인: 새로고침 뒤 구독 응답인 실제 authoritative 스냅샷(seq 78)이 숨김 마커 주입 **뒤에** 도착해 hidden dirty
  상태를 정상적으로 지웠다. 게다가 주입한 seq(77)가 새로고침 이전 스냅샷 기준이라 이미 받은 것보다 오래됐다.
- 개선: 하니스에 `withholdServerScreenRecovery(sessionId)` 를 추가했다(스크립트 구간 동안 대상 세션의 실제
  `screen-*`·`session:ready` 프레임을 페이지로 넘기지 않음). AC-8 은 새로고침된 세대의 실제 스냅샷이 확인(ack)된 뒤에
  그 스냅샷을 기준으로 seq 를 정하고 주입한다.
