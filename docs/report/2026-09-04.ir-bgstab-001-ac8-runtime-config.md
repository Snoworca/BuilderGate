# IR-BGSTAB-001 AC-8: `/api/runtime-config`에 `terminalWireFormat` 노출

## 이슈 설명

IR-BGSTAB-001 AC-8은 `/api/runtime-config` 응답에 `realtime.terminalWireFormat` 필드를 노출할 것을 요구합니다. 변경 전에는 브라우저 측에서 서버가 바이너리 인코딩 협상에 응할 준비가 되어 있는지 알 방법이 없었습니다.

## 문제 원인

런타임 설정 저장소는 `wsTransportMode`와 같은 패턴으로 일곱 지점을 미러링하지 않았습니다. 그 일곱은 타입 import, 기본값 상수, `PublicRuntimeConfig` 인터페이스 필드, private 필드, 생성자, `replaceFromConfig`, 그리고 `getPublicRuntimeConfig` 의 반환 객체입니다. `replaceFromConfig` 를 빠뜨리면 설정을 바꿔도 프로세스가 시작할 때의 값을 계속 내보냅니다.

## 해결 방법

`server/src/services/RuntimeConfigStore.ts`에서 다음 일곱 지점을 수정했습니다.

1. **타입 import** (`:5`): `TerminalWireFormat,`
2. **기본값 상수** (`:160`): `const DEFAULT_TERMINAL_WIRE_FORMAT: TerminalWireFormat = 'json';`
3. **PublicRuntimeConfig 인터페이스** (`:165`): `terminalWireFormat: TerminalWireFormat;`
4. **private 필드** (`:216`): `private terminalWireFormat: TerminalWireFormat;`
5. **생성자** (`:254`): `this.terminalWireFormat = source.realtime?.terminalWireFormat ?? DEFAULT_TERMINAL_WIRE_FORMAT;`
6. **공개 설정 반환** (`:283`): `getPublicRuntimeConfig` 의 반환 객체에 `terminalWireFormat: this.terminalWireFormat,` 를 넣었습니다.
7. **설정 재적재** (`:1264`, `replaceFromConfig`): `this.terminalWireFormat = config.realtime?.terminalWireFormat ?? DEFAULT_TERMINAL_WIRE_FORMAT;`

## TDD 경과

기존 테스트는 `assert.deepEqual`로 공개 설정 객체 전체를 단정했습니다. 이 단정이 곧 화이트리스트 역할을 했으므로, 그 기대값에 `terminalWireFormat`을 추가해 red를 확인했습니다.

테스트는 기본값 선택 시 `'json'`이 아니라 `'binary-shadow'`를 사용했습니다. 이유는 기본값을 쓰면 설정값이 실제로 흘러오는지와 기본값으로 수렴하는지를 구별할 수 없기 때문입니다.

구현 뒤 테스트 두 개를 추가했습니다.

- 첫 번째 테스트 (라인 207-228): `realtime` 블록이 없을 때 기본값 `'json'`으로 수렴하는지, 최상위 키 집합이 정확히 5개(`inputReliabilityMode`, `resourceLimits`, `stabilityModes`, `terminalWireFormat`, `wsTransportMode`)인지, 사다리 4값(`'json'`, `'binary-shadow'`, `'binary-optin'`, `'binary'`)이 모두 그대로 실리는지 확인합니다.
- 두 번째 테스트 (라인 230-247): 설정 재적재 뒤에도 값이 갱신되는지, 그리고 `realtime` 블록을 통째로 뺀 설정으로 재적재하면 기본값으로 돌아오는지 검증합니다.

## 검증에서 확인된 사실

- `getPublicRuntimeConfig`이 반환하는 최상위 키는 정확히 5개이며, 새로 추가된 것은 `terminalWireFormat` 하나뿐입니다.
- 이 필드에 값을 대입하는 지점은 생성자와 `replaceFromConfig` 두 곳뿐입니다.
- 설정 파일 감시자는 없고 `loadConfig()`는 모듈 최상위에서 한 번만 호출되므로, 재적재 경로는 `SettingsService`의 적용 코드와 롤백 코드 두 갈래입니다.
- 프론트엔드의 `RuntimeConfigPayload`는 모든 멤버가 선택적이고 이름으로 지정한 필드만 읽으므로, 새 키가 추가되어도 기존 클라이언트가 깨지지 않습니다.
