# 모바일 전체 화면 프로그램 스크롤 속도 설정 (#196)

## 개요

이 보고서는 이슈 #196을 커밋 `65d933b0`에서 고친 결과를 기록한다. 작업일은 2026-10-28이고 브랜치는 `feat/mobile-scroll-speed`다. 요구사항은 새로 만든 FR-ARCH-015다.

## 이슈 (#196)

아이폰에서 Claude Code 같은 전체 화면 프로그램을 쓸 때 터미널의 세로 끌기 스크롤이 너무 빠르다. 사용자는 스크롤 속도를 개인 설정으로 조절하기를 원했다. 기본값과 적용 범위는 작업 중에 정했다(아래 "진행 중 바뀐 결정"). 이슈는 커밋의 `Closes #196`으로 머지할 때 닫힌다.

## 문제 원인

모바일 터미널의 한 손가락 세로 끌기는 FR-ARCH-008에 따라 두 경로로 나뉜다.

- 일반 출력(스크롤백이 있고 마우스를 추적하지 않는 화면)은 손가락이 글자 한 줄 높이만큼 움직일 때 한 줄씩 스크롤되어 손가락을 그대로 따라간다.
- 전체 화면 프로그램(대체 화면이거나 마우스를 추적하는 화면)은 한 줄마다 휠 신호를 하나씩 보낸다. 프로그램이 휠 한 번에 여러 줄을 움직일 수 있어 체감 속도가 빠르다.

속도를 조절하는 설정이 없었으므로 사용자가 이 차이를 줄일 방법이 없었다.

## 해결 방법

- FR-ARCH-015를 신설했다(target `mobile-scroll-speed`, Stability `evolving`, Status `implemented`).
- `frontend/src/utils/mobileScrollSettings.ts`는 배율을 브라우저 localStorage의 `buildergate.mobileScroll.speed` 키에 저장한다. 선택지는 0.25, 0.5, 0.75, 1, 1.5, 2이고 기본값은 1배다. 저장된 값이 숫자가 아니면 기본값을 쓰고, 범위를 벗어나면 0.25~2 사이로 맞춘다. 저장소를 읽을 수 없으면 기본값을 쓴다.
- `frontend/src/utils/mobileTouchScroll.ts`의 `accumulatePanRows`는 이동 거리에 배율을 곱한 뒤 줄 수와 남은 거리로 나눈다. 배율이 1이면 기존 계산과 같다. `mobilePanSpeed`는 휠 경로이면 설정 배율을, 스크롤백 경로이면 1을 돌려준다.
- `TerminalView.tsx`는 끌기가 시작될 때(touchstart) 배율을 읽는다. 이동할 때마다 경로를 먼저 정하고, 그 경로의 배율로 줄 수를 계산한다.
- `SettingsPage.tsx`와 en/ko 카탈로그에 "모바일 터미널" 카드의 "전체 화면 프로그램 스크롤 속도" 선택 항목을 두었다. 설명에는 일반 출력은 손가락을 그대로 따라간다고 적었다.
- 소비자 매니페스트는 `TerminalView.tsx`의 소스 해시만 재봉인했다. 소비자는 88개이며 튜플과 분류는 바뀌지 않았다.

## 진행 중 바뀐 결정

- 처음 구현은 배율을 일반 출력과 전체 화면 프로그램 모두에 적용했다. 사용자가 전체 화면 프로그램에만 적용하기로 정하면서 범위를 좁혔다. 이에 따라 SRS 제목, 요구 문장, AC-2, AC-3을 고치고 Change Note를 남겼다.
- 기본값은 사용자 요청에 따라 1배로 두었다. 기존 사용자의 스크롤 동작은 바뀌지 않는다.
- 측정 중 끌기 한 번이 길게 누르기로 처리되어 메뉴가 열린 적이 있다. 측정 스크립트가 메뉴를 닫도록 고친 뒤 다시 쟀다. 이 과정은 SRS 증거에는 없고 이 작업의 세션 기록에만 있다.

## 검증

### 자동 테스트

- `frontend/tests/unit/mobileScrollSpeed.test.ts` 8건을 구현 전에 먼저 작성해 실패하는 것을 확인했다. 지금은 8/8 통과한다.
- 터미널 뷰 전용 러너(`terminal-view-behavior`)는 84/84 통과한다.
- tsc 검사(app, editor, test)는 모두 오류 0이다.
- i18nGuards는 7/7 통과한다.
- TerminalResourcePolicy는 재봉인 뒤 21/21 통과한다.
- 범위를 좁히기 전에 돌린 프런트 단위 전체 실행(`tests/unit/*.test.ts`)은 2637건이었고, 실패 목록은 이전과 같았다. 다만 가끔 실패하는 fileListView 한 건이 추가로 실패했다. 이 파일은 단독으로 돌리면 14/14로 통과했다.

### 실측 (ego 브라우저, 390x844 터치 에뮬레이션, 2222 포트, 200px 끌기)

표의 수치는 모두 ego 브라우저에서 끈 뒤 디버그 기록의 이벤트를 세어 얻었다. 일반 출력은 `mobile_touch_scroll_applied`, 전체 화면 프로그램은 `mobile_touch_wheel_dispatched` 이벤트다. 범위를 좁힌 뒤의 측정이며, 근거는 FR-ARCH-015 VE-4다.

| 경로 | 배율 1 | 배율 0.5 | 배율 0.25 |
|---|---|---|---|
| 일반 출력 스크롤 줄 수 | 12줄 | 12줄 | 미측정 |
| 전체 화면 프로그램 휠 신호 수 | 12회 | 6회 | 3회 |

- 배율은 새로고침 없이 바로 적용되었다.
- 설정 화면에 "모바일 터미널" 카드와 "1배 (기본값)" 선택지가 보였다. 이 확인은 범위를 좁히기 전의 실측(VE-2)이다.
- 커밋 직전에 worktree에서 `speckiwi validate --fail-on-warning`을 실행했고 오류 0, 경고 0이었다. `npm run check:srs-change-notes`와 `npm run check:kiwi-status`도 통과했다. 이 결과는 SRS 증거에는 없고 세션 기록에 있다.

### AC별 근거

- AC-1(저장값이 없으면 1배이고 이전과 같은 줄 수): 단위 테스트(VE-3), 실측 배율 1의 12줄과 12회(VE-4)
- AC-2(휠 경로에만 배율 적용, 남은 거리 이월): 단위 테스트(VE-3), 실측의 일반 출력 12줄 유지와 휠 12·6·3회(VE-4)
- AC-3(설정 화면 선택지, 브라우저 저장, 새로고침 없이 적용): 단위 테스트의 소스 단언(VE-3), 설정 화면 확인(VE-2), 배율을 바꿔 가며 잰 실측(VE-4)
- AC-4(잘못된 값과 읽을 수 없는 저장소): 단위 테스트(VE-3)

## 남은 한계

- 테스트 프로그램 화면에는 받은 휠 수가 0으로 나왔다. 위 표의 휠 신호 수는 앱이 보낸 신호를 디버그 기록으로 센 값이다. Windows 콘솔 계층(ConPTY)을 거치며 프로그램이 기대한 형식으로 도착하지 않은 것으로 보이며, 프로그램 쪽에서 받는지는 확인하지 못했다. 실제 아이폰의 Claude Code에서 확인해야 한다.
- `check:consumer-manifest`의 differential `disabledSha256` 불일치는 `origin/main` 81b75d24에도 있는 기존 상태이며, 이번 변경에서 건드리지 않았다.
- 같은 날 확인한 편집기 창 318px 현상은 데스크톱 크기로 연 앱을 새로 고치지 않고 휴대폰 크기로 줄였을 때만 생기는 검증 방식의 산물이었다. 처음부터 휴대폰 크기로 시작하면 창이 화면 전체를 채운다.
