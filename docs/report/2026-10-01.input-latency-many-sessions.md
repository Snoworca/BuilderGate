# 세션이 많을 때 입력이 느려지는 문제 (PERF-BGSTAB-021/022/023)

## 이슈

세션이 수십 개 돌면 입력이 매우 느려졌다. 운영 서버(2002, 29 세션)는 메인 스레드가 80% 바빴고
(Windows 스레드별 CPU 20초 표본), 서버 CPU 는 한 코어 기준 76~165% 였다.

## 원인 (2222 CPU 프로파일로 확정)

스크롤백이 긴 세션이 계속 출력할 때, 서버 메인 스레드가 스크롤백 전체를 글자 칸 단위로 반복 처리했다.

1. **출력 프레임마다 전체 체크포인트 생성** — `sendTerminalFrame` 이 `sourceSeq`/`streamEpoch` 두 값을 읽으려고
   `getRetainedTerminalAuthorityState` 를 불렀고, 그것이 스크롤백 전체를 직렬화·해시했다. 5 세션에서 메인 스레드의 57%,
   GC 34%.
2. **섀도 비교** — 출력이 있는 세션마다 최대 5초에 한 번 스크롤백 전체를 직렬화하고 새 터미널에 재구성해 비교했다
   (1만 줄에서 1회 2.47초, 동기). 결과는 제품에서 쓰지 않는 서버 권한 승격 게이트에만 쓰인다.
3. **스냅샷 이후 출력 꼬리 자르기** — 2MB 상한에 닿은 세션은 청크마다 2MB 문자열 전체를 다시 측정·절단했다
   (20 세션에서 30%).

## 해결

- PERF-BGSTAB-022: 순번만 읽는 `getRetainedTerminalAuthorityOrdinal` 을 추가하고, 프레임마다 부르던 세 곳을 바꿨다.
- PERF-BGSTAB-021: 설정 `terminalAuthority.shadowComparison`(기본 `false`)을 추가했다. 끄면 비교를 예약·실행하지
  않는다. 섀도 수집과 복원 경로는 그대로다. REL-BGSTAB-011 AC-4 에 변경 노트.
- PERF-BGSTAB-023: 꼬리 자르기를 상한의 1.25배를 넘을 때만 하도록 분할 상환했다. 읽는 쪽은 원래대로 다시 자른다.

## 후속 (2026-10-02): 메모리 점검과 v0.10.6 회귀 수정

- 서버 힙 스냅샷(바쁜 세션 24개, 10분): 5.24MB 문자열 42개(122MB). PERF-BGSTAB-023 의 상한을 글자 수로 비교해
  박스 문자·한글 출력이 최대 약 3.7배 보관됐고, 잘라낸 뒤에도 이전 문자열이 남았다. 상한을 UTF-8 바이트로 되돌리고
  자를 때 복사하도록 고쳤다.
- 나머지: 서버 터미널 버퍼 세션당 약 4.3MB(52칸 기준, 폭에 비례), 전달 대기열·기록 객체는 모두 상한이 있다.
  새로고침 30회·전환 40회·세션 삭제에서 누수 없음.
- 브라우저: 메인 스레드 78~86% 유휴, JS 힙 45~57MB, 누수 없음. 전환 시 100~260ms 끊김(숨겨진 터미널 스냅샷 재생).
- 운영(2002)은 세션 29개로 3.7GB. 디버거를 붙일 수 없어 OBS-BGSTAB-011 로 상태 로그에 메모리 내역을 추가했다.
