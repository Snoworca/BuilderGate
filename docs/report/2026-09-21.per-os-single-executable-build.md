# 릴리스 산출물을 OS별 단일 실행 파일로 되돌린다 (OPS-BGSTAB-017)

- 요구사항: `OPS-BGSTAB-017` — Release builds produce one executable per OS, and that executable boots
- 대상: `0.5.5-buildergate-stability`
- 일자: 2026-09-21
- 기준 커밋: `cc42461b`

## 요청

> OS 별 빌드하도록 합시다. 윈도우/리눅스/MAC 이렇게요.

앞선 연구(같은 세션)에서 확인한 것: `npm run build` 가 `node.exe` 와 `server/node_modules` 를 통째로 복사하는 portable 런타임을 만들고 있었고, 단일 실행 파일 빌드는 이미 존재하지만 기본값에서 강등된 상태였다.

## 문제

### 1. 기본 빌드가 단일 실행 파일이 아니었다

`npm run build` → `tools/build-portable-runtime.js`. linux-amd64 산출물이 **277 MB / 6,324 파일**이다. `server/node_modules` 를 필터 없이 복사하므로 devDependency 가 그대로 실린다(`typescript` 23 MB, `@esbuild` 11 MB, `@types` 2.9 MB). node-pty prebuild 는 네 플랫폼 것이 전부 들어가며 `.pdb` 디버그 심볼까지 포함해 60 MB — win32-x64 런타임이 실제로 필요한 것은 2.5 MB 다.

단일 실행 파일 빌드(`tools/build-daemon-exe.js`)는 `4c8b7f93`(2026-05-06)에서 `build:pkg:*` 로 강등됐다. **이유를 적은 요구사항도 보고서도 없다.** 그 빌드의 `validateBuildOutput` 은 지금도 실행 파일 옆의 `server/`·`tools/`·`node_modules`·Node 바이너리를 금지 경로로 열거하고 있고, 그 테스트 이름은 `validateBuildOutput accepts complete TTTGate-style dist/bin runtime` 이다.

### 2. 만들어진 실행 파일이 부팅하지 못했다

```
./buildergate --foreground -p 2222
[start] Failed: The "path" argument must be of type string or an instance of URL. Received undefined
```

원인은 esbuild 다. 서버를 `format: 'cjs'` 로 번들하는데 CJS 에는 `import.meta` 가 없어 esbuild 가 **빈 객체로 치환**한다. 가드 없는 `fileURLToPath(import.meta.url)` 은 `fileURLToPath(undefined)` 가 되어 던진다. esbuild 는 경고만 남기고 빌드는 성공하므로, **증상은 실행 파일이 뜨지 않는 것뿐이고 빌드 로그는 초록이다.** 그리고 패키지 경로는 CI 에도 릴리스 파이프라인에도 없어서 아무도 실행해 보지 않았다.

`index.ts:197` 하나라고 보고 고쳤는데 **같은 에러가 그대로 났다.** 벤치마크 쪽 사이트도 모듈 초기화 시점에 던지기 때문이다. 번들의 세 곳을 모두 가드하고 다시 말았을 때 비로소 떴다.

소스 가드를 붙이자 grep 이 찾지 못한 두 파일이 더 나왔다 — `import.meta.url` 을 다른 모양으로 읽고 있었다. 최종 7곳 / 4파일:

| 파일 | 줄 |
|---|---|
| `server/src/index.ts` | 197 (FR-BGSTAB-030, 2026-09-20) |
| `server/src/benchmarks/terminalFairnessCharacterization.ts` | 281, 304, 499, 2398 (**봉인 소스**) |
| `server/src/benchmarks/retainedStateLegacyBoundary.ts` | 127 |
| `server/src/benchmarks/terminalCharacterization.ts` | 206 |

이 저장소는 이미 올바른 모양을 알고 있었다 — `SSLService.ts:19`, `utils/config.ts:30`, `SessionManager.ts:4400` 셋 다 `typeof __dirname === 'string' ? __dirname : …` 로 가드되어 있다. 가드를 못 받은 쪽만 빠졌고, 그래서 가드는 요구사항이 아니라 **테스트**로 박았다.

### 3. FR-BGSTAB-030 이 패키지 모드에서 매번 오탐했다

패키지 실행 파일이 뜰 때마다:

```
[Provenance] This runtime is serving files from outside the checkout it was loaded from.
[Provenance]   running code: /snapshot/ProjectMaster-issue2-20260916
```

pkg 안에서 모듈은 디스크에 없는 `/snapshot/…` 에서 로드되고, config 와 web 은 실행 파일 옆의 실제 경로다. 그래서 세 root 가 전부 "외부"로 판정된다. FR-BGSTAB-030 자신이 *올바른 시작마다 뜨는 경고는 아무도 읽지 않는다*고 적고 있으므로 무시가 아니라 구분이 답이다.

## 해결

| 변경 | 내용 |
|---|---|
| `import.meta.url` 가드 | 4파일 7곳. 봉인 소스가 포함되므로 authority 를 **build → publish → build → verify** 순서로 재발행 |
| `runtimeProvenance.ts` | `packagedExecutableDir` 입력 추가. 패키지일 때 anchor 를 실행 파일 디렉터리로 — `runtime-paths.js` 가 이미 패키지 root 로 해석하는 그 경로다. **검사를 끄지 않는다** |
| `build-daemon-exe.js` | 타깃별 node-pty asset. pkg `--config` 로 전달 |
| `build-daemon-exe.js` | 호스트 지원 판정. Linux 타깃은 아키텍처가 맞는 호스트에서만 |
| `build-daemon-exe.js` | Windows 아이콘 단계는 비-Windows 호스트에서 건너뛴다 |
| `package.json` | `build` 계열을 exe 빌더로. portable 은 `build:portable*` 로 보존 |
| `release.yml` | 산출물 단언을 단일 실행 파일 형태로. **금지 경로 검사 추가** |
| `packaged-bootstrap-smoke.js` | 기본 포트 2002 → 2222 |

### 타깃별 asset

정적 `prebuilds/**/*` 는 모든 플랫폼 것을 모든 실행 파일에 넣었다. **리눅스 바이너리 안에 `winpty-agent.pdb` 와 `OpenConsole.exe` 가 들어 있었고**, 그건 추측이 아니라 빌드된 산출물에서 문자열로 읽어낸 것이다.

Windows 목록(`pty.node`·`conpty.node`·`conpty_console_list.node`·`winpty.dll`·`winpty-agent.exe`·`conpty/*`)은 **그 목록만 담은 exe 로 conpty·winpty 두 백엔드를 실제로 돌려서** 정했다. 둘의 escape sequence 가 달라(`?9001h` vs `[0m`) 서로 다른 경로를 탔음이 보인다 — winpty 는 #117 설정 UI 에서 도달 가능하므로 빼면 안 된다.

macOS 는 `spawn-helper` 를 추가한다. node-pty 는 `__APPLE__` 에서만 이걸 exec 하고(`src/unix/pty.cc`) Linux 는 직접 fork/exec 하므로 Linux 목록에는 없다.

Linux 는 prebuild 자체가 없다. node-pty 1.1.0 은 darwin-{arm64,x64}·win32-{arm64,x64} 만 배포하고 Linux 는 설치 시 컴파일한다. 그래서 Linux 타깃은 **같은 아키텍처 호스트에서만** 실화다.

## 함정: pkg `--config` 의 glob 기준 디렉터리

타깃별 asset 을 넘기려면 `--config` 가 필요한데(pkg 는 `package.json` 과 `--config` 를 동시에 거부한다), **pkg 는 그 파일의 `scripts`/`assets` glob 을 config 파일 자신의 디렉터리 기준으로 푼다.**

config 를 `dist/` 아래 두자 `server/dist-pkg/*.cjs` 가 `dist/server/dist-pkg/*.cjs` 로 풀려 아무것도 매치하지 않았다. pkg 는 **exit 0** 으로 끝났고, 70 MB 짜리 그럴듯한 실행 파일을 썼고, 그 안에는 서버 번들도 node-pty 도 없었다. `validateBuildOutput` 은 통과했다 — 그것이 검사하는 것은 전부 실행 파일 **옆**이기 때문이다.

측정: config 를 ROOT 로 옮기자 같은 바이너리의 `node-pty` 문자열이 0 → 16, `Provenance` 가 0 → 34 가 됐다.

### 여기서 계측기를 한 번 틀렸다

이 함정을 막으려고 실행 파일 안에 marker 문자열이 있는지 보는 가드를 넣었다. **그 가드가 정상 win-amd64 빌드를 실패시켰다.** Windows 바이너리는 경로 형태 marker 를 그대로 담지 않는다. 그리고 음성 대조군(glob 이 아무것도 매치하지 않는 config)을 만들어 보니 심볼 형태 marker 는 **망가진 바이너리에도 전부 존재**했다 — 판별력이 없다.

그래서 그 가드를 **제거**했다. 잘못 빨개지는 가드는 없는 가드보다 나쁘다. 대신 실제로 깨졌던 불변식을 단위 테스트로 박았다: config 파일은 ROOT 에 있어야 하고, 타깃마다 다른 이름이어야 하며, 빌드가 끝나면 지워져야 한다.

## 남은 것

- **macOS 는 빌드만 확인했다.** macOS 호스트가 없다. `spawn-helper` 는 다른 어느 타깃도 쓰지 않는 경로이고, pkg 스냅샷에서 exec 가능한지는 측정하지 못했다.
- **pkg 가 네이티브 모듈을 어디에 푸는지 모른다.** 실행 파일 옆에도 Windows `%TEMP%` 에도 아무것도 남지 않는다(실행 중·후 모두 확인). 읽기 전용 설치 디렉터리와 AV 환경에서의 동작이 여기에 달려 있으므로 릴리스 전에 확인해야 한다.
- **패키지 모드에서 fair scheduler 가 비활성일 수 있다.** `TerminalResourcePolicyCanary` 가 `terminalFairnessCharacterization` 의 self-location 을 거치는데, 그 함수는 `src/` 와 `dist/benchmarks/…` 두 런타임만 지원하고 번들은 세 번째다. 기본 terminal authority 가 `legacy` 라 부팅에는 영향이 없었으나 측정하지 않았다.
- **선재 실패 7건** (전부 `cc42461b` 에서 재측정해 확인, 2026-09-21):
  - `node-pty ConPTY helper fork is patched with windowsHide`, `node-pty hidden-console patch is idempotent` — `tools/daemon/node-pty-windows-hide.test.js`
  - `terminal snapshot eviction removes old snapshots while preserving the current session save` — `tools/daemon/terminal-snapshot-quota.test.js`
  - `MIG-BGSTAB-002` 4건 — `server/src/services/TerminalAuthorityController.test.ts`
  - 원인은 측정하지 않았다. 이름이 아니라 실패 서명으로 대조했다.

## 안전

TCP 2001/2002 는 작업 내내 미접촉이다(PID 30596, 시작·종료 시점 동일). 2222 검증은 두 번 모두 실행 파일 경로와 명령줄로 소유를 확인한 뒤 해당 PID 하나만 종료했고(`/T` 미사용), Windows 실행 시에는 상속된 `BUILDERGATE_*` 15개를 자식 환경에서 전부 제거한 뒤 띄웠다.
