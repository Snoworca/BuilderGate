# 런타임 provenance 관측과 키 불일치 진단 (FR-BGSTAB-030)

## 발견 경위

사용자 요청으로 2222 서버를 WSL 에서 내리고 cmd.exe 를 통해 Windows 기반으로 띄우는 중에
나왔다. 기능 작업이 아니라 운영 시도에서 나온 것이며, 둘 다 **틀린 런타임이 맞는 것처럼
보이는** 같은 모양이다.

## 발견 1 — cmd.exe 는 설치본 환경을 상속하고, 서버는 조용히 그것을 따른다

Windows 환경에 `BUILDERGATE_*` 가 15개 설정돼 있고 전부 설치본
(`C:\Work\agent-tools\builder-gate__`)을 가리킨다. WSL 셸에는 하나도 없다.

이름을 아는 4개만 지우고 이 체크아웃의 `dist\index.js` 를 띄운 결과:

- 서버 정상 기동, `/health` **200**
- 그러나 `[Static] Production assets served from C:\Work\agent-tools\builder-gate__\web`
- `2FA: TOTP` (이 체크아웃의 설정은 `Disabled`) — 설치본 config 를 읽었다는 뜻

**관측 가능한 신호 중 어느 것도 이것을 말하지 않았다.** 기동 로그에 한 줄이 있었지만
health 를 본 사람에게는 도달하지 않는다.

즉시 내리고 설치본을 감사했다: 실행 창(09:23:30~09:24:10)에 쓰인 설치본 파일 **0건**,
데몬 상태 파일과 `config.json5` 원래 날짜 그대로, 운영 데몬 정상(세션 28개).

## 발견 2 — 설정 암호화가 플랫폼에 묶여 있고, 실패가 원인을 말하지 않는다

```ts
const machineId = `${os.hostname()}-${os.platform()}-${os.arch()}`;   // server/src/index.ts
```

`os.platform()` 만 다르므로(`linux` vs `win32`) 마스터 키가 갈리고, WSL 에서 암호화된
`config.json5` 를 Windows 가 복호화하지 못한다. 표면에 나온 것은 node 의 GCM 원문뿐이었다:

```
Decryption failed: Unsupported state or unable to authenticate data
    at CryptoService.decrypt (...)
    at AuthService.initializeJwtSecret (...)
```

이 문장은 **손상된 값·잘린 값·다른 키로 암호화된 값 모두에 대해 똑같이 참**이고, 어느
것인지 말하지 않는다. 실제로 일어나는 것은 마지막이다.

## 해결

### AC-1 · AC-2 — `server/src/utils/runtimeProvenance.ts`

판정의 기준점은 이미 존재하고 환경변수가 옮길 수 없다: **실행 중인 모듈 자신의 디렉터리.**
`dist/index.js` 는 환경이 뭐라 하든 정확히 한 체크아웃에 있다.

- 기동 시 `serverRoot`·`configPath`·`webRoot` 가 그 체크아웃 밖이면 `[Provenance]` 경고가
  **변수 이름과 해석된 경로**를 지목한다. 크립토 초기화보다 **먼저** 출력한다 — 복호화 실패가
  그 몇 줄 뒤에서 던져지므로, 뒤에 두면 원인을 설명하는 유일한 줄이 영영 안 보인다.
- `/health` 가 `rootsForeign`(boolean)과 `buildId`(서빙 중인 번들 sha256 앞 12자)를 낸다.
  **절대 경로와 비밀값은 넣지 않는다** — `/health` 는 인증이 없고, 경로는 대가 없는 노출이다.

포함 판정은 `startsWith` 가 아니라 `path.relative` 로 한다. 형제 체크아웃 `checkout-a2` 는
`checkout-a` 와 접두사를 공유하며 다른 트리다. 앵커 자체에도 조용한 off-by-one 이 둘 있는데
(모듈 디렉터리 기준이면 정상 배치를 foreign 으로 보고, 한 단계 더 올라가면 모든 형제가
local 로 보임) **후자를 실제로 썼고 형제-접두사 테스트가 출하 전에 잡았다.**

### AC-3 — `CryptoService` 의 `keySourceLabel`

키 유도 자체는 바꾸지 않는다. 바꾸면 기존 config 가 전부 무효가 된다. 대신 실패를 읽을 수
있게 만든다:

```
Decryption failed: Unsupported state or unable to authenticate data. This value was most
likely encrypted with a different master key. This process derives its key from
"DESKTOP-LCF0D3R-linux-x64", which includes the platform, so a config written by a
different platform on the same machine cannot be read here.
```

**경계가 중요하다**: `enc(...)` 형식이 아닌 값은 키 탓으로 돌리지 않는다. 모든 실패에
"키가 틀렸다" 를 붙이면 대체한 메시지만큼이나 무정보하고, 방향만 새로 틀린다.

## 검증

단위 12/12(`runtimeProvenance.test.ts` 7, `cryptoServiceKeyMismatch.test.ts` 5).
단위는 로직을 보증하지 배선을 보증하지 않으므로 **실서버 3-arm** 을 한 빌드에서 돌렸다:

| arm | 조건 | 결과 |
|---|---|---|
| A | `BUILDERGATE_*` 전부 제거 | 경고 0건, `rootsForeign:false`, `buildId:ba6bae7491dc` |
| B | `BUILDERGATE_WEB_ROOT` → 남의 트리 | 경고가 변수·경로 지목, `rootsForeign:true` |
| C | `BUILDERGATE_CONFIG_PATH` → win32 로 암호화된 config | 원래 실패 재현, 메시지가 원인 지목 |

B 는 **설치본이 아니라 임시 디렉터리**를 가리켰다 — 위험을 재현하는 일이 그 위험의 대상을
건드려서는 안 된다. C 는 `[Provenance]` 경고를 내지 **않는데** 그것이 맞다: 그 config 는
체크아웃 안이라 foreign 이 아니고 키만 틀렸다. **두 가드가 서로를 대신 울리지 않는다.**
