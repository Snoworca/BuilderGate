# 모바일 터미널 경로 열기와 HTML 뷰어 수정 (#193, #194)

## 개요

이 보고서는 아이폰 Safari에서 확인된 두 이슈를 커밋 `55d6396d`에서 고친 결과를 기록한다. 이슈 #193은 터미널 경로 열기(FR-ARCH-013)이고, 이슈 #194는 모바일 HTML 뷰어(FR-MDE-028)다. 작업일은 2026-10-28이고 브랜치는 `fix/mobile-path-open`이다.

## 이슈 1: 아이폰 터미널 경로 열기 (#193)

### 증상

- 모바일 Ctrl 래치를 켠 채 경로를 탭해도 파일이 열리지 않았다.
- 길게 누르기 메뉴가 '확인 중…'에서 멈췄다.

### 문제 원인

- 터치 탭이 `TerminalRuntimeLayer`의 `onClickCapture`에서 포커스 처리만 되었다. Ctrl 래치 상태에서 경로를 여는 처리가 없었다.
- `MobileContextMenuDialog`가 `items`를 `useState`로 한 번만 복사했다. 그래서 뒤에 갱신된 항목이 화면에 반영되지 않았다.
- 경로 확인 요청이 응답하지 않으면 메뉴가 끝없이 기다렸다.

### 해결 방법

- `latchedTapPathOpen.ts`의 `openPathOnLatchedTap`을 추가했다. 래치가 켜져 있고 탭 근처에 경로가 있으면 그 경로를 연다. 한 번만 켠 래치는 이때 꺼지고, 잠근 Ctrl은 그대로 유지된다. 근처에 경로가 없으면 포커스만 하고 래치도 그대로 둔다. (AC-6 수정, AC-10 추가)
- `contextMenuNavigation.ts`의 `resolveContextMenuPages`로 갱신된 항목을 따르게 했다. (AC-11)
- `terminalPathVerification.ts`의 `checkMenuPaths`는 `MENU_PATH_CHECK_TIMEOUT_MS`(5초)까지만 기다린다. 확인하지 못한 경로는 그대로 표시한다. (AC-12)

## 이슈 2: 모바일 HTML 뷰어 (#194)

### 증상

- 다시 불러오기 버튼이 보이지 않았다.
- PC용 시안이 좁은 폭에 다시 배치되고 글자가 커졌다.
- 두 손가락으로 확대하면 앱 전체가 확대되었다.

작업 중 발견한 회귀: 확대용 조작 면을 처음 넣었을 때, 그 면이 시안의 터치를 모두 가로채서 시안 내부를 스크롤하거나 클릭할 수 없었다. 사용자가 확인해 알려 주었고, 같은 작업에서 고쳤다(FR-MDE-028 AC-11 수정 Change Note).

### 문제 원인

- HTML 툴바가 `.editor-code-toolbar`의 `justify-content: flex-end`를 물려받았다. 넘친 부분이 왼쪽으로 잘려 버튼이 보이지 않았다.
- 뷰어 폭에 맞춰 시안을 그려서 PC 배치와 글자 크기가 달라졌다.
- 시안은 다른 출처로 격리된 iframe에 들어 있다. 앱은 그 안의 터치를 받을 수 없고, iOS Safari가 페이지 전체를 확대한다.

### 해결 방법

- `.html-tab-toolbar`에 `justify-content: flex-start`를 주었다. (AC-9 결함 수정)
- 뷰어가 1280px보다 좁으면 시안을 1280px로 그린 뒤 축소한다. 툴바의 "1280 맞춤" 버튼으로 실제 폭 보기와 전환한다. (AC-10)
- 터치 화면의 맞춤 보기에서는 시안 위에 조작 면을 덮는다. 그래서 시안만 확대된다(최대 실제 크기의 2배). 두 번 탭하면 실제 크기와 맞춤 크기를 오간다. (AC-11)
- 위의 회귀를 고치려고 편집기 텍스트 끝에 보조 스크립트를 붙여 draft 경로로 불러오고, 앱 창의 `postMessage`로 스크롤과 클릭을 전달하게 했다. 보조 스크립트는 앱 창에서 온 메시지만 따른다. 서버에 스크립트를 넣는 방법은 운영 중인 2222 서버를 재시작해야 반영되므로, 클라이언트에서 처리했다. 그래서 서버 파일은 바꾸지 않았다. 마우스 환경과 실제 폭 보기는 그대로 두었다.

## 검증

### 자동 테스트

- 새 단위 테스트를 먼저 실패시킨 뒤 구현했다. 대상은 `latchedTapPathOpen`, `contextMenuNavigation`(4건 추가), `terminalScreenPathVerification`(4건 추가), `htmlTabToolbarOverflow`(2건), `htmlFrameFit`(5건), `htmlFrameZoom`(10건)이다.
- 마지막 수정 뒤 돌린 프런트 단위 전체 실행(`tests/unit/*.test.ts`)은 2630건이며, 그중 실패 15건은 변경 전과 같은 목록이다. 전용 러너 대상 9건과 `git*` 6건이다.
- tsc 검사(app, editor, test)는 모두 오류 0이다. node와 e2e-ownership 프로젝트는 이번 변경 범위 밖이라 돌리지 않았다. `i18nGuards`는 7/7 통과다. `TerminalResourcePolicy`는 21/21 통과다.

### 실측 (ego 브라우저의 390x844 터치 에뮬레이션, 2222 포트)

아래는 이 작업 중 ego 브라우저로 직접 측정한 결과다. 앞의 두 항목은 SRS 증거에 수치가 없고 이 작업의 세션 기록에만 있다. Ctrl 래치 탭은 키보드 높이를 흉내 내려고 visualViewport 높이를 500으로 바꾼 상태에서 측정했다.

| 항목 | 결과 |
|---|---|
| 길게 누르기 메뉴 갱신 | 0.3초 안에 갱신됨 |
| Ctrl 래치 탭 | 파일이 열리고 래치가 해제됨 |
| 툴바 | 밀어서 모든 버튼에 닿음 |
| 1280 맞춤 | 배율 0.248 |
| 4배 확대 | 시안 배율 0.994, 앱 확대 배율 1 유지 |
| 한 번 탭 | 시안 버튼 클릭(clicks 1) |
| 200px 끌기 | 메시지 10건으로 시안 기준 805px 스크롤을 요청했고, 결과 위치는 y 810 |

### SRS

- FR-ARCH-013과 FR-MDE-028에 AC, 증거, Change Note를 남겼다.
- `speckiwi validate --fail-on-warning` 결과는 오류 0, 경고 0이다. `check:srs-change-notes`(Change Note 유실 없음)와 `check:kiwi-status`(지문 일치, lock 없음)도 통과했다.

## 남은 한계

- 실제 아이폰 Safari에서 확대와 스크롤을 직접 확인하지 못했다. ego 브라우저의 터치 에뮬레이션으로만 확인했다.
- 관성 스크롤이 없다. 한 번 탭 클릭은 약 0.3초 늦게 일어난다. 입력란에 글자를 넣는 조작은 실제 폭 보기에서 해야 한다.
- 폰에서 편집기 창이 화면 전체 폭이 아니라 약 318px로 열린다. 이 현상은 별도 문제로 남겼다.
- `check:consumer-manifest`는 `origin/main` 6ecd33d4에서도 같은 differential `disabledSha256` 불일치로 실패한다. 이 변경과 무관하다.
