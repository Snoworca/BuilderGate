# Issue #24 — `command-presets.json.tmp` write race

| | |
| --- | --- |
| Issue | [Snoworca/BuilderGate#24](https://github.com/Snoworca/BuilderGate/issues/24) |
| Requirement | REL-BGSTAB-022, `docs/spec/30.buildergate-stability.srs.md` |
| Target | `0.5.5-buildergate-stability` |
| Baseline HEAD | `e7c162c` |
| Host | Linux/WSL2, node v24.21.0 |

## The issue

Multiple `tsx` watchers sharing one worktree reacted to the same source change
and raced on the `server/data/command-presets.json.tmp` → `command-presets.json`
rename. On Windows that raised `EPERM` and killed the dev instance outright. Two
instances (ports 2380 and 2402) died this way on 2026-08-12, and the dead
instances then failed unrelated E2E specs, which was misdiagnosed as product
defects.

## What the investigation found

The reported symptom is one of three failures that follow from the same cause,
and the scope is wider than the one file in the title.

**Seven writers, not one.** Five JSON stores under `server/data/` were unsafe.
Four publish with an identical shape — write `dest + '.tmp'`, copy `dest` to
`dest + '.bak'`, rename — where the temp path is derived from the destination
and is therefore the same string in every process sharing the checkout
(`CommandPresetService`, `WorkspaceService`, `TerminalShortcutService`,
`RecoveryOptionService`). A fifth, `AgentLifecycleService`, had no temp file at
all: it wrote `agent-command-profiles.json` straight onto its destination, with
no rename and no backup, so a reader could see a half-written document and a
process dying mid-write destroyed the store. Two more —
`McpControlConfigStore` and `WebhookInvocationService` — already named their temp
file per instance and so never produced the crash, but neither retried its
rename, which leaves them exposed to the Windows destination contention the
retry exists for. All seven are in scope.

**Three failures, measured (2026-09-16, node v24.21.0, Linux/WSL2).**

1. *The publish fails.* Two processes each running the `CommandPresetService`
   publish sequence 300 times against one shared temp path: **293 of 600
   publishes (48.8%) failed `ENOENT`** on the rename, because the peer's rename
   had already moved the shared temp file away. Reproduced twice with the same
   total.
2. *A publish moves a document it did not write.* Deterministic, not
   statistical: a publish writes the shared temp file, a peer overwrites it
   before the first reaches its rename, and the rename moves the peer's bytes
   into place while the call resolves with no error. Reproduced directly —
   writer A wrote `A-change`, writer B overwrote the temp path with `B-change`,
   A's rename resolved, and the destination held `B-change`.
3. *A publish moves a partially written document.* **539 of 4,000 and 598 of
   4,000 publishes (13.5%, 14.9%)** moved a file that does not parse as JSON. The
   mechanism is not `fs.writeFile` splitting into several writes — for these
   payload sizes it does not. Each writer opens the shared path with `O_TRUNC`
   and writes from offset zero, so a shorter document laid over a longer one
   leaves the shorter document's bytes at the head and the longer one's tail
   beyond them. Instrumented over four runs, **2,914 of 2,923 torn publishes**
   were byte-for-byte that overlay.

**Why the process died rather than logged.** `index.ts:1028-1042` awaits
`initialize()` on the four temp-file stores during bootstrap, and
`CommandPresetService.initialize()` and `TerminalShortcutService.initialize()`
call `flushToDisk()` on every path through them with no guard. A rejection
reaches the `catch` at `index.ts:1654-1657`, which logs
`[Fatal] Failed to start server:` and calls `process.exit(1)`. Every start opens
the window; losing the race kills the instance.

## The decision

A shared helper, `server/src/utils/atomicStoreWrite.ts`, that all seven stores
publish through. It does four things:

1. names the temp file per write — `${dest}.${pid}.${randomUUID()}.tmp`;
2. publishes the backup the same way, through its own private temp file and a
   rename, instead of `copyFile` in place onto a shared `.bak`;
3. retries a rename that fails with `EPERM`, `EACCES` or `EBUSY` up to four times
   after the first attempt, waiting 10, 20, 40 and 80 ms — five attempts and
   about 150 ms;
4. on failure unlinks only the temp files that call created.

The per-instance naming is not an invention: `McpControlConfigStore` and
`WebhookInvocationService` already did it. This generalises an existing in-repo
convention that had been applied to two writers out of eight.

### What was rejected, and why

- **Retry alone** — the cheapest of the three directions the issue lists, and it
  reaches only the first of the three failures. A publish that moves a peer's
  bytes into place raises no error at all, so there is nothing for a retry to
  observe. Retry is kept, but as a complement to a private temp path, never as a
  substitute: two instances still rename onto the same destination, and on
  Windows that rename is refused while a peer holds the destination open.
- **A cross-process lock file** — a dev instance that is killed leaves the lock
  held, so the design immediately needs liveness detection and a staleness
  timeout: more mechanism than the thing it replaces. It also buys nothing
  semantically, because two instances legitimately hold divergent complete
  snapshots, so serializing them orders the overwrite without preventing it.
- **A per-instance destination path**, as the issue suggests by analogy with
  `workspace.dataPath` — a data-layout change rather than a bug fix. In a
  deployment the store is meant to be a single source of truth, and splitting it
  per instance would make two instances of one installation disagree
  permanently. It would also make correctness depend on every operator
  configuring it.
- **The `dev.js` watcher structure**, which the issue also names — restarting
  less eagerly narrows the window without closing it, and leaves the store unsafe
  for any other pair of processes. Declared out of scope in the requirement with
  a reopen condition.
- **`data/totp.secret`** (`TOTPService`), found during review, is the same defect
  class — a bare `writeFileSync` onto the destination — but is declared out of
  scope with a reason: its failure mode is divergent credentials rather than a
  torn document, it is written once at first setup rather than on every flush,
  and routing a credential through a temp file raises a separate question about
  what a stray temp file exposes. It needs its own requirement.

### What the fix deliberately does not do

It does not make concurrent publishes agree. With a private temp name and an
atomic rename the outcome across two instances is last-writer-wins over whole
documents, which is the right semantics here — each instance owns a complete
snapshot and there is nothing to merge — and is what the existing code already
intended. What changes is that a publish either puts its own complete bytes in
place or reports failure, and never reports success for a document it did not
write.

## TDD

Nine acceptance criteria, all covered. Each RED run and each GREEN run is kept as
a separate log; none was overwritten. See
`docs/analysis/2026-09-16.issue24-store-publish/00.evidence-index.md`.

| phase | criteria | RED | GREEN |
| --- | --- | --- | --- |
| PH-001 | AC-1, AC-2, AC-3, AC-4, AC-7 | 5 fail at HEAD | 5 pass |
| PH-002 | AC-5, AC-6 | 5 fail without the retry | 7 pass |
| PH-003 | AC-8, AC-9 | 2 fail with six stores unconverted | 8 pass |

The RED runs for PH-001 and PH-003 were re-verified by stashing the production
change and re-running, so the failures are against the real prior code rather
than against a remembered state.

The fixture interposes the peer deterministically instead of racing. A racing
fixture cannot distinguish a publish that moved a peer's bytes from a peer that
published afterwards, and it reproduces the torn case only sometimes. The peer
always writes to the path a peer can actually reach — the one derived from the
destination — which is why the same fixture still fails against a shared temp
path and passes against a private one, rather than becoming vacuous.

### Two honest qualifications

**AC-6's ENOSPC case is a boundary control, not a RED.** In the PH-002 RED run it
passed, because a helper that never retries also rejects ENOSPC on its first
attempt with no waits. It guards against an implementation that retries every
error. The other five AC-5 assertions are genuine REDs: each counts attempts, so
none can pass against a helper that renames once.

**The Windows `EPERM` branch is injected, not natively reproduced.** `EPERM`,
`EACCES` and `EBUSY` on a rename are Windows semantics. A rename on this
Linux/WSL2 host is not refused because a peer holds the destination open, so
those codes cannot arise here and are injected at the filesystem boundary. The
tests pin the attempt count and the exact wait schedule, so they constrain the
implementation tightly; what they cannot do is prove the real Windows error
arrives. A Windows run remains the stronger check and has not been performed.

## A regression this work introduced and then removed

The first version of the helper called `fs.mkdir(dirname, { recursive: true })`
unconditionally. Four of the stores never did that in their publish path — they
create the directory once in `initialize()` — and REL-BGSTAB-020's and
REL-BGSTAB-021's boundary controls prove a genuine I/O failure still reaches the
caller by pointing the store at a directory that is not there. The helper turned
those failures into successes and **8 tests went red**. The directory creation is
now opt-in (`ensureDirectory`), passed only by the three stores whose own publish
path created it.

This is the failure mode the plan's RISK-05 predicted: routing several call sites
through one helper silently homogenises behaviour that differed on purpose. The
same risk is why a test asserts each store still rejects with the error type it
rejected with before — `WorkspaceService` rethrows the raw error while three
others wrap it in `AppError(CONFIG_PERSIST_FAILED)`.

## Regression result

Acceptance is set equality of failing test names against a baseline recorded at
`e7c162c` before any production change, not an exit code.

- Baseline: **16 failing** across 31 files.
- After: **16 failing** across 33 files — **no new failures**.
- Monolithic runner `npx tsx src/test-runner.ts`: 3 failures, the same 3
  reproduced at the baseline tree with the production change stashed, which is
  how they are classified as pre-existing rather than assumed to be.

One earlier sweep showed a 17th failure,
`TerminalResourcePolicyCanary.test.ts :: PERF-BGSTAB-010 gated real-session PTY
chain settles within the fixture bound after overflow cleanup`. It is recorded
rather than excluded. It is not attributed to this change on four observations
against one: that file passed in isolation on the changed tree three times
(26/26 each) and the second full sweep reproduced the baseline set exactly. It
concerns PTY settling time under a fixture bound and touches no store.
