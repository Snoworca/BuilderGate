# 터미널 한도를 넘겨 열면 워크스페이스 이동 뒤 터미널 출력이 멈추던 문제 수정 보고서

- 날짜: 2026-10-14
- 요구사항: IR-BGSTAB-001 (VE-9, AC-4·AC-11)
- 버전: 0.10.12

## 1. 이슈

`resourceLimits.workspaceRuntime.maxLiveTerminals` 를 32 로 둔 채 터미널을 40개 열면, 워크스페이스를
옮긴 뒤 터미널 화면이 갱신되지 않는 경우가 있었다. 글자를 치고 Enter 를 눌러도 화면에 아무것도
나오지 않았다. 새로고침하면 친 글자와 그 결과가 보였다. 즉 입력은 서버에 도착했고, 출력만 화면에
도달하지 못했다.

## 2. 재현

- 이 체크아웃의 서버를 WSL 에서 2222 포트로 띄웠다. 설정은 `maxTabsPerWorkspace: 16`,
  `maxLiveTerminals: 32` 이고, 재현을 빠르게 하려고 `hiddenRuntimeTtlMs: 1000` 으로 두었다.
- 워크스페이스 4개에 터미널 10개씩, 모두 40개를 만들었다.
- Playwright 스크립트로 워크스페이스를 차례로 옮기면서, 보이는 터미널에 `echo <고유 표식>` 과 Enter
  를 입력하고, xterm 버퍼에 표식이 두 번(명령과 출력) 나타나는지 확인했다.
- 수정 전에는 첫 바퀴나 두 번째 바퀴에서 출력이 멈췄다. 서버 디버그 기록에는
  `output_skipped_delivered_by_authority` 가 찍혔다. 즉 서버는 출력을 바이너리 데이터 평면으로 보냈다.
  브라우저는 그 바이너리 프레임을 받았지만 `[WS] binary frame rejected {scoped: ["unknown-channel"]}`
  로 버렸다.

## 3. 원인

1. 터미널이 한도를 넘으면, 브라우저는 숨겨진 지 오래된 터미널을 내리고 그 세션의 구독을 해제한다.
2. 서버는 구독 해제마다 `terminal-binary:channel-retired` 를 reason `unsubscribed` 로 보낸다
   (`server/src/ws/WsRouter.ts` 의 `retireTerminalBinaryChannels`, `demoteTerminalBinarySession`).
   그런데 그룹 전체를 되돌리는 `rollbackTerminalBinaryGroup` 도 같은 `unsubscribed` 를 보냈다.
   따라서 이 reason 만으로는 "세션 하나가 빠짐" 과 "채널 번호 공간 초기화" 를 구별할 수 없었다.
3. 브라우저(`frontend/src/utils/terminalBinaryNegotiationClient.ts`)는 `session-exited` 와
   `session-deleted` 만 세션 범위로 보고, 그 밖의 reason 은 안전을 위해 채널 표 전체를 `clear()`
   했다(#31 의 결정).
4. 그래서 구독 해제가 한 번만 일어나도 다른 모든 세션의 채널이 표에서 사라졌다. 그 세션들의 출력
   프레임은 디코더에서 `unknown-channel` 로 거절되었다.
5. 복구 요청(`terminal-binary:unknown-channel`)은 `unroutable` 목록으로만 만든다. 그런데 디코더는
   표에 없는 채널을 조회 단계보다 먼저 거절하므로, 그 채널은 `unroutable` 에 들어가지 않았다.
   그 결과 복구 요청이 나가지 않았다.
6. 다른 터미널이 새로 마운트되면 협상(`terminal-binary:negotiate`)이 다시 나가서 표가 우연히 다시
   채워졌다. 그래서 문제가 항상 나타나지 않고 "종종" 나타났다.

한도 이하(예: 32개 이하)에서는 구독 해제가 일어나지 않으므로 문제가 나타나지 않는다.

## 4. 해결

| 파일 | 변경 |
| --- | --- |
| `frontend/src/utils/terminalBinaryNegotiationClient.ts` | `unsubscribed` 를 세션 범위 reason 에 넣었다. 이제 메시지에 적힌 채널만 retire 한다. |
| `server/src/ws/WsRouter.ts` | `rollbackTerminalBinaryGroup` 의 통지 reason 을 `codec-epoch-bump` 로 바꾸었다. 브라우저는 이 경우에 계속 표 전체를 비운다. 이 값은 설계 문서(`docs/research/binary-comms/01-frame-format-and-negotiation.md`)의 reason 목록에 있다. |
| `frontend/src/utils/binaryFrameIntake.ts` | 디코더가 `unknown-channel` 로 거절한 채널도 `unroutable` 에 넣었다. 그러면 기존 배선이 복구 요청을 보내고, 서버는 채널 표를 다시 알린다. retire 된 채널은 넣지 않는다. |

## 6. 남은 사항

- **시작 직후 입력 유실(별개 문제).** 페이지를 연 직후 세션 40개의 구독 응답이 오기까지 약 4초가
  걸린다. 그 사이에 친 입력은 서버로 보내지지 않았다. 새로고침해도 보이지 않으므로 이번 증상과는 다른
  문제다. 이번 수정 범위 밖이다.
- **사라진 출력.** 표가 비어 있던 동안 거절된 프레임의 출력은 복구 요청으로 되살아나지 않는다. 복구
  요청은 채널 표만 다시 받는다. 이번 수정으로 표가 비는 경로 자체가 없어졌으므로, 이 공백은 롤백처럼
  드문 경우에만 남는다.
- **봉인된 소스 갱신.** `WsRouter.ts` 가 바뀌어 fair-scheduler authority 를 새 generation
  `b10b20d7…` 으로 재발행했다(build → publish → build). 소비자 매니페스트는 커밋 직전에 재봉인한다.
