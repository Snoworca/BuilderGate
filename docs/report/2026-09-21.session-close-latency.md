# 세션 닫기가 한참 뒤에 반영되는 문제 (PERF-BGSTAB-012)

- 날짜: 2026-09-21
- 요구사항: `PERF-BGSTAB-012` — 세션 닫기는 프로세스 트리 종료 검증을 기다리지 않는다
- 관련 요구사항: `FR-BGSTAB-011` (Wave 2 검증된 프로세스 트리 종료)

## 1. 이슈

사용자 보고: 터미널 화면에서 오른쪽 버튼 → 컨텍스트 메뉴 → `세션 닫기` 를 선택하면
세션이 즉시 닫히지 않고 한참 뒤에 닫힌다.

## 2. 원인

두 개의 독립된 원인이 겹쳐 있었다.

### 2-1. 클라이언트가 서버 응답을 기다린 뒤에야 탭을 지운다

`frontend/src/hooks/useWorkspaceManager.ts` 의 `closeTab` 은
`await workspaceApi.deleteTab(...)` 이 끝난 뒤에 `setTabs` 를 호출했다.
따라서 서버의 종료 지연이 그대로 화면에 드러난다.
확인 모달은 즉시 닫히므로(`App.tsx` `handleConfirmCloseTab` 이
`setPendingCloseTabId(null)` 을 동기로 호출), 사용자에게는
"모달은 사라졌는데 탭은 그대로" 로 보인다.

### 2-2. 서버가 자손 PID 하나당 전체 프로세스를 다시 열거한다

`WorkspaceService.deleteTab` 은 `sessionManager.terminateSession` 을 `await` 하고,
`processCleanup.mode` 가 `enforce` 일 때(이 저장소 `server/config.json5:26` 의 값)
`DefaultProcessTreeTerminator.terminate` 가 실행된다.

Windows 비-WSL 백엔드에서 그 경로는 `processInfoProvider` 를 통해
`Get-CimInstance Win32_Process` **전체 열거**를 수행하는데, 호출 횟수가
`2 + N` 이다(`N` = 종료 직전에 표본으로 수집된 자손 수).
`2` 는 kill 전 inspect 와 kill 후 inspect 이고, `N` 은
`inspectAfterDelay` 안의 `mergeSampledDescendants` 가 자손 PID 마다
생존 여부를 묻느라 발생한다.

이 파일의 주석은 이미 "노드마다 CIM 을 묻는 것은 5.8초가 들어
어떤 타임아웃으로도 흡수할 수 없다" 고 적고 있었다. 쿼리 스크립트 안에서는
그것을 고쳤지만, 검증 루프가 같은 형태를 다시 만들어 놓았다.

## 3. 실측

측정 호스트: 이 개발 머신, 실행 중 프로세스 1289개.

| 측정 항목 | 값 |
|---|---|
| `Get-CimInstance Win32_Process` 전체 열거 1회 | 3.59s / 3.01s / 3.38s |
| `Get-CimInstance Win32_Process -Filter "ProcessId=N"` (단일 PID) | 6.08s / 2.46s / 2.16s |
| `powershell.exe -NoProfile -Command 'exit 0'` (기동만) | 0.41s / 0.42s |

필터를 걸어도 비용이 비슷하다 — **비용은 열거 크기가 아니라 CIM 자체**이고
PowerShell 기동은 0.41초뿐이다.

`terminate()` 의 전체 열거 호출 횟수(stub provider 로 실측):

| 표본 자손 수 N | 호출 횟수 | 열거 3.2초 기준 예상 소요 |
|---|---|---|
| 0 | 2 | 약 7.2s |
| 1 | 3 | 약 10.4s |
| 3 | 5 | 약 16.8s |
| 8 | 10 | 약 32.8s |

(+ `gracefulWaitMs` 750ms)

WSL 백엔드는 `inspect` 가 즉시 `skipped-unverified` 로 빠져나가므로 이 경로를 타지 않는다
(실측: 0 probe, 0ms). 그러나 **배포본의 탭 28개 중 27개가 `shellType=auto`** 이고,
win32 에서 `auto` 는 `resolveAutoShell` 에 의해 `powershell.exe` / `conpty` 로 해석된다
(`SessionManager.ts` `resolveAutoShell`, `resolveSessionProcessBackend`).
즉 사용자의 세션은 대부분 느린 경로를 탄다.

POSIX(Linux/macOS)에서는 provider 호출이 2–14ms 이므로 이 증폭이 체감되지 않는다.
고정 대기(`gracefulWaitMs` 750ms, 필요 시 `forceWaitMs` 1500ms)만 남는다.

## 4. 해결

### 4-1. 클라이언트: 낙관적 제거 + 실패 시 복구 (AC-1, AC-2)

`frontend/src/hooks/workspaceTabClose.ts` 를 새로 만들어 닫기 절차를
테스트 가능한 seam 으로 분리했다.

- `planTabClose` — 제거 전에 롤백에 필요한 것(탭 본체, 목록 내 인덱스,
  다음 활성 탭, 직전 활성 탭)을 먼저 확보한다.
- `runTabClose` — `applyLocalClose` 를 먼저 호출하고 그 다음에
  `requestDelete` 를 `await` 한다. 거부되면 `revertLocalClose` 와 `reportError`.
- `restoreTabToList` — 원래 인덱스에 다시 끼워 넣는다. 목록에는 모든
  워크스페이스의 탭이 함께 있고 `sortOrder` 는 워크스페이스 안에서만
  유일하므로, 전체 재정렬은 다른 워크스페이스의 순서를 흐트러뜨린다.

`useWorkspaceManager.closeTab` 이 이 seam 을 쓰도록 바꿨다.

복구되지 않는 것 두 가지를 주석으로 남겼다 — mosaic 레이아웃 항목과
터미널 스냅샷 캐시. 전자는 다음 레이아웃 패스에서 탭 목록으로부터 다시
만들어지고 후자는 캐시다.

### 4-2. 서버: 자손 생존 판정을 단일 PID 질문으로 (AC-3, AC-4)

`DefaultProcessTreeTerminator` 에 `processLivenessProbe` 의존성을 추가하고
`mergeSampledDescendants` 가 그것을 쓰도록 했다. 기본값은 `isProcessRunning`
(`process.kill(pid, 0)`) 이며, 이 파일이 PowerShell 쿼리 실패 시 이미 쓰던 판정이다.

이 probe 로는 **kill 결정을 하지 않는다.** 무엇을 "살아남은 자손" 으로
보고할지만 정한다. kill 전 identity 검증은 그대로 `processInfoProvider` 를 쓴다.

결과: 전체 열거 횟수가 `2 + N` → **`2` (상수)** 가 된다.
N=8 기준 10회 → 2회, 예상 32.8s → 7.2s.

## 5. 남은 한계 (고치지 않음)

- **kill 전 열거 1회(약 3.2초)는 남는다.** PID 재사용을 배제하려면 kill 직전에
  살아 있는 프로세스의 identity 를 확인해야 하고, 위 표대로 필터 쿼리도
  같은 비용이다. 줄이려면 identity 확인 방식 자체를 바꿔야 한다.
- **kill 후 검증(750ms + 열거 1회)도 여전히 요청 경로 위에 있다.**
  `FR-BGSTAB-011` AC-5 가 `deleteTab` 이 종료 결과를 `await` 하도록 요구하기
  때문이다. 다만 `deleteTab` 은 그 반환값을 읽지 않으므로 현재로서는 지연
  외의 의미가 없다. 이것을 비동기로 돌리려면 AC-5 승계가 필요하다.
- 결과적으로 서버가 실제로 셸 프로세스 트리를 죽이는 시점은 닫기 후 약 3초,
  요청이 끝나는 시점은 약 7초다. 화면에서는 즉시 사라진다.
