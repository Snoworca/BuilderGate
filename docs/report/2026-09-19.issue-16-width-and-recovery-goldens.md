# issue #16 항목 1·2 — 폭 golden corpus 와 snapshot-recovery golden

- 날짜: 2026-09-19
- 요구사항: FR-BGSTAB-029 (AC-1, AC-2), REL-BGSTAB-011 (AC-2, AC-4)
- 범위: GitHub issue #16 의 항목 1 과 항목 2 만. 항목 3 과 issue #20 은 다른 레인이 소유한다.

## 이슈

**항목 1.** FR-BGSTAB-029 AC-1/AC-2 를 닫고 있던 것은 `frontend/tests/unit/terminalWidthPolicyParity.test.ts`
하나였고, 그것은 두 소스를 **텍스트로 읽어** terminal 생성 옵션과 unicode addon 로드의 비대칭을 대조하는
탐지기다. 같은 바이트에 대해 두 쪽이 실제로 같은 셀 수를 배정하는지는 어디에서도 측정되지 않았다.

**항목 2.** 대체화면 전환, 커서 위치, DECSC/DECRC 저장 커서, 우측 마진의 wrap-pending, 여러 write 에 걸쳐
쪼개진 escape — 이 상태들에서 snapshot 을 떠 복원하면 같은 상태가 되는지를 기록한 golden 이 없었다.

## 문제 원인

정적 가드는 **양쪽이 동일하게 설정된 채 실제 폭이 어긋나는 경우**를 통과시킨다. 가장 현실적인 경로는
`@xterm/xterm` 과 `@xterm/headless` 가 서로 다른 릴리스로 갈라지는 것이고, 그때 두 패키지는 각자의 폭
테이블 복사본을 들고 있다. 소스 텍스트는 하나도 바뀌지 않는다.

항목 2 의 기존 증거(REL-BGSTAB-011 VE-3, registry 57건)는 배선을 실행하지만 **상태 자체를 기록하지 않는다.**
round-trip 비교는 checkpoint 를 자기 자신의 복원본과 견주므로, 양쪽을 똑같이 바꾸는 회귀는 자기 자신과
같다고 비교되어 통과한다.

## 해결 방법

### 항목 1 — `frontend/tests/unit/terminalUnicodeWidthGolden.test.ts` (20 tests)

두 엔진을 **한 Node 프로세스에서 실제로 생성**해 같은 입력을 쓴다. `open()` 을 부르지 않는 한 브라우저
빌드도 DOM 없이 동작하므로 jsdom 이 필요 없고, 따라서 이 파일은 component-render 스크립트가 아니라 평범한
`--experimental-strip-types` 스윕에 속한다.

- 17개 항목: ASCII / 넓은 CJK(한글 음절·한자·전각 라틴) + 대조군으로 반각 가나 / East Asian Ambiguous /
  결합 문자(단일·중첩·조합형 자모 L+V+T) / 이모지(astral·BMP+VS16·ZWJ 쌍·ZWJ 가족·피부톤 수정자) /
  zero-width 와 BOM / C0 제어문자 / 혼합 스크립트 통합 행.
- 항목마다 세 가지를 **이 순서로** 단언한다: 서버 엔진 = golden, 브라우저 엔진 = golden, 둘이 서로 일치.
  마지막 것만으로는 공유 의존성 업그레이드가 양쪽을 똑같이 깨뜨렸을 때 통과한다.
- headless 엔진의 옵션은 `server/src/utils/headlessTerminal.ts` 의 `DEFAULT_TERMINAL_OPTIONS` 를 **파싱해서**
  가져온다. 서버가 옵션을 추가하면 corpus 가 red 가 되지, 프로덕션에 없는 터미널을 조용히 측정하지 않는다.

### 항목 2 — `server/src/utils/terminalSnapshotRecoveryGolden.test.ts` (11 tests)

9개 시나리오 각각에 대해 네 가지를 단언한다.

1. 구동된 터미널의 투영이 기록된 golden 과 일치한다.
2. `compareRetainedHeadlessCheckpointRoundTrip` 의 내부 6축이 모두 `match` 다.
   (folded 결과는 일부러 단언하지 않는다 — `parserTail`·`eviction` 은 호출자가 넘기는 외부 축이라
   여기서는 `unavailable` 로 읽히고, 아무 말도 하지 않는다.)
3. `rehydrateAnsi` 로 복원한 터미널이 같은 투영을 낸다.
4. **원본과 복원본에 같은 다음 바이트를 써서 같은 상태에 도달한다.**

(4) 가 핵심이다. `wrap-pending-at-right-margin` 과 그 대조군은 입력이 한 칸 다르고 보이는 행이 같아서,
다음 글자가 어디에 떨어지는지(1행 1열 대 0행 20열)로만 구별된다. pending-wrap 플래그를 잃은 포맷은
(1)(2)(3) 을 통과하고 여기서만 걸린다.

## 실측 기록

**두 엔진은 17개 항목 전부에서 일치했다.** 특성화로 기록해 둘 것: xterm 6.0.0 내장 UnicodeV6 테이블에서
이 corpus 의 모든 이모지는 **1셀**이고, ZWJ 시퀀스는 이모지 하나당 1셀을 쓴다. 이는 설치된 엔진이 하는
일을 기록한 것이지 옳다고 승인한 것이 아니며, unicode11 addon 을 붙이면 그 행들이 움직일 것이다.

**escape 중간에 뜬 checkpoint 는 parser tail 을 담지 않는다.** `rehydrateAnsi` 는 커밋된 접두사 `pre`
정확히 그것이고, 거기서 복원한 뒤 나머지 바이트를 받으면 `pre1mRED` 가 무채색으로 찍힌다(원본은
`preRED` 가 빨강). 이것은 checkpoint 의 결함이 아니라, REL-BGSTAB-011 AC-2 가 incomplete parser tail 을
별도 항목으로 두고 AC-4 가 `parserTail` 을 별도 축으로 두는 **이유**다. 테스트는 구성적 반쪽도 말한다 —
파킹된 tail 을 나머지 앞에 재생하면 원본이 정확히 재현된다.

## 변이 검증

**31개 테스트 전부를 red 로 관측했다.** 변이 48회, 전부 해당 테스트만 실패시키고 원본으로 복구.

| 대상 | 변이 |
| --- | --- |
| 폭 golden 17개 | 각각 2회 — 첫 셀 폭 +1, `cursorX` +1 |
| 옵션 출처 테스트 | 선언 집합에서 `reflowCursorLine` 제거 |
| 버전 대체 가드 | 다른 패키지의 version 을 보게 바꿈 |
| 폭 corpus 커버리지 바닥 | `emoji-skin-tone-modifier` 항목 이름 변경 |
| 복구 golden 9개 | 각각 `afterContinuation` 의 `cursor.x` +1 |
| 복구 커버리지 바닥 | `wrap-pending-at-right-margin` 항목 이름 변경 |
| parser tail 테스트 | naive 복원이 `preRED` 를 낸다고 주장 |

추가로, corpus 가 **폭 테이블 교체 자체에 반응하는지**를 따로 측정했다. headless 쪽에만 unicode provider 를
등록하면 `emoji-astral` 이 기록된 값에서 움직인다. **한계를 명시한다**: 그 프로브의 수제 provider 는
`charProperties` 의 비트 패킹이 틀려 폭 0 을 냈고, 실제 `@xterm/addon-unicode11` 이라면 2 가 나왔을 것이다.
어느 쪽이든 기록된 1 과 다르므로 민감도 주장에는 충분하지만, addon 의 충실한 시뮬레이션은 아니다.

## 남은 것 (기록만, 이 범위에서 닫지 않음)

- **CI 는 server 의 `*.test.ts` 를 하나도 돌리지 않는다.** `.github/workflows/ci.yml` 의 server 잡은
  `src/test-runner.ts` 만 실행하고, 그 러너는 `*.test.ts` 를 디스커버리하지 않는다. 항목 2 의 새 파일도
  기존 100여 개 server 테스트 파일과 같은 처지다. 직접 호출용으로
  `npm --prefix server run test:snapshot-recovery-golden` 을 추가해 두었다. 디스커버리 격차 자체를 닫는 것은
  이 범위 밖이다.
