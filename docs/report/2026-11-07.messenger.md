# 메신저 기능 구현 완료 보고서

## 이슈 설명

BuilderGate 에 메신저 기능을 추가한다. 목표는 시안 `docs/design/messenger.html` 과 같은 기능을 구현하는 것이다. 요구사항은 `docs/spec/50.messenger.srs.md` 의 FR-MSG-001 ~ FR-MSG-015 이고, 계약은 `docs/design/messenger.contract.md` 에 정의한다. 요구사항 15건은 모두 `implemented` 상태이며 검증 증거 행은 38건이다.

## 문제 원인 (배경)

두 명의 개발자(서버 담당, 프런트엔드 담당)가 야간에 코딩 에이전트를 돌린다. 두 사람 사이의 소통은 Google Chat 웹훅 메시지를 복사해 대상 에이전트 세션에 수동으로 붙여넣는 방식이었다. 여러 PC 사이에서 메시지 순서를 정하고, 기록을 보관하고, 세션에 전달하는 경로가 없었다.

## 해결 방법

- 방(room)을 도입했다. 방을 만든 PC 를 저장 PC 로 두고, 저장 PC 가 메시지 순서를 정하고 로그를 보관한다. 나머지 PC 는 사본을 가지고 저장 PC 와 동기화한다.
- 메시지는 참여 세션에 `[BG-ROOM:<room> | <sender>]` 접두사와 함께 붙여넣는다. 사람 메시지와 에이전트 메시지를 모두 전달한다.
- 멘션을 지원한다. `@세션` 은 1:1 전달, `@사람::세션` 은 특정 사람의 세션으로 전달한다. 1:n 전달도 가능하다.
- MCP 도구 4종을 추가했다: `buildergate.room.list`, `buildergate.room.members`, `buildergate.room.send`, `buildergate.room.history`.
- 에이전트가 연속으로 20건 메시지를 보내면 보류(hold)한다. 메시지가 5건을 넘거나 30분 이상 밀린 경우 요약 줄을 보여준다.
- 연락처는 주소 또는 `bgc1` 연결 코드로 추가한다. 저장 PC 의 연락처가 아닌 사람은 방 티켓으로 초대한다. 방 전용 키를 쓰며, 내보내기(kick) 시 키가 폐기된다.
- 저장 PC 가 오프라인이면 로컬 붙여넣기만 허용하고, 디스크 발신함(outbox)에 쌓은 뒤 저장 PC 복귀 시 전달한다. 저장 PC 를 옮기거나 새 방에서 계속할 수 있다.
- Google Chat 웹훅을 지원한다.
- UI: 헤더 버튼(배지 포함), 모달리스 창, 멘션 선택기, 새 방, 연락처, 참여 대화상자, 멤버 패널, 전달 상태 표시, 배너, 탭과 그리드의 점 표시, 좁은 화면 레이아웃, 한국어와 영어 카탈로그를 구현했다.

## 주요 결정

1. 저장 PC 는 방을 만든 PC 로 한다. 연구 subagent 5명과 교차 검증을 거쳐 팀 허브 방식과 복제형 메쉬 방식보다 이 방식을 택했다.
2. 「사내망 연결 받기」는 별도 TLS 리스너로 분리했다(MCP 포트 + 1). 이 리스너는 `/mcp/peer` 와 `/mcp/contact-request` 만 열고, 사설 주소 대역만 허용하며, 전달 헤더(forwarding header)를 거부한다. 결정위원회 2라운드에서 메인 포트 재사용안이 표결로 나왔으나, 옵션 A 가 이미 구현되어 있었고 역방향 프록시 뒤에서 더 안전하므로 옵션 A 를 유지했다. 이 분리로 로컬 에이전트의 `http://127.0.0.1` MCP 연결이 끊기지 않는다.
3. 실사용(E2E) 중 일반 bash 세션에 붙여넣은 방 메시지가 셸 명령으로 실행되는 문제가 발견되었다. 이후 붙여넣기는 AI 에이전트가 감지된 세션에만 보낸다. 에이전트 감지는 포그라운드 앱(claude, codex, hermes, opencode) 또는 MCP 의 `agentKind` 로 판정한다. 제어 문자는 제거하고, 탭은 공백으로 바꾸며, 여러 줄은 bracketed paste 가 있을 때만 보낸다.
4. 연락처의 이름은 상대 PC 가 보고한 `nodeName` 을 그대로 쓴다. 다른 PC 에 연락처나 방이 남아 있으면 이름 변경을 거부한다.

- 프런트엔드 메신저 및 가드 번들: 146/146 통과.
- 서버와 프런트엔드의 app, test, editor, node 타입 검사: 오류 없음.
- 작업 흐름 중 구현 subagent 3명(서버 방, 서버 연락처·키·사내망, 프런트엔드)은 각자 테스트 우선으로 작업했고 독립 리뷰어가 검토했다. 시안과 SRS 에 대한 적합성 리뷰에서 high 4건(멤버 PC 의 보류 상태, 내보내진 연락처의 재참여, 제어 문자, `@true` 배지)이 나와 모두 수정했다.
- `https://localhost:2222` 에서 오프라인 에이전트 stub 을 두고 E2E 를 5라운드 수행했다. 창 열기, 연락처, 방 생성, 입장 알림, 방 전체 메시지, 1:1 `@` 멘션, 미등록 멘션 차단, Enter 끄기, 여러 줄(bracketed paste 또는 MULTILINE_UNSUPPORTED 로 건너뜀), 제어 문자, 좁은 화면, 방 나가기, 영어 UI 를 확인했고 모두 통과했다.

## 남은 한계

- 여러 PC 에 걸친 흐름은 가짜 전송 계층을 쓴 다중 서버 테스트와 실제 TLS 리스너 테스트로만 검증했다. 두 번째 실물 PC 로는 검증하지 않았다.
- 실제 에이전트 세션 안에서 보류 상태와 `buildergate.room.*` 도구는 실시간으로 검증하지 않았다.
- 저장 PC 는 멤버 PC 가 보고한 사람/에이전트 종류를 그대로 신뢰한다.
- 낮은 우선순위 항목이 남아 있다: 메시지별 실행 카운터(19/20 표시), 「붙여넣음 · 이 PC 안」 상태, 새 방 대화상자의 Enter 토글, 여러 메시지를 한 번의 붙여넣기로 묶기.
- consumer manifest 검사는 차등(differential) 증거 지점에서 여전히 다르다. 이는 이번 변경 이전 HEAD 에서도 같은 상태였으며 기존 문제다.
