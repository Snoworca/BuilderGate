## 4. 이슈가 지적한 일반 문제 — unknown key 무음 strip

이슈 말미의 지적은 **여전히 유효하며 이 이슈의 범위 밖이다.**

정확히는 **파일 전체로는 `.strict()` 가 11군데** 있다
(`config.schema.ts` 의 49, 82, 111, 119, 132, 153, 160, 174, 186, 196, 202행).
문제는 그 분포가 고르지 않다는 것이다 — 깊은 하위 객체는 이미 오타를 거부하는데
최상위와 대부분의 섹션 루트는 그러지 않는다.

`configSchema` 의 최상위 키 13개 기준으로 보면:

| strict (오타를 즉시 거부) | loose (오타를 조용히 버림) |
| --- | --- |
| `realtimeSchema`, `resourceLimitsSchema`(하위 `workspaceRuntime`·`telemetry` 등 포함), `stabilityModesSchema` | 최상위 `configSchema`, `serverSchema`, `ptySchema`, `sessionSchema`(단 하위 `processCleanup` 은 strict), `sslSchema`, `securitySchema`(하위 `corsSchema` 포함), `twoFactorSchema`, `bootstrapSchema`, `authSchema`, `fileManagerSchema`, `workspaceSchema` |

즉 `resourceLimits.telemetry.misspelledIntervalMs` 나 `session.processCleanup` 의 오타는
오늘도 부팅을 막는다(`server/src/schemas/config.schema.test.ts:61-72`).
반면 `workspace.terminalTitleDebouncMs` 는 조용히 사라진다. 후속 warn 경로가 실제로
다룰 대상은 **최상위 + loose 섹션 10개**이지 파일 전체가 아니다.

### 권고: `.strict()` 확대는 안 된다. warn 경로여야 한다

`.strict()` 를 최상위와 나머지 10개 섹션에 확대하면 **현재 정상 로드되는 설정이 거부된다.**
`ed03769` ("구설정 호환성을 유지하며 미사용 설정 제거") 가 세운 `FR-BGSTAB-025` 계약이
바로 그 반대를 단언한다 — `server/src/schemas/config.schema.test.ts:32-58` 의 13개 케이스는
은퇴한 키(`logging.level`, `bruteForce.*`, `auth.maxDurationMs` 등)를 담은 설정이
**파싱에 성공하고 그 키만 사라질 것**을 요구한다. strict 로 바꾸면 이 13개가 전부 red 가 되고,
기존 사용자의 `config.json5` 가 부팅을 막는다.

따라서 권고하는 형태는 **거부가 아니라 경고**다.

1. 로더(`loadConfigFromPath` / `loadConfigFromPathStrict`)에서 parse 전후 raw 키와
   validated 키를 비교해 사라진 키를 수집한다.
2. `FR-BGSTAB-025` 의 은퇴 키 목록에 있으면 "은퇴한 설정" 으로, 없으면 "알 수 없는 키(오타 가능)" 로
   구분해 `console.warn` 한다.
3. 값은 로그에 쓰지 않는다(비밀값 노출 방지). 경로만 쓴다.

이는 로더 동작 변경이므로 자체 요구사항이 필요하다. `FR-BGSTAB-026` 에 끼워 넣지 않는다.
별도 결함으로 오케스트레이터에 보고했다.

## 5. 독립 리뷰 반영

리뷰어(Opus, 읽기 전용, `0abec8b` 관측)가 HIGH 1 / MEDIUM 1 / LOW 2 를 제기했다.

### HIGH — 설정 표면에 두 키가 없다 (수정함)

스키마에는 있지만 **운영자가 보는 파일 어디에도 두 키가 없었다.**
새 설치가 생성하는 부트스트랩 템플릿(`server/src/utils/configTemplate.ts`, `config.ts:203` 이 기록)과
동봉 예제(`server/config.json5.example`) 의 `workspace` 블록은 형제 키 다섯 개만 나열했다.
이슈 제목이 "`config.json5` 로 설정할 수 없다" 인 이상, 값이 도달하더라도 존재를 알 수 없으면
이슈가 닫히지 않는다. 리뷰어 지적이 옳다.

TDD 로 수정했다.

1. RED — 파생을 막는 parity 가드 3건을 먼저 추가(`server/src/utils/configTemplate.test.ts`).
   `workspaceSchema.shape` 의 키 집합과 템플릿(linux/win32)·예제의 `workspace` 키 집합이
   **정확히 같을 것**을 단언한다. 관측된 실패: `actual` 5키 / `expected` 7키,
   그리고 `linux bootstrap: terminalTitleDebounceMs — undefined !== 250`.
2. GREEN — 두 키를 템플릿과 예제에 스키마 기본값(250 / 600)으로 추가.
3. 재실행 — `tests 6 / pass 6 / fail 0`.

가드는 값 하드코딩이 아니라 스키마에서 키 집합을 읽으므로, 앞으로 `workspaceSchema` 에
키가 추가되면 문서화를 빠뜨린 순간 red 가 된다.

### MEDIUM — §4 의 strict 집계가 오해를 부른다 (수정함)

§4 를 위와 같이 고쳐, 파일 전체 `.strict()` 11군데와 최상위 13키 기준 집계를 분리하고
후속 warn 경로의 실제 대상 범위를 명시했다.

### LOW — `corsSchema` 누락 (수정함)

§4 표에 `securitySchema` 하위로 명시했다.

### LOW — 기본값 250/600 이 두 곳에 중복되며 parity 단언이 없다 (수정하지 않음, 기록함)

`config.schema.ts:257-258` 과 `WorkspaceService.ts:121`/`:123` 의 3순위 폴백이 같은 값을
각각 하드코딩한다. `workspace` 섹션이 통째로 없는 설정에서는 후자가 권위값이 되므로
조용한 drift 가 가능하다. 이번 작업으로 **문서 ↔ 스키마** parity 는 고정했으나
**스키마 ↔ 서비스 폴백** parity 는 열려 있다.

수정하지 않은 이유: 근본 해법은 서비스가 리터럴 대신 `workspaceSchema.parse({})` 를
폴백으로 쓰는 것인데, 이는 이슈가 요구하지 않은 프로덕션 동작 변경이다.
소스 텍스트를 읽어 리터럴을 대조하는 방식은 `CLAUDE.md` 가 경고하는 `src/` 전용 취약 테스트
계열을 하나 더 늘린다. 별도 결함으로 오케스트레이터에 보고한다.
