## 이슈 설명

에이전트가 터미널에서 코드를 바꾸면, 사용자는 IDE 없이 브라우저에서 아래 세 가지를 확인할 수 있어야 한다.

1. 세션 하단바의 브랜치 칩
2. Git 창(커밋 그래프와 커밋 상세)
3. diff

첫 버전은 보기 전용이다. 기준 브랜치는 자동으로 감지하며, 사용자가 이를 권장 사항으로 정했다.

## 해결 방법

### 서버

- `GitService`: 비동기 git 실행기를 쓴다. 동시 실행 수는 서버 전체 4개, 저장소당 2개다.
- REST 경로: `/api/sessions/:id/git/{summary,status,log,commit,diff,compare}`.
- 입력은 모두 서버에서 검증한다. fsmonitor, 외부 diff, textconv는 끈다.

### 클라이언트

- MetadataRow 의 칩: 폭에 따라 7단계로 줄어든다.
- 모달리스 Git 창: 그래프, 커밋 상세, diff(한 줄 보기 / 좌우 보기, 숨긴 문맥 펼치기, 특수 파일 10종 안내)를 보여 준다.
- 갱신 규칙: 자동 새로고침을 끌 수 있고, 목록 배지와 diff 배지를 띄운다.
- 모바일: 폭 900px 미만에서는 전체 화면 3단계로 열린다.

### 설계에서 바꾼 것

- WS 대신 REST 폴링을 쓴다. 봉인 소스인 `WsRouter.ts` 를 고치지 않기 위해서다.
- WSL 세션은 셸 실행 명령으로 감지한다.

## 성능 측정 (T18)

측정 조건: 커밋 50,000개, 파일 10,000개인 저장소. 도구는 `server/src/benchmarks/gitSummaryBench.ts` 이고, 커밋 694f6eaf 의 Windows 호스트에서 쟀다.

| 항목 | 목표 | 결과 |
|---|---|---|
| summary (Windows) | p95 ≤ 300ms | p50 245ms / p95 973ms |
| summary (WSL) | p95 ≤ 600ms | p50 553ms / p95 1145ms |
| 칩 클릭 → 첫 diff (Windows) | p95 ≤ 1초 | p50 1.3초 / p95 3.0초 |
| 칩 클릭 → 첫 diff (WSL) | p95 ≤ 1초 | p50 3.1초 / p95 8.7초 |
| wsl.exe 1회 | ≤ 250ms | p50 359ms. 목표를 넘어 WSL 작업 중 폴링을 5초로 바꿨다 |
| 부하: 세션 6개 × 클라이언트 2개 | CPU < 5%, 이벤트 루프 p99 < 50ms | 서버 CPU 0.7%, 이벤트 루프 p99 60.5ms |

측정하면서 git 호출을 다음과 같이 줄였다.

- 기준 브랜치 조회를 한 번의 호출로 합치고 status 와 병렬로 돌린다.
- log 의 rev-parse 두 번을 병렬로 돌린다.
- diff 의 입력 조회를 diff 와 병렬로 돌린다.
- 줄 끝 검사는 줄 끝 변경일 가능성이 있을 때만 한다.

그 결과 작은 저장소의 summary p50 이 510ms 에서 180ms 로 줄었다.

p95 목표와 WSL 목표는 맞추지 못했다. 이 호스트에서는 `git --version` 한 번에도 49~136ms 가 걸린다. 그래서 PERF-GIT-001 은 `in_progress` 로 남긴다.
