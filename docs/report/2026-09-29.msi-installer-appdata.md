# Windows MSI 설치와 LocalAppData 사용자 데이터

- 날짜: 2026-09-29
- 요구사항: OPS-BGSTAB-020 (Windows MSI 는 Program Files 에 설치되고, 사용자 데이터는 버전을 넘어 LocalAppData 에 남는다), 타깃 `msi-install-appdata`
- 커밋: 이 보고서가 들어간 커밋

## 이슈

사용자 요청:
- 버전을 올려도 설정을 공유하고 싶다.
- MSI 로 설치할 수 있게 빌드하고, 사용자 데이터는 사용자 AppData 에 저장한다(Windows 기준).
- 설치형이 아닌 경우에는 AppData 에 쓰지 않는다.
- 설치는 Windows 표준 경로에 한다.

## 원인

- 패키지된 exe 는 모든 경로를 exe 폴더 기준으로 정한다(`tools/daemon/runtime-paths.js`). 대상은 `config.json5`, `data/`(세션 저장·명령 프리셋·Workspace·MCP 토큰 등 9곳), `certs/`, `runtime/`(데몬 상태·로그·TOTP)이다.
- 새 버전 폴더를 풀면 설정이 빈 상태로 시작한다.
- 설치 프로그램은 없었고, 릴리즈에는 zip 만 올라갔다.

## 해결

- **설치판 판별**
  - MSI 가 exe 옆에 `buildergate-install.json` 을 함께 설치한다. zip 에는 이 파일이 없다.
  - `runtime-paths.js` 는 패키지 실행이고 Windows 이며 이 표식이 exe 옆에 있을 때만 `dataRoot` 를 `%LOCALAPPDATA%\BuilderGate` 로 둔다.
  - 표식은 `BUILDERGATE_ROOT` 가 아니라 실행 파일 위치에서 찾는다. 런처가 자식에게 `BUILDERGATE_ROOT` 를 넘기므로, 부모와 자식이 같은 데이터 위치를 얻는다.
- **경로 분리** (설치판만)
  - LocalAppData: `config.json5`, 서버 cwd(`data/`), `certs/`, `runtime/`
  - 설치 폴더: `web/`, `shell-integration/`
  - 명시한 `BUILDERGATE_CONFIG_PATH` 는 여전히 우선한다.
- **첫 실행**: `tools/start-runtime.js` 가 데이터 폴더를 만든다. 그다음 설정 로더가 부트스트랩 `config.json5` 를 그 안에 쓴다.
- **출처 검사**: `runtimeProvenance.ts` 에 `installedDataRoot` 를 추가했다. 이 값은 `serverRoot`·`configPath` 만 로컬로 인정하고, `webRoot` 나 다른 배포본 경로는 여전히 foreign 으로 잡는다. `index.ts` 도 같은 표식 규칙으로 이 값을 구한다.
- **MSI**: `tools/build-msi.js` (WiX Toolset v5)
  - per-machine 설치이고 위치는 `ProgramFiles64Folder\BuilderGate` 이다(amd64·arm64).
  - 고정 UpgradeCode 로 major upgrade 한다. 다운그레이드는 거부한다.
  - 시작 메뉴에 *BuilderGate*·*Stop BuilderGate* 를 추가한다.
  - 업그레이드·제거 전에 기존 exe 의 `stop` 을 실행해 파일 잠금을 푼다.
  - payload 에서 `config.json5` 를 뺀다. LocalAppData 는 건드리지 않으므로 업그레이드·제거 때 사용자 데이터가 남는다.
  - 포터블 폴더를 복사해 staging 하므로 zip 용 폴더에는 표식이 생기지 않는다.
- **릴리즈**: `release.yml` 의 Windows 빌드에 WiX 설치와 MSI 빌드 단계를 넣고, `*.msi` 를 artifact 와 릴리즈에 추가했다.
- **README**: 영문과 한국어 모두에 MSI 설치, 데이터 위치, 빌드 방법을 적었다.
- **데이터 위치**: Roaming 이 아니라 Local 로 정했다. 설정의 암호화 키가 호스트 이름에 묶여 있어서, 로밍된 설정은 다른 PC 에서 복호화되지 않는다.

## 검증

- **단위 테스트**
  - `tools/daemon/runtime-paths.test.js`: 8/8. 새 4건은 구현 전 실패를 확인했다.
  - `tools/daemon/build-msi.test.js`: 5/5. 모듈이 없던 상태에서 실패를 확인했다.
  - `server/src/utils/runtimeProvenance.test.ts`: 14/14. 새 3건 중 2건이 구현 전 실패했다. WSL node 에서 `.js→.ts` resolve hook 으로 돌렸다. Windows node 에서는 이 파일의 POSIX 경로 테스트가 원래 실패한다.
- **실측** (https://localhost:2222)
  - `msiexec /a` 로 푼 설치 이미지의 exe 를 `LOCALAPPDATA`=임시 폴더로 띄웠다.
  - config·certs·data·runtime 이 `…\BuilderGate` 아래에 생겼다.
  - 설치 폴더의 파일 목록은 실행 전후 동일했다.
  - `/health` 는 `rootsForeign:false` 를 냈고, Provenance 경고는 0줄이었다.
  - `exe stop` 이 LocalAppData 의 상태 파일로 데몬을 정상 종료했다.
  - 이어서 표식이 없는 기존 2222 폴더(`win-amd64-0.10.0`)는 자기 폴더의 `config.json5` 와 기존 상태(stateGeneration 25)를 그대로 썼다.
- **MSI 빌드**
  - x64·arm64 모두 빌드된다.
  - `wix msi validate` 는 오류 0 이다. 경고는 ICE60 과 ICE61 이며, ICE61 은 `AllowSameVersionUpgrades` 때문이다.
- **회귀**
  - `test:release-pipeline` exit 0. 소비자 매니페스트는 `index.ts` 해시만 바꿔 재봉인했고, tuples 와 classifications 는 unchanged 다.
  - `tools/daemon/*.test.js` 는 242/245 다. 실패 3건(`node-pty-windows-hide`, `terminal-snapshot-quota`)은 바꾼 모듈을 import 하지 않는다. WSL 과 Windows `node_modules` 차이로 실패한다.
  - server tsc clean, `docs.test.js` 4/4.

## 한계

- 관리자 권한이 필요한 실제 설치·업그레이드·제거와 CI 의 MSI 단계는 아직 돌리지 않았다. 그래서 AC-4 는 체크하지 않았다.
- 코드 서명이 없어 MSI 실행 시 SmartScreen 경고가 뜬다.
- 기존 포터블판의 설정을 설치판으로 자동으로 가져오지 않는다.
- 부트스트랩 설정의 기본 포트는 2002 이다. 운영 데몬이 2002 에 떠 있는 PC 에서 설치판을 처음 실행하면 포트가 겹친다. 시작 메뉴 바로가기는 포트 인자를 주지 않는다.
- BuilderGate 터미널 안에서 설치판 exe 를 실행하면, 상속된 `BUILDERGATE_*`(예: `BUILDERGATE_CONFIG_PATH`)가 우선한다. 이는 기존 동작과 같다.
