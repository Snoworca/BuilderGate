## 문제 원인

근본 원인은 세 가지이며, 모두 TypeScript 컴파일러의 소스 코드 재출력(re-printing) 과정에서 비롯된 표기법 차이입니다.

1. **타입 주석으로 인한 앵커 문자열 단절**  
   원본 소스: `readDriverViewIdentity: (): DriverViewIdentity | null =>`  
   테스트 앵커: `readDriverViewIdentity: () =>`  
   타입 정보가 제거되면서 앵커와 실제 텍스트가 일치하지 않습니다.

2. **여러 줄 인자 목록을 한 줄로 병합**  
   원본은 인자가 한 줄에 하나씩 배치되어 있으나, 컴파일 산출물에서 `buildCheckpointCapability(sessionId, view, 'legacy', record,` 와 같이 여러 인자가 한 줄에 나타납니다.

3. **후행 쉼표(trailing comma) 제거**  
   컴파일 과정에서 후행 쉼표가 제거되는데, 테스트의 정규식이 이를 반영하지 못합니다.

## 해결 방법

다음 두 가지 방향의 조합으로 해결했습니다.

### 1. 검사 대상을 `.ts` 원본으로 변경

```
readFile(new URL('./TerminalAuthorityProductionAdapter.js', import.meta.url))
  ↓
readFile(new URL('./TerminalAuthorityProductionAdapter.ts', import.meta.url))
```

**선택 근거**:
- 저장소의 다른 모든 소스 텍스트 계약 테스트가 `.ts` 원본을 읽고 있습니다. 이 파일만 예외였습니다.
- `TerminalAuthorityController.test.ts` 의 7537줄이 **같은 어댑터를 이미 `.ts` 로 읽고 있었습니다**. 한 어댑터에 대해 두 개의 계약이 서로 다른 텍스트를 보고 있었습니다.
- 계획 사이드카 10곳이 실행 커맨드를 `--test src/…test.ts` 로 등재해 두었습니다.
- 요구사항 `MIG-BGSTAB-002` 의 AC-1~AC-6 은 검사 대상에 대해 명시하지 않습니다.

### 2. 앵커 문자열을 포맷 차이에 견디도록 확장

13개 위치에서 `.js` 를 `.ts` 로 변경하고, 다음 세 곳에서 정규식을 조정했습니다.

- **`readDriverViewIdentity` 검사** (3곳): `readDriverViewIdentity: () =>` 로 타입 주석 부분 제거
- **`buildCheckpointCapability` 정규식**: 인자 구분자마다 `\s*` 추가하여 공백 허용
- **`restartCompatibilityRecovery` 정규식**: 선택적 쉼표(`(?:,)?`) 허용

### 1. 잘못된 앵커로 인한 과도한 슬라이싱

`:1181` 의 앵커 문자열이 `'const scheduleTopologyRecovery'` 로 정의되어 있으나, 실제 식별자는 `scheduleCompatibilityTopologyRecovery` 입니다. 가드(guard)가 없어 `.indexOf()` 가 `-1` 을 반환하고, 결과 슬라이스가 파일 끝까지 17,324 자로 넓어집니다.

### 2. 약한 정규식으로 인한 검증 허점

`buildCheckpointCapability` 정규식의 꼬리 부분에 `[\s\S]*?` 가 있어서, 5번째 인자 자리에 새로운 인자를 추가하더라도 정규식이 여전히 통과합니다.

### 3. 간헐적 격리 실패

광역 실행 4회 중 1회에서 `SessionManagerTerminalAuthorityRuntimePorts.test.ts:764` 가 실패했습니다. 동일 파일을 격리 실행한 3회는 전부 통과했으므로, 다른 테스트와의 상태 공유 또는 타이밍 문제로 추정됩니다.
