# Issue #7 — pasteInput facade와 copy-promise ownership: 검증 표면 복구

- Issue: [Snoworca/BuilerGate#7](https://github.com/Snoworca/BuilderGate/issues/7) (Parent #2)
- Requirement: `FR-BGSTAB-021` — Generation-safe terminal clipboard ownership (Status=implemented, Stability=evolving)
- Baseline: worktree HEAD `bb5a657`, branch `work/issue-2-orca-terminal-20260916`

## 1. 이슈와 전제 검증

이슈 제목의 `pasteInput` 은 이 저장소의 식별자가 아니라 Orca 연구 계획의 어휘다. 실제 표면은
`terminalClipboardCoordinator` 와 그 어댑터(`pasteTerminalText`, `pasteTerminalClipboard`,
`pasteText`, `pasteClipboard`)다.

전제를 먼저 확인한 결과 **여섯 개 AC 모두 프로덕션 코드에서 이미 충족되어 있었다.**

아래 표의 번호는 **이슈 #7 본문의 AC-1..AC-6** 이다. `FR-BGSTAB-021` 요구사항 자신의 AC 는
AC-1..AC-9 로 별개 체계이며 §4.1 과 SRS 의 VE 행은 후자를 쓴다. 두 체계에서 같은 번호가 다른
절을 가리킨다 — 예를 들어 이슈 AC-6 은 UI 무변경이지만 요구사항 AC-6 은 async clipboard read 중
target 변경이고, UI 무변경은 요구사항 AC-7 이다.

| 이슈 AC | 지목된 결함이 현재도 있는가 | 근거 |
|---|---|---|
| AC-1 programmatic paste 단일 facade | 없음 | tab/grid context menu 와 registered preset 세 경로가 모두 `App.tsx`·`MosaicContainer.tsx` → TerminalView imperative handle → coordinator 로 들어간다. **clipboard** 경로 중 coordinator 를 우회하는 것은 없다. 단 `sendInput` 은 비-paste 입력 문으로 남아 있고 살아 있는 호출자가 둘 있다 (`CommandPresetDialog#handleExecute`, `TerminalShortcutDialog#handleTestSend`) — 둘 다 clipboard 에서 온 값이 아니므로 AC 위반은 아니지만, `CommandPresetDialog#handleCopy` 가 **같은** `preset.value` 문자열을 clipboard 에 쓰므로 값 공간은 겹치고 그 분기에는 `unsupported-multiline-paste` 가드가 적용되지 않는다. 초판의 "`sendInput` 우회 경로가 남아 있지 않다" 는 측정한 것보다 넓은 주장이었다 |
| AC-2 Ctrl+V native owner 보존 | 없음 | keydown 핸들러는 `\x16` 전송만 차단하고 xterm textarea paste 에 위임한다 |
| AC-3 copy-promise ownership | 없음 | `copySelection` 은 `writeClipboardText` 성공 뒤 `isCurrent` 와 `isSelectionCurrent` 가 모두 참일 때만 selection 을 지운다. 실패는 `reject` → `observe` → `recordTerminalDebugEvent` 로 관측된다 |
| AC-4 selection 없는 Ctrl+C → SIGINT | **미해결** | Ctrl+C 분기는 `hasClipboardSelection` 로 게이트되는데 그 게이트는 **저장된 우클릭 선택**으로도 참이 되고, 그 ref 는 마우스 버튼 0·`clearSelection`·터미널 생성/파괴로만 지워진다. 보이는 선택 없이 가로채일 수 있다는 논증이 열려 있다 — §3.13, **이슈 #88** 소유. 요구사항 자신의 AC-2 에 해당하며 그 체크는 해제했다 |
| AC-5 exactly-once | 없음 | `admitPaste` 단일 진입, payload 재구성 없음, `activate()`/`dispose()` 가 lifecycle epoch 을 올려 StrictMode remount 가 in-flight 작업을 되살리지 못한다 |
| AC-6 UI 무변경 | 해당 없음 | 되돌릴 변경이 없다 |

**결함은 그것을 검증하는 표면에 있었다.**

## 2. 문제 원인

### 2.1 Class A — 연결되지 않은 계측

`frontend/tests/unit/terminalClipboardAdapterContract.test.ts` 와
`frontend/tests/unit/terminalClipboardCoordinator.test.ts` 가 이 요구사항의 단위 검증 표면 전부인데,

1. **어느 TypeScript 프로그램에도 들어 있지 않았다.** `tsconfig.test.json` 은 명시적 `files`
   allowlist 를 쓰는데 두 파일 모두 등재되어 있지 않아 `npm run typecheck:tests` 가 본 적이 없다.
2. **어느 npm 스크립트에도 이름이 없었다.** frontend 의 단위 테스트 스크립트는 전부 기능별 명시
   allowlist 이고, 릴리스 워크플로는 frontend 단위 테스트를 돌리지 않는다.

손으로 실행하면 통과했다. 통과하는 테스트는 조용하므로, 아무도 돌리지 않는다는 사실은 그 자체로는
아무 신호도 내지 않는다.

### 2.2 Class B — 변별력이 부족한 단언

연결을 복구해도 "통과한다" 는 "입증력이 있다" 가 아니므로, TypeScript AST 로
`terminalClipboardCoordinator.ts` 의 구문과 불리언 피연산자를 전수 열거해 삭제 스윕을 돌렸다.
정규식이 아니라 AST 를 쓴 이유는 정규식 열거가 `if` 가드와 다중행 표현식 구문을 구조적으로 놓치기
때문이다.

**구문 삭제만으로는 부족했다.** 이 모듈의 결정적 술어는 구문이 아니라 한 표현식 안의 conjunct 다
(`!disposed && lifecycleGeneration === operationGeneration && options.isTargetCurrent(target)`).
구문 삭제는 그 피연산자를 한꺼번에 지우므로 개별 피연산자를 변별하지 못한다. AC-3 의 내용 전체가
"generation 과 selection 이 **둘 다** 여전히 일치할 때만 지운다" 이므로, 피연산자 단위 변이를
추가하지 않았다면 AC-3 의 핵심 질문을 한 번도 던지지 않은 채 깨끗한 생존자 수를 보고했을 것이다.

## 3. 해결 방법

### 3.1 연결 복구와 재발 방지

- 두 테스트 파일과 새 가드를 `tsconfig.test.json` 의 `files` allowlist 에 등재했다.
- `test:unit:clipboard` 스크립트를 추가했다.
- `terminalClipboardSurfaceWiring.test.ts` 가드를 추가했다. 이 가드는 고정 목록이 아니라
  **디렉터리에서 clipboard 단위 테스트를 열거**해 allowlist 와 스크립트 양쪽에 대조한다. 자기
  파일명도 그 열거에 걸리므로, 가드 자신이 빠지면 가드 자신이 실패한다.
- 가드의 비공허성은 가정하지 않고 측정했다. allowlist 에서 coordinator 테스트를 빼면 tsconfig 절만
  red 가 되고, 스크립트에서 가드 자신의 파일명을 빼면 스크립트 절만 red 가 된다 — 각 변이가 그것을
  잡으라고 존재하는 바로 그 절을 red 로 만든다. 또한 빈 집합 위에서 두 차집합 단언이 공허하게
  통과하지 못하도록 선행 단언을 두었다.

### 3.2 변이 스윕과 닫은 공백

스윕은 구문 61개와 불리언 피연산자 11개, 합계 변이 72개를 열거했다. 생존자는 27개에서 7개로 줄었다.

**한 번에 하나씩 지우는 변이는 "아무도 검증하지 않는다" 와 "중복된 형제가 여전히 강제한다" 를
구별하지 못한다.** 그래서 그룹 변이로 갈랐다. 그 결과 드러난 공백과, 이후 사후 스윕과 독립 리뷰가
추가로 드러낸 것을 합쳐 **여덟 절**을 테스트로 닫았다. 출처를 함께 적는다 — 스윕만으로 찾은 것과
다른 수단이 찾은 것을 뭉뚱그리면 스윕의 입증력을 실제보다 크게 적게 된다.

- `pasteCapturedText` 의 currency 재확인 — 아래 §3.6 참조. 스윕이 아니라 **리뷰가 찾았다**
- `copySelection` 진입 가드(대상 없음 / 대상 교체)
- `copySelection` 무선택 가드(selection 없음 / 빈 문자열)
- `pasteClipboard` 진입 가드
- `pasteText` 무대상 가드
- clipboard read 실패의 `clipboard-read-failed` 거절
- accepted **paste** 관측 — accepted **copy** 관측은 이미 잡히고 있었고 paste 쪽만 비어 있었다.
  exactly-once 주장이 adapter admission 위에 서 있는데, 그 admission 을 기록하는 채널이 조용히
  삭제 가능했다. **이것은 커버리지 공백의 옷을 입은 요구사항 공백이다** — 나머지 일곱은 가드에
  단언이 없는 것이지만, 이것은 AC 자신의 관측 채널이 검증되지 않은 것이다. 이 에픽에서 AC 의
  관측 채널이 미검증으로 발견된 것은 **두 번째**이며(#6 의 무가드 debug emit 10건이 첫 번째),
  두 건이면 다음 레인이 알아야 할 패턴이다. 비대칭이 판별점이다 — copy 쪽은 잡히고 paste 쪽만
  비어 있었으므로, 한쪽만 보고 "관측은 덮여 있다" 고 결론내릴 수 있는 형태였다.
- 살아 있는 coordinator 에 대한 `activate()`

### 3.3 사후 스윕이 앞선 분류를 반증했다

브리프가 사후 스윕을 형식이 아니라 필수로 규정한 이유가 이 레인에서도 확인됐다. 사전 스윕의 생존자를
그룹으로 묶는 과정에서 **`pasteClipboard` 진입 가드가 어느 그룹에도 들어가지 않은 채 누락**됐고,
`clipboard-read-failed` 거절도 try/catch 전체로만 검증되고 있었다. 두 건 모두 **사후 스윕이 잡았다.**
수정 뒤 두 번째 스윕을 돌리지 않았다면 잘못된 종결 주장이 기록에 들어갔을 것이다.

### 3.4 남은 생존자 7개 — 근거 두 개씩

"이것을 지워도 아무것도 바뀌지 않는다" 는 관측이 아니라 주장이므로 독립된 근거 두 개를 요구했다.

1. **기계적** — 삭제 아래 생존
2. **측정된** — 원본과 변이체의 전체 관측 출력(결과·관측·admission·write·clear·focus)을
   차분 실행으로 비교. 공개 연산 7종에 대한 길이 1..4 의 모든 시퀀스, **pending clipboard read 중
   길이 0..3 의 모든 개입 시퀀스**, 그리고 §3.6 이후에는 **currency 가 in-flight 중 뒤집히고
   `captureTarget` 과 `isTargetCurrent` 가 서로 독립인 픽스처**.

개입(interleaving) 축은 선택이 아니라 필수였다. 순차 하네스는 pending read 에 상태 변경을 끼워 넣지
못하는데, post-read recheck 가 존재하는 이유가 정확히 그 상황이다. 그 축 없이 "2800개 시퀀스에서
무변화" 를 보고했다면, 이 가드들이 하는 일을 볼 수 없는 하네스에 대한 진술을 능력에 대한 진술처럼
읽히게 했을 것이다.

일곱 생존자(S43·S48·S56·S58·S60·S61·B1)는 **하나도 빠짐없이** 중복 쌍의 구성원이면서(그룹 삭제는
스위트가 잡는다) 각각 **1600개 시나리오**에서 관측 불가능하다 — currency 뒤집힘·재복귀·dispose·
이중 dispose·activate·selection 교체를 길이 0..3 으로 조합한 in-flight 시퀀스에, admitPaste 거절과
동시 in-flight 2건을 교차한 하네스 변형 4종. 초판은 이 문장이 일곱을 덮는데 픽스처에는 셋만
들어 있었다 — §3.6 의 픽스처 결함과 같은 형태가 한 층 위에서 반복된 것이며, 리뷰가 잡았다. 이 문장의 근거는 **수정 이후에 다시 돌린 그룹 실행**이며, 수정 전 실행을 그대로
인용하지 않는다 — 수정 전 실행은 아래 §3.6 이 기술하는 결함을 품고 있었다.

### 3.5 완전성 주장의 두 축

- **연산자 축**: 삭제 변이만 적용했다. 조건 약화, 경계 off-by-one, 피연산자 재배치,
  인자 치환은 이 방법이 만들지 못한다. 이 방법이 만들 수 없는 AC 관련 결함을 두 개 지목할 수 있다 —
  `await` 를 selection clear 뒤로 옮기는 것, `selection` 자리에 `target` 을 넘기는 것.
- **열거 축**: `terminalClipboardCoordinator.ts` 모듈 **전체**(구문·불리언 피연산자 100%).
  `TerminalView.tsx` 의 배선(`clipboardViewGenerationRef` 등)은 **전혀 스윕하지 않았다.**
  읽기와 e2e 로만 덮인다. 이것은 덮인 영역이 아니라 명시된 공백이다.

두 축을 함께 적는 이유는 비대칭 때문이다. 연산자 축을 축소 서술하면 누군가 변이를 시도하다 모순을
관측하지만, **아예 보지 않은 대상은 아무 신호도 내지 않는다.**

### 3.6 독립 리뷰가 반증한 것 — 결함은 내가 그것을 닫으려고 쓴 도구 안에 있었다

리뷰어가 아홉 건을 냈고 전제를 직접 재측정한 뒤 전부 수용했다. 그중 셋은 이 레인의 결론을 바꿨다.

**(1) 차분 하네스가 스스로 던질 수 없는 질문에 "무변화" 라고 답했다.** `equivalence.mjs` 와
`interleaved.mjs` 의 픽스처는 `captureTarget: () => target` 과
`isTargetCurrent: (t) => t === target` 로 정의되어 **구성상 항상 일치**한다. 그래서 어떤 시퀀스도
"캡처는 됐지만 더 이상 current 가 아닌 target" 상태를 만들 수 없는데, 그것이 정확히
`pasteCapturedText` 의 currency 재확인이 존재하는 유일한 상태다. `pasteText` 의 진입 가드는
대상의 **존재만** 확인하고 currency 는 확인하지 않으므로, 그 재확인이 superseded target 과
admission 사이에 선 유일한 장치다.

두 입력이 독립인 픽스처로 다시 재면 **갈라진다** — 삭제하면 stale target 으로 paste 가
admit 된다. 즉 그것은 no-op 이 아니라 **입증력 있는 가드**였고, 픽스처가 질문을 던지지 못해서
no-op 으로 읽혔을 뿐이다. 테스트를 추가해 닫았고 생존자는 9 → 7 이 됐다.

이것이 이 에픽이 반복해 관측한 형태다. **결함은 직전 결함을 닫으려고 쓴 도구 안에 있었고, 그
도구는 깨끗한 숫자를 확신을 갖고 보고했다.** 통과하는 단언이 조용한 것과 같은 이유로, 던져지지
않은 질문도 조용하다.

**(2) 반증 도구가 자기 변이를 조용히 덜 적용했다.** `combined.mjs` 의 R3 그룹은
`disposed ? null : options.captureTarget()` 세 곳을 모두 지울 의도였는데, JS 의
`String.replace(string, string)` 은 **첫 번째 일치만** 치환한다. 두 곳이 남은 변이체에 대해
"SURVIVED (genuinely unverified)" 가 기록됐고, 그 위에서 "`disposed` 플래그는 epoch 과 완전히
중복" 이라는 진술이 나왔다. **그 진술은 틀렸다.** 치환을 전부 적용하면 그 그룹은 **잡힌다**.
도구를 고치고(치환 횟수를 보고하고 0건이 아니라 기대치와 대조) 다시 돌린 결과 여덟 그룹 전부
잡힌다. 사전 실행에 기대던 §3.4 의 문장은 사후 실행에서 재도출했다.

**(3) VE-8 이 관측할 수 없는 절을 덮는다고 주장했다.** VE-8 은 요구사항 AC-2 를 덮는다고 적었는데,
그 절의 핵심은 "선택 없는 Ctrl+C 를 intercept·preventDefault·sendInput 하지 않는다" 이고 그
동작은 `TerminalView` 의 keydown 핸들러에 있다. coordinator 단위 스위트는 그 모듈을 부르지 않으며
§3.5 가 그 파일을 스윕 대상에서 명시적으로 제외한다. 그 단언이 통과한 채 남을 결함을 지목할 수
있다 — keydown 분기를 무조건 `preventDefault()` + `sendInput('\x03')` 로 바꾸면 SIGINT 소유권이
깨지지만 단위 테스트는 전부 green 이다. VE-8 의 covers 에서 AC-2 를 제거했다.

나머지 여섯 건(가드 열거의 대소문자·확장자 사각, 스크립트 절이 실행이 아니라 이름만 검사하던 점,
살아있는 grep 수치, AC 번호 체계 혼용, 그리고 아래 §6.4 의 CI 공백)도 전부 수정하거나 기록했다.
가드의 새 사각 두 개는 리뷰어가 구성한 그대로 재현해 red 가 되는 것을 확인했다.

### 3.7 2차 리뷰 — 완전성 문장은 자기 픽스처가 실제로 받은 것만 덮는다

2차에서 일곱 건이 나왔고 전부 재측정 후 수용했다. 둘이 결론을 바꿨다.

**(1) 완전성 문장이 픽스처가 받지 않은 항목까지 덮었다.** §3.4 는 일곱 생존자가 "currency 가
뒤집히는 픽스처" 에서 무변화라고 적었는데, 그 픽스처에는 **다섯 그룹 중 셋만** 들어 있었고
`S56`·`S60` 은 아예 전달되지 않았다. 둘의 차분 근거는 §3.6 이 결함으로 규정한 바로 그 두
픽스처뿐이었다. **§3.6 의 결함이 한 층 위에서 그대로 반복된 것이다** — 그것을 손에 쥐고 고친
직후에, 그 교훈을 적은 문장 안에서.

일곱 전부를 훨씬 넓은 시나리오 공간에 넣어 다시 측정했고(각 1600개) 결과는 바뀌지 않았다.
**주장은 참이었고 산출물이 그것을 지탱하지 않았다.** 이 구분을 지우지 않는 이유는, 다음 독자에게
뒷받침 없는 참인 주장과 거짓인 주장이 똑같이 보이기 때문이다.

**(2) 가드가 "이름을 부른다" 와 "실패하면 빨개진다" 를 구별하지 못했다.** 스크립트를
`node --test <경로들>` 뒤에 or-else-true 접미사를 붙인 형태로 바꾸면, 파일을 전부 이름으로 부르고
실제로 실행하며 **실패한 스위트에서도 exit 0** 이 된다. 1차 수정은 술어를 substring 에서 호출
형태로 옮겼을 뿐 종료 코드 전파까지 닿지 않았다. 러너와 호출자 사이에 종료 코드를 삼킬 수 있는
셸 연산자가 없어야 한다는 절을 추가했다. 같은 라운드에서 정규화 비대칭(한쪽만 `./` 를 벗김)과
`tokens[0] === 'node'` 강제가 정당한 배선을 false-red 로 만든 것도 고쳤고, 멤버십은 유지한 채
`strict` 만 끄면 프로그램이 조용히 검사를 멈추는 구멍도 절로 닫았다. 다섯 구성 전부 재현해
각각 자기 절만 red 가 되는 것을 확인했다.

나머지(관측 객체를 투영해 target identity 를 놓치던 새 테스트, 첫 Change Note 의 과대주장, 본
보고서의 일곱/여덟 불일치)도 수정했다.

### 3.8 Class B 전수 — 이름과 술어가 갈라진 단언

삭제 스윕은 "이 단언이 입증력이 있는가" 에 답하고 **"이 단언을 통과하는 결함을 지목할 수
있는가" 에는 답하지 않는다.** 원래 열두 단언에 그 축을 따로 적용했다.

어댑터 계약 테스트 넷 중 **셋은 프로덕션 소스를 `readFileSync` 로 읽어 정규식으로 단언한다.**
코드를 실행하지 않는다. 가장 날카로운 것:

```
test('Terminal imperative handles expose no legacy programmatic paste bypass', …)
  assert.doesNotMatch(terminalViewSource, /\bpasteInput\s*:/);
  assert.doesNotMatch(terminalContainerSource, /\bpasteInput\s*:/);
```

`pasteInput` 은 저장소 어디에도 없다. 두 단언은 **공허하게 참**이며 그 식별자로 철자되지 않은
어떤 우회에도 실패할 수 없다. 이름은 성질("programmatic paste 우회 없음")을 주장하고 구현은
**특정 토큰의 부재**를 검사한다 — AC-5 raw-text 가드와 같은 괴리다.

**통과하는 결함을 지목할 수 있다**: 핸들에 `pasteRaw: (data) => sendInput(data)` 를 더하고 Grid
context menu 를 거기로 붙이면 네 단언이 전부 통과한다. 가정이 아니다 — 같은 핸들에
`sendInput` 이 `pasteText` 바로 옆에 이미 있다.

교체본은 `TerminalHandle` 을 AST 로 열거한다. 실측 근거: 멤버 **34개**, 그중 paste 가능 멤버는
**정확히 둘**(`pasteClipboard`·`pasteText`)이고 둘 다 coordinator 로 위임한다. **부분집합이
아니라 정확한 집합**을 단언하므로 `pasteRaw` 가 추가되면 red 다. 그 우회와 위임 제거 둘 다
red 임을 재현했고, 옛 형태는 전자를 통과했다. **테스트 이름도 바꿨다** — 이름이 술어보다 강한
주장을 하지 않게 하는 것이 요점이지 단언을 세게 만드는 것이 요점이 아니다.

범위 한정: 이것은 핸들에 다른 paste 진입점이 없고 둘이 위임함을 증명한다. **두 컴포넌트를
실행하지는 않으므로** keydown 핸들러의 동작(선택 없는 Ctrl+C 의 SIGINT 소유권 포함)은 이
요구사항의 어떤 단위 증거 행에도 들어오지 않는다. §6.5 참조.

### 3.10 3차 리뷰 — 이번 라운드에 쓴 가드가 전부 우회 가능했다

3차에서 여덟 건이 나왔고 전부 재현한 뒤 수용했다. **그중 다섯이 2차에서 새로 쓴 가드를 우회한다.**

| 우회 | 무엇을 통과시켰나 |
|---|---|
| `insertText` | 이름이 `/paste/i` 에 걸리지 않는 진짜 paste 우회. 가드는 **성질이 아니라 명명 규칙**을 검사하고 있었다 |
| `'pasteRaw'` (따옴표) | `ts.isIdentifier` 가 인용된 이름을 버려, "정확한 집합" 이 **부분집합 위에서** 계산됐다. VE-11 이 예시로 든 바로 그 우회가 따옴표 한 쌍으로 뚫렸다 |
| 블록 본문 이중 전달 | 위임 검사가 substring 이라 `sendInput` 으로도 보내면서 coordinator 도 부르는 형태를 통과시켰다 — AC-5/AC-8 의 exactly-once 위반 |
| `echo node … --test …` | 러너 토큰을 **아무 위치에서나** 받도록 고친 것이 2차에서 닫은 `echo` 우회를 토큰 하나 차이로 되열었다 |
| `\|\|true` · `;true` · 개행 | 셸 연산자를 공백 분리 토큰에서만 찾아, 붙여 쓰거나 개행으로 이으면 보이지 않았다 |

앞의 셋은 **이름과 술어의 괴리**(§3.8)가 그것을 고치려고 쓴 교체본 안에서 재발한 것이고, 뒤의 둘은
**2차 수정이 2차에서 닫은 구멍을 되연 것**이다. 후자가 특히 그렇다 — F6(정당한 배선이 false-red)을
고치려고 러너 토큰 위치 제약을 푼 것이 F4 우회를 되살렸다. **한 축을 느슨하게 하면 다른 축이 열린다.**

**F1·F2·F3 은 한 결함의 세 가지 옷이다.** 성질은 매번 "paste 가능한 멤버 전부가 coordinator 를
거친다" 이고, 구현은 매번 그 성질의 **대리(proxy)** 였다 — 이름 패턴, identifier 전용 순회,
substring. 즉 **대리-대신-성질 결함을 새 대리 셋으로 닫았다.** 셋을 따로 고치는 동안에는 그것이
하나의 결함임을 보지 못했다.

따라서 교체본은 **더 나은 대리를 찾지 않는다. 대리를 없앤다.** 어떤 멤버가 paste 가능한지를
추측하는 대신 전부 열거한다 — 이름 패턴은 추측이고, 고정된 집합은 추측하지 않는다. 술어가 대리일
때의 일반 수순이 이것이다: **근사를 개선하지 말고 대상을 열거하라.**

그리고 교체본 자신이 **무엇을 못 보는지 테스트 본문에 적었다.** 보고서에 적어봐야 먼저 읽히지
않는다 — 집합 안에 이미 있는 멤버가 callee 텍스트를 바꾸지 않은 채 본문만 이중 전달로 바뀌는 경우,
`TerminalHandle` 을 거치지 않고 컨테이너 핸들에만 붙는 경로, 그리고 런타임 동작 일체(#87).

교체본은 이제 `TerminalHandle` 의 **34개 멤버 전체를 고정**한다. paste 라는 이름이 붙었는지가 아니라
**핸들에 멤버가 추가되면 무조건 red** 가 되고, 누군가 그것이 paste 진입점인지 판단해야 한다. 이름 해석은
인용·계산 이름까지 포함하며 `names.length === members.length` 로 **아무것도 조용히 누락되지 않음**을
단언한다. 위임은 substring 이 아니라 **본문이 그 호출 자체여야** 한다(블록 본문 금지, `?? fallback` 만 허용).
셸 제어문자는 토큰이 아니라 **원문 문자열**에서 찾고, 러너는 알려진 접두사(`npx`·`cross-env`·`VAR=`) 제거 후
**첫 토큰**이어야 한다. 여덟 우회 전부와 정당한 배선 셋을 재현해 확인했다.

리뷰가 지적한 공허한 단언 하나도 지웠다 — `!/paste/i.test('sendInput')` 은 **문자열 리터럴에 정규식을
돌리는 상수**라 결코 실패할 수 없었다. **공허한 단언을 없애는 커밋이 공허한 단언을 추가했다.**

### 3.9 계측기가 조용히 실패한 다섯 번 — 전부 깨끗한 숫자를 돌려줬다

이 레인에서 결함이 가장 자주 나온 곳은 프로덕션이 아니라 **결함을 찾으려고 쓴 도구**였다.

| 계측기 | 조용한 실패 | 발견 경로 |
|---|---|---|
| `combined.mjs` 그룹 변이 | 세 곳 중 한 곳만 치환 | 리뷰 |
| 차분 픽스처 | 두 입력이 구성상 일치 → 질문 자체가 불가 | 리뷰 |
| §3.4 완전성 문장 | 일곱을 덮는다면서 픽스처엔 셋만 | 리뷰 |
| AST 프로퍼티 열거 | 괄호 감싼 화살표 본문에서 **0개** 반환 | 자체 probe |
| 본 보고서 패치 스크립트 | 치환이 하나도 일치하지 않음 | 자체 grep |
| `flipping.mjs` 주석 | "target currency 와 독립" 이라 적었으나 `flipOff` 가 둘 다 내리고 `flipOn` 은 하나만 올려 (거짓,참) 조합이 **도달 불가** | 리뷰 |
| `/paste/i` 이름 게이트 | 성질이 아니라 **명명 규칙**을 검사 | 리뷰 |
| `ts.isIdentifier` 이름 해석 | 인용된 멤버를 조용히 누락 → "정확한 집합" 이 부분집합 | 리뷰 |
| substring 위임 검사 | `sendInput` 으로도 보내면서 coordinator 도 부르는 이중 전달을 통과 | 리뷰 |
| `!/paste/i.test('sendInput')` | 문자열 리터럴에 정규식을 돌리는 **상수** — 결코 실패 불가 | 리뷰 |
| 인터페이스 고정 | **타입**을 지켰는데 출하되는 것은 객체 리터럴이다 | 리뷰 |
| 컨테이너 미열거 | 멤버 열거를 view 에만 돌려 컨테이너 전용 우회가 통과 | 리뷰 |
| `??` 좌변만 검사 | 우변은 미검사 — 그런데 우변은 좌변이 nullish 일 때 **실제로 실행된다** | 리뷰 |
| callee 만 비교 | 인자 미검사 → `pasteText(data + data, source)` 통과 (payload 중복) | 리뷰 |
| AC-2 probe (통제 침묵) | `helper.focus()` 로는 xterm 이 키를 못 받아 **통제 자체가 무음** → 거짓 안전 2회 | 자체 |
| AC-2 probe (교란변수) | Escape 뒤 포커스 없음을 검사하지 않아 **거짓 양성** → 상부에 잘못된 에스컬레이션 | 자체 |

**열여섯 전부 오류를 내지 않고 성공을 보고했다.** 그중 **마지막 하나만 거짓 양성** 방향이고 나머지
열다섯은 전부 일을 실제보다 깨끗해 보이게 했다 — 방향이 바뀐 그 하나가 상부 에스컬레이션을 낳았다. 그리고 **판정을 읽어서 잡힌 것은 하나도 없다** — 자체
발견은 전부 숫자·제외 목록·커밋된 바이트를 본 결과이고, 나머지는 독립 리뷰어가 찾았다. 운영 형태는
따라서 이렇다: **계측기를 돌린 뒤 결론을 읽기 전에, 그것이 무엇을 봤는지 출력해 기대치와 대조한다.**

이 표 자체도 같은 결함을 한 번 겪었으므로 고친 숫자 뒤에 숨기지 않고 적는다. 직전 판에서 **표는 여덟
행인데 요약 문장은 "아홉"** 이라고 적었고, §3.10 산문이 이미 기술한 둘(substring 위임 검사, 상수
단언)이 표에 들어가지 않았다. 직전 판 기준 실제는 **열**이었고, 4차가 넷, 5차의 AC-2 probe 가 둘을 더해 지금은 **열여섯**이다.
이 레인에서 계측기 수를 정정한 것이 **일곱 번째**이고 **일곱 번 모두 위로** 움직였다 — 아래로
움직인 적이 한 번도 없다. 그래서 이 수는 **계수가 아니라 하한**이다. 한 방향으로만 틀리는 것은 잡음이
아니라 **편향**이며, 방향은 계측기가 실제보다 더 믿을 만해 보이는 쪽이다. 네 번째가 특히 그렇다 — `() => ({ ... })` 는
객체 리터럴을 괄호로 감싸므로 언래핑 없이는 프로퍼티 맵이 비고, **공집합 위의 전칭 주장은
참이다.** "금지된 일을 하는 멤버가 없다" 형태로 썼다면 공허하게 통과했을 것이다. 규칙:
**0을 반환할 수 있는 열거는 성질을 단언하기 전에 자기 개수를 먼저 단언한다.** 이것을 잡은
방법은 **판정이 아니라 숫자를 본 것**이다. 판정만 봤다면 green 이었다.

그런데 열거·변별·제기가능성이라는 세 축보다 **한 단계 더 정확한 서술**이 있다. `members.length > 10`
단언은 **틀리지 않았다.** 공집합 결함을 겨냥해 썼고 그 결함에 대해 실제로 입증력이 있다. 그런데
F2(인용된 이름 누락)는 **그 단언을 만족시킨 채로 그대로 지나간다** — 10보다 크다는 것은 어느 쪽이든
참이기 때문이다.

> **가드는 자기가 겨냥한 질문에 답한다. 다음 결함은 겨냥하지 않은 질문에 있다.**

세 축은 실명(失明)의 **종류**를 나열하지만, 이 문장은 셋을 모두 만들어내는 **기전**을 말한다. 그래서
더 일반적이다 — 새 가드를 쓸 때 물어야 할 것은 "이것이 강한가" 가 아니라 **"이것이 겨냥하지 않은
질문은 무엇인가"** 다.

같은 이유로 **공허한 단언을 지우는 커밋이 공허한 단언을 낳는다.** 이것은 부주의가 아니라 기전이다 —
약한 단언을 교체할 때 우리는 **방금 실패 양상을 이해했다는 믿음** 아래에서 새 술어를 쓰고, 그 믿음이
바로 점검을 억제한다. 대책 둘: 교체본의 공허성 검사를 **같은 커밋에서** 돌릴 것, 그리고 **내가 타이핑한
리터럴이 아니라 검사 대상 코드에서 계산된 값**에 대해 단언할 것. 리터럴은 내가 이미 쓴 것만 말해준다.

다섯 번째도 같다. 이 보고서의 이전 패치 배치에서 `#85` 인용이 들어가지 않았다 — 치환 문자열에
선행 공백 셋이 있고 대상 줄에는 없어 `str.replace` 가 아무것도 일치시키지 않은 채 성공을
반환했다. 같은 배치의 다른 치환에는 `assert s.count(old)==1` 을 걸었고, **걸지 않은 바로 그것이
빠졌다.** 변이 스크립트에 대해 이미 적은 규칙을 편집 스크립트에 적용하지 않은 결과다. 증상만
고치지 않고 배치 전체를 감사했으며 나머지 아홉 개는 정확히 한 번씩 존재한다.

### 3.12 4차 리뷰 — 고정 대상이 출하되는 물건이 아니었다

4차에서 일곱 건이 나왔고 전부 재현 후 수용했다. 핵심은 하나다.

**3차의 수정은 게이트를 `TerminalHandle` *인터페이스* 위로 옮겼는데, 인터페이스는 출하되는 물건이
아니다.** `useImperativeHandle<T, R extends T>` 는 객체 리터럴이 인터페이스에 없는 멤버를 갖는 것을
허용한다. 따라서 **인터페이스는 건드리지 않고 리터럴에만** 우회 멤버를 넣으면 24/24 green 이었고,
실제 핸들은 그 우회를 정말로 노출한다. 컨테이너 쪽도 같다 — 멤버 열거를 `view` 에만 돌렸으므로
**컨테이너 전용 우회**가 존재했다(내가 4차에 명시적으로 물었던 질문이고, 답은 "있다" 였다).

**대리-대신-성질 결함의 네 번째 등장이며, 이번에는 타입 수준이었다.** 이름 패턴 → identifier 전용
순회 → substring → **인터페이스**. 매번 성질의 대리를 골랐고 매번 뚫렸다. 그래서 이번에는 대리를
하나 더 고르지 않고 **출하되는 세 표면을 전부 고정**한다 — 인터페이스, view 리터럴, container 리터럴.

나머지도 같은 결 — `??` 를 좌변으로 풀면서 **우변을 검사하지 않았는데, 우변은 좌변이 nullish 일 때
실제로 실행되는 경로**다. callee 만 비교하고 인자를 보지 않아 `pasteText(data + data, source)` 가
통과했다(payload 중복 = 이 행이 인용된 exactly-once 부류). 셸 스캔은 정당한
`--test-name-pattern='copy\|paste'` 와 `&` 가 든 경로를 **false-red** 로 만들었다 — 방향은 안전하지만
그 red 를 만난 유지보수자는 절을 약화시키고 싶어진다. 인용 구간을 제외하고 스캔하도록 고쳤고,
**느슨하게 만든 뒤 그 절이 잡으라고 존재하던 우회 넷을 전부 다시 돌려 red 임을 확인했다** — 3차에서
F6 수정이 F4 우회를 되열었던 바로 그 실수를 반복하지 않기 위해서다.

마지막 하나는 설계 비판이었고 가장 유용했다. 34개 이름을 **맨 문자열 목록**으로 두면 미래에 red 를
만난 사람의 가장 값싼 대응이 "이름을 붙여넣는 것" 이 되고, 그러면 가드는 시간이 지나며 **형식**이
된다. 각 이름에 *왜 paste 진입점이 아닌지*를 붙였고, 추가로 **lone `string` 인자를 받는 멤버는 별도
목록에 명시**되어야 하도록 했다 — `insertText: (data: string) => …` 는 고정 집합과 이 목록 **둘 다**
깨뜨리며, 두 번째는 이름 복사로 만족시킬 수 없다.

### 3.13 AC-2 는 열려 있다 — 그리고 그것을 닫으려던 내 실험은 무효였다

5차 리뷰가 코드 경로 논증을 냈다. Ctrl+C 게이트는 `term.hasSelection()` 또는 **저장된 우클릭
선택**으로 참이 되고, `savedRightClickSelRef` 는 **마우스 버튼 0·`clearSelection`·터미널
생성/파괴** 세 곳에서만 지워진다. 타이핑도, 컨텍스트 메뉴를 Escape 로 닫는 것도 지우지 않는다.

리뷰어는 브라우저가 없어 **인증하지 않았고**, 브라우저가 있으면 판정된다고 말했다. 둘 다 옳았다.
나는 2222 레인이 있었으므로 논쟁 대신 측정했다 — **그리고 그 측정은 무효였다.**

probe 는 세 번 연속 "SIGINT 삼켜짐" 을 보고했고, 그 뒤 추가한 통제가 전부를 무너뜨렸다:

```
[probe] typing after Escape reached the terminal: frames=0 data=""
```

Escape 와 Ctrl+C 사이의 타이핑이 **입력 프레임을 하나도 만들지 않았다.** 터미널에 키보드 포커스가
없었고, 모든 0 은 가로채기가 아니라 **포커스 상실**로 설명된다. 가설은 확인되지도 반증되지도 않았다.

소스를 읽으면 오히려 어려워진다. `ContextMenu` 는 닫을 때 `closeAndRestoreFocus` 로 포커스를
복원하는데 **document 레벨 Escape 리스너는 `onClose()` 를 직접 불러 복원을 건너뛴다.** Escape 경로가
둘이고 포커스 결과가 다르다.

**네 번째 시도를 하지 않았다.** 이 probe 는 한 시간 동안 **확신에 찬 오답을 셋** 냈다 — 무음 통제로
인한 거짓 안전 둘, 미검증 교란변수로 인한 거짓 양성 하나. 그런 이력의 계측기가 프로덕션 결함의
존부를 결정해서는 안 되고, "한 번만 더 고치면 믿을 수 있다" 는 2·3·4 차에서 매번 실패한 추론이다.

**AC-2 의 체크는 해제했다** — 열린 미인증 논증 아래에서 검증 주장을 유지할 수 없기 때문이며,
위반이 입증됐다는 뜻은 아니다. 질문은 **#88** 이 소유한다. probe 와 무효 실행 로그 전부를 그쪽에
넘기고 이 저장소에는 커밋하지 않는다 — **세 번 틀린 계측기를 테스트로 남기면 다음 사람이 그것을
신뢰한다.** 아무것도 판정하지 못한 실험도 증거 가치는 있다: 같은 교란변수를 다시 만들지 않게 한다.

**한 가지 정정 — 나는 도달 불가능 쪽으로 너무 세게 말했다.** 철회문에서 "포커스를 되돌리려면
버튼 0 클릭이 필요하고 그것이 ref 를 지우므로 두 조건이 상호배타적일 수 있다" 고 적었다. 그
문장은 틀렸다. `closeAndRestoreFocus` 는 `onClose()` 뒤 50ms 에 `restorePreviousFocus()` 를 불러
**버튼 0 클릭 없이 포커스를 복원한다.** 그 경로에서는 포커스가 helper textarea 로 돌아오고 saved
ref 는 지워지지 않는다 — **두 조건이 공존하며 시나리오는 살아 있을 수 있다.** 내 probe 가 측정한
것은 다른 경로(document 리스너가 `onClose()` 만 부르고 복원하지 않는 쪽)였다.

즉 #88 은 "아마 도달 불가" 가 아니라 **"미검증이며 살아 있을 법한 경로가 특정됨"** 이다. 내 철회가
가설을 실제보다 약하게 보이게 했으므로 여기서 바로잡는다.

넘기는 함정 넷:
1. 확인은 **키보드 포커스와 비어 있지 않은 saved ref 가 공존**함을 보여야 한다.
2. 포커스는 **타이핑이 입력 프레임을 만드는 것으로 증명**해야 한다. `.focus()` 도, 클릭도 근거가
   아니다 — 클릭은 버튼 0 이고 **검사 대상인 바로 그 ref 를 지운다.**
3. **Escape 경로가 둘이고 포커스 결과가 다르다.** 어느 쪽이 먼저 발화하는지를 먼저 판정해야 한다.
4. 복원에 **50ms 지연**이 있다. 관측이 복원보다 앞서면 없는 것처럼 보인다.

**접근과 통제는 분리해서 평가해야 한다 — 이 probe 는 접근이 옳았고 통제가 틀렸다.** 결과와 함께
기법까지 버리면 다음 사람이 같은 벽 앞에서 멈춘다.

기법 쪽은 재사용 가능하다: #85 는 prompt 텍스트가 아니라 **클라이언트가 내는 입력 프레임**에
단언하는 probe 를 막지 못하고(그래서 shell-agnostic 하게 이 Linux 호스트에서 돈다), #81 은
**단일 결정적 시퀀스**에는 적용되지 않는다(첫 실행 포함 매번 같은 결과였다). 운이 아니라 기법이다.

통제 쪽이 틀렸고, 규칙은 하나다 — **통제는 probe 단위가 아니라 arm 단위·전제 단위다.** 한 arm 의
통제가 검증됐다고 다른 arm 이 검증되지 않는다. 차분 결과를 믿기 전에 **"이 판독을 만들어낼 수 있는
다른 원인이 무엇인가" 를 묻고, 처음 떠오른 하나가 아니라 각각을 통제**해야 한다.

그리고 이 레인 전체에서 가장 무거운 사실 하나 — **다섯 번의 리뷰 라운드, 31건의 finding,
`frontend/src` 전수 fan-out 열거를 거친 뒤에, AC 에 대한 유일한 실질적 의문은 브라우저를 열고 키를
눌러서 나왔다.** #85 와 #81 을 고칠 가치에 대한 이 에픽에서 가장 강한 논거다.

### 3.11 파이프가 종료 코드를 가린다 — 이 레인에서 두 번

파이프라인의 종료 상태는 **마지막 명령의 것**이므로 `| tail`·`| head`·`| grep`·`| jq` 가 전부
앞 명령의 실패를 가린다. 그리고 잘라내기는 **출력이 시끄러운 명령**에 쓰게 되므로, 가림은 정확히
읽기 싫은 명령에 집중된다.

이 레인에서 두 번 적중했다. 두 번째가 결정적이다 — `npm run typecheck:tests` 가 **STATUS=2** 로
타입 오류 셋을 내는 동안 스위트는 **24/24 green** 이었다(TypeScript 가 클로저에서 대입되는 `let` 을
`never` 로 좁힌다). `| tail` 로 봤다면 exit 0 이다. **green 스위트가 red 타입체크를 가린 것**이며,
파이프 앞에서 상태를 캡처했기 때문에만 보였다. 한 레인에서 두 번이면 예외 사례가 아니다.

규칙: **파이프를 거친 호출로 green 을 결론내지 않는다.** 파이프 전에 상태를 캡처하거나 `pipefail`
을 쓰고, 증거에 **어느 형태가 그 숫자를 냈는지** 적는다 — 파이프를 거친 "exit 0" 과 직접 호출의
"exit 0" 은 다른 주장이고 허용되는 것은 하나뿐이다. `WsRouterSplitHandshake` 가 CLAUDE.md 에 남긴
위험(assertion 14건이 깨진 채 exit 0)과 기전은 다르지만 교훈은 같다 — **종료 코드는 프로세스에 대한
주장이지 내 질문에 대한 주장이 아니다.**

### 4.0 e2e 표면의 연결 상태 — 단위 파일과 같은 질문을 먼저 던졌어야 했다

### 4.1 브라우저 검증은 부분 통과이며 부분으로 기록한다

데몬과 `start.bat` 을 우회해 `server/dist/index.js` 를 `NODE_ENV=production PORT=2222` 로 직접
띄우고, Playwright 의 `webServer` 를 끈 소유 config 로 실행했다. TCP 2001/2002 는 실행 전후 모두
운영 PID 30596 이 그대로 LISTENING 이며 어떤 수단으로도 건드리지 않았다. 종료는 `/proc` 의
cmdline·cwd·exe 로 소유를 확인한 단일 PID 에만 적용했다.

Desktop Chrome 6케이스 중 **2 통과 / 4 실패**. 실패 4건은 단언이 아니라 전제에서 끝났다
(`fresh PowerShell prompt did not become visible`). 원인을 추정하지 않고 측정했다 — 그 4건은
`shell: 'powershell'` 로 세션을 만들고, `normalizeShellForPlatform`
(`server/src/utils/ptyPlatformPolicy.ts`)은 platform 이 `win32` 가 아니면 Windows 전용 셸을
`'auto'` 로 되돌린다. 캡처된 페이지 스냅샷에도 bash 프롬프트가 찍혀 있다. 즉 **Linux 호스트에서는
구조적으로 통과할 수 없는 케이스**이며, 제품 회귀가 아니다. **이슈 #85** 가 소유하며,
같은 기전이 `powershell` 을 참조하는 **e2e spec 14개**에 걸린다 — 이 에픽의 하류 wave 가
의존하는 spec 들을 포함한다. 단언이 아니라 **전제**에서 끝나므로 AC 증거는 green 도 red 도
아닌 **0**인데, 로그는 red 로 읽힌다.

따라서 **AC-2·AC-3·AC-4·AC-7 은 이번 실행에서 브라우저 증거가 없다.** 단위 증거와 과거 VE-3 실행에만
의존한다. 관측하지 않은 green 을 보고하지 않는다.

   붙이는 것이 F7 의 목적이었으므로 그 목적은 달성됐다. 주장만 좁힌다.

## 6.5 종료 판단 — 잔여 취약성은 #7 의 것이 아니다

라운드를 거듭해도 **내 수정본의 결함률이 떨어지지 않았다.** 정직한 읽기는 "수렴 중" 이 아니라
**이 검증 표면이 그것이 검증하는 대상보다 검증하기 어렵다** 는 것이다. 숫자로 적는다.

| 항목 | 값 |
|---|---|
| 독립 리뷰 라운드 | **5회 완료** |
| 라운드별 finding | 9 / 7 / 8 / 7 / 7 |
| finding 합계 | **38** |
| **계측기 결함 (하한)** | **16** |
| **입증된 프로덕션 결함** | **0** |
| 미해결 프로덕션 질문 | **1** (AC-2, #88) |
| 프로덕션 코드 변경 | 0줄 (`bb5a657..` 전 구간에서 coordinator 바이트 동일) |
| 변이 스윕 | 6회, 생존자 7개로 안정 |
| 차분 시나리오 | 변이당 17,776, divergence 0 |

**다섯 AC 는 이 레인이 시작되기 전에 이미 프로덕션에서 충족되어 있었고, 여섯 번째(AC-2)는 열려
있다.** 다섯 라운드가 계측기 결함 **열여섯 건**(하한)과 **입증된 프로덕션 결함 0건**, 그리고 **미해결
프로덕션 질문 하나**를 냈다. 마지막 항목은 리뷰가 코드 읽기로 제기했고 **브라우저 없이는 판정할 수
없으며**, 이 레인의 판정 시도는 무효였다(§3.13). 이 표본에서 그 비대칭은 잡음이 아니라 **측정 결과**이며,
#86(도는데 검사하지 않는 테스트)과 #87(`TerminalView` 가 양쪽 절반 모두에 보이지 않음)의 근거를
산문이 아니라 증거로 진술한 것이다. **두 이슈 어느 쪽도 스스로 만들어낼 수 없는 종류의 증거다.**

종료 기준은 따라서 **"깨끗한 라운드가 나올 때까지" 가 아니다.** 그것은 수렴을 전제하는데 위 데이터가
바로 그 전제를 부정한다. 기준은 둘이다.

1. 현재 라운드의 finding 이 전부 수정되었거나 사유를 명시해 유예되었고,
2. 그 finding 이 **장치(apparatus)** 에 한정된다 — 즉 **미래의** 결함을 통과시킬 수 있는 것들이며,
   **여섯 AC 가 기술하는 동작에 현재 결함을 허용하는 것은 하나도 없다.**

두 번째가 실제 게이트다. F1(`insertText` 통과)은 장치에 해당한다 — 그런 멤버가 존재하지 않으므로
오늘 잘못된 것은 없고 가드가 내일을 놓칠 뿐이다. 살아 있는 AC 위반을 보이는 finding 이라면 라운드
수와 무관하게 이 레인은 닫히지 않는다.

AC-2 논증은 그 경계에 놓인다. **입증되지 않았으므로 게이트를 열지 않고, 반증되지도 않았으므로
'깨끗함' 으로 기록하지도 않는다.** 판정에는 브라우저와 #87 이 만들 계측기가 필요하고, 둘 다 이
레인 밖이다. 그래서 체크를 해제하고 #88 로 넘긴다 — **닫힌 것으로도, 위반으로도 적지 않는 것**이
증거가 지탱하는 유일한 기록이다.

그리고 종결문의 형태를 명시한다: 이 보고서는 **"살아 있는 AC 위반은 발견되지 않았다" 고 말하지
않는다.** AC-2 에 대한 논증이 제기됐고, 그것을 판정하려는 시도가 **무효였고**, 질문이 열린 채
#88 에 있다고 말한다. 앞의 문장은 다섯 라운드가 도달한 결론이지만 마지막 실험이 그것을 확인해
주지 못했고, 확인되지 않은 결론을 확인된 것처럼 적는 것이 이 레인이 열여섯 번 관찰한 바로 그
실패다.

잔여 취약성은 #7 이 없앨 것이 아니다. 그것을 #7 안에서 쫓는 것은 **이 에픽의 구조적 문제를 이슈 하나씩
푸는 일**이며, #86·#87 을 연 목적이 정확히 그것을 피하는 데 있다.

## 7. 범위 경계

이슈가 명시적으로 차단한 Wave 4 영역(native paste owner 전환, operation ID, server dedup/result
replay, reconnect/eviction, OSC52)에는 들어가지 않았다. 작업이 그 영역을 요구하는 지점도 없었다.

`FR-BGSTAB-021` 의 Rationale 은 구현 이전 상태를 현재형으로 서술하고 있으나 **의도적으로 두었다.**
Rationale 은 작성 시점의 동기 기록이고 Status=implemented 가 현재 상태를 말하므로, 고쳐 쓰면 이
요구사항이 왜 작성됐는지의 기록이 사라진다. 대신 Change Note 에 그 사실을 남겼다.

Status 는 `implemented` 로 유지한다. 브라우저 증거가 부분이므로 `verified` 로 올릴 근거가 없다.
