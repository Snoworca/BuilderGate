# Issue #7 — pasteInput facade와 copy-promise ownership: 검증 표면 복구

- Issue: [Snoworca/BuilerGate#7](https://github.com/Snoworca/BuilderGate/issues/7) (Parent #2)
- Requirement: `FR-BGSTAB-021` — Generation-safe terminal clipboard ownership (Status=implemented, Stability=evolving)
- Baseline: worktree HEAD `bb5a657`, branch `work/issue-2-orca-terminal-20260916`

## 1. 이슈와 전제 검증

이슈 제목의 `pasteInput` 은 이 저장소의 식별자가 아니라 Orca 연구 계획의 어휘다. 실제 표면은
`terminalClipboardCoordinator` 와 그 어댑터(`pasteTerminalText`, `pasteTerminalClipboard`,
`pasteText`, `pasteClipboard`)다.

전제를 먼저 확인한 결과 **여섯 개 AC 모두 프로덕션 코드에서 이미 충족되어 있었다.**

아래 표의 번호는 **이슈 #7 본문의 AC-1..AC-6** 이다. `FR-BGSTAB-021` 요구사항 자신의 AC 는
AC-1..AC-9 로 별개 체계이며 §4.1 과 SRS 의 VE 행은 후자를 쓴다. 두 체계에서 같은 번호가 다른
절을 가리킨다 — 예를 들어 이슈 AC-6 은 UI 무변경이지만 요구사항 AC-6 은 async clipboard read 중
target 변경이고, UI 무변경은 요구사항 AC-7 이다.

| 이슈 AC | 지목된 결함이 현재도 있는가 | 근거 |
|---|---|---|
| AC-1 programmatic paste 단일 facade | 없음 | tab/grid context menu 와 registered preset 세 경로가 모두 `App.tsx`·`MosaicContainer.tsx` → TerminalView imperative handle → coordinator 로 들어간다. `sendInput` 우회 경로가 남아 있지 않다 |
| AC-2 Ctrl+V native owner 보존 | 없음 | keydown 핸들러는 `\x16` 전송만 차단하고 xterm textarea paste 에 위임한다 |
| AC-3 copy-promise ownership | 없음 | `copySelection` 은 `writeClipboardText` 성공 뒤 `isCurrent` 와 `isSelectionCurrent` 가 모두 참일 때만 selection 을 지운다. 실패는 `reject` → `observe` → `recordTerminalDebugEvent` 로 관측된다 |
| AC-4 selection 없는 Ctrl+C → SIGINT | 없음 | Ctrl+C 분기는 `hasClipboardSelection` 로 게이트되어 미선택 시 native 경로로 떨어진다 |
| AC-5 exactly-once | 없음 | `admitPaste` 단일 진입, payload 재구성 없음, `activate()`/`dispose()` 가 lifecycle epoch 을 올려 StrictMode remount 가 in-flight 작업을 되살리지 못한다 |
| AC-6 UI 무변경 | 해당 없음 | 되돌릴 변경이 없다 |

**결함은 그것을 검증하는 표면에 있었다.**

## 2. 문제 원인

### 2.1 Class A — 연결되지 않은 계측

`frontend/tests/unit/terminalClipboardAdapterContract.test.ts` 와
`frontend/tests/unit/terminalClipboardCoordinator.test.ts` 가 이 요구사항의 단위 검증 표면 전부인데,

1. **어느 TypeScript 프로그램에도 들어 있지 않았다.** `tsconfig.test.json` 은 명시적 `files`
   allowlist 를 쓰는데 두 파일 모두 등재되어 있지 않아 `npm run typecheck:tests` 가 본 적이 없다.
2. **어느 npm 스크립트에도 이름이 없었다.** frontend 의 단위 테스트 스크립트는 전부 기능별 명시
   allowlist 이고, 릴리스 워크플로는 frontend 단위 테스트를 돌리지 않는다.

손으로 실행하면 통과했다. 통과하는 테스트는 조용하므로, 아무도 돌리지 않는다는 사실은 그 자체로는
아무 신호도 내지 않는다.

### 2.2 Class B — 변별력이 부족한 단언

연결을 복구해도 "통과한다" 는 "입증력이 있다" 가 아니므로, TypeScript AST 로
`terminalClipboardCoordinator.ts` 의 구문과 불리언 피연산자를 전수 열거해 삭제 스윕을 돌렸다.
정규식이 아니라 AST 를 쓴 이유는 정규식 열거가 `if` 가드와 다중행 표현식 구문을 구조적으로 놓치기
때문이다.

**구문 삭제만으로는 부족했다.** 이 모듈의 결정적 술어는 구문이 아니라 한 표현식 안의 conjunct 다
(`!disposed && lifecycleGeneration === operationGeneration && options.isTargetCurrent(target)`).
구문 삭제는 그 피연산자를 한꺼번에 지우므로 개별 피연산자를 변별하지 못한다. AC-3 의 내용 전체가
"generation 과 selection 이 **둘 다** 여전히 일치할 때만 지운다" 이므로, 피연산자 단위 변이를
추가하지 않았다면 AC-3 의 핵심 질문을 한 번도 던지지 않은 채 깨끗한 생존자 수를 보고했을 것이다.

## 3. 해결 방법

### 3.1 연결 복구와 재발 방지

- 두 테스트 파일과 새 가드를 `tsconfig.test.json` 의 `files` allowlist 에 등재했다.
- `test:unit:clipboard` 스크립트를 추가했다.
- `terminalClipboardSurfaceWiring.test.ts` 가드를 추가했다. 이 가드는 고정 목록이 아니라
  **디렉터리에서 clipboard 단위 테스트를 열거**해 allowlist 와 스크립트 양쪽에 대조한다. 자기
  파일명도 그 열거에 걸리므로, 가드 자신이 빠지면 가드 자신이 실패한다.
- 가드의 비공허성은 가정하지 않고 측정했다. allowlist 에서 coordinator 테스트를 빼면 tsconfig 절만
  red 가 되고, 스크립트에서 가드 자신의 파일명을 빼면 스크립트 절만 red 가 된다 — 각 변이가 그것을
  잡으라고 존재하는 바로 그 절을 red 로 만든다. 또한 빈 집합 위에서 두 차집합 단언이 공허하게
  통과하지 못하도록 선행 단언을 두었다.

### 3.2 변이 스윕과 닫은 공백

스윕은 구문 61개와 불리언 피연산자 11개, 합계 변이 72개를 열거했다. 생존자는 27개에서 7개로 줄었다.

**한 번에 하나씩 지우는 변이는 "아무도 검증하지 않는다" 와 "중복된 형제가 여전히 강제한다" 를
구별하지 못한다.** 그래서 그룹 변이로 갈랐다. 그 결과 드러난 공백과, 이후 사후 스윕과 독립 리뷰가
추가로 드러낸 것을 합쳐 **여덟 절**을 테스트로 닫았다. 출처를 함께 적는다 — 스윕만으로 찾은 것과
다른 수단이 찾은 것을 뭉뚱그리면 스윕의 입증력을 실제보다 크게 적게 된다.

- `pasteCapturedText` 의 currency 재확인 — 아래 §3.6 참조. 스윕이 아니라 **리뷰가 찾았다**
- `copySelection` 진입 가드(대상 없음 / 대상 교체)
- `copySelection` 무선택 가드(selection 없음 / 빈 문자열)
- `pasteClipboard` 진입 가드
- `pasteText` 무대상 가드
- clipboard read 실패의 `clipboard-read-failed` 거절
- accepted **paste** 관측 — accepted **copy** 관측은 이미 잡히고 있었고 paste 쪽만 비어 있었다.
  exactly-once 주장이 adapter admission 위에 서 있는데, 그 admission 을 기록하는 채널이 조용히
  삭제 가능했다. **이것은 커버리지 공백의 옷을 입은 요구사항 공백이다** — 나머지 일곱은 가드에
  단언이 없는 것이지만, 이것은 AC 자신의 관측 채널이 검증되지 않은 것이다. 이 에픽에서 AC 의
  관측 채널이 미검증으로 발견된 것은 **두 번째**이며(#6 의 무가드 debug emit 10건이 첫 번째),
  두 건이면 다음 레인이 알아야 할 패턴이다. 비대칭이 판별점이다 — copy 쪽은 잡히고 paste 쪽만
  비어 있었으므로, 한쪽만 보고 "관측은 덮여 있다" 고 결론내릴 수 있는 형태였다.
- 살아 있는 coordinator 에 대한 `activate()`

### 3.3 사후 스윕이 앞선 분류를 반증했다

브리프가 사후 스윕을 형식이 아니라 필수로 규정한 이유가 이 레인에서도 확인됐다. 사전 스윕의 생존자를
그룹으로 묶는 과정에서 **`pasteClipboard` 진입 가드가 어느 그룹에도 들어가지 않은 채 누락**됐고,
`clipboard-read-failed` 거절도 try/catch 전체로만 검증되고 있었다. 두 건 모두 **사후 스윕이 잡았다.**
수정 뒤 두 번째 스윕을 돌리지 않았다면 잘못된 종결 주장이 기록에 들어갔을 것이다.

### 3.4 남은 생존자 9개 — 근거 두 개씩

"이것을 지워도 아무것도 바뀌지 않는다" 는 관측이 아니라 주장이므로 독립된 근거 두 개를 요구했다.

1. **기계적** — 삭제 아래 생존
2. **측정된** — 원본과 변이체의 전체 관측 출력(결과·관측·admission·write·clear·focus)을
   차분 실행으로 비교. 공개 연산 7종에 대한 길이 1..4 의 모든 시퀀스, **pending clipboard read 중
   길이 0..3 의 모든 개입 시퀀스**, 그리고 §3.6 이후에는 **currency 가 in-flight 중 뒤집히고
   `captureTarget` 과 `isTargetCurrent` 가 서로 독립인 픽스처**.

개입(interleaving) 축은 선택이 아니라 필수였다. 순차 하네스는 pending read 에 상태 변경을 끼워 넣지
못하는데, post-read recheck 가 존재하는 이유가 정확히 그 상황이다. 그 축 없이 "2800개 시퀀스에서
무변화" 를 보고했다면, 이 가드들이 하는 일을 볼 수 없는 하네스에 대한 진술을 능력에 대한 진술처럼
읽히게 했을 것이다.

일곱 생존자(S43·S48·S56·S58·S60·S61·B1)는 **하나도 빠짐없이** 중복 쌍의 구성원이면서(그룹 삭제는
스위트가 잡는다) 각각 **1600개 시나리오**에서 관측 불가능하다 — currency 뒤집힘·재복귀·dispose·
이중 dispose·activate·selection 교체를 길이 0..3 으로 조합한 in-flight 시퀀스에, admitPaste 거절과
동시 in-flight 2건을 교차한 하네스 변형 4종. 초판은 이 문장이 일곱을 덮는데 픽스처에는 셋만
들어 있었다 — §3.6 의 픽스처 결함과 같은 형태가 한 층 위에서 반복된 것이며, 리뷰가 잡았다. 이 문장의 근거는 **수정 이후에 다시 돌린 그룹 실행**이며, 수정 전 실행을 그대로
인용하지 않는다 — 수정 전 실행은 아래 §3.6 이 기술하는 결함을 품고 있었다.

### 3.5 완전성 주장의 두 축

- **연산자 축**: 삭제 변이만 적용했다. 조건 약화, 경계 off-by-one, 피연산자 재배치,
  인자 치환은 이 방법이 만들지 못한다. 이 방법이 만들 수 없는 AC 관련 결함을 두 개 지목할 수 있다 —
  `await` 를 selection clear 뒤로 옮기는 것, `selection` 자리에 `target` 을 넘기는 것.
- **열거 축**: `terminalClipboardCoordinator.ts` 모듈 **전체**(구문·불리언 피연산자 100%).
  `TerminalView.tsx` 의 배선(`clipboardViewGenerationRef` 등)은 **전혀 스윕하지 않았다.**
  읽기와 e2e 로만 덮인다. 이것은 덮인 영역이 아니라 명시된 공백이다.

두 축을 함께 적는 이유는 비대칭 때문이다. 연산자 축을 축소 서술하면 누군가 변이를 시도하다 모순을
관측하지만, **아예 보지 않은 대상은 아무 신호도 내지 않는다.**

### 3.6 독립 리뷰가 반증한 것 — 결함은 내가 그것을 닫으려고 쓴 도구 안에 있었다

리뷰어가 아홉 건을 냈고 전제를 직접 재측정한 뒤 전부 수용했다. 그중 셋은 이 레인의 결론을 바꿨다.

**(1) 차분 하네스가 스스로 던질 수 없는 질문에 "무변화" 라고 답했다.** `equivalence.mjs` 와
`interleaved.mjs` 의 픽스처는 `captureTarget: () => target` 과
`isTargetCurrent: (t) => t === target` 로 정의되어 **구성상 항상 일치**한다. 그래서 어떤 시퀀스도
"캡처는 됐지만 더 이상 current 가 아닌 target" 상태를 만들 수 없는데, 그것이 정확히
`pasteCapturedText` 의 currency 재확인이 존재하는 유일한 상태다. `pasteText` 의 진입 가드는
대상의 **존재만** 확인하고 currency 는 확인하지 않으므로, 그 재확인이 superseded target 과
admission 사이에 선 유일한 장치다.

두 입력이 독립인 픽스처로 다시 재면 **갈라진다** — 삭제하면 stale target 으로 paste 가
admit 된다. 즉 그것은 no-op 이 아니라 **입증력 있는 가드**였고, 픽스처가 질문을 던지지 못해서
no-op 으로 읽혔을 뿐이다. 테스트를 추가해 닫았고 생존자는 9 → 7 이 됐다.

이것이 이 에픽이 반복해 관측한 형태다. **결함은 직전 결함을 닫으려고 쓴 도구 안에 있었고, 그
도구는 깨끗한 숫자를 확신을 갖고 보고했다.** 통과하는 단언이 조용한 것과 같은 이유로, 던져지지
않은 질문도 조용하다.

**(2) 반증 도구가 자기 변이를 조용히 덜 적용했다.** `combined.mjs` 의 R3 그룹은
`disposed ? null : options.captureTarget()` 세 곳을 모두 지울 의도였는데, JS 의
`String.replace(string, string)` 은 **첫 번째 일치만** 치환한다. 두 곳이 남은 변이체에 대해
"SURVIVED (genuinely unverified)" 가 기록됐고, 그 위에서 "`disposed` 플래그는 epoch 과 완전히
중복" 이라는 진술이 나왔다. **그 진술은 틀렸다.** 치환을 전부 적용하면 그 그룹은 **잡힌다**.
도구를 고치고(치환 횟수를 보고하고 0건이 아니라 기대치와 대조) 다시 돌린 결과 여덟 그룹 전부
잡힌다. 사전 실행에 기대던 §3.4 의 문장은 사후 실행에서 재도출했다.

**(3) VE-8 이 관측할 수 없는 절을 덮는다고 주장했다.** VE-8 은 요구사항 AC-2 를 덮는다고 적었는데,
그 절의 핵심은 "선택 없는 Ctrl+C 를 intercept·preventDefault·sendInput 하지 않는다" 이고 그
동작은 `TerminalView` 의 keydown 핸들러에 있다. coordinator 단위 스위트는 그 모듈을 부르지 않으며
§3.5 가 그 파일을 스윕 대상에서 명시적으로 제외한다. 그 단언이 통과한 채 남을 결함을 지목할 수
있다 — keydown 분기를 무조건 `preventDefault()` + `sendInput('\x03')` 로 바꾸면 SIGINT 소유권이
깨지지만 단위 테스트는 전부 green 이다. VE-8 의 covers 에서 AC-2 를 제거했다.

나머지 여섯 건(가드 열거의 대소문자·확장자 사각, 스크립트 절이 실행이 아니라 이름만 검사하던 점,
살아있는 grep 수치, AC 번호 체계 혼용, 그리고 아래 §6.4 의 CI 공백)도 전부 수정하거나 기록했다.
가드의 새 사각 두 개는 리뷰어가 구성한 그대로 재현해 red 가 되는 것을 확인했다.

### 3.7 2차 리뷰 — 완전성 문장은 자기 픽스처가 실제로 받은 것만 덮는다

2차에서 일곱 건이 나왔고 전부 재측정 후 수용했다. 둘이 결론을 바꿨다.

**(1) 완전성 문장이 픽스처가 받지 않은 항목까지 덮었다.** §3.4 는 일곱 생존자가 "currency 가
뒤집히는 픽스처" 에서 무변화라고 적었는데, 그 픽스처에는 **다섯 그룹 중 셋만** 들어 있었고
`S56`·`S60` 은 아예 전달되지 않았다. 둘의 차분 근거는 §3.6 이 결함으로 규정한 바로 그 두
픽스처뿐이었다. **§3.6 의 결함이 한 층 위에서 그대로 반복된 것이다** — 그것을 손에 쥐고 고친
직후에, 그 교훈을 적은 문장 안에서.

일곱 전부를 훨씬 넓은 시나리오 공간에 넣어 다시 측정했고(각 1600개) 결과는 바뀌지 않았다.
**주장은 참이었고 산출물이 그것을 지탱하지 않았다.** 이 구분을 지우지 않는 이유는, 다음 독자에게
뒷받침 없는 참인 주장과 거짓인 주장이 똑같이 보이기 때문이다.

**(2) 가드가 "이름을 부른다" 와 "실패하면 빨개진다" 를 구별하지 못했다.** 스크립트를
`node --test <경로들>` 뒤에 or-else-true 접미사를 붙인 형태로 바꾸면, 파일을 전부 이름으로 부르고
실제로 실행하며 **실패한 스위트에서도 exit 0** 이 된다. 1차 수정은 술어를 substring 에서 호출
형태로 옮겼을 뿐 종료 코드 전파까지 닿지 않았다. 러너와 호출자 사이에 종료 코드를 삼킬 수 있는
셸 연산자가 없어야 한다는 절을 추가했다. 같은 라운드에서 정규화 비대칭(한쪽만 `./` 를 벗김)과
`tokens[0] === 'node'` 강제가 정당한 배선을 false-red 로 만든 것도 고쳤고, 멤버십은 유지한 채
`strict` 만 끄면 프로그램이 조용히 검사를 멈추는 구멍도 절로 닫았다. 다섯 구성 전부 재현해
각각 자기 절만 red 가 되는 것을 확인했다.

나머지(관측 객체를 투영해 target identity 를 놓치던 새 테스트, 첫 Change Note 의 과대주장, 본
보고서의 일곱/여덟 불일치)도 수정했다.

### 4.0 e2e 표면의 연결 상태 — 단위 파일과 같은 질문을 먼저 던졌어야 했다

### 4.1 브라우저 검증은 부분 통과이며 부분으로 기록한다

데몬과 `start.bat` 을 우회해 `server/dist/index.js` 를 `NODE_ENV=production PORT=2222` 로 직접
띄우고, Playwright 의 `webServer` 를 끈 소유 config 로 실행했다. TCP 2001/2002 는 실행 전후 모두
운영 PID 30596 이 그대로 LISTENING 이며 어떤 수단으로도 건드리지 않았다. 종료는 `/proc` 의
cmdline·cwd·exe 로 소유를 확인한 단일 PID 에만 적용했다.

Desktop Chrome 6케이스 중 **2 통과 / 4 실패**. 실패 4건은 단언이 아니라 전제에서 끝났다
(`fresh PowerShell prompt did not become visible`). 원인을 추정하지 않고 측정했다 — 그 4건은
`shell: 'powershell'` 로 세션을 만들고, `normalizeShellForPlatform`
(`server/src/utils/ptyPlatformPolicy.ts`)은 platform 이 `win32` 가 아니면 Windows 전용 셸을
`'auto'` 로 되돌린다. 캡처된 페이지 스냅샷에도 bash 프롬프트가 찍혀 있다. 즉 **Linux 호스트에서는
구조적으로 통과할 수 없는 케이스**이며, 제품 회귀가 아니다.

따라서 **AC-2·AC-3·AC-4·AC-7 은 이번 실행에서 브라우저 증거가 없다.** 단위 증거와 과거 VE-3 실행에만
의존한다. 관측하지 않은 green 을 보고하지 않는다.

## 6. 보고만 하고 고치지 않은 것

범위 밖이거나 다른 주체의 판단이 필요해 기록만 남긴다.

1. **`tsconfig.test.json` allowlist 밖의 단위 테스트가 다수 있다.** baseline `bb5a657` 에서
   `frontend/tests/unit/` 의 116개 중 45개였고, 이 레인이 파일을 추가하고 셋을 등재한 뒤인
   `2946690` 에서는 117개 중 43개다. 이 수치는 읽는 시점에 달라지므로 측정 커밋과 함께만
   인용한다. 이번에 고친 셋은 그 집합의 일부다. 디렉터리와 allowlist 를 대조하는 일반 가드는 없다
   (`e2eOwnershipTypecheck.test.ts` 는 `tsconfig.e2e-ownership.json` 의 references 와 진단만
   지킨다). 전수 정리는 이 이슈 범위를 크게 벗어난다. **이슈 #82** 가 소유한다.
2. **`frontend/src/components/MetadataBar/MetadataRow.tsx` 가 clipboard 실패를 빈 catch 로
   삼킨다.** AC-3 의 "실패는 debug-observable" 과 같은 결함 부류이지만 다른 표면이다. **이슈 #83** 이 소유한다.
3. **이 가드는 CI 에서 돌지 않는다.** `test:unit:clipboard` 를 부르는 곳은 자기 정의뿐이고,
   릴리스 워크플로는 `build:*` 스크립트만 실행한다. `tsconfig.test.json` 은 `tsconfig.json` 의
   `references` 에 **의도적으로** 빠져 있어(그 파일 상단 주석이 이유를 적는다) `tsc -b` 도 이
   파일들을 컴파일하지 않는다. 따라서 스크립트를 통째로 지워도 아무 곳도 red 가 되지 않는다.
   "이름이 없다" 는 닫았지만 "아무 데서도 돌지 않는다" 는 그대로다. 해결에는 CI 변경이 필요하고
   영향 범위가 저장소 전체라 이 요구사항 범위를 벗어난다. VE-9 에도 같은 한정을 적었다.
   **`typecheck:tests` 도 마찬가지로 부르는 곳이 없다** — tsconfig 쪽 절반에도 자동 실행자가
   없다는 뜻이며, `tsc -b` 경로가 없다는 것만으로는 부족한 서술이다. **이슈 #84** 가 소유한다.
4. **`terminal-clipboard.spec.ts` 에 호스트 플랫폼 가드가 없다.** 브라우저 project 가드는 있으나
   OS 가드가 없어, 비-Windows 호스트에서 PowerShell 의존 4건이 skip 이 아니라 **fail** 로 보고된다.
   진짜 회귀와 구분되지 않는다는 점에서 이 이슈가 다룬 결함 부류와 같은 형태다. 공유 spec 파일이라
   다른 레인의 결과에 영향을 주므로 직접 고치지 않았다.

## 7. 범위 경계

이슈가 명시적으로 차단한 Wave 4 영역(native paste owner 전환, operation ID, server dedup/result
replay, reconnect/eviction, OSC52)에는 들어가지 않았다. 작업이 그 영역을 요구하는 지점도 없었다.

`FR-BGSTAB-021` 의 Rationale 은 구현 이전 상태를 현재형으로 서술하고 있으나 **의도적으로 두었다.**
Rationale 은 작성 시점의 동기 기록이고 Status=implemented 가 현재 상태를 말하므로, 고쳐 쓰면 이
요구사항이 왜 작성됐는지의 기록이 사라진다. 대신 Change Note 에 그 사실을 남겼다.

Status 는 `implemented` 로 유지한다. 브라우저 증거가 부분이므로 `verified` 로 올릴 근거가 없다.
