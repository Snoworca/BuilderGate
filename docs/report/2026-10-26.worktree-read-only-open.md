# 형제 worktree 파일을 읽기 전용으로 열기 (SEC-FOP-002, 이슈 #150)

## 이슈 설명

GitHub 이슈 #150에서 보고된 문제다. 세션 폴더 `d`와 같은 저장소의 형제 worktree `d-1`, `d-23`에서 에이전트가 만든 시안 파일을 BuilderGate에서 열 수 없었다. 파일이 세션 폴더 밖에 있다는 이유로 거부되었다.

사용자는 형제 worktree를 대상으로 이 문제를 해결하기를 요청했다. MCP 도구의 `filePath` 열기도 함께 처리하기를 요청했다.

## 문제 원인

세션 폴더 `d`와 형제 worktree `d-1`, `d-23`은 같은 git 저장소에 속한다. 그럼에도 다음 경로가 세션 폴더 밖 경로를 `PATH_TRAVERSAL`로 거부했다.

- Ctrl+클릭으로 파일 열기
- 편집기 창
- MCP 편집기 도구

터미널 셸의 cwd는 `d`에 남아 있다. 그래서 에이전트가 worktree에서 파일을 만들어도 사용자는 그 파일을 열 수 없었다.

MCP 도구에서는 우회 경로가 있었다. 본문을 `content`로 넘기면 파일 내용이 `d/.buildergate/mcp-docs/`에 복사본으로 누적되었다. 이 복사본은 상대 경로 CSS와 이미지를 깨뜨렸다.

## 해결 방법

### 읽기 허용 범위

- 신규 `server/src/services/worktreeRoots.ts`를 추가했다. 이 모듈은 git 프로세스를 실행하지 않는다. git 등록부 파일을 읽어 worktree 목록을 만든다.
- `FileService.resolveReadable`은 등록된 worktree 안의 경로를 읽기용으로 허용한다.
- `blockedPaths`, `blockedExtensions`, 링크 검사는 그대로 적용한다. worktree 밖의 경로는 여전히 거부된다.
- worktree 목록은 `cwdCacheTtlMs`(기본 1000ms) 동안 캐시한다.
- `statPath`, `readFile`, `readImageFile`은 응답에 `worktree` 필드를 돌려준다.
- HTML 보기는 해당 worktree 안에서 상대 경로 자산을 불러온다.

### 편집기

- 다른 worktree의 파일은 읽기 전용으로 연다.
- 안내 문구는 i18n 키 `editor.access.otherWorktree`로 표시한다.
- "화면의 파일" 메뉴는 이미 `fileApi.statPath`를 쓰므로 같은 규칙을 따른다.

### MCP 도구

- `open_markdown`, `open_code`, `open_image`, `open_html`에서 `filePath`로 기존 파일을 열 때는 `FileService.inspectReadablePath`를 쓴다. 파일 탐색과 같은 읽기 규칙을 적용한다(AC-10).
- `McpWorkspaceControl.inspectEditorFile`은 용도(`open` 또는 `write`)를 인자로 받는다.
- `html`과 `content` 본문 저장은 지금처럼 세션 폴더 안에서만 가능하다. 다른 worktree를 가리키면 `PATH_TRAVERSAL`로 거부한다(AC-3).
- `server/src/index.ts`에서 `inspectReadablePath`를 MCP 제어에 연결했다.

### 요구사항

- SEC-FOP-002(`docs/spec/43.file-operations.srs.md`, Status `implemented`, Stability `evolving`, target `worktree-read-open`)를 갱신했다.
- AC-3 문구를 고쳤다. AC-10을 추가했다. 증거 VE-5를 추가했다. Change Note를 추가했다.
- FR-ARCH-012 AC-8 문구도 함께 고쳤다.
- `docs/spec/00.index.md`에서 Active Target을 `session-stall-recovery`에서 `worktree-read-open`으로 전환했다. 그 결과 `session-stall-recovery`의 상태는 `active`에서 `planned`로 바뀌었다.
- Rationale의 "MCP 도구는 넓히지 않는다" 문장은 고칠 도구가 없어서 그대로 두었다. 대신 Change Note에 승계 사실을 적었다.

### 소비자 매니페스트 재봉인

- `server/src/index.ts`는 소비자 매니페스트가 해시로 봉인한 파일이다. 그래서 재봉인했다.
- 커밋 직전에 dry-run을 한 번 더 돌렸다. exact consumer tuples와 classifications가 모두 `unchanged`였다.
- 매니페스트 파일의 diff는 해시 4줄이다.

## 테스트와 검증

TDD 순서를 지켰다. 새 테스트를 구현 전에 작성했고, 의도한 이유로 실패하는 것을 확인한 뒤 구현했다. 테스트와 구현이 커밋 하나에 함께 들어 있으므로, 이 순서는 작업 과정의 기록으로 남긴다.

아래 수치는 커밋 직전의 최종 실행값이다. SRS VE-1에 적힌 `FileServiceWorktreeRead` 10/10은 1단계 시점의 값이다. 그 뒤 MCP 열기 단계에서 AC-10 테스트 1건을 추가해 11건이 되었다.

## 남은 한계

- 실제 브라우저와 실제 MCP 호출로는 확인하지 않았다. ego 브라우저가 자체 서명 인증서를 거부했다. Chrome은 탭 그룹을 잃었다. 그래서 SEC-FOP-002를 `verified`로 올리지 않았다.
- `npm run check:consumer-manifest`는 이 PC에서 실패한다. 이전 매니페스트 파일이 저장소에는 LF로, 작업 트리에는 CRLF로 받아져 해시가 다르기 때문이다. 이번 변경과는 무관하다. 같은 매니페스트를 검사하는 `TerminalResourcePolicy` 테스트는 21/21 통과한다.
- 이 PC의 작업 트리는 CRLF로 체크아웃되어 있다. 저장소 설정은 `core.autocrlf=false`다. 그래서 첫 스테이징 때 파일 전체가 CRLF로 들어갔다. `git -c core.autocrlf=true add`로 다시 스테이징해 HEAD와 같은 LF로 커밋했다. 실제 diff는 766줄 추가, 78줄 삭제다. 다음 커밋에서도 같은 주의가 필요하다.
- 파일 탐색기에서 worktree를 고르는 기능(2단계)은 이번 범위에 없다.
- 운영 데몬 설치본 0.10.14는 갱신하지 않았다.
