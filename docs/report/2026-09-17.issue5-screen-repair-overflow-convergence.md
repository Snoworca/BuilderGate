# Issue #5 — screen-repair overflow 를 fresh authoritative snapshot 으로 수렴

- GitHub issue: https://github.com/Snoworca/BuilderGate/issues/5 (`[Orca][P1-B]`)
- Requirement ID: `REL-BGSTAB-008` (Status `implemented`, Stability `evolving`)
- 검토 기준 트리: `e901676`
- 증거 번들: `docs/analysis/2026-09-17.issue5-screen-repair-overflow-verification/`

## VE-5 가 기록한 통과는 현재 트리에서 재현되지 않는다

`REL-BGSTAB-008` 의 verification evidence 행 VE-5 는 "HTTPS resync 2/2 PASS" 를 기록한다.
`e901676` 에서 그 두 test 는 실패하므로 **그 주장은 현재 트리에서 재현되지 않는다.**

원인은 픽스처와 클라이언트 게이트의 불일치다. 합성 `screen-repair:restore-needed` 와 그 답인
`screen-snapshot` 이 `authorityEpoch`·`authorityRevision`·`coversThroughSeq` 를 싣지 않아
`hasValidAuthorityProof` 가 거부하고, 클라이언트가
`visible_output_resync_restore_invalid_proof_ignored` 로 폐기해 stale barrier 가 engage 되지 않는다.
실 서버가 그 세 필드를 보낸다는 것은 live wire 캡처로 확인했다(`raw/probe-authority.log`).

**이것을 evidence 위조로 읽지 않는다.** 이 브랜치 이력에서 `hasValidAuthorityProof` 와 해당 spec
파일은 **같은 커밋 `c25d761`(2026-08-31)에서 함께 처음 나타나며, 그때 spec 은 proof 필드를 갖고
있지 않았다**(`git show c25d761:frontend/tests/e2e/wave2-screen-repair-resync.spec.ts` 의
`authorityEpoch` 출현 0회). VE-5 의 Change Note 는 2026-07-16 자로 그보다 6주 앞서고, 이 브랜치에는
`c25d761` 이전의 그 파일 버전이 존재하지 않는다. 따라서 VE-5 가 기록될 당시 그 실행이 통과했는지
여부는 **이 이력만으로는 판정할 수 없다.** 말할 수 있는 것은 게이트가 들어온 커밋이 픽스처를 함께
갱신하지 않았고, 그 결과 `e901676` 시점에 둘이 어긋나 있었다는 것뿐이다.

이 lane 은 VE-5 를 덮어쓰지 않았다. 새 evidence 행(VE-7·VE-8)과 Change Note 로 현재 재현 상태를
기록했다.

## 이슈 설명

screen-repair pending queue 가 byte/chunk cap 을 넘길 때 누적 출력을 하나의 문자열로 flush 하지
않고, 해당 client view 를 stale 로 만든 뒤 fresh authoritative snapshot transaction 으로
수렴해야 한다. viewport-only 복구를 retained-history 복구 완료로 판정하지 않는 것과, local
snapshot 성공만으로 dirty/skipped 를 지우지 않는 것이 함께 요구된다.

## 문제 원인

두 층으로 나뉜다.

### 1. 제품 동작 — 이미 반영되어 있었다

`e901676` 에서 이슈가 요구한 동작은 전부 존재한다.

- `WsRouter.appendScreenRepairQueuedOutput` 의 cap 초과 분기는 pending 을 삭제하고
  `startScreenRepairSnapshotRecovery` 를 호출한다. 그 안에서 `screen-repair:restore-needed`
  (`state: 'stale'`, `outcome: 'fresh-snapshot-started'`) 를 priority control 로 보내고 fresh
  snapshot replay 를 시작한다. snapshot 으로 덮이지 않은 tail 이 cap 을 다시 넘으면
  `screen-repair:reconnect-required` 로 종료한다.
- 누적 문자열 flush 는 repair 경로에 남아 있지 않다. `flushScreenRepairQueuedOutputChunks` 는
  정상 ACK 국면에서만 호출되며 chunk 단위로 identity 를 보존한 채 보낸다.
- `getScreenRepairQueuePolicy()` 는 `getReplayQueueLimit()` 과
  `resourceLimits.headless.pendingOutputMaxChunks` 를 `source: 'compatibility-cap'` 으로 재사용한다.
- 프런트는 `retainedHistoryEquivalent` 를 승급하지 않고 `currentViewTransactionReady` 만 올리며,
  local/fallback restore 는 `provisionalLocalState` 로 남는다.

### 2. 검증 산출물 — HTTPS 계약이 조용히 끊겨 있었다

`frontend/tests/e2e/wave2-screen-repair-resync.spec.ts` 의 두 테스트가 `e901676` 에서 모두
실패한다. 원인은 제품이 아니라 픽스처이며, 원인이 둘이다.

첫째, `establishTerminalHarness` 가 로그인 뒤 곧바로 `waitForTerminal` 을 기다릴 뿐 터미널을
만들지 않는다. workspace 에 터미널이 없으면 여기서 타임아웃한다. 이것이 authority proof 와 무관한
별개의 실패 경로이며, 증거 번들의 `raw/e2e-wave2-screen-repair-resync.log` 가 그 실행이다. 이것은
spec 의 전제이지 결함이 아니라고 판단해 코드를 바꾸지 않았다 — 아래 '철회한 변경' 참조.

둘째, 프런트의 `handleScreenRepairRestoreNeeded` 는 `hasValidAuthorityProof` 를 통과하지 못하는
`screen-repair:restore-needed` 를 `visible_output_resync_restore_invalid_proof_ignored` 로 버리고
`restore-needed-invalid-authority-proof` reconnect 로 수렴한다. 이 검사는
`authorityEpoch` 가 비어 있지 않은 문자열이고 `authorityRevision` 이 정수이며
`coversThroughSeq === snapshotSeq` 일 것을 요구한다.

spec 의 `buildRestoreNeeded` 는 이 세 필드를 싣지 않았다. 후속 `screen-snapshot` 주입도
`...initialSnapshot` 을 펼친 뒤 `seq` 만 덮어써서 `coversThroughSeq` 가 초기 snapshot 값으로
남았고, `matchesRestoreNeededSnapshotAuthorityProof` 에서 다시 어긋났다.

실 서버는 이 필드를 보낸다. `tools/issue5-probe-authority.mjs` 로 `https://localhost:2222` 의
`screen-snapshot` wire 를 캡처해 `authorityEpoch`(문자열), `authorityRevision`(정수),
`coversThroughSeq === seq` 를 직접 확인했다(`raw/probe-authority.log`). 따라서 어긋난 쪽은 테스트다.

그 결과 `REL-BGSTAB-008` VE-5 의 "HTTPS resync 2/2 PASS" 는 이 수정 전까지 현재 트리에서
재현되지 않는 주장이었다.

## 해결 방법

`buildRestoreNeeded` 가 authority proof 를 싣도록 하고, 그 proof 를 새 헬퍼
`resyncAuthorityProof()` 가 **관측된 authoritative snapshot 에서 파생**하게 했다. proof 필드가
없으면 헬퍼가 precondition 으로 실패하므로, 서버가 언젠가 이 필드를 보내지 않게 되면 테스트가
그 사실을 드러낸다. 같은 proof 를 restore-needed 의 답으로 주입하는 세 개의 `screen-snapshot`
프레임에도 함께 실어 `coversThroughSeq` 불일치를 없앴다. 단언을 약화한 곳은 없다 — 픽스처를
프로덕션 wire 형태에 다시 맞춘 것이다.

spec 을 `frontend/tsconfig.test.json` 의 allowlist 에 추가해 `npm run typecheck:tests` 가 이
파일을 실제로 프로그램에 넣도록 했다(`tsc --listFiles` 로 등재 확인).

`frontend/playwright.external-server.config.ts` 를 추가했다. 기본 config 의 `webServer` 를
`undefined` 로 덮어 Playwright 가 어떤 서버도 자동 기동하지 못하게 한다. E2E 는 이 lane 이 직접
띄워 소유한 외부 `https://localhost:2222` listener 만 사용한다.

## 철회한 변경 — spec 자체 시드

`establishTerminalHarness` 가 터미널을 직접 만들게 하는 변형을 작성했다가 **철회했다.** 두 가지가
드러났다. 소유권을 생성 응답의 id 가 아니라 전체 tab 목록의 차집합으로 잡아 `/api/workspaces` 읽기가
한 번 실패하면 기존 tab 전부를 자기 것으로 분류해 `afterEach` 가 사용자의 터미널을 지울 수 있었고,
hydration 신호로 쓴 sidebar 선택 표시가 `.xterm-screen` 보다 먼저 떠 터미널이 이미 있는 workspace
에서 시드 분기로 잘못 들어갔다. 대신 전제를 기록으로 남기고 도구
(`docs/analysis/…/tools/issue5-seed-terminal.mjs`)와 그 실행(`raw/seed-before-final.log`)을 함께 둔다.

## 게이트 비공허성

주장의 근거가 통과 실행 하나뿐이 되지 않도록, 두 축 모두 프로덕션 소스를 변형해 red 를 확인하고
원본을 바이트 복원했다.

- `appendScreenRepairQueuedOutput` 의 overflow 분기를 giant concatenation flush 로 되돌리면
  `Repair queue·protocol RED 계약 — AC-1/AC-3/AC-5/AC-7/AC-10` 5건이 모두 FAIL 한다.
- `handleScreenRepairRestoreNeeded` 가 stale/resync transaction 을 열지 않게 하면 수리된 E2E
  AC-4·AC-8 이 모두 FAIL 한다 (`raw/e2e-mutation-nobarrier.log`, 커밋되는 spec 에 대한 실행).

## E2E 가 덮지 못하는 범위

이 E2E 는 모든 프레임을 주입하므로 서버의 cap 초과·token abort 경로를 구동하지 않는다. SRS AC-3 의
obligation 은 VE-7 이 가리키는 서버 계약이 소유한다. `truncated:false` 완전 payload 만 주입하므로
SRS AC-4 의 incomplete parser/ANSI tail 절반도 다루지 않는다. AC-8 test 의 late-frame 단언은
`visible_output_resync_failed_snapshot_ignored` 이벤트 대신 replacement-generation fence 로도
충족되는데, 이 절충은 이번 변경 이전부터 있던 것이다. 같은 블록의 `screen-snapshot:ready` 미전송과
marker 비가시 단언은 그대로 유효하다.

## 미충족·범위 밖

- `REL-BGSTAB-008` Status 는 `implemented` 로 유지했다. `speckiwi update-status ... verified` 가
  VE-5 의 쉼표로 결합된 reference 를 단일 경로로 해석해 `MUTATION_DENIED` 로 거부하며, 기존
  evidence 행을 덮어쓰지 않기로 했다. 도구 제약이 먼저 해결되어야 한다.
- `FR-BGSTAB-015` Settings policy 와 `REL-BGSTAB-003` AC-5 는 이슈 본문이 Wave 3 로 이관했다.
- 선재 실패는 두 스위트를 합쳐 **6건**이며 전부 이 lane 의 범위 밖이고 고치지 않았다.
  - server monolithic runner 3건 — `SessionManager keeps PowerShell prompt redraw idle in heuristic mode`,
    `SessionManager powershell shell bootstrap avoids delayed prompt-hook injection`,
    `authRoutes twoFactor.externalOnly: localhost bypass skips TOTP (bugfix)`. 앞의 둘은 CLAUDE.md 가
    기록한 WSL2 플랫폼 바닥이다.
  - frontend full unit 3건 — `terminalHiddenOutput.test.ts` 의
    `REL-BGSTAB-012 settles ledger and holds stale view through drain`,
    `workspaceOwnershipMigration.test.ts` 의 B2 inventory 2건. 이 셋은 기준 트리에서 동일 재현을 확인했다.
- `WsRouterSplitHandshake.test.ts` 의 todo 13건은 Wave 3 범위다 — 12건이 Wave-1 production unified
  limitation characterization, 1건이 Wave-3 split client-group routing 이다.
- **1차 시도 불안정성이 남아 있다.** 커밋되는 spec 을 갓 만든 터미널 위에서 4회 돌렸다. 회마다
  test 2개이므로 1차 시도는 8회이고 그중 **5회가 실패해 저장소 기본 설정인 `retries: 1` 에서
  통과했다**(네 run 모두 exit 0). 내역은 RED 계약 단언 자체가 3회(iteration 1·2 의 AC-8,
  iteration 3 의 AC-4), `E2E precondition failed: target did not become actually
  hidden/dirty/skipped` 가 2회(iteration 3·4 의 AC-8)다. 계약 단언이 깨진다는 것은 stale barrier 가
  때때로 engage 되지 않는다는 뜻이다. `compatibility-post-ack-failed:convergence-timeout` 진단은
  iteration 3 의 덤프에만 있으므로 다섯 실패의 공통 증상으로 읽지 않는다. 같은 spec 의 다른 두 실행(11·12번)은 1차 시도에
  통과했다. "갓 만든 session 이 변수" 는 **가설이며 확인된 인과가 아니다** — 시드 도구가 서버 tab
  수 증가를 확인하지 않아 터미널이 실제로 새로 만들어졌는지 보증되지 않고, 대조군 로그에는 터미널
  나이가 기록되어 있지 않다. 확실한 것은 이 실패들이 커밋되는 spec 에서 관측되었다는 것뿐이다.
  표와 두 서명을 증거 번들에 남기고 별도 결함으로 보고한다.
