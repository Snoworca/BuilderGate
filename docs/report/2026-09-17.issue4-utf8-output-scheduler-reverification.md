# Issue #4 — UTF-8 output scheduler allocation과 giant coalesce 재검증

- 이슈: [Snoworca/BuilderGate#4](https://github.com/Snoworca/BuilderGate/issues/4) (부모 #2)
- 요구사항: `PERF-BGSTAB-009` (`FR-BGSTAB-003`, `PERF-BGSTAB-001`, `PERF-BGSTAB-004` 를 extends)
- 워크트리: `ProjectMaster-issue2-20260916`, 브랜치 `work/issue-2-orca-terminal-20260916`
- 검증 기준 트리: HEAD `7f7d961` (모든 원시 로그 캡처 시점)

## 1. 이슈 설명

이슈는 `frontend/src/utils/terminalOutputScheduler.ts` 의 출력 hot path 에 두 가지 결함이
있다고 기술한다. UTF-8 prefix 를 자를 때 code point 마다 `TextEncoder.encode()` 를 호출하는
것과, coalesce 가 하나의 무제한 문자열을 만드는 것이다. 요구는 출력 바이트 의미와 순서를
보존하면서 둘을 제거하는 것이다.

## 2. 문제 원인 — 이슈 본문의 전제는 이 HEAD 에서 낡았다

두 결함은 모두 커밋 `c25d761`
(`feat(terminal): decode binary frames in the browser and stop killing live terminals`) 의
부모 시점 파일에 실재했다. `takeUtf8Prefix` 가 code point 마다 `getUtf8ByteLength` 를 부르고
그것이 `textEncoder.encode(value).length` 였으며, `coalesceChunks` 가
`chunks.map(chunk => chunk.data).join('')` 로 큐 전체를 하나의 문자열로 합쳤다.

`c25d761` 이 둘을 오늘의 표현으로 교체했다 — consumed-head 인덱스를 가진 `Uint8Array` 세그먼트
deque, `subarray()` 얕은 슬라이스, continuation byte 역탐색(`findUtf8SliceEnd`), 그리고 두
비활성 세그먼트의 합이 유효 flush budget 이하일 때만 합치는 bounded merge 다. 따라서 이슈가
지목한 기전은 이 HEAD 에 존재하지 않는다.

남은 것은 결과 쪽이다. 회귀 커버리지와 legacy 대비 비용 기록이 이 호스트에서 성립하는지를
재확인했고, 그 과정에서 아래 3절의 실제 간극을 찾았다.

## 3. 해결 방법

### 3.1 이 호스트에서의 재측정 (이슈 AC-5 / `PERF-BGSTAB-009` AC-8·AC-9 — long-task 는 6절 참조)

`frontend/tests/benchmarks/` 의 기존 paired 하네스를 재사용했다. 이 하네스는 legacy 구현을
리비전 `ca111fef3b5a5a25d3aa488415c929e90ade46fd` 에서 `git show` 로 불러와 현재 프로덕션
모듈과 같은 코퍼스(mixed 110 bytes, boundary 65,542 bytes)로 맞붙인다. 두 번째 하네스를
만들지 않았고, `runPairedTerminalOutputSchedulerBenchmark` 를 5회 반복 구동했다.

결정론적 게이트는 5회 모두 동일했다.

| 지표 | legacy | 현재 |
| --- | --- | --- |
| prefix-loop `TextEncoder.encode()` 호출 | 65,638 | 0 |
| code-point 별 임시 allocation | 65,638 | 0 |
| encoder 결과 allocation | 65,640 | 2 |
| accepted ingress 당 최대 encode | — | 1 |
| output digest parity | true | true |

`output digest parity` 가 동작 동등성의 증거다 — 두 구현이 같은 바이트를 낸다.

Scheduler elapsed p95 는 legacy 290.672~399.637ms(median 354.877), 현재
2.559~13.289ms(median 5.200) 였고 paired bootstrap 게이트는 5회 모두 통과했다. 현재 구현의
산포가 자기 크기에 비해 넓으므로 timing 주장은 서수적으로만 한다 — 이 코퍼스에서 두 자릿수
배수만큼 싸다. 정확히 재현 가능한 부분은 위의 allocation 카운트다.

### 3.2 회귀 커버리지 확인 (이슈 AC-3·AC-4)

`frontend/tests/unit/terminalOutputScheduler.test.ts` 가 `PERF-BGSTAB-009` 의 AC-1~AC-10
계약을 담고 있으며, 이슈가 지정한 코퍼스를 그대로 포함한다 — ASCII, `한글`, combining
sequence, ZWJ sequence, split ANSI/OSC 를 unsplit xterm 대조군과 비교, 고립된 high/low
surrogate, N-1/N/N+1 `maxBytes` 예산. `terminalOutputSliceAlignment.test.ts` 는 실제
스케줄러를 무작위 1/2/3/4 바이트 코퍼스 200회로 구동해 어떤 write 슬라이스도 continuation
byte 에서 시작하지 않음을 단언하며, naive 고정폭 분할이었다면 어긋났을 케이스가 존재함을
함께 단언해 공허하지 않음을 보인다.

### 3.3 찾아서 고친 결함 — AC 가드가 타입 검사되지 않고 있었다

`frontend/tsconfig.test.json` 은 명시적 allowlist 인데
`tests/unit/terminalOutputScheduler.test.ts` 와 `tests/benchmarks/` 아래 파일이 하나도 들어
있지 않았다. 즉 이 요구사항의 AC-1~AC-10 가드와 AC-9 벤치마크 하네스가 어떤 TypeScript
program 에도 포함되지 않은 상태였다.

`tests/unit/terminalOutputScheduler.test.ts` 와 benchmarks 세 파일
(`terminalNoRenderFixture.ts`, `terminalNoRenderFixtureEvidence.ts`,
`terminalOutputSchedulerBenchmark.test.ts`) 을 allowlist 에 넣자
`npm run typecheck:tests` 가 10건으로 red 가 되었다.

| 결함 | 위치 |
| --- | --- |
| union 을 좁히지 않고 `droppedBytes` 를 읽음 | `terminalNoRenderFixture.ts` NO_RENDER 오버플로 경로 |
| lease 타입에 `policyId`/`profileVersion` 누락 | `terminalOutputScheduler.test.ts` `FrontendPolicyLease` |
| 파라미터 이름이 자기 `typeof` 를 가림 (2건) | `rollbackCanaryTransition` 로컬 타입 선언 |
| `Array<...>` 에 잘못된 `readonly` 수식 | canary ledger 스냅샷 타입 |
| 콜백 5개가 제어흐름 분석에서 `null` 로 좁혀짐 | restore/settle 캡처 지점 |
| 모듈 네임스페이스가 `never` 로 좁혀짐 | `@xterm/xterm` 동적 import |

10건 모두 수정해 green 이다. 콜백 5개는 기존에 optional-call 이라 캡처가 일어나지 않았어도
조용히 건너뛰고 통과했을 자리였다. 캡처를 단언한 뒤 호출하도록 바꿨고 전부 통과하므로 그
지점들이 공허했던 것은 아니다.

다섯 번째 항목 `tests/benchmarks/terminalNoRenderFixture.test.ts` 는 그 뒤에 추가했다. 이
파일은 자기가 구동하는 fixture 모듈과 별개 파일이고 AC-8·AC-10 NO_RENDER 가드를 담고 있으며
아무도 import 하지 않으므로 다른 항목을 통해 program 에 끌려오지 않는다. 포함 즉시 clean 이라
수정이 아니라 커버리지 추가다. 앞의 네 항목 중 둘도 포함 즉시 clean 이었다 — 10건은 전부
`terminalOutputScheduler.test.ts` 9건과 `terminalNoRenderFixture.ts` 1건에서 나왔다. 따라서
"포함 즉시 clean" 은 다섯 번째를 구별하는 성질이 아니며, 구별하는 것은 다른 항목이 그 파일을
program 으로 끌어오지 못한다는 점이다. allowlist 는 결국 **다섯 항목** 늘었다.
커밋 `86ea78a` 의 메시지는 이 항목을 넣기 전에 쓰여 "세 파일" 이라고 말하는데, 그 수치는 이
문서와 분석 문서가 대체한다.

프로덕션 소스 `frontend/src/utils/terminalOutputScheduler.ts` 는 이 패스에서 변경하지 않았다.
벤치마크가 고정하는 candidate source digest 가 그대로이므로 3.1 의 측정은 커밋된 트리에
그대로 적용된다.

`raw/final-verification-20260917T0950.log` 이며, `speckiwi validate` 0 errors 와

적혀 있으며 이 문서는 그것을 되풀이하지 않는다 — 틀릴 수 있는 자리를 한 곳으로 둔다. 그
커밋 이후의 커밋은 문서만 바꾸므로(`frontend/` 와 `server/` 에 차이가 없다) 기록된 결과는
그대로 유효하다.

## 6. 충족하지 못한 조건

- 이슈 AC-5 의 "CPU/allocation/**long-task** 지표" 중 long-task 는 기록하지 않았다. long-task
  는 브라우저 메인 스레드 관측인데 이 하네스는 렌더러 없이 Node 에서 스케줄러만 돌린다.
  Scheduler elapsed p95 가 가장 가까운 대리 지표이며 같은 측정이 아니다. SRS 가 실제로
  보유한 계약인 `PERF-BGSTAB-009` AC-9 는 long-task 를 요구하지 않는다.
- 이 호스트의 timing 산포 때문에 속도 향상은 서수적으로만 주장한다. 5회 반복으로 점추정은
  뒷받침되지 않는다.

어떤 포트에도 listener 를 열지 않았고 TCP 2001/2002 는 건드리지 않았다.
