### 2.2 미사용 선언 2건은 태어날 때부터 죽어 있었다

둘 다 `c25d761`(2026-08-31)에서 도입됐고 `git log -S` 상 이후 이력이 없으며, 그 커밋 시점에도
파일 안 등장 횟수가 각각 **1** — 선언 줄 자신뿐이다.

`REPLY_DA1_CONPTY = '\u001b[?61;4c'` 는 단순히 미사용인 것을 넘어 **이 spec 에 적용될 수 없다.**
이 파일의 DA1 응답 단언은 전부 `page-to-server` 방향이고, 그 방향의 응답자는 브라우저의 xterm.js
로 플랫폼과 무관하게 `'\u001b[?1;2c'` 를 답한다. ConPTY 의 응답은 서버 측이라 이 방향을 지나지 않는다.

`waitForSnapshot` 은 promotion spec 안에서 호출부가 없다. 같은 이름이 형제
`wave3-terminal-authority-fairness.spec.ts:320` 에도 있고 그쪽은 8회 쓰이지만, **구현이 다른 별개
모듈의 함수**라 이번 삭제와 무관하다.

### 2.3 신규 결함 — 대괄호 IPv6 peer 가 live 증명에서 탈락한다

첫 control 실행은 실패했다. 원인은 타입 작업과 무관했다.

`workspaceOwnershipFixture.ts:52` 의 "live loopback 증명" 이 `isLoopbackIp(address.ipAddress)` 를
쓰는데, **Chromium 이 CDP 로 보고하는 IPv6 peer 는 대괄호 리터럴 `[::1]`** 이고 `isLoopbackIp` 는
Node 의 `socket.remoteAddress` 형식(맨 `::1`)에 대한 정확 일치다. 이 런타임은 dual-stack 으로
바인드되어 브라우저가 `::1` 로 도달하므로, **모든 UI workspace 생성이 "not proven live loopback
traffic" 으로 폐기되어 소유권 registry 가 비어 있었다.** control spec 자체가 성립할 수 없었다.

## 3. 해결 방법

| # | 변경 | 비고 |
| --- | --- | --- |
| 1 | `tsconfig.e2e-ownership.json` 에 `"references": [{ "path": "./tsconfig.editor.json" }]` | `tsconfig.test.json` 과 동일한 구문 |
| 2 | 미사용 선언 2건 삭제 | **가짜 사용·`@ts-ignore`·noUnused 완화 없음** |
| 3 | `peerAddress()` 로 CDP 경계에서 대괄호 한 쌍만 제거 | `isLoopbackIp` 의 입력 계약은 건드리지 않았다 |

3번의 위치 선택이 핵심이다. `isLoopbackIp` 는 bootstrap 접근 제어에도 쓰이는 production 서술어이므로
테스트 편의로 그 허용 집합을 넓히지 않고, **CDP 형식이 들어오는 fixture 경계**에서 정규화했다.
`peerAddress()` 는 완전한 대괄호 쌍 하나만 벗기므로 잘린 대괄호(`[::1`, `::1]`), 이중 대괄호
(`[[::1]]`), zone id(`[::1%eth0]`), 비-loopback(`[2001:db8::1]`)은 전부 거부된다.
독립 reviewer 가 열거 입력 전수를 추적해 **허용 집합이 넓어지지 않았음**을 확인했다.

독립 리뷰는 2회 받았고 **두 번 모두 CRITICAL·HIGH·MEDIUM 0건**이다. 1회차 LOW 6건, 2회차 LOW
2건을 각각 `f16a8b4`·`1d718e8` 에서 반영했다. 2회차 지적 중 하나는 **`test:unit:e2e-ownership`
가 11개 중 5개만 돌리면서 하필 유일한 red 파일을 빼고 있어 "green 이 되도록 고른 것처럼 읽힌다"**
는 것이었고, 11파일 전부로 확대해 exit 1 을 그대로 드러내도록 했다. 다른 하나는 미사용 심볼
가드가 주석·문자열까지 세는 텍스트 매칭이었던 것으로, `typescript` AST 파싱으로 교체했다.
자세한 내용은 결정표 §6 에 있다.

TDD 순서를 지켰다 — RED 테스트를 먼저 커밋(`bdda2bb`, `c217524`)한 뒤 최소 구현(`dc8913a`, `0e88600`).

### 4.1 두 run 사이에 사라진 workspace — 규명

3회차 리뷰가 run 1 의 `preservedIds` 에 있던 `cbaef065-…` 가 run 2 에는 없다고 지적했다.
**실행자가 만들었고 실행자가 지웠다. 코드 경로는 관여하지 않았다.** §2.3 의 `[::1]` 결함을
진단하던 실패 실행이 UI 로 만든(POST 201) workspace 가 registry 등록에 실패한 채 남은 것이고,
실행자가 05:28 에 단일 ID `curl DELETE` 로 제거했다. 소유권 규칙("성공 POST ID 만 소유")상
실행자 소유가 맞고 사용자·형제 workspace 가 아니다. 하네스가 내는 workspace DELETE 는 `workspaceLeakGuard.ts:170`
**단 한 곳**이고 그 대상은 registry record 로만 구성된다. prefix·이름·`createdAt`·sweep-all·quota
회복 기준 선택은 0건이며, 서버 목록은 `absent` 분류에만 쓰이고 차집합 삭제에 관여하지 않는다.
**소유 집합 밖을 지울 수 있는 경로가 존재하지 않는다 — 등록할 결함이 없다.**
"run 1 의 teardown 이 쓸어갔다" 는 가설은 복원된 run 1 아티팩트가 반증한다(그 실행의 `finalIds` 에
`cbaef065` 가 남아 있다). 또한 이 worktree 의 `server/data/` 는 전부 `20:10Z` 에 생성된 checkout
전용 디렉터리라 **사용자·형제 데이터가 애초에 없었다** — 실제 제3자 데이터 위반은 없었다.

그럼에도 두 가지는 결함으로 남긴다. (1) 삭제 시점에 그 ID 는 통과한 두 run 이 `preserved` 로
분류한 상태였고 **그 provenance 가 번들 어디에도 없었다** — 리뷰어 지적 전까지 번들만으로는
판별 불가였다. (2) 재측정이 control 산출물을 **같은 이름으로 덮어써** 그 존재의 유일한 기록을
지웠다. 전자는 결정표 §3.3 에, 후자는 §9.2 의 파일 명명 규칙 변경과, 덮어쓰기 이전 커밋 `0b8a39f` 에서 run 1 원본을
**바이트 단위로 복원**해 보존하는 것으로 처리했다(재구성이 아니다).
`preservedIds == finalIds` 단언의 범위가 **run 1회 안**임도 결정표에 명시했다.

**회귀 2건은 사전 존재이며 이 변경의 결과가 아니다.** baseline `1a68731` 의 e2e 트리를 일시
checkout 해 같은 명령을 돌린 결과 **동일한 2건이 동일 이름으로 실패**했다(49/47/**2**).
`workspaceOwnershipMigration.test.ts` 가 `markdown-editor-{persistence,save}.spec.ts` 의
소유권 경계 위반을 잡는 것으로, 이 작업이 건드리지 않은 파일들이다. **별도 이슈 대상이다.**

## 5. 안전 규칙 준수

- 2222 만 사용했다. **2001·2002(PID 30596)에는 어떤 종료·신호·요청도 보내지 않았고**, 실행 전후
  netstat 재관측에서 네 행이 동일하게 LISTENING 이다.
- Playwright 가 서버를 자동 기동하지 않았다 — `playwright.ownership-validation.config.ts` 가
  `webServer: undefined` 다.
- 종료는 cmdline·cwd 를 확인한 **단일 PID(초회 24553, 재측정 30194)** 에만 `kill`. 트리 종료·전체 node 종료 없음.
  **단, 그 WSL PID 는 어떤 아티팩트에도 보존돼 있지 않다** — `netstat.exe` 의 PID 열은 Windows PID 라
  WSL listener 는 릴레이 PID(`26080`)로 나타나기 때문이다. 보존된 캡처가 증명하는 것은
  **2001·2002 가 PID 30596 아래에서 계속 LISTENING 이라는 사실**뿐이다(결정표 §3.1).
- 사용자/형제 workspace 를 삭제하지 않았고 quota 실패 시 eviction 을 하지 않았다.
- 원본 checkout `…/ProjectMaster` 는 건드리지 않았다. SRS 변경은 CLI 에 `--root <worktree>` 로만.

  위험하지만, 그 단언이 같은 파일에 있고 더 강하므로 **추격하지 않기로 결정했다**(RG-04-F6).
