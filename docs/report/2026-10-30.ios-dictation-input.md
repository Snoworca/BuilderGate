# 아이폰 음성 입력에서 어절이 반복되는 문제 수정

## 개요

이 보고서는 아이폰에서 키보드의 음성 입력으로 터미널에 말하면 어절이 반복해서 들어가던 문제를 고친 결과를 기록한다.

- 요구사항: FR-BGSTAB-037(신설, `docs/spec/30.buildergate-stability.srs.md`), 타깃 `ios-hangul-input`
- 이슈: #210
- 브랜치: `fix/ios-dictation-input`(맥 Safari 수정 브랜치 `fix/mac-safari-hangul-input`의 `577e89ab` 위)
- 작업일: 2026-10-30

## 증상

"안녕하세요 오늘 날씨가 좋네요"라고 말하면 터미널에 `안안녕하안녕하세요안녕하세요 오늘…`처럼 앞 어절이 반복해서 들어갔다.

## 측정

입력 직전의 선택 범위를 함께 기록하는 진단 페이지를 2222에 임시로 두고 아이폰(iOS 18.7 Safari)에서 측정했다. 비교 대상은 일반 입력칸과, 그 시점에 배포된 터미널 입력 처리(FR-MKB-015, FR-BGSTAB-036)를 붙인 xterm이다.

| 순서 | 입력 직전 선택 범위 | `insertText`로 넣은 내용 | xterm이 보낸 것 |
|---|---|---|---|
| 1 | 0-0 | `안` | `안` |
| 2 | 0-1 (`안`) | `안녕하` | `안녕하` |
| 3 | 0-3 (`안녕하`) | `안녕하세요` | `안녕하세요` |
| 4 | 0-5 | `안녕하세요 오늘` | `안녕하세요 오늘` |

일반 입력칸에서는 인식이 끝날 때 종류가 없는 입력(`inputType` 빈 문자열)으로 문장을 정리하는 단계도 보였다.

## 문제 원인

- 음성 입력은 인식 결과가 다듬어질 때마다, 지금까지 넣은 문장 전체를 선택하고 새 결과 전체를 `insertText`로 다시 넣는다.
- xterm.js 6.0.0은 키가 눌려 있지 않을 때 온 `insertText`의 데이터를 그대로 보내고, 선택된 부분을 지우지 않는다. 그래서 결과가 나올 때마다 문장 전체가 덧붙었다.
- 맥 Safari 수정(FR-BGSTAB-036)은 xterm이 직접 보내는 `insertText`를 건드리지 않게 만들었으므로 이 경우를 덮지 못했다.

## 해결 방법

- 입력 직전에 선택 범위가 있는 `insertText`는 입력칸의 상위 요소(`termEl`)에서 capture 단계로 먼저 받는다. 이 리스너는 입력칸에 직접 붙은 xterm의 리스너보다 먼저 실행된다. 이 이벤트는 전파를 멈춰 xterm에 넘기지 않는다. (AC-4)
- 대신 입력칸이 바뀐 만큼만 보낸다. `안녕하` → `안녕하세요`는 `세요`를 보내고, `안녕하세요 오늘 날씨` → `안녕하세요. 오늘 날씨가`처럼 앞부분이 바뀌면 공통 부분 뒤를 `DEL`로 지운 뒤 새 내용을 보낸다. 같은 내용으로 다시 넣으면 아무것도 보내지 않는다. (AC-1, AC-2, AC-3)
- 입력칸에 실제로 넣는 일은 iOS가 하므로 음성 입력 세션을 방해하지 않는다.
- 인식이 끝날 때의 종류 없는 입력은 FR-BGSTAB-036 경로가 바뀐 만큼 보내므로 따로 처리하지 않았다. 테스트로 최종 문장이 맞는지 확인했다.
- 선택 범위가 없는 입력, 조합 입력, 아이폰 자모 입력은 바꾸지 않았다. (AC-5)

## 검증

- `dictationInput.test.ts` 7/7: 수정 전에는 7건 모두 실패했다(`interceptInput` 없음).
- `terminalIosHangulInput.test.ts` 9/9: 새 배선 테스트는 수정 전에 실패했다(세 입력 모두 입력칸 리스너까지 감).
- 회귀: `macSafariHangulInput.test.ts` 8/8, `iosHangulInput.test.ts` 14/14, 터미널 뷰 동작 93/93, 모바일 키보드 98/98, 앱·테스트 타입 검사 통과. 프런트 단위 테스트 전수에서 실패한 파일은 전용 러너에서만 도는 렌더 테스트 목록과 같았다.
- 아이폰 확인(사용자, 2222): 음성 입력으로 말한 문장이 반복 없이 한 번 들어갔고, 이어서 키보드로 치거나 지워도 문제가 없었다.

## 한계

- 선택 범위가 문장 끝까지 이어지지 않는 덮어쓰기(가운데 일부만 고치기)도 공통 부분 뒤를 모두 지우고 다시 보내므로 결과 문장은 맞다. 다만 터미널 커서가 입력 끝에 있다고 가정한다.
- 입력칸의 상위 요소에서 전파를 멈춘 이벤트는 TerminalView의 입력칸 리스너(디버그 기록)에도 가지 않는다.
