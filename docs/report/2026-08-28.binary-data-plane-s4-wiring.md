# 바이너리 데이터 평면 — S4 프로덕션 배선 (A1~A11 · B1 전건 · B2 #1~#9)

작성일 2026-08-28 · 브랜치 `work/mcp-session-orchestration-20260709` · **미커밋**

## 1. 이슈

2026-08-27 세션이 순수 모듈 8개를 만들었으나 **프로덕션 경로에 배선하지 않아 아무것도 흐르지 않는 상태**였다. 남은 계획은 A1~A11(S4 완주), B1(S3 조용한 폐기 8항목), B2(S4-0b 열린 항목 9건)였다.

blocking 결정이었던 `streamEpoch` 승격 범위는 사용자가 **전체 승격**을 선택했다.

## 2. 문제 원인

### 2.1 `streamEpoch` 승격의 전제가 문서보다 가벼웠다

핸드오프는 `SessionManager.ts:1076` 의 카운터가 **전역**이라 세션 소유가 아니라고 기술했으나, 실측 결과 `retained.streamEpoch` 는 **이미 세션별 상태**(`SessionManager.ts:405`)이고 전역 카운터는 최초 값을 발급하는 원천일 뿐이었다. 빠져 있던 것은 `01:476-480` 의 다섯 증가 사건을 이름 붙여 검사하는 원장이다.

### 2.2 협상 거절 사유 오보

`terminalBinaryGroupSession` 이 설정 사실(`terminalWireFormat`)을 `everySocketBinaryCapable` 에 그대로 넣어, 원인이 `group-not-eligible` 인데 `socket-not-binary-capable` 로 보고했다. 클라이언트는 서버 운영자만 바꿀 수 있는 것을 자기 연결 탓으로 오해하게 된다.

### 2.3 뮤테이션 하네스의 공허한 KILLED

provenance 핀 파일(`WsRouter.ts`·`wsSendPolicy.ts` 등 6개)을 뮤테이트하면 published generation 이 무효화되어 capability admission 게이트가 닫히고, 그 게이트를 타는 스펙은 **뮤턴트와 무관하게 빨개진다.** 초기 하네스가 `WsRouterSendPriority.test.ts` 를 포함해 4/4 KILLED 를 보고했으나, 그 스펙을 제외하자 **2건이 실제로는 살아남았다.**

### 2.4 xterm 이중 디코더 순서 위험 (`03:340` 의 `[미확인]` 판정)

- **혼합 조건은 현행 코드에 이미 존재한다.** `compatibility-write` 가 문자열을 그대로 보존하고(`terminalWriteCoordinator.ts:1983`) `terminalRawMutationAdapter.ts:82` 가 `terminal.write` 로 그대로 넘긴다. 반면 live·repair·checkpoint body·parser-tail 은 전부 `Uint8Array` 다.
- **체크포인트 슬라이스는 코드포인트 경계에 정렬되지 않는다** — `terminalWriteCoordinator.ts:1091-1093` 이 32 KiB 고정 `Math.min` 을 쓴다. live 경로가 쓰는 `findUtf8SliceEnd`(`terminalOutputScheduler.ts:1271`)와 대비된다.
- **그럼에도 슬라이스 사이 역전은 도달 불가능하다.** `pump()`(`:900`)가 활성 mutation 이 있으면 다른 것을 시작하지 않고, 체크포인트가 `queue.unshift`(`:997`)로 큐 머리를 유지한다. 즉 **막고 있는 것은 인코딩이 아니라 큐**다.
- ⚠️ **미판정**: 마지막 `parser-tail` 바이트 write 직후 큐에 대기하던 비어 있지 않은 문자열 write 가 실행되는 창. `parserTail` 이 코드포인트 중간에서 끝날 수 있는지는 이 작업에서 확인하지 않았다.

## 4. 도중에 잡은 실제 결함

1. **`streamEpoch` 발급 방식** — 세션별 1부터로 바꾸자 `RetainedTerminalAuthority` 가 깨졌다. 명세(`01:462`)가 "기존 전역 카운터를 정본으로 승격"이라 못박고 있어 전역 단조 발급으로 되돌렸고, bump·adopt 도 전역 카운터에서 값을 받아 세션 간 epoch 이 겹치지 않게 했다.
2. **`session` 없는 레거시 `SessionData`** — `ensureRetainedTerminalSessionState` 가 `TypeError` 로 resize 를 깨뜨렸다. 경계 테스트를 추가하고 가드했다.
3. **협상 거절 사유 오보** (§2.2) — 설정 사실과 소켓 능력을 분리했다.
4. **불필요한 그룹 할당** — 협상을 시도하지도 않은 클라이언트에 그룹 상태를 만들고 있었다. 생성 지점을 offer 핸들러 하나로 좁혔다.
5. **하네스 잔류물** — 하네스가 중간에 죽어 `WsRouter.ts` 에 뮤턴트(`?? 'binary'`)가 남아 있었다. 복구했고, 이후 하네스는 앵커를 전부 사전 검증하고 `finally` 로 복원한다.

### 7.2 #4 — `retained.checkpoint.cursor` 상한: **uint32 유지**

프롤로그를 200 → 192 B 로 줄이려면 커서 4필드(off 80~95)를 uint16 으로 좁혀야 한다. **좁힐 수 없다.**

값의 출처는 `headlessTerminal.ts:312-314` 의 `terminal.buffer.active.cursorX/Y` 이고, 그 상한은 단말의 `cols`/`rows` 다. 그런데 **서버 어디에도 `cols`/`rows` 상한 검사가 없다**.

- `WsRouter.handleResize`(`:3182-3199`)는 `message.cols`/`message.rows` 를 검사 없이 `SessionManager.resize` 로 넘긴다.
- `SessionManager.resize`(`:3410`) → `applyRetainedTerminalResize` → `resizeHeadlessTerminal`(`headlessTerminal.ts:251-253`)는 `state.terminal.resize(cols, rows)` 한 줄이다.
- `VALIDATION_LIMITS.MAX_COLS = 500` / `MAX_ROWS = 200`(`utils/constants.ts:131-137`)은 **정의만 있고 사용처가 0건**이다.

실측 (2026-08-28, xterm headless):

| 요청 | 실제 적용 | `cursor.x` | uint16 초과 |
|---|---|---:|---|
| 80×24 | 80×24 | 79 | 아니오 |
| 500×200 (`VALIDATION_LIMITS` 최대) | 500×200 | 499 | 아니오 |
| 65535×50 | 65535×50 | 65534 | 아니오 |
| 65536×50 | 65536×50 | 65535 | 아니오 |
| **70000×50** | **70000×50** | **69999** | **예** |

xterm 은 클램프하지 않는다. 따라서 uint16 으로 좁히면 **도달 가능한 값이 잘리고**, 잘린 커서는 "커서가 틀림"이 아니라 digest 불일치 → 복구 루프로 나타난다. 8바이트를 얻으려면 `cols`/`rows` 에 실제로 강제되는 상한을 먼저 도입해야 하며, 그것은 별도 변경이다.

`server/src/utils/headlessTerminal.test.ts` 에 이 도달성과 경계 대조군을 테스트로 고정했다(`0x11223344` 를 왕복시키는 기존 코덱 테스트는 uint32 를 고정하지만 **왜** 필요한지는 고정하지 않는다).

### 7.3 #9 — `screen-repair` ACK 타임아웃 경로: **수렴한다**

항목이 전제한 "미지 `repairTokenIndex`" 는 **아직 존재하지 않는다** — `binaryFrameCodec.ts:133-145` 의 `prologueBytes` 가 `SCREEN_REPAIR` 를 `default: return 0` 으로 떨어뜨리므로 `0x03` 프롤로그 자체가 미구현이고, 두 코덱 파일 어디에도 `repairToken` 이 없다.

다만 그 프레임이 착지할 **타임아웃 경로는 실재**하며, 응답하지 않는 클라이언트만으로 오늘도 도달한다. 그 경로가 끝나는지를 실측했다.

- 무장: `armScreenRepairAckTimeout`(`WsRouter.ts:4015-4029`), `SCREEN_REPAIR_ACK_TIMEOUT_MS = 5_000`(`:108`), 타이머는 `unref()`.
- 만료: `handleScreenRepairAckTimeout`(`:4180-4214`)가 토큰 일치를 확인하고, 계수를 올리고, **pending 항목을 삭제한 뒤** `startScreenRepairSnapshotRecovery(..., 'ack-timeout', ...)` 를 부른다.
- 복구(`:4283-`)는 스냅샷 재생 또는 `reconnect-required` 로 끝나며 **repair 타임아웃을 다시 무장하지 않는다.**

`server/src/ws/WsRouterScreenRepairAckTimeout.test.ts` 6건으로 고정했다 — 정확히 1회 계수 · pending 삭제로 재발화 불가 · 수퍼시드된 토큰은 무시 · 클라이언트가 행동할 수 있는 메시지로 종결 · 대기 중이 아니면 발화하지 않음(경계 대조군). 뮤턴트 4/4 KILLED(대조군 생존).

### 7.4 #5 — split 모드의 `view.connectionId`: **control 소켓이 발급하고 output 이 상속**

`0x04` 프롤로그에서 `connectionId` 를 제거하고 "수신 클라이언트가 자기 `connected` 값으로 복원한다"는 설계는 **값의 일의성 측면에서는 성립한다.**

| 확인 항목 | 실측 (2026-08-28) |
|---|---|
| control 발급 | `WsRouter.ts:1685-1687` — `const connectionId = uuidv4();` · `const clientGroupId = requestedMode === 'unified' ? connectionId : uuidv4();` · `const clientId = clientGroupId;`. split 에서 `clientGroupId` 는 **별도 uuid** 이므로 세 개념이 같지 않다 |
| output 상속 | output 소켓은 `uuidv4()` 를 부르지 않고 `connectionId: group.connectionId` 를 그대로 쓴다 — 5곳(`:1617`·`:1627`·`:1642`·`:1652`·`:1672`) |
| 뷰 수집 | `WsRouter.ts:717` 이 `meta.channelRole === 'output'` 인 meta 를 루프 초입에서 배제한다 → `view.connectionId` 는 **control meta 에서만** 유래 |
| 클라이언트 저장 | `WebSocketContext.tsx:1066-1075` 가 output 채널의 `connected` 에서 조기 반환하고, control 만 `:1078` 에서 `controlConnectionIdRef` 에 저장한다 |

즉 unified·split·split-shadow 세 모드 모두에서 "클라이언트가 아는 자기 `connectionId`" 와 "서버가 `view.connectionId` 에 넣는 값" 은 **같은 하나의 uuid** 이며, "어느 소켓 값을 골라야 하나"라는 모호성은 없다.

⚠️ **다만 제거하면 검사 하나가 공허해진다.** `terminalCheckpointRuntime.ts:519` 의 `matchesTransactionIdentity` 가 `identity.connectionId === value.connectionId` 를 비교하는데, 프롤로그가 값을 싣지 않고 클라이언트가 자기 값으로 채우면 **두 피연산자의 출처가 같아져 항상 참**이 된다. 낡은 연결 세대의 프레임을 걸러내던 검사가 무력화되는 것이므로, 필드 제거는 그 손실을 감수하는 결정이다.

정정: 서브에이전트 보고는 이 공허화의 대상을 `TerminalView.tsx:3635`(`control-socket-identity-mismatch`)로 지목했으나 **그 검사는 해당하지 않는다.** 그것이 읽는 `message` 는 `terminal-authority:legacy-responder-enabled`(`TerminalAuthorityController.ts:1801`)이며 **JSON control 평면**으로 서버 값을 계속 싣는다. 공허해지는 것은 `0x04` 프롤로그에서 값을 얻던 checkpoint identity 비교 쪽이다.

이 항목은 `06` 이 "D3 상 v1 범위 밖이나 판정 근거는 필요"로 분류한 것이므로, v1 에서 필드를 제거하지 않는다면 위 손실은 발생하지 않는다.

### 7.5 #8 — `replayToken` 회전 속도: **(소켓, 세션)당 동시 1개** — `repairToken` 과 같은 논증이 성립한다

| 확인 항목 | 실측 (2026-08-28) |
|---|---|
| 저장 구조 | `meta.replayPendingSessions` 는 소켓 meta 당 `Map<sessionId, ReplayPendingState>` → **한 쌍에 상태 하나** |
| 발급 지점 **전수 2곳** | `WsRouter.ts:3574` `replayToken: uuidv4()` (새 pending 상태 생성) · `WsRouter.ts:5406` `pending.replayToken = uuidv4()` (스냅샷 갱신 시 **같은 상태 위에 제자리 덮어쓰기**, 직전에 `clearTimeout(pending.timer)`) |
| 유효성 | `consumeReplayPendingForPair`(`:3717`)가 `pending.replayToken !== replayToken` 이면 거부한다 → **수퍼시드된 토큰은 유예 없이 즉시 무효** |
| 기존 커버리지 | `src/ws/WsRouterRestoreMetadata.test.ts:427` 이 token-fenced supersede 를 end-to-end 로 덮는다(stale 토큰 케이스 `:453`). 같은 계약을 다시 쓰지 않았다 |

**회전은 메시지마다가 아니라 스냅샷 갱신마다** 일어난다. 한 토큰이 살아 있는 동안 그것을 싣는 것은 `screen-snapshot` 1건 + 그 창 안의 **출력 메시지 N건**이다 — 토큰은 전송 사이드카 필드(`wsSendPolicy.ts:29`)이자 출력 delivery 필드(`frontend/src/utils/terminalOutputDelivery.ts:45`)로 함께 실린다.

**인덱스화 이득: 있음(조건부).** `repairToken` 을 닫은 논증이 그대로 성립한다 — 한 쌍에 살아 있는 토큰이 하나뿐이므로 작은 인덱스로 충분하고, 그 인덱스가 replay 창 안의 모든 출력 프레임에 반복해서 실린다. 이득의 크기는 한 토큰이 덮는 출력 프레임 수에 비례하며, replay 가 걸려 있지 않은 동안에는 필드 자체가 부재이므로 이득도 0 이다.

⚠️ **런타임 빈도는 측정하지 않았다.** 위는 전부 정적 판독이다. 실제 운용에서 스냅샷 갱신이 얼마나 자주 일어나는지(= 한 토큰이 평균 몇 개의 출력 프레임을 덮는지)는 계측하지 않았으므로, 이득의 **크기**는 미지수이고 이득의 **존재**만 확정했다.

### 7.6 값싸게 판정한 것

- **#6** `0x04` metadata 의 프론트엔드 **외부** 소비자: `tools/`·`server/tools/` 전수에서 **0건**.
- **#7** 골든 벡터 `output-minimal-52` 의 `authorityEpochIndex = 0` 은 **"부재" 의도가 아니다.** 그 벡터는 `screenSeq`·`chunkIdBase`·`authorityRevision`·`segmentCount` 가 전부 0 인 "최소 유효 OUTPUT 프레임"이며, 0 은 각 필드의 최소값이다. 따라서 이 벡터를 근거로 1-based 인덱스 규칙을 소급할 수 없고, 현재 구현(`terminalBinaryGroupSession` 의 `authorityEpochIndex: 0`)과도 일치한다.

### 7.7 서브에이전트

CLAUDE.md 규칙대로 #2·#3 을 opus5 서브에이전트 2개에 위임했다. `b2-lane-fallback`(#2)과 `b2-replay-token`(#8)은 재요청 후에도 판정 없이 유휴로 종료해 **기권 처리**했고 두 항목 모두 직접 확인했다. `b2-connection-id`(#5)는 재요청 뒤 판정을 회신했으며, 하중을 받는 주장 4가지(control 발급 · output 상속 5곳 · 뷰 수집의 output 배제 · 프론트의 조기 반환)를 전부 현재 소스로 재확인했다. 다만 그 보고가 공허화 대상으로 지목한 `TerminalView.tsx:3635` 는 **틀렸고**, 실제 대상은 `terminalCheckpointRuntime.ts:519` 다(§7.4 참조). `b2-responder-lease` 는 재요청 뒤 판정을 회신했으며, 그 주장 중 하중을 받는 것(인코더 `RangeError` 3종 · 디코더 동형 복원 · 픽스처 오프셋 · `identity` 조립 파일 · 코덱 테스트 green)을 전부 현재 소스로 재확인했다. 다만 그 보고가 든 `frontend/src/types/ws-protocol.ts:1000` 의 `isCheckpointIdentity` 는 **확인되지 않았다** — 프론트 `ws-protocol.ts` 에는 그 가드가 없고 서버 쪽에만 있다.

### 7.8 이 조사 중에 잡은 제 결함

`WsRouter.ts` 를 읽던 중 **A5 편집이 남긴 중복 줄**을 발견했다. `this.terminalBinaryGroups.delete(...)` 가 들여쓰기가 어긋난 채 두 번 들어가 있었고, 두 번째 teardown 지점(`:1750`)은 **아예 누락**되어 있었다. 원인은 치환 앵커가 12칸 들여쓰기 줄의 접미사와도 일치해 한 지점에 두 번 적용된 것이다. 두 저장소를 함께 지우는 `forgetSplitClientGroup` 하나로 모으고 테스트 2건과 뮤턴트 2건(R14·R15, 둘 다 KILLED)을 붙였다.
