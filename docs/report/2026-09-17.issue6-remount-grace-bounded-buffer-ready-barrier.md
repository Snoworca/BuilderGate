## 2. 실제로 남아 있던 결함 — 게이트가 공허했다

`remount grace lane`(`bufferGraceMessage` / `flushGraceBuffer`)은 `WebSocketContext` 안의 의존성 없는 `useCallback` 두 개였고, 그 계약은 **`WebSocketContext.tsx` 를 문자열로 읽어 regex 로 단언하는 테스트로만** 지켜지고 있었다. 그런 게이트는 토큰을 보존하는 어떤 재작성으로도 만족된다.

실측으로 확인했다. baseline `b34fda9` 를 별도 worktree 에 꺼내 `flushGraceBuffer` 의 snapshot 블록과 held-tail 루프를 **맞바꾸고**(= current server snapshot 이 held tail *뒤에* 적용되는 AC-3 정면 위반) **프런트 단위 테스트 전체**를 돌렸다:

```
cd <b34fda9 worktree>/frontend && node --experimental-strip-types --test tests/unit/*.test.ts
→ tests 1258 / pass 1255 / fail 3        [exit 1]
```

실패 3건은 그 변형과 무관한 선재 실패와 **같은 3건**이다. 즉 이슈가 "the ordering is the product" 라고 부른 바로 그 성질이 **저장소의 어떤 테스트로도 지켜지고 있지 않았다.** (이 수치는 부분 집합이 아니라 전체 집합이므로 스위트 이름을 열거할 필요 없이 그대로 재현된다.)

## 4. 순서 증명 (AC-3)

`grace flush applies the current server snapshot before the held tail and opens the input gate only after the tail drains` 는 모든 핸들러 호출을 배열에 기록하고 **관측된 시퀀스 전체**를 단언한다:

```
['restore-needed', 'snapshot', 'output:tail-a', 'output:tail-b', 'output:tail-c', 'ready']
```

리터럴 시퀀스에 더해 불변식을 따로 단언한다 — 모든 `output:` 인덱스가 `snapshot` 뒤이고 `ready` 앞이다. 최종 버퍼 상태만 보는 단언은 잘못된 순서에서도 통과하므로, 순서 자체를 관측 대상으로 삼는다.

### held prefix 에 대한 정정

처음에 "snapshot 이전에 도착한 held prefix 는 제거된다" 를 단언하는 테스트를 썼고 red 가 났다. 그러나 **처음 쓴 정정도 지나치게 넓었다.** 이 lane 은 prefix 를 제거한다 — 다만 **restore 가 걸려 있지 않을 때만** 그렇다. 두 경로가 갈린다:

- **plain grace**(`!current.restoreNeeded`) — snapshot 이 곧 현재 view 전체이므로 그 앞의 held prefix 는 이미 covered 다. `case 'screen-snapshot'` 의 `if (!current.restoreNeeded)` 블록이 `output`·`outputBytes`·`outputOverflowReason` 를 비운다. `a plain grace snapshot with no outstanding restore prunes the held prefix it covers` 가 이것을 덮는다.
- **restore 가 걸린 경우** — 서버가 새 generation 의 replay tail 을 보내며 그 청크들은 snapshot 프레임을 사이에 두고 걸쳐 있다. **도착 순서로 자르면 출력을 잃는다.** coverage 는 sequence 로 증명되며 그 증명은 하류의 `visibleOutputRecovery`(`authoritative-snapshot-applied` / `output-arrived` 경로, `visible output recovery drops a snapshot-covered late chunk before cap accounting` 가 덮는다)에 있다. 이 경로에서는 grace lane 이 선점해서는 안 된다. 테스트를 프로덕션에 맞춰 통과시킨 것이 아니라, **어느 층의 계약인지**를 다시 판정하고 그 판정을 테스트 주석에 남겼다.

**남은 한계를 명시한다.** 하류 pruning 이 존재한다는 것은 확인했지만(`visibleOutputRecovery` 가 `screenSeq <= snapshotSeq` 로 자른다), grace lane → 하류 pruning 의 **hand-off 자체는 이 스위트에서 end-to-end 로 단언되지 않는다.** 인용한 하류 테스트는 recovery coordinator 를 직접 구동하며 grace lane 을 거치지 않고, 이 스위트의 `output()` 픽스처는 하류가 키로 쓰는 `screenSeq` 를 아예 싣지 않는다. 그 연결은 현재 주석으로만 기술되어 있다. AC-3 의 "snapshot sequence coverage 가 증명된 held prefix 제거" 절을 두 층에 걸쳐 관통 검증하는 것은 이 lane 에서 하지 않았다.

## 5. AC-5 의 세 경합 — 각각의 실패 케이스

이슈는 delayed write callback / dispose / generation 의 셋을 각각 다루라고 요구한다. grace lane 에 대응되는 실패 케이스:

| 경합 | 실패 케이스 (테스트 제목) |
| --- | --- |
| generation supersede | `grace buffer drops held output from a superseded replay generation` — 이전 `replayToken` 의 청크는 버퍼에 들어가지 못한다 |
| authority 교체 | `grace flush reports an authority proof mismatch and withholds the snapshot and ready` — proof 불일치 generation 은 snapshot·ready 를 현재 view 에 전달하지 못한다 |
| 반복 remount(생애 교체) | `a new restore generation purges the previous generation held tail from the same session state` — **하나의 state 객체**를 두 generation 에 걸쳐 유지한다. 프로덕션 `bufferGraceMessage` 가 session 의 map 엔트리를 재사용하므로, state 객체를 두 개 만들면 정작 중요한 in-place purge 경로가 실행되지 않는다 |
| duplicate 판정 축소 | `a re-issued restore with the same repair token but a new replay generation is not treated as a duplicate` — 3-key 판정이 repairToken 단독으로 좁아지면 새 generation 이 duplicate 로 삼켜진다 |
| stale ready token | `a replacement snapshot invalidates the ready token latched for the generation it replaces` — snapshot 교체 후 옛 ready 로 input gate 가 열리지 않는다 |
| unproven authority | `a restore-needed frame with no authority proof is rejected rather than engaging the barrier` — fail-closed 거절 분기 자체 |

`TerminalView` 측 delayed callback/dispose 경합은 이 lane 의 범위가 아니며 `isCurrentRestoreAttempt` / `terminalDisposedRef` 로 이미 fence 되어 있다(VE-2 가 덮는다). 이 lane 에서 새로 증명한 것은 위 여섯 축이다.

**공허한 픽스처는 이 스위트에서 세 번 나왔다**(row E, snapshot proof-mismatch, 그리고 그 사이의 하나). 셋 다 같은 형태다 — **설정된 적 없는 state 는 그것이 지워졌음을 증명할 수 없다.** 셋 다 통과하는 실행으로는 드러나지 않았고 변형으로만 드러났다. 공허한 단언은 존재하는 내내 통과하며, 통과하는 테스트는 조용하기 때문이다. 그래서 실행 가능한 규칙은 "단언을 눈으로 검토하라" 가 아니라 이것이다: **전이(transition)를 단언하는 테스트는 그 전이를 수행하는 프로덕션 줄을 변형해 보라. 그래도 통과하면 그 단언은 전이가 아니라 초기 상태를 기술하고 있다.**

**K1 은 이 표가 두 번째로 잡은 자기 결함이다.** row E 를 위해 쓴 테스트가 빈 state 에서 시작해 `restoreNeeded === undefined` 를 단언했는데, 그것은 프로덕션이 무엇을 하든 참이었다 — invalid-proof 분기가 그 필드를 비우기를 그만둬도 통과한다. 채택된 generation 을 먼저 시드하도록 픽스처를 고쳤다. 이것은 2라운드에서 닫은 결함(두 개의 state 객체 대 하나)이 **이번에는 테스트 내부에서** 재발한 것이다.

**의도한 가드가 red 가 된 변형: 31/31.** 우연히 걸린 무관한 테스트로만 잡힌 변형은 없다.

리뷰가 지적한 `subscribedInfo` 공백은 이 판에서 닫혔다. 그 전까지 `recoveryBlocked ? false : …` 의 ready 억제와 `onSubscribed` 방출 전체는 **오직 잔존 regex 스위트만이** 지키고 있었다 — 실행 가능한 스위트는 `subscribedInfo` 를 한 번도 설정하지 않았다. 지금은 `subscribed ready is forced false while recovery is blocked and passes through once it is not` 가 그 계약을 소유한다. ## 9. 충족·미충족

**이 절의 체크박스는 AC 자체의 상태가 아니라 *이 lane 이 만든 증거가 무엇을 덮는가* 를 표시한다.** `REL-BGSTAB-009` 의 AC-1~AC-10 은 SRS 에서 모두 `[x]` 이며 이 lane 은 그것을 바꾸지 않았다. 아래에서 "미충족" 은 **그 AC 가 거짓이라는 뜻이 아니라 이 lane 의 증거가 그 절반에 닿지 않는다는 뜻**이다. 소유가 다른 곳에 있는 항목은 소유자를 함께 적었다.

## 10. 신규 결함 (오케스트레이터 보고용, 이슈를 직접 열지 않음)

1. **`kiwi/.status.json` 자동 갱신이 stale 값을 쓴다** — #79 의 실측 사례. `add-change-note` 직후 `.status.json` 의 `30.buildergate-stability.srs.md` sha256·size 가 실제 바이트와 불일치했다. `sync-index` 로 덮어써야 맞는 값이 된다.
2. **`WebSocketContext.tsx` 의 grace map 이 세션 수에 대해서는 unbounded** 다. per-session byte/chunk cap 은 있지만 `graceBufferedSessionsRef` 자체의 엔트리 수 상한은 없다. detach 된 세션 수에 묶여 있어 현실적 위험은 낮으나 이 이슈의 범위(lane 내부 bounded 화) 밖이라 손대지 않았다.
3. **`applyGraceBufferedMessage` 의 `case 'screen-repair:restore-needed'` 안 `current.reconnectRequired = undefined;` 는 도달 불가능한 dead store 다.** 같은 case 머리의 `if (current.reconnectRequired) { ...; break; }` 가 그 상태를 이미 걸러내므로 이 줄이 실행되는 입력이 없다. 삭제해도 관측 가능한 변화가 없음을 확인했다(테스트 구멍이 아니라 프로덕션 dead code). **이 lane 에서 고치지 않았다** — 추출이 공백 정규화 후 토큰 동일하다는 provenance 가 이 작업의 핵심 증거이고, 그것을 깨는 대가가 dead store 하나를 지우는 이득보다 크다고 판단했다. baseline `b34fda9` 의 `WebSocketContext.tsx` 에도 같은 형태로 존재한다.

4. **`applyGraceBufferedMessage` 의 `case 'screen-repair:restore-needed'` 안 `current.ready = undefined;` 도 관측 가능한 효과가 없다.** 같은 reset 이 `current.snapshot = undefined` 를 함께 하므로 이후 flush 는 `recoverySnapshotReady` 에서 막히고, snapshot 이 도착하면 `case 'screen-snapshot'` 이 `current.ready` 를 다시 비운다. 제거해도 28/28 + 60/60 green 임을 확인했다. 위 3번과 같은 이유로 **이 lane 에서 고치지 않았다** — 토큰 동일 이동 provenance 를 유지한다. baseline `b34fda9` 에도 같은 형태로 존재한다.
