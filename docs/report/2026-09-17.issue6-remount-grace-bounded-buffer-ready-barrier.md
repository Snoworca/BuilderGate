## 2. 실제로 남아 있던 결함 — 게이트가 공허했다

실측으로 확인했다. baseline HEAD 에서 `flushGraceBuffer` 의 snapshot 블록과 held-tail 루프를 **맞바꾸면**(= current server snapshot 이 held tail *뒤에* 적용되는 AC-3 정면 위반):

## 4. 순서 증명 (AC-3)

`grace flush applies the current server snapshot before the held tail and opens the input gate only after the tail drains` 는 모든 핸들러 호출을 배열에 기록하고 **관측된 시퀀스 전체**를 단언한다:

```
['restore-needed', 'snapshot', 'output:tail-a', 'output:tail-b', 'output:tail-c', 'ready']
```

리터럴 시퀀스에 더해 불변식을 따로 단언한다 — 모든 `output:` 인덱스가 `snapshot` 뒤이고 `ready` 앞이다. 최종 버퍼 상태만 보는 단언은 잘못된 순서에서도 통과하므로, 순서 자체를 관측 대상으로 삼는다.

### held prefix 에 대한 정정

처음에 "snapshot 이전에 도착한 held prefix 는 제거된다" 를 단언하는 테스트를 썼고 red 가 났다. 프로덕션이 옳고 그 단언이 틀렸다. restore 중 서버는 새 generation 의 replay tail 을 보내며 그 청크들은 snapshot 프레임을 사이에 두고 걸쳐 있다. **도착 순서로 자르면 출력을 잃는다.** coverage 는 sequence 로 증명되며 그 증명은 하류의 `visibleOutputRecovery`(`authoritative-snapshot-applied` / `output-arrived` 경로, `visible output recovery drops a snapshot-covered late chunk before cap accounting` 가 덮는다)에 있다. grace lane 이 선점해서는 안 된다. 테스트를 프로덕션에 맞춰 통과시킨 것이 아니라, **어느 층의 계약인지**를 다시 판정하고 그 판정을 테스트 주석에 남겼다.

## 5. AC-5 의 세 경합 — 각각의 실패 케이스

이슈는 delayed write callback / dispose / generation 의 셋을 각각 다루라고 요구한다. grace lane 에 대응되는 실패 케이스:

| 경합 | 실패 케이스 (테스트 제목) |
| --- | --- |
| generation supersede | `grace buffer drops held output from a superseded replay generation` — 이전 `replayToken` 의 청크는 버퍼에 들어가지 못한다 |
| authority 교체 | `grace flush reports an authority proof mismatch and withholds the snapshot and ready` — proof 불일치 generation 은 snapshot·ready 를 현재 view 에 전달하지 못한다 |
| 반복 remount(생애 교체) | `a repeated remount cycle does not replay an earlier generation held tail into the new view` — 앞 generation 의 tail 이 다음 flush 에 나타나지 않는다 |

`TerminalView` 측 delayed callback/dispose 경합은 이 lane 의 범위가 아니며 `isCurrentRestoreAttempt` / `terminalDisposedRef` 로 이미 fence 되어 있다(VE-2 가 덮는다). 이 lane 에서 새로 증명한 것은 grace 측 세 축이다.

## 6. 비공허성 증명

게이트가 "이 검사를 만족시키면서 거짓일 수 있는 입력" 을 허용하는지 두 가지 변형으로 확인했다. 두 변형 모두 바이트 동일 복원했다(`diff -q` 확인).

| 변형 | 새 스위트 | 기존 regex 스위트 |
| --- | --- | --- |
| A: `flushGraceBufferedSession` 의 snapshot 블록 ↔ held-tail 루프 교환 | **2 fail / 11** | 60/60 pass |
| B: chunk cap 의 `>` → `>=` (off-by-one) | **1 fail / 11** | 60/60 pass |

두 축이 분리되어 있다: 순서를 위조하면 A 가, 경계를 위조하면 B 가 red 다. 그리고 regex 게이트는 둘 다 잡지 못한다 — 그것이 이 작업의 이유다.
