## 4. 순서 증명 (AC-3)

`grace flush applies the current server snapshot before the held tail and opens the input gate only after the tail drains` 는 모든 핸들러 호출을 배열에 기록하고 **관측된 시퀀스 전체**를 단언한다:

```
['restore-needed', 'snapshot', 'output:tail-a', 'output:tail-b', 'output:tail-c', 'ready']
```

리터럴 시퀀스에 더해 불변식을 따로 단언한다 — 모든 `output:` 인덱스가 `snapshot` 뒤이고 `ready` 앞이다. 최종 버퍼 상태만 보는 단언은 잘못된 순서에서도 통과하므로, 순서 자체를 관측 대상으로 삼는다.

### held prefix 에 대한 정정

처음에 "snapshot 이전에 도착한 held prefix 는 제거된다" 를 단언하는 테스트를 썼고 red 가 났다. 프로덕션이 옳고 그 단언이 틀렸다. restore 중 서버는 새 generation 의 replay tail 을 보내며 그 청크들은 snapshot 프레임을 사이에 두고 걸쳐 있다. **도착 순서로 자르면 출력을 잃는다.** coverage 는 sequence 로 증명되며 그 증명은 하류의 `visibleOutputRecovery`(`authoritative-snapshot-applied` / `output-arrived` 경로, `visible output recovery drops a snapshot-covered late chunk before cap accounting` 가 덮는다)에 있다. grace lane 이 선점해서는 안 된다. 테스트를 프로덕션에 맞춰 통과시킨 것이 아니라, **어느 층의 계약인지**를 다시 판정하고 그 판정을 테스트 주석에 남겼다.

**남은 한계를 명시한다.** 하류 pruning 이 존재한다는 것은 확인했지만(`visibleOutputRecovery` 가 `screenSeq <= snapshotSeq` 로 자른다), grace lane → 하류 pruning 의 **hand-off 자체는 이 스위트에서 end-to-end 로 단언되지 않는다.** 인용한 하류 테스트는 recovery coordinator 를 직접 구동하며 grace lane 을 거치지 않고, 이 스위트의 `output()` 픽스처는 하류가 키로 쓰는 `screenSeq` 를 아예 싣지 않는다. 그 연결은 현재 주석으로만 기술되어 있다. AC-3 의 "snapshot sequence coverage 가 증명된 held prefix 제거" 절을 두 층에 걸쳐 관통 검증하는 것은 이 lane 에서 하지 않았다.

## 5. AC-5 의 세 경합 — 각각의 실패 케이스

이슈는 delayed write callback / dispose / generation 의 셋을 각각 다루라고 요구한다. grace lane 에 대응되는 실패 케이스:

| 경합 | 실패 케이스 (테스트 제목) |
| --- | --- |
| generation supersede | `grace buffer drops held output from a superseded replay generation` — 이전 `replayToken` 의 청크는 버퍼에 들어가지 못한다 |
| authority 교체 | `grace flush reports an authority proof mismatch and withholds the snapshot and ready` — proof 불일치 generation 은 snapshot·ready 를 현재 view 에 전달하지 못한다 |
| 반복 remount(생애 교체) | `a new restore generation purges the previous generation held tail from the same session state` — **하나의 state 객체**를 두 generation 에 걸쳐 유지한다. 프로덕션 `bufferGraceMessage` 가 session 의 map 엔트리를 재사용하므로, state 객체를 두 개 만들면 정작 중요한 in-place purge 경로가 실행되지 않는다 |
| duplicate 판정 축소 | `a re-issued restore with the same repair token but a new replay generation is not treated as a duplicate` — 3-key 판정이 repairToken 단독으로 좁아지면 새 generation 이 duplicate 로 삼켜진다 |
| stale ready token | `a replacement snapshot invalidates the ready token latched for the generation it replaces` — snapshot 교체 후 옛 ready 로 input gate 가 열리지 않는다 |
| unproven authority | `a restore-needed frame with no authority proof is rejected rather than engaging the barrier` — fail-closed 거절 분기 자체 |

`TerminalView` 측 delayed callback/dispose 경합은 이 lane 의 범위가 아니며 `isCurrentRestoreAttempt` / `terminalDisposedRef` 로 이미 fence 되어 있다(VE-2 가 덮는다). 이 lane 에서 새로 증명한 것은 위 여섯 축이다.

## 6. 비공허성 증명

게이트가 "이 검사를 만족시키면서 거짓일 수 있는 입력" 을 허용하는지 여덟 가지 변형으로 확인했다. 모든 변형은 적용 후 바이트 동일 복원했다(`diff -q` 로 확인).

| 변형 | 새 스위트 (16건) | 기존 regex 스위트 |
| --- | --- | --- |
| A: `flushGraceBufferedSession` 의 snapshot 블록 ↔ held-tail 루프 교환 | **2 fail** | 60/60 pass |
| B: `applyGraceBufferedMessage` chunk cap 의 `>` → `>=` (off-by-one) | **1 fail** | 60/60 pass |
| C: new-generation reset 에서 `current.output = []` 제거 | **2 fail** | 60/60 pass |
| D: snapshot 교체 시 `current.ready = undefined` 제거 | **1 fail** | 60/60 pass |
| E: `hasSameRestoreNeededAuthorityProof(msg, msg)` 가드 fail-open | **1 fail** | 60/60 pass |
| F: duplicate 판정을 `repairToken` 단독으로 축소 | **1 fail** | 60/60 pass |
| G: `outputOverflowReason` early-return 제거 | **1 fail** | 60/60 pass |
| H: `reconnectRequired` output 가드 제거 | **1 fail** | 60/60 pass |

축이 분리되어 있다: 순서, 경계, generation 교체, ready 무효화, proof, duplicate 판정, overflow 지속성, terminal 상태가 각각 독립적으로 red 를 낸다. 그리고 regex 게이트는 **여덟 가지 모두** 잡지 못한다 — 그것이 이 작업의 이유다.

C~H 는 독립 리뷰가 지목한 축이다. 최초 스위트는 A·B 만 잡았고, 특히 반복 remount 테스트가 state 객체를 두 개 만들어 프로덕션의 in-place purge 경로를 실행하지 않았다.
