Every JSON store the server publishes under `server/data/` shall be publishable concurrently by more than one process sharing the checkout without any publish failing because of another publish, without any publish moving a document it did not write into place, and without any publish moving a partially written document into place.

Eight writers persist state under `server/data/`. Seven of them publish JSON stores and all seven are in scope. One, the TOTP secret, is not; it is treated at the end of this paragraph block.

Two of the seven already avoid the shared-temp-path defect: `McpControlConfigStore.ts:68` and `WebhookInvocationService.ts:430` name their temp file per instance, `${dataFilePath}.${process.pid}.${Date.now()}.tmp`. The convention already exists in this codebase and is applied to two of eight writers. They are not, however, already compliant. Neither retries its rename (`McpControlConfigStore.ts:74`, `WebhookInvocationService.ts:436` are bare `await fs.rename` calls), so both remain exposed to the destination contention described under "Why retry is still needed" below, which on Windows fails a publish because of another publish. They need the retry and nothing else, and they are covered by this requirement for that reason.

The remaining five JSON stores need both halves of the fix. Four publish with one identical shape — write `dest + '.tmp'`, copy `dest` to `dest + '.bak'`, rename `dest + '.tmp'` onto `dest` — where the temp path is a fixed string derived from the destination and is therefore the same path in every process that opens the same checkout: `CommandPresetService.ts:270-289`, `WorkspaceService.ts:1726-1755`, `TerminalShortcutService.ts:528-552`, `RecoveryOptionService.ts:410-437`. The fifth of these, `AgentLifecycleService.ts:106-113`, has no temp file at all: it writes `agent-command-profiles.json` directly onto the destination, with no rename and no backup, so a reader can observe a half-written document and a process that dies mid-write destroys the store outright. It is the same defect class in a worse form.

The eighth writer is `TOTPService.ts:113`, which writes the encrypted TOTP secret to `data/totp.secret` with a bare `writeFileSync`, no temp file and no rename. It is deliberately **out of scope** here. Its failure mode is not a torn document but divergent credentials — two processes bootstrapping a checkout with no secret each generate one, and the loser keeps an in-memory secret that no longer matches the file — which needs a decision about which process's secret wins and how the other reloads, not just an atomic publish. It is also a credential, so routing it through a temp file raises a separate question about what a stray temp file would expose. It is written once at first setup rather than on every flush, so it does not share the every-bootstrap exposure that motivates this requirement. Reopen it as its own requirement.

Measured on 2026-09-16, node v24.21.0 on Linux/WSL2. Two failures were reproduced, and a third was looked for and found in a different form than first assumed.

**The publish fails.** Two independent processes each performing the `CommandPresetService` publish sequence 300 times against one shared temp path, writing payloads of 200 and 340 bytes: 293 of 600 publishes (48.8%) failed with `ENOENT` on the rename, because the peer's rename had already moved the shared temp file away. Reproduced twice with the same total.

**A publish moves a document it did not write.** This one is deterministic, not statistical. A publish writes the shared temp file; a peer overwrites that same temp file before the first publish reaches its rename; the rename then moves the peer's bytes into place and the first call resolves with no error. Reproduced directly: writer A wrote `A-change` to the temp path, writer B overwrote the temp path with `B-change`, A's rename resolved successfully, and the destination held `B-change`. B's own rename then failed `ENOENT` against a temp file A had already consumed. The caller was told its write succeeded and its change was not on disk.

**A publish moves a partially written document.** Not because a single `fs.writeFile` splits into several `write` calls — for payloads below Node's 512 KiB chunk threshold it does not — but because each writer opens the shared temp path with `O_TRUNC` and writes from offset zero. A shorter document written over a longer one leaves the shorter document's bytes at the head and the longer one's tail beyond them, and a rename then publishes that. Measured with two processes on one temp path, one writing a 423-byte document and one a 60,023-byte document, the publisher renaming after each write: **539 of 4,000 publishes in the first run and 598 of 4,000 in the second moved a file into place that does not parse as JSON** (13.5% and 14.9%). A published sample is 60,023 bytes long, opens `{"writer":"A","pad":"AAAA…` and ends `…BBBB"}`. Instrumenting the probe to test the mechanism rather than only the symptom (`raw/tear3.mjs`, four runs retained), 2,914 of 2,923 torn publishes across those runs were byte-for-byte the short document followed by the tail of the long one, which is exactly the overlay described. The nine that were not are page-aligned or empty partial views of the longer write — observed lengths 0, 4,096, 8,192, 12,288 and 20,480 — so the overlay is the dominant mechanism rather than the only one. Per-run torn counts were 753, 727, 669 and 674 out of 4,000 publishes each. This is a real corruption path and not a theoretical one, and the destination never has to be read mid-write for it to happen — the rename is atomic and still publishes a broken document, because the bytes it moves were broken before it moved them.

The consequence of the first failure is a dead process rather than a logged warning. `index.ts:1028-1042` awaits `initialize()` on the four temp-file stores during bootstrap. `CommandPresetService.initialize()` and `TerminalShortcutService.initialize()` call `flushToDisk()` on every path through them — file loaded, file absent, backup recovered — with no guard. `WorkspaceService.initialize()` and `RecoveryOptionService.initialize()` open a narrower but real window: the first writes on a successful load whenever the sanitize and migration pass changed tab metadata (`WorkspaceService.ts:214-218`, reached through `ensureMcpTabBinding` for any store written by an older build) or the store held no workspace, and the second writes on a successful load when loading produced new diagnostics (`RecoveryOptionService.ts:52-57`). A rejection from any of them propagates to the `catch` at `index.ts:1654-1657`, which logs `[Fatal] Failed to start server:` and calls `process.exit(1)`. Losing the race kills the instance. A dead instance then fails whatever was pointed at it, which on 2026-08-12 was read as unrelated product defects in E2E specs, on ports 2380 and 2402 (GitHub issue #24).

On Windows the same source-side collision also raises `ENOENT` — the losing rename still finds no temp file — but Windows adds a second failure mode the measurements above cannot produce: a rename onto a destination another process holds open is refused with `EPERM`, which is the code GitHub issue #24 reports. `EPERM` is therefore an additional mode on that platform, not a substitution for `ENOENT`, and it is the one that survives giving each writer a private temp name.

The `.bak` copy has the same weakness for the same reason. Two processes running `copyFile` onto one backup path truncate and rewrite it concurrently, and the backup is what `CommandPresetService.recoverFromBackup()` (`:137-152`), `TerminalShortcutService.recoverFromBackup()` (`:182-200`), `RecoveryOptionService.recoverFromBackupOrDefaults()` (`:192-203`) and `WorkspaceService.initialize()` (`:178-195`) read when the primary will not parse. A backup published non-atomically is a recovery path that can itself be unreadable.

Rejected alternative — retry only. It is the cheapest of the three directions the issue lists and it reaches only one of the three failures. Retrying the rename turns the 48.8% `ENOENT` into a slower success, but a publish that moves a peer's bytes — whole or partial — into place raises no error at all, so there is nothing for a retry to observe. Retry is required here for a narrower reason given below, but as a complement to a private temp path, never as a substitute.

Rejected alternative — a cross-process lock file. A dev instance that is killed leaves the lock held, so the design immediately needs liveness detection and a staleness timeout, which is more mechanism than the thing it replaces. It also buys nothing semantically: two instances legitimately hold divergent complete snapshots, so serializing them orders the overwrite without preventing it.

Rejected alternative — a per-instance destination path. This is the direction the issue names as the one that would have avoided the problem, and it is a data-layout change rather than a bug fix: in a deployment the store is meant to be a single source of truth, and splitting it per instance would make two instances of one installation disagree permanently. The paths are in fact separable — `workspaces.json` through `workspace.dataPath` in the config schema (`config.schema.ts:252`, reaching the service at `WorkspaceService.ts:115`), and the other four through a `dataPath` constructor option (`CommandPresetService.ts:14`, `TerminalShortcutService.ts:20`, `RecoveryOptionService.ts:21`, `AgentLifecycleService.ts:79`; `WorkspaceServiceOptions` at `:43-47` has no such field, so that store is separable only through configuration). But no construction site passes an override — `index.ts:1028-1042` for the four temp-file stores and `index.ts:1049` for the agent-profile store — so every process in a checkout resolves the same absolute path, and making separation the fix would mean asking every operator to configure it correctly forever.

Out of scope — the watcher structure. The issue also names the `tsx` watchers in `dev.js` reacting to one source change as a cause. Making the watchers restart less eagerly would narrow the window without closing it, and it would leave the store unsafe for any other pair of processes. A store that cannot be written safely by two processes is the defect; how often two processes happen to write it is not. Reopen separately if watcher restart storms cause harm on their own.

What the correct fix does not do is make concurrent publishes agree. With a private temp name and an atomic rename the outcome across two instances is last-writer-wins over whole documents. That is the right semantics here — each instance owns a complete snapshot and there is nothing to merge — and it is what the existing code already intended. What changes is that a publish either puts its own complete bytes in place or reports failure, and never reports success for a document it did not write.

Why retry is still needed, and how much. A private temp name removes the shared source, but two instances still rename onto the *same destination*, and on Windows that rename is refused with `EPERM` while another process holds the destination open. The publish shall therefore retry a rename that fails with `EPERM`, `EACCES` or `EBUSY` up to four times after the first attempt, waiting 10 ms, 20 ms, 40 ms and 80 ms — five attempts and about 150 ms in total. The budget is fixed here rather than left open because an unspecified budget cannot be tested: an implementation retrying once and one retrying fifty times would both satisfy a criterion that only says "bounded". 150 ms is chosen to cover a peer's brief hold on the destination without adding a visible stall to bootstrap, and it is a starting value open to revision against a Windows measurement, which does not yet exist. The retry shall be selective: an implementation that retried every error would turn a permanent failure such as `ENOSPC` into a delay before the same failure.

REL-BGSTAB-020 is not superseded. It serializes `flushToDisk` behind a promise chain so two flushes inside one process cannot overlap, and it remains correct and necessary for that. A promise chain is per-process state; it cannot observe a second process, and a shared temp path defeats it across the process boundary. This requirement extends it outward and must not weaken it: the in-process chain stays.

Platform honesty. The `EPERM` this issue reports is a Windows rename semantic, and every measurement above was taken on Linux/WSL2, which has no equivalent of it: a rename there is not refused because a peer holds the destination open, so the destination-contention failure could not be produced at all. The source-side collision, which does reproduce here as `ENOENT`, is a different failure and is not a stand-in for it. The retry branch must therefore be verified by injecting the transient codes at the filesystem boundary rather than by a native reproduction. That is weaker evidence, and a Windows run remains the stronger check.
