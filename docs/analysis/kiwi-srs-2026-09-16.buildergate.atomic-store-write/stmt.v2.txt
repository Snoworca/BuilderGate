Every JSON store the server publishes under `server/data/` shall be publishable concurrently by more than one process sharing the checkout without any publish failing because of another publish, and without any publish reporting success for bytes it did not write.

Five services persist a store under `server/data/`. Four publish it with one identical shape — write `dest + '.tmp'`, copy `dest` to `dest + '.bak'`, rename `dest + '.tmp'` onto `dest` — where the temp path is a fixed string derived from the destination and is therefore the same path in every process that opens the same checkout: `CommandPresetService.ts:270-289`, `WorkspaceService.ts:1726-1753`, `TerminalShortcutService.ts:528-552`, `RecoveryOptionService.ts:410-437`. The fifth, `AgentLifecycleService.ts:106-113`, has no temp file at all: it writes `agent-command-profiles.json` directly onto the destination, with no rename and no backup, so a reader can observe a half-written document and a process that dies mid-write destroys the store outright. It is the same defect class in a worse form and this requirement covers it.

Two other services already avoid the collision by naming the temp file per instance — `McpControlConfigStore.ts:68` and `WebhookInvocationService.ts:430` both use `${dataFilePath}.${process.pid}.${Date.now()}.tmp`. The convention already exists in this codebase and is applied to two of seven writers.

Measured on 2026-09-16, node v24.21.0 on Linux/WSL2, with two independent processes each performing the `CommandPresetService` publish sequence 300 times against one shared temp path and writing payloads of different lengths (200 and 340 bytes):

- 293 of 600 publishes (48.8%) failed with `ENOENT` on the rename, because the peer's rename had already moved the shared temp file away.
- Of the publishes that did resolve, most put a payload on disk that the resolving call had not written.

The second number is the one that decides the design, and its mechanism is deterministic rather than statistical. A publish writes the shared temp file, a peer overwrites that same temp file before the first publish reaches its rename, and the rename then moves the peer's bytes into place. The first call resolves with no error. Its own change is gone and its caller has been told the write succeeded. Reproduced directly: writer A wrote `A-change` to the temp path, writer B overwrote the temp path with `B-change`, A's rename resolved successfully, and the destination held `B-change`. B's own rename then failed `ENOENT` against a temp file A had already consumed.

A claim that was checked and does not hold: that the two writers can interleave *within* the temp file and leave bytes from both. On this platform they do not. 400 rounds of two concurrent `fs.writeFile` calls on one path with mismatched payload lengths — 50 KB against 900 KB, the larger deliberately above Node's 512 KiB chunking threshold — produced zero torn files; every observation was one payload or the other, whole. The corruption hazard here is therefore not a torn document but a lost update reported as success, and this requirement is written against the failure that exists rather than the one that sounded likely.

The consequence of the first failure is a dead process rather than a logged warning. `index.ts:1028-1042` awaits `initialize()` on the four temp-file stores during bootstrap, and `CommandPresetService.initialize()` and `TerminalShortcutService.initialize()` call `flushToDisk()` on every path through them — file loaded, file absent, backup recovered — with no guard. (`WorkspaceService.initialize()` does not write on a successful load, and `RecoveryOptionService.initialize()` writes on that path only when loading produced new diagnostics, so those two open a narrower window.) A rejection from either unguarded flush propagates to the `catch` at `index.ts:1654-1657`, which logs `[Fatal] Failed to start server:` and calls `process.exit(1)`. Every start therefore opens the window, and losing the race kills the instance. A dead instance then fails whatever was pointed at it, which on 2026-08-12 was read as unrelated product defects in E2E specs, on ports 2380 and 2402 (GitHub issue #24).

On Windows the losing rename raises `EPERM` rather than `ENOENT`, because a rename onto a destination another process holds open is refused there. The reported symptom differs; the collision does not.

The `.bak` copy has a related weakness. Two processes running `copyFile` onto one backup path truncate and rewrite it concurrently, and the backup is what `CommandPresetService.recoverFromBackup()` (`:137-152`), `TerminalShortcutService` (`:182-200`), `RecoveryOptionService.recoverFromBackupOrDefaults()` (`:192-203`) and `WorkspaceService.initialize()` (`:178-195`) read when the primary will not parse. A backup published non-atomically is a recovery path that can itself be unreadable.

Rejected alternative — retry only. It is the cheapest of the three directions the issue lists and it cannot reach the failure that matters. Retrying the rename turns the 48.8% `ENOENT` into a slower success, but a publish that moves a peer's bytes into place raises no error at all, so there is nothing for a retry to observe. Retry is required here for a different reason — see below — but as a complement to a private temp path, never as a substitute.

Rejected alternative — a cross-process lock file. A dev instance that is killed leaves the lock held, so the design immediately needs liveness detection and a staleness timeout, which is more mechanism than the thing it replaces. It also buys nothing semantically: two instances legitimately hold divergent complete snapshots, so serializing them orders the overwrite without preventing it.

Rejected alternative — a per-instance destination path. This is the direction the issue names as the one that would have avoided the problem, and it is a data-layout change rather than a bug fix: in a deployment the store is meant to be a single source of truth, and splitting it per instance would make two instances of one installation disagree permanently. Four of the five services do accept a `dataPath` constructor option (`CommandPresetService.ts:14`, `TerminalShortcutService.ts:20`, `RecoveryOptionService.ts:21`, `AgentLifecycleService.ts:79`); `WorkspaceService` does not — `WorkspaceServiceOptions` (`:43-47`) has no such field and the path comes from the config module. In any case `index.ts:1028-1042` passes no override, so every process in a checkout resolves the same absolute path.

Out of scope — the watcher structure. The issue also names the `tsx` watchers in `dev.js` reacting to one source change as a cause. Making the watchers restart less eagerly would narrow the window without closing it, and it would leave the store unsafe for any other pair of processes. A store that cannot be written safely by two processes is the defect; how often two processes happen to write it is not. Reopen separately if watcher restart storms cause harm on their own.

What the correct fix does not do is make concurrent publishes agree. With a private temp name and an atomic rename the outcome across two instances is last-writer-wins over whole documents. That is the right semantics here — each instance owns a complete snapshot and there is nothing to merge — and it is what the existing code already intended. What changes is that a publish either puts its own bytes in place or reports failure, and never reports success for someone else's.

Why retry is still needed. A private temp name removes the shared source, but two instances still rename onto the *same destination*, and on Windows that rename is refused with `EPERM` while another process holds the destination open. A bounded retry over the transient codes covers that residual window. It must be bounded and it must be selective: an implementation that retried every error would turn a genuine, permanent failure such as `ENOSPC` into a delay before the same failure.

REL-BGSTAB-020 is not superseded. It serializes `flushToDisk` behind a promise chain so two flushes inside one process cannot overlap, and it remains correct and necessary for that. A promise chain is per-process state; it cannot observe a second process, and a shared temp path defeats it across the process boundary. This requirement extends it outward and must not weaken it: the in-process chain stays.

Platform honesty. The `EPERM` this issue reports is a Windows rename semantic, and the measurements above were taken on Linux/WSL2, where the same collision surfaces as `ENOENT`. The retry branch must therefore be verified by injecting the transient codes at the filesystem boundary rather than by a native reproduction. That is weaker evidence, and a Windows run remains the stronger check.
