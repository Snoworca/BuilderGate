Every JSON store the server publishes under `server/data/` shall be publishable concurrently by more than one process sharing the checkout without any publish failing because of another publish, and without any reader ever observing a partially written document — neither in the store itself nor in the backup it recovers from.

Four services publish a store with one identical shape: write `dest + '.tmp'`, copy `dest` to `dest + '.bak'`, rename `dest + '.tmp'` onto `dest`. The temp path is a fixed string derived from the destination, so it is the same path in every process that opens the same checkout — `CommandPresetService.ts:270-289`, `WorkspaceService.ts:1726-1753`, `TerminalShortcutService.ts:528-552`, `RecoveryOptionService.ts:410-437`. Two other services in the same codebase already avoid this by naming the temp file per instance — `McpControlConfigStore.ts:68` and `WebhookInvocationService.ts:430` both use `${dataFilePath}.${process.pid}.${Date.now()}.tmp`. The convention already exists in the repo; it is applied to two of six writers.

Three distinct failures follow from the shared temp path, and they are not the same defect wearing three names.

First, the publish fails. The first rename moves the shared temp file away and the second finds no source. On Linux that is `ENOENT`; on Windows, where a rename onto a destination another process holds open raises `EPERM`, it is the `EPERM` reported in GitHub issue #24, which killed two dev instances outright on 2026-08-12 (ports 2380 and 2402).

Second, the process dies rather than logging. `index.ts:1028-1041` awaits `initialize()` on all four of these stores during bootstrap, and every bootstrap path inside `initialize()` — the file loaded, the file absent, the backup recovered — calls `flushToDisk()` unguarded. The rejection propagates to the `catch` at `index.ts:1654-1657`, which logs `[Fatal] Failed to start server:` and calls `process.exit(1)`. The race window is therefore opened by every start, not only by an error path, and the consequence is a dead instance rather than a warning. A dead instance then fails whatever else was pointed at it, which on 2026-08-12 was read as unrelated product defects in E2E specs.

Third — and this one survives fixing the first two by retry alone — two processes writing the same temp path interleave. `fs.writeFile` opens with `O_TRUNC` and issues several `write` calls for a payload of this size, so two writers on one path can leave that file holding bytes from both. A later rename then publishes it. The store the next reader parses is not a document either writer wrote.

The `.bak` copy has the same defect for the same reason. Two processes running `copyFile` onto one backup path truncate and rewrite it concurrently, and the backup is precisely what `recoverFromBackup()` reads when the primary is unreadable — a torn backup removes the recovery of a recovery.

Rejected alternative — retry only. It is the cheapest of the three directions the issue lists and it addresses only the first failure. It leaves the interleaved temp file intact as a corruption path, and it converts a crash into a silent last-writer-wins without making the published bytes a whole document. Retry is required here, but as a complement to unique naming, never as a substitute for it.

Rejected alternative — a cross-process lock file. A dev instance that is killed leaves the lock held, so the design immediately needs liveness detection and a staleness timeout, which is a larger mechanism than the one it replaces. It also buys nothing semantically: two instances legitimately hold divergent complete snapshots of the store, so serializing them orders the overwrite without preventing it. Reopen only for a design in which the two processes have some state to merge.

Rejected alternative — a per-instance destination path, as `workspace.dataPath` allows. This is the direction the issue names as the one that would have avoided the problem, and it is a data-layout change rather than a bug fix: in a real deployment the store is meant to be one source of truth, and splitting it per instance would make two instances of the same installation disagree permanently. The four services do accept a `dataPath` option, but `index.ts:1028-1041` passes none, so in practice every process in a checkout resolves the same absolute path.

What the correct fix does not do is make concurrent publishes agree. With a private temp name and an atomic rename the outcome across two instances is last-writer-wins over whole documents. That is the right semantics here — each instance owns a complete in-memory snapshot and there is nothing to merge — and it is what the existing code already intended. What changes is that the loser no longer crashes and the winner always publishes a document that one writer actually produced.

REL-BGSTAB-020 is not superseded by this. It serializes `flushToDisk` behind a promise chain so that two flushes inside one process cannot overlap, and it remains correct and necessary for that. A promise chain is per-process state; it cannot observe a second process, and the same fixed temp path defeats it across the process boundary. This requirement extends it outward and must not weaken it: the in-process chain stays.

Platform honesty. The reported `EPERM` is a Windows rename semantic, and the implementation and verification of this requirement were carried out on Linux/WSL2, where the same collision surfaces as `ENOENT` on the losing rename and as interleaved temp content. The retry branch is therefore exercised by injecting the transient error codes at the filesystem boundary, not by a native Windows `EPERM`. That is weaker evidence than a native reproduction and is recorded here as such. A Windows run remains the stronger check and has not been performed.
