## 2. The three failures had three different causes, stacked

The scanner throws on the first missing signature, so only one cause was visible at a time. Each
fix exposed the next. This is why the count stayed at three while the reason changed.

| # | Cause | Pre-existing at `bc94bea`? |
| --- | --- | --- |
| A | `1ae3787` (REL-BGSTAB-009) moved the grace lane from `WebSocketProvider#bufferGraceMessage` into `terminalGraceBuffer#applyGraceBufferedMessage`; the consumer catalog still named the old owner | **no** — introduced inside this epic |
| B | `ConfigFileRepository.ts`'s classification `accessEvidenceSha256` pin went stale when `resourceLimits.telemetry.sampleIntervalMs` was retired, so the file lost its exemption and its `@resource-limits-root.[dynamic]` render access surfaced as an unregistered call site | yes |

| D | `TerminalResourcePolicyObservations.ts`'s compact decision list never gained `resourceLimits.terminal.checkpointMaxBytes` when REL-BGSTAB-023 registered it | yes |

Cause A matters beyond itself. Both prior records — VE-11 on `REL-BGSTAB-001`, and this
Requirement's 2026-09-16 Change Note — classify these three test names as pre-existing and
out of scope. Measured ancestry: `1ae3787` is **not** an ancestor of `a6c7edc` (VE-11's HEAD) or of
`8f8f934` (the Change Note's baseline), and **is** an ancestor of `bc94bea`. A regression introduced
after those measurements was therefore sheltering under a "pre-existing" label inherited from trees
in which it did not exist. The label was correct for causes B, C and D and wrong for A, and nothing
in the failing output distinguished them.

### 3.1 A fifth cause, found by the review round rather than by the audit

The audit stopped at four causes. Hardening the fixture *insertion* to an exact hit count while
leaving the fixture *replacement* at `available >= replacements` concealed a fifth: the
`split-owner-does-not-share-evidence` fixture declares `replaceCount: 2` against
`limits.serverBufferedHighWaterBytes` in `WsRouter.ts`, intending one occurrence per catalog owner.
That file now holds three occurrences, two of them inside `WsRouter.sendTransportMessage` and one
inside `WsRouter.flushTransportQueue`. `String.replace` takes the first match each iteration, so both
replacements landed in the first owner and `flushTransportQueue` was never mutated — while the
fixture stayed green, because the discovery still threw on the first owner's missing signature.

The three-occurrence state is pre-existing. The concealment was not: this work rewrote that exact
assertion and picked the predicate that keeps it invisible. It is now `assert.equal(available,
replacements)` with `replaceCount: 3`, which restores the fixture to mutating every owner.

**Residual, stated because the fixture's name claims more than it now proves:** mutating every
occurrence shows that both owners must carry evidence. It does not show that one owner's evidence
cannot be counted for the other, which is what "split owner does not share evidence" asserts.
Proving that needs occurrence-targeted mutation, which this harness cannot express.

### 3.2 Five fixtures shared one disjunction; three were load-bearing and two were not

The `manifestDrift` fixtures accepted `missing-tuple` OR `orphan-tuple` OR `source-hash-mismatch`.
Every mutated file is in `evidenceSourcePaths`, so `source-hash-mismatch` fires for any byte-level
change at all — a stray space satisfies it — and the disjunction therefore could not distinguish a
fixture that discriminates its decoy from one that does not, reporting both as the same pass.

Measured rather than assumed, by printing each fixture's actual error codes:

Measured codes, now emitted by the suite itself on every run so the table is re-derivable rather
than transcribed — see `raw/R4-driftcodes.20260917T160835Z.log`:

| Fixture | error codes | discriminates its decoy? |
| --- | --- | --- |
| `object-option-noop-callee-decoy` | `source-set-mismatch`, `source-hash-mismatch`, 3× `orphan-tuple`, 3× `missing-tuple` | yes |
| `call-input-noop-callee-decoy` | `source-set-mismatch`, `source-hash-mismatch`, `orphan-tuple`, `missing-tuple` | yes |
| `control-guard-wrong-return-decoy` | `source-set-mismatch`, `source-hash-mismatch`, `orphan-tuple`, `missing-tuple` | yes |
| `unchanged-guard-after-constant-return` | `source-set-mismatch`, `source-hash-mismatch` | **no** |
| `unchanged-guard-after-try-finally-return` | `source-set-mismatch`, `source-hash-mismatch` | **no** |

An earlier draft of this table wrote "source only" for the last two rows and had no preserved log at
all — the one measurement in this work that overrode an external review finding was also the one
with no artifact behind it.

The review round that raised this said all five passed vacuously; the measurement says three of them
are genuinely load-bearing, so that claim was too strong and is corrected here rather than adopted.
The two that are not match what PH-001 declared about them — inserting `if (true) return` ahead of an
unchanged guard is caught by the coarse source seal, not by the AST losing the tuple.

Each fixture now declares `driftMechanism`, and the assertion holds it to that declaration: `tuple`
fixtures must produce tuple drift, `seal-only` fixtures must produce a source hash mismatch **and no
tuple drift**, so that if the AST ever learns to see one of those decoys the fixture goes red and
gets promoted instead of staying quietly in the weaker class.

**The split itself is pinned — 5 fixtures, 3 `tuple`, 2 `seal-only` — because nothing else pinned
it.** A per-fixture declaration that the assertion merely honours makes the cheapest green for a
future "declared tuple drift, but the decoy changed no tuple" red a one-word demotion to
`seal-only`. That red is exactly the AST regression AC-6 exists to catch, and that demotion already
happened once, here, in `raw/R3-policy.20260917T154833Z.log`. With the counts pinned it cannot happen
again without editing a number and arguing for it. Declaration is also asserted at runtime, not only
by `tsc`: `npx tsx --test` strips types, and that is the command this suite is actually run with.

**And the seal-only label is now measured rather than asserted.** Each seal-only fixture is
additionally run with an inert comment in place of its decoy, in a separate tree, and the two error
sets must be identical — which is what "this fixture cannot tell its decoy from whitespace" means, as
a check rather than a sentence. If a decoy ever starts to matter, that equality breaks and the
fixture is promoted.

## 4. AC-1 is the Class B instance

AC-1's text requires the manifest to name each key's real consumer path. Its only condition on the file's content was
`existsSync`, which is true of the correct state *and* of the defect: the file still exists after
the consuming expression leaves it. AC-6's AST scan was the only thing that could see the drift.

AC-1 now additionally asserts that each entry's `evidenceSignature` — the consuming expression
itself — occurs in the file the manifest names, and asserts that the number of entries it checked
equals the number of entries in the manifest, so the loop cannot pass while examining a subset or
nothing at all.

Falsification, run and recorded: restoring `consumerPath` to `frontend/src/contexts/WebSocketContext.tsx`
for the four grace tuples reddens AC-1, and the failing assertion is the new one, by its own
message — `manifest names frontend/src/contexts/WebSocketContext.tsx#applyGraceBufferedMessage as
the consumer, but its evidence signature ... does not occur in that file`
(`raw/ac1-mutation-M1.20260917T144451Z.log`). The manifest was restored byte-identically afterwards.
This reaches the **specific** layer: the mutation reddens AC-1 *through AC-1's own assertion*.

What this check does **not** establish, stated because a textual hit reads like more than it is: it
does not show the expression is owned by the named symbol, is reachable, or is anything but a
comment or an import. AC-6 carries ownership and liveness. This is a second independent condition on
the same claim, not a replacement. In particular it would **not** have caught cause A had the
catalog named the symbol's leaf identifier instead of the expression, because `bufferGraceMessage`
still exists in `WebSocketContext.tsx` — only its body left.

### The classification pin was never valid, and the re-pin grants an exemption the file never held

An earlier draft of this record said the pin's movement was "unexplained" and offered a candidate
cause. **Both were wrong, and "unexplained" meant "unmeasured".** The measurement is cheap: the
scanner's code (`discoverAstResourceAccesses`, `hashAstResourceAccessEvidence`) is unchanged from
`5918146` to HEAD, so the pin can simply be recomputed against historical blobs by staging a root
and using the tool's own `pending` sentinel. Doing that:

| `ConfigFileRepository.ts` blob | computed pin |
| --- | --- |
| `1f76132` (= `5918146^`) | `b988b5e4f820…` |
| `5918146` — the commit that *recorded* `99ca442c…` | `633123e7ef05…` |
| `ed03769` — retires `resourceLimits.telemetry.sampleIntervalMs` | `9c7bd117e083…` |
| `bc94bea` = HEAD | `d5ee2b5e94dd…` |

`99ca442c…` is **not** any of them. It was never this scanner's output for this file, so the pin was
invalid at the commit that wrote it rather than going stale later. Three corrections follow:

1. **Cause (B) above is wrong as stated.** The pin did not "go stale when `sampleIntervalMs` was
   retired" — at that commit the correct value was `9c7bd117…`, and the pin was already wrong one
   commit earlier. The lapsed exemption is real; the mechanism named for it was not.
2. **The candidate cause was refuted, not merely unproven.** `5918146^` contains no
   `TerminalResourcePolicyInventory.ts` and no such pin in `TerminalResourcePolicy.ts`, so nothing
   was carried across the split.
3. **The re-pin widens rather than restores.** `d5ee2b5e…` was already the correct value at
   `bc94bea` — unsurprising in hindsight, since this work never touched `ConfigFileRepository.ts`, so
   its hash could not have moved. `exactlyClassifiedPaths` admits a path only on hash equality, so
   under `99ca442c…` this file was **never exempt** from the unregistered-call-site scan. The re-pin
   therefore grants an exemption the file has never held. That is precisely the operation the new
   `--accept-classification-change` gate exists to make deliberate, and it should be justified by
   what the exemption covers, not by a delta.

**What the exemption actually covers, measured.** With the stale pin in place the scan reports
exactly one residual for this file: `{ path: 'server/src/services/ConfigFileRepository.ts', symbol:
'@resource-limits-root.[dynamic]' }`. Those are the two `resourceLimits[sectionName]` element
accesses in the JSON5 render helpers, unchanged since wave0 `1f76132`, in a file classified
`persistence-boundary` — it writes configuration and applies no terminal runtime decision. That is
the whole of what the exemption suppresses, and it is the correct basis for granting it.

**Reported, not resolved:** that the pin was invalid from birth is a pre-existing defect in
`5918146`, separate from this issue.
