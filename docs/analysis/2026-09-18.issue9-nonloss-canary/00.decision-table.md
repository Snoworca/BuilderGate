## 4. The watcher-probe failure — characterised by a control, not guessed

**An earlier draft of this section said the failures occurred only when the focused command was
spawned as a child of the guard. That was wrong**, and it is corrected here rather than quietly
replaced: the failure later reproduced in a direct invocation with no guard involved
(`raw/R49-server-focused-standalone-r5.*.log`).

A control isolates the actual condition. All three of these run the same tests:

| run | form | result |
|---|---|---|
| `raw/R52-focused-serialised-r5.*.log` | the identical four files with `--test-concurrency=1` | **106/106 green** |
| `raw/R50-canary-only-{1,2,3}.*.log` | `TerminalResourcePolicyCanary.test.ts` alone, three times | **26/26 green each** |
| the ordinary concurrent four-file run | as the guard invokes it | fails intermittently |

So the condition is **concurrent execution of the four-file focused command**, not guard spawning
and not any one test.

Tally over the committed logs. The reds are derived by grep; the denominator needs a stated rule,
because a guard run that aborts before it spawns the focused command is not an execution and the
guard prints nothing from a child that succeeded.

**Classification rule for the denominator.** A log counts as one execution of the four-file
focused command if any of these hold: it contains a `"serverFocused"` JSON summary; it contains a
TAP `ℹ tests 106`; it contains `total: 106` inside an artifact diff; or it is a guard/probe run
whose first failure occurs at or after `summarizeFocused`, since in the guard both `runCommand`
calls complete before either summary is taken.

**This denominator is a live count and must be read scoped to a commit.** Every later
re-verification run of the guard adds another qualifying log, so any figure written into an
immutable record here is stale the moment the next run happens — which is exactly what occurred:
a figure of 26 was published and the three re-verification runs committed alongside it took the
same rule to 29. Recorded properly, therefore:

**At commit `072ccf2`, the rule yields 29 executions — 28 concurrent and 1 serialised — with 7
red, all of them concurrent.** The reds are the stable part; the denominator grows with every
verification run and is not a property of the work.

Two classification notes a reader will need:

- `raw/P1-VE3-*.log` does **not** count. It aborts at the unregistered-test-source assertion,
  which at the guard revision then in force sits three statements before
  `const serverRun = runCommand(focusedCommands.server)`, so neither command was spawned.
- `raw/P1-probe-registration-only.*.log` **does** count, and only the fourth clause admits it. Its
  first failure is `focused TAP did not pass registered test: TerminalContainer never ACKs …` — a
  **frontend** lineage name — so the server command had already run and summarised. Note the
  limit of that inference honestly: the probe was a private modified copy of the guard that was
  deleted after use and never committed, so the statement ordering is established from the guard's
  source rather than from the probe's. A review round proposed dropping this log and naming
  `P1-VE3` as the miscount instead; both halves of that were checked against the bytes and the
  recount was declined.

```
cd docs/analysis/2026-09-18.issue9-nonloss-canary/raw
grep -lF "same-path watcher probe must observe a fixture CWD file update before cleanup" *.log
```

All seven reds are the identical assertion, all in
`server/src/services/TerminalResourcePolicyCanary.test.ts`, which this work does not touch, and
they fall under **four different test names**:


- `PERF-BGSTAB-010 gated real-session fixture releases resources after an assertion failure`
- `PERF-BGSTAB-010 gated real-session PTY chain settles within the fixture bound after overflow cleanup`
- `PERF-BGSTAB-010 gated real-session fixture drains a held write before public cleanup`
- `PERF-BGSTAB-010 emergency cleanup preserves a public finalizer error while releasing held callbacks`

Four tests failing on one assertion, with a green serialised control, is evidence about that
fixture's probe under concurrency rather than about any of the four tests. It is a pre-existing
defect in a file this work does not own, reported as such rather than classified as a flake.

## 5. Mutation coverage, and a contaminated column that would have read clean

The battery is scripted, asserts its own substitution count per mutation, and verifies the edit
landed before running (`raw/MUT-*.log`, `raw/MUT3-*.log`, `raw/MUT3B-*.log`).

**Contamination found and discounted rather than reported as coverage.** Every mutation changes
`TerminalResourcePolicyInventory.ts`, and the suite's manifest-freshness assertion reads that
file's sha256, so the production contract row fails under *every* mutation regardless of what the
mutation does. That column carries no information and must be discounted.

Discounting it, the final battery over the reordered function is 10 mutations including **two
reorderings**, which one-at-a-time statement deletion cannot produce. Nine were caught by the test
named for them. **One survived**: disabling the `duplicate-reservation` `continue` left the suite
green, so the documented deferral behaviour was an unverified defensive statement. The raw failure
count would have read 10 of 10. A fixture pinning the deferral was added and the mutation
**re-measured** as caught by the test named for it (`raw/MUT3B-M10-recheck.*.log`) — the
implementer's reasoning about the kill was not accepted in place of the measurement.

### What this method cannot produce

- Reordering beyond the two encoded above.
- An argument swapped between `catalogConsumerIds` and `manifestConsumerIds` at a call site.
- Any defect in `TerminalResourcePolicyCanary.ts` or the WS and frontend consumers, which are not
  swept at all and rest on reading plus the existing focused suites.

## 8. What this work did not establish

- No browser verification and no E2E. Nothing was served on 2222.
- No enforcement was promoted and no stable contract registered, so the canary remains inert in
  production by construction: the runtime registry reports 0 stable profiles on both server and
  frontend, and the activation gate returns `{eligible: false, reason: 'candidate-unavailable'}`.
- No Settings UI, stored shape, public runtime payload or product default changed.
- The AC-7 guard is **reachable by someone who types the command, not enforced**: nothing invokes
  it at build, lint, hook or CI time, and this repository runs no tests in CI. Those are different
  claims and only the first is earned.
- No process was started or stopped and TCP 2001/2002 were untouched — a negative claim this
  bundle cannot itself reproduce.
