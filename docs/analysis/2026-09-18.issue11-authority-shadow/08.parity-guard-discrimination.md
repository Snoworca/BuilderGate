# Issue #11 — making `retained-shadow-parity` tell addition from substitution

Orchestrator ruling, 2026-09-18: the guard's conflation of *addition* with
*substitution* is **a defect in the guard**, not a fact about this tree. 0 lost is directly
measurable and §2 measured it. Re-sealing 57 → 80 would have bought a green and left the
guard unable to tell the two apart, which the standing brief's rule about loosening makes
the weaker outcome.

## 1. First the question that decides where this goes — measured, not asserted

**Is `retained-shadow-parity` a named verification for an AC this lane owns?**

`grep -rn "retained-shadow-parity" docs/spec/` returns three hits, two of which are
evidence rows:

| Requirement | Row | Reference | Covers |
|---|---|---|---|
| `REL-BGSTAB-011` | **VE-4** | `…/retained-shadow-parity.json` | **AC-1 … AC-9** |
| `REL-BGSTAB-007` | **VE-6** | `…/retained-shadow-parity.json` | AC-2, AC-3, AC-6, AC-9, AC-10, AC-11, AC-12 |

**Yes.** `REL-BGSTAB-011` VE-4 covers AC-3 and AC-4 — precisely the two ACs this lane owns
through VE-8. So under the ruling it must discriminate before those can close, and the fix
is the discrimination.

**One distinction the rows make and the redness hid.** Both VE rows name the **JSON
artifact**, not the `.test.mjs` script that produces it. The artifact in the tree matched
its seal (§1, row 6); the script that regenerates it was red. So the named verification was
a **committed snapshot that could no longer be reproduced** — green-looking bytes behind a
guard that could not run.

## 2. What was wrong, precisely

`assertExactFocusedTestIdentity` asserted `deepEqual(actual, expected)`. That single
predicate is red for three different reasons:

1. a pinned test was **deleted**;
2. a pinned test was **substituted** — same count, different name, the case the guard exists
   for;
3. a new test was **added**.

Only (1) and (2) are hazards. (3) is the normal consequence of any later lane adding a test
to one of the four pinned sources, and it is structurally benign because *nothing was lost*
is directly measurable: it is `missing.length === 0`.

The caller compounded it: `assert.equal(focusedIdentity.sha256, expectedFocusedTestNamesSha256)`
compared the pin against the **executed** set, so the same growth failed twice.

And one layer down, `thresholds.focused.exactTests: 57` compared `focused.total` for exact
equality — the same conflation in the activation gate.

## 3. The change

- **`assertExactFocusedTestIdentity`** now asserts that every pinned name still executes
  (`missing` must be empty) and *records* additions instead of failing on them. Deletion and
  substitution both remove a pinned name, so both still fail here.
- It asserts its **own enumeration is non-empty** before asserting the property — `every
  pinned name is present` is vacuously true of an empty allowlist.
- **The call site** now pins the **allowlist's** hash rather than the executed set's.
- **`thresholds.focused.exactTests` → `minimumTests`**, compared with `<` instead of `!==`.

**`thresholds.coverage.exactAxes: 42` was deliberately left exact.** The axis set is
authored inside the script as a closed literal list; it is not derived from the tree and
cannot grow behind anyone's back. Exact is the correct contract there, and the asymmetry is
recorded in the code so the next reader does not "fix" it.

## 4. Loosening a guard obliges re-running the evasions it was written to catch

| Evasion | Injection | Result | Which assertion fired |
|---|---|---|---|
| **E1** | disable a pinned test with `test.skip` | **caught**, exit 1 | `summarizeFocused` pass-count reconciliation (`81 !== 82`) — a pre-existing arm, not the new predicate |
| **E2** | rename a pinned test in place (substitution, same count) | **caught**, exit 1 | **the new predicate**, naming the lost test: `focused test identity regression — 1 pinned test(s) no longer execute` |
| **E3** | swap an entry in the allowlist so the tree agrees with the tamper | **caught**, exit 1 | `focused test allowlist hash changed without an explicit evidence contract update` |
| **E4** | pure addition (the real tree, 82 tests) | **passes**, exit 0 | — |

Two honest notes about this table.

**E2's first attempt did not exercise the new predicate and I nearly recorded it as if it
had.** Renaming `router destroy unregisters retained views before terminating sockets`
failed at `extractNamedTestBody` — the coverage registry binds that name to a source body,
so the rename broke the binding before the identity check ran. A failure for a different
reason does not validate a predicate, so the evasion was redone against a pinned test with
no registry binding, and *then* the new assertion fired and named the lost test.

**E3 was already caught before this change, and the code comment initially overclaimed
otherwise.** `runEvidenceToolSelfTests` already asserted
`canonicalSha256(expectedFocusedTestNames) === expectedFocusedTestNamesSha256`. Moving the
call-site assertion onto the allowlist hash **does not add protection**; it removes the
false red on growth while leaving the pin meaningful. The comment was corrected to say so
before commit.

The script's own self-tests were extended to cover all four cases as unit-level controls, so
the discrimination is guarded by the script itself and not only by this one-off run.

## 5. Result, and the reason the gate is closed

`node tools/wave3/retained-shadow-parity.test.mjs` → **exit 0**:

```
{"focused":{"total":82,"passed":82,"failed":0},"coverageAxes":42,
 "activationGate":{"eligible":false,"reason":"no-local-cache-retained-authority-unproven"},
 "verdict":"PASS_FAIL_CLOSED"}
```

The gate is still **closed**, and it is closed for the **intended** reason —
`no-local-cache-retained-authority-unproven` — rather than `focused-test-threshold-failed`.
A gate closed for the wrong reason is a coincidence, not a closed gate; the script asserts
its own reason, and that assertion is what surfaced the threshold conflation in §2's third
paragraph.

82 = the 57 pinned + 23 from earlier lanes + **2 added by this lane** (VE-8's named-owner
guards).

## 6. The artifact hash moved. Naming the inputs that moved, and why.

| | |
|---|---|
| sealed & previously committed | `9914e22418e315184ef7cdc315b95b57d693efbe6ad6f84da144ac59a248e265` |
| regenerated at this HEAD | `b68df22c4400363362a80494c95bba8348522aee38dc1431e95b76185002b772` |

A moved artifact hash is what a functioning seal looks like **and** what a silent
re-blessing looks like. Three distinct causes, separated:

1. **The run grew.** `total`/`passed` 57 → 82, and `passedTestNamesSha256`
   `1e7da1ab…` → `4c696286…`. **`expectedTestNamesSha256` is unchanged at `1e7da1ab…`** — it
   appears in the diff only because a trailing comma moved when two fields were appended
   after it. The pin did not move.
2. **Two new recorded fields**, `pinnedTestNamesMissing: []` and `unpinnedTestNamesAdded`,
   plus `exactTests` → `minimumTests`.
3. **The artifact caught up to this tree.** Sixteen per-file source hashes changed. Attributed
   against `git diff --name-only` rather than from memory: **2 were touched by this lane**
   (`docs/spec/30.buildergate-stability.srs.md` via VE-8, and
   `server/src/services/RetainedTerminalAuthority.test.ts`), and **14 were not** — including
   `SessionManager.ts`, `WsRouter.ts`, `headlessTerminal.ts`, `WsRouterCheckpointProtocol.test.ts`
   and the four config files, every one of which this lane restored byte-identically.

Cause 3 is the same measurement as §1 seen from the other side: the committed artifact was
sealed against the **Wave-3 tree**, so regenerating it here re-hashed inputs this lane never
touched. That is not a re-blessing — it is the artifact ceasing to describe a tree that no
longer exists.

**What this does not do.** It does not make the PH-004 result claims true here, and it does
not promote anything. The gate's verdict and reason are unchanged.

## 7. A downstream consumer pins this artifact — found by searching for the content, not the name

`tools/wave3/authority-promotion-evidence.test.mjs:31` hard-pins the parity artifact:

```js
const retainedShadowBaselineExpectedSha256 =
  '9914e22418e315184ef7cdc315b95b57d693efbe6ad6f84da144ac59a248e265';
```

It is consumed by `verifyRedProductionUnchanged()` — the **PH-005 lane's** guard that
PH-004's baseline has not shifted underneath it. That is `#12` territory, not this lane's.

This was found by grepping for the **moved content** (the hash literal) as well as the file
name, which is the standing brief's rule about evidence-signature indexes surviving a rename
search. A search for `retained-shadow-parity` alone would have found it; a search for the
artifact's *name* in the SRS only, which is what §1 of this file did, would not have.

### It was already red at this HEAD, and that is measured, not inferred

`verifyRedProductionUnchanged` has two independent arms. The second,
`verifyHashManifest(readCurrentHashes(retainedPaths), retainedFiles, …)`, compares the
**current tree** against the production hashes **recorded inside the parity artifact**.

Computed statically — the script itself was **not run**, because it executes Playwright
against `https://localhost:2222` and would invoke `start.bat`, which can start a production
server:

| artifact under test | recorded production hashes vs this tree |
|---|---|
| **committed at HEAD, before this lane** | **4 of 4 mismatch** — `SessionManager.ts`, `ws-protocol.ts`, `headlessTerminal.ts`, `WsRouter.ts` |
| **regenerated by this lane** | **0 of 4 mismatch** |

So `verifyRedProductionUnchanged` was **already failing before this lane touched anything**,
for the same root cause as §1: the artifact was sealed against the Wave-3 tree. This lane
did not break it.

What this lane changed is *which* arm fails. The substantive staleness failure — four
production files whose recorded baseline describes a different tree — is now **fixed**. What
remains is the single `sha256` pin on line 31, which fails because the artifact legitimately
moved and §6 names every input that moved it.

### Default taken: the pin was left alone

Updating another lane's sealed baseline is the same act this lane declined for its own seal,
and for the same reason — naming the moved input is a decision, not a mechanical step, and
this seal belongs to `#12`. The one-line update from `9914e224…` to `b68df22c…` is
recommended and is the orchestrator's call, not this lane's.

Recorded plainly: **after this change, `authority-promotion-evidence.test.mjs` fails on line
31's pin instead of on four stale production hashes.** Both are red; one is a one-line
decision and the other was a substantive divergence.
