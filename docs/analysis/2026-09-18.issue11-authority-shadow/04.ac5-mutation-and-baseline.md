# Issue #11 AC-5 — mutation results, and the server baseline at HEAD

HEAD `5c82d523bf3753ba490b64649af6aa3dc0b76dd0`. Every source edit below was reverted
byte-identically and confirmed with `git status` on the specific path before the next step.

## 1. What issue AC-5 asks, and what is actually in the tree

> checkpoint total이 기존 2MiB를 넘어도 empty success가 되지 않고 bounded ordered
> chunk/digest 또는 observable rejection+fresh resync로 수렴한다.

Two halves: **must not be an empty success**, and **must converge** by one of two named
mechanisms.

The production surface is `serializeRetainedHeadlessCheckpoint`
(`server/src/utils/headlessTerminal.ts:284`). It takes **no byte-cap parameter at all** —
unlike its compatibility sibling `serializeHeadlessTerminal(state, maxSnapshotBytes)` at
`:253`, which is the function that really does return `{ data: '', truncated: true }` when
the payload exceeds the cap. The retained serializer's own comment says so: it "is not a
transport-sized payload and therefore never converts a valid model into an empty/truncated
success." Its return type declares `truncated: false` as a **literal type**, and the
producer hardcodes that literal.

So the first half of AC-5 is satisfied **structurally**, and it is satisfied more strongly
than a runtime check would satisfy it. The `maxSnapshotBytes: 16` that the guarding test
passes cannot reach this function.

That makes one of the test's two assertions vacuous by construction: in
`RetainedTerminalAuthority.test.ts` the `REL-BGSTAB-011 AC-3` case asserts
`state.checkpoint.truncated === false`, over a field whose type admits exactly one value.
Per the standing brief, a field that can take one value across every path reaching it is a
constant no matter what it is named.

## 2. Mutation M1 — the empty-success defect. CAUGHT.

Injected at the single return site of `serializeRetainedHeadlessCheckpoint`: when the
payload exceeds a 16-byte cap, emit `serializedData: ''`. The scripted edit asserted its
own match count (`1`) before writing.

`cd server && npx tsx --test src/services/RetainedTerminalAuthority.test.ts`
→ **exit 1, tests 52 / pass 51 / fail 1**.

The single catching test is `Retained server model shadow and driver lease RED contract —
REL-BGSTAB-011 AC-3`, and the assertion that does the work is
`assert.ok(state.checkpoint.serializedData.length > 0, signature)`.

**This falsified the hypothesis I went in with.** I expected the guard to be vacuous
because its named input (`maxSnapshotBytes`) is inert against the function under test. It
is not vacuous: it owns the empty-success property and it can go red. Recording the
direction — my prediction was that the surface was weaker than it is, and the measurement
moved it toward stronger.

Raw: `raw/mutation-M1-empty-success.log`.

## 3. Mutation M2 — the silent-tail variant. SURVIVED the primary suite.

Same site, same predicate, one change: over the cap the payload stays **non-empty** but is
lossily truncated to its first 8 bytes. No chunking, no digest, no rejection — exactly the
failure mode AC-5's second half ("converge by bounded ordered chunk/digest **or**
observable rejection + fresh resync") exists to forbid.

`npx tsx --test src/services/RetainedTerminalAuthority.test.ts`
→ **exit 0, tests 52 / pass 52 / fail 0 / todo 0.**

### The mutation ran — checked before blaming the test

A survivor has two causes, and a dead mutation is a dead control one level down. Two
independent grounds that M2 is live:

1. **M1 and M2 share the injection site and the `> 16 bytes` predicate**, and M1 reddened.
   The path is reached with that predicate true.
2. **Direct observation.** A probe built a headless state, wrote two lines and read the
   checkpoint back:

   | run | `serializedData` bytes | `rehydrateAnsi` bytes | equal? | `truncated` |
   |---|---:|---:|---|---|
   | unmutated | 54 | 54 | yes | false |
   | under M2 | **8** | 54 | **no** | false |

   46 bytes of authoritative payload silently lost, `truncated` still reading `false`, and
   the suite green.

### Group check — covered, but unowned

M2 was then run against every adjacent suite. Results:

| Suite | exit | pass/fail |
|---|---:|---|
| `WsRouterCheckpointProtocol.test.ts` | 0 | 15/0 |
| `types/wsCheckpointProtocol.test.ts` | 0 | 3/0 |
| `utils/terminalQueryResponder.test.ts` | 0 | 1/0 |
| `SessionManagerTerminalAuthorityRuntimePorts.test.ts` | 0 | 12/0 |
| `SessionManagerPartialEscapeTail.test.ts` | 0 | 10/0 |
| `ws/WsRouterRestoreMetadata.test.ts` | 0 | 3/0 |
| **`SessionManagerTerminalAuthorityDebugIsolation.test.ts`** | **1** | **10/2** |

The two catching tests are:

- `MIG-BGSTAB-002 cleanup serializes live PTY output after the restored headless checkpoint`
- `MIG-BGSTAB-002 debug isolation uses the production headless queue and restores its retained override`

Neither is named for checkpoint payload integrity. So the disposition is the fourth one,
not the first: **covered but unowned.** It looks identical to "covered" in any coverage
measurement and behaves like "uncovered" under maintenance — rewriting either of those two
tests for its own stated `MIG-BGSTAB-002` reason would silently unguard the silent-tail
property, and nothing would flag it.

**Bound on this claim:** two loss modes were tried — full empty and head-truncation to 8
bytes. **Two modes is not all modes.** Tail truncation, per-line dropping, reordering and
attribute loss were not injected.

### The proposed remedy

Give the property a named owner: a test whose *name* is the property — an over-cap retained
checkpoint converges without a silent tail — asserting payload **identity**
(`serializedData === rehydrateAnsi`, plus the retained logical-line count) rather than a
lower bound of `> 0`. `> 0` is true of the correct state and of the defect; that is the
Class B shape.

Note this is a **test gap, not a production defect.** Production is correct here, and
correct by construction rather than by a runtime branch.

## 3b. The first failure is an instrument defect, and it matters for AC-8

`testSessionManagerPowerShellPromptRedrawStaysIdle` mocks the platform (`platform: 'win32'`)
and the PTY, so it looks host-independent. It is not. `SessionManager.resolveSpawnCwd`
(`SessionManager.ts:4222`) calls the **real, unmocked** `existsSync` at `:4247`. The session
is created with cwd `C:\Users\beom`; on this Linux host that path does not exist, so the
tracked cwd falls back to `$HOME`, the prompt-redraw suppressor's cwd equality no longer
holds, and the very first prompt output is classified as real output → `running`. The
failure is at line 4673, the **first** assertion, before the test reaches the behaviour it
was written to examine.

**Confirmed by execution, not by reading.** Creating a directory literally named
`C:\Users\beom` under `server/` (backslashes are ordinary filename characters on Linux) made
`existsSync` return true, and the same runner then produced **539 PASS / 2 FAIL** with that
test passing. The directory was removed afterwards and `git status` confirmed the tree
unchanged.

Raw: `raw/baseline-server-test-runner.log` (3 FAIL) and
`raw/probe-cwd-existsSync-test-runner.log` (2 FAIL, same binary, one directory different).

**Why this is more than a flaky test.** That test is the named verification of
`REL-BGSTAB-011` **AC-8** — the AI-TUI idle invariant, which is `checked` on an
`implemented` requirement. On any Linux host it is red, and it is red *before* it exercises
the invariant. So on this host the AC-8 checkbox has **no passing named verification**, and
the reason has nothing to do with the property. The invariant itself is **not** shown to be
violated — this is an instrument defect, not a production defect, and I did not measure
whether the invariant holds independently of this fixture.
