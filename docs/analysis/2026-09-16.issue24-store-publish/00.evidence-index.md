## Regression baseline and comparison

files under `server/src/services` and `server/src/utils` at `e7c162c`, before any
production change: **16 failing**.

Acceptance is set equality against that baseline, not an exit code. A run that
fails only for the known Linux/WSL2 baseline reasons and a run that additionally
fails because a store broke both exit non-zero, so an exit code cannot tell them
apart. `tools/issue24-regression-diff.mjs` does the comparison by name.

| run | files | failing | new vs baseline |

the second full sweep of the changed tree reproduced the baseline set exactly.
The test concerns PTY settling time under a fixture bound and touches no store
under `server/data/`. It is recorded here rather than excluded.

One honest qualification. In the PH-002 RED run the ENOSPC case
(`AC-6: ENOSPC rejects on the first attempt with zero recorded waits`) passed,
because a helper that never retries also rejects ENOSPC on its first attempt with
no waits. That assertion is a boundary control against an implementation that
retries everything, not a RED. The other five AC-5 assertions are genuine REDs:
each counts attempts, so none can pass against a helper that renames once.
