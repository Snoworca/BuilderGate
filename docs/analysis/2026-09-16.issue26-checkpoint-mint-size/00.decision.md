## 1. Verdict in one line

The mechanism is real and unchanged, the unbounded-retry half of the issue is **bounded**
(with a wider reset surface than §3 first claimed), and the severity is **wrong in the
issue's favour**. The defect is a **width × SGR-density surface**, and two realistic
corners of it cross the default budget:

- at **per-token SGR density** — one colour plus reset per token, which is how a syntax
  highlighter or a coloured diff actually emits — the crossover is at **166 columns**,
  read off direct full-scrollback runs rather than projected (165 col = 99.09% of budget,
  166 col = 100.06%), with everything else at stock defaults;
- at **400 columns**, as little as **two attribute runs per line** crosses (100.1%), and
  even entirely uncoloured output sits at 93.4%.

Between those corners there is real headroom: at 200 columns, eight attribute runs per
line reaches only 63.7%. The issue's own "extreme conditions" framing and its
priority `low` do not survive the first corner; its 124-column measurement sat at 72%,
just inside.

No code change is made here. The remedy is gated behind issue #25 and
`REL-BGSTAB-007` AC-11, and is recorded below with an executable characterization test.

### 2.1 Two facts the issue did not record

**The `encodedByteTotal` the browser tests is exactly the utf8 byte length of
`checkpoint.serializedData`.** `TerminalAuthorityProductionAdapter.ts:1660-1666` sets
`data = retained.checkpoint.serializedData`, and `encodeCheckpointChunks`
(`:888-906`) reports `encodedBytes` as the raw pre-base64 chunk length. Measuring
`Buffer.byteLength(checkpoint.serializedData, 'utf8')` is therefore exact, not an
approximation.

**The retained path is deliberately budget-free, and the compatibility path is not.**
`serializeHeadlessTerminal(state, maxSnapshotBytes, …)` applies a byte budget and can
return `truncated: true`. `serializeRetainedHeadlessCheckpoint` takes no budget and its
return type declares `truncated: false` as a *literal* type. The in-file comment states
the reason: the retained checkpoint "is not a transport-sized payload and therefore
never converts a valid model into an empty/truncated success". The absence of a
mint-time check is an explicit design position, not an oversight.

## 3. The infinite-retry half is closed

The issue's fourth claim no longer holds. `invalid-checkpoint-metadata` reaches
`requestRecovery` → `adapter.requestFreshRecovery` → `TerminalView`'s
`requestCheckpointRecovery` → `TerminalContainer.handleVisibleOutputOverflow`, which
consumes a bounded budget before it will ask the server for another snapshot:

- `TerminalContainer.tsx:178` — `VISIBLE_OUTPUT_RECOVERY_MAX_FRESH_SNAPSHOT_ATTEMPTS = 3`
- `TerminalContainer.tsx:3640` — exhaustion emits `visible_output_resync_retry_budget_exhausted` and **returns without sending**
- `visibleOutputRecovery.ts` — `consume()` refuses past the cap; the counter resets only through `resetAfterConvergence` (fired at `TerminalContainer.tsx:1486` and `:1706`, both on *successful* convergence) or `resetForNewScope` (session-scope change)

This is `REL-BGSTAB-009` AC-8 ("Retry와 concurrent restore 수는 bounded"), Status
`implemented`, and it is covered by `frontend/tests/unit/visibleOutputRecovery.test.ts:365`
and `frontend/tests/unit/terminalContainerRecoveryContract.test.ts:153`.

### 3.1 The reset surface is wider than "convergence or session change"

A first draft of this section said the counter "resets only through
`resetAfterConvergence` … or `resetForNewScope` (session-scope change)". That
understates it, in the direction that flatters this document's conclusion. Three
corrections:

1. `resetForNewScope()` at `TerminalContainer.tsx:1136` sits in the **unconditional**
   block of the effect opened at `:1111`. Only the generation bump at `:1119` is guarded
   by a `sessionId` check. The effect's own production comment at `:1125-1129` says
   plainly that "the effect also re-runs on a callback identity change" — so the reset
   is not strictly session-scoped, it fires on every re-run of that effect.
2. There is a **third** reset path this document omitted:
   `resetAfterMatchingReconnectConvergence` at `TerminalContainer.tsx:2342`, reaching
   `reset()` in `visibleOutputRecovery.ts`.
3. Whether the six callbacks in that effect's dependency list are identity-stable for a
   session's lifetime was **not** established here. Until it is, the correct statement is
   that the budget is bounded **per effect scope**, not that the loop is closed outright.

The premise the issue stated — *server regenerates an identical checkpoint forever
because nothing reduces its size* — is still wrong: there is a cap, and exhausting it
stops the request. But "stale" is the right word for that premise, not "closed", and a
successor to this issue should either prove the callback identities stable or re-rate the
residual retry exposure.

So an oversized checkpoint today produces: up to three rejected promotion attempts per
effect scope, then a session that stays on legacy browser authority with a named
diagnostic. Degraded and observable — **not** an unbounded identical-regeneration loop.

## 4. Re-measurement

Harnesses preserved as `threshold-harness.ts` and `full-scrollback-harness.ts`; raw
output in `raw/`. Both drive the production serializer
(`serializeRetainedHeadlessCheckpoint`). The threshold harness measures a 1,500-line
sample exactly and projects to the configured `scrollbackLines`; the full-scrollback
harness fills the whole scrollback and measures directly.

**The projection is validated against the direct measurement to within 0.07%:**

| Condition | Projected | Directly measured | Error |
| --- | --- | --- | --- |
| 124 col, scrollback 10000 | 3,037,975 B | 3,040,000 B | 0.067% |
| **200 col, scrollback 10000** | **5,127,582 B** | **5,131,000 B** | **0.067%** |
| 400 col, scrollback 10000 | 10,537,975 B | 10,545,000 B | 0.067% |

The 200-column row is the geometry the characterization test gates on, and it was added
in review precisely so the gate does not rest on an unvalidated extrapolation.

**The error is systematic, one-directional, and was initially explained wrongly here.** A
draft attributed it to the 1500-written / 1501-retained off-by-one (1/1501 = 0.0666%),
which is numerically close to the observed 0.067% and therefore looked convincing. It is
not the cause. Measuring the per-line ratio directly:

| Condition | Sample B/line | Direct B/line (÷10001) | Ratio |
| --- | --- | --- | --- |
| 124 col | 303.79747 | 303.96960 | 1.000567 |
| 200 col | 512.75816 | 513.04870 | 1.000567 |
| 400 col | 1053.79747 | 1054.39456 | 1.000567 |

The 1,500-line sample **underestimates bytes-per-line by a constant 0.0567%** across three
geometries — not 0.0666%. The reported 0.067% figure conflates that with the separate 0.01%
from projecting over 10,000 rather than the 10,001 lines actually retained. Both push the
same way: **the projection always undershoots.**

That matters where the margin is thin, and §4.1 originally ignored it. Corrected
projection = sample B/line × 1.000567 × 10,001.

Two things follow, and the second is the one an earlier draft of this document got

- **At 400 columns the defect is nearly density-independent.** Two attribute runs per

- **At 200 columns it is entirely density-dependent.** Everything up to eight runs per

  terminal near 400 columns, almost regardless of colour".

Per-token density is not a strawman — it is what syntax highlighting and coloured diffs
produce, and those are BuilderGate's stated primary workload — but it is a precondition
and this document states it as one.

### 4.3 What this corrects in the issue

The original measurement used **124 columns** at a density near §4.1's, which sits at
72% — just under the line. It listed "very wide terminals" as an untested risk
condition. That condition is not exotic and it does not need a raised `scrollbackLines`:
**at stock defaults, with per-token-coloured output, every checkpoint minted past 166
columns is one the browser is required to reject** — and near 400 columns that holds at
almost any colouring (§4.2). The issue's "즉시 발동 조건 없음" and priority `low` do not
survive either corner. What the issue got right, and this document initially blurred, is
that in the middle of the surface — moderate width with moderate colouring — the headroom
it measured is real.

## 5. Decision: record, correct the severity, do not patch here

### 5.1 What was rejected, and why

**Truncate at mint (shed scrollback).** Mechanically available —
`ISerializeOptions.scrollback` exists and `VIEWPORT_ONLY_SERIALIZE_OPTIONS` already
uses it. *A first reading of this rejected it for the wrong reason:* the round-trip
parity gate compares a checkpoint against a terminal rehydrated **from that same
checkpoint** (`compareRetainedHeadlessCheckpointRoundTrip`), so a truncated checkpoint
would still pass parity. The correct reason is `MIG-BGSTAB-002` AC-4, which requires
the **configured retained range** to be recoverable from the server checkpoint. Shedding
scrollback silently violates that AC, and the `truncated: false` literal type encodes
the same position. Not available without a requirement change.

**Refuse to mint.** An earlier draft rejected this as "outcome-neutral — a better-named
reason, not a better outcome". **That was wrong, and the error mattered.** The browser
rejects at the `checkpoint-start` frame (`terminalWriteCoordinator.ts:1786-1789`), but
by then the whole payload has already been sent: `TerminalAuthorityProductionAdapter.ts:1990`
maps the entire `recovery.checkpointMessages` array — start, every chunk, commit — into
one delivery batch with no per-message admission gating. At the 400-column figure that is
10,545,000 raw bytes as 161 base64 chunks, roughly 14 MB on the wire, plus a full 10,000-line
`serializeRetainedHeadlessCheckpoint`, plus a `checkpointInputBarrierRef` toggle
(`TerminalView.tsx:3226`) — **repeated on each budgeted attempt**. Refusing at mint would
avoid all of it.

So refusing to mint is **not** outcome-neutral: the terminal ends in the same authority
mode, but the transmitted bytes, serializer CPU and input-barrier churn are real and
avoidable. This raises the value of a mint-time check rather than lowering it. It is still
not done here, but §5.2's reason — the approval gate — is the only reason, and it has to
carry the weight alone.

**Bound the retry loop.** Already done (§3). Nothing to add.

### 5.2 What is actually left, and why it is not done here

The only remedy that preserves `MIG-BGSTAB-002` AC-4 is **raising the budget**, which
is an operator action, and the only thing the mint could usefully add is an
**observation** — emit a named diagnostic when the minted `encodedByteTotal` exceeds
the configured `resourceLimits.terminal.visibleOutputQueueMaxBytes`, so the operator
learns which lever to pull instead of reading three failed promotions.

That observation is deliberately **not** implemented in this lane:

1. It makes the server a new consumer of `resourceLimits.terminal.visibleOutputQueueMaxBytes`.
   Every consumer is catalogued in `TerminalResourcePolicyInventory.ts` and pinned by
   `tools/wave3/terminal-resource-consumer-manifest.test.mjs`, which validates a manifest,
   a lineage file and a hashed evidence bundle under
   `docs/analysis/kiwi-coder-2026-07-16.projectmaster.wave3-authority-fairness/`.
2. That is the republish procedure issue #25 priced (16 files, a forced republish, 21
   tests red until it completes), and #25 states it is gated on user approval under
   `REL-BGSTAB-007` AC-11 and `OBS-BGSTAB-005` AC-1/AC-6.

**The precise trigger is narrower than "add an observation", and this document should not
have blurred it.** The inventory sweep keys on the literal property name `resourceLimits`
and skips `*.test.*` files. So what costs a republish is specifically *a read of
`resourceLimits.*` inside non-test `server/src`* — not the act of observing. Emitting
`encodedByteTotal` unconditionally, with no limit read, and thresholding it downstream
carries **zero** manifest cost.

That cheaper variant is not adopted, for a reason worth stating rather than hiding behind
the cost: **a number is not a check.** The gap the issue names is "mint 시점에 수용 가능
여부 검사 자체가 없음" — an admission decision. Emitting a byte count that nothing compares
against a budget leaves the operator exactly where they are today, reading three failed
promotions and guessing. It would be motion, not a fix. If a follow-up wants the cheap
half, it should land it knowing it closes the telemetry gap and not the admission gap.

Front-running an approval-gated procedure to add a log line is the wrong trade. The
severity correction is what unblocks the decision; the remedy belongs with #25.

`TerminalAuthorityProductionAdapter.ts` itself is **not** provenance-pinned
(`server/tools/write-fair-scheduler-source-provenance.mjs` pins six files, and it is not
one of them), so the adapter edit alone would be cheap. The cost is entirely in the
resource-consumer manifest.

### 5.3 Executable contract left behind

`server/src/services/TerminalCheckpointMintSizeAdmission.test.ts`, 3 cases, run with
`npm run test:checkpoint-mint-size` from `server/`. It reads no source text, so it works
from `src/` and from `dist/`:

- the retained checkpoint declares `truncated: false` as a literal type, pinning the no-shedding position
- at parsed schema defaults, a 200-column session at per-token SGR density projects past `visibleOutputQueueMaxBytes`
- the same density at 80 columns still fits

It also asserts the two defaults it depends on (4 MiB, 10000 lines) so that a defaults
change fails loudly rather than silently invalidating the measurement. **These cases pass
because the defect is present**; a fix must revisit them together.

Three limits are stated in the file itself rather than left for a reader to discover:

- **The browser side is arithmetic, not execution.** `browserWouldReject` is a hand-copy
  of the comparison at `terminalWriteCoordinator.ts:1786`. The real predicate is not
  exported and lives in the frontend package, so a server-side test cannot drive it.
  Nothing here covers the `checkpointMaxBytes ?? postCheckpointMaxBytes` fallback at
  `:430-432` — which is the only reason the limit applies at all. A change to that chain
  leaves these cases green.
- **Case 1 pins a type declaration, not a threshold.** `truncated` is a hardcoded literal;
  an implementation that shed scrollback above some size would still pass it. Its title
  says so.
- **The sample is 1,500 lines**, the size the 0.07% agreement was established at, and the
  200-column gate geometry is now directly measured (§4) rather than extrapolated on trust.

### 6.0 A second thing reported, not repaired: `MIG-BGSTAB-002` AC-4's own status

§5.1 uses AC-4 to veto truncation. Fair enough — but the same measurement puts AC-4's
`[x]` in question, and this document owed that the same treatment it gave the ID mismatch
below.

AC-4 (`docs/spec/30.buildergate-stability.srs.md:3621`) requires that on a hard reload
with an absent or poisoned browser cache, the **configured retained range** and the
terminal state hash are recoverable from the server checkpoint plus post-snapshot output.
Above the measured crossover the server checkpoint is rejected wholesale at
`terminalWriteCoordinator.ts:1786-1789`, so recovery *from the server checkpoint* does not
happen at all. That is a stronger failure than partial recovery, which is the thing AC-4
is being cited to forbid.

AC-4 is marked `[x]`, Status `implemented`, Stability `evolving`. Whether it still holds
at default configuration above 166 columns at per-token density was **not** re-verified
here, and should not be assumed from its checkbox. Routed to the SRS owner as a question,
not repaired.

## 7. What this says about #28

Nothing conclusive — #28 was not investigated here — but three observations from the
same code region:

1. `retainedStateParity-gate-failed` does not exist as a string anywhere in the current
   source tree. The only hits are an archived `.kiwi` task record from 2026-07-28. The
   production blockers are `retained-state-parity-mismatch` and
   `retained-state-parity-unavailable` (`SessionManager.ts:2989-2992`). #28 should
   confirm which label its harness actually produced.
2. The two blockers separate cleanly, and the disjunction is wider than a first draft of
   this document listed. `SessionManager.ts:2959-2966` computes `retainedStateParity` as an
   eight-term conjunction — `headlessHealth === 'healthy'`, `headless !== null`,
   `mode === 'shadow'`, `comparerReady`, `!comparerMismatch`, `parserEquivalent`,
   `evictionEquivalent`, `!blockers.has('model-degradation')` — and `:2990` selects
   `-unavailable` whenever `comparerMismatch` is false. So `-unavailable` covers **seven**
   distinct causes, not the three named earlier: the three environmental ones plus
   `comparerReady`, `parserEquivalent` and `evictionEquivalent` failing. #28 should not
   narrow its search on the short list.
3. `cells` and `unicodeWidth` are the only axes that can be attribute-sensitive —
   `cells` folds in `attributeHash`, `unicodeWidth` only `cellHash`. If SGR density is
   causally implicated, `cells` mismatching while `unicodeWidth` matches would isolate
   the attribute round-trip as the cause. That is a one-run discriminator for #28.

Separately, the size facts here do **not** explain #28: #28 reports failure at 2,000
SGR-dense lines, which at any of the measured densities is far inside the budget.
Size and #28 are different problems.
