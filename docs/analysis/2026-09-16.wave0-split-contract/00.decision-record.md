## 2. 결정 근거 (전부 이 커밋에서 직접 재측정함)

### E-1. split 과 binary 데이터 평면은 현재 구현상 상호 배타적이며, binary 는 이미 채택 결정이 끝났다

`server/src/ws/terminalWireFormat.ts` 의 `isTransportEligible` 은 단 한 줄이다:

```ts
function isTransportEligible(transportMode: WsTransportMode): boolean {
  return transportMode === 'unified';
}
```

`isBinaryNegotiable` 과 `decideTerminalWireFormat` 이 모두 이 술어를 통과해야 하며, 통과하지 못하면
`json('transport-not-eligible')` 로 수렴한다. 같은 파일의 주석이 그 이유를 명시한다 —
*"Split transport moves terminal payload between two sockets, which multiplies the states the channel
table has to survive for no rollout benefit."*

epic #2 의 `wave-5` Goal 은 binary 데이터 평면 채택이 **이미 결정된 사항**(2026-08-16 owner decision,
adopt-or-skip gate 폐지)이라고 기록한다. 따라서 production 에서 split 을 복원하는 것은 이미 내려진
상위 결정을 되돌려 채택된 binary 평면을 비활성화하는 일이 된다. 0A 는 이 지점에서 단독으로 기각된다.

주의: epic 은 "split 채택 여부는 별도 판단으로 남는다" 고도 적었다. 그 별도 판단이 곧 이 문서이며,
binary 가 결정되었다는 사실이 split 을 자동으로 결정하지는 않는다. 위 논증은 "binary 가 결정되었으므로
split 도 결정되었다" 가 아니라 "현재 구현에서 둘이 배타적이므로 split 복원은 binary 철회를 수반한다" 이다.

### E-2. production 은 split 로 **터미널 페이로드를 라우팅한 적이 없고**, 그 사실이 green 테스트로 고정되어 있다

> **정정 (리뷰 라운드 1).** 이 항목의 최초 서술은 "`config.realtime.wsTransportMode` 는 라우터에 도달하지 않는다" 였다.
> **그것은 틀렸다.** 실측하면 `server/src/index.ts` 는 그 값을 `configuredWsTransportMode` 로 읽어
> (a) `WsRouter` 의 `binaryNegotiationTransportMode` 옵션과 (b) `attachProductionTerminalAuthority` 의
> `transportMode` 인자로 **넘긴다.** 즉 operator 가 `wsTransportMode: "split"` 을 설정하면 오늘도
> production 동작이 바뀐다 — binary 협상이 꺼지고 terminal authority 토폴로지가 `split` 으로 선택된다.
> 정확한 명제는 아래이며, `REL-BGSTAB-024` AC-8 이 이 두 경로를 계약으로 기록한다.

`server/src/index.ts` 의 `new WsRouter(...)` 호출은 **`wsTransportMode` 라는 이름의 옵션을 넘기지 않는다.**
`realtime` 옵션으로는 `terminalWireFormat` 만 전달된다. 따라서 라우팅 판정이 읽는
`WsRouter` 의 `this.wsTransportMode` 는 production 에서 항상 `'unified'` 로 기본값에 수렴하며,
터미널 페이로드는 단일 소켓 경로를 벗어나지 않는다. 설정값은 **eligibility·topology 선택자**로는 살아 있고
**라우팅 스위치**로는 죽어 있다 — 이 비대칭이 이 이슈가 고정해야 할 drift 의 정확한 형태다.

이 누락은 사고가 아니라 **의도적으로 테스트가 지키고 있다.** `server/src/test-runner.ts` 의
서버 기동 배선 검사가 construction 슬라이스에 대해 다음을 단언한다:

```ts
assert.doesNotMatch(construction, /wsTransportMode/u);
```

바로 위 주석: *"Handing over config.realtime wholesale would revive the hardcoded wsTransportMode as well.
AC-7 requires the two keys to stay orthogonal, and Wave-1 characterized the transport side separately."*

0A 는 이 green 단언을 삭제하는 것에서 시작해야 한다.

### E-3. 브라우저는 split 에 도달할 수 없다 — 클라이언트/서버 파라미터 이름이 다르다

- `frontend/src/utils/webSocketUrl.ts` 의 `buildControlWebSocketUrl` 은 `mode=split&channel=control` 을 emit 한다.
- `server/src/ws/WsRouter.ts` 의 upgrade 경로는 `url.searchParams.get('wsTransportMode')` 를 읽는다.

이름이 달라 브라우저가 만든 URL 로는 `requestedMode` 가 결코 split 이 되지 않는다.
정본 파서 `parseWsTransportRequest`(`server/src/ws/wsTransportMode.ts`)는 `mode`/`channel` 을 읽고
configured 가 `unified` 일 때 `split-disabled` 400 을 돌려주지만, **production upgrade 경로에서 호출되지 않는다.**
현재 이 함수의 유일한 호출자는 `server/src/ws/wsTransportMode.test.ts` 다.

0A 는 이 클라이언트/서버 계약 불일치를 먼저 닫아야 한다.

`server/src/ws/WsRouterSplitHandshake.test.ts` 를 이 커밋에서 직접 실행한 결과

### E-5. Wave-1 이 disposition 을 명시적으로 미결로 동결했고, 그 후속 결정자가 이 이슈다

`REL-BGSTAB-006 — Split runtime·test·SRS drift characterization`(target `wave-1`, Status=implemented,
Stability=evolving, GitHub Issue = 본 이슈 #3) 의 AC-5:

> Characterization 결과와 Change/decision artifact는 restore와 supersede 중 하나를 선택하지 않고
> disposition을 unresolved로 남기며, FR-BGSTAB-006/007의 Status·Stability·본문을 변경하거나

Wave-1 은 의도적으로 판단을 유보했고 그 판단을 이 이슈에 남겼다. 따라서 여기서 XOR 을 확정하는 것은
REL-BGSTAB-006 을 위반하는 것이 아니라 그것이 예정한 후속 절차다.

### E-6. 비용·리스크의 비대칭

0A 는 Wave 0(계약 게이트)에서 transport 계층 재작업을 요구한다. E-2/E-3 의 두 배선 결함을 닫고,
12건의 todo 를 실제 green 으로 만들고, 채택된 binary 평면을 철회해야 한다. 그리고 #4~#22 전부가
그 위에 놓인다 — Wave 0 이 최대 리스크 구현 작업이 되어 의존 방향이 뒤집힌다.

0B 는 SRS 를 관측된 runtime 에 맞추고, 관측을 테스트로 고정하고, 활성화 판단을 명시적 후속 결정으로

## 4. 결정의 범위 — 무엇을 하고 무엇을 하지 않는가

**한다**
- FR-BGSTAB-006/007 의 **production 적용 주장**을 superseding Requirement 로 대체한다.
  새 Requirement 는 production transport 가 unified 전용이라는 것, split 이 standalone 라우터 역량으로만
  존재한다는 것, 그리고 활성화가 명시적 후속 결정을 요구한다는 것을 계약으로 기술한다.
- 관측된 불변식을 characterization 테스트로 고정한다(동작 변경 아님).
- FR-BGSTAB-006/007 의 VE 노트 중 사실과 어긋나는 진술("Focused split handshake tests passed")을
  실제 관측(15 pass / 13 todo, exit 0)으로 정정한다. 기존 행을 덮어쓰지 않고 새 행으로 추가한다.

**하지 않는다**
- split 코드 삭제 (#21/#22)
- split runtime 활성화
- `WsRouter` upgrade 경로의 동작 변경 (§7 의 결함 D-1 은 후속 이슈로 보고)
- FR-BGSTAB-006/007 의 Status·Stability 를 임의 승급/강등
- 전체 server 스위트를 green 으로 만드는 일 (#40 / RG-06 범위)

## 6. Rollback

이 결정은 SRS 계약과 characterization 테스트로만 구성되므로 rollback 이 bounded 하다.

1. superseding Requirement 를 `discarded` 로 전이하고 supersedes 관계를 해제한다.
2. 추가한 characterization 테스트를 되돌린다. 이 테스트들은 관측을 고정할 뿐 production 경로를 바꾸지 않으므로
   되돌려도 runtime 동작이 변하지 않는다.
3. FR-BGSTAB-006/007 은 본문·Status·Stability 를 건드리지 않았으므로 자동으로 원래 계약으로 복귀한다.
4. runtime 변경이 없으므로 배포 rollback·soak·마이그레이션 절차가 필요하지 않다.

전환 metric 은 **둘**이다 (E-2 정정 참조). 하나만 보면 부족하다.

1. `server/src/test-runner.ts` 의 `assert.doesNotMatch(construction, /wsTransportMode/u)` — 깨지면
   라우팅 스위치가 production 배선에 들어온 것이다.
2. `server/src/index.ts` 의 `binaryNegotiationTransportMode` 와 `attachProductionTerminalAuthority` 의
   `transportMode` 인자 — 둘 중 하나라도 설정값에서 파생되기를 멈추거나, 반대로 라우팅 모드를 먹이기
   시작하면 이 계약은 무효다.

1번만 감시하면 operator 가 `split` 을 설정해 binary 협상이 조용히 꺼지는 경우를 놓친다.

## 7. 이 조사에서 발견한 결함 (직접 이슈를 열지 않고 오케스트레이터에 보고)

### D-1. 클라이언트가 선언한 `?wsTransportMode=` 가 configured 설정을 무시한다

`WsRouter` upgrade 경로는 쿼리 파라미터를 읽어 그 값이 `split`/`split-shadow`/`unified` 중 하나면
**configured mode 를 확인하지 않고** 그대로 `requestedMode` 로 채택한다. 그 값은 연결 메타데이터의
`wsTransportMode` 에 저장되고 이후 라우팅 판정이 그 메타데이터를 읽는다.

결과: `realtime.wsTransportMode: "unified"` 로 설정된 서버에서도, 인증된 사용자가 URL 을 직접 만들면
자기 연결에 대해 split 그룹(30초 pairToken 포함)을 할당받고 라우팅 메타데이터를 split 으로 바꿀 수 있다.
operator 설정이 transport 를 가두지 못한다.

**보안 등급에 대한 정직한 평가**: 인증은 `handleUpgrade` 이전에 이미 검증되고, output 소켓 페어링은
pairToken 과 인증 identity 일치를 요구한다. 따라서 authn/authz 우회가 아니며 타 사용자에게 영향이 없다.
**권한 상승이 아니라 설정 계약 위반**으로 분류한다.

**왜 이 이슈에서 고치지 않는가**: `server/src/ws/terminalWireFormatBoot.test.ts` 의
`IR-BGSTAB-001 a client asking for split cannot negotiate binary on a unified server` 가 현재 green 이며,
클라이언트가 선언한 split 이 unified 서버에서 **binary 협상을 좁히는 효과를 실제로 가진다**는 것을
의도적으로 단언한다. D-1 을 고치면 이 단언의 전제가 사라진다. 이는 wave-5 의 `IR-BGSTAB-001`
계약 변경이며 Wave 0 계약 게이트의 범위를 넘는다. 후속 이슈로 분리한다.

### D-2. 이슈 #3 본문의 SRS 참조가 틀렸다

본문은 관련 SRS 로 `PERF-BGSTAB-005/006/007` 을 든다. 실제로 이 셋은 benchmark 와 무관하다:

- `PERF-BGSTAB-005 — 비대상 포그라운드 감지기의 프레임당 문자열 처리 조기 회피`
- `PERF-BGSTAB-006 — 디버그 캡처 비활성 시 원시 출력 디버그 상세 생성 생략`
- `PERF-BGSTAB-007 — onData 청크당 제어시퀀스 strip 단일 계산 공유`

benchmark 계약을 실제로 소유한 요구사항은 **`PERF-BGSTAB-008 — Benchmark modes and raw evidence contract`**
이며, 그 `GitHub Issue` 필드가 이미 본 이슈 #3 을 가리키고 있다.

### D-3. `CLAUDE.md` 의 split 테스트 수치가 낡았다
