# Issue #12 AC-2 — how a non-zero responder window would be observed, and what that shows

HEAD `db16233863df6310251da55449d3399fc22fc506`.

Issue AC-2: *구 responder disable ACK 뒤 신규 responder를 enable하여 **두 responder 동시 활성
구간이 0**이다.* The lane brief is explicit that this is the deliverable rather than a side
condition, and that **the observation method must be decided before the window is declared
zero** — an untestable safety property is a finding, not a pass.

This file does that, in the order the brief prescribes: name the observable, name the control
that would make a zero meaningful, then report the first measurement and its bound.

## Step 1 — what "two responders active" is, in terms the code has

`runtime.responder` carries three relevant fields:

| field | type | meaning |
|---|---|---|
| `active` | `'server-headless' \| 'legacy-browser' \| null` | **single-valued** |
| `serverEnabled` | boolean | |
| `legacyEnabled` | boolean | |

So the AC's phrase maps onto **two different observables**, and they are not equivalent:

- **Literal reading:** `serverEnabled && legacyEnabled` true at some instant.
- **Hazard reading:** a side effect is admitted by both responders — the thing AC-2 exists to
  prevent (a duplicated reply, a torn screen).

Per #10's rule, the second is an experiment and the first is a vocabulary question, so both
are recorded but the second decides.

## Step 2 — the hazard is arbitrated by a field the AC does not name

The two reply paths guard as follows (`SessionManager.ts`, the
`…ServerQueryReply` / `…LegacyQueryReply` pair around `:5397` and `:5416`):

```
server path:  responder.active === 'server-headless' && responder.serverEnabled
              && responder.activeLeaseId === input.responderLeaseId
              && !responder.revokedLeaseIds.has(...)

legacy path:  responder.active === 'legacy-browser'  && responder.legacyEnabled
              && responder.activeLeaseId === input.responderLeaseId
              && !responder.revokedLeaseIds.has(...)
              && retained.driverLease.state === 'active'
```

Both conjunctions include `responder.active`, which holds **one** value. So a duplicate reply
requires `active` to be two values simultaneously, which it cannot be. **The hazard is
excluded by a single-valued discriminator, not by the pair of booleans the AC names.**

That is a real answer to the specification question, obtained by reducing it to a mechanism:
*is the hazard AC-2 exists to prevent present?* For the query-reply path — **no**, and the
reason is structural rather than timing-dependent.

## Step 3 — the literal reading, enumerated

`serverEnabled` and `legacyEnabled` are assigned in **23 statements across 12 sites**, all in
`SessionManager.ts`. The shape of those 12 is not uniform, and the exceptions are the
interesting part:

| shape | sites | statements |
|---|---|---|
| both assigned adjacently, as a pair | `:2578` `:2651` `:2838` `:3042` `:3197` `:3234` `:5286` `:6110` `:6646` `:8606` | 20 |
| **one assigned alone** — `serverEnabled = false`, `legacyEnabled` left as it was | `:2594` | 1 |
| **two mutually-exclusive conditionals**, so exactly one fires | `:2737` / `:2738` | 2 |

In **all 12**, `responder.active` is assigned **before** either boolean, and in the two
non-paired sites it is assigned `null` — which closes both reply paths regardless of what the
booleans hold. So the non-paired sites are safe, and they are safe for the *same* reason the
paired ones are: the discriminator, not the pair.

Two orderings appear:

| order | sites | transient state between the two statements |
|---|---|---|
| `legacyEnabled = false` then `serverEnabled = true` | `:2578`, `:2651` | neither enabled — safe |
| `legacyEnabled = true` then `serverEnabled = false` | `:2838`, `:3197`, `:6110` | **both enabled**, for the width of one statement |

So under the **literal** reading the window is not provably zero: three sites pass through a
both-true state. Under the **hazard** reading it is zero anyway, because `active` was already
switched to `'legacy-browser'` on a line above, so the server reply path is already closed
before `legacyEnabled` is raised.

**The honest disposition:** the property holds, and it holds for a reason the criterion does
not state. Held at the strength the measurement supports — this is an enumeration of
assignment sites, so it is search-derived over two identifiers and carries that discount; and
single-threaded JavaScript means "between two statements" is unobservable **unless** one of
the assignments is interposed (a setter, a proxy, an emit). None of these is a plain-object
setter today. That is a property of today's code, not a guarantee.

## Step 4 — nothing verifies any of this

Measured: `grep` for a line naming `serverEnabled` that also names `legacyEnabled`, over all
of `server/src` **including tests**, returns **nothing** outside the paired assignments
themselves.

So the zero-window property has **no named owner** — #10's fourth disposition, *covered but
unowned*, applied to this lane's headline safety invariant. It is held by an assignment
convention across eleven sites, and the cheapest way for a future lane to break it is to add
a twelfth site that assigns only one of the two. Nothing would go red.

That is the standing brief's allowlist test run in reverse: *ask what the cheapest way to make
a future red go green is.* Here there is no red to make green, which is worse.

## Step 5 — the observation method, stated before any zero is claimed

Three arms, and the third is what makes the first two mean anything:

1. **Literal-window instrument.** Wrap `runtime.responder` in a proxy (or instrument the
   eleven assignment sites) that records, on every mutation, the tuple
   `(active, serverEnabled, legacyEnabled, activeLeaseId)` with a monotonic step counter.
   A non-zero window is any recorded state with `serverEnabled && legacyEnabled`. Because the
   both-true state is intra-statement, the instrument must sample **per assignment**, not per
   turn — a per-turn sampler would report zero and would be a false negative.
2. **Hazard instrument: prefix injection.** For each prefix of the handoff sequence, inject a
   terminal query and **count replies**. Zero window means every prefix yields exactly one
   reply or an observably-recorded zero; a non-zero window shows up as a prefix yielding
   **two**. This is the brief's AC-11 instruction (*test each prefix, not just the end state*)
   applied to AC-2, and unlike arm 1 it measures the hazard rather than the vocabulary.
3. **Controls, per arm and per precondition.** Arm 1: force `serverEnabled = legacyEnabled =
   true` and confirm the instrument **reports** a non-zero window — otherwise its zero is
   indistinguishable from a dead probe, which is how #9's AC-2 probe gave three confident
   wrong answers in an hour. Arm 2: force `active` to admit both paths and confirm the
   injector **observes two replies** — the count must be asserted **on the subject arm**, not
   only on a roomy control (#10's `binaryFrameCodec` finding).

**The existing fault surface does not provide arm 2 yet.** `TerminalAuthorityDebugService`
exposes exactly **one** injectable fault point,
`legacy-disable-ack-immediate-send-failed`, which is one step of the sequence rather than a
general prefix stepper. Arm 2 therefore needs a new test-scoped seam, and that is a design
item for the plan phase, not something to improvise here.

## What this file licenses

- It does **not** license checking AC-2. Arms 1 and 2 have not been run; only the static
  enumeration behind them has.
- It does establish that the hazard is excluded on the query-reply path by `responder.active`,
  and it names the exact three sites where the literal wording is not satisfied.
- It records the **bound**: the query-reply path is one side-effect path. Output delivery,
  semantic facts and resize were **not** examined for whether they arbitrate on `active` or on
  the booleans. *Two paths are not all paths*, and here it is one.

## Correction to this file's own enumeration

The first draft of Step 3 said the booleans were assigned in **eleven** places and that *"in
every one they are assigned adjacently, as a pair"*. Recounted: **23 statements across 12
sites**, and **two of the twelve are not pairs** (`:2594` assigns `serverEnabled` alone;
`:2737`/`:2738` are mutually-exclusive conditionals).

The direction matters and is recorded rather than quietly fixed: the correction moved toward
the code being **less uniformly paired** than I first reported — that is, toward the invariant
resting on *less* convention than I claimed, which is the direction that would have made my
own conclusion look better than the evidence warranted. The safety conclusion survives, but
only because `responder.active` is nulled first at both exceptional sites; had I not
recounted, I would have been asserting a uniformity that does not exist and citing it as the
reason the invariant holds.
