# Issue #12 AC-11 — the dedup ledger across a rollback, and what its key can and cannot do

HEAD `a25ed9e366208ded22075de40d96f5cd275017f2`.

Issue AC-11 requires the rollback ordering *and* that **the dedup ledger be retained until the
epoch stabilises**. `01.ac-map.md` measured that the retention clause exists in **no** SRS
criterion (`dedup ledger` 0 hits, `epoch 안정` 0, `안정될 때까지` 0, against controls
`ledger` 9/6 and `retain` 52/27), while the checked criterion `MIG-BGSTAB-002` AC-5 orders
`기존 ACK/backlog 폐기` — *discard*. The standing brief's #10 entry says to reduce that to an
experiment rather than arbitrate the vocabulary:

> **does a rollback let a fact already settled in the pre-rollback epoch be settled again?**

This file answers the structural half of that question. It is **read from source**, not
executed, and is labelled accordingly throughout.

## The ledger exists, and it is three components, not six

`RetainedTerminalSessionState.committedFactKeys: Set<string>` is the dedup ledger.
`SessionManager.ts:8537` constructs the key:

```ts
const key = `${retained.streamEpoch}:${retained.sourceSeq}:${ordinal}`;
const duplicate = retained.committedFactKeys.has(key);
```

Issue AC-4 specifies `(sessionId, epoch, sourceSeq, offset/ordinal, factType, valueHash?)`.
The implementation uses **epoch + sourceSeq + ordinal**. `sessionId` is implied — the set is
per-session state — but `factType` and `valueHash` are **absent from the key**, which
independently confirms by implementation what `01.ac-map.md` found by specification: three of
six components, and the two missing ones occur **zero** times in the 913-row AC corpus.

Consequence, stated as a property of the key rather than as a defect: two facts of *different
types* derived at the same `(epoch, sourceSeq, ordinal)` are indistinguishable to this ledger.
Whether that is reachable depends on `factOrdinal` being incremented per detected fact —
which it is, at `:8534` — so within one record the ordinals differ and the collision does not
arise there. The gap is between *records*, and I have not probed it.

## Retention across rollback: the ledger IS carried, deliberately

`restoreRetainedLedger` (`SessionManager.ts:5964`) restores it explicitly:

```ts
retained.committedFactKeys = new Set(original.committedFactKeys);
```

So on this path — the debug-isolation rollback — the issue's retention requirement is
**implemented**, even though no criterion states it. That is the *opposite* of the direction I
expected from the AC map, and it is worth saying plainly: the specification gap is real and
the implementation gap is not, at least here.

## But the key is epoch-scoped, so retaining it may buy nothing

`streamEpoch` is the key's **first component**, and rollback raises the epoch — the same
function calls `setTerminalStreamEpoch(..., restoredStreamEpoch, 'authority-rollback')` at
`:5957`.

So if a rollback lands on a **new** epoch, every retained key is unreachable by construction:
a fact re-derived after the rollback is keyed `(newEpoch, …)` and cannot collide with
`(oldEpoch, …)`. **Retaining the ledger "until the epoch stabilises" would then be a no-op for
the property it is meant to protect.**

Two things keep this from being a finding yet, and both are stated rather than resolved:

1. `restoredStreamEpoch` is `max(liveAuthorityStreamEpoch, original.streamEpoch)`, so this
   path may restore the **same** epoch rather than a new one, in which case the retained keys
   remain live and the ledger does its job.
2. Whether a fact *should* be deduped across an epoch boundary is a genuine design question —
   a new epoch replays from a fresh snapshot, so a re-derived fact may be a legitimately new
   observation rather than a duplicate.

**So the honest disposition is: the issue's AC-11 retention clause is satisfiable only when
the rollback keeps the epoch, and the criterion does not say which case it means.** That is a
specification question the plan phase must settle, and it is the strongest argument in this
bundle for touching the SRS at all.

## A production-reachable trigger for the `03` defect, sitting on this same path

`restoreRetainedLedger` ends with a **conditional** resync (`:5980`):

```ts
if (data.pendingHeadlessOutputs.size === 0 && data.pendingRetainedResizes === 0) {
  data.nextTerminalAuthoritySourceSeq = BigInt(restoredSourceSeq);
  data.nextTerminalAuthorityStreamEpoch  = restoredStreamEpoch;
  data.nextTerminalAuthoritySnapshotSeq  = restoredSnapshotSeq;
}
```

with the comment two lines above: *"Pending reservations are not model commits."*

The guard's existence says the author knew that clobbering the reservation counter while
reservations are outstanding would be wrong. The converse is the hazard: **when pending
outputs exist, the reservation counter is left where it is while `retained.sourceSeq` is moved
to `restoredSourceSeq`.** If that move is ever *downward* relative to an outstanding
reservation in the same epoch, the next commit hits exactly the condition measured in
`03.reserved-ordinal-gap.md` — `terminal-authority-reservation-commit-mismatch` — which
**destroys the session's headless model permanently**.

**This is a hypothesis with a named observable, not a finding.** What would confirm it: a
rollback executed with `pendingHeadlessOutputs.size > 0` where `restoredSourceSeq` is below
the highest outstanding reservation in the restored epoch, followed by a commit, observed to
raise `markHeadlessDegraded(phase='write')`. What would refute it: `restoredSourceSeq` being
`max(...)` over `committedPositions` means it may never drop below a reservation's ordinal in
the same epoch — in which case the guard is complete and nothing can diverge.

I have not run it. Saying in advance what result would change my mind, per the standing
brief: **if a rollback cannot lower `retained.sourceSeq` within the restored epoch, this
hypothesis is dead**, and I should report that rather than keep it alive as a worry.

It matters because it is the first candidate that would make `03`'s defect
**production-reachable** rather than fixture-only, and because it lands on the exact path
AC-11 governs. It is the next experiment.
