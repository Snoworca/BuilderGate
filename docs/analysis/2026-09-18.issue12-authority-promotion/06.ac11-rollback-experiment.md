`05.ac11-dedup-ledger.md` was read from source and said so. This file executes it. One

## Pre-registered, before the run

- **AC-11 question:** after a rollback, can a fact already settled in the pre-rollback epoch be
  settled again? The key is `${streamEpoch}:${sourceSeq}:${ordinal}`, so **if rollback lands on
  a different epoch, every retained key is unreachable** and retention buys nothing.
- **`#106` reachability question:** does rollback move `retained.sourceSeq` **downward** while
  reservations are outstanding? That is the state `03` measured as destroying the model.
- **My stated refutation condition, written before running it:** *"if a rollback cannot lower
  `retained.sourceSeq` within the restored epoch, this hypothesis is dead, and I should report
  that rather than keep it alive as a worry."*

## Result 1 — my own `#106` hypothesis is dead, exactly as pre-registered

**`seqLowered=false` in 24 of 24 observed rollback events.** `restoredSourceSeq` is a `max`
over committed positions in the restored epoch, so it cannot drop below the current retained
position. The path I nominated as `#106`'s most promising production trigger **does not
produce the ahead-counter state.**

The guard at `:5980` is not dead code either — it was **exercised**: 2 of the 24 events ran
with `pendingOutputs=1`, where the counter was genuinely ahead (`reservedSeq=3` against
`seqAfter=2`) and the resync was correctly skipped. So the guard fires, it fires for the
reason it was written, and it holds.

Reporting this against myself, in the direction the standing brief asks for: **this is the
second correction in this lane moving the same way — toward production being more correct
than my search-derived read suggested.** `#106`'s reachability is now *more* open, not less,
because its two most promising candidates (the `try`-less enqueue, and this rollback path)
have both thinned under measurement.

## Result 2 — AC-11's property has never been exercised by any test, and could not be

**`keysBefore=0, keysAfter=0` in 24 of 24 rollback events.**

That zero is worthless without knowing the ledger can be non-empty, so the fact-commit site
was instrumented too. The two populations turn out to be **disjoint**:

| suite | fact-key additions | rollback events |
|---|---|---|
| `RetainedTerminalAuthority.test.ts` | **196** | **0** |
| `TerminalAuthorityController.test.ts` | 0 | 4 |
| `SessionManagerTerminalAuthorityDebugIsolation.test.ts` | 0 | 8 |
| `TerminalAuthorityDebugService.test.ts` | 0 | 0 |

**The suites that populate the dedup ledger never roll back. The suites that roll back never
populate it.** No committed test reaches a rollback with a non-empty ledger, so **issue AC-11's
retention clause has never been observed to hold or fail.**

Both controls fired, which is what makes the two zeroes measurements:

- the fact probe produced **196** additions with real keys — `1:1:0`, `1:1:1`, `1:1:2`, … and
  a ledger reaching **size 81** — confirming both that the probe works and that the key is the
  three-component shape `05` read from source;
- the rollback probe produced **24** events with *varying* epoch, sourceSeq and pending-output
  values, so it is not returning a constant.

This is the empty-enumeration rule applied to a safety property: *a universal claim over an
empty set is true.* Anyone asserting "the ledger survives rollback" from a green suite would
be asserting it over zero observations.

**The disposition is stronger than *covered but unowned*.** An unowned property is at least
exercised incidentally; this one is **not reachable by the corpus at all**. `05` found the
retention is *implemented* (`retained.committedFactKeys = new Set(original.committedFactKeys)`
at `:5964`) — so the code does the right thing and nothing anywhere would notice if it stopped.

## Result 3 — an unplanned observation: the epoch can move backwards

**`epochChanged=true` in 4 of 24**, and two of those four go **2 → 1**:

```
[ISSUE12-RB] epochBefore=2 epochAfter=1 epochChanged=true  seqBefore=0 seqAfter=0 …
[ISSUE12-RB] epochBefore=1 epochAfter=2 epochChanged=true  seqBefore=0 seqAfter=0 …
```

`MIG-BGSTAB-002` AC-5 — **checked** — and `REL-BGSTAB-007` AC-12 both require rollback to use
**`새 streamEpoch`**, a *new* stream epoch. An epoch decreasing is not a new epoch.

**Held at the strength the observation supports, and it is weaker than it looks:**

1. This is `restoreRetainedLedger`, the **debug-isolation restore**, whose stated semantics are
   to return to a pre-isolation snapshot — including its epoch. Restoring the original epoch
   *and* the original ledger together is internally coherent, and it is what makes the
   retained keys remain valid.
2. `restoredStreamEpoch` is `max(liveAuthorityStreamEpoch, original.streamEpoch)`. The probe
   prints `retained.streamEpoch` as "before", and **retained and live can differ** — so the
   decrease is of the *retained* field toward the live/original value, not a violation of the
   `max`.
3. The shipping production rollback path (`rollbackSession` in
   `TerminalAuthorityProductionAdapter`) was **not** instrumented here.

So this is **recorded, not reconciled**: on one rollback path, the retained epoch can decrease,
and two checked criteria say rollback uses a new epoch. Whether the criteria are about this
path is a specification question for the plan phase.

## What changes, and what this licenses

| claim | before | after |
|---|---|---|
| `#106` reachable via rollback lowering the counter | plausible candidate | **refuted, 24/24** |
| dedup ledger retained across rollback | implemented (read) | implemented, and **never exercised** (executed) |
| AC-11 retention verifiable today | unknown | **no — the corpus cannot pose the question** |
| rollback always raises the epoch | assumed | **false on this path, 4/24 changed, 2 decreased** |

- AC-11 is **not** checkable. The honest disposition is that its property is implemented and
  **unexercised**, which is a different and more actionable statement than "unverified".
- The fix this points at needs no production change: **a test that rolls back a non-empty
  ledger**, asserting the ledger's size before the rollback (so it fails rather than passes
  vacuously if the fixture ever stops populating it) and the fact's re-settlement disposition
  after. That is the `#10` repair — *assert the setup you depend on before asserting the
  property* — and it gives the property a named owner at the same time.
- **Bound:** 24 events on **one** rollback path, in four suites. The production
  `rollbackSession` path was not instrumented, and it is the one that ships.
