# Issue #12 — the reserved-ordinal-gap red, attributed by execution

HEAD `395cf49d42ae03aae6c692a7371b7be052161a91` (tree identical to `240d86a` for all
`server/src` and `frontend/src` paths).

`02.premise-table.md` recorded one substantive failure and deliberately did **not** attribute
it, marking the causal story as read-from-source and therefore discounted. This file replaces
that discount with a measurement.

## Method

Two probes were injected into production source, run, and the files then restored
**byte-identically**:

| file | sha256 before | sha256 after restore |
|---|---|---|
| `server/src/ws/WsRouter.ts` | `e2ae4af70060376e8083078d435dac7248f5aa45f53146eff83811f1123c46ae` | same |

Every scripted edit asserted its own match count before writing (2 sites for `WsRouter`,
1 each for the two `SessionManager` edits), per the standing brief's rule that a replacement
matching nothing is indistinguishable from one that succeeded. Both probes are
`process.env.ISSUE12_PROBE`-gated `console.error` lines and neither changed behaviour.

## Control: the probe fires, and it discriminates

The first control I tried **did not fire** — running the probe under a passing sibling
(`fresh legacy isolation performs a real promotion and compatibility rollback`) produced no
probe output at all, because that test never reaches either mode site. Per the standing
brief, a probe whose control produces nothing is indistinguishable from a subject that
produces nothing. So the control was replaced with the whole suite:

| observation | count |
|---|---|
| site A (`WsRouter.ts:5053`), `mode=authoritative health=healthy` | **128** |
| site B (`WsRouter.ts:5362`), `mode=authoritative health=healthy` | 24 |
| site A, **`mode=fallback health=degraded`** | **1** |

129 hits on the subject site, 128 healthy. The probe is live, it distinguishes the two
outcomes, and the degraded outcome is **unique to this one scenario across all 148 tests**.

## Measured cause

```
[ISSUE12-DEG] sid=session-ph005 phase=write
  err=Error: terminal-authority-reservation-commit-mismatch: reserved=7/2, commit=7/1
    at SessionManager.commitRetainedTerminalOutput (SessionManager.ts:8099)
    at SessionManager.applyHeadlessOutput   (SessionManager.ts:7965)
[SessionManager] Headless terminal degraded (write) for session session-ph005: …
[ISSUE12-SM] atomic sid=session-ph005 hasData=true health=degraded hasHeadless=false …
[ISSUE12]    site=A5053 mode=fallback health=degraded truncated=false dataLen=0
```

The chain, each link observed rather than inferred:

1. The test advances the reservation counter without consuming it
   (`nextTerminalAuthoritySourceSeq += 1n`), so the reservation is `7/2` while the retained
   ordinal projects `7/1`.
2. `commitRetainedTerminalOutput` (`SessionManager.ts:8096-8099`) **throws** on the mismatch.
3. The throw reaches `markHeadlessDegraded(sessionId, data, 'write', error)`, which sets
   `headlessHealth = 'degraded'`, **disposes the headless terminal and nulls it**
   (`hasHeadless=false` in the probe), and clears the snapshot cache.
4. `getAtomicRestoreSnapshot` returns `headless-degraded`, so
   `WsRouter.getRestoreAuthoritySnapshot` falls back to `getScreenSnapshot`, which yields
   `health: 'degraded'` and a zero-length body.
5. `WsRouter.ts:5053` therefore computes `mode = 'fallback'`, and the test's
   `assert.equal(snapshot.mode, 'authoritative')` fails.

So my read-derived hypothesis in `02.premise-table.md` — degraded snapshot health — was
**correct**, and is now measured. The hypothesis I had already discarded (split-transport
ineligibility) stays discarded.

## What this does and does not establish about production

**Established.** A reservation/commit ordinal mismatch is handled by **destroying the
session's authoritative headless model**, not by rejecting the one offending record. Once
that happens, every subsequent recovery snapshot for that session is `fallback`, and
degradation blocks promotion (`REL-BGSTAB-011` AC-7, `MIG-BGSTAB-002` AC-1). The blast radius
of a single ordinal accounting error is therefore the whole session, permanently.

**Not established: whether production can produce the mismatch.** The test reaches the state
by mutating a private counter directly. I looked for a path by which a reservation could be
taken and never committed, and the enumeration I swept is small enough to state exactly:

- `nextTerminalAuthoritySourceSeq` is advanced in exactly one place,
  `reserveTerminalAuthorityOrdinal` (`:4580`), called from `queueAcceptedHeadlessOutput`.
- `synchronizeTerminalAuthoritySourceOrdinal` (`:5111`) runs immediately before every
  reservation, but it only repairs a counter that is **behind** (`<`). A counter that is
  **ahead** is left alone — which is correct while reservations are genuinely in flight, and
  is also the state the test forces.
- The only site that clears `pendingHeadlessOutputs` while the session lives is
  `drainHeadlessPendingOutput` (`:8714`), and it has **exactly one caller**:
  `markHeadlessDegraded` itself, which calls
  `settleRetainedTerminalPendingOutputsBeforeDegrade` first and then **resyncs the counter on
  the next line** (`:8650`). So that path does not leak a gap.

**One candidate leak path, unverified and named as such.** In `queueAcceptedHeadlessOutput`
the reservation at `:4567` and the `terminalAuthorityController.enqueueHeadlessOutput(...)`
call at `:4570` are **not inside a `try`**. If that call throws, the counter has already been
advanced and no pending output exists to commit it. Whether any caller catches that throw and
keeps the session alive — which is what would turn an advanced counter into a persistent gap
— I have **not** measured. That is the next probe, not a claim.

**Stated bound.** This enumeration is search-derived over one identifier
(`nextTerminalAuthoritySourceSeq`) and its two neighbours, and the standing brief's rule
applies: *before writing "there is no X", state the set you searched and ask whether it is as
wide as the claim.* It is not as wide as "production cannot reach this state" — it is as wide
as "the three sites that touch this counter, plus the single queue-clearing site". So the
correct disposition today is **unknown**, not *unlikely*.

## Why this is on this lane rather than filed away

The failure mode is the `#28` shape that `MIG-BGSTAB-002`'s own 2026-09-16 Change Note
records: a gate that, once tripped, blocks promotion for the life of the session. There the
trigger was an SGR palette round-trip in the parity comparer; here it would be an ordinal
accounting divergence. Both convert a transient accounting event into a permanent loss of
server authority.

It also touches issue AC-11 directly. AC-11 requires rollback to discard `기존 ACK/backlog`
while retaining the dedup ledger. Any discard of *reserved-but-uncommitted* output is
precisely the shape that would leave the counter ahead. The rollback path was not probed
here; it is the experiment named in `01.ac-map.md`'s divergence (d), and this measurement
raises its priority rather than answering it.

## Disposition of the test itself

**The test is not vacuous and should not be relaxed.** It asserts a real property —
`checkpoint identity follows the committed authority source across reserved ordinal gaps` —
and it is red because the product does not have that property: a reserved gap does not make
the checkpoint follow the committed source, it destroys the model. Whether the right repair
is to make commit tolerate a gap, to make the mismatch a record-scoped rejection rather than
a model-scoped degradation, or to prove the state unreachable and characterize the test as
such, is a design question for the plan phase and **not** something to settle by editing the
assertion.
