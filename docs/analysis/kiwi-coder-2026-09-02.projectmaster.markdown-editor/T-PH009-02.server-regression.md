## 4. 기준선 대조의 함정 — `server/config.json5`

`git worktree add --detach` 로 만든 기준선에는 **gitignore 된 `server/config.json5` 가 없다.** 처음 대조했을 때 `.internal-core-race` 가 기준선에서 `7 tests / 0 pass / 7 fail` 로 나왔는데, 원인은 코드가 아니라 이것이었다.

```
Error: missing config_lock: ENOENT … \baseline\server\config.json5
```

`fair-readmission-closure-v3.mjs:939` 가 이 파일을 `config_lock` 종류의 입력으로 읽고, `:622` 는 그 파일이 **`!!` 상태 행을 정확히 하나** 가져야 한다고 요구한다. 워킹트리의 파일을 기준선으로 복사한 뒤 `git status --porcelain --ignored` 로 `!! server/config.json5` 한 줄만 나오는 것을 확인하고 재대조하여 §3.4 의 값을 얻었다.

**따라서 이 계열 스위트를 기준선과 대조할 때는 `server/config.json5` 를 먼저 복사해야 한다.** 그러지 않으면 기준선이 환경 문제로 더 빨갛게 나와, 워킹트리가 오히려 개선된 것처럼 보이는 거짓 대조가 만들어진다.

## 5. 두 게이트

### 5.1 `boundary-gate` 는 공허하게 통과한다 — 실측으로 확인

| 측정 | 값 |
|---|---|
| 게이트 내부 소요 (`t.diagnostic` 의 `elapsed_ms`) | **98ms** |
| 게이트 전체 wall time | 366ms |
| 게이트 exit code | **0** |
| 같은 9개 파일을 셸에서 직접 실행한 wall time | **36,265ms** |
| 같은 9개 파일을 직접 실행한 exit code | **1** (49 tests / 43 pass / 6 fail) |

**370배의 시간 차이**가 그 자체로 증거다. 게이트가 실제로 9개를 돌았다면 36초가 걸렸어야 한다.

원인은 `:35` 의 `spawnSync` 에 `env` 지정이 없어 **`NODE_TEST_CONTEXT` 를 자식에게 그대로 상속**하는 것이다. 최소 프로브로 재현했다.

```
$ NODE_TEST_CONTEXT=child node --test <closure 파일 2개>
Warning: node:test run() is being called recursively within a test file. skipping running files.
EXIT=0                                     ← 0개 실행 후 성공

$ env -u NODE_TEST_CONTEXT node --test <같은 파일 1개>
EXIT=1   (tests 6 / pass 5 / fail 1)       ← 실제로 실행되고 red
```

`admission-gate` 는 `:63` 에서 `Object.entries(process.env).filter(([key]) => !key.startsWith('NODE_TEST_'))` 로 그 변수를 걸러낸다. **그 한 줄이 두 게이트의 유일한 차이**다.

여기서 한 걸음 더 나아간 사실이 있다. 게이트가 검사하는 9개 중 **5개(베이스 파일 · `.hardening` · `.ingress` · `.strict` · `.wave`)가 개별 실행에서 red** 이고, 9개를 한 번에 돌리면 exit 1 이다. 게이트는 `assert.equal(result.status, 0)` 을 단언하므로, **재귀 가드가 실행을 삼키지 않았다면 이 게이트는 통과할 수 없었다.** 즉 이 green 은 증거가 없는 정도를 넘어 **실제 사실과 반대**다.

**`boundary-gate` 의 green 을 형제 9개에 대한 증거로 인용해서는 안 된다.**

### 5.2 `admission-gate` 는 실제로 실행하지만 118초 안에 끝나지 못한다

| 측정 | 값 |
|---|---|
| exit code | 1 |
| wall time | 118,266ms |
| `t.diagnostic` 의 `elapsed_ms` | 118,014 |
| 단언 실패 메시지 | `combined closure gate failed to launch: spawnSync … node.exe ETIMEDOUT` |

`FIXED_GATE_LIMIT_MS = 118_000` 인데 형제 21개 중 `.internal-core-race` **한 파일만으로 202초**가 걸린다(§3.4). 이 게이트는 `.internal-core-race` 의 115초 부모 타임아웃이 해소되지 않는 한 구조적으로 통과할 수 없다.

`boundary-gate` 와 달리 **이 게이트는 공허하지 않다.** 자식을 실제로 띄우고 실제로 시간이 초과되어 죽는다.

**중복 실행 주의**: `admission-gate` 는 자기 자신을 제외한 형제 **21개 전부**(`boundary-gate` 포함)를 `node --test` 로 재실행한다. §3.4 의 파일별 실행과 이 게이트를 함께 돌리면 중첩 2단계로 중복 실행된다. **§3.4 의 합계(100 tests)에 이 게이트가 내부적으로 돌린 실행분은 포함하지 않았다.**

이번 측정에서 이 게이트의 `spawnSync` 타임아웃 뒤 **고아 프로세스는 남지 않았다**(§1).

### 6.2 `WsRouterSplitHandshake` 의 진단법이 작동하지 않는다

`CLAUDE.md` 는 이 파일에 대해 "**todo 카운트와 `✖` 목록을 대조**"하라고 지시한다. **그 지시를 그대로 따르면 아무것도 잡히지 않는다.**

실측(cwd=`server/`, `npx tsx --test src/ws/WsRouterSplitHandshake.test.ts`):

| 항목 | 값 |
|---|---|
| exit code | **0** |
| 카운트 | tests 28 / pass 14 / fail 0 / todo **14** |
| 실패 절 안에서 `✖` 로 시작하는 줄 | **1개** — 절 제목 `✖ failing tests:` 뿐 |
| 실패 절 안에서 `⚠` 로 시작하는 줄 | **13개** |
| 실패 절의 `test at …` 항목 | **13개** |

**절 제목만 `✖` 이고 개별 항목은 전부 `⚠` 로 렌더링된다.** 따라서 `✖` 를 세면 1(제목)이 나오고, 제목을 빼면 0이 되어 14개의 todo 와 대조할 대상이 없다.

**작동하는 진단법**: 실패 절 안의 `test at …` 줄 수를 세거나, `⚠` 로 시작하는 줄을 센다.

깨진 13건의 내역 — 오류 종류는 `AssertionError` 11 · `TypeError` 1 · `ZodError` 1 이고, 값 불일치는 `3 !== 1` · `true !== false` · `0 !== 1` 꼴이다. 12건이 "Wave-1 production unified limitation characterization" 을, 나머지 1건이 `REL-BGSTAB-008 AC-10` 을 가리킨다.

**node 가 보고하는 todo 는 14 인데 렌더링된 목록은 13 이다.** 남은 하나는 실행 목록에도 실패 절에도 나타나지 않는다. 규명 실익이 없다고 판단하여 **불일치 사실 자체만 기록한다.**
