## 8. `tab create failed: 500` 의 경로 조사 (레인 T)

**이 절은 사실만 기록하며 수정을 제안하지 않는다.** 이 현상은 `PH-007` 의 범위 밖이고, 고치면 이번 작업의 회귀 판정이 흐려진다.

### 8.1 500 을 낼 수 있는 지점

`addTabAt` 은 `/api/sessions` 가 아니라 `POST /api/workspaces/:id/tabs` 를 호출한다 (`frontend/tests/e2e/markdown-editor-lifecycle.spec.ts:105`). 그 라우트는 `server/src/routes/workspaceRoutes.ts:98` 이고, 예외를 같은 파일 `:217` 의 `handleError` 로 넘긴다.

```ts
function handleError(res: Response, error: unknown): void {
  if (error instanceof AppError) {
    res.status(error.statusCode).json(error.toJSON());
  } else {
    console.error('[WorkspaceRoutes] Unexpected error:', error);
    res.status(500).json({ error: { code: 'INTERNAL_ERROR', ... } });
  }
}
```

`WorkspaceService.addTab`(`server/src/services/WorkspaceService.ts:548`) 이 스스로 던지는 `AppError` 는 셋뿐이며 **어느 것도 500 이 아니다.**

| 예외 | 조건 | statusCode |
|---|---|---|
| `WORKSPACE_NOT_FOUND` | `getWorkspace` 가 워크스페이스를 찾지 못함 | 404 (`errors.ts:200`) |
| `TAB_LIMIT_EXCEEDED` | 워크스페이스 탭이 `maxTabsPerWorkspace`(기본 8) 이상 | 409 (`errors.ts:202`) |
| `SESSION_LIMIT_EXCEEDED` | 전체 탭이 `maxTotalSessions`(기본 32) 이상 | 409 (`errors.ts:204`) |

**따라서 관측된 500 은 `AppError` 가 아닌 예외가 올라온 결과이며, 위 `else` 갈래를 거쳤으므로 서버가 `[WorkspaceRoutes] Unexpected error:` 를 반드시 남겼어야 한다.** §3.1 의 "서버 로그에 대응하는 오류 라인이 없다" 는 서술은 이 코드 경로와 맞지 않는다. 로그를 끝까지 보지 않았거나 검색어가 이 문구를 비껴갔을 가능성이 있다. 재현되면 `[WorkspaceRoutes] Unexpected error:` · `[WorkspaceService] Flush failed:` · `[Error]` 세 문구를 함께 찾아야 한다.

### 8.2 `AppError` 가 아닌 예외가 나올 수 있는 두 지점

레인 T 는 500 을 재현하지 못했으므로 아래는 확정된 원인이 아니라 코드에서 확인한 후보다.

**첫째, `pty.spawn`.** `SessionManager.createSession`(`server/src/services/SessionManager.ts:1246`) 이 `this.spawnPty` 를 호출하는데, 이것은 `:1201` 에서 `pty.spawn` 그 자체로 묶인다. 이 호출을 감싸는 `try` 가 그 경로에 없으므로, node-pty 가 ConPTY 생성에 실패해 던지는 평범한 `Error` 는 그대로 라우트까지 올라간다.

**둘째, `WorkspaceService.flushToDisk`.** `addTab` 은 마지막에 `await this.save(true)` 를 호출하고(`:614`), 이것이 `:1682` 의 `flushToDisk` 를 직접 기다린다. `flushToDisk` 는 `workspaces.json.tmp` 에 쓴 뒤 `fs.rename` 으로 바꿔치는데, 실패하면 `[WorkspaceService] Flush failed:` 를 남기고 그대로 다시 던진다(`:1706` 과 `:1709`). **이 메서드에는 동시 진입을 막는 장치가 없다.** `save()` 는 즉시 경로에서 `flushToDisk` 를 직접 기다리는 한편(`:1652`), 디바운스 타이머 콜백도 같은 메서드를 호출한다(`:1661`). 두 흐름이 겹치면 같은 `.tmp` 경로를 두 번 쓰고 두 번 `rename` 하게 되며, 뒤늦은 `rename` 은 대상이 이미 사라진 상태를 만난다. 디바운스 쪽 실패는 `catch` 가 삼키지만, 즉시 경로의 실패는 요청까지 올라가 500 이 된다.

### 8.3 `cleanup: {attempted N, completed 0, unverifiedSkipped N}` 이 뜻하는 것

**이 값은 500 의 원인이 아니다.** 8개 케이스가 전부 통과한 신선한 인스턴스에서도 동일하게 나타났다(§3.3).

발생 조건은 다음과 같다.

1. 세션을 만들 때 `createSessionProcessMetadata` 는 `osStartIdentity` 를 `null` 로 두고(`SessionManager.ts:6389`), 신원 확인은 `scheduleProcessStartIdentityCapture` 가 비동기로 따로 수행한다(`:1355`).
2. 그 탐침은 Windows 에서 PowerShell CIM 질의를 띄우며 예산이 `identityProbeTimeoutMs` 기본값 10초다(`schemas/config.schema.ts:93`).
3. `handleProcessStartIdentityResult` 는 결과가 도착했을 때 세션이 이미 사라졌으면 **카운터를 올리지 않고 그대로 반환한다**(`:6421`). E2E 는 탭을 만들고 3초 안에 지우므로 탐침은 매번 세션보다 늦게 끝난다. `identityCaptureSucceeded` · `identityCaptureFailed` · `identityCaptureRetried` 가 **셋 다 0** 인 것이 그 증거다.
4. `osStartIdentity` 가 `null` 인 채로 정리에 들어가면 `ProcessTreeTerminator.inspect` 가 `'Session root identity is unavailable'` 로 `skipped-unverified` 를 돌려주고(`utils/processTreeTerminator.ts:462`), `terminate` 는 `taskkill /PID <root> /T /F` 를 아예 실행하지 않는다(`:514`).

**다만 이것이 프로세스 누수를 뜻하지는 않는다.** `finalizeSession` 은 텔레메트리 기록과 별개로 `data.pty.kill()` 을 호출하며(`SessionManager.ts:6597`), 실측에서도 그렇게 나왔다.

- 21:41~21:42 에 `skipped-unverified` 로 기록된 rootPid 20개를 직후에 조회한 결과, **20개 전부 이미 종료된 상태였다.**
- 3차 실행 전후로 `conhost.exe` · `OpenConsole.exe` · `powershell.exe` · `pwsh.exe` · `cmd.exe` 의 개수를 셌고, **증가분이 모두 0 이었다** (`powershell.exe` 는 오히려 1개 줄었다).

건너뛴 것은 PTY 종료가 아니라 그 뒤의 트리 일괄 종료 단계이며, 이 워크로드에서는 `pty.kill()` 이 트리를 함께 회수했다.

### 9.1 `WsRouterSplitHandshake` 의 진단법이 작동하지 않는다

`CLAUDE.md` 는 이 파일에 대해 "todo 카운트와 `✖` 목록을 대조" 하라고 지시하지만, 그대로 따르면 아무것도 잡히지 않는다.

실측 (cwd=`server/`, `npx tsx --test src/ws/WsRouterSplitHandshake.test.ts`):

| 항목 | 값 |
|---|---|
| exit code | 0 |
| 카운트 | tests 28 / pass 14 / fail 0 / todo **14** |
| 실패 절에서 `✖` 로 시작하는 줄 | **1개** — 절 제목 `✖ failing tests:` 뿐 |
| 실패 절에서 `⚠` 로 시작하는 줄 | **13개** |
| 실패 절의 `test at …` 항목 | **13개** |

절 제목만 `✖` 이고 개별 항목은 전부 `⚠` 로 렌더링된다. 따라서 `✖` 를 세면 1(제목)이 나오고 제목을 빼면 0 이 되어, 14개의 todo 와 대조할 대상이 없다.

**작동하는 방법은 실패 절의 `test at …` 줄 수를 세거나 `⚠` 로 시작하는 줄을 세는 것이다.**

다만 node 가 보고하는 todo 는 14 인데 렌더링된 목록은 13 이다. 남은 하나는 실행 목록에도 실패 절에도 나타나지 않으며, 레인은 규명 실익이 없다고 판단해 불일치 사실만 기록했다.

### 9.2 타입 검사가 테스트 파일 82개에 닿지 않는다

이 항목은 앞의 여섯보다 범위가 크다.

- `frontend/tsconfig.json` 은 `"files": []` 이고 `references` 가 `tsconfig.editor.json` · `tsconfig.app.json` · `tsconfig.node.json` **셋뿐**이므로, `npx tsc -b` 는 **테스트 파일을 하나도 보지 않는다.**
- `frontend/tsconfig.test.json` 은 `include` 가 아니라 **`files` 허용목록**이며 **47개**만 담는다. 그중 `tests/e2e/` 는 **0개**다. 이 파일은 그 자신의 주석이 밝히듯("Deliberately NOT listed in tsconfig.json references") solution 참조에 의도적으로 등재되어 있지 않다 — 테스트 전용 타입 오류가 `npm run build` 와 CI 를 깨뜨리지 않게 하려는 선택이다.

| 대상 | 디스크 | 허용목록 | 검사 밖 |
|---|---|---|---|
| `tests/e2e/*.spec.ts` | 37 | 0 | **37** |
| `tests/unit/*.test.ts` | 92 | 47 | **45** |
| **합계** | | | **82** |

허용목록 방식이므로 **새로 만든 테스트는 명시적으로 등재하지 않는 한 영원히 검사 밖에 있다.** 다른 레인의 보고에 따르면 이번 작업에서도 등재하는 순간 숨어 있던 `TS2367` 셋이 드러났다.

따라서 `tsc -b` 가 통과했다는 것은 그 참조 셋(`src` · `src/editor` · node 설정)이 통과했다는 뜻이지, 테스트에 관한 진술이 아니다.
