- server/src/routes/workspaceRoutes.ts GET / returns getState() as JSON. server/src/index.ts:895 registers the router behind existing authMiddleware.
- frontend/src/services/api.ts:344 workspaceApi.getAll returns Promise<WorkspaceState> after authFetch; no capacity metadata validation exists.
- frontend/src/hooks/useWorkspaceManager.ts:206 receives the initial API state and has existing loading/error/mounted handling. App.tsx supplies hard-coded 10 and 8 to WorkspaceSidebar and WorkspaceMoveDialog.
- WorkspaceSidebar already uses workspaces.length >= maxWorkspaces; WorkspaceMoveDialog passes its limit to existing target eligibility logic. Keep those algorithms and visuals.
- workspaceSchema currently accepts finite numbers in 1..50 and 1..16 without .int(). Preserve fractional values and comparison behavior; do not round, clamp, reject fractions or change capacity schema while implementing this task.

## Minimum changes

1. Add a small service-owned getLimits() accessor returning a fresh object with exactly maxWorkspaces and maxTabsPerWorkspace from this.config. Do not change getState(), insert limits into persisted state, or expose config/dataPath/maxTotalSessions/secrets.
2. GET /api/workspaces returns { ...workspaceService.getState(), limits: workspaceService.getLimits() }. Existing fields and nested values remain compatible; auth middleware registration is unchanged. No new endpoint, settings hot-reload mechanism or /api/runtime-config fields.
3. Keep WorkspaceState as the disk/domain state. Add WorkspaceLimits and an API response type WorkspaceState & { limits: WorkspaceLimits } in the frontend workspace type module. Search for any equivalent reusable shape again before adding it.
4. Validate only the newly introduced limits boundary when workspaceApi.getAll decodes its successful response. Require a non-null, non-array object with exactly the two known own fields, finite numeric values in the existing ranges. Use explicit condition checks, not exceptions to branch through parsers. A small reusable parseWorkspaceLimits helper is justified only because getAll and direct tests need the same boundary; otherwise keep validation in the API function and execute it in tests.
5. Missing, partial, unknown-key, string, null, non-finite or out-of-range limits cause workspaceApi.getAll to log one targeted console.warn with a stable `invalid-workspace-limits` reason and reject with an Error carrying that reason; do not include the raw response or other configuration in the warning. The existing hook catch retains the error through getErrorMessage/setError. App currently does not render wm.error, so setting hook state alone is not sufficient observable evidence; the API warning provides an operator-visible path without adding UI. Invalidity is detected by explicit conditions before logging/rejection, not by catching a parser exception as a branch. This is not a request to broaden validation to unrelated workspace fields. Never substitute values and report the response as valid. An old server response lacking limits is explicitly unsupported by this new contract, not silently inferred as 10/8.
6. useWorkspaceManager initializes its limits state to { maxWorkspaces: 10, maxTabsPerWorkspace: 8 }, exposes it in its return type, and updates it only after successful validation/receipt while mounted. Existing initial-load failure handling remains observable; no new control lock or disabled loading policy. An invalid response leaves the initialized values in place as unconfirmed defaults and sets the existing error, rather than applying invented limits.
7. App passes wm.limits.maxWorkspaces and wm.limits.maxTabsPerWorkspace into the existing components. No CSS, icon, label, layout, modal, session-status or disk-data changes. Updating a limit changes existing capacity-dependent control behavior, as expressly required by AC-4.
8. AC-4 was narrowly amended through MCP after independent review to include existing terminal-creation controls omitted from the original inventory: App's WorkspaceTabBar.maxTabs and Sidebar's WorkspaceItem.maxTabs are also fixed at8. Pass wm.limits.maxTabsPerWorkspace to TabBar and through a typed Sidebar maxTabsPerWorkspace prop to WorkspaceItem. Preserve TabBar's independent maxSessions32 conjunction and all rendering/interaction code. This does not expose another configuration field.
