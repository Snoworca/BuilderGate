## Proposed ownership connection for independent re-review

### Existing authority and missing API

`TerminalCheckpointRuntimeState` (`terminalCheckpointRuntime.ts:83`) already owns `active`, `ready`, `disposed`, `recoveryPending`, `legacyRecoveryPending`, `checkpointDeliveryPreparationPending`, `orderedRollbackPending` and view/registration generations. Its private `activeIdentity` is installed only after an accepted start (`:1245`). `matchesLifecycle`/`matchesDrainedLifecycle` (`:586/602`) compare view generation, stream/checkpoint epochs, snapshot/retention identity, chunk count, byte total and digest; drain permits a canonical source ordinal at or beyond the starting source ordinal. Keep that matching logic in the runtime.

The View's public handle currently exposes only authority view generation, active authority and legacy-recovery pending (`TerminalView.tsx:2956`). It does not expose the full pending-state decision. More importantly, `onRestorePendingSettled?: () => void` (`:359`) is called by both legacy completion (`:2289`) and checkpoint drain (`:3513`), and Container binds it to `flushPendingGridScreenRepair` (`TerminalContainer.tsx:3817`). It is neither an identity-bearing hidden-owner completion event nor proof that hidden recovery was released. Keep that callback and its grid behavior unchanged; do not reinterpret it as authoritative completion.

### Local completion permission

Reuse the existing View runtime state through a thin read-only handle method returning its immutable state (or null when unavailable); do not create a second authority flag. Local completion is eligible only when the same mounted View/restore attempt remains current, there is no pending server data-gap owner, and the current runtime explicitly has `active=false`, `recoveryPending=false`, `legacyRecoveryPending=false`, `checkpointDeliveryPreparationPending=false`, `orderedRollbackPending=false`, `disposed=false`. Null/unavailable state cannot establish permission. Check this before local work and again after its asynchronous completion. Existing View guards at `:2327/2353` already reject local restore while active/recovering/ordered rollback; the proposed integration must respect them rather than bypass them.

An active visible resync still makes a local snapshot provisional. **No active resync alone never establishes legacy permission.** Keep the existing local replay helper's release semantics for an eligible local completion and keep another replay's barrier protected. The authoritative regression must exercise a real pending runtime/gap context, not pass an arbitrary `authoritative: true` boolean into otherwise identical helper inputs. This resolves the two test expectations by different real owners, not by changing the meaning of the same input.

### Identity-bearing checkpoint lifecycle connection

Propose one narrow in-process lifecycle notification from the existing checkpoint runtime, forwarded by View to Container, separate from `onRestorePendingSettled`. It reports accepted checkpoint start and accepted drain using existing `TerminalCheckpointLifecycleMetadata`; pending/recovery-required/disposal transitions use the existing runtime state notifications to invalidate a bound completion. This notification does not issue ACKs, allocate protocol epochs, or duplicate lifecycle validation. Start notification occurs after the runtime installs its accepted identity; drain notification occurs only after matching identity, apply-before-drain and successful drain ACK send. The View must forward drain independently of whether `restorePendingRef.current` happens to be true.

The Container's hidden recovery owner record has two stages: waiting for an authoritative start, then bound to that accepted start. Capture the actual `sessionId`, existing `sessionGenerationRef` and `wsConnectionGenerationRef`, mounted View/runtime instance, and the current pending owner record itself when accepting the start. Reuse an object reference to correlate this in-process attempt; it is not a wire ID or an invented stream/checkpoint epoch. Bind the runtime-provided view generation and full checkpoint lifecycle metadata to that record. A later start replaces that binding; a later gap invalidates it before fresh recovery is requested. Session/connection changes or runtime replacement invalidate the old record without releasing the new owner's barrier.

At drain, require the same owner record, session, captured session/connection generations and mounted runtime instance, plus the runtime-validated metadata for that accepted start. Compare view generation, stream/checkpoint epochs, snapshotSeq, oldestRetainedSeq, retentionPolicyId, chunkCount, encodedByteTotal and digest; preserve the runtime's sourceSeq rule (drained ordinal may advance). Do not compare a fresh checkpoint's epochs for equality with the old gap's checkpoint: fresh recovery can legitimately replace them. Gap view/connection identity must first be accepted through the existing dispatcher/registration boundary, and only a subsequent accepted start for that pending owner may bind completion. A delayed drain from before the gap cannot be adopted as that start.

`TerminalCheckpointLifecycleMetadata` (`terminalWriteCoordinator.ts:12`) contains no session or connection ID. Those values must come from the existing runtime's session/registration and Container's captured generations, not from fabricated metadata fields. The start/drain notification must retain the original runtime instance and bound owner correlation across the real runtime → View → Container callback path; reading only the latest Container refs at completion is insufficient. If the current adapter cannot transport this association without changing protocol ownership, stop for design revision rather than weakening the checks.

### Server gap without active legacy resync

Trusted routing input is an explicit second argument, never copied from the incoming gap: `admitHiddenDataGap(message, context: Readonly<{ sessionId: string; connectionId: string | null; viewGeneration: number | null; visibility: Readonly<{ generation: bigint; isVisible: boolean; deliveryInterestRefCount: number }> | null }>)`. Context snapshots `controlConnectionIdRef.current`, `handlers.getViewGeneration()` and `terminalDeliveryVisibilityRef.current.get(sessionId)` immediately before synchronous registry dispatch. Copy the visibility values rather than passing the mutable Map record. Registry verifies the selected session/runtime and forwards that snapshot; runtime checks it against its existing session/view registration. This is an in-process parameter, not a new wire field or authority history. Unknown connection/view rejects before any current owner mutation. The runtime instance remains the notification owner described above.

Visibility admission uses the following explicit outcomes after session/connection/view and canonical ordinal validation:

| Gap visibility versus trusted current generation | Outcome |
|---|---|
| Equal | Continue epoch-floor admission; current isVisible/interest do not cancel a server-issued committed gap. |
| Older | Also continue epoch-floor admission. A reveal or interest change increments the local generation before its publication reaches the server; delayed hidden loss must still trigger recovery for the same connection/view. Do not reject merely because the browser is now visible. |
| Future | Reject as inconsistent routing visibility, do not latch the supplied gap or advance the floor from its boundary. For an otherwise matched active runtime, use existing fail-closed recovery with its current identity (no offending boundary), preserving input/stale protection and observable diagnostics. |
| Visibility record absent | Reject as unavailable routing visibility, with the same existing-identity fail-closed behavior for an otherwise matched active runtime. Absence is not proof of no loss and cannot authorize local completion. |

An older visibility generation is distinct from an older **epoch boundary**. The former may describe outstanding loss; the latter, strictly below the runtime's current active/failed floor, is already superseded by the recovery transaction and must not reset that owner or floor. An equal epoch gap must retain the matching current barrier; an exact duplicate must not replace its start binding. A newer epoch can advance the existing failed floor and require a later checkpoint. The current checkpoint/drain readiness gate remains authoritative even when a superseded gap is rejected. Do not add a visibility-history collection, infer historical isVisible from current values, allocate epochs, or treat lastDeliveredSeq as a checkpoint identity.

Source basis: `publishTerminalDeliveryVisibility` (`WebSocketContext.tsx:707-729`) increments generation on visibility or interest changes and stores it before `flushTerminalDeliveryVisibility`; the flush sends asynchronously through the socket (`:686-703`). Server hidden delivery (`WsRouter.ts:5240-5303`) builds the gap from its issued continuity/current server visibility and queues it in fair delivery order. Browser reveal publication and server-to-browser delivery can cross; therefore current-generation equality is not a prerequisite for recovering a previously committed omission. AC-1 rejects stale updates changing the server gate; it does not require discarding an older delivered gap and violating AC-2/4/6. The runtime's existing `laterBoundary`, `failClosed` and `installFreshGeneration` govern recovery progression independently of visibility publication.

Concrete current defect in the proposed admission assumption: Context invokes the handler **before** `failSession` (`WebSocketContext.tsx:1229`). Before `ed1ca25`, registry `failSession` (`terminalCheckpointRuntime.ts:1780`) returned `handled:true` after calling the runtime even if the runtime rejected it and discarded `decision.accepted`. The current implementation exposes that decision as `recoveryAccepted`; Context does not yet consume it, and it is still not gap identity validation. Runtime `coordinatorRecoveryFailed` (`:1494`) rejects only an older view generation before calling `failClosed`; it does not establish equality of the incoming stream/checkpoint epochs. Consequently neither current ordering nor `handled:true` is proof that a server gap belongs to the current checkpoint. Keep generic `failSession` semantics for its other callers; do not widen it into an implicit admission API.

Proposed exact narrow API: runtime `admitHiddenDataGap(message: TerminalDeliveryDataGapMessage, context)` (the explicit trusted-context type defined above) returns a discriminated result `{accepted:true, duplicate:boolean}` or `{accepted:false, reason:string}`; registry routes this method to the session's registered runtime and returns its acceptance unchanged (missing runtime/capability returns rejected). It performs admission and the existing fresh-recovery transition as one synchronous operation. It is not a second parser or a general recovery-failure API.

Admission requires the message session to equal the runtime's session, the connection ID to equal Context's current controlConnectionIdRef (forwarded as trusted routing context), and the view generation to equal that registration/runtime generation. Validate required ordinals with existing canonical ordinal helpers. Reuse laterBoundary (:364) to derive the current epoch floor from failedBoundary and activeIdentity, using canonical BigInt stream/checkpoint lexicographic order. Reject a gap below that floor without mutation. An equal or newer server-issued boundary for the current registered view may request recovery; do not demand equality to activeIdentity or install its snapshot as authoritative state. Newer gap epochs are a failure floor, not a checkpoint acceptance. Snapshot/retention fields remain gap provenance and require valid types/ordinals; their equality with an older active checkpoint is not an admission condition. Never accept merely because a view number is greater or handled is true. Visibility generation is checked against the existing current browser visibility publication for this session/connection; route that value from Context's existing publication owner rather than inventing a second counter. A lower epoch floor, wrong connection/view or malformed boundary returns rejected without changing the current hidden owner, ACK flags or readiness. A newer epoch boundary is passed to existing failClosed as offendingBoundary; subsequent installFreshGeneration (:868) still requires the requested view generation and epochs strictly beyond that floor. When activeIdentity is absent but runtime recovery is already pending, use failedBoundary as the floor and allow a valid current-view gap to advance it. With neither active nor pending checkpoint authority, reject as unavailable and preserve any existing barrier; never synthesize a checkpoint identity. Context routing uses controlConnectionIdRef, terminalDeliveryVisibilityRef and current runtime/registered view, so no wire fields or independent visibility counter are added.

On first valid admission, synchronously notify the receiving View/Container of the admitted gap using the runtime instance and validated gap identity, **before** invoking `failClosed` and its outbound fresh-recovery calls. The notification invalidates the previous start binding, latches the hidden owner and blocks local completion. Then reuse `failClosed` to invalidate readiness, queue input and request fresh recovery. Its ordinary rejected return means recovery was requested, not that gap admission failed; the dedicated API returns accepted after this explicit sequence. If owner notification fails, do not report acceptance: keep runtime fail-closed recovery and propagate the observable error. The last admitted gap identity is scoped to this runtime/connection: an exact duplicate returns accepted/duplicate without another owner reset or recovery request; an admitted newer boundary while recovery is pending invalidates its bound completion before failClosed advances the floor and sends recovery; a stale gap during recovery is rejected without changing the current binding. Dispose/connection replacement clears this deduplication state along with the runtime, not the server ledger.

Context replaces only this data-gap case's handler-before-failure sequence with registry admission. It must not additionally invoke generic `failSession` or the old raw handler after admission. The new admitted-gap notification is the sole owner latch path; rejection emits the existing debug/error diagnostic and cannot call the success handler. Thus a fresh-start response cannot race ahead of owner creation through a synchronous send callback. Tests must execute the actual Context → registry → runtime → View → Container chain and distinguish `accepted:false` from `handled:true`, including duplicate, stale epoch at the same view, absent runtime/identity and notification failure. These are proposed changes requiring reviewed RED first; current code does not provide this admission API.

`WebSocketContext.tsx:1229` invokes the Container handler and then independently calls dispatcher `failSession` with the supplied view/stream/checkpoint boundary. Therefore Container must not return before protecting a current, admitted server-gap owner merely because `activeVisibleOutputResyncRef` is null. Validate the receiving session/view/connection through the existing registration/dispatcher path, latch the pending hidden owner and stale/input barrier, and let the existing dispatcher initiate fresh recovery. Do not infer successful dispatcher admission solely from receipt of a message; the new actual-callback tests must show how rejection of a stale/wrong identity leaves the current owner unchanged.

With an active legacy resync, additionally retain its browser-view-only stale marking. With none, the full-checkpoint runtime remains the recovery authority. Local snapshot success, local restore-settled/grid flush, legacy server-ready or an unrelated drain cannot clear this pending owner. Matching subsequent start/drain can complete it. Runtime absence, rejected identity, failed ACK send, disconnect or unavailable authority must preserve unresolved recovery for the affected view and surface the existing rejection/recovery-required/authority-unavailable diagnostics; they cannot turn into local success. No new automatic codec rollback or session-wide action is introduced.

Independent review must specifically accept the runtime-to-Container admission/owner correlation above before new RED. Its actual callback controls must cover a gap arriving between start and drain and between local restore begin and completion, not only helper state transitions.

## Execution order and evidence

### Runtime/registry RED slice interface

Pending recovery distinguishes installed from requested view generation. After failure of installed view7, runtime `getState().viewGeneration` remains7 while `registrationViewGeneration` advertises requested8. Gap routing must match the installed view7 and its current connection; advertised/requested8 is not yet an installed renderer or permission to accept its gap. An accepted fresh checkpoint start installs8 under the existing registration and strictly advancing epoch rules, after which view7 gaps are stale. Do not equate the two state fields in admission. This permits a newer failure boundary on the same installed view while recovery is pending without allocating another view generation in the gap API.

Missing owner callback uses the specific rejection reason `hidden-gap-owner-unavailable`; the test must first provide matching connection/view/epoch inputs so another identity rejection cannot satisfy it. Snapshot the last successfully notified gap identity by value; caller mutation of the message or nested trusted visibility context must not change deduplication of the original identity. A subsequently supplied changed epoch is separately admitted and advances the existing failure floor. No mutable caller references or history collection are needed for that record.

This slice adds only runtime/registry admission tests; View accepted-start/drain and Context routing implementation remain subsequent work. The optional runtime option is named `onHiddenDataGapAdmitted(message, context): void`, with the same typed message and trusted context as admission. Its absence rejects admission observably and enters existing fail-closed protection; it must not silently behave as a successful no-op. A thrown notification is propagated with original error identity after fail-closed protection. Admission success means validated gap plus successful owner notification, not the return from failClosed (which normally returns rejected even while installing recovery). An exact duplicate of an already successfully notified immutable gap identity does not notify again. Retain only the last such identity per runtime, not a history Map. Tests use the existing actual runtime/registry harness with that option forwarded; they require the missing actual method explicitly before invocation and never substitute a fake admission implementation.
