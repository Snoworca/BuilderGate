## Pre-correction observations at 3a0addf

- wsSendPolicy.scheduleFallback releases only the affected lane before calling the router fallback callback. releaseLane retains a released lane entry, clears queue/sent/credit and increments its release count. enqueue into it returns lane-released.
- WsRouter.createFairDeliveryScheduler.onFallback discards that session's queued fair transport, calls releaseFairDeliveryIfIdle and starts existing screen-repair snapshot recovery. There is no current helper named releaseFairDeliveryLaneForLegacyFallback.
- releaseFairDeliveryIfIdle deletes the connection scheduler only when its snapshot has no active lanes. With an active peer lane, the scheduler remains and the failed lane stays released. Normal routeSessionOutput currently ignores the fair enqueue result.
- startScreenRepairSnapshotRecovery obtains the actual restore snapshot and invokes sendSnapshotReplay; recovery uses the generated replayToken and screen-snapshot:ready. An unavailable snapshot produces an explicit reconnect-required result. Reuse the existing healthy snapshot fixture and real router handlers rather than setting recovery flags by hand.
- Existing legacy terminal-delivery:checkpoint-start/invalidate are externally accepted even though no production frontend sender was located. Their separate terminate/settled-direct behavior is not proof of the actual timeout/overflow recovery path. Do not invoke them as a substitute for the production fallback trigger.

## Interpretation boundaries

- PERF-BGSTAB-010 AC-7 allows a bounded JSON compatibility fallback. Therefore FRR-01/03 must not fail solely because successful JSON post-recovery output lacks fair identity after the last lane removes its connection scheduler. Classify that result explicitly; do not silently redefine it as fair resumption.
- With peers, suspected loss from an ignored lane-released enqueue is not established until the real trigger, successful recovery-ready and missing post-snapshot outputs are reproduced. Keep peer and last-lane controls together so an unavailable snapshot or bad harness cannot masquerade as this defect.
- Four green JSON preservation cases establish only compatibility recovery. They cannot satisfy the eventual requirement that every binary normal OUTPUT (opcode0x01) be admitted exactly once to a fair ledger before automatic source ACK. Checkpoint OUTPUT (opcode0x07) retains its separate apply/drain ACK owner.
- Do not amend thresholds, force capability acceptance, issue a new epoch arbitrarily, use JSON output inside a binary stream, add a header membership flag, or treat legacy controls as unreachable.
- If source digest prevents admission, retain that failure and use the existing three-role provenance boundary process. Do not mutate publication within a test to obtain green.
