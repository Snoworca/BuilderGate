04 모드 전환 — 트리와 목록

위 03 절의 창에서 경로 막대의 “트리 · 목록” 을 눌러 보십시오. 아래 창은 같은 것을 목록 모드로 열어 둔 것이고, 뿌리도 docs 로 한 단계 내려가 있습니다.

파일 탐색기 — 목록 모드

모순은 “모드”가 아니라 “뿌리”에 있었습니다

트리가 현재 디렉터리 하위만 본다는 것은 맞습니다. 그런데 그 제약은 현재 디렉터리가 움직일 수 있게 되면 제약이 아니게 됩니다. 그래서 고칠 곳은 뷰가 아니라 훅입니다 — useFileTree 가 가변 뿌리와 goUp() · setRoot() 를 갖습니다. 그러면 두 모드는 두 기능이 아니라 한 상태의 두 뷰가 됩니다.

  • 트리 — 뿌리 + 펼쳐 둔 자손
  • 목록 — 뿌리의 직계만
  • childrenByPath 캐시를 공유하므로 모드 전환에 서버 요청이 0건입니다
  • 펼침 상태는 뿌리가 바뀌어도 버리지 않습니다. 절대 경로라 뿌리 밖의 항목은 그리지 않을 뿐, 되돌아오면 그대로 살아 있습니다

.. 는 트리 노드가 아니라 창의 크롬입니다

보이는 모양은 요청하신 그대로 — 맨 위에 고정된 .. 행이고 눌러서 올라갑니다. 다른 것은 데이터 모델뿐입니다. 그 행에는 data-path 가 없어서 선택·클립보드·Delete 가 애초에 닿지 못합니다.

설계안이 이미 이 판단을 내려 뒀습니다. §8.1 은 서버 listDirectory 가 루트 아닌 디렉터리마다 넣어 주는 .. 항목을 훅이 일부러 걸러낸다고 적고, 이유를 “부모로 가는 일은 뿌리를 바꾸는 조작이지 자식 노드가 아니므로”라고 밝힙니다. 노드로 만들면 선택 · Ctrl+A · Shift 범위 · 컨텍스트 메뉴 · 클립보드 · Delete 여섯 곳 전부에 예외를 심어야 하고, 하나만 빠지면 .. 를 복사하거나 지우려 드는 버그가 됩니다.
덤 — 버리던 신호를 쓰게 됩니다. 걸러내던 그 서버 .. 항목이 이제 “위로 갈 수 있는가”의 답입니다. 올라갈 수 없는 자리에서는 ↑ 가 흐려집니다 (위 두 창에서 뿌리까지 올라가 보시면 됩니다). 클라이언트가 실패할 요청을 쏘지 않아도 됩니다.

편집기 좌측 패널은 트리 전용입니다

212px 폭에 수정한 날짜·크기 컬럼은 들어가지 않습니다. 모드 토글은 탐색기 창에만 둡니다. 다만 .. 는 그쪽에도 둡니다 — 설계안 §9.1 이 이미 “사용자가 트리 안에서 뿌리를 옮겼다면 그 조작을 유지한다”고 뿌리 이동을 허용하고 있습니다. 아래 05 절의 편집기 창에서 확인하실 수 있습니다.

05 편집기 창 좌측 패널 — 표면 문제가 보이는 자리

설계안 §9.1. 같은 트리가 흰 종이 옆에 섭니다. 위의 전환 버튼으로 A·B 와 C 를 번갈아 보시면 이 시안의 유일한 구조적 선택이 드러납니다.

  • 파일 조작을 지원합니다 — 우클릭 메뉴와 단축키가 탐색기 창과 같습니다. 빠지는 것은 새 탭에서 열기 하나뿐입니다(여기엔 탭이 없습니다)
  • 항상 트리 모드입니다. 목록 모드는 없습니다 — 이 폭에 날짜·크기 컬럼이 들어가지 않습니다
  • 경계를 끌어서 폭을 조절합니다. 오른쪽 가장자리를 잡고 끌어 보십시오. 상한은 창 폭의 50% 이고, 배지가 상한에 닿으면 노란색이 됩니다. 더블클릭하면 기본값(212px)으로 돌아갑니다
저장값과 렌더값을 나눕니다. 창이 좁아져 50% 상한에 걸려도 저장한 폭은 그대로라, 창을 다시 넓히면 원래 폭으로 돌아옵니다. 상한이 사용자의 설정을 덮어쓰면 창을 한 번 줄였다 키운 것만으로 폭이 영영 달라집니다.

작성일: 2026-09-12 · 2026-09-13 개정

1. 요구사항

  1. 마크다운 편집기 창의 왼쪽에 파일 트리 형식의 탐색 뷰를 붙입니다.
  2. 파일 탐색기를 독립된 모달리스 창으로 띄웁니다. 이 창은 탭으로 구분됩니다.
  3. 파일 조작(복사·이동·삭제)을 구현합니다.

2. 현재 코드가 이미 갖고 있는 것

이번에 실제로 파일을 열어서 확인한 사실입니다.

지금 보시는 것 — A

트리가 어두운 채로 흰 종이와 맞닿습니다. 창 하나 안에 두 개의 테마가 보입니다. 경계가 뚜렷해서 트리가 창에 속한 물건으로 읽히는 장점이 있고, 실제로 설계안은 트리를 창 전체의 것으로 규정합니다. 단차를 결함이 아니라 의도로 볼 여지가 있습니다.

지금 보시는 것 — B

A 와 같은 구조입니다. 단차는 그대로이고 트리 쪽이 조금 더 부드럽습니다. 행 높이 28px 라 손가락으로 누를 수 있게 되고, 선택 행의 왼쪽 강조 바 덕분에 여러 항목을 골랐을 때 어디까지 골랐는지가 A 보다 잘 읽힙니다.

지금 보시는 것 — C

트리가 종이 쪽 색으로 갈아탔습니다. 창 하나가 하나의 문서 작업 공간으로 읽히고, 탭 막대까지 같은 결이 됩니다. 값을 치른 곳은 탐색기 창과 편집기 트리가 더 이상 같은 색이 아니라는 점입니다 — 위의 03 절과 번갈아 보시면 같은 컴포넌트가 두 얼굴을 갖는 것이 보입니다.

참고 — 이미 있는 선례

벤더링된 편집기가 [data-theme="light"] 로 정확히 같은 일을 합니다 (inline-preview.css:767-811). EditorWindow.css 의 주석도 “같은 색을 두 벌 적으면 상류를 다시 들여올 때 한쪽만 움직여 조용히 어긋난다”고 적어 두었습니다.

그래서 C 를 고르면 물어야 할 것 — 새 --bg-* 토큰과 --atomic-editor-* 를 하나로 합칠지, 나란히 둘지. 합치면 상류 재도입이 어려워지고, 나란히 두면 색이 두 벌 남습니다.

07 진행 표시 세 단계

설계안 §4. 진행은 세 자리에 뜹니다 — 탐색기 창 하단의 진행 줄(§4.4, 03 절 창에서 보실 수 있습니다), 앱 하단 상태바, 그리고 상태바를 눌러 여는 우하단 알림창. 셋 다 작업이 없을 때 자리를 차지하지 않습니다.

진행이 앱 전역이고 질문이 창 안인 이유는 작업이 창보다 오래 살기 때문입니다 — §3.5 가 작업을 브라우저 연결이 아니라 세션에 매답니다. 탐색기 창을 닫아도 복사는 계속 돌고, 창 안 진행 줄이 사라진 자리를 상태바가 이어받습니다.
