## A. 운영 결함

실측으로 확인된 것만 싣는다.

### A1. 데몬 로그 로테이션 부재

- **사실**: `runtime/buildergate-daemon.log` = `3,391,752,904` bytes (2026-08-29 실측). `runtime/buildergate-sentinel.log` = 82,366 bytes.
- **영향**: 디스크를 계속 소모한다. 상한도 회전도 없다.
- **완료 조건**: 로그 크기 상한과 회전이 동작하고, 회전이 실행 중인 데몬의 기록을 끊지 않는다는 것을 테스트로 고정한다.

### A2. resize 입력 검증 부재

- **사실**: `server/src/utils/constants.ts:133` `MAX_COLS: 500`, `:137` `MAX_ROWS: 200` 이 정의만 되어 있고 **사용처가 0건**이다.
- **경로**: `WsRouter.handleResize` → `SessionManager.resize` → `data.pty.resize(cols, rows)` 가 치수 검증 없이 통과한다. 저장소의 유일한 `cols <= 0` 가드는 `WsRouter.ts:4457` 인데 그것은 screen-repair 라는 **다른 메시지 타입**의 경로다.
- **완료 조건**: 범위를 벗어난 resize 가 PTY 에 도달하지 않고, 정상 범위는 그대로 통과한다. 경계값(0, 1, MAX, MAX+1) 테스트 포함.
- **주의**: `WsRouter.ts` 는 fair-scheduler provenance 핀 파일이다. 그곳을 수정하면 authority generation 재게시가 필요하다(절차는 §부록).

### A3. E2E 워크스페이스 누수

- **사실**: 워크스페이스 정원은 `maxLiveWorkspaces: 10`. 2026-08-30 시점 10개 전부가 E2E 잔재였다 — `Codexp-Recovery-`, `PH5A-`, `KBD-E2E-`, `W3-SOLE-WRITER-`, `PW-RL-`, `SwitchTarget-`, `AuthoritySource-`.
- **영향**: 정원이 차면 `POST /api/workspaces` 가 409, 이어서 500 을 낸다. 무관한 스펙이 제품 버그처럼 빨개진다.
- **완료 조건**: 워크스페이스를 만드는 스펙이 자기 산출물을 정리한다. 정리는 실패 경로에서도 실행되어야 한다.

### A4. 세션 정리의 미검증 스킵

- **배경**: `cleanupStatus: skipped-unverified` 의 원인이었던 신원조회 조기 포기는 `5918146` 에서 고쳤다(재시도를 세션 종료까지 지속).
- **남은 것**: 실제 운영에서 `unverifiedSkipped` 가 0 이 되는지 **미확인**이다. 마지막 관측치는 수정 전 값(`attempted=7 completed=0 unverifiedSkipped=7`, `identityCaptureSucceeded=0`)이다.
- **완료 조건**: 세션을 만들고 지운 뒤 `/api/sessions/telemetry` 의 `cleanup.completed` 가 `attempted` 와 같고 `unverifiedSkipped` 가 0 임을 실측한다.
