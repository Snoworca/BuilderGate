## Ownership contract

1. Only a successful, real `POST /api/workspaces` response from the configured `https://localhost:2222` origin, with a validated nonempty returned `id`, establishes ownership. An ID from GET, a name/prefix, localStorage, a baseline difference, request body or failed/malformed POST does not. UI-generated POST responses follow the same rule. Never infer a missing ID after a transport failure; report the unresolved creation without guessing cleanup candidates.
2. Each run gets a newly created registry directory and run ID. Each test attempt and browser context gets an owner ID, including retry identity. A test/context cleanup may delete only IDs assigned to that owner. Another test's successful response does not grant deletion authority, even within the same run. Global teardown can process remaining run-owned IDs only after every worker and response-write drain has completed.
3. Register the workspace before subsequent tab creation or setup can fail. API helpers must await registration before returning the created ID. Browser response handlers track their asynchronous response-body reads and persistence promises. At test teardown, stop issuing creation work, await already tracked POST requests and their response writes, then clean that owner before closing its context. Do not detach handlers or close the context while the response body is still needed. Request failure, drain failure or persistence failure is observable and blocks successful cleanup reporting.
4. Preserve failed DELETE IDs and registry evidence. Count successful deletion, already absent (404 or authenticated validated list absence), refused/unowned and failed separately. Never report attempts as removed. Authentication failure, non-OK/malformed list response or corrupt registry fails closed: no DELETE from that cleanup pass, retain records, and fail/report the cleanup rather than replacing unknown state with an empty set. Read and validate the complete applicable registry and list before issuing any DELETE. A later network/DELETE failure retains the affected record and fails the pass; earlier successful deletions remain honestly recorded.
5. No stale previous-run cleanup by default. No automatic name-based quota recovery. A quota error remains a useful explicit precondition failure. Cleanup of already finished resources owned by this exact attempt may occur through the same ownership helper; it must not evict an active sibling/context resource. Product UI, API shapes, workspace limits and auth behavior stay unchanged.

## Minimal implementation shape

- Replace the difference-based implementation in `frontend/tests/e2e/workspaceLeakGuard.ts`, retaining the global setup module location and `workspaceTeardown.ts` wiring. Setup authenticates and validates the workspace list as readiness evidence, not ownership; it creates a unique empty run registry only after successful preflight. Publish its absolute path/run ID to workers through the existing setup environment pattern, replacing the old baseline file semantics. Do not reuse `.workspace-baseline.json` contents as IDs to adopt.
- Use one immutable UTF-8 record per returned ID in that run directory, containing `{runId, ownerId, workspaceId}`. Derive a safe filename from a digest of the ID, never interpolate raw IDs as filesystem paths. Exclusive file creation avoids cross-worker whole-registry read/modify/write loss. A repeated same-ID/same-owner record is idempotent; a different owner or malformed existing record is a conflict and fails closed. A partial write is retained as corrupt evidence, never treated as empty. Only remove that record after confirmed deletion/absence. No recursive deletion of a registry containing unresolved entries.
- Add `frontend/tests/e2e/workspaceOwnershipFixture.ts` as a thin extension of Playwright's existing `test`, attaching context request/response observation before `use`. Export the owned cleanup and API creation adapter from the existing guard module; avoid a second ownership store. Live workspace-creating specs import this fixture. Extra `browser.newContext` and direct `APIRequestContext` creation must explicitly use the fixture's context/API adapter so ownership exists before any request. Context response events cover real UI and `page.evaluate` fetches; they do not observe independent APIRequestContext calls, which must register returned IDs directly.
- Do not enable ownership collection for mocked workspace API specs. Route-fulfilled or service-worker synthetic responses must never become real DELETE authority. Inventory each live fixture context for matching workspace mocks; reject unsupported mixed mocked/live creation rather than assuming a response is real. Keep existing mock-only auth/settings tests separate. Add a source contract to catch a new workspace creator bypassing the fixture/API adapter.
- Make every explicit workspace DELETE delegate to the owner-checked helper, including partial-setup catch blocks and localStorage-based afterEach paths. Keep additional existing owner-token checks as diagnostics if useful, but names/tokens alone never confer ownership. Teardown uses the run registry after all workers; per-test helpers use only their owner records. A shared run-wide afterEach sweep is forbidden.
- Preserve exact 2222 browser validation and existing B1 safe external server ownership. Do not let a new ownership fixture start/stop the server. Existing Playwright webServer behavior needs the separate B1 lifecycle gate before any real E2E invocation.

## Core API contract for test-first implementation

The implementation stays in `frontend/tests/e2e/workspaceLeakGuard.ts`. The following exports describe the implemented foundation's shared fixture/core contract; the checkpoint above does not establish spec adoption or browser coverage:

```ts
type RegistryOptions = {
  registryPath: string; runId: string; baseUrl: string;
  fetch?: typeof globalThis.fetch;
};
recordWorkspaceBaseline(options?: RegistryOptions): Promise<void>;
registerWorkspaceCreation(options: RegistryOptions & {
  ownerId: string;
  proof: { url: string; method: string; status: number; body: unknown };
}): Promise<{ workspaceId: string; registered: boolean }>;
cleanupOwnedWorkspaces(options: RegistryOptions & { ownerId?: string }): Promise<{
  deleted: string[]; absent: string[];
  failed: Array<{ workspaceId: string; reason: string }>;
}>;
removeWorkspacesCreatedDuringRun(options?: RegistryOptions): Promise<void>;
deleteOwnedWorkspace(options: RegistryOptions & {
  ownerId: string; workspaceId: string;
}): Promise<WorkspaceCleanupResult>;
validateWorkspaceOwner(options: RegistryOptions & {
  ownerId: string;
}): Promise<RegistryOptions>;
```

`recordWorkspaceBaseline` keeps its existing hook name but initializes a new registry after successful auth/list preflight, never grants baseline ownership. Explicit options support controlled unit fetch and unique Temp roots. Playwright passes FullConfig to default hooks: retain separate default setup/teardown wrappers that call the named functions without overrides; never treat FullConfig as RegistryOptions, and reject invalid explicitly supplied overrides rather than silently falling back. Hook defaults read `BUILDERGATE_E2E_RUN_DIR`, `BUILDERGATE_E2E_RUN_ID`, and the fixed approved base URL; setup may allocate a fresh owned directory/run ID when absent and publishes both for worker inheritance. Teardown with missing identity must report unavailable ownership and issue no DELETE; it must not allocate a new registry. `BUILDERGATE_E2E_BASELINE` does not become an ownership registry.

Creation proof is the actual response adapter's data: exact configured origin/path `/api/workspaces`, method POST, status 201, and direct response `body.id` (not `{workspace:{id}}`). Invalid proofs reject without a record. Names are optional irrelevant response data. `registered=false` means an identical already-published same-owner record; a conflicting owner rejects. Callers may not synthesize proof from a known ID. Tests use synthetic responses only with controlled fetch/storage, never as live cleanup authority.

The run root contains `run.json` with `{runId, baseUrl}` and `records/<sha256(workspaceId)>.json` immutable `{runId, ownerId, workspaceId}` records. Validate the entire applicable registry before cleanup. Publish a complete UTF-8 temporary record in the same directory and atomically create the final name without replacement (for example exclusive hard-link publication followed by removal of that owned temporary link). A loser of an EEXIST race reads only the fully published final record; ordinary rename-overwrite is insufficient. Retain incomplete/pending evidence on write failure; a pending/corrupt record at cleanup fails closed. Cleanup occurs after writer drains, not concurrently with publication.

`cleanupOwnedWorkspaces` returns confirmed deleted/absent IDs and per-ID failures; successful/absent records are removed, failed records remain. Auth/list/registry validation errors reject before any DELETE. The global wrapper invokes it without ownerId after all workers and throws if failures remain, retaining their records. The core unit suite is `frontend/tests/unit/workspaceOwnershipRegistry.test.ts`; the existing three setup/teardown regression tests remain separate and unchanged.

`deleteOwnedWorkspace` is the new single-ID operation, returning the same deleted/absent/failed result. Require a nonempty ownerId and workspaceId and matching published ownership. Missing/invalid/unowned/sibling IDs reject; never fall back to owner-wide or global cleanup. Deleting X must preserve Y even when X and Y have the same owner. Reuse core validation/deletion logic without broadening deletion scope.

`validateWorkspaceOwner` reuses options/run-metadata/owner validation without mutation or network and returns validated RegistryOptions. Registration, the API adapter and the automatic fixture share it. The adapter must await it before issuing POST; the automatic fixture must await it before `use` can run UI creation. Invalid/foreign options, empty owner and mismatched persisted run metadata therefore cause zero POST/use calls and leave the registry unchanged. Post-response registration checks remain necessary; preflight does not replace them.

## Thin fixture API and response provenance

Implemented foundation exports from `frontend/tests/e2e/workspaceOwnershipFixture.ts`:

```ts
attachWorkspaceOwnership(context: BrowserContext, registry: RegistryOptions, ownerId: string): {
  drain(): Promise<void>;
  cleanup(): Promise<WorkspaceCleanupResult>;
  deleteWorkspace(id: string): Promise<WorkspaceCleanupResult>;
  dispose(): Promise<void>;
};
deleteOwnedWorkspaceForContext(context: BrowserContext, id: string): Promise<WorkspaceCleanupResult>;
createOwnedWorkspaceViaApi(
  request: Pick<APIRequestContext, 'post'>, registry: RegistryOptions,
  ownerId: string, options: Parameters<APIRequestContext['post']>[1],
): Promise<{ id: string; [key: string]: unknown }>;
export const test; // base.extend with automatic workspaceOwnership fixture
```

The API adapter passes the caller's complete POST options unchanged (including explicit Authorization headers and data), performs the actual `request.post` at the approved workspace URL, validates response URL/status/direct body, awaits core registration, then returns that body. It neither guesses a bearer token nor assumes browser localStorage becomes APIRequestContext authentication. It must not offer a raw-ID registration convenience. Browser tracking uses the real context `request`, `response`, `requestfinished`, `requestfailed` events and Playwright response methods, not an invented route-fulfilled flag. For matching workspace creation, require `fromServiceWorker() === false` and non-null `serverAddr()` showing loopback at port2222 before consuming POST201 as live authority. A synthetic fulfilled response with no server address cannot establish ownership; unexpected missing address in a supported browser fails closed rather than guessing. Prove these real browser metadata assumptions in the later gated browser control before broad E2E; unit ports are not that proof.

Nonmatching origin/method/path events are ignored. Matching failed/malformed/synthetic responses and request failures remain drain errors with no record. Tracking begins on request, not only on response, so cleanup cannot pass while an already-issued creation has no response yet. Keep body and core persistence promises in the same drain. `cleanup` awaits drain then calls core with exactly that owner. `dispose` awaits drain before removing listeners; an error is reported and listeners are released safely without claiming a successful cleanup. Requests must not be newly initiated once teardown starts; captured in-flight requests still finish and their response writes must settle.

The automatic `workspaceOwnership` fixture installs tracking before `use`, awaits owner cleanup after use, and disposes listeners in finally. Cleanup with nonempty failed results rejects the fixture even when its test body succeeded. If both test body and cleanup fail, preserve both in an AggregateError; do not mask one with the other. The captured fixture tests require record retention and listener removal on failure. It reads only the setup-published run options and uses a fresh owner identity for each test/retry/context. Contexts outside the default fixture use explicit attachment and independent owner IDs. `createOwnedWorkspaceViaApi` and browser observers must not both register the same HTTP request under different owners. Mock-only specs continue importing the base Playwright fixture. No production import, custom browser implementation or second registry is introduced.

`tracker.deleteWorkspace(id)` drains pending proof writes then delegates only to core `deleteOwnedWorkspace` with the tracker's fixed owner. `deleteOwnedWorkspaceForContext(context,id)` resolves the already attached tracker and delegates to that operation; an unattached/disposed context rejects instead of discovering authority from names or IDs. A weak context-to-tracker association is sufficient, not another persistent registry. Live origin checks accept IPv4 loopback and IPv6 `::1` at2222; non-loopback:2222 and loopback:other-port fail closed and never register.

Reuse the existing public pure `isLoopbackIp` export from `server/src/utils/bootstrapAccessPolicy.ts` for server-address validation. Its type-only dependency has no application startup side effects. The fixture imports `../../../server/src/utils/bootstrapAccessPolicy.ts`; the unit loader permits exactly that real module through nativeRequire, rather than stubbing it or duplicating a private UI validator. Existing IPv4/IPv6 positive and remote/port negative assertions remain unchanged.

## Optional diagnostic details during validation

REL-BGSTAB-001 also requires reliable failure reporting. Before the correction, the promotion spec dereferenced optional event details in three readiness callbacks and two diagnostic projections. The correction now has independent8/8 passing tests. Missing details must not make a readiness predicate pass or replace the original validation failure with a secondary TypeError.

- For the three readiness callbacks, a missing latest gate or missing details returns false. Do not search an older ready event as a fallback; retain all existing input-ready, capture, barrier, focus and grid-repair conditions.
- For client/server diagnostic projections, retain an event whose details are absent and record `details: null`. Preserve the existing selected fields and protocol/error reasons when details are present. Do not filter out incomplete events or fabricate successful values.
- Preserve the final failure builder's original error message and include the diagnostic observation. Exercise the actual source callbacks/projections and error expression with absent, empty and valid details before changing the spec. Browser serialization boundaries and different client/server projections do not justify a new shared helper for these few optional accesses.
- These changes are limited to test diagnostics. They do not change production event schemas, terminal readiness or protocol behavior. Existing unused declarations remain preserved while the separate deletion question is pending.
