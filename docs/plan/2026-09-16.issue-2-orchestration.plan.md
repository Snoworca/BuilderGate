### wave-4 산출 — 요구사항이 없던 구간

#15–#18 은 앞의 것들과 달리 **실제 미구현 기능**이었고, `docs/spec/` 에 요구사항이 아예 없었다. 그래서 사용자 지시의 1단계(`/kiwi-srs`)로 돌아가 다섯 요구사항을 신설했다 — PERF-BGSTAB-013(#15), FR-BGSTAB-029(#16), OBS-BGSTAB-010(#17), REL-BGSTAB-028·SEC-BGSTAB-001(#18 분할). #7–#14 가 그 단계를 건너뛴 것은 요구사항이 이미 있었기 때문이지 단계가 불필요해서가 아니었다.

**일곱 번째 변종 — 계측기가 자기가 보고할 현상을 만든다.** #15 AC-3 의 "간헐적 입력 전달 실패"는 제품 결함이 아니라, e2e spec 초안이 실행마다 탭을 누수시켜 residency 상한에 닿은 결과였다. 앞의 여섯은 정적인 시스템에 대해 거짓말하는 계측기였고, 이것은 현상 자체를 만들어낸다.

> **측정을 반복했을 때 결과가 단조롭게 움직이면, 제품보다 측정을 먼저 의심한다.**

실용 형태: **가장 현실적인 probe 가 아니라 설정이 가장 적게 필요한 probe 를 고른다.** 재작성된 spec 은 세션을 만들지도 입력을 보내지도 않는다 — 남길 상태가 없으면 누수도 없다.

**한 층 위의 같은 결함**: 오케스트레이터가 띄운 2222 검증 서버가 모놀리식 러너의 `SEC-MCP-001 AC-6` 을 `EADDRINUSE` 로 떨어뜨렸다(540/541). **공유 검증 호스트 자체가 변수이며, 그것을 바꾼 사람이 거기 대고 측정하는 사람들에게 알릴 책임을 진다.**

**봉인은 재봉인 가능해야 통제다.** #18 배선이 `WsRouter.ts`(fair-scheduler provenance 의 봉인 입력 6개 중 하나)를 건드려 69개 중 37개가 red 가 되었다. 회피 경로 둘(`SessionInputGateway` 에 은닉, `metadata` 필드로 id 밀반입)을 거부하고 재봉인했다. 재봉인 불가능한 봉인은 통제가 아니라 동결이며, 봉인의 목적은 변경 금지가 아니라 **변경이 눈치채이지 않고 일어나지 않게** 하는 것이다. 재발행은 **이전 세대의 워크로드를 그 세대 산출물에서 복구**해 동일 조건으로 수행했다 — 새 파라미터로 돌렸다면 결과 변화가 코드 변경 때문인지 워크로드 때문인지 귀속 불가능했다. 기존 세대는 수정·삭제 없이 새 세대를 추가하고 포인터만 재지정했다.

**digest 는 두 곳에 산다.** 재봉인 후에도 `FairSchedulerSourceProvenanceRuntime`·`FairSchedulerEvidenceBundleRuntime` 이 red 로 남는데, 소스 트리가 아니라 `dist` provenance 를 읽기 때문이다. `npm run build` 가 재봉인 뒤에 와야 한다. 실패 텍스트는 둘 중 어느 것도 말하지 않는다.

**OSC52 결정 (SEC-BGSTAB-001)**: 읽기 영구 금지(설정 항목 없음) · 쓰기 기본 허용 + 레일 · 100KB 거부 · 프롬프트 없음 · `terminal.osc52.allowWrite` 하나. 읽기 금지의 근거는 응답이 PTY **입력** 채널로 주입된다는 것과, 그것을 막을 브라우저 권한이 오리진 범위라 세션별 게이트가 **구조적으로 불가능**하다는 것이다. 현재의 안전은 결정이 아니라 우연이다 — xterm.js 6 이 OSC 52 핸들러를 등록하지 않고(등록 목록: 0,1,2,4,8,10,11,12,104,110,111,112) 애드온이 미설치일 뿐이라, `@xterm/addon-clipboard` 추가 한 번이면 읽기·쓰기가 함께 켜진다.

**요구사항 안에 두 종류의 규칙이 산다.** 읽기 금지는 보안 결정이라 성능·사용성 논거에 면역이고, 쓰기 기본값·상한·프롬프트 부재는 그 논거로 정해졌다. 변경 노트에 비대칭을 명시하지 않으면, 새 방침을 선의로 적용하는 독자가 읽기도 협상 가능하다고 결론짓는다.

### 검증 인프라 수리 산출 — 분류가 둘이 아니라 셋이었다

이 에픽은 결함을 두 가지로 세어 왔다. 제품 결함과, 그것을 검증하는 표면의 결함. **셋째가 있다.**

**검사가 적극적으로 틀린 결론을 만들어내는 결함.** 구별점은 "보기 어렵다" 가 아니다. 앞의 두 분류는 주의 깊은 독자라면 공백을 볼 수 있다. 여기서는 코드를 **정확히 읽을수록 틀린 결론에 도달한다.**

실측된 두 사례:

| | 관측된 증상 | 검사가 만들어낸 결론 | 실제 |
|---|---|---|---|

### Wave 2 #10 산출 — 처음으로 프로덕션이 무게중심이었다

앞선 세 레인과 달리 결함이 검증 표면이 아니라 **코드**에 있었다. rollback 후 바이트·청크 캡이 도달 불가능해져 **선언된 1 MiB 에 78.1 MiB 를 수용**했고, 이는 `REL-BGSTAB-007` AC-12 의 *"new admission 중지"* 에 대한 **stable 기준 직접 위반**이다.

`live` lane 은 멈추긴 했으나 **바이트 캡이 아니라 settlement ledger 엔트리 개수** 때문이었다 — *"멈추는가?"* 만 본 사람은 양쪽을 통과시켰을 것이다.

| 규칙 | 근거 |
|---|---|
| **회계를 추가하지 않는 수정을 골라라** | 청크 캡을 먼저 강제하면 큐가 유계가 되어 바이트 합이 유계 큐 위에서 돈다. 큐 변이 지점 20곳에 카운터를 심지 않았고, 그만큼 후속 레인이 틀릴 자리가 없다 |
| **RED 에는 음성 대조군이 필요하다** | 없으면 **무조건 deferral 하는 구현**이 실패 arm 을 전부 만족시킨다. 실패 arm 은 결함의 존재를, 음성 대조군은 **통과하는 구현의 공간이 의도보다 넓지 않음**을 보인다 |
| **생존한 변이의 원인은 둘이다** | 약한 테스트이거나 **경로에 닿지 않은 변이**. 관측 로그가 변이 전과 바이트 동일하면 후자다. **자기에게 불리한 결론도 대조군이 발화했어야 한다** |
| **변이는 시나리오 오류도 잡는다** | 술어 오류는 단언문을 읽으면 보이지만, 시나리오 오류는 **이름이 여전히 의도를 서술**하므로 읽어서는 알 수 없다 |
| **덮였으나 소유자 없음** | 네 번째 처분. 커버리지 측정에서는 "덮임"과 같아 보이고 유지보수 하에서는 "안 덮임"처럼 행동한다 |
| **명세 분쟁은 측정 가능한 질문으로 환원하라** | *"용어 X 가 기전 Y 를 포함하는가"* 를 *"X 가 막으려는 위험이 Y 에 있는가"* 로. 앞은 논쟁이고 뒤는 실험이다 |
| **방법을 고쳐도 편향은 서술에 남는다** | 레인이 검색에서 실행으로 바꾼 뒤에도 *"설정 해석에 부재"* 를 *"전혀 배선되지 않음"* 으로 적었고, **그 간극이 범위 문제 전체**였다 |
