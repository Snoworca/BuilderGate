# Binary rollback contract proposal

Requirement scope: IR-BGSTAB-001 AC-3/4/11, FR-BGSTAB-024 AC-5, MIG-BGSTAB-002 AC-5 and MIG-BGSTAB-004 AC-3. Mode sdd. This proposal follows the [source investigation](../research/2026-09-08.binary-rollback-integration-gaps.md). It is not an approved implementation contract and does not change the SRS.

## Required owner decision

A clarification is pending: when one consumer of a shared session fails, may healthy consumers perform a lossless new-epoch checkpoint synchronization without closing their sockets, stopping the PTY or losing output? IR001 AC-3 fixes encoding within the session's epoch, while FR024 AC-5 prohibits interrupting other clients. The permitted meaning and bounds of a healthy consumer's transition must be explicit before implementing it. No answer is inferred from elapsed time.

Also distinguish initial JSON negotiation decline from failure of an established binary generation. Inventory the actual old encoding, channel/session/view membership and existing stream before deciding whether a transition is required. Do not implement an exception to AC-4 merely because it is easier to pass.

## Recommended ownership direction, pending integration proof

- Reuse SessionManager's existing `TerminalStreamEpochLedger` for wire-epoch allocation. Do not add another allocator or treat a group codec counter as a uint64 source epoch.
- Preserve each already reserved output tuple. Commit a new source epoch only at a proven boundary after the old finite prefix is settled or covered by the recovery checkpoint; do not retag pending bytes while flushing them.
- Authority transition state and its responder/lease identities need an explicit relationship to the issued source epoch. A codec failure does not by itself prove that authority ownership should reverse.
- Group `codecEpoch` remains an internal codec-generation fence. A session-specific transition must not invalidate unrelated sessions' queued frames.

The current `beginRollback` requires server authority and affects frozen views. It cannot be called indiscriminately for legacy authority, an in-progress transition or an unknown affected session. Preserve explicit unavailable/rejected branches while designing the compatible recovery path.

## Existing transport signal candidate

`WebSocketContext.tsx:1758–1772` already exposes `requestReconnect(reason)` using close4001. `TerminalContainer` also uses this for ordinary output recovery, so code4001 alone is not a binary-failure signal. A bounded fixed ASCII prefix plus an existing fatal decoder code is a candidate for server classification, not a selected new protocol contract.

Browser `WebSocket.close` accepts an explicitly supplied code only if it is1000 or3000–4999, and restricts the UTF-8 reason to123 bytes. Browser code cannot directly call close1002. An ASCII-only bounded signal can satisfy the byte limit without treating123 characters as123 bytes. See the [WHATWG close algorithm](https://websockets.spec.whatwg.org/#dom-websocket-close).

Necessary conditions before adopting this candidate:

1. Exact reason grammar, a known-code allowlist and the existing `rejectionGrade` must all agree. Keep `unknown-channel`, `payload-limit-exceeded` and `prologue-domain-violation` scoped; do not turn their recovery into a connection fault.
2. Treat the reason as a client assertion, not authority. Resolve authenticated socket/group/current generation and affected membership from server-owned state **before** `handleDisconnect` removes it. Never accept a client-selected session or new epoch from the reason.
3. Distinguish ordinary reconnect, malformed/oversized reasons, stale reports and repeated reports of the same generation. Do not grant rollback rights from the close code alone.
4. Fence frames and old callbacks from the failed connection generation. Preserve already accepted prefix/write-completion and exactly-once credit accounting; `requestReconnect() === true` is not rollback completion.
5. Account for close-frame loss and reconnect loops. Signal delivery is not guaranteed, so the recovery/admission design must remain correct if the reason is not received.

The server currently discards close code/reason at `WsRouter.ts:1771`; adding an interpretation is new behavior requiring TDD. Neither inventing a sixth binary negotiation type nor abusing the unknown-channel request is part of this proposal.

## Single recovery transaction

A single production entry should normalize the four required triggers and resolve server-owned affected groups/sessions/views. The name and exact API remain to be finalized. Every trigger's actual caller must be covered by a static no-bypass contract plus behavioral tests.

The transaction needs: generation validation and duplicate coalescing; targeted admission closure while PTY/model collection remains bounded; a finite old prefix; one issued epoch; exactly-once old queue/credit/ACK settlement; a fresh checkpoint with actual apply/drain completion; ordered post-checkpoint output; and admission reopening. Existing checkpoint/authority paths should supply these operations where their preconditions hold. A disconnected group may not block healthy peers indefinitely.

Fatal framing may make its header/channel/session untrustworthy. Scope selection must use server-owned connection membership, not a guessed failing frame identity. If several sessions share that group, their transition/isolation contract must be explicit.

Full default rollback must retain MIG004 AC-3's ordered MIG002 operations inside the same entry. A codec-only repair may not silently become a second authority rollback implementation or skip an applicable required operation. Authority legacy/server/promoting/rolling-back states need separate preconditions and convergence into this transaction, not parallel competing transactions.

## Before RED tests prescribe new behavior

- Resolve the owner decision above and align the SRS contract without narrowing the full objective.
- Freeze the epoch/admission boundary with the brought-forward P9 all-consumer/fair-membership work. Existing responder capability quorum is insufficient as codec agreement.
- Define initial decline, established failure, each authority state, healthy shared consumers and unrelated sessions in the test matrix.
- Define the valid fatal signal, stale callback fencing, duplicate trigger behavior and lost-signal recovery.
- Select actual supported old-build artifacts and prove distinct source identity plus fresh compatibility checkpoint/tail ordering across restart. An empty channel table or a new socket is insufficient.

Local artifact discovery has not established a supported rollback release/artifact pair. The local `0.5.4` tag resolves to commit `e584c2a4f2216ba689b7f77b8352ac3cde9ac171`; its `server/src/schemas/config.schema.ts` already declares all four terminalWireFormat values. Thus the earlier research's pre-key strict-schema hazard must not be generalized to every older build. This source observation is not an executable release artifact, full configuration acceptance or restart recovery proof. Select and hash the actual supported distribution before that test; do not label an arbitrary old commit as the supported rollback version.
