## 1. 요구사항

1. 마크다운 편집기 창의 왼쪽에 파일 트리 형식의 탐색 뷰를 붙입니다.
2. 파일 탐색기를 독립된 모달리스 창으로 띄웁니다. 이 창은 탭으로 구분됩니다.
3. 파일 조작(복사·이동·삭제)을 구현합니다. `Ctrl+C`·`Ctrl+X`·`Ctrl+V`·`Delete` 단축키를 지원합니다.
4. 모바일에서는 단축키 대신 눌러서 실행하는 버튼을 제공합니다.
5. 파일 조작에 대한 컨텍스트 메뉴를 제공합니다.
6. 복사·이동·삭제는 비동기로 진행하고, 하단 상태바에 막대 프로그레스로 진행 상황을 보여줍니다.
7. 작업이 여러 개이면 현재 무슨 작업 중인지 텍스트로 보여주고 회전하는 프로그레스를 띄웁니다.
8. 그것을 클릭하면 오른쪽 아래에 작은 알림창이 열리고, 그 안에 작업마다 진행 막대와 취소 버튼이 있습니다.
9. 조작 도중 문제가 생기면 무시·재시도·취소를 묻는 모달이 뜹니다. 이 모달은 파일 탐색기 안에서만 동작합니다.
10. 같은 이름이 있으면 덮어쓰기·이름 바꾸기(뒤에 숫자를 붙이는 규칙)·복사하지 않기를 고르게 합니다.
11. 위 두 모달 하단에 "더 이상 묻지 않기" 체크박스를 둡니다.
12. 탐색기 탭 사이의 파일 이동과 복사를 지원합니다.
13. 마크다운 파일을 더블클릭하면 마크다운 편집기가 열립니다.
14. 세션 경로 우클릭 메뉴에 파일 탐색기를 여는 항목을 추가합니다.
15. 편집기 창의 컨텍스트 메뉴로 좌측 패널을 열고, 패널 상단의 닫기(X) 버튼으로 닫습니다.
16. *(2026-09-23 추가)* 탐색기 창에 **모드 전환**을 둡니다. 트리 모드와, 윈도우 탐색기처럼 현재 디렉터리만 보여 주는 목록 모드입니다.
17. *(2026-09-23 추가)* 두 모드 모두 **맨 위에 `..`** 를 두어 상위 디렉터리로 올라갑니다.
18. *(2026-09-23 추가)* **편집기 창 좌측 패널도 파일 조작을 지원합니다.** 컨텍스트 메뉴와 단축키로 복사·잘라내기·붙여넣기·삭제를 합니다.
19. *(2026-09-23 추가)* 단 좌측 패널은 **목록 모드를 지원하지 않습니다. 항상 트리 모드**입니다.
20. *(2026-09-23 추가)* 좌측 패널의 **경계를 손으로 잡아 끌어 폭을 조절**합니다. **전체 창의 50% 를 넘을 수 없습니다.**

## 3. 서버: 파일 조작 작업(Job) 모델

이 설계에서 새로 만드는 것 가운데 가장 큰 덩어리입니다.

### 3.1 작업은 중간에 멈춰서 물어볼 수 있어야 합니다

요구사항 9번과 10번이 이 설계 전체의 모양을 정합니다. 작업이 도중에 멈춰서 사용자에게 묻고, 답을 받은 뒤에 이어서 진행해야 하기 때문입니다. 그래서 작업은 단순한 비동기 함수가 아니라 **답을 기다리며 멈출 수 있는 상태 기계**입니다.

```
queued → running → (awaiting-decision → running)* → completed
                 ↘ cancelled
                 ↘ failed
```

미리 훑어서 충돌을 모두 찾아낸 다음 한꺼번에 물어보는 방식도 가능하지만 채택하지 않았습니다. 훑는 동안 파일이 바뀔 수 있어서 그때 없던 충돌이 실행 중에 생기고, 결국 실행 중에 묻는 경로를 어차피 만들어야 하기 때문입니다. 같은 일을 하는 경로가 둘이 되면 한쪽만 고쳐집니다.

### 3.2 두 단계로 진행합니다

| 단계 | 하는 일 | 화면에 보이는 것 |
|---|---|---|
| `scanning` | 옮길 대상을 걸어 다니며 파일 수와 전체 바이트를 셉니다 | 회전 프로그레스와 "계산 중" |
| `transferring` | 파일을 하나씩 옮기면서 누적 바이트를 보고합니다 | 막대 프로그레스 |

전체 크기를 먼저 세지 않으면 막대의 길이를 정할 수 없습니다. 큰 트리에서는 세는 일 자체가 오래 걸리므로 그 동안은 막대가 아니라 회전 프로그레스를 보여줍니다.

파일 하나가 아주 클 때를 위해 복사는 스트림으로 수행하고 읽은 바이트를 세어 보고합니다. `fs.copyFile` 을 쓰면 2기가바이트짜리 파일에서 막대가 0퍼센트에 멈춰 있다가 갑자기 100퍼센트가 되는데, 그것은 진행 표시가 있으나 마나 한 상태입니다.

삭제는 바이트가 의미 없으므로 **항목 수**로 진행률을 냅니다. 그래서 진행 보고에는 바이트와 항목 수를 함께 싣고, 화면이 작업 종류에 따라 골라 씁니다.

### 3.3 REST 진입점

```
POST   /api/file-jobs
       { operation: 'copy' | 'move' | 'delete',
         sourceSessionId, sources: string[],
         destSessionId?, destPath?,
         conflictPolicy?: 'ask' | 'overwrite' | 'rename' | 'skip',
         errorPolicy?: 'ask' | 'ignore' | 'abort' }
       → { jobId }

POST   /api/file-jobs/:jobId/decision
       { decisionId, choice, applyToAll: boolean }
       → { accepted: boolean }

DELETE /api/file-jobs/:jobId        작업 취소

GET    /api/file-jobs               현재 살아 있는 작업 목록 (새로고침 후 복구용)
```

출발지와 목적지의 세션을 따로 받는 이유는 요구사항 12번 때문입니다. 탐색기 탭마다 뿌리가 다르고 서로 다른 세션일 수 있는데, `resolveAndValidate` 는 세션의 작업 디렉터리를 기준으로 경로를 검사합니다. 그래서 출발지는 출발지 세션 기준으로, 목적지는 목적지 세션 기준으로 각각 검사해야 합니다. 하나의 세션만 받는 현재 API로는 탭 사이의 이동을 표현할 수 없습니다.

### 3.4 진행 보고는 WebSocket 으로 보냅니다

`server/src/types/ws-protocol.ts` 의 `ServerWsMessage` 에 다음을 추가합니다.

```
{ type: 'file-job:progress', jobId, phase, processedBytes, totalBytes,
  processedEntries, totalEntries, currentPath }
{ type: 'file-job:decision-required', jobId, decisionId, kind, path, detail }
{ type: 'file-job:done', jobId, outcome, summary }
```

REST 폴링을 쓰지 않는 이유는 초당 여러 번 갱신되는 값을 요청·응답으로 받으면 요청 수가 그대로 늘기 때문입니다. 터미널 출력이 이미 같은 연결을 쓰고 있으므로 새 연결도 필요하지 않습니다.

진행 보고는 작업마다 **초당 10회로 제한**합니다. 작은 파일이 수천 개인 디렉터리를 복사할 때 파일마다 메시지를 보내면 화면을 갱신하는 비용이 복사 자체보다 커집니다.

`ws-protocol.ts` 에는 메시지 목록을 원본 텍스트로 읽어 대조하는 테스트(`wsProtocolParityAck.test.ts`)가 붙어 있으므로, 형식을 추가할 때 그 테스트도 함께 갱신해야 합니다.

### 3.5 답을 기다리는 동안 연결이 끊기면

작업은 특정 브라우저 연결이 아니라 **세션에 매답니다.** 그래서 사용자가 새로고침해도 진행 중이던 복사가 중단되지 않습니다. 다시 접속한 클라이언트는 `GET /api/file-jobs` 로 살아 있는 작업을 다시 받아 오고, 답을 기다리던 작업이 있으면 서버가 `decision-required` 를 다시 보냅니다.

답이 오지 않는 상태가 무한히 이어지면 작업이 자원을 붙든 채 남으므로, **멈춰 있는 시간의 총합이 10분을 넘으면 작업을 자동으로 취소**합니다. 취소는 아래 3.7의 규칙을 그대로 따릅니다.

### 3.6 이름이 겹칠 때의 규칙

이름 바꾸기는 `이름 (2).확장자` 형태로 만들고, 그 이름도 이미 있으면 숫자를 하나씩 올립니다. 디렉터리는 확장자가 없으므로 `이름 (2)` 가 됩니다. 숫자를 2부터 시작하는 이유는 원본이 첫 번째이기 때문입니다.

"더 이상 묻지 않기"를 체크하면 그 선택이 **그 작업이 끝날 때까지만** 적용됩니다. 작업을 넘어서 기억해 두면, 한참 뒤의 다른 작업에서 사용자가 모르는 사이에 파일을 덮어쓰게 됩니다. 덮어쓰기는 되돌릴 수 없으므로 그 위험을 기본값으로 둘 수 없습니다.

### 3.7 취소했을 때 이미 옮긴 것은 어떻게 되는가

**되돌리지 않습니다.** 이미 복사를 마친 파일은 그대로 두고, 취소한 순간 쓰고 있던 파일 하나만 지웁니다. 반쯤 쓰이다 만 파일을 남기면 사용자가 그것을 온전한 파일로 착각하기 때문입니다.

전부 되돌리는 방식은 채택하지 않았습니다. 되돌리는 일 자체가 또 하나의 긴 작업이고, 그 도중에 실패하면 되돌리다 만 상태가 되는데 그것을 설명할 방법이 없습니다.

작업이 끝나면 "23개 복사 후 취소됨"처럼 **무엇이 실제로 끝났는지 숫자로** 보고합니다.

이동의 경우 취소 시점까지 옮긴 파일은 출발지에서 이미 사라진 상태입니다. 그래서 이동은 파일 하나 단위로 "복사 후 삭제"를 완료한 뒤 다음 파일로 넘어가며, 절대로 전체를 복사한 다음 전체를 삭제하지 않습니다. 후자는 취소나 실패가 났을 때 어느 쪽에도 온전한 사본이 없는 구간을 만듭니다.

## 4. 화면: 진행 표시 세 단계

### 4.1 하단 상태바

새 하단 바를 `App.tsx` 에 추가합니다. 파일 작업이 없을 때는 자리를 차지하지 않습니다.

| 상황 | 표시 |
|---|---|
| 작업 1개 | 막대 프로그레스와 현재 파일 이름 |
| 작업 2개 이상 | "3개 작업 진행 중" 같은 텍스트와 회전 프로그레스 |
| 어느 경우든 | 클릭하면 알림창이 열립니다 |

### 4.2 오른쪽 아래 알림창

상태바를 클릭하면 열리는 작은 팝오버입니다. 작업마다 한 줄씩 놓고, 각 줄에 진행 막대와 취소 버튼을 둡니다.

이것은 창이 아니라 팝오버이므로 `dialogStack` 에 등록하지 않습니다. 끌어서 옮기거나 크기를 바꿀 수 없고, 바깥을 클릭하면 닫힙니다. 창으로 만들면 z-순서와 최소화 같은 것들을 전부 따라오게 해야 하는데 이 용도에는 필요가 없습니다.

### 4.3 답을 기다리는 작업이 있는데 탐색기 창이 닫혀 있으면

요구사항 9번이 결정 모달을 파일 탐색기 안으로 한정했으므로, 탐색기 창이 닫혀 있으면 물어볼 자리가 없어집니다. 그래서 상태바에 "응답 대기 중"을 표시하고, **그것을 클릭하면 해당 탐색기 창을 다시 열면서 모달을 띄웁니다.** 이렇게 하면 모달이 탐색기 안에서만 동작한다는 규칙을 지키면서도 작업이 답을 못 받아 영원히 멈추는 일이 없습니다.

### 4.4 탐색기 창 안의 진행 줄

*(2026-09-23 추가)*

4.1 과 4.2 만으로는 **시선과 피드백이 너무 멀리 떨어집니다.** `Ctrl+V` 를 누르는 순간 시선은 화면 가운데 떠 있는 탐색기 창에 있는데, 피드백은 앱 맨 아래 가장자리에 뜹니다. 게다가 3분짜리 복사가 도는 동안 **탐색기 창은 완전히 가만히 있습니다** — 대상 디렉터리에 파일이 하나씩 늘어나지도 않습니다. 트리를 다시 읽는 것은 작업이 끝난 뒤이기 때문입니다(8.1).

그래서 탐색기 창 하단에 **얇은 진행 줄**을 답니다.

| | |
|---|---|
| 무엇을 보여 주나 | **그 창에서 시작한 작업만.** 다른 창이나 다른 워크스페이스의 작업은 상태바에만 뜹니다 |
| 담는 것 | 막대 · 작업 종류 · `128 / 337` · 취소 버튼 |
| 여러 개일 때 | 가장 최근 것 하나와 "외 2개". 누르면 4.2 의 알림창이 열립니다 |
| 작업이 없을 때 | 자리를 차지하지 않습니다 (4.1 과 같은 규칙) |
| 창을 닫으면 | 작업은 계속 돕니다. 상태바가 그대로 이어받습니다 (3.5) |

**새로 만드는 것은 표시뿐입니다.** 데이터는 이미 `file-job:progress` 로 오고 있고(3.4), 서버도 작업 모델도 바뀌지 않습니다. 모바일 버튼 줄(6.3)이 놓이는 자리를 함께 씁니다.

윈도우 탐색기는 이 자리를 작업마다 뜨는 진행 대화상자로 채우는데, 그 길은 막아 두었습니다 — 전역 모달로 두면 복사하는 동안 터미널까지 멈춥니다(5절).

**대상 디렉터리 행에 회전자를 다는 것은 하지 않습니다.** 트리 재렌더가 따라붙고, 얻는 것이 이 줄과 겹칩니다.

## 5. 창 범위 모달

요구사항 9번의 "파일 탐색기 안에서만 동작합니다"는 지금 없는 개념을 하나 요구합니다.

현재 `dialogStack` 은 모달과 모달리스 두 대역을 두고, 모달은 화면 전체를 막으며 가장 위의 모달이 포커스를 가둡니다. 결정 모달을 그 대역에 넣으면 복사가 질문을 띄운 동안 터미널까지 멈추게 됩니다. 파일 하나를 덮어쓸지 묻는 질문 때문에 에이전트를 지켜보지 못하게 되는 것은 받아들이기 어렵습니다.

그래서 **창 하나만 막는 모달**을 새로 만듭니다.

- 탐색기 창의 표면 안에 겹쳐서 그립니다. 창 바깥은 덮지 않습니다.
- 포커스를 그 창 표면 안에 가둡니다.
- `Escape` 는 그 질문을 취소한 것으로 처리합니다.
- 전역 모달 대역에 등록하지 않습니다. 따라서 터미널과 편집기는 그대로 쓸 수 있습니다.

결정 모달은 두 종류이고 둘 다 하단에 "더 이상 묻지 않기" 체크박스를 답니다.

| 모달 | 선택지 |
|---|---|
| 오류 | 무시 · 재시도 · 취소 |
| 이름 충돌 | 덮어쓰기 · 이름 바꾸기 · 복사하지 않기 |

삭제 확인도 같은 창 범위 모달로 띄웁니다. 다만 삭제 확인에는 "더 이상 묻지 않기"를 달지 않습니다. 삭제는 되돌릴 수 없고, 묻지 않기로 한 사실 자체를 사용자가 잊었을 때 잃는 것이 너무 크기 때문입니다.

## 6. 클립보드와 단축키

### 6.1 클립보드는 브라우저 것이 아니라 우리 것입니다

```
{ mode: 'copy' | 'cut', entries: [{ sessionId, path }] }
```

웹 페이지는 시스템 클립보드에서 파일 핸들을 얻을 수 없으므로, 탐색기 안에서만 통하는 클립보드를 따로 둡니다. 탭과 창을 가리지 않는 하나의 값이므로 요구사항 12번의 탭 사이 복사가 저절로 됩니다.

잘라내기로 담긴 항목은 트리에서 흐리게 그려서, 붙여넣기 전까지는 아직 옮겨지지 않았다는 사실을 보이게 합니다.

### 6.2 단축키

| 키 | 동작 |
|---|---|
| `Ctrl+C` | 선택한 항목을 복사 모드로 담습니다 |
| `Ctrl+X` | 선택한 항목을 잘라내기 모드로 담습니다 |
| `Ctrl+V` | 현재 탭의 디렉터리에 붙여넣습니다 |
| `Delete` | 선택한 항목을 지웁니다 (확인 모달) |
| `F2` | 이름을 바꿉니다 |

**포커스가 트리 표면 안에 있을 때만 가로챕니다.** 이 판정이 빠지면 터미널에서 누른 `Ctrl+C` 가 인터럽트로 가지 못하고 탐색기에 먹히는데, 그것은 에이전트를 멈출 수 없게 되는 심각한 고장입니다. 편집기의 `Ctrl+S` 가 이미 같은 방식으로 포커스를 확인하고 있으므로(`editorWindowSaveShortcut.ts`) 그 판정 방식을 따릅니다.

**"트리 표면"의 범위가 두 자리에서 다릅니다.**

| 자리 | 가로채는 범위 |
|---|---|
| 탐색기 창 (9.2) | 창 표면 전체 |
| 편집기 좌측 패널 (9.1) | **트리 패널 표면만.** 문서 영역은 제외합니다 |

*(2026-09-23 추가)* 아래쪽이 결정 16 을 안전하게 만드는 장치입니다. 편집기 좌측 패널이 파일 조작을 지원하게 되면서, CodeMirror 본문에서 누른 `Delete` 가 파일을 지우는 사고가 가능해집니다. 그래서 범위를 창이 아니라 **패널**로 잡습니다 — 본문에 포커스가 있으면 `Delete` 는 글자를 지우고, 트리에 포커스가 있을 때만 파일로 갑니다. 같은 장치를 한 칸 더 조이는 것이라 새 개념이 아닙니다.

남는 위험은 "트리에 포커스가 있는 줄 모르고 누르는 경우"인데, 삭제 확인 모달이 받아 냅니다. 그 모달에 "더 이상 묻지 않기"를 달지 않은 것이 여기서도 값을 합니다(5절).

### 6.3 모바일 버튼

모바일에서는 단축키를 쓸 수 없으므로 탐색기 창 하단에 버튼 줄을 둡니다. 복사·잘라내기·붙여넣기·삭제·이름 바꾸기·새 폴더 여섯 개이며, 지금 할 수 없는 동작은 흐리게 처리합니다. 예를 들어 클립보드가 비어 있으면 붙여넣기 버튼이 눌리지 않습니다.

## 7. 컨텍스트 메뉴

트리 항목에서 오른쪽 버튼을 누르면, 모바일에서는 길게 누르면 메뉴가 열립니다. 기존 `ContextMenu` 컴포넌트와 `useLongPress` 훅을 그대로 씁니다.

| 항목 | 조건 |
|---|---|
| 편집기로 열기 | 열 수 있는 파일일 때만 |
| 새 탭에서 열기 | 디렉터리일 때만 |
| 복사 · 잘라내기 | 항상 |
| 붙여넣기 | 클립보드가 비어 있지 않을 때 |
| 이름 바꾸기 · 삭제 | 항상 |
| 새 폴더 | 디렉터리이거나 빈 곳을 눌렀을 때 |
| 새로 읽기 | 디렉터리일 때 |

**메뉴 항목에 단축키를 함께 적습니다** — `복사   Ctrl+C` 꼴입니다. 6.2 의 단축키를 아는 길이 이 메뉴뿐이고, 마우스로 한 번 해 본 사람이 다음부터 키를 쓰게 되는 자리입니다.

#### 우클릭이 선택을 어떻게 다루나

*(2026-09-23 추가 — 앞선 설계가 적지 않은 채 남겨 둔 것입니다)*

| 어디를 눌렀나 | 선택 |
|---|---|
| 선택되지 않은 항목 | 그 항목 하나만 선택하고 메뉴를 엽니다 |
| **이미 선택된 항목** | **선택을 그대로 둡니다.** 메뉴의 복사·잘라내기·삭제는 선택 전체에 적용됩니다 |
| 빈 곳 | 선택을 모두 해제하고, 현재 디렉터리에 대한 메뉴를 엽니다 — **붙여넣기 · 새 폴더 · 새로 읽기** 셋입니다 |

가운데 줄이 빠지면 **여러 항목을 골라 놓고 우클릭하는 순간 선택이 하나로 줄어듭니다.** 여러 개를 지우거나 복사하려던 사람이 그 자리에서 다시 고르게 되는데, 이 기능의 주된 쓰임새가 정확히 그것이라 그냥 두면 메뉴로는 다중 조작을 할 수 없게 됩니다.

#### 목록 모드에서도 같습니다

8.4 의 목록 모드는 표시 방식만 다르고 선택·클립보드·메뉴는 트리와 같은 것을 씁니다(8.2). 메뉴에서 빠지는 항목은 **새 탭에서 열기**뿐입니다 — 목록에서 디렉터리를 여는 길은 더블클릭으로 들어가는 것이고, 새 탭은 탭 막대의 더하기 버튼이 맡습니다.

#### 세션 경로 자리의 메뉴

*(2026-09-23 승계)* 앞선 설계는 **파일 탐색기**를 세 파일 **아래에** 두기로 했습니다. **위로 옮깁니다.**

그 자리는 `MetadataRow` 의 cwd 텍스트입니다 — 타일에서 터미널 **아래**에 붙는 28px 줄이고(`MosaicTile.tsx:114` → `:119`), 이미 `onPathContextMenu` 를 물고 있습니다(`MetadataRow.tsx:79`). 메뉴를 만드는 곳은 `buildEditorFileMenuItems` 입니다.

```
├─────────────────┤   ← 구분선
│ CLAUDE.md       │
│ CLAUDE.local.md │

```

**위에 두는 이유**는 세 파일이 `EDITOR_INSTRUCTION_FILES` 로 고정된 목록이고 앞으로 늘 수 있기 때문입니다(`editorFileMenu.ts:19`). 목록 아래에 붙이면 그 목록이 길어질 때마다 탐색기가 아래로 밀려 내려가, 같은 메뉴인데 항목의 자리가 해마다 달라집니다. 위는 고정된 자리입니다.

`buildEditorFileMenuItems` 는 지금 `EDITOR_INSTRUCTION_FILES.map` 하나로 끝납니다. 탐색기 항목과 구분선이 **그 map 앞에** 들어갑니다. 반환 타입(`ContextMenuItem[]`)은 그대로입니다.

## 8. 트리 자체의 설계

### 8.1 `useFileTree(sessionId, initialRoot)` 훅

```
expandedPaths: Set<string>              펼쳐진 디렉터리의 절대 경로
childrenByPath: Map<string, ChildState> ChildState = 로딩중 | 항목 배열 | 오류
selectedPaths: Set<string>              선택된 항목들
root: string                            현재 뿌리 — 고정이 아니라 움직입니다
mode: 'tree' | 'list'                   같은 상태를 보는 두 가지 방식
goUp() / setRoot(path)                  뿌리를 옮깁니다
```

**2026-09-23 승계**: 앞선 설계는 이 훅을 `useFileTree(sessionId, rootPath)` 로 두고 뿌리를 고정으로 받았습니다. 모드 전환(결정 6)이 들어오면서 뿌리가 움직여야 하므로 위와 같이 갱신합니다.

디렉터리를 처음 펼칠 때 그 디렉터리만 조회합니다. 이미 담겨 있으면 다시 조회하지 않으며, 다시 읽으려면 `refresh(path)` 를 명시적으로 호출해야 합니다. 파일 시스템 감시는 넣지 않습니다.

**두 모드는 두 기능이 아니라 한 상태의 두 뷰입니다.** 트리는 뿌리와 펼쳐 둔 자손을 그리고, 목록은 뿌리의 직계만 그립니다. 둘이 `childrenByPath` 를 공유하므로 **모드를 바꿀 때 서버 요청이 0건**입니다.

**뿌리가 바뀌어도 `expandedPaths` 를 버리지 않습니다.** 절대 경로이므로 뿌리 밖의 항목은 그리지 않을 뿐이고, 되돌아오면 그대로 살아 있습니다. 위로 갔다가 내려왔을 때 펼쳐 둔 것이 전부 접혀 있는 편이 더 나쁩니다.

파일 작업이 끝나면 영향을 받은 디렉터리만 다시 읽습니다. 트리 전체를 다시 읽으면 펼쳐 둔 상태가 흐트러집니다.

#### `..` 는 노드가 아닙니다

서버의 `listDirectory` 는 루트가 아닌 디렉터리마다 `..` 항목을 목록 맨 앞에 넣어서 돌려줍니다(`FileService.ts:170` 부근). 앞선 설계는 이 항목을 훅이 **걸러낸다**고 적었고, 이유는 "부모로 가는 일은 뿌리를 바꾸는 조작이지 자식 노드가 아니므로" 였습니다.

**그 이유는 그대로 유효하고, 결론만 한 걸음 나아갑니다.** 화면에는 맨 위에 `..` 행을 둡니다(요구사항 17번). 다만 그것은 **노드 목록에 들어가지 않고 창의 크롬입니다.**

노드로 두면 선택 · `Ctrl+A` · `Shift` 범위 선택 · 컨텍스트 메뉴 · 클립보드 · `Delete` **여섯 곳 전부**에 예외를 심어야 합니다. 하나만 빠지면 `..` 를 복사하거나 지우려 드는 버그가 되고, 그런 예외는 나중에 조작이 하나 늘 때 함께 늘지 않습니다. 크롬으로 두면 모든 조작이 **애초에 닿지 못합니다.**

#### 위로 어디까지 갈 수 있는가

**서버의 blocked path 정책(`NFR-SEC-004`)만 따릅니다. 클라이언트가 별도 경계를 두지 않습니다.**

세션 작업 디렉터리에서 멈추는 안을 버린 이유는, 그것이 클라이언트에만 있는 제한이라 서버가 강제하지 않기 때문입니다 — 보안이 아니라 장식이고, 같은 정책을 두 군데 두면 어긋납니다. 저장소 밖 파일을 끌어오는 것은 여러 프로젝트를 동시에 운용할 때 실제로 쓰이는 동작이기도 합니다.

`↑` 버튼의 활성 여부는 **서버 응답에 `..` 가 들어 있는지**로 판정합니다. 클라이언트가 경계 규칙의 사본을 갖지 않게 하려는 것입니다. 바로 위에서 걸러낸다고 적은 그 항목이, 이제 "위로 갈 수 있는가"의 답입니다.

### 8.2 클릭이 하는 일

| 조작 | 트리 | 목록 |
|---|---|---|
| 단일 클릭 | 선택합니다. `Ctrl` 을 누른 채면 추가 선택, `Shift` 면 범위 선택입니다 | 같습니다 |
| 더블 클릭 (파일) | 편집기 창에서 엽니다 | 같습니다 |
| 더블 클릭 (디렉터리) | 펼치거나 접습니다 | **그 안으로 들어갑니다** (뿌리 변경) |
| 삼각형 아이콘 클릭 | 선택을 바꾸지 않고 펼치거나 접습니다 | 없습니다 |
| 맨 위 `..` | 뿌리를 한 단계 올립니다 | 같습니다 |

**선택 집합은 모드와 무관하게 하나입니다.** 목록에서 고른 것이 트리로 바꿔도 그대로 선택되어 있고, 클립보드와 단축키도 모드를 가리지 않습니다.

앞선 설계에서 "단일 클릭으로 연다"고 적었던 것을 **취소합니다.** 파일 조작에는 여러 항목을 고르는 일이 필요하고, 단일 클릭이 파일을 열어 버리면 고를 방법이 없어집니다.

### 8.3 열 수 있는 파일의 판정

편집기는 텍스트 편집기이므로 바이너리 파일을 열면 내용이 깨집니다. `frontend/src/utils/viewableExtensions.ts` 의 확장자 집합을 재사용하고, 그 밖의 파일은 트리에서 흐리게 그려 더블클릭을 받지 않습니다. 다만 그 파일은 제거된 구 뷰어를 위해 만들어진 것이고 지금 렌더 트리에 연결되어 있지 않다는 점을 적어 둡니다.

**조작 대상은 이 판정과 무관합니다.** 열 수 없는 파일도 복사·이동·삭제는 됩니다. 판정이 막는 것은 여는 일뿐입니다.

### 8.4 목록 모드

현재 디렉터리의 직계만 그립니다. 컬럼은 **이름 · 수정한 날짜 · 크기** 셋입니다.

| | |
|---|---|
| 기본 정렬 | 서버가 주는 순서 — 상위 경로, 디렉터리, 파일 (`FR-FILE-002`) |
| 사용자 정렬 | 머리글을 눌러 이름 · 수정한 날짜 · 크기. 어느 것으로 정렬해도 **디렉터리가 항상 파일 앞**입니다 |
| 저장 | 모드와 정렬 모두 탭마다 따로, 워크스페이스별 `localStorage` (9.2) |

`유형` 컬럼은 두지 않습니다. 확장자가 이름에 이미 보이고, 좁은 창에서 가장 먼저 잘리는 자리입니다.

목록 응답은 이미 필요한 것을 전부 담고 있습니다 — `DirectoryEntry` 가 `name`·`type`·`size`·`extension?`·`modified` 입니다(2절). 서버를 고칠 것이 없습니다.

**가상 스크롤은 넣지 않습니다**(결정 22). 앞선 설계는 이것을 "`maxDirectoryEntries` 가 상한을 거니 실측한 뒤에" 로 미뤄 두었고, 2026-09-23 에 실측했습니다.

| 대상 | 측정 |
|---|---|
| 렌더 (Chromium, 28px 3컬럼 행) | 10000행 = DOM 50000노드, build+layout **253ms**, 선택 1회 re-style 4.9ms |
| 서버 (`FileService.ts:180` 순차 `fs.stat`, Windows 네이티브) | 4983항목 = readdir 3.9ms + stat **286ms**, 페이로드 544KB. 10000 외삽 시 ~575ms / ~1.1MB |

**병목은 렌더가 아니라 서버입니다.** 가상 스크롤은 렌더만 고치므로 253ms 를 없애자고 7단계 전체의 상호작용 모델을 복잡하게 만드는 셈입니다. 서버 쪽은 결정 24 로 따로 답니다.

그리고 가상 스크롤은 **스크롤 복원을 어렵게 만듭니다**(9.2). 행이 DOM 에 없으면 이름으로 찾아갈 수 없어 index→px 를 직접 계산해야 하는데, 그것은 행 높이가 균일할 때만 정확하고 `--row-h` 는 조밀 모드에서 22px 로 바뀝니다.

같은 이유로 **행이 DOM 에 실재한다는 것 자체가 계약**입니다 — `FR-FEX-002` AC-8 이 그것을 박습니다.

편집기 좌측 패널에는 목록 모드가 없습니다(9.1).

## 9. 두 자리에 놓이는 트리

### 9.1 편집기 창 좌측 패널

```
WindowDialog (제목 표시줄: 파일명 · 저장 · 최대화 · 최소화)
└ 본문 (가로 배치)
   ├ FileTreePane      상단에 뿌리 경로와 닫기(X) 버튼
   └ 문서 영역 (세로 배치)
      ├ EditorTabBar
      └ EditorDocumentPanel 들
```

탭 막대를 트리 위에 얹지 않고 트리 오른쪽에 둔 이유는, 탭이 문서 영역에 속한 것이고 트리는 창 전체에 속한 것이기 때문입니다. 탭 막대가 트리를 덮으면 트리가 활성 탭에 딸린 물건처럼 읽힙니다.

뿌리는 **활성 탭이 결속된 세션의 작업 디렉터리**로 잡되, 사용자가 트리 안에서 뿌리를 옮겼다면 그 조작을 유지합니다. 뿌리를 다시 잡는 시점은 활성 탭의 세션이 달라질 때뿐입니다.

너비와 접힘 여부는 워크스페이스별로 `localStorage` 에 저장합니다. 펼쳐 둔 디렉터리 목록은 저장하지 않습니다. 그 사이에 사라진 경로가 남아 복원할 때마다 오류를 내는 비용이 얻는 편의보다 큽니다.

모바일에서는 기본적으로 접혀 있고, 펼치면 문서 영역 위에 겹쳐 뜬 뒤 항목을 고르면 다시 접힙니다.

#### 여는 길과 닫는 길

패널을 **여는 길은 편집기 창의 컨텍스트 메뉴**이고, **닫는 길은 패널 상단의 X 버튼**입니다. 제목 표시줄에는 토글 버튼을 두지 않습니다.

제목 표시줄에 넣지 않은 이유는 그 줄에 저장·최대화·최소화가 이미 있기 때문입니다. 네 번째 버튼을 더하면 창이 좁아질 때 가장 먼저 뭉개지는 자리가 되고, 모바일에서는 손가락으로 누르기에 이미 작습니다. 반면 패널 안의 X 는 패널이 차지한 폭만큼 여유가 있어서 누르기 좋은 크기로 둘 수 있습니다.

컨텍스트 메뉴를 붙이는 자리는 **탭 막대와 제목 표시줄의 빈 곳으로 한정**합니다. 편집기 본문에는 붙이지 않습니다. 본문에서 우클릭을 가로채면 브라우저가 주는 텍스트 복사·붙여넣기·맞춤법 검사 메뉴를 사용자가 잃는데, 편집기에서 그 메뉴는 실제로 쓰이는 기능이므로 항목 하나를 얻자고 내줄 것이 아닙니다.

메뉴 항목은 패널이 열려 있을 때도 그대로 두고 체크 표시를 붙입니다. 닫고 나면 다시 여는 길이 우클릭 하나뿐이라 사용자가 찾지 못할 수 있는데, 열려 있는 동안 메뉴에서 그 항목을 본 사람은 자리를 기억하게 됩니다. 그 결과 닫는 길이 X 와 메뉴 둘이 되지만 해가 되지는 않습니다.

편집기 창에는 지금 컨텍스트 메뉴가 없다는 점을 적어 둡니다. 우클릭 메뉴가 있는 곳은 터미널(`TerminalRuntimeLayer.tsx:128`)과 세션 경로 자리(`useEditorWindows` 의 `pathMenu`)뿐이므로, 이 메뉴는 새로 만드는 것입니다.

#### 파일 조작 — 2026-09-23 승계

앞선 설계는 이 패널을 **탐색 전용**으로 두고, 파일 조작 단축키와 컨텍스트 메뉴를 탐색기 창에만 두었습니다. 근거는 "편집 중인 창에서 `Delete` 키가 파일을 지우게 만들면 본문을 지우려던 키가 파일을 지우는 사고가 난다" 였습니다.

**그 결정을 승계합니다.** 이 패널도 **탐색기 창과 같은 파일 조작을 지원합니다** — 우클릭 메뉴와 단축키로 복사·잘라내기·붙여넣기·삭제·이름 바꾸기·새 폴더(요구사항 18번). 메뉴에서 빠지는 것은 **새 탭에서 열기** 하나뿐입니다. 여기에는 탭이 없습니다.

**근거가 사라진 것이 아니라 막혔습니다.** 6.2 가 단축키를 가로채는 범위를 이 패널에서는 *창 표면*이 아니라 **트리 패널 표면**으로 잡습니다. CodeMirror 본문에 포커스가 있으면 `Delete` 는 글자를 지우고, 트리에 포커스가 있을 때만 파일로 갑니다. 삭제는 그 위에서 다시 확인 모달을 거칩니다(5절).

클립보드와 작업 목록은 탐색기 창과 **공유합니다**(9.3). 편집기 패널에서 잘라낸 것을 탐색기 창에서 붙여넣을 수 있습니다.

#### 모드 토글은 두지 않습니다 — 항상 트리입니다

212px 폭에 *수정한 날짜*·*크기* 컬럼이 들어가지 않습니다. 이 패널에 목록 모드는 없습니다(요구사항 19번).

다만 **`..` 는 둡니다.** 이 절이 이미 "사용자가 트리 안에서 뿌리를 옮겼다면 그 조작을 유지합니다"라고 뿌리 이동을 허용하고 있으므로, 올라가는 길이 없으면 그 문장이 가리키는 조작 자체가 불가능합니다.

### 9.2 탐색기 모달리스 창

`WindowDialog` 를 `mode="modeless"` 로 띄우고, 편집기 창과 같은 방식의 탭 막대를 답니다. 탭마다 독립된 `useFileTree` 인스턴스를 가지며 뿌리가 서로 다를 수 있습니다.

- 창은 워크스페이스마다 하나이고 `dialogId` 는 `file-explorer:{workspaceId}` 입니다.
- 진입점은 셋입니다. **세션 경로 우클릭 메뉴**(7절 — 맨 위 항목), **터미널 우클릭 메뉴**의 `파일 탐색기 열기`, 그리고 **헤더의 아이콘 버튼**.
- 이미 떠 있으면 다시 누를 때 닫지 않고 앞으로 끌어올립니다. `dialogStack.raiseDialogById` 가 그 일을 이미 합니다.
- 쌓임 순서는 `CON-MDE-001` 의 3000번대 대역과 `FR-MDE-003` 의 규칙을 그대로 따르므로 새 규칙이 필요 없습니다.

- 탭 막대 아래에 **경로 막대**를 둡니다. 왼쪽부터 `↑`(상위로) · 현재 뿌리 경로 · 모드 토글 · 새로 읽기 · 새 폴더 순입니다.

새 탭은 디렉터리의 컨텍스트 메뉴에서 "새 탭에서 열기"로, 또는 탭 막대의 더하기 버튼으로 만듭니다.

#### 모드와 정렬은 탭마다 따로 저장합니다

워크스페이스별 `localStorage` 에 담습니다. 9.1 이 패널 너비를 저장하는 방식과 같습니다.

**탭마다 따로인 이유**가 이 기능의 쓰임새입니다. 큰 디렉터리를 목록으로 훑는 탭과 구조를 트리로 보는 탭이 동시에 있는 것이 정상이고, 모드를 창 단위로 묶으면 탭을 옮길 때마다 보던 방식이 바뀝니다.

**기본 모드는 트리입니다.** 편집기 좌측 패널이 트리 전용이라 사용자가 이 제품에서 먼저 만나는 것이 트리이고, 두 자리의 첫인상이 같아야 같은 물건으로 읽힙니다.

펼쳐 둔 디렉터리 목록은 저장하지 않습니다 — 9.1 과 같은 이유로, 그 사이에 사라진 경로가 남아 복원할 때마다 오류를 내는 비용이 얻는 편의보다 큽니다.

#### 스크롤은 픽셀이 아니라 앵커로 되살립니다

*(2026-09-23 추가 — 결정 23)*

모드·정렬과 같은 자리에 **맨 위에 보이던 행의 이름**을 저장합니다. 픽셀을 저장하지 않는 이유는 에이전트가 도는 동안 파일이 생기고 사라지기 때문입니다 — **같은 픽셀이 다른 항목을 가리킵니다.**

측정에서 조용한 실패 두 가지가 나왔습니다. 둘 다 오류를 내지 않습니다.

| | 무슨 일이 일어나는가 |
|---|---|
| 행이 없는데 `scrollTop = 150000` | **0 으로 클램프.** 쓰기는 성공하고 아무 일도 없습니다 |
| 목록이 짧아진 뒤 픽셀 복원 | 86600 으로 잘려 **맨 아래**에 섭니다 |

앵커는 첫 번째를 공짜로 막습니다. 픽셀 쓰기와 달리 `querySelector` 가 `null` 을 돌려주므로 **아직 안 왔다는 것이 관측됩니다**.

| 관측 | 의미 | 동작 |
|---|---|---|
| 행 0개 | 아직 안 그려짐 | 기다립니다 |
| 행 있음 + 앵커 없음 | 그 파일이 지워짐 | 정렬 순서상 가장 가까운 이름, 없으면 맨 위 |
| 앵커 있음 | 복원 가능 | `scrollIntoView` |

**실패한 복원은 저장값을 갱신하지 않습니다.** 못 찾았다고 "맨 위" 를 기억에 되쓰면 늦게 그려진 것이 영구 손실로 바뀝니다. Orca 가 같은 사고를 겪고(STA-5949) 클램프된 값 대신 목표값을 다시 단언하는 것으로 막고 있습니다.

펼쳐 둔 디렉터리와 달리 앵커는 실종되어도 **해롭지 않은 대비책**이 있어서 저장합니다. 비용 구조가 다릅니다.

#### 여러 개는 뜨지 않습니다

*(2026-09-23 추가)*

편집기 창이 이미 그 모양입니다. `useEditorWindows` 의 창 목록은 `Record<workspaceId, shell>` 이고, 가시성은 `editorWindowVisibility.ts` 의 3항 논리곱입니다.

```ts
!minimized && screen === 'workspace' && windowWorkspaceId === activeWorkspaceId
```

워크스페이스는 한 번에 하나만 활성이므로 **화면에는 언제나 최대 한 개**입니다. 탐색기도 같은 규칙을 따릅니다.

여러 디렉터리를 동시에 보는 길은 **한 창 안의 탭**입니다. 탭마다 독립된 `useFileTree` 를 갖고 뿌리가 서로 다를 수 있으며, 클립보드가 탭과 창을 가리지 않는 하나의 값이므로(6.1) 탭 사이 이동이 요구사항 12번을 충족합니다.

**다만 원래 Mdir 은 이중 패널이었습니다.** 좌우에 다른 디렉터리를 놓고 사이를 옮기는 것이 그 물건의 핵심이었는데, 이 설계로는 **양쪽을 동시에 보면서** 옮길 수 없습니다. 세 갈래를 검토했습니다.

| | 내용 | 판단 |
|---|---|---|
| A | 워크스페이스당 하나. 여러 디렉터리는 탭으로 | **채택** |
| B | 창 하나 안에서 좌우 분할 — 탭 막대가 둘, 각각 독립 트리 | 13절로 넘깁니다. 나중에 얹을 수 있습니다 — 탭 모델을 두 벌 두면 되고, 이 설계의 어느 것도 되돌리지 않습니다 |
| C | 창을 여러 개 허용 (`file-explorer:{workspaceId}:{n}`) | 버립니다. 창 목록이 `Record` 에서 배열이 되고 트레이·복원·z-순서가 전부 따라오며, **편집기 창까지 같이 바꿔야 합니다** |

A 로 둬도 막히는 것이 없고, B 를 나중에 정해도 늦지 않습니다.

#### 최소화

*(2026-09-23 추가)*

**닫히지 않습니다.** `minimized: true` 가 서고 창 표면이 `display: none` 이 될 뿐, **언마운트하지 않습니다.**

편집기가 언마운트하지 않는 이유는 `editorWindowVisibility.ts` 가 적어 둔 그대로입니다 — "포팅된 편집기는 마운트할 때 `markdownSource` 를 한 번 읽고 그때부터 문서의 source of truth 이므로, 컴포넌트를 헐면 사용자가 친 것이 버려진다". **탐색기에는 그 문제가 없습니다** — 트리의 원본은 서버입니다. 그런데도 같은 규칙을 가져갑니다: 헐면 펼쳐 둔 디렉터리와 선택이 날아가고, 8.1 이 그것을 저장하지 않기로 했기 때문입니다.

최소화한 창은 **헤더의 편집기 트레이 버튼**(`Header.tsx:134`)으로 갑니다. 거기에 **줄 하나**를 놓습니다.

| | |
|---|---|
| 줄의 이름 | `파일 탐색기 — {워크스페이스 이름}` |
| 몇 줄인가 | **창 하나당 한 줄.** 탭마다 줄을 만들지 않습니다 |
| 누르면 | `minimized: false` + 필요하면 워크스페이스 전환 + `raiseDialogById`. 편집기의 `reviveByPath` 와 같은 순서입니다 |
| 배치 | 그대로 따라옵니다. 최대화 상태였으면 복귀 후에도 최대화입니다 |
| 진행 중인 작업 | 창 안 진행 줄(4.4)은 함께 사라지고 하단 상태바가 이어받습니다(3.5) |

**탭마다 줄을 만들지 않는 이유**는 트레이가 지금 문서의 목록이기 때문입니다(`listEditorTrayEntries(documents)`). 거기에 디렉터리 이름이 섞이면 그 메뉴가 무엇의 목록인지 흐려집니다. 탐색기는 한 줄로 들어가고, 어느 탭이 활성이었는지는 창이 자기 상태로 기억합니다.

`minimized` 를 푸는 것은 **3항 중 하나만** 푸는 것이라, 창이 다른 워크스페이스에 속해 있으면 여전히 보이지 않습니다. 그래서 되살리는 동작이 워크스페이스 전환까지 함께 합니다.

### 9.3 두 자리는 트리 상태를 공유하지 않습니다

컴포넌트와 훅은 공유하되 인스턴스는 나눕니다. 편집기 좌측 트리는 활성 문서가 속한 세션을 따라가고, 탐색기 창은 사용자가 직접 옮겨 다니는 자리입니다. 상태를 공유하면 탐색기에서 디렉터리를 옮긴 순간 편집기 트리도 따라 움직이는데, 그것은 사용자가 요청하지 않은 변화입니다.

반면 **클립보드와 작업 목록은 공유합니다.** 그 둘은 어느 창에 속한 것이 아니라 애플리케이션 전체에 하나씩 있어야 하는 값입니다.

### 10.3 표면 적응형이 뜻하는 것

같은 트리 컴포넌트가 두 표면에 놓입니다.

| 표면 | 어디 | 값 |
|---|---|---|
| `data-surface="chrome"` | 탐색기 모달리스 창 (9.2) | 어두운 계열. `--bg-surface: #272727` |
| `data-surface="paper"` | 편집기 창 좌측 패널 (9.1) | 밝은 계열. `--bg-surface: #fbfbfb`, `--fg: #1f1f1f` |

**토큰 이름은 하나이고 값만 다시 걸립니다.** CSS 한 블록이면 됩니다.

```css
[data-surface="paper"] {
  --bg-surface:#fbfbfb; --bg-raised:#f1f1f1;
  --bg-hover:rgba(0,0,0,.05); --bg-active:rgba(0,120,212,.14);
  --fg:#1f1f1f; --fg-strong:#000; --fg-muted:#5c5c5c; --fg-faint:#8a8a8a;
  --line:#e3e3e3; --line-strong:#cdcdcd;
}
```

그래서 컴포넌트는 자기가 어느 표면에 있는지 몰라도 됩니다. 조건 분기가 컴포넌트에 들어가지 않는 것이 이 방식을 고른 이유입니다.

**치르는 값**: 탐색기 창의 트리와 편집기 창의 트리가 더 이상 같은 색이 아닙니다. 같은 컴포넌트가 두 얼굴을 갖습니다. 그것을 받아들이는 대신, 편집기 창 안에서 어두운 트리와 흰 종이가 맞닿는 단차가 사라집니다 — 그 창이 이 제품에서 문서를 읽고 쓰는 유일한 자리이므로 그쪽을 택했습니다.

### 10.4 벤더링된 편집기 토큰과의 관계

**나란히 둡니다. 합치지 않습니다.**

벤더링된 편집기는 `[data-theme="light"]` 로 이미 같은 일을 하고 있습니다 (`inline-preview.css:767-811`). 방식이 검증돼 있다는 뜻이기도 하지만, 그쪽은 **상류를 다시 들여올 수 있어야 하는 코드**입니다. `EditorWindow.css` 의 기존 주석이 같은 판단을 이미 적어 두었습니다 — "같은 색을 두 벌 적으면 상류를 다시 들여올 때 한쪽만 움직여 조용히 어긋난다".

그러므로 `--atomic-editor-*` 는 편집기 본문의 것으로 두고, 새 `--bg-*`/`--fg-*` 는 창 크롬과 탐색기의 것으로 둡니다. 두 벌이 남는 것은 값이지만, 합쳤을 때 치르는 값이 더 큽니다.
