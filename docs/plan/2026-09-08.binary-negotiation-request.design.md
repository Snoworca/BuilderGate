## Observed contract mismatch

AC-11 requires five distinct control types: client `terminal-binary:negotiate`, server `terminal-binary:capability`, `terminal-binary:rejected`, `terminal-binary:channel-retired`, and client `terminal-binary:unknown-channel`. Request and response must not share a type discriminator.

Before implementation, the source used `terminal-binary:capability` for both the offer and accepted response. All source anchors in this section describe that pre-implementation baseline:

- `server/src/ws/terminalBinaryNegotiation.ts:18` declares the offer discriminator; the pure validator at :80 checks payload fields but not that discriminator. The accepted response at :39/:119 must stay capability.
- `server/src/ws/WsRouter.ts:1881` routes the old request to the handler at :2020. The unknown-channel path at :2005 and its capability response are separate and must remain intact.
- `frontend/src/utils/terminalBinaryNegotiationClient.ts:13/:20` declares/builds the offer; `frontend/src/contexts/WebSocketContext.tsx:296` sends the existing builder's result. The exact server-response classifier at :64 and capability handling at :141 must retain their response role.
- `frontend/src/types/ws-protocol.ts:655` contains the public client-message request union.

## Intended behavior

1. The client offer and public client-message type use `terminal-binary:negotiate`. Version, flag mask, subprotocol, kill switch, eligibility and channel behavior stay under their existing contracts.
2. The pure server validator rejects a missing or incorrect request type using the existing `invalid-message` reason. A capability-shaped client request must not become a negotiate alias. Preserve the existing rejection reason enum and precedence for correctly typed offers.
3. Exercise the real router message dispatch: a valid negotiate request reaches existing negotiation and produces capability or the applicable rejected response. A legacy capability request is observably rejected without enabling binary. Retain an explicit dispatcher rejection path through the type-checking validator; simply deleting the old case and leaving the sender unanswered is insufficient. Do not prove routing solely by directly calling a private handler.
4. The browser owns only the existing server-response types capability/rejected/channel-retired. It must not consume negotiate or unknown-channel as a server negotiation response. Unknown-channel recovery and all accepted capability-response assertions remain unchanged.
5. A connection that has never negotiated remains on its existing JSON path after a rejected old request. Already-negotiated failure/rollback behavior must be inspected separately and recorded against AC-4; this discriminator change does not establish epoch migration, fresh-checkpoint rollback or complete binary delivery. Do not use an implicit mid-epoch JSON switch to make a test pass.

Independent review identified the concrete AC-4 audit path: successful negotiation followed by a rejected renegotiation. The current group retains `negotiated` and its acceptance on rejection, while the browser warns without resetting its channel table. There is no demonstrated fresh stream epoch/checkpoint rollback on that path. Keep this as an explicit full-goal follow-up; neither preserving nor renaming the request type proves AC-4.
