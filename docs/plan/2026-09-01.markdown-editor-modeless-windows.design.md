# 마크다운 편집기 모달리스 창 설계

- 작성일: 2026-09-01
- 브랜치: `feature/markdown-editor`
- 상태: 설계 확정, 구현 계획 수립 대기

## 1. 개요

DocuLight2.0 의 마크다운 편집기를 BuilderGate 로 이식하고, 그 편집기를 담을 모달리스 창 시스템을 세운다. 사용자는 세션의 작업 경로에서 우클릭하여 `CLAUDE.md` · `CLAUDE.local.md` · `AGENTS.md` 를 편집할 수 있어야 하며, 편집 창은 여러 개를 동시에 띄우고 클릭으로 앞뒤 순서를 정할 수 있어야 한다.

**버튼 명칭 대응.** 요구사항의 용어와 이 문서의 용어를 아래와 같이 대응시킨다.

| 요구사항 용어 | 이 문서의 용어 | 결과 |
| --- | --- | --- |
| 최대화 | 최대화 | 터미널 스테이지 영역 전체 (`stage`) |
| 터미널 내에서 최대화 | 터미널 채움 | 그 세션의 터미널 영역. 아래 경로 표시줄 28px 은 덮지 않는다 (`docked`) |
| 최소화 | 최소화 | 화면에서 감추고 트레이에만 남김 |

## 2. 조사 결과

구현에 앞서 두 코드베이스를 전수 조사하고, 그 결과를 두 차례 코드와 대조하여 검증했다. 설계 판단의 근거가 되는 사실을 아래에 정리한다.

### 2.1 DocuLight2.0 편집기

| 항목 | 확인된 사실 |
| --- | --- |
| 패키지 | `packages/editor` (`@doculight/editor`) |
| 규모 | `src/` 의 `.ts`/`.tsx` 25개(`__tests__/` 10개 제외) + CSS 2개 = 27개 파일 / 7,333줄 |
| 실체 | CodeMirror 6 기반. `src/vendor/atomic-editor/` 는 `kenforthewin/atomic-editor` v0.6.2 의 MIT 벤더링 사본이다 |
| 벤더 수정 | 도입 커밋 `fc4ded1` 이후 DocuLight 이 벤더 디렉터리를 7건의 커밋으로 고쳤다(소스 5건, 테스트 전용 2건). 커밋 제목으로는 판별되지 않는다 — `be66168` 은 `docs(spec):` 접두사를 달고 있으나 실제로는 `table-widget.ts` 를 고쳤다. 도입 시점 대비 순 증분은 `table-widget.ts` +210/-16, `inline-preview.ts` +22/-1 이며, 테스트 파일 `__tests__/table-reveal-state.test.ts` 1개(+209줄, 케이스 8개)가 추가되었다. `src/vendor/UPSTREAM.md` 의 "적용한 패치" 표는 갱신되지 않은 채 "(아직 없음)" 으로 남아 있으므로 그 표를 신뢰하면 안 된다 |
| 결합도 | `packages/editor/src` 전체에서 `fetch(` · `/api/` · `useContext` · `localStorage` · `react-router` 검색 결과가 0건이다. 단독 실행 데모(`packages/editor/demo/`)가 앱 없이도 동작함을 증명한다 |
| 외부 접점 | `doculightExtensions` 의 optional 콜백 5개(`onTagClick` · `onAttach` · `suggestWikiLinks` · `onOpenWikiLink` · `resolveWikiLink`)뿐이다 |
| 스타일 | 전역 CSS 두 파일(`src/styles/editor.css` 129줄, `vendor/atomic-editor/styles/inline-preview.css` 830줄). 클래스 대부분이 `.dl-*` · `.cm-atomic-*` · `.atomic-*` 로 namespace 되어 있으나, `.cm-content` · `.cm-line` · `.cm-searchMatch` 와 `.katex-*` 는 CodeMirror·KaTeX 의 전역 이름이다. BuilderGate 가 두 라이브러리를 쓰지 않으므로 실제 충돌은 없다 |
| 테마 변수 | `--atomic-editor-*` 31종. 정의되지 않은 7종은 사용처에 인라인 fallback 이 붙어 있어 호스트가 아무것도 정의하지 않아도 렌더된다. 기본값이 다크 계열이다 |
| 저장 로직 | 편집기 패키지에 없다. `packages/web/src/document/` 의 `DocumentSurface.tsx` · `useAutosave.ts` · `autosave.ts` 가 담당한다 |
| 키맵 | 편집기가 등록하는 CodeMirror 키맵에 `Ctrl+S`(`Mod-s`)가 없다. 따라서 호스트가 그 조합을 저장에 써도 편집기 동작을 빼앗지 않는다 |

편집기가 강제하는 계약이 둘 있으며, 이식할 때 반드시 지켜야 한다.

1. **`markdownSource` 는 controlled value 가 아니다.** 마운트 시점에 한 번만 읽히고 그 뒤로는 편집기가 문서의 정본이다. 타이핑마다 값을 되돌려 넣으면 안 된다.
2. **문서 교체는 `documentId` prop 으로 한다.** 생략하면 `markdownSource` 문자열 자체가 문서의 정체성이 되어, 저장 응답이 새 본문을 내려보낼 때마다 EditorView 가 파괴·재생성되고 포커스와 입력이 유실된다. DocuLight 의 커밋 `f54ee4e fix(web): 저장이 편집기를 갈아 끼우지 않게 한다` 가 이 계약의 근거다.

`extensions` 배열도 마운트 시점에 포획되므로 `useMemo` 로 참조를 고정해야 한다. `readOnly` 만은 `Compartment` 기반이라 토글해도 재마운트가 일어나지 않는다.

**이 두 계약이 최소화 설계를 구속한다.** 편집기를 언마운트하면 그 안의 편집 내용이 사라지고, 다시 마운트하면 `markdownSource` 로 준 값에서 다시 시작한다. 따라서 최소화는 언마운트가 아니라 감추기여야 한다.

**의존성 버전 차이.** 편집기는 `mermaid ^11.4.1` 을 요구하는데 BuilderGate 는 `mermaid ^10.9.5` 다. `^10.9.5` 는 `^11.4.1` 을 만족하지 않으므로 메이저 업그레이드가 필요하다.

| 10001 | `ContextMenu.css:17` | 서브메뉴. 프로젝트 최댓값 |

**`3000`~`5000` 사이의 z-index 는 프로젝트 전체에 0건이다.** 편집기 창의 대역을 그 구간에 두는 근거가 된다.

`ConfirmModal` 은 `WindowDialog` 를 쓰지 않는다는 점이 중요하다. `createPortal` · `inert` · 포커스 트랩이 없고 Escape 처리만 있으며(`ConfirmModal.tsx:23-29`), `.modal-overlay` 의 `z-index: 9999` 를 쓴다. 그 클래스는 `Modal/RenameModal.css:1` 에만 정의되어 있고 `ConfirmModal.css` 에는 없다.

- Active Target 은 `wave-5` 이고 work mode 는 `sdd` 이며 Active Task 는 없다.
- 마크다운·편집기·모달리스 창 관련 요구사항은 `docs/spec/` 에 0건이다.
- scope SRS 문서의 최대 번호는 `40` 이므로 새 문서는 `41` 이다.
- 컨텍스트 메뉴 요구사항 `FR-ARCH-001`~`006` 이 `Stability=stable` 로 존재한다.

## 4. 아키텍처

### 4.1 창의 상태 모델

창은 **배치 상태 하나**와 **감춤 플래그 하나**를 가진다. 최소화를 배치 상태와 같은 축에 두면 "직전 상태" 정의가 성립하지 않는 전이 조합이 생기므로 축을 분리한다.

**배치 상태** — `docked` · `stage` · `floating` 중 하나.

| 상태 | rect |
| --- | --- |
| `docked` (기본) | 창이 매인 **탭**의 터미널 영역. 계단식 오프셋을 적용한다 |
| `stage` | 터미널 스테이지 영역 전체 |
| `floating` | 사용자가 놓은 자리. `docked` 나 `stage` 에서 드래그로 진입할 때는 그 직전의 rect 를 그대로 계승한다 |

**감춤 플래그** — `minimized`. 참이면 창 표면에 `display: none` 을 걸되 **언마운트하지 않는다.** 편집기 인스턴스와 본문 ref 가 그대로 살아 있어야 복원했을 때 편집 내용이 남는다.

**버튼 동작.**

| 버튼 | 동작 |
| --- | --- |
| 터미널 채움 | 배치 상태를 `docked` 로 바꾼다. 이미 `docked` 면 비활성으로 표시한다 |
| 최대화 | `stage` 가 아니면 직전 배치 상태를 기록하고 `stage` 로 바꾼다. 이미 `stage` 면 기록해 둔 상태로 돌아간다. 기록이 없으면 `docked` 로 간다 |
| 최소화 | `minimized = true` |
| 트레이에서 선택 | 감춤 사유를 해소하고 맨 앞으로 올린다 (§4.9) |
| 드래그·리사이즈 | 배치 상태를 `floating` 으로 바꾼다 |

직전 상태는 `stage` 로 들어갈 때만 기록하므로, 세 배치 상태의 어떤 전이 조합에서도 목적지가 정의된다.

**`docked` 의 대상은 터미널 영역이다.** 요구사항이 "터미널 위를 덮는" 것이므로, 탭 영역 전체가 아니라 xterm 이 실제로 차지하는 rect 를 대상으로 삼는다. 그 rect 는 `TerminalHostSlot` 이 `upsertHost(tabId, …)` 로 등록하고 `TerminalRuntimeLayer` 가 터미널 배치에 쓰는 값을 그대로 읽는다. 새로 측정하는 코드를 만들지 않는다. 등록된 좌표가 `TerminalRuntimeLayer` 의 오버레이 div 상대이고 창은 portal 로 `document.body` 에 붙으므로, 그 오버레이의 `getBoundingClientRect()` 를 더해 뷰포트 좌표로 바꾼다.

**가시성 판정은 rect 값이 아니라 `isVisible` 필드로 한다.** `TerminalRuntimeLayer` 가 쓰는 것과 같은 식을 쓴다.

```
배치 가능 = host 가 존재하고
          && host.isVisible
          && host.rect.width > 0
          && host.rect.height > 0
```

rect 값만 보면 안 되는 이유가 둘이다. 등록 좌표가 스테이지 상대값이라 감춰진 슬롯은 `{0,0,0,0}` 이 아니라 사이드바 너비만큼 음수가 되고, 슬롯이 언마운트되면 엔트리 자체가 삭제되어 조회 결과가 `undefined` 다. `{0,0,0,0}` 을 조건으로 삼으면 프로덕션에서 그 판정이 한 번도 참이 되지 않고, 그 값을 손으로 만들어 넣은 테스트만 통과한다.

**레지스트리는 React context 다.** `hosts` 는 `TerminalRuntimeProvider` 의 context 값이므로 창 컴포넌트가 그 provider 안에 렌더되어야 읽을 수 있다. 그 provider 는 `App.tsx:623`~`:716` 에만 있고 그 구간은 `wm.activeWorkspace` 가 있을 때만 렌더된다(`App.tsx:606`·`:718`). 화면 전환은 `display:none` 이라 언마운트되지 않지만, **마지막 워크스페이스를 삭제하면 provider 째로 언마운트되어 창도 함께 사라진다.** 그 경우 미저장 본문을 잃는다. 워크스페이스 삭제는 명시적인 파괴 조작이므로 그대로 두고 §10 에 제약으로 기록한다.

**`tabId` 에서 현재 `sessionId` 를 얻는 경로.** `useWorkspaceManager` 의 `tabs` 가 전 워크스페이스를 담은 평면 배열이므로 `wm.tabs.find(t => t.id === tabId)?.sessionId` 로 조회한다. 이 훅은 `App.tsx:128` 한 곳에서만 호출되고 context provider 가 없으므로, 조회 함수를 `AppContent` 에서 창 관리자로 prop 으로 내려보낸다. 새 context 를 만들지 않는다.

이 정의의 결과가 셋이다.

- **경로 표시줄(28px)이 가려지지 않는다.** 창이 떠 있어도 우클릭으로 다른 파일을 열 수 있다.
- **`docked` 와 `stage` 가 항상 다르다.** 탭 모드에서도 최소한 경로 표시줄 28px 만큼 차이가 나므로, 두 버튼이 같은 결과를 내는 상황이 생기지 않는다.
- **뷰 모드별로 분기할 필요가 없다.** 그리드 모드에서는 타일 안의 터미널 영역이, 탭 모드에서는 스테이지에서 경로 표시줄을 뺀 영역이 같은 레지스트리에서 나온다.

**계단식 오프셋.** 창을 새로 열 때, **같은 `tabId` 에 매이고 배치 상태가 `docked` 인 창이 몇 개 존재하는지** 세어 그 수를 `k` 로 삼는다. 감춤 여부는 따지지 않으므로 최소화되었거나 비활성 탭에 있어 보이지 않는 창도 센다. `stage` 나 `floating` 인 창은 그 터미널 영역을 점유하지 않으므로 세지 않는다.

`k` 단계의 창은 `x + 28k`, `y + 28k`, `width - 28k`, `height - 28k` 에 놓는다. 즉 오프셋만큼 **크기를 줄여** 창이 대상 영역 안에 그대로 머문다. 크기를 줄이지 않고 위치만 옮기면 창이 반드시 대상 영역을 벗어나고, 벗어난 창을 되돌리는 규칙이 다시 오프셋을 0으로 만들어 모든 창이 완전히 겹친다. 그러면 계단식을 도입한 목적인 "뒤 창의 제목표시줄을 눌러 앞으로 가져오기" 가 성립하지 않는다.

`k` 는 0부터 3까지 쓰고 4가 되면 0으로 되감는다. 줄인 크기가 `WindowDialog` 의 `minSize`(`EditorWindow` 가 `320 × 240` 으로 준다)보다 작아지면 그 창도 `k = 0` 으로 놓는다.

**대상 영역 자체가 `minSize` 보다 작은 경우** — 타일을 잘게 나눈 상태가 그렇다 — 창은 `k = 0` 으로 놓고 **대상 영역의 크기를 그대로 쓴다.** `minSize` 를 만족시키려고 대상 밖으로 넘치게 하지 않는다. 대상보다 큰 창을 그 안에 넣을 방법은 없고, 넘친 창은 옆 타일의 터미널을 가린다.

**`k` 는 `docked` 에 진입할 때마다 다시 계산한다.** 창을 처음 열 때는 물론이고, `stage` 나 `floating` 에서 "터미널 채움" 으로 돌아올 때도 그 시점의 개수로 다시 센다. 창이 자기 `k` 를 계속 보유하면, 창 A 가 `floating` 으로 나가 있는 사이에 연 창 B 도 `k = 0` 을 받고 A 가 복귀할 때 둘이 정확히 겹친다.

중간의 창이 닫혀도 남아 있는 창의 위치는 그대로이고, 그 자리의 `k` 는 다음에 `docked` 로 진입하는 창이 가져간다.

**`stage` 의 경계.** `TerminalWorkspaceStage` 가 렌더하는 컨테이너(`App.tsx:103` 의 `div{flex:1, position:relative, overflow:hidden}`)를 ref 로 잡아 실측한다. 그 컨테이너가 이미 사이드바 220px, 헤더 58px, 탭바 36px 을 제외한 나머지이므로 상수를 복제하지 않는다. 상수를 두 곳에 두면 레이아웃이 바뀔 때 한쪽만 고쳐진다.

**좌표 가둠.** 세 배치 상태 모두 `EditorWindow` 가 rect 를 계산하여 controlled prop 으로 넘기며, `WindowDialog` 의 `clampDialogRect` 는 타지 않는다. `floating` 의 가둠은 `EditorWindow` 가 직접 수행하되 기준을 뷰포트가 아니라 터미널 스테이지 영역으로 삼는다. 그래야 사용자가 창을 사이드바나 헤더 위로 끌어다 놓을 수 없다. 요구사항은 "최대화 시켜도" 가리면 안 된다고만 했으나, 최대화 때만 막고 드래그로는 허용하면 규칙이 일관되지 않으므로 모든 이동에 같은 경계를 적용한다. `Rnd` 의 `bounds` 도 `"window"` 대신 스테이지 컨테이너를 가리키게 한다.

**초기 좌표.** `WindowDialog` 는 `readDialogGeometry` 로 저장된 좌표를 초기 state 에 넣는데, 이 읽기는 `persistGeometry` 와 무관하게 실행된다. `EditorWindow` 는 마운트 시점부터 controlled `rect` 를 넘겨 그 초기값이 화면에 반영되지 않게 한다.

**추적.** `TerminalHostSlot` 의 선례를 따라 `ResizeObserver` 와 `window.resize` 로 대상 rect 를 재측정하여 창 좌표에 반영한다.

**가시성.** 창은 아래 조건을 **모두** 만족할 때만 보인다. 하나라도 어긋나면 `display: none` 이며, 어느 경우에도 언마운트하지 않는다.

```
보임 = !minimized
     && screen === 'workspace'
     && 창의 워크스페이스 === 현재 워크스페이스
     && (그리드 모드이거나, activeTabId === 창의 tabId)
     && (배치 상태가 docked 가 아니거나, host.isVisible && rect.width > 0 && rect.height > 0)
```

마지막 조건은 `docked` 에만 적용된다. `stage` 와 `floating` 은 터미널 rect 를 쓰지 않기 때문이다.

첫 조건을 뺀 나머지는 시스템이 정하는 것이라 창의 버튼으로 해제되지 않는다. 최소화한 창의 탭을 다시 활성화해도 `minimized` 가 남아 있으면 여전히 보이지 않는다.

### 4.2 클릭으로 순서 정하기

이것이 요구사항의 핵심 동작이며, 현재 코드에 없는 기능이다.

`dialogStack.ts` 는 모듈 전역 배열을 `entries.push` 로만 관리하고 재정렬 API 가 없다. 따라서 두 가지를 더한다.

1. **스택을 종류별로 나눈다.** 하나의 전역 배열 대신 `modal` 과 `modeless` 두 스택을 둔다. 모달의 `isTopmost` 는 모달 스택 안에서만 판정한다.
2. **`raise(token)` 연산을 더한다.** 해당 항목을 스택 맨 뒤로 옮기고 구독자에게 알린다.

창 표면의 `pointerdown` 에서 `raise` 를 부른다. 캡처 단계에서 잡아 내부 요소를 눌러도 창이 올라오게 하되, `stopPropagation` 도 `preventDefault` 도 하지 않아 편집기의 입력을 방해하지 않는다.

**스택 순서는 z-index 산출에만 쓰고, 창의 마운트 순서는 생성 순서로 고정한다.** `raise` 가 DOM 노드를 옮기면 `pointerdown` 직후 노드가 재삽입되어 진행 중인 텍스트 선택 드래그가 끊긴다. 앞뒤는 z-index 로만 바꾼다.

스택을 나누는 것은 `raise` 때문만이 아니다. 하나의 스택에 섞으면 모달리스 창이 위로 올라가는 순간 모달의 `isTopmost` 가 거짓이 되어 Tab 가둠과 Escape 차단이 전부 꺼진다.

### 4.3 z-index 계층

**모달 대역을 올리지 않고 모달리스 대역을 내린다.**

| 계층 | z-index | 비고 |
| --- | --- | --- |
| 편집기 창 (모달리스) | `3000 + n * 20`, 상한 `3980` | `n` 은 0부터 세므로 50번째 창(`n = 49`)이 상한에 닿는다 |
| `WindowDialog` 모달 | `5000 + n * 20` | **변경 없음** |
| `.command-preset-toast` | `5100` | 변경 없음 |
| `ConfirmModal` | `9999` | 변경 없음 |
| 컨텍스트 메뉴 | `10000` · `10001` | 변경 없음 |

이 배치의 이점은 셋이다.

첫째, **기존 여섯 다이얼로그의 z-index 가 전혀 바뀌지 않는다.** 모달 대역을 위로 옮기면 `.command-preset-toast` 가 `WindowDialog` 바깥의 형제로 렌더되므로 다이얼로그 뒤로 숨는다. 대역을 그대로 두면 그 회귀가 아예 발생하지 않는다.

둘째, **모달·확인 팝업·컨텍스트 메뉴가 모두 편집기 창 위에 온다.** 설정 다이얼로그가 편집기에 가려지지 않는다.

셋째, **편집기 창 안에서 띄운 컨텍스트 메뉴가 창 위에 보인다.**

편집기 창은 `100` 과 `1000` 대역보다 위에 온다. 설정 화면(`SettingsPage.css:7`, `100`)은 §4.1 의 가시성 규칙이 창을 감추므로 가려지지 않고, 모바일 사이드바(`1000`)는 범위 밖이다.

다만 **폰트 크기 토스트**(`FontSizeToast.css:13`, `100`)는 워크스페이스 화면 안에서 뜨므로 `docked` 창이 그 타일을 덮는 동안 창 뒤로 숨는다. 터미널 폰트 크기를 바꾸는 조작은 터미널이 보일 때 하는 것이고, 편집기 창이 터미널을 덮고 있다면 그 토스트를 볼 이유도 없다. 이 프로젝트의 다른 요소를 고치지 않기 위해 그대로 두고 §10 에 제약으로 기록한다.

**`inert` 의 한계.** 모달은 마운트 시점의 `document.body.children` 스냅샷에만 `inert` 를 건다. 편집기 창이 먼저 열려 있고 그 뒤에 모달이 열리는 정상 흐름에서는 창이 스냅샷에 포함되어 조작 불가가 된다. 모달이 이미 떠 있는 동안에는 UI 가 잠겨 새 편집기 창을 열 수 없으므로 역순은 발생하지 않는다.

### 4.4 `WindowDialog` 에 가하는 변경

추가하는 prop 은 다섯이며 모두 optional 이다. 주지 않으면 현재 동작을 유지한다.

- `rect` · `onRectChange` — controlled 좌표. 주면 내부 state 대신 이 값을 쓰고 clamp 를 건너뛴다.
- `boundsElement` — `Rnd` 의 `bounds` 로 넘길 대상. 주지 않으면 현재대로 `"window"` 를 쓴다. `EditorWindow` 는 터미널 스테이지 컨테이너를 넘긴다.
- `titlebarActions` — 제목표시줄에 삽입할 추가 버튼. `showCloseButton` 이 렌더하는 닫기 버튼의 **좌측**에 놓인다. 창 상태 버튼은 `EditorWindow` 가 이 prop 으로 주입한다. `WindowDialog` 는 창 상태 개념을 알지 못한다.
- `dirty` — 제목 앞 `*` 표시 여부.

`windowDialogModel.ts:20` 의 `const layerZ = 5000 + input.layerIndex * 20;` 은 두 모드가 공유하는 하나의 산식이다. 여기에 **`mode` 에 따라 기저값을 가르는 분기**를 넣어 모달리스는 `3000`, 모달은 `5000` 에서 시작하게 한다. 모달 쪽 값은 바뀌지 않는다.

이 변경은 두 곳을 건드린다. `createWindowDialogBehaviorModel` 의 입력 타입(`windowDialogModel.ts:13-19`)에 `mode` 가 없고, 호출부(`WindowDialog.tsx:41-47`)도 `mode` 를 넘기지 않는다. `mode` 의 기본값을 `'modal'` 로 두면 반환 필드가 늘지 않으므로 기존 계약 테스트는 그대로 통과한다.

`useDialogStack` 을 두 스택 지원으로 바꾸고 `raise` 를 더하는 것은 기존 동작의 변경이므로, 모달 6곳의 동작이 그대로인지 회귀 테스트로 확인한다.

`EditorWindow` 는 `persistGeometry={false}` 를 **명시한다.** 이 prop 의 기본값이 `true` 이므로 생략하면 `writeDialogGeometry` 가 별도 저장소에 좌표를 또 기록하여 정본이 둘이 된다. 다만 이 prop 은 쓰기만 막고 읽기는 막지 못하므로(§2.2), 마운트 시점부터 controlled `rect` 를 넘겨 저장된 초기값을 무효화한다.

제목표시줄 최종 배치는 좌측부터 `* 제목`, 우측에 `저장 / 터미널 채움 / 최대화 / 최소화 / 닫기` 다섯 버튼이다.

### 4.5 탭 결속

**창은 탭에 매인다. 세션에 매이지 않는다.**

`WorkspaceTab` 은 `id` 와 `sessionId` 를 별개 필드로 갖고, `restartTab` 은 `tab.id` 를 유지한 채 `tab.sessionId` 만 새 세션으로 교체한다. 즉 세션 ID 는 탭의 생애에 걸쳐 안정적이지 않다. 게다가 `docked` rect 를 얻는 레지스트리가 `upsertHost(tabId, …)` 로 탭 ID 를 키로 쓰고, 활성 탭 판정도 `activeTabId === tab.id` 다. 창을 세션 ID 로 매면 rect 를 조회할 수 없고 탭 재시작 후 결속이 조용히 끊긴다.

따라서 창은 `tabId` 를 들고, **저장·읽기 API 를 부를 때만 그 시점의 `sessionId` 를 그 탭에서 다시 얻는다.** 그러면 탭을 재시작해도 편집 창이 살아남아 새 세션으로 계속 저장한다.

**탭이 살아 있으나 세션만 끊긴 상태**(재시작 대기 등)에서는 창을 그대로 두고 저장도 시도한다. 실패하면 오류로 표시할 뿐이며, `floating` 으로 떨어뜨리지 않는다. 창을 닫을 때도 일반적인 미저장 확인을 쓴다.

**탭이 닫히면** 창은 `floating` 으로 떨어지고 저장 경로를 잃는다. 이때 rect 는 **닫히기 직전에 화면에서 차지하던 뷰포트 좌표를 계승한다.** 대상 터미널 영역이 사라져 `docked` 를 다시 계산할 근거가 없기 때문이다.

**계승한 좌표에도 §4.1 의 가둠을 적용한다.** 마지막 탭이 닫혀 탭바가 사라지거나 스테이지가 좁아지면 계승한 좌표가 새 경계 밖일 수 있는데, 그때는 가둠이 이긴다. 화면 밖으로 나간 창은 제목표시줄을 누를 수단이 없어 되돌릴 방법도 없기 때문이다. 제목표시줄의 파일명 옆 배지로 그 사실을 표시하고 저장 버튼과 `Ctrl+S` 를 비활성화한다.

**탭이 닫힌 창을 닫으려 하면** "저장할 수 없습니다. 그래도 닫으시겠습니까?" 로 묻는다. 일반적인 미저장 확인과 분기가 다르다.

### 4.6 편집기 이식

`packages/editor/src` 를 `frontend/src/editor/` 아래로 구조 그대로 옮긴다. `vendor/atomic-editor/LICENSE` 는 MIT 고지 의무이므로 함께 유지한다. 벤더 디렉터리에 DocuLight 패치가 들어 있으므로 upstream 원본이 아니라 **DocuLight 의 현재 상태**를 복사한다.

추가할 의존성은 `@codemirror/*` · `@lezer/*` · `katex` · `shiki` 이며, 여기에 **`mermaid` 를 `^11.4.1` 로 올린다.** 현재 `^10.9.5` 는 편집기 요구를 만족하지 않는다. `mermaid` 는 이 프로젝트에서 사용처가 없으므로 업그레이드의 영향 범위가 편집기로 한정된다.

빌드 도구는 호스트 것을 쓴다. 편집기의 devDependency 는 `vite ^8.1.4` · `typescript ^7.0.2` 이고 BuilderGate 는 `vite ^7.2.4` · `typescript ~5.9.3` 이다. 소스를 복사해 넣으므로 편집기의 devDependency 는 따라오지 않지만, TypeScript 버전 차이로 컴파일 오류가 나올 수 있으므로 이식 직후 `tsc` 를 먼저 통과시킨다.

편집기 패키지에는 `peerDependencies` 선언이 없고 React 를 `dependencies` 로 직접 들고 있다. 소스를 복사해 넣으므로 중복 적재는 발생하지 않는다.

편집기를 감싸는 `EditorWindow` 컴포넌트가 `WindowDialog` 와 편집기를 잇는다. 이 컴포넌트가 `documentId` 를 **정규화한 절대 경로**로 준다. 창 하나가 파일 하나에 대응하므로(§4.8) 그 경로가 곧 문서의 정체성이다. 세션 ID 를 쓰면 탭을 재시작할 때 값이 바뀌어 편집기가 파괴·재생성되고 미저장 본문이 사라진다.

호스트가 `<html data-theme>` 규약을 쓰지 않으면 mermaid 다이어그램만 다크로 남는다. 이 프로젝트는 다크 고정이므로 편집기 기본값과 어긋나지 않아 별도 조치가 필요 없다.

### 4.7 파일 입출력 경로

**서버.** `POST /api/sessions/:id/files/write` 를 신설한다. 읽기 경로가 쓰는 두 단계를 그대로 따른다.

1. `resolveAndValidate(cwd, filePath, blockedPaths)` — 디렉터리 탈출과 차단 경로를 막는다.
2. `isBlockedExtension` — 차단 확장자를 막는다. `resolveAndValidate` 는 확장자를 보지 않으므로 이 검사가 별도로 필요하다.

요청 본문은 `{ path, content }` 다. 파일이 없으면 생성하고, 있으면 덮어쓴다. 인코딩은 UTF-8 이며 BOM 을 붙이지 않는다. 줄바꿈은 편집기가 내보낸 문자열을 변환 없이 그대로 쓴다. 접근 범위는 세션 cwd 하위로 한정된다.

**프론트엔드.** `frontend/src/services/api.ts` 의 `fileApi` 에 `writeFile(sessionId, path, content)` 를 추가한다.

**저장과 dirty.** 본문 정본은 React state 가 아니라 ref 한 곳에만 둔다. 편집기가 `markdownSource` 를 controlled value 로 다루지 않기 때문에, 정본을 두 곳에 두면 어느 쪽이 최신인지 판정할 근거가 사라진다.

`Ctrl+S` 는 **DOM 포커스가 그 창 안에 있을 때**만 동작한다. 모달리스 스택의 최상위인지는 보지 않는다. 트레이에서 막 복원한 창은 맨 앞에 있지만 포커스가 없을 수 있고, 그 상태에서 다른 창의 편집 중인 내용이 저장되면 사용자가 의도하지 않은 파일이 바뀐다. 저장 함수는 제목표시줄 저장 버튼과 같은 것을 쓴다. 저장에 성공하면 `*` 가 사라진다.

편집기가 등록하는 CodeMirror 키맵에 `Ctrl+S` 가 없으므로 편집기와 충돌하지 않는다. 다만 브라우저 기본 동작을 막기 위해 `preventDefault()` 를 호출해야 한다. 터미널이 포커스를 가진 상태에서는 기존 xterm 처리를 방해하지 않는다.

**오류 표시.** 읽기·쓰기 실패는 해당 창의 제목표시줄 아래 배너로 표시한다. 창이 아직 없는 단계(읽기 실패)의 오류는 기존 `MessageBox` 로 알린다.

### 4.8 컨텍스트 메뉴

`MetadataRow.tsx` 의 `.metadata-cwd-path` 에 `onContextMenu` 를 붙인다. 기존 `onClick={handleCopy}` 는 그대로 둔다. `<MetadataRow>` 렌더 지점이 둘이므로 탭 모드와 그리드 모드 양쪽에 적용한다.

항목 조립은 새 빌더 함수가 담당한다. 기존 `contextMenuBuilder.ts` 를 건드리지 않아 `FR-ARCH-004`~`006` 계약과 엮이지 않는다. `ContextMenu.tsx` 와 다단계·뷰포트·모바일 모듈도 수정하지 않는다. 서브메뉴를 만들지 않으므로 `FR-ARCH-001` 의 깊이 상한 5에 걸리지 않는다.

파일이 없으면 기존 `ConfirmModal` 로 생성 여부를 묻고, 확인하면 빈 파일을 만든 뒤 편집 창을 연다. `ConfirmModal` 은 `inert` 를 걸지 않지만, 이 시점에는 아직 해당 편집기 창이 없으므로 문제가 되지 않는다.

**이미 열려 있는 파일을 다시 고르면 새 창을 만들지 않고 기존 창을 앞으로 올린다.** 감춰져 있으면 §4.9 의 절차대로 되살린다.

**중복 판정 키는 정규화한 절대 경로다.** 탭 ID 와 경로의 쌍으로 판정하면, 같은 `cwd` 를 가진 두 탭에서 각각 `CLAUDE.md` 를 열었을 때 같은 디스크 파일을 편집하는 창이 둘 생긴다. 충돌을 감지하지 않기로 했으므로(§3) 두 창은 서로의 저장을 조용히 덮어쓴다. `tab.cwd` 가 절대 경로이므로 `cwd` 와 파일명을 합쳐 정규화한 값을 키로 쓴다.

심볼릭 링크 해석은 서버(`pathValidator.ts:61-67`)에서만 일어나므로 프론트엔드의 키는 정규화까지다. 링크로 이어진 서로 다른 `cwd` 두 개는 여전히 창을 둘 만든다. 드문 경우이므로 §10 에 제약으로 기록한다.

다른 탭에 매인 창이 이미 그 파일을 열고 있으면 그 창을 되살린다. 즉 창은 처음 연 탭에 계속 매인다.

**새 창을 만드는 사용자 조작의 진입점은 이 컨텍스트 메뉴 하나다.** 새로고침 후의 복원(§4.10)은 사용자 조작이 아니라 저장된 상태의 재구성이다.

### 4.9 최소화 트레이

`header-right` 안에 편집기 아이콘을 둔다. 요구사항의 "햄버거 버튼 좌측"은 데스크톱 우측 상단을 가리키는데, 실제 `.hamburger-button` 은 모바일 전용이고 좌측에 있으므로(§2.2), 데스크톱에서 그 자리에 해당하는 뷰 모드 토글 버튼의 좌측에 놓는다. 뷰 모드 토글이 렌더되지 않는 경우에는 `header-right` 의 첫 번째 자리에 놓는다.

**현재 워크스페이스에 창이 하나라도 있을 때만** 표시한다. 목록의 범위와 같은 기준이라야 아이콘은 떠 있는데 목록이 비는 상황이 생기지 않는다. 표시 여부는 이 아이콘 자체의 조건식으로 정한다. `Header.tsx:110` 의 바깥 조건식은 `App.tsx:584-587` 이 콜백을 무조건 넘겨 항상 참이므로, 거기에 콜백을 더해도 표시·숨김에 영향이 없다.

누르면 기존 `ContextMenu` 로 문서 목록이 뜬다. **현재 워크스페이스에 속한 창 전체**가 최소화 여부와 무관하게 나오며, 미저장 문서에는 `*` 를 붙인다. 다른 워크스페이스의 창은 목록에 넣지 않는다. 그 창을 보이게 하려면 워크스페이스부터 옮겨야 하는데, 트레이 항목 하나가 워크스페이스를 바꾸는 것은 사용자가 예상하기 어렵다.

항목을 고르면 §4.1 의 가시성 조건 중 **해소할 수 있는 것을 모두 해소한 뒤** 맨 앞으로 올린다. 구체적으로 `minimized` 를 풀고, 설정 화면에 있으면 워크스페이스 화면으로 돌아가며, 탭 모드에서 그 창이 매인 탭이 비활성이면 그 탭으로 전환한다. `minimized` 만 풀면 나머지 조건에 막혀 화면에 아무 변화가 없다.

요구사항의 "선택하여 이것만 출력 가능합니다" 는 최소화한 여러 문서 가운데 고른 것을 되살린다는 뜻으로 읽는다. 고른 창만 남기고 나머지를 감추는 배타적 동작으로는 해석하지 않는다. 바로 뒤 문장이 "문서 편집창을 동시에 여러개 띄울수 있습니다" 이므로, 다른 창을 감추는 동작은 그 문장과 어긋난다.

### 4.10 워크스페이스별 영속화

`frontend/src/hooks/windowStateStorage.ts` 에 `window_state_<workspaceId>` 키로 저장하고, `useWindowState(workspaceId)` 훅이 그것을 감싼다. `mosaicLayoutStorage.ts` 와 `useMosaicLayout.ts` 의 계층 분리를 그대로 따른다.

저장하는 것은 창 목록(**탭 ID**, 파일 경로, 배치 상태, `stage` 직전 상태, `minimized`, `floating` 좌표, 스택 순서)이며 본문은 저장하지 않는다. 계단식 단계 `k` 도 저장하지 않는다. 복원할 때 스택 순서대로 창을 만들면서 `docked` 진입 규칙(§4.1)이 다시 계산하므로 같은 배치가 재현된다. 세션 ID 는 저장하지 않는다. 탭 재시작으로 값이 바뀌기 때문이며, 필요한 시점에 탭에서 다시 얻는다(§4.5). 복원할 때 파일을 디스크에서 다시 읽는다.

**복원 시 `docked` rect 측정은 그 탭이 보이게 된 뒤로 미룬다.** 비활성 탭의 슬롯은 `isVisible` 이 거짓이고 `width`·`height` 도 0 이라, 그 값으로 창을 배치하면 크기가 0 이 된다. §4.1 의 배치 가능 조건이 참이 될 때까지 창을 감춘 채로 둔다. §4.9 의 트레이 복원도 같다 — 탭을 전환한 뒤에 측정해야 한다.

**워크스페이스를 전환해도 창은 언마운트되지 않는다.** §4.1 의 가시성 규칙이 감출 뿐이므로, 돌아오면 미저장 본문이 그대로 남아 있다. 이 저장소는 새로고침 이후의 재구성에만 쓰인다. 즉 세션이 살아 있는 동안의 본문 보존은 런타임 메모리가 담당하고, 이 저장소는 창의 배치만 담당한다.

`floating` 좌표의 정본은 이 저장소 하나다. `persistGeometry={false}` 로 기존 저장 경로를 끈다(§4.4). `docked` 와 `stage` 는 저장하지 않고 §4.1 이 매번 실측한다.

**스택 순서는 현재 워크스페이스의 창에 대해서만 복원한다.** 스택 자체는 전역이지만(§4.2) 저장은 워크스페이스별이므로, 복원 시에는 그 워크스페이스의 창들을 저장된 상대 순서대로 스택에 넣는다. 다른 워크스페이스의 창은 이미 스택에 있던 자리를 유지한다.

## 5. 데이터 흐름

```
세션 경로 우클릭 (그 탭의 tabId 와 cwd 를 얻는다)
  → 컨텍스트 메뉴 (CLAUDE.md / CLAUDE.local.md / AGENTS.md)
  → 같은 절대 경로를 연 창이 이미 있으면 → 되살리고 raise 한 뒤 끝
  → fileApi.readFile(tab.sessionId, path)
      ├ 성공  → 편집 창 열기 (tabId 에 매고 docked)
      └ 404   → ConfirmModal "파일이 없습니다. 새로 생성하겠습니까?"
                  → 확인 → fileApi.writeFile(tab.sessionId, path, '')
                          → 편집 창 열기 (tabId 에 매고 docked)

편집 중
  → onMarkdownChange → lastBody ref 갱신 + dirty = true → 제목에 * 표시

창 표면 pointerdown
  → modelessStack.raise(token) → 그 창이 맨 앞으로

Ctrl+S 또는 저장 버튼 (그 시점의 tab.sessionId 를 다시 얻는다)
  → fileApi.writeFile(tab.sessionId, path, lastBody)
      ├ 성공 → dirty = false → * 제거
      └ 실패 → dirty 유지 + 창 안 배너로 오류 표시

창 닫기
  ├ 저장 가능 + dirty → "저장하시겠습니까?"
  │     ├ 저장 → 성공하면 닫고, 실패하면 닫지 않고 오류를 표시한다
  │     ├ 저장 안 함 → 닫는다
  │     └ 취소 → 닫지 않는다
  ├ 저장 불가(탭 닫힘) + dirty → "저장할 수 없습니다. 그래도 닫으시겠습니까?"
  └ dirty 아님 → 바로 닫는다
```

## 6. 오류 처리

| 상황 | 처리 |
| --- | --- |
| 파일 읽기 실패 (404 이외) | 창을 열지 않고 `MessageBox` 로 알린다 |
| 저장 실패 | `dirty` 를 유지하고 창 안 배너로 표시한다 |
| 미저장 상태에서 닫기 | 저장 여부를 묻는다. 저장을 택했는데 실패하면 창을 닫지 않고 오류를 표시한다 |
| 탭 재시작 (세션만 교체) | 창을 유지한다. 다음 저장은 새 세션으로 간다 |
| 세션만 끊긴 상태에서 닫기 | 일반적인 미저장 확인을 쓴다. 저장을 택하면 시도하고, 실패하면 닫지 않는다 |
| 탭 닫힘 | 창을 `floating` 으로 떨어뜨리고 저장을 차단한다. 미저장 본문은 화면에 남지만 저장할 수 없다 |
| 탭 닫힘 후 창 닫기 | 저장할 수 없음을 알리고 닫을지 묻는다 |
| 복원 시 탭 부재 | 그 창은 복원하지 않는다 |
| 경로 검증 실패 | 서버가 거부하고 프론트엔드는 오류를 표시한다 |

## 7. 테스트 전략

TDD 를 적용한다. 요구사항별로 실패하는 테스트를 먼저 작성하고 red 를 확인한 뒤 구현한다.

**서버 단위 테스트** — 쓰기 경로의 경로 탈출 차단, 차단 확장자 거부, 신규 파일 생성, 기존 파일 덮어쓰기, cwd 밖 접근 거부, UTF-8 인코딩과 줄바꿈 보존.

**프론트엔드 단위 테스트** (`frontend/tests/unit/`, node:test) — 배치 상태 전이와 `stage` 토글 시 직전 상태 복원, `minimized` 플래그가 배치 상태와 독립인 것, `docked`·`stage` rect 계산, **계단식 오프셋이 항상 대상 영역 안에 머무는 것**과 다섯 번째 창에서 `k = 0` 으로 되감기는 것, `minSize` 미만이면 `k = 0` 으로 떨어지는 것, 감춰진 창도 `k` 계수에 포함되는 것, 가시성 논리곱이 다섯 조건 각각에서 거짓이 되는 것과 rect 조건이 `stage`·`floating` 에는 적용되지 않는 것, `floating` 으로 나갔던 창이 `docked` 로 복귀할 때 `k` 가 다시 계산되어 다른 창과 겹치지 않는 것, 두 스택 분리와 `raise` 후의 순서, z-index 상한, dirty 전이, 영속화 직렬화와 역직렬화.

**E2E 테스트** (`frontend/tests/e2e/`) — 경로 우클릭으로 메뉴가 뜨는 것, 없는 파일에 대해 확인 팝업이 뜨고 생성되는 것, 편집 시 `*` 가 붙고 `Ctrl+S` 로 사라지는 것, 제목표시줄 저장 버튼으로도 `*` 가 사라지는 것, **창 두 개를 띄웠을 때 뒤 창의 일부가 보이고 그것을 클릭하면 앞으로 오는 것**, **최소화 후 트레이에서 복원했을 때 미저장 편집 내용이 남아 있는 것**, **창이 떠 있는 상태에서도 경로 표시줄을 우클릭할 수 있는 것**, **같은 파일을 다시 골랐을 때 창이 하나로 유지되는 것**, **`cwd` 가 같은 두 탭에서 같은 파일을 열어도 창이 하나인 것**, **탭을 재시작해도 창이 살아남고 새 세션으로 저장되는 것**, **탭을 전환했다가 돌아왔을 때 창이 다시 나타나고 미저장 내용이 남아 있는 것**, 최대화가 사이드바 220px·헤더 58px·탭 모드의 탭바 36px 을 침범하지 않는 것, **`WindowDialog` 기반 모달(설정·MCP)이 열렸을 때 그 모달이 편집기 창보다 위에 오고 편집기가 조작 불가가 되는 것**.

`ConfirmModal` 은 `inert` 를 걸지 않으므로 모달 잠금 테스트의 대상이 아니다.

기존 회귀를 보려면 `CLAUDE.md` 의 테스트 표에 있는 스위트를 모두 돌려야 한다. 특히 두 곳을 확인한다.

- `useDialogStack` 변경이 모달 6곳의 포커스 트랩과 Escape 처리에 영향을 주는지.
- **`frontend/tests/unit/windowDialogContract.test.ts`.** 이 테스트가 `createWindowDialogBehaviorModel(...)` 의 반환값 **전체**를 `assert.deepEqual` 로 고정한다. 계획한 변경은 입력에 `mode` 를 더할 뿐 반환 필드를 늘리지 않으므로 기본값을 `'modal'` 로 두면 그대로 통과해야 한다. 통과하지 않는다면 의도하지 않은 반환 변경이 섞인 것이므로 그 자체가 신호다. 서버 build 를 트리거하는 명령이 많고 evidence-bundle 검증이 실패하면 테스트와 무관한 이유로 red 가 되므로, 진단 전에 build 로그를 먼저 확인한다.

## 9. 범위 밖

- 임의 파일을 고르는 파일 탐색기 UI. 내부 API 는 임의 경로를 받도록 만들되 UI 진입점은 세 파일로 제한한다.
- 새로고침 이후의 미저장 본문 복원. 세션 안에서는 최소화·워크스페이스 전환·화면 전환 모두 본문을 유지한다.
- 저장 시 외부 변경 충돌 감지.
- 편집기의 첨부 업로드·위키링크 기능. 콜백을 주지 않으면 비활성 상태로 남는다.
- 모바일 레이아웃에서의 창 동작.
- 라이트 테마 대응. 프로젝트가 다크에 고정되어 있다.

## 10. 알려진 제약

- mermaid 초기화가 1회뿐이라 런타임 테마 전환이 반영되지 않는다. 이 프로젝트는 다크 고정이므로 문제가 되지 않는다.
- 파일 접근이 세션 cwd 하위로 한정된다. 세션 밖의 파일은 열 수 없다.
- 탭이 닫히면 그 창의 미저장 본문을 저장할 방법이 없다.
- **브라우저를 새로고침하면 미저장 본문이 사라진다.** 창의 배치는 복원되지만 본문은 디스크에서 다시 읽기 때문이다.
- **탭이 닫힌 창은 새로고침을 넘기지 못하고 사라진다.** §4.10 이 탭 ID 를 저장하고 복원 시 탭이 없으면 복원하지 않기 때문이다. 두 규칙이 만난 귀결이며 의도한 것이다 — 저장할 수 없는 창을 되살려도 할 수 있는 일이 없다.
- 편집기 창이 50개(`n = 49`)에 이르면 z-index 가 상한 `3980` 에 닿고, 그 뒤로 여는 창들은 같은 값을 공유해 앞뒤가 마운트 순서로 결정되며 클릭해도 바뀌지 않는다.
- `docked` 창이 터미널을 덮고 있는 동안 그 타일의 폰트 크기 토스트가 창 뒤로 숨는다.
- **마지막 워크스페이스를 삭제하면 편집기 창이 함께 사라지고 미저장 본문을 잃는다.** 창이 `TerminalRuntimeProvider` 안에 렌더되는데 그 provider 가 활성 워크스페이스와 함께 언마운트되기 때문이다.
- 심볼릭 링크로 이어진 서로 다른 경로에서 같은 파일을 열면 창이 둘 생긴다. 링크 해석이 서버에서만 일어나기 때문이다.
- 같은 탭에 `docked` 로 다섯 번째 창을 열면 계단식 오프셋이 `k = 0` 으로 되감기므로 첫 창과 정확히 겹친다. 그 창은 트레이를 통해서만 앞으로 가져올 수 있다. 한 터미널 위에 창을 다섯 개 이상 겹쳐 두는 사용이 드물다고 보아 절충한 것이다.
- 프로젝트에 CSS 스코프 격리가 없다. 새 클래스에는 접두사를 둔다. 편집기 쪽 클래스는 대부분 namespace 되어 있으나 CodeMirror·KaTeX 의 전역 이름이 일부 섞여 있다.
- 벤더링 사본에 DocuLight 패치가 들어 있어 upstream 과 단순 대조가 되지 않는다. `UPSTREAM.md` 의 패치 표도 갱신되어 있지 않다.
