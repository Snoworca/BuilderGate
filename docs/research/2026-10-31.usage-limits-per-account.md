# 사용량 한도 막대를 계정별로 나누는 방법 조사

- 작성일: 2026-10-31
- 대상: 워크스페이스 목록 아래에 표시할 Claude Code · Codex 의 5시간/주간 사용량 막대
- 범위: 조사만 한다. 코드는 바꾸지 않았다.

## 1. 목적

사용량 막대를 **계정별로** 나눠 보여 줄 수 있는지 확인한다. 예를 들어 Claude 로그인이 둘이거나, Windows 와 WSL 이 서로 다른 계정으로 로그인했거나, `CLAUDE_CONFIG_DIR` · `CODEX_HOME` 이 여럿인 경우다. 각 사용량 측정값을 어느 계정의 것인지 안정적으로 판별할 수 있는지, 그리고 비밀값을 드러내지 않고 계정 이름을 표시할 방법이 있는지 본다.

지켜야 할 조건은 둘이다.

- 자격 증명(토큰·API 키·쿠키)의 값을 읽어 쓰거나 저장하거나 표시하지 않는다.
- 사용자의 구독 자격 증명으로 Anthropic/OpenAI API 를 호출하지 않는다(사내 규정: 구독 계정을 도구에 연결 금지). 로컬의 비밀이 아닌 파일만 읽는다.

## 3. Claude

### 3.1 무엇이 계정을 식별하는가

- **식별 키는 `oauthAccount.accountUuid` 다.** 계정마다 고유한 UUID 이고 비밀값이 아니다(F3).
- 같은 사람이 여러 조직(팀 · 개인 Max)에 속하면 한도가 조직 단위로 갈릴 수 있다. 그래서 키는 `accountUuid` 와 `organizationUuid` 를 함께 쓰는 것이 안전하다(추정: Claude 한도가 계정 단위인지 조직 좌석 단위인지 공식 근거를 이번에 확인하지 못함. 둘을 함께 쓰면 어느 쪽이든 틀리지 않는다).

### 3.2 릴레이가 계정을 알아내는 방법

statusLine stdin 에는 계정이 없으므로(F1), 릴레이가 실행될 때 **자기 환경에서 `.claude.json` 을 직접 읽는다.**

1. statusLine 명령은 Claude 프로세스의 자식으로 실행되므로 `CLAUDE_CONFIG_DIR` 을 물려받는다(추정: 자식 프로세스의 일반적인 환경 상속. 바이너리에서 statusLine 실행부의 env 처리까지는 확인하지 않음).
2. 경로 결정: `CLAUDE_CONFIG_DIR` 이 있으면 `$CLAUDE_CONFIG_DIR/.claude.json`, 없으면 `~/.claude.json`(F5). claude-hud 와 같은 규칙이다(F6).
3. `oauthAccount` 에서 `accountUuid`, `organizationUuid`, 그리고 표시용 비밀 아닌 필드만 꺼낸다. `.credentials.json` 은 읽지 않는다(F7).
4. `ANTHROPIC_API_KEY`(값 말고 **존재 여부만**)가 있으면 API 키 모드로 분류한다(F6). API 키 모드에서는 `rate_limits` 가 대개 오지 않는다(추정: 구독 한도가 없으므로. F2 에 따라 값이 없으면 필드 자체가 빠진다).
5. 보조 근거: stdin 의 `transcript_path` 는 `<설정 디렉터리>/projects/...` 아래를 가리키므로, `CLAUDE_CONFIG_DIR` 을 못 읽는 경우에도 설정 디렉터리를 거꾸로 알아낼 수 있다(추정: 경로 규칙은 관찰 기반이며 계약은 아님).

릴레이는 매 호출마다 `.claude.json` 을 다시 읽거나, claude-hud 처럼 파일의 mtime · 크기 · inode 를 키로 캐시한다. 그러면 `/login` 으로 계정이 바뀐 직후의 측정부터 새 계정으로 기록된다.

### 3.3 별칭과의 관계

`claudep` 같은 별칭은 계정을 바꾸지 않는다(F14). 계정을 가르는 것은 **명령 이름이 아니라 그 프로세스의 설정 디렉터리**다. 사용자가 `CLAUDE_CONFIG_DIR=... claude` 형태의 별칭을 만들어도 릴레이가 그 환경에서 실행되므로 자동으로 맞게 갈린다. 따라서 별칭 설정에 계정 필드를 추가할 필요는 없다.

## 4. Codex

### 4.1 무엇이 계정을 식별하는가

- **식별 키는 롤아웃 `session_meta.creator_account_id` 다**(F8). 롤아웃 파일 안에 이미 있으므로 자격 증명 파일을 열 필요가 없다. 같은 파일 안의 `rate_limits` 와 짝지으면 측정값마다 계정이 붙는다.
- `rate_limits.limit_id` · `plan_type` 은 계정 식별자가 아니다(F9). 표시용 보조 정보(요금제 이름)로만 쓴다.

### 4.2 `auth.json` 을 읽어도 되는가

- `auth.json` 의 `tokens.account_id` 는 그 자체로는 식별자이고, `id_token`(JWT)의 payload 에는 이메일 등이 들어 있다(추정: JWT 구조는 이번에 디코드하지 않음).
- 그러나 이 파일은 **access/refresh 토큰이 함께 든 자격 증명 파일**이다. 파일 전체를 메모리에 올리는 순간 토큰이 BuilderGate 프로세스에 들어오고, 로그 · 오류 덤프로 새어 나갈 경로가 생긴다. 사내 규정의 취지(자격 증명을 도구에 연결하지 않음)에도 어긋난다.
- **권장: 읽지 않는다.** 롤아웃의 `creator_account_id` 로 충분하다. 이메일 같은 표시 이름이 필요하면 사용자가 붙인 별명을 쓴다(6.4).

### 4.3 롤아웃에 식별자가 없을 때

- 오래된 CLI(0.104.0 등)의 롤아웃에는 `creator_account_id` 가 없다(F11). 그런 측정은 "계정 미상" 으로 분류하고, 같은 `CODEX_HOME` 의 최신 식별 측정과 **자동으로 합치지 않는다**.

### 4.4 `CODEX_HOME`

- Codex 는 `CODEX_HOME` 으로 홈을 바꿀 수 있다(F13). 여러 계정을 쓰는 사람은 홈을 나눠 쓸 가능성이 높다. 그러나 **한 홈 안에서도 계정이 바뀐다**(F10, `/login` 재실행). 따라서 홈은 "어디서 읽을지" 를 정하는 데만 쓰고, 계정 판별은 롤아웃 단위 `creator_account_id` 로 한다.

## 6. 권장 설계

### 6.1 계정 키

- 키 원본: Claude `claude:{accountUuid}:{organizationUuid}`, Codex `codex:{creator_account_id}`.
- **저장 · 전송 · 화면에는 원본이 아니라 해시를 쓴다.** 예: `sha256(키 원본)` 앞 16자. 계정 UUID 는 비밀은 아니지만 굳이 퍼뜨릴 이유가 없다.
- 식별 실패 시 키는 `{agent}:unknown:{환경}:{설정 디렉터리 해시}` 로 하고 "미상" 표시를 붙인다.

### 6.2 측정값을 어디에 저장하는가

- **Claude**: 릴레이가 stdin 을 원래 statusLine 명령으로 그대로 넘기고, 따로 아래 레코드 한 줄을 BuilderGate 로 보낸다(또는 BuilderGate 가 읽는 파일에 쓴다).
  `{ agent, accountKey, label 후보(비밀 아님), environment: "windows"|"wsl", configDir 해시, observedAt, five_hour, seven_day }`
  WSL 의 릴레이는 Windows 서버에 직접 닿기 어려울 수 있으므로(이 저장소의 CLAUDE.md: WSL 의 `localhost` 는 Windows 리스너에 닿지 않음), **각 환경의 설정 디렉터리 안 파일**(예: `<configDir>/buildergate-usage.json`)에 계정 키별 최신값을 쓰고 서버가 그 파일을 읽는 방식이 단순하다. Windows 서버는 `\\wsl.localhost\<배포판>\home\...` 경로로 WSL 파일을 읽을 수 있다(추정: 이번에 서버 쪽에서 실측하지 않음).
- **Codex**: 별도 장치가 필요 없다. 서버가 각 `CODEX_HOME`(Windows 홈, WSL 홈, 사용자가 등록한 추가 홈)의 최신 롤아웃 몇 개를 꼬리부터 읽어 `session_meta.creator_account_id` 와 마지막 `rate_limits` 를 짝짓는다. `auth.json` 은 열지 않는다.
- 서버는 계정 키별로 **가장 최근 측정 하나**만 유지한다. 합칠 때 기준은 `observedAt`.

### 6.3 UI 묶음

- 워크스페이스 목록 아래에 계정 하나당 한 블록. 블록 안에 5시간 · 주간 막대 두 개.
- 블록 제목: `{에이전트 아이콘} {표시 이름} · {요금제}` . 같은 계정이 두 환경에서 보이면 작은 표식(Win · WSL)만 붙이고 블록은 하나.
- 계정이 하나뿐이면 제목을 생략해 지금 디자인과 같은 모양으로 보인다. 계정이 둘 이상일 때만 이름이 나온다.
- "계정 미상" 블록은 맨 아래, 흐리게.

### 6.4 표시 이름(비밀 노출 없이)

우선순위:

1. 사용자가 붙인 별명(계정 키 해시 → 별명, BuilderGate 설정에 저장). 가장 안전하고 의미가 분명하다.
2. Claude: 가린 이메일(`i***@hancomins.com` 형태) 또는 `organizationName` + `organizationType`(팀 · Max). 단 `organizationName` 에 이메일이 그대로 들어간 경우가 있으므로(F4 Windows 쪽) 이메일 패턴은 같은 방식으로 가린다.
3. Codex: 롤아웃에는 이메일이 없으므로 `plan_type`(예: Pro) + 짧은 해시(`#a1b2`) + 환경. 이메일을 얻으려고 `id_token` 을 디코드하지 않는다.

### 6.5 계정을 모를 때

- 막대는 그리되 "미상" 그룹에 넣는다. 사용자가 그 블록에 별명을 붙이면 그 별명은 해당 미상 키(환경 + 설정 디렉터리 해시)에 붙는다.
- 미상 측정을 추측으로 알려진 계정에 합치지 않는다.

## 7. 한계와 미확인 사항

- Claude 한도가 계정 단위인지 조직 좌석 단위인지 공식 근거를 확인하지 못했다. 키에 둘 다 넣어 피해 간다.
- statusLine 자식 프로세스의 환경 상속, `/login` 직후 `.claude.json` 갱신 시점은 바이너리에서 끝까지 추적하지 않았다(추정).
- WSL Codex 0.157.1 의 롤아웃이 이 기계에 없어 `creator_account_id` 존재 여부를 WSL 에서 확인하지 못했다. Windows 0.166.0 에서만 확인했다.
- `creator_user_id` 는 `auth.json` 의 어떤 필드와도 일치하지 않았다. 의미를 확인하지 못했으므로 키로 쓰지 않는다.
- Codex 가 실행 중에 계정을 바꾸면 그 프로세스의 이후 롤아웃이 어느 계정을 적는지 확인하지 못했다.
- API 키 모드 표본이 이 기계에 없다(Claude · Codex 모두).
- statusLine stdin 페이로드 필드는 2.1.314 기준이다. 이후 버전에서 계정 필드가 추가될 수 있다. 추가되면 그것을 우선 사용한다.
- Windows 서버에서 `\\wsl.localhost` 경로 읽기는 실측하지 않았다.

## 8. 결론

**가능하다.** 두 에이전트 모두 비밀값을 건드리지 않고 측정값마다 계정을 붙일 수 있다.

- **Claude**: statusLine stdin 에는 계정이 없다(확인). 릴레이가 자기 환경의 `CLAUDE_CONFIG_DIR`(없으면 홈)의 `.claude.json` → `oauthAccount.accountUuid` · `organizationUuid` 를 읽어 측정값에 붙인다. claude-hud 가 이미 같은 방식으로 계정을 표시한다(확인). `.credentials.json` 은 읽지 않는다.
- **Codex**: 롤아웃 `session_meta.creator_account_id` 가 계정 식별자이며 `auth.json` 의 `account_id` 와 일치함을 확인했다. `auth.json` · `id_token` 은 읽지 않는다. 한 홈 안에서도 계정이 바뀌므로(이 기계에서 실제로 바뀜) 홈 단위가 아니라 롤아웃 단위로 귀속한다.
- 이 기계는 지금 Windows 와 WSL 이 Claude · Codex 모두 **서로 다른 계정**이다. 계정별 분리가 실제로 필요한 상황이다.
- 표시 이름은 사용자가 붙인 별명을 우선하고, 없으면 가린 이메일 · 조직 유형 · 요금제 · 짧은 해시를 쓴다. 계정을 모르면 "미상" 그룹으로 따로 보여 주고 합치지 않는다.

## 9. 추가 실측 (구현 중, 2026-10-31)

- **Codex 의 계정 id 가 달라도 같은 한도일 수 있다.** 최근 이틀 동안 Windows Codex 기록에 `creator_account_id` 두 개가 함께 쓰였다. 각 id 는 서로 다른 `creator_user_id` 와 짝을 이룬다. 그런데 두 id 의 주간 사용률(44%)과 `resets_at` 이 같은 초까지 같았다. 같은 한도를 공유하는 것으로 보인다. 다만 이 데이터만으로는 확정할 수 없다.
  - 처리: 같은 에이전트에서 모든 창의 사용률이 같고 초기화 시각 차이가 5초 이내인 기록은 한 막대로 합친다. 별명이 바뀌지 않도록 가장 작은 계정 키를 남긴다(`usageModel.ts` 의 `mergeReadings`).
  - 진짜로 다른 두 계정이 우연히 같은 값이어도, 보이는 숫자는 맞다.
- **`rate_limits.limit_id` 에 `codex` 말고 `premium` 도 나온다.** 최근 기록 320건 가운데 3건이다. 서로 다른 한도이므로 `limit_id` 가 `codex` 가 아닌 기록은 읽지 않는다. 옛 CLI 처럼 `limit_id` 가 없는 기록은 받아들인다.
- 첫 읽기는 약 3초 걸렸다. 2일치 기록 약 320개를 읽은 시간이다. 그 뒤에는 바뀐 파일만 다시 읽는다.
