# Orca 대비 BuilderGate 다중 세션 성능 주장 검증 및 개선 계획

날짜: 2026-07-15

Orca 기준선: e0edc8ef76d341f7ab8083a006f785322bcaeb23

문서 성격: 기존 성능 연구의 사실 교정과 후속 구현 계획. 이 문서 자체는 SRS를 변경하지 않는다.

## 1. 결론

제시된 문서의 큰 방향은 타당하다.

- BuilderGate를 Electron으로 다시 만들 근거는 현재 없다.
- control/output 분리, 얕은 소켓 gate, 세션 간 공정성, hidden 출력의 복구 가능한 상태화는 검토할 가치가 높은 원칙이다.
- 프런트 스케줄러의 코드포인트별 TextEncoder.encode() 호출은 현행 코드에서 확인되는 명백한 핫패스다.

그러나 “현재 코드에 이미 있는 기능을 설정으로 활성화하면 된다”는 전제와 일부 Orca 설명은 사실과 다르다. 그대로 구현 순서로 채택하면 안 된다.

가장 중요한 교정은 다음 네 가지다.

1. BuilderGate의 split 관련 파서·도우미·테스트는 존재하지만 실제 서버와 프런트 런타임에 연결되지 않았다. FR-BGSTAB-006/007은 implemented/stable로 기록되어 있어 코드·테스트·SRS가 서로 불일치한다.
2. 현재 체크인된 로컬 운용 조합은 unified + safe-send-enforce + headless observe + frontend bounded다. direct + unified + observe라는 설명은 스키마·예제 기본값에는 맞지만 현재 운용값에는 맞지 않는다.
3. headlessQueueMode=observe도 실제 큐를 무제한으로 두지 않는다. 현행 큐는 bounded이며 overflow 시 headless를 degrade한다.
4. Orca의 64K slice, 4K bypass, 512K tail, 2M 공유 목표는 대부분 byte가 아니라 JavaScript 문자열의 char/code-unit 기준이다. Orca는 현재 binary data plane이나 DRR을 사용하지 않는다.

따라서 최종 판정은 다음과 같다.

| 질문 | 판정 |
| --- | --- |
| Electron 재작성 없이 개선할 수 있는가 | 가능성이 높다. 다만 Orca와 동일 성능 달성은 동일 워크로드 벤치마크 전에는 가설이다. |
| 원문의 데이터 플레인 개선 방향은 맞는가 | 대체로 맞다. |
| 원문의 P0 순서대로 바로 구현해도 되는가 | 아니다. split 진실성 복구와 기준선 측정이 먼저다. |
| 지금 바로 할 수 있는 저위험 변경은 무엇인가 | allocation-free UTF-8 prefix 계산을 TDD로 분리 구현하는 것이다. |
| binary/WebGL/hidden drop을 바로 도입해야 하는가 | **binary 는 도입한다** (2026-08-16 오너 결정, `docs/research/binary-comms/00-decision-record.md`) — 독립 계약과 rollback 은 그대로 필수다. WebGL/hidden drop 은 여전히 측정 확인 후 도입한다. |

## 2. 조사 방법과 한계

사용자가 요청한 대로 정확히 세 개의 독립 서브에이전트가 서로 다른 축을 감사했다.

| BuilderGate 현행 코드 감사 | 출력 스케줄러, SessionManager.onData, WebSocket 전송, split wiring, hidden 복구, runtime residency, 설정과 테스트 |
| Orca 공식 소스 감사 | Electron/React/xterm 구성, control/stream 소켓, batcher, keep-tail, dataGap, PTY flow control, WebGL |
| 계획·위험 감사 | SRS 정합성, 구현 의존성, TDD 경계, 벤치마크 정의, rollout과 rollback |

메인 검증에서는 다음을 추가로 수행했다.

- docs/spec/00.index.md와 Active Target 요약을 확인했다.
- 관련 BGSTAB Requirement의 Status, Stability, Acceptance Criteria, Verification Evidence를 대조했다.
- BuilderGate 기준선을 커밋 ca111fe로 고정했다.

- split parser/helper와 실제 WsRouter handshake 테스트를 분리 실행했다.
- 현행 설정, 테스트 러너, 런타임 import/call site를 직접 대조했다.

이 조사의 한계도 명확하다.

- 정적 코드 감사와 집중 테스트는 수행했지만 동일 하드웨어의 Orca 대 BuilderGate 성능 프로파일은 수행하지 않았다.
- 따라서 CPU 비중, echo 지연 개선 폭, 적정 gate/slice/tail 크기는 확정값이 아니다.
- Orca 코드 주석에 있는 과거 지연 수치는 중요한 1차 단서지만 장비·워크로드·raw 결과가 없는 독립 벤치마크로 취급하지 않는다.

이후 문서에서 “확인”은 코드 또는 테스트로 입증된 사실, “가설”은 측정이 필요한 설명, “후보”는 의사결정 게이트를 통과해야 하는 설계를 뜻한다.

- allocation-free UTF-8 prefix 및 bounded coalescing
- 세션별 ordered queue, 공정성, slice, starvation bound
- client visibility/freshness hint의 generation과 TTL

## 4. BuilderGate 주장 사실 검증

### 4.1 기반 기능과 런타임 상태

| 원문 주장 | 판정 | 현행 코드 근거와 교정 |
| --- | --- | --- |
| unified / split-shadow / split 전송 모드가 구현돼 있다 | 부분 사실 | server/src/ws/wsTransportMode.ts와 frontend/src/utils/webSocketUrl.ts에 parser/helper가 있다. 그러나 WsRouter가 realtime 옵션을 소비하지 않고 handleUpgrade가 role/pair handshake를 하지 않으며 WebSocketContext는 단일 socket만 연다. |
| WebSocket 안전 전송 큐가 있다 | 사실 | wsSendPolicy는 control lane과 terminal lane, bounded queue, coalescing, enforce 경로를 갖는다. |
| 세션별 공정한 전송이 없다 | 사실 | control은 terminal보다 우선하지만 terminal lane 내부는 세션 간 FIFO다. per-session deque, DRR, active/visible/hidden 우선순위는 없다. |
| headless terminal과 viewport snapshot이 있다 | 사실 | 서버에 headless xterm과 viewport snapshot/repair 기반이 있다. 다만 전체 10,000-line scrollback의 권위 모델은 아니다. |
| hidden snapshot-restore가 있다 | 사실 | 프런트는 hidden output 적용을 건너뛰고 reveal 시 snapshot으로 복구한다. 서버 측 visibility-aware drop/shared budget/data-gap은 없다. |
| runtime residency 제한이 있다 | 사실 | 최대 32 live terminal과 hidden TTL 600,000ms 기본값이 있다. visible과 보호 대상 hidden을 유지하는 기존 안정 계약 때문에 실제 수가 hard cap을 넘을 수 있다. |

핵심은 “스캐폴딩이 있다”와 “런타임에서 작동한다”를 구분하는 것이다. split은 전자이고 safe-send, hidden snapshot-restore, visible scheduler는 후자다.

### 4.2 프런트 UTF-8 스케줄러

원문의 가장 강한 정적 진단은 사실이다.

frontend/src/utils/terminalOutputScheduler.ts의 takeUtf8Prefix()는 문자열을 code point별로 순회하고 매번 getUtf8ByteLength()를 부른다. 이 함수는 각 호출마다 TextEncoder.encode(value).length를 실행한다.

기본 visibleFlushBudgetBytes는 262,144다. 충분히 긴 ASCII entry 하나를 budget만큼 자르면 약 262,144번의 encode 호출과 임시 Uint8Array 생성이 가능하다. 큐 chunk 수가 한도를 넘으면 coalesceChunks()가 모든 문자열을 join하여 이 조건을 실제로 만들 수 있다.

다만 원문 PR 2 중 다음은 이미 구현돼 있다.

- 한 terminal당 xterm write 하나만 in-flight
- 기본 7ms frame CPU budget
- input pending 시 yield
- callback ordering

그러므로 첫 변경은 다음처럼 좁혀야 한다.

1. enqueue 시 entry별 UTF-8 byteLength를 한 번만 계산한다.
2. entry 전체가 budget 이하면 code-point loop 없이 그대로 보낸다.
3. entry를 실제로 나눌 때만 code point 값으로 UTF-8 폭을 계산한다.
4. coalescing 후에도 byteLength를 재사용한다.
5. 256KiB budget은 첫 PR에서 유지한다.

코드포인트 폭 계산 자체는 다음 규칙으로 충분하지만, lone surrogate가 TextEncoder의 replacement semantics와 일치하는지도 테스트로 고정해야 한다.

    U+0000..U+007F      1 byte
    U+0080..U+07FF      2 bytes
    U+0800..U+FFFF      3 bytes
    U+10000..U+10FFFF   4 bytes

256KiB를 32~64KiB로 즉시 줄이는 제안은 아직 사실이 아니라 실험 가설이다. PERF-BGSTAB-001에는 과거 16KiB 처리량 한계를 해소하려 262,144를 복원한 결정이 있으므로 byte slice와 frame time budget을 독립 변수로 비교해야 한다.

### 4.3 SessionManager.onData semantic 경로

다음 구조는 확인됐다.

    PTY onData
      -> OSC 133 parser
      -> terminal title parser
      -> title signal parser
      -> foreground/AI TUI classification
      -> 상태 전이 판단
      -> headless output queue

따라서 semantic 분석이 headless enqueue보다 앞에서 같은 Node.js 이벤트 루프를 점유한다는 구조적 위험은 있다.

그러나 원문의 세부 설명 일부는 현행 HEAD보다 오래됐다.

- 비-Hermes 출력은 Hermes detector에서 strip 전에 early return한다.
- raw debug detail은 debug capture가 켜진 세션에서만 만든다.
- 여러 classifier가 쓰는 strip/normalize 결과는 청크 안에서 lazy 공유한다.
- event-loop delay, process CPU, headless write 누적 관측이 이미 추가됐다.

따라서 “detector가 P0 병목”이라는 우선순위는 정적 코드만으로 확정하지 않는다. 먼저 detector 단계별 sampled ns/byte와 NO_ANALYZER 차이를 측정한다.

배칭을 하게 되더라도 상태를 유지하는 OSC/title parser는 arrival order를 보존하는 동기 경로에 두는 것이 안전하다. stateless classifier만 session generation, arrival timestamp, 최근 사용자 입력 epoch와 함께 세션별 FIFO에서 배치해야 한다. 늦게 끝난 과거 분석이 사용자 입력 뒤 세션을 running으로 되돌리는 회귀를 막아야 한다.

### 4.4 설정과 큐

설정은 “스키마·예제 기본값”과 “현재 체크인 운용값”을 구분해야 한다.

| 항목 | 스키마·예제 기본 | 현재 server/config.json5의 유효값 |
| --- | --- | --- |
| wsTransportMode | unified | unified 기본 적용 |
| wsSendMode | direct | safe-send-enforce 명시 |
| headlessQueueMode | observe | observe 기본 적용 |
| frontendRuntimeResidency | bounded | bounded 기본 적용 |

또한 observe는 “관찰만 하고 실제 제한하지 않음”이 아니다. headless queue는 모드와 무관하게 byte-bounded deque를 사용하고 overflow를 거부하며 SessionManager는 headless 상태를 degrade한다. 따라서 observe 대 bounded A/B는 두 모드의 실제 의미 차이가 먼저 정의되지 않으면 유효한 실험이 아니다.

현행 기본 자원 한도 자체는 원문과 대체로 일치한다.

| 한도 | 현재 기본 |
| --- | ---: |
| headless pending output | 8MiB / 1,024 chunks |
| headless write batch | 64KiB |
| server socket high-water | 8MiB |
| server socket hard limit | 32MiB |
| per-client output queue | 2MiB |
| per-client control queue | 256KiB |
| browser visible queue | 4MiB |
| browser visible flush | 256KiB |
| hidden debug tail | 256KiB |
| live terminal 기본 상한 | 32 |
| hidden runtime TTL | 10분 |

이 값이 interactive latency에 너무 깊다는 문제 제기는 합리적이지만 128KiB, 32KiB, 64KiB 등의 대체값은 BuilderGate에서 입증되지 않았다. 로컬 IPC인 Orca의 숫자를 WAN 가능 WebSocket에 그대로 복사하면 안 된다.

### 4.5 JSON data plane과 복구

현행 terminal output은 JSON 문자열이다.

    PTY string
      -> detector/parser
      -> JSON.stringify
      -> Buffer.byteLength UTF-8 scan
      -> WebSocket text frame
      -> browser JSON.parse
      -> JavaScript string
      -> xterm parser

따라서 반복 스캔·encoding 비용이 있다는 주장은 사실이다. 다만 이것이 전체 CPU의 몇 퍼센트인지, binary 전환이 유의미한 개선을 내는지는 측정하지 않았다.

binary 전환은 단순 최적화가 아니라 새 프로토콜이다. 최소한 다음 계약이 필요하다.

- protocol version과 capability negotiation
- JSON fallback을 포함한 dual stack
- UUID에서 channelId로의 mapping과 ACK barrier
- control mapping보다 output frame이 먼저 도착하지 않는 순서 보장
- 기존 screenSeq와 별도인 streamFrameSeq
- snapshot string write와 live Uint8Array write의 단일 ordered gate
- multibyte 경계, duplicate/loss/reorder 검출

현재 snapshot/repair write 일부는 live scheduler를 우회한다. 따라서 FR-BGSTAB-017 recovery write gate가 binary보다 먼저다.

재구독 시 여러 snapshot이 연속 생성·전송되는 burst 가능성도 구조상 있다. 다만 현재 snapshot serialize는 이미 동기 직렬이다. “동시 생성 1~2개 제한”보다 다음이 우선이다.

1. active/visible session 우선 admission
2. hidden snapshot 지연
3. snapshot 사이 event-loop yield
4. 브라우저 recovery write gate
5. replay/repair/live causal ordering 보존

### 4.6 renderer와 scrollback

BuilderGate에는 현재 @xterm/addon-webgl이 없다. WebGL 실험 가치는 있지만 서버 큐, semantic 분석, JSON 처리 병목을 해결하지 않는다.

서버 headless scrollback 기본은 1,000줄이고 브라우저 terminal scrollback 기본은 10,000줄이다. remount/reconnect 뒤 동일한 10,000줄을 복구할 수 없다는 지적은 타당하다. 단순히 두 숫자를 같게 만드는 것만으로는 해결되지 않는다. 현재 권위 snapshot이 viewport 중심이므로 historical scrollback 보존 계약을 별도로 정해야 한다.

## 5. split 구현 상태: 가장 시급한 진실성 문제

FR-BGSTAB-006과 FR-BGSTAB-007은 SRS에서 implemented / stable이고 split handshake, pairing, routing, fallback 검증 evidence를 기록한다.

그러나 현행 런타임은 다음 상태다.

- server/src/index.ts가 WsRouter 생성 시 realtime 설정을 넘기지 않는다.
- WsRouter 생성자가 realtime/wsTransportMode 상태를 만들지 않는다.
- handleUpgrade가 parseWsTransportRequest()를 호출하지 않는다.
- control/output role, group, pair token lifecycle이 없다.
- 프런트 WebSocketContext는 webSocketUrl/split lifecycle helper를 사용하지 않고 단일 socket만 연다.
- 모든 프런트 수신 메시지는 JSON text로 가정된다.

집중 테스트 결과는 이 차이를 그대로 보여 준다.

| 테스트 | 결과 | 의미 |
| --- | ---: | --- |
| server wsTransportMode parser | 6/6 PASS | parser 스캐폴딩은 정상 |
| server WsRouter split handshake/routing | 3/16 PASS, 13 FAIL | 실제 runtime 계약 미구현 |
| 두 server suite 합계 | 9/22 PASS | parser 통과가 split 구현 완료를 뜻하지 않음 |
| frontend URL/split lifecycle helper | 5/5 PASS | helper는 정상이나 WebSocketContext에 미연결 |
| WsRouter safe-send priority | 5/5 PASS | 기존 control 우선 lane은 정상 |
| frontend scheduler/residency/hidden-output 집중 테스트 | 32/32 PASS | 기존 보호 기반은 정상 |

server/package.json의 기본 npm test는 build 후 dist/test-runner.js만 실행한다. WsRouterSplitHandshake.test.ts 같은 standalone node:test 파일은 빌드되지만 권위 테스트 러너에서 실행되지 않는다. 이 때문에 “evidence가 있으나 runtime은 없는” drift가 장기간 탐지되지 않았을 가능성이 높다.

따라서 원문의 첫 PR처럼 설정만 split으로 바꾸면 안 된다. 이 성능 목표와 stable SRS 계약을 고려하면 권장 분기는 기존 RED 테스트를 출발점으로 split runtime wiring을 완성하는 것이다. 제품 결정으로 split을 철회·연기할 때만 두 번째 분기를 사용한다.

1. 복원 분기: SRS 계약대로 split runtime wiring을 완성하고 모든 테스트를 권위 suite에 포함한다.
2. 철회·연기 분기: SpecKiwi MCP로 Status와 Verification Evidence를 실제 상태에 맞게 정정하고 split 설정을 명시적으로 unavailable로 거부한다.

이 결정 전 기본은 unified로 유지한다.

### 6.2 BuilderGate에 가져올 원칙과 가져오지 않을 숫자

가져올 원칙:

- bulk output과 control 경로를 분리한다.
- socket queue는 얕게 유지하고 나머지는 application queue에 둔다.
- 한 session이 socket을 독점하지 않게 한다.
- 작은 interactive output에 bounded latency를 제공한다.
- background backlog를 무한 보존하지 않고 복구 가능한 상태로 다룬다.
- 권위 snapshot과 explicit gap을 사용한다.
- renderer는 feature detection과 fallback을 갖춘다.

그대로 복사하지 않을 항목:

- 128KiB gate
- 64K/4K chars slice와 bypass
- 512K/64K/2M chars tail 정책
- same-host IPC에서 관측된 절대 지연
- Orca의 조건부 bypass를 DRR이라고 부르는 것
- Orca가 binary를 쓴다는 전제

Orca와 BuilderGate는 React/xterm/node-pty/headless snapshot이라는 추상 구조는 비교 가능하다. 그러나 Orca는 같은 호스트의 node:net IPC와 Electron main/renderer 경계이고 BuilderGate는 HTTPS/WSS와 WAN RTT, 여러 브라우저 client, reconnect를 포함할 수 있다. “Electron과 브라우저의 차이는 전혀 중요하지 않다”는 단정 대신 “재작성보다 데이터 경로가 우선이지만 transport 환경 차이는 임계값에 반영해야 한다”가 정확하다.

## 8. 단계별 구현 계획

아래 Phase는 구현 PR 경계를 뜻한다. 각 Phase 시작 전에 관련 Requirement의 Stability가 evolving 또는 stable이며 draft/deprecated가 아님을 확인한다. 동작 변경은 실패하는 자동 테스트를 먼저 추가한다.

모든 구현 Phase의 공통 완료 게이트:

1. 관련 build/test/lint/typecheck/guard 중 적용 가능한 자동 검증을 실행한다.
2. 까칠한 서브에이전트가 해당 Phase의 계획, Requirement, 코드, 테스트를 대조한다.
3. finding을 수정하고 관련 자동 검증을 다시 실행한다.
4. 같은 리뷰어 또는 동등한 역할이 재리뷰한다.
5. No findings 판정 후에만 해당 Phase를 완료 처리한다.

의존 관계는 다음과 같다.

    Phase 0 split 진실성 복구 -------> Phase 3 실제 split
         |
         +--> Phase 1 기준선/하니스 --> Phase 2A/2B/2C UTF-8·queue 국소 개선
                                  |--> Phase 4 semantic 조건부
                                  |--> Phase 9 renderer 조건부
                                  |
    FR-BGSTAB-015 Settings/runtime contract
         -> REL-BGSTAB-003 bounded recovery
         -> FR-BGSTAB-017 recovery write gate = Phase 5
                                  |
    Phase 1 ----------------------+--> Phase 6 fair scheduler
                                           |--> Phase 7 binary 조건부
                                           |--> Phase 8 hidden gap/tail 조건부

    선택되어 구현된 Phase 2~9 전체 -------> Phase 10 공통 soak/default gate

Phase 3 split과 Phase 6 fair scheduler는 서로의 선행 조건이 아니다. unified JSON transport에서도 fair scheduler를 검증할 수 있으며, split 복구가 지연되더라도 Phase 6은 Phase 1과 Phase 5가 끝나면 독립 진행할 수 있다.

### Phase 2 — UTF-8 scheduler 국소 개선

완료 기준:

- auth/pairing/expiry/duplicate/reconnect/fallback 테스트 green
- control starvation이 기준선보다 개선
- active output loss/duplicate/reorder 0
- close/replay storm 악화 없음

rollback:

- 설정 한 번으로 unified + 기존 safe-send-enforce로 복귀

### Phase 4 — 잔여 semantic path 조건부 최적화

go 조건:

- NO_ANALYZER 또는 stage timer가 semantic path를 유의미한 CPU/echo 지연 원인으로 입증
- 최소 유의 개선폭은 Phase 1에서 사전 등록

작업:

- 상태 유지 OSC/title parser는 동기 순차 경로에 유지한다.
- 비용이 큰 stateless classifier만 16~50ms 또는 bounded byte 단위 세션 FIFO batch 후보로 삼는다.
- batch에 session generation, arrival timestamp, input epoch를 포함한다.
- worker thread는 batching 후에도 CPU 비중이 높은 순수 분석기에만 검토한다.

필수 회귀:

- 사용자 keyboard input, local echo, cursor move, ticker, prompt redraw는 idle 유지
- output→input→늦은 semantic result 순서에서도 running 오판 없음
- session dispose/recreate 시 이전 generation result 폐기
- Codex/Claude/Hermes launch, waiting, prompt return
- debug capture on/off 의미 동일

rollback:

- session별 immediate semantic path feature flag

### Phase 5 — recovery 선행 계약, write gate와 snapshot admission

목표:

- live output, snapshot, repair, replay tail을 하나의 causal ordering으로 묶는다.
- reconnect burst가 input/control을 굶기지 않게 한다.

요구사항 구현 순서:

1. FR-BGSTAB-015: Settings-backed transport/recovery limits와 runtime apply 계약
2. REL-BGSTAB-003: byte-aware replay/repair queue, overflow abort, authoritative refresh
3. FR-BGSTAB-017: bounded frontend recovery write gate와 queued input release barrier
4. FR-BGSTAB-016 확장/fair scheduler가 recovery ordering을 재사용할 수 있도록 contract test 고정

Settings 화면의 시각·상호작용 변경이 필요하면 저장소 UI 규칙에 따라 구현 전에 사용자 승인을 받는다.

구현 작업:

- snapshot/repair의 direct term.write 우회를 제거하고 ordered recovery gate에 통합한다.
- ACK는 실제 xterm write 완료 뒤에만 보낸다.
- 모든 session의 control/lifecycle subscription은 reconnect 즉시 등록하여 status, cwd, exited를 놓치지 않게 한다.
- initial snapshot/output admission을 subscription과 분리하는 flag 또는 별도 snapshot-request 계약을 먼저 SRS에 등록한다. FR-BGSTAB-007/014/017 확장 또는 새 Requirement 여부는 SpecKiwi MCP로 결정한다.
- client는 snapshot/output admission만 active, visible, recent, hidden 순으로 요청하고 server는 그 요청 순서를 보존한다.
- admission이 지연된 session은 snapshot을 받기 전부터 명시적으로 stale/recovery-needed로 취급한다.
- persistent server-side visibility 상태나 visibility-aware drop은 여기서 도입하지 않고 Phase 8로 미룬다.
- snapshot admission 사이에 event-loop yield를 둔다.
- replay/repair overflow는 oversized direct write 대신 abort와 authoritative snapshot refresh로 전환한다.

필수 회귀:

- lifecycle subscription 직후 snapshot admission이 지연되는 동안 status/cwd 변경과 session exit 전달
- deferred session의 stale/recovery-needed 전이와 후속 snapshot 성공
- admission 전 output이 잘못 live 적용되지 않음
- reconnect 중 중복 subscription/admission과 stale token 폐기

완료 기준:

- FR-BGSTAB-015 → REL-BGSTAB-003 → FR-BGSTAB-017 의존성 순서와 Settings runtime consumer 검증
- snapshot→replay→live output 순서가 loss/duplicate 없이 보존
- queued input release가 write 완료 전 발생하지 않음
- deferred snapshot/output admission 중에도 status, cwd, exited lifecycle event를 놓치지 않고 stale/recovery-needed 상태를 유지
- reconnect/reveal burst 중 control starvation 없음
- session cleanup 뒤 gate/queue/map 0

rollback:

- ordered recovery gate 자체는 유지한다.
- recovery budget을 보수적으로 낮추고 overflow/timeout 시 server authoritative snapshot refresh를 강제한다.
- legacy direct term.write 경로는 rollback으로 복원하지 않는다.

### Phase 6 — 세션별 fair output scheduler

목표:

- 한 bulk session이 다른 session의 echo/prompt/status를 terminal FIFO 뒤에 매몰시키지 못하게 한다.

선행 조건:

- Phase 1 baseline slice
- FR-BGSTAB-015, REL-BGSTAB-003, FR-BGSTAB-017을 순서대로 완료한 Phase 5
- split은 선행 조건이 아니다. unified JSON transport에서 먼저 구현·검증할 수 있다.

설계 원칙:

- 기존 global control 우선 lane은 유지한다.
- session마다 output/snapshot/repair/ready/status/exited의 required ordering을 보존하는 ordered lane을 둔다.
- session 간에만 DRR 또는 측정으로 선택한 공정 알고리즘을 적용한다.
- configurable max slice와 soft socket gate를 둔다.
- 작은 recent-input output에 bounded bypass를 허용하되 starvation 상한을 둔다.
- visibility 우선순위는 generation/TTL이 있는 protocol hint가 생긴 뒤에만 사용한다.

권장 rollout:

1. observe: legacy drain 결과와 새 scheduler 선택 결과를 비교
2. shadow accounting: 실제 전송은 legacy, starvation/ordering oracle만 비교
3. opt-in enforce
4. soak 후 기본 검토

TDD:

- A가 flood 중일 때 B의 작은 echo가 starvation bound 내 전송
- 동일 session의 output→status→exited 순서
- snapshot/repair/replay barrier
- slow socket, drain, reconnect, duplicate control
- recent-input bypass 남용과 background starvation 방지

완료 기준:

- 1+7/15 flood에서 echo SLO 달성
- queue가 시간에 따라 무한 증가하지 않음
- active output loss/reorder/duplicate 0
- WAN profile에서 close/replay storm 없음

rollback:

- 기존 단일 terminal FIFO

### Phase 7 — negotiated binary data plane

go 조건:

- profile에서 JSON stringify/parse, byte-length 재스캔, UTF-8 encoding이 전체 비용의 유의미한 비중임을 입증
- fair scheduler와 recovery write gate가 먼저 안정화

목표:

- control JSON은 유지하고 terminal output만 versioned binary로 선택 전환한다.

필수 계약:

- capability negotiation과 JSON fallback
- channelId mapping ACK
- frame header version/type/flags/channelId/frameSeq/payloadLength
- screenSeq와 streamFrameSeq의 의미 분리
- UTF-8 streaming decoder 및 gap/reconnect reset
- snapshot/live 혼합 write ordering

TDD:

- 모든 multibyte fragmentation 위치
- invalid/unpaired surrogate 정책
- mapping ACK race
- duplicate/loss/reorder
- output socket reconnect
- 구버전 client의 JSON fallback

완료 기준:

- shadow hash/counter가 JSON과 동일
- CPU/allocation/wire bytes가 사전 정의한 유의 수준 이상 개선
- active output 무결성 100%

rollback:

- capability negotiation으로 JSON output 선택

### Phase 8 — hidden gap/tail과 reveal recovery

go 조건:

- Phase 5/6 이후에도 hidden flood가 per-client queue 또는 network를 지속 압박
- visibility hint, stream sequence, recovery ACK 계약 완료
- 해당 session의 headless가 healthy이거나 snapshot sequence를 복구할 수 있다고 검증된 degraded-recovery 상태

목표:

- healthy server headless가 모든 output을 반영하는 동안 per-client hidden transport backlog만 명시적으로 줄인다.
- headless가 degrade되면 새로운 intentional hidden gap/drop을 자동 중지하고 기존 bounded close/reconnect/snapshot recovery로 복귀하며 truncation을 observable하게 유지한다.

필수 계약:

- visibility hint generation/TTL/stale 처리
- active/visible output은 lossless
- hidden output drop 범위와 stream sequence
- explicit data-gap
- tail 정책과 전체 hidden budget
- reveal 시 snapshot→ACK→snapshot 이후 frame 재개
- reconnect와 gap 중첩
- viewport recovery와 historical scrollback 손실 범위 분리
- authoritative snapshot sequence가 drop된 gap 범위를 실제로 덮는다는 검증
- headless degrade 감지 시 hidden drop disable과 bounded close/reconnect/snapshot fallback

TDD:

- stale visibility hint
- gap 범위와 frame ordering
- gap 중 reconnect
- reveal snapshot 적용 중 live output
- gap 뒤 headless degrade와 recovery
- hidden session 종료와 queue cleanup

완료 기준:

- hidden flood 동안 queue 무한 증가 없음
- active echo/control SLO 유지
- reveal SLO 달성
- hidden loss는 data-gap/telemetry로 항상 추적 가능
- snapshot sequence가 gap 범위를 덮고 서버 headless viewport 상태가 최신
- soak 동안 headless degrade 0 또는 사전 정의한 제한시간 안에 검증된 recovery 완료
- headless가 권위 상태를 제공하지 못하는 동안 hidden drop 0

UI에 새로운 stale 표시나 설정을 추가하려면 기존 UI 변경 규칙에 따라 사용자 승인을 먼저 받는다.

rollback:

- 새로운 intentional hidden gap/drop을 중지하고 기존 bounded close/reconnect/snapshot-restore로 복귀하며 truncation을 observable하게 유지

## 9. 벤치마크 설계

### 9.1 핵심 workload

가장 중요한 workload는 전체 처리량 최대화가 아니라 session 간 간섭이다.

    Session A: active shell, unique marker로 input echo 측정
    Session B..H: 대량 ANSI/flood output

확장 matrix:

| 축 | 값 |
| --- | --- |
| session 수 | 1, 8, 16, 32 |
| 가시성 | 1 visible + 나머지 hidden, 4/8 grid visible, all hidden 후 reveal |
| 출력 | ASCII, 한글/emoji 혼합, ANSI full-screen repaint, line log |
| 네트워크 | local LAN, RTT/bandwidth throttle |
| lifecycle | steady, reconnect, resize, reveal, close |
| transport | unified, split-shadow, split |
| scheduler | legacy, shadow fair, enforce fair |

### 9.2 진단 모드

| 모드 | 유지할 것 | 제거할 것 | 판정 |
| --- | --- | --- | --- |
| NO_RENDER | network parse/demux/ACK와 동일 scheduler | 실제 xterm sink만 대체 | 빨라지면 browser/xterm 병목 |
| NO_ANALYZER | OSC/title/status 필수 계약과 workload | 비교 대상 classifier만 선택 우회 | 빨라지면 residual semantic 병목 |
| NO_NETWORK | 동일 chunk 크기/ANSI/rate/scheduler | WebSocket만 synthetic feed로 대체 | 여전히 느리면 renderer/runtime 병목 |

진단 모드가 workload 자체를 가볍게 만들면 잘못된 결론이 나오므로 byte 수, chunk 분포, arrival cadence를 동일하게 유지한다.

### 9.3 초기 SLO 후보

다음 값은 현재 성능 사실이 아니라 Phase 1에서 ratify할 초기 목표다.

| 지표 | 초기 후보 |
| --- | --- |
| active input processing echo | key event→xterm write callback을 별도 보고 |
| active input visible echo | key event→xterm onRender 또는 검증된 post-rAF paint proxy, LAN p95 50ms 이하·p99 100ms 이하를 초기 후보로 사용 |
| queue 안정성 | steady 구간에서 지속 양의 기울기 없음, flood 종료 5초 안에 기준선 복귀 |
| hidden reveal | p95 500ms 이하 |
| control starvation | flood 중 timeout/장기 정체 0, p99는 기준선에서 확정 |
| active output 무결성 | loss/duplicate/reorder 0 |
| hidden output 손실 | gap 계약을 활성화한 경우에만 허용하고 항상 observable |
| browser Long Task | 50ms 초과 횟수와 연속성 감소, 정량 상한은 기준선 후 확정 |
| cleanup | session 종료 후 관련 runtime/queue/map 0 |

echo는 두 지표로 분리한다.

1. processing echo: browser key event에서 해당 unique marker의 xterm write 완료 callback까지
2. visible echo: 같은 key event에서 marker가 포함된 row의 xterm onRender 또는 테스트 전용 post-rAF paint proxy까지

end-to-end 값은 시작과 끝이 모두 browser monotonic clock에 있는 span으로 계산한다. 서버 receive, PTY write, PTY output, WebSocket send/receive는 trace ID로 상관시키고 각 process 내부 monotonic span으로 기록한다. clock-offset 보정이 없는 browser/server raw timestamp를 직접 빼지 않는다.

## 12. 하지 말아야 할 것

- 현 상태에서 config만 split으로 바꾸지 않는다.
- parser/helper 테스트 통과를 runtime 구현 완료 evidence로 사용하지 않는다.
- Orca의 char 단위 상수를 BuilderGate byte 한도로 복사하지 않는다.
- 256KiB flush budget을 프로파일 없이 32~64KiB로 낮추지 않는다.
- 이미 구현된 one-in-flight, frame budget, Hermes bail, debug gating, strip sharing을 새 작업으로 중복 계획하지 않는다.
- stateful OSC/title parser를 순서·generation 계약 없이 worker로 옮기지 않는다.
- binary를 Orca 성능의 필수 조건이라고 주장하지 않는다.
- 서버 headless viewport snapshot을 전체 scrollback 권위 모델이라고 부르지 않는다.
- hidden output을 observable gap과 recovery 계약 없이 버리지 않는다.
- WebGL이나 TTL 변경을 성능 측정과 UI 승인 없이 기본화하지 않는다.

## 13. 최종 권고

BuilderGate의 우선 전략은 Electron 재작성이 아니다. binary 는 2026-08-16 오너 결정으로 도입이 확정됐으나, 그 앞의 split 진실성·UTF-8 핫패스 정리는 여전히 선행 작업으로 남는다. WebGL 은 측정 후 판단한다.

권장 착수 순서는 다음과 같다.

1. FR-BGSTAB-006/007의 split 코드·SRS·test-runner drift를 복구한다.
2. OBS-BGSTAB-001 기반 1 active + 7/15/31 flood 기준선을 만든다.
3. allocation-free UTF-8 prefix를 독립 TDD 변경으로 적용한다.
4. FR-BGSTAB-015 → REL-BGSTAB-003 → FR-BGSTAB-017 순으로 recovery 선행 계약을 완성한다.
5. 실제 split runtime의 unified→split-shadow→split 측정과, unified JSON 위의 ordered fair scheduler 검증을 서로 독립 트랙으로 진행한다.
6. binary 는 도입이 확정됐다 (2026-08-16). semantic batching, hidden gap/tail, WebGL 은 profile 결과에 따라 각각 독립 결정한다.

따라서 제시 문서의 결론은 다음처럼 교정하면 사실에 가장 가깝다.

> BuilderGate는 Electron 재작성 없이 다중 세션 반응성을 크게 개선할 구조적 기반을 일부 갖고 있다. 다만 Orca와 같은 절대 성능은 아직 입증되지 않았고, split은 현행 런타임에서 작동하지 않는다. 먼저 split 진실성, 재현 벤치마크, UTF-8 핫패스를 해결한 뒤 세션별 공정성과 복구 계약을 강화해야 한다. binary 는 2026-08-16 오너 결정으로 도입이 확정됐다(측정은 전후 비교용으로 수행). WebGL은 측정으로 비용 대비 효과가 입증될 때 도입한다.
