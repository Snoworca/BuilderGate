# Binary rollback integration gaps

Scope: IR-BGSTAB-001 AC-3/4/11, MIG-BGSTAB-002 AC-5, FR-BGSTAB-024 AC-2/5, FR-BGSTAB-017 AC-5/6 and MIG-BGSTAB-004. These requirements were looked up through MCP; the relevant requirements are evolving. MIG-BGSTAB-003 is draft and is not an implementation authority for this work. Requirement SSOT remains `docs/spec/`; this is an investigation record, not a frozen implementation contract.

The AC-11 request discriminator correction and actual boot6 do not complete codec rollback. The existing authority/checkpoint machinery offers useful ordered recovery paths, but directly calling an existing method named rollback would not establish AC-4's new source epoch and single codec rollback entry.

## Three distinct epoch owners

| Value | Observed source ownership |
| --- | --- |
| Retained/source `streamEpoch` | SessionManager owns `createTerminalStreamEpochLedger()` (`SessionManager.ts:1166`). The issuer reserves globally increasing values and manages per-session current values; reservation does not itself change current. The default initial issue is1 (`terminalStreamEpoch.ts:61`). |
| Authority controller `streamEpoch` | It starts from retained state but promotion/rollback uses `nextOrdinal(state.streamEpoch)` in the production adapter (`TerminalAuthorityProductionAdapter.ts:923,2643,4447`). The manager's promotion/rollback wrappers delegate to the controller; an adoption into the retained source ledger was not found on those paths. |
| Group `codecEpoch` | A connection-group numeric value, initially0 with no increment path in `terminalBinaryGroupSession.ts:82–113`. It is not the uint64 source epoch or authority UUID. |

The distinction reaches delivery: controller output uses controller `state.streamEpoch` (`TerminalAuthorityController.ts:863,984`), while legacy delivery uses reserved source tuples (`SessionManager.ts:7954`). Binary channel seeds come from the authority state read by `WsRouter.ts:1970`. Initial value equality is not proof that these are one allocator or one domain. No new counter, client-invented epoch or reinterpretation of codecEpoch is justified by this investigation.

## Existing recovery paths to reuse deliberately

- `TerminalAuthorityProductionAdapter.ts:4410–4465` selects a frozen compatibility view, prepares responder identities and invokes the manager/controller rollback. `compatibility-view-unavailable` is a real branch.
- `SessionManager.ts:5306` delegates to `TerminalAuthorityController.beginRollback` (:1438). The controller requires server authority (or its specific recovery state), validates identities and frozen views, then manages admission closure, stale/parser/ACK reset and ordered snapshot/tail recovery.
- `frontend/src/utils/terminalCheckpointRuntime.ts:916` (`rollbackToLegacy`) resets local generation/coordinator/ACK state and requests recovery. `beginCompatibilityRollback` (:967) installs supplied server identities and blocks legacy enable until apply/drain completion.
- `WebSocketContext.tsx:791–885` forwards existing authority rollback controls.

These are authority/responder recovery contracts. `rollbackTerminalResourcePolicyLease` and `drainTransportQueueForPolicyRollback` in WsRouter instead manage policy leases and transport queues; they do not by themselves change the codec, issue a fresh source epoch or provide a checkpoint.

## Four triggers are not connected to one codec rollback

| Trigger | Current behavior | Missing integration |
| --- | --- | --- |
| Runtime config replacement | RuntimeConfigStore replaces `terminalWireFormat` (:1253), but WsRouter stores a readonly construction value (:599,651); `updateRuntimeConfig` (:1210) accepts resource/send-policy updates | An observable codec-policy change reaching existing groups and the single ordered rollback entry |
| Fatal binary decode | `WebSocketContext.tsx:758–766` warns and returns | A trustworthy failure signal, stale/fencing action and fresh epoch/checkpoint recovery |
| Rejected renegotiation | Group changes state only on acceptance; rejection leaves negotiated/acceptance state in place | Ordered invalidation and recovery without silently switching encoding inside the old epoch |
| Old-build restart | Disconnect clears connection ledgers/views and reconnect creates a new group (`WsRouter.ts:3510`) | Proof of distinct source identity and fresh compatible recovery under the actual supported old build |

Recoverable unknown-channel reports already request a scoped table reannouncement and must remain distinct from fatal decode. A valid checkpoint failure can use the existing `terminal-checkpoint:failure-ack`; an untrusted framing failure may not have a trustworthy channel/session/checkpoint identity. Fabricating that identity or misusing unknown-channel as a generic failure envelope is not acceptable.

AC-11's existing five binary control types do not currently provide a generic client fatal-decode report. A transport-close design needs explicit failure-vs-normal disconnect semantics and a reconnect-loop test. A new message or reason contract requires an SRS decision first; it must not be slipped into the implementation or disguised as an existing message.

## Shared-session consumers and admission

An authority rollback closes session admission and affects the frozen views of that session (`TerminalAuthorityController.ts:1504,1531`). Therefore a failing group cannot blindly call it and claim other healthy clients are isolated. Conversely, a client-local JSON switch could mix encodings within a source epoch.

Existing `getTerminalAuthorityCanaryContext`, responder/negotiated-view inventories and `prepareTerminalAuthorityPromotionCandidate` provide view capability and recovery-quorum checks. They establish responder/recovery readiness, not all-consumer binary-codec agreement. The full plan's brought-forward P9 all-consumer/fair-admission work remains a prerequisite for selecting the codec transition boundary.

For old-build validation, MIG004 requires an actual supported old build accepting the JSON configuration, stale parser/ACK/backlog state not being reused, and fresh compatible checkpoint/tail ordering. A new WebSocket or empty channel table alone is not a new `streamEpoch` proof. The in-memory epoch issuer's default initial value also cannot establish cross-process monotonicity without examining the actual session/restart contract.

## Next design gate

Before implementation or RED tests that prescribe a new API:

1. Map the retained source tuple, controller epoch and codec generation at each producer/channel/checkpoint boundary and choose their explicit relationship using the existing issuer.
2. Specify the affected group/session/view set, all-consumer codec agreement, old-ACK fencing and exactly-once queue/credit cleanup. Preserve unrelated sessions and avoid waiting indefinitely on the failed client.
3. Select an observable fatal-decode signal consistent with the approved protocol; distinguish recoverable unknown-channel and normal disconnect.
4. Specify the fresh checkpoint/write-completion barrier and supported old-build restart evidence. Route all four triggers through one entry, with static caller and behavioral tests rather than copied rollback implementations.

The design must explicitly distinguish an initial JSON connection's cold decline (including group-not-eligible or an invalid initial offer) from failure after binary has already been established, including rejected renegotiation. For each case, inventory the existing codec/channel/epoch state and determine the affected group, session and views, and whether a new epoch and fresh checkpoint are required under the SRS contract. Do not assume that every initial rejection should trigger a shared-session rollback affecting healthy clients. This is an unresolved contract decision, not an exception that weakens IR-BGSTAB-001 AC-4 or permission to adopt a new threshold.

Independent source investigations were read-only. No runtime behavior, protocol enum, requirement, test assertion or lifecycle status was changed for this analysis. B2 browser validation, AC-4, P9 convergence, mixed-version/default/soak/deletion gates remain open.
