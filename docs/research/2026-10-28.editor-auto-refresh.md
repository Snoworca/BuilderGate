# 편집기 창 자동 새로고침 연구

- 날짜: 2026-10-28
- 요청: HTML 뷰어, 마크다운·코드 편집기, 이미지 뷰어가 디스크의 파일이 바뀌면 스스로 다시 읽게 한다. 창 위쪽에 자동 새로고침 토글을 둔다.
- 상태: 연구. 요구사항(SRS)은 아직 없다.

## 1. 현재 상태

### 1.1 파일을 읽는 방법

| 보기 | 읽는 곳 | 보관하는 값 | 다시 읽는 기능 |
|---|---|---|---|
| 마크다운·코드 | `hooks/editorDocumentLoad.ts:83-107` 의 `loadDocument` → `fileApi.readFile` | 본문(`bodyAtOpen`)과 인코딩만 보관. 수정 시각·해시는 없다 | 없다. 본문은 탭이 마운트될 때 한 번 읽는다(`EditorDocumentPanel.tsx:354-363`) |
| HTML 뷰어 | 토큰 주소를 iframe 에 연다(`HtmlFileTab.tsx:78-90`). 서버는 요청마다 파일을 새로 읽어 보낸다 | 토큰 | 있다. "다시 불러오기" 버튼과 F5, 저장 직후(`HtmlFileTab.tsx:118-130`). 단, iframe 만 다시 그리고 소스 편집기의 본문은 그대로다 |
| 이미지 | `readImage` → Blob(`editorDocumentLoad.ts:91`) | Blob | 없다. 단, 같은 창에서 이웃 이미지로 넘어가는 `navigateImage` 가 문서를 새로 읽어 바꿔 끼운다(`useEditorWindows.ts:726-764`). 이 경로를 다시 쓸 수 있다 |
| SVG 소스 | 처음 열 때 한 번 읽어 캐시한다(`svgTabModel.ts:60-68`) | 본문 | 없다 |

### 1.2 저장과 충돌

- 저장은 `POST /files/write {path, content}` 이다(`services/api.ts:419-428`). 예상 수정 시각이나 해시를 보내지 않는다. 서버는 그대로 덮어쓴다(`FileService.ts:668-704`).
- 저장하지 않은 편집 상태(dirty)는 `editorWindowSave.ts:98-180` 이 관리한다.
- SRS 는 충돌 감지를 일부러 범위 밖에 두었다. `41.markdown-editor.srs.md:38` 에 "저장 시 외부 변경 충돌 감지. 덮어쓰기가 확정된 결정이다." 라고 적혀 있다. 같은 문서의 `:919` 는 파일 탐색기가 생기면 이 결정을 다시 보라고 한다. 파일 탐색기는 이미 있다.

### 1.3 서버

- 편집기 파일을 감시하는 장치는 없다. 파일 변경을 알리는 WebSocket 메시지도 없다(`WsRouter.ts` 는 터미널·세션 메시지만 다룬다).
- 서버에 있는 `fs.watch` 는 Git 요약용 하나뿐이다(`git/gitRepoWatcher.ts`). 그 주석은 WSL 경로(`\\wsl.localhost`)에서는 이벤트가 믿을 만하게 오지 않는다고 적는다(`:15-17`). 그래서 Windows·macOS 의 일반 저장소에서만 쓴다.
- 파일 하나의 속성을 가볍게 묻는 API 가 이미 있다. `GET /api/sessions/:id/files/stat` 은 크기, 수정 시각(`modified`), 변경 시각(`changed`)을 돌려준다(`fileRoutes.ts:88-99`, `FileService.ts:446-497`). 프런트엔드에는 `fileApi.statPath` 가 있다.
- 읽기 API(`/files/read`)는 수정 시각을 돌려주지 않는다. 안에서 `fs.stat` 을 이미 호출하므로(`FileService.ts:510`) 응답에 넣는 비용은 거의 없다.

### 1.4 다시 쓸 수 있는 폴링 방식

- Git 창의 "보이는 동안만 폴링"(FR-GIT-011): `Git/gitPollPolicy.ts` 와 `Git/gitSummaryStore.ts`.
  - 아무것도 보이지 않으면 폴링하지 않는다. 페이지가 숨겨지면(`visibilitychange`) 멈춘다.
  - 응답이 느리면 간격을 늘리고(마지막 응답 시간의 5배, 최대 30초), 같은 답이 계속되면 느리게 묻는다.
  - 같은 답이면 같은 객체를 돌려주어 다시 그리지 않는다.
- 편집기 창이 지금 화면에 보이는지는 `editor/editorWindowVisibility.ts` 가 판단한다.

## 2. 감지 방법 비교

| 방법 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. 서버 감시(`fs.watch`) + WebSocket 알림 | 즉시 알 수 있다. 요청이 없다 | WSL 경로에서 믿을 수 없다. 삭제된 폴더를 감시하면 이벤트가 끝없이 온다(`gitRepoWatcher.ts:10-13` 실측). 감시 핸들의 수명 관리, 세션·사용자별 구독 관리가 필요하다 | 1차 범위에서 제외 |
| B. 클라이언트 폴링(`/files/stat` 의 수정 시각 + 크기) | Windows, WSL, macOS, Linux 에서 똑같이 동작한다. 서버 변경이 없다. Git 창과 같은 방식이다 | 1~3초 늦게 반영된다. 보이는 탭마다 짧은 요청이 생긴다 | **추천** |
| C. 폴링하면서 내용 해시 비교 | 수정 시각이 바뀌지 않은 변경도 잡는다 | 파일 전체를 매번 읽어야 한다 | 제외 |

B 의 비용은 크지 않다. 화면에 보이는 탭 하나에 2초마다 `stat` 한 번이다. 숨겨진 탭, 최소화된 창, 백그라운드 브라우저 탭은 묻지 않는다. 응답이 느리면(WSL) 간격을 늘린다.

## 3. 보기별 동작 (안)

| 보기 | 파일이 바뀌면 |
|---|---|
| HTML 뷰어 | 기존 "다시 불러오기" 와 같은 경로로 iframe 을 다시 연다. 스크롤 위치는 iframe 이 다시 열리면서 맨 위로 돌아간다. 같은 출처가 아니라서(샌드박스) 위치를 되살릴 수 없다 |
| 이미지·SVG 미리보기 | 새 Blob 을 받아 바꿔 끼운다. 확대·이동 상태는 유지한다 |
| 마크다운·코드: 저장하지 않은 편집이 없을 때 | 새 본문으로 바꾼다. 커서와 스크롤은 가능한 한 유지한다 |
| 마크다운·코드: 저장하지 않은 편집이 있을 때 | 덮어쓰지 않는다. 편집기 위에 "디스크의 파일이 바뀌었습니다" 띠를 띄우고 [다시 불러오기] [내 편집 유지] 를 고르게 한다 |
| 파일이 지워지거나 이름이 바뀌었을 때 | 내용은 그대로 두고 "파일이 없습니다" 띠를 띄운다 |

내가 저장해서 바뀐 수정 시각은 외부 변경으로 보지 않는다. 저장 응답에 새 수정 시각을 담거나, 저장 직후 `stat` 으로 기준값을 새로 잡는다.

## 4. 토글

- 위치: 편집기 창 위쪽(제목 막대 또는 탭 막대 오른쪽)에 "자동 새로고침" 토글을 둔다.
- 범위: 브라우저에 저장하고 모든 편집기 창에 함께 적용한다. Git 창의 "제목 줄바꿈" 과 같은 방식이다.
- 기본값: 켜짐을 추천한다. 꺼져 있으면 지금과 같다(HTML 뷰어의 수동 "다시 불러오기" 는 남는다).

## 5. 요구사항에 미치는 영향

- 새 요구사항이 필요하다(편집기 범위, `41.markdown-editor.srs.md`).
- `:38` 의 "충돌 감지 제외, 덮어쓰기" 결정과 부딪힌다. 3절의 "저장하지 않은 편집이 있을 때" 동작은 사실상 외부 변경 감지다. 저장할 때 막을지(저장 직전 `stat` 비교 후 확인)는 따로 정한다.
- 파일 탐색기 트리의 자동 갱신(`42.file-explorer.srs.md:33`, 범위 밖)은 이번 범위에 넣지 않는다.

## 6. 정할 것

1. 기본값: 켜짐(추천) 또는 꺼짐.
2. 저장하지 않은 편집이 있을 때 외부 변경이 오면: 띠로 묻기(추천) 또는 무시.
3. 저장할 때 외부 변경이 있었으면: 지금처럼 덮어쓰기(추천: 1차는 그대로) 또는 확인 묻기.
4. 폴링 간격: 2초(추천), 응답이 느리면 늘림.
