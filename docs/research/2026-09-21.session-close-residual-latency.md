# 세션 닫기 잔여 지연 제거 연구

- 날짜: 2026-09-21
- 선행: `PERF-BGSTAB-012` (`docs/report/2026-09-21.session-close-latency.md`)
- 대상 요구사항: `FR-BGSTAB-011` (Wave 2 검증된 프로세스 트리 종료)
- 측정 호스트: 이 개발 머신, Windows PowerShell 5.1.26100, 프로세스 약 1220–1290개, `pwsh` 7 없음

## 1. 무엇이 남아 있나

`PERF-BGSTAB-012` 이후 화면에서는 탭이 즉시 사라진다. 그러나 서버의
`WorkspaceService.deleteTab` 요청 경로에는 아직 아래가 남아 있다
(Windows, `shellType=auto` → `powershell.exe`/conpty, `processCleanup.mode=enforce`).

| 단계 | 현재 비용 | 왜 있는가 |
|---|---|---|
| ① kill 전 `inspect` — CIM 전체 열거 1회 | 약 3.2s | 루트 PID 의 start identity 를 기록값과 대조(PID 재사용 방어) + 자손 표본 수집 |
| ② `taskkill /PID /T /F` | 약 0.1s | 실제 종료 |
| ③ `gracefulWaitMs` 대기 | 0.75s | POSIX SIGTERM 유예의 흔적 |
| ④ kill 후 `inspect` — CIM 전체 열거 1회 | 약 3.2s | 루트 생존 재확인 |
| ⑤ 표본 자손 생존 probe | ≈0 | `PERF-BGSTAB-012` 로 이미 상수화 |

합계 약 **7.2초**. 실제로 셸 트리가 죽는 시점은 ①+② 뒤 **약 3.3초**.

## 2. 실측

같은 PID(`explorer.exe`)에 대해 각 방법의 벽시계 시간.

| 방법 | 실측 | 비고 |
|---|---|---|
| `Get-CimInstance Win32_Process` 전체 열거 | 3.59 / 3.01 / 3.38s | 현행 ① ④ |
| `Get-CimInstance Win32_Process -Filter "ProcessId=N"` | 6.08 / 2.46 / 2.16s | 필터를 걸어도 CIM 비용은 그대로 |
| `powershell.exe -NoProfile -Command 'exit 0'` | 0.41 / 0.42s | 기동 하한 |
| **`(Get-Process -Id N).StartTime`** | **0.46 / 0.33 / 0.31s** | Win32 API 경로, WMI 를 안 탄다 |
| **`[System.Diagnostics.Process]::GetProcessById(N).StartTime`** | **0.29 / 0.27s** | 위와 같은 API, 파이프라인 오버헤드 없음 |
| `tasklist /FI "PID eq N"` | 1.19 / 1.07s | 생성 시각을 주지 않음 |
| `Get-Process` 전체(1218개) 카운트 | 0.42s | 전체 열거도 CIM 보다 8배 빠름 |
| `wmic` | 없음 | 이 호스트에서 제거됨(deprecated) |

결론: **비용은 PowerShell 도 열거 크기도 아니고 CIM/WMI 다.** 같은 정보를
`System.Diagnostics.Process` 로 읽으면 기동 비용(0.3–0.4s)만 남는다.

### 2-1. 두 시각은 마지막 자리가 다르다

```
CIM CreationDate.ToUniversalTime().ToString('o') = 2026-09-16T15:15:43.8052290Z
NET StartTime.ToUniversalTime().ToString('o')    = 2026-09-16T15:15:43.8052293Z
```

CIM 은 마이크로초(6자리)에서 잘리고 .NET 은 100ns(7자리)까지 준다.
문자열 동일성 비교(`info.startIdentity !== metadata.osStartIdentity`)를
그대로 두면 **소스를 바꾸는 순간 모든 세션이 `skipped-unverified`** 가 된다.
캡처(`readProcessStartIdentity`)와 검증(`queryWindowsProcessInfo`)을 반드시 함께
바꾸고, identity 문자열에 소스 접두어를 넣어(`win32net:<pid>:<iso>`) 구세대와
섞이지 않게 해야 한다.

### 2-2. node-pty 는 이미 네이티브로 콘솔 프로세스 목록을 안다

`node-pty/lib/windowsPtyAgent.js` `kill()`:

- conpty: `_getConsoleProcessList()` → `conpty_console_list_agent` 를 `fork` 해
  Win32 `GetConsoleProcessList` 를 부르고, 나온 PID 전부에 `process.kill`.
- winpty: `_ptyNative.getProcessList(pid)` 동기 호출 후 같은 처리.

즉 `data.pty.kill()` 만으로 콘솔에 붙은 프로세스 트리가 이미 죽고, 그 목록은
CIM 없이 네이티브로 얻는다. 현행 ① 의 "자손 표본 수집" 을 CIM 으로 하는
것은 이 정보를 두 번, 훨씬 비싸게 구하는 것이다.

## 3. 선택지

### A. identity 소스를 `System.Diagnostics.Process.StartTime` 으로 (① ④ 각 3.2s → 0.3s)

- `readProcessStartIdentity` 와 `queryWindowsProcessInfo` 의 PowerShell 본문을
  `[System.Diagnostics.Process]::GetProcessById(N).StartTime` 으로 교체.
- 접두어 `win32net:`. 구세대 `win32:` identity 를 가진 **업그레이드 시점의 살아있는
  세션**은 대조 불가 → `skipped-unverified` → kill 시도 없음. 안전한 쪽으로
  실패하며, `FR-BGSTAB-011` AC-2 가 정확히 이 동작을 요구한다. 재시작 후 사라지는
  일회성 비용.
- `ExecutablePath` 는 `MainModule.FileName` 으로 대체 가능하나 다른 세션 소유
  프로세스에서 접근 거부가 날 수 있다 — 어차피 Windows 경로는 cwd/경로를
  검증에 쓰지 않으므로(AC-2 명시) 빼도 된다.
- 위험: 낮음. 우리 자식 프로세스에 대한 `GetProcessById` 는 권한 문제가 없다.

### B. Windows 에서 `gracefulWaitMs` 를 0 으로 (③ 0.75s → 0)

`taskkill /F` 는 강제 종료라 유예가 의미가 없다. `terminate()` 의 win32 분기에서
`inspectAfterDelay(metadata, 0, …)` 로 바꾸면 끝. 설정값 자체는 POSIX 용으로 남긴다.
위험: 없음.

### C. Windows 자손 목록을 CIM 대신 네이티브로 (① 의 자손 수집 제거)

두 갈래:

- C-1. **자손 표본을 걷지 않는다.** Windows 는 `/T` 가 트리를 처리하고, kill 후
  검증은 루트 생존 + `PERF-BGSTAB-012` 의 probe 로 충분하다. `childPids: []` 를
  돌려주면 `descendantPids` 가 비고 표본 루프가 돌지 않는다. 대신 "살아남은 자손"
  보고가 Windows 에서 사라진다 — `FR-BGSTAB-011` AC-4 는 POSIX 조항이라 위반은
  아니지만 텔레메트리 한 항목이 준다.
- C-2. **node-pty 의 콘솔 프로세스 목록을 쓴다.** `conpty_console_list` 네이티브
  모듈은 `node-pty` 패키지에 포함돼 있고 `loadNativeModule('conpty_console_list')`
  로 직접 로드할 수 있다. 콘솔에 붙은 PID 를 ms 단위로 준다. 단 "콘솔에 붙은
  프로세스" 와 "자손" 은 같지 않다(콘솔을 떼고 나간 데몬은 빠진다). 단일 exe
  빌드(`OPS-BGSTAB-017`)에서는 이 `.node` 가 자산 글롭에 포함돼 있는지 확인해야 한다.

권장은 **C-1**. 얻는 것은 ① 이 "identity 한 번 읽기" 로 줄어드는 것이고,
잃는 것은 Windows 한정 자손 보고다.

### D. kill 후 검증(④ ⑤)을 요청 경로 밖으로

`terminate()` 를 `kill` 과 `verify` 로 나누고, `terminateSession` 은 kill 까지만
`await` 한 뒤 `finalizeSession` 을 실행하고, verify 결과는 나중에
`recordCleanupObservation` 으로 흘려 넣는다.

- `FR-BGSTAB-011` AC-5("… await the result …") **승계 필요.** `deleteTab` 은 이미
  반환값을 읽지 않으므로 HTTP 의미는 바뀌지 않지만, `markTabStopped` 의
  `cleanupStatus` 가 'not-started' → 최종 상태로 넘어가는 시점이 응답 뒤로 밀린다.
  workspace 저장을 한 번 더 하거나, cleanupStatus 를 `finalizeSession` 이 아니라
  verify 완료 시 갱신하도록 옮겨야 한다.
- 서버 종료 중 verify 가 진행 중이면 잘릴 수 있다 — 텔레메트리 손실일 뿐 프로세스는
  이미 죽었다.
- 위험: 중간. `test-runner.ts` 의 `testSessionManagerTerminateSessionAwaitsEnforceTerminator`
  가 정확히 이 대기를 단언하고 있어 함께 바뀐다.

**A+B+C 를 먼저 하면 D 없이도 요청 경로가 약 0.7s 로 내려온다.**
그 시점에 D 가 남기는 것은 0.3s 다. D 는 승계 비용 대비 이득이 작아 후순위.

### E. 기각: PowerShell/CIM 상주 워커

기동 0.4s 를 없애도 CIM 2–3s 가 남는다. A 가 같은 비용을 더 단순하게 없앤다.

### F. 기각(현재): identity 검증 자체를 생략

pty 가 `onExit` 를 내지 않았으면 루트 PID 는 살아 있고 재사용되지 않았다는 논리는
대부분 맞지만, `FR-BGSTAB-011` AC-1/AC-2 의 존재 이유가 "대부분" 을 믿지 않는
것이다. A 로 비용이 0.3s 가 되면 생략의 이득이 없다.

## 4. 권장 순서와 기대치

| 단계 | 요청 경로 | 실제 kill 시점 | SRS 영향 |
|---|---|---|---|
| 현재 | 약 7.2s | 약 3.3s | — |
| B | 약 6.5s | 약 3.3s | 없음 |
| B + A | 약 0.8s | 약 0.4s | `FR-BGSTAB-011` 구현 노트에 identity 소스 변경·`win32net:` 접두어·업그레이드 시점 세션의 `skipped-unverified` 기록 |
| B + A + C-1 | 약 0.7s | 약 0.4s | Windows 자손 보고 제거를 AC-4 옆에 명시 |
| + D | 약 0.4s | 약 0.4s | AC-5 승계 |

A 를 위한 테스트: `processInfoQueryTimeout.test.ts` 옆에 (1) 캡처와 검증이 같은
PowerShell 본문 소스를 쓴다, (2) `win32:` 구세대 identity 는 `skipped-unverified`,
(3) `win32net:` 동일 identity 는 통과 — 를 두면 2-1 의 함정이 다시 들어오지 못한다.

## 5. 열린 질문

- `GetProcessById(N).StartTime` 이 **다른 사용자 세션/권한 상승 프로세스**에서
  거부되는지는 재지 않았다. 우리 세션 루트는 서버의 자식이므로 해당 없음.
- 단일 exe 빌드에서 `powershell.exe` 를 `execFile` 하는 것은 그대로다 —
  PowerShell 이 없는 Windows 는 없다고 가정한다(Server Core 포함).
- 이 연구의 숫자는 이 머신 하나의 것이다. CIM 비용은 설치된 WMI provider 수에
  따라 크게 흔들리므로(같은 파일 주석의 과거 실측 1990/2033/3063ms), 상대 비교만
  신뢰한다.
