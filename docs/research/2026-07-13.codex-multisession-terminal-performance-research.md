# Codex 다중 세션 시 성능·키 입력 지연 — 원인 분석과 해결 로드맵

> BuilderGate에서 Codex(TUI 코딩 에이전트)를 여러 개 동시 실행하면 전체가 느려지고 **특히 키보드 입력이 심하게 느려지는** 증상에 대한 통합 연구. 4개 서브에이전트(출력 파이프라인 / 입력 지연 / TUI·감지기 / 아키텍처)가 코드를 직접 조사한 결과를 취합했다.

---

## 1. 증상

- Codex가 작업 중 "thinking 스피너 / 텍스트 반짝임" 애니메이션을 **초당 여러 번 전체 화면 repaint** 한다.
- 이런 Codex 세션을 여러 개(목표 수십 개) 동시에 돌리면 전체 반응성이 급락한다.
- 무엇보다 **키를 눌러도 화면 반영이 느리다**(입력 왕복 지연).

---

## 2. 근본 원인 (4축 공통 결론)

**단일 Node.js 프로세스·단일 이벤트 루프**가 모든 세션의 PTY 출력을 동기 처리한다. 서버는 검증상 `worker_threads`/`cluster`가 전혀 없다(`index.ts`). PTY 출력 chunk 하나가 도착할 때마다 메인 스레드가 다음을 **동기로** 수행한다 (`SessionManager.ts:724` `onData`):

1. **감지기 다발** — OSC133 마커, 터미널 타이틀 ×2, foreground 앱 감지, echo/AI-TUI 분류. 이 안에서 `stripTerminalControlSequences`(정규식 4패스 + 문자열 4할당)가 **프레임당 약 4회** 호출된다.
2. **headless write** — 세션마다 서버측 `@xterm/headless` 가상 터미널에 `terminal.write()`로 ANSI를 파싱해 화면 상태를 재구성.
3. **브로드캐스트** — 구독자별 `JSON.stringify` + `ws.send`.

이 전부가 **`= 세션 수 × repaint 빈도 × 프레임당 감지/파싱 비용`**으로 한 코어에 집중된다. 그 결과 생성되는 마이크로태스크·CPU 점유가 **키 입력 콜백(`writeInput`→`pty.write`)을 뒤로 밀어** 입력 지연으로 체감된다.

> 단일 스레드이므로 "출력이 느려지는 것"과 "입력이 느려지는 것"은 **같은 병목의 두 얼굴**이다. 출력 처리가 루프를 점유하면 입력이 굶는다.

## 3. 판을 바꾸는 4가지 교차 발견 (코드로 검증됨)

이 사실들이 해법의 우선순위를 결정한다.

| # | 발견 | 근거 | 함의 |
|---|------|------|------|
| **F1** | **라이브 출력은 이미 raw passthrough** | `applyHeadlessOutput`이 headless 직렬화 결과가 아니라 큐에서 꺼낸 **원본 바이트**를 그대로 전송 (`SessionManager.ts:3391-3400`) | 세션마다 돌리는 **headless write는 라이브 스트리밍에 불필요**. 오직 재접속/스냅샷/screen-repair용. → TUI 세션에서 스킵 가능 |
| **F2** | **직렬화(serialize)는 병목이 아니다** | `serializeHeadlessTerminal`은 스냅샷 요청 시에만 lazy 호출 + `screenSeq` 캐시 (`:2465`/`:2489`). 연속 스트리밍 중엔 안 돎 | 병목은 "무거운 직렬화"가 아니라 **프레임 빈도에 비례하는 per-chunk 오버헤드** |
| **F3** | **입력 방향엔 우선순위·패스트패스가 전무** | 우선순위 3-레인(`wsSendPolicy.ts:102-138`)은 **서버→클라 출력 전용**. 클라→서버 입력은 평범한 I/O 콜백으로 출력 뒤에 큐잉 | 입력을 먼저 빼낼 스케줄링 장치가 아예 없음 |
| **F4** | **coalescing 인프라는 있으나 기본값에서 꺼져 있음** | `wsSendMode` 기본 `'direct'`(`config.schema.ts:199`) → 청크당 `ws.send` 1회, 병합 없음. 병합(`tryCoalesceOutputMessage`, 16ms)은 백프레셔로 큐가 쌓인 뒤에만 진입. `writeBatchMaxBytes`/`writeLagWarnMs`는 배선만 되고 **미구현 스캐폴딩** | 배칭을 "정상 경로에서 항상" 켜지게 바꾸면 됨 |

추가: `writeInput`은 `pty.write`(`:1330`) **앞에** 커맨드버퍼 갱신·foreground hint·상태전환·echoTracker 등 ~50줄 부가 처리를 몰아둔다(`:1277-1327`). 이들 중 **PTY에 쓰이는 바이트에 영향을 주는 것은 하나도 없다** → 뒤로 미룰 수 있다.

## 4. 통합 실행 로드맵

여러 축의 제안을 중복 제거하고 **위험도·효과·난이도**로 재배열했다. 구현 시 각 항목은 **CLAUDE.md의 TDD 원칙(동작 변경은 실패 테스트 먼저)** 을 따른다.

### 0단계 — 측정 하니스 먼저 (필수 선행)
"이벤트 루프 포화 vs 물리 CPU 부족"을 객관적으로 구분해야 이후 판단이 선다.

- `perf_hooks.monitorEventLoopDelay()` 히스토그램(mean/p99) + `process.cpuUsage()` 델타를 **1코어 대비 %** 로 환산(`os.cpus()`) + `applyHeadlessOutput`의 `writeHeadlessTerminal` 구간(`:3384`) 누적 시간.
- 노출: 기존 `GET /api/sessions/telemetry`(`index.ts:797`, `getObservabilitySnapshot`)에 지표 추가. 이미 `maxSnapshotSerializeMs`·`headlessOutput.overflowCount`·`degradedCount` 포함됨.
- 판정: **루프 지연 p99 高 + 프로세스 CPU ≈ 100%(1코어) + 나머지 코어 유휴 → 단일 스레드 CPU-bound 확정**(멀티코어/offload가 정답). 루프 지연 高 but CPU 여유 → GC/동기 fs/backpressure 의심.
- 재현: 40세션이 전체 화면 ANSI를 ~10fps repaint하는 스크립트 + 한 세션에서 타이핑하며 **입력→에코 지연** 측정.

### 1단계 — 즉효·저위험 (난이도 S, 지금 바로)
프레임 발생원을 줄이고, 프레임당 낭비를 제거하고, 키 입력을 최우선화한다.

| 항목 | 출처 | 내용 | 효과 | 리스크 |
|------|------|------|------|--------|
| **① Codex 애니메이션 억제** | 축3 A1 | 세션 env `CODEX_HOME` 격리 config 또는 `-c tui.animations=false -c tui.alternate_screen="never" -c tui.show_tooltips=false` 주입 (`buildShellEnv` `:1814` / `createSession` envPatch `:590`) | **최상** — 프레임 발생원 감소로 감지기·headless·WS·브라우저 전 스택 + 키 지연 동시 완화 | 잔여 elapsed-timer repaint는 남을 수 있음(→ B 병행). `alternate_screen` 스크롤 UX 변화 실측 필요 |
| **② TUI 세션 headless write 스킵** | 축4 C | F1 근거. `isInteractiveForeground` 감지 세션은 `writeHeadlessTerminal` 생략, 라이브는 이미 raw로 나감. 재접속은 raw ring buffer + resize/`\x0c` nudge로 앱 자가 repaint 유도 | **최상 ROI** — 문제 세션의 per-chunk 메인스레드 파싱을 사실상 0으로 | 스크롤 출력 중간 재접속 시 화면 충실도↓(TUI 한정 수용). 설정 플래그 뒤 opt-in |
| **③ writeInput 재정렬** | 축2 A | `pty.write`를 가드 직후 **최우선** 실행, 부가 처리(`:1277-1327`)는 write 뒤(필요 시 `setImmediate`)로 | 모든 키의 동기 prefix 지연 제거 | status/`input:rejected` 브로드캐스트 순서 회귀 테스트 필요 |
| **④ HermesForegroundDetector 조기 bail** | 축3 B1 | `inspect` 최상단 `if (!attached && appHint!=='hermes') return null;` — Codex/Claude 세션은 절대 attach 안 됨 | 프레임당 낭비 strip 1회+appendTail 제거 | **거의 0** (동작 불변) |
| **⑤ 디버그 캡처 낭비 제거** | 축1 H2 | `buildRawOutputDebugDetails`(`:822`)를 `isDebugCaptureEnabled` 뒤로 가드. 현재 결과가 곧 폐기됨에도 매 청크 생성 | 프레임당 객체 alloc + byteLength 2회 제거 | 없음(단 echoTracker 프루닝 부수효과 분리 확인) |

### 2단계 — 중기·구조 개선 (난이도 M)
남는 프레임의 단가를 낮추고 프레임을 병합한다.

- **⑥ strip/normalized 메모이즈** (축3 B2): onData 1회 내에서 strip→정규화→trim을 **한 번만** 계산해 `classifyAiTuiOutputSignal`·`isLikelyCommandEchoOutput`에 전달. 프레임당 strip 4회→1회(정규식 ~16패스→~4패스). 순수 리팩터, 테스트로 회귀 고정.
- **⑦ per-session 출력 coalescing** (축1 H1 = 축2 C = 축4 D 통합): onData 청크를 세션별 8–16ms 창(leading-edge)으로 모아 감지·headless·라우팅을 **1회**로 접음. 미구현 `writeBatchMaxBytes`/`writeLagWarnMs` 스캐폴딩을 그대로 배선 → config on/off. **headless write의 마이크로태스크 홍수(`:3350`)도 이 배칭으로 해소** → 입력이 매크로태스크 사이에 끼어들 틈 확보.
- **⑧ repaint-only 프레임 재분류 throttle** (축3 B3): foreground가 AI로 확정 + 직전 activity가 `repaint_only`면 이후 프레임은 값싼 semantic-hint(raw 1패스) false일 때 full 분류 스킵. 기존 `lastRepaintOnlyAt`/`lastSemanticOutputAt` 재사용. **트레이드오프**: 상태 전이 감지가 최대 ~100–150ms 지연(idle/running 표시 순간 어긋남) → 보수적 THROTTLE_MS로 실측 튜닝.

### 3단계 — 장기·확장성 (난이도 L, 스케일 목표 도달용)
1·2단계로 단일 프로세스 상한을 최대한 밀어낸 뒤, 그래도 부족하면.

- **⑨ 백그라운드(비포커스) 세션 프레임 감축** (축1 H3): client→server focus 신호 추가, 안 보이는 세션은 저레이트/드롭 후 재포커스 시 screen-repair 재동기화. 전송·stringify 부하를 **세션 수가 아니라 가시 세션 수**에 비례시킴.
- **⑩ worker_threads 풀 offload** (축4 A): headless 상태유지+serialize를 `hash(sessionId)`로 워커에 고정 배정. **②로 라이브/헤드리스를 이미 분리해두면 워커는 순수 백그라운드가 되어 도입 난이도 급락.** 난점: postMessage 구조적 복제 비용(→ SharedArrayBuffer 링버퍼 고려), 순서는 세션-워커 1:1로 보장.
- **⑪ 세션 샤딩(멀티 프로세스)** (축4 B): 샤드별 node-pty + 부분 SessionManager, 메인은 라우팅만. 코어 수만큼 선형 확장 + 장애 격리. 최대 리팩터(WorkspaceService·MCP·cross-session broadcast 결합 해체 필요). **최후 수단.**

## 5. 권장 착수 순서 (요약)

```
0. 측정 하니스 (loop-delay + cpuUsage% + headless-write 시간)  ← 먼저
1. ① Codex 애니메이션 억제  +  ② TUI headless 스킵  +  ③ writeInput 재정렬
   +  ④ Hermes bail  +  ⑤ 디버그 낭비 제거      ← 즉시, 저위험, 최대 효과
2. ⑥ strip 메모이즈  →  ⑦ 출력 coalescing  →  ⑧ repaint throttle
3. ⑨ 백그라운드 감축  →  ⑩ worker offload  →  ⑪ 세션 샤딩
```

**핵심 논리**: ①로 프레임 **수**를 줄이고 → ②/④/⑤/⑥으로 남는 프레임 **단가**를 낮추고 → ③으로 키 입력을 **최우선**화 → ⑦로 프레임을 **병합** → 그래도 세션 수가 상한을 치면 ⑨/⑩/⑪로 **멀티코어 확장**. ①·②는 코드 대비 효과가 압도적이라 가장 먼저 검증할 가치가 있다.

## 6. 미확인·실측 필요 항목 (정직성)

- Codex `tui.animations=false`가 스피너는 끄지만 **elapsed-timer repaint까지 제거하는지**는 버전에 따라 다를 수 있음 → 적용 후 잔여 프레임 측정 전제.
- `tui.alternate_screen="never"` / `tui.raw_output_mode`의 렌더링·스크롤 영향은 문서 명시 부족 → BuilderGate xterm에서 실측.
- `CODEX_HOME` 격리 시 사용자 기존 `~/.codex` 인증과 분리됨 → 인증 상속 또는 `-c` 최소 개입 방식 검토.
