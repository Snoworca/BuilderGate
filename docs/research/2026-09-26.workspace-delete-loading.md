# Workspace 삭제 로딩 UI 연구·설계

- 일자: 2026-09-26
- 브랜치 / HEAD: `work/mcp-session-orchestration-20260709` / `77347a81`
- 성격: 연구·계획만 한다. 이 문서 말고는 아무 파일도 바꾸지 않았다.
- 관련 요구사항: PERF-BGSTAB-015 (AC-2·AC-3 과 충돌하므로 승계 대상), FR-UIDS-002 (공용 부품), FR-UIDS-003 (문구), NFR-UIDS-001 (대비·초점·터치)
- 결론: **(a) 확인창 안에서 진행 표시.** "모두 삭제"를 누르면 같은 창의 버튼이 스피너와 "삭제하는 중…"으로 바뀌고 창이 잠긴다. 서버가 답하면 **같은 React 커밋에서** 창이 닫히고 목록에서 행이 사라진다. 실패하면 창은 그대로 두고 오류와 "다시 시도"를 보여 준다.

## 3. 대안 비교

| 안 | 설명 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| **(a) 확인창 안 진행 표시** | 같은 창에서 주 버튼이 스피너+"삭제하는 중…"으로 바뀌고 창이 잠긴다 | 사용자가 누른 자리에서 바로 반응이 보인다. 창을 바꾸지 않아 깜빡임과 초점 이동이 없다. 이중 제출이 자연히 막힌다. 어떤 Workspace·몇 개 터미널인지 맥락이 그대로 남는다. 앱의 기존 패턴(LoginForm, SessionSaveDialog)과 같다. 코드 변경이 가장 작다 | 1.5–4 s 동안 앱이 막힌다(요청이 원하는 바다). Esc·바깥 클릭·취소를 잠가야 한다 | **채택** |
| (b) 전용 로딩 창으로 교체 | 확인창을 닫고 "삭제하는 중" 창을 새로 띄운다 | 상태별 역할이 분리된다 | 창이 바뀌면서 화면이 튄다. 새 창으로 초점을 옮겨야 하고 스크린리더가 창을 새로 읽는다. 맥락을 다시 적어야 한다. 부품이 하나 더 는다 | 기각 |
| (c) 전체 화면 오버레이 | 앱 전체를 덮는 로딩 화면 | 가장 강하게 막는다 | 몇 초짜리 국소 작업에는 과하다. 앱이 멈추거나 새로고침되는 것처럼 보인다. 어느 Workspace 인지 맥락이 사라진다. WindowDialog·편집기 창과 z-index 가 얽힌다 | 기각 |
| (d) 사이드바 행 busy (막지 않음) | 창은 곧바로 닫고 행에 스피너를 띄운다 | 기다리는 동안 다른 일을 할 수 있다. 체감 성능이 가장 좋다 | 요청("삭제 버튼 → 로딩 → 로딩이 사라지며 반영")과 흐름이 다르다. 삭제 중인 Workspace 에 탭 추가·이름 변경·선택·드래그·죽어 가는 터미널에 입력을 모두 막아야 한다. 모바일에서는 서랍이 닫혀 있어 행이 안 보인다 | 기각. 필요해지면 후속으로 검토 |

## 4. 채택안 상세

### 4.1 상태와 전이

```
confirm ──모두 삭제──▶ deleting ──서버 200 (또는 404)──▶ (창 닫힘 + 행 제거, 같은 커밋)
   │                     │
   │취소/Esc/바깥          └─서버 오류──▶ error ──다시 시도──▶ deleting
   ▼                                        │
 (닫힘, 아무 일 없음)                           └─닫기/Esc/바깥──▶ (닫힘, Workspace 그대로)

터미널 없는 Workspace: 확인창 없이 요청 → 성공하면 행 제거 / 실패하면 창을 error 상태로 연다
```

| 상태 | 창 | 주 버튼 | 보조 버튼 | Esc · 바깥 클릭 | 목록의 행 |
|---|---|---|---|---|---|
| `confirm` | 열림 | "모두 삭제" | "취소" | 취소 | 있음 |
| `deleting` | 열림, 잠김 | 스피너+"삭제하는 중…", `aria-disabled="true"`, 클릭 무시 | "취소" `disabled` | 무시 | **있음** |
| `deleting` + 10 s 경과 | 같음 | 같음 | 같음 | 무시 | 있음 |
| 성공 | **닫힘** | - | - | - | **사라짐 (창과 같은 커밋)** |
| `error` (다시 시도 가능) | 열림 | "다시 시도" | "닫기" | 닫기 | 있음 |
| `error` (`LAST_WORKSPACE`) | 열림 | 숨김 | "닫기" | 닫기 | 있음 |

### 4.2 시간 값

| 이름 | 값 | 근거 |
|---|---|---|
| 클릭 반응 | 클릭 이벤트 핸들러 안에서 바로 `deleting` 으로 바꾼다 (1프레임 이내) | Nielsen 0.1 s |
| 스피너 띄우는 지연 | **0 ms** | 대기가 거의 항상 1 s 를 넘는다. 버튼 문구 변경 자체가 클릭 확인이다 |
| 최소 표시 시간 `WORKSPACE_DELETE_MIN_BUSY_MS` | **500 ms** (클릭 시점부터) | 서버가 더 빨리 답해도 500 ms 까지 기다렸다가 닫는다. 진행 상태가 한두 프레임만 번쩍이지 않게 한다. 탭 3개 기준으로는 서버가 늘 더 늦으므로 지연이 더해지지 않는다 |
| 느림 안내 `WORKSPACE_DELETE_SLOW_AFTER_MS` | **10 000 ms** | Nielsen 10 s 한계. 문구만 바꾼다 |
| 클라이언트 타임아웃 | **없음** | 서버는 터미널 종료를 되돌릴 수 없고, 중간에 포기하면 상태가 어긋난다. 자기 클라이언트는 `workspace:deleted` 방송을 받지 않으므로 나중에 끝난 삭제가 화면에 반영되지 않는다. 네트워크가 끊기면 fetch 가 실패하므로 `error` 로 간다 |
| 닫힘·행 제거 애니메이션 | **없음** | "로딩이 사라지면서 반영"을 한 프레임에 맞춘다. 애니메이션은 반영을 늦춘다 |
| 취소 | 불가 | 서버에 중단 API 가 없다. 이미 죽은 터미널은 살릴 수 없다 |

### 4.3 성공 순간 ("로딩이 사라지면서 삭제가 반영")

- [ ] 서버 응답을 기다리는 동안 목록·탭·그리드 상태를 건드리지 않는다.
- [ ] 응답 뒤에 최소 표시 시간을 마저 기다린다.
- [ ] 하나의 동기 블록 안에서 다음을 모두 한다. 그러면 React 가 한 번에 커밋한다.
  - `setWorkspaces` (활성 Workspace 는 `resolveActiveWorkspaceAfterRemoval` 로 옆 Workspace 로 옮긴다)
  - `setTabs`, `setGridLayouts`
  - `clearMosaicLayoutForWorkspace`, `clearWorkspaceSnapshots`
  - `onRemoved()` → App 의 창 상태를 `null` 로 만든다
- [ ] 404(`WORKSPACE_NOT_FOUND`)는 성공으로 친다. 다른 클라이언트가 먼저 지운 경우이며, 목표(없어짐)가 이미 이루어졌다.

### 4.4 오류

| 경우 | 판정 | 주 문구 (`role="alert"`) | 보조 줄 | 버튼 |
|---|---|---|---|---|
| `LAST_WORKSPACE` (409) | 다시 시도 불가 | 마지막 Workspace는 삭제할 수 없습니다. | 없음 | "닫기"만 |
| `WORKSPACE_NOT_FOUND` (404) | 성공으로 처리 | - | - | - |
| 그 밖 (500, 네트워크) | 다시 시도 가능 | Workspace를 삭제하지 못했습니다. 일부 터미널은 이미 종료되었을 수 있습니다. | `원인: {서버 메시지}` | "닫기" · "다시 시도" |

- 판정은 오류 메시지 안의 코드 문자열(`LAST_WORKSPACE`, `WORKSPACE_NOT_FOUND`)로 한다. `apiError.ts` 가 `message (CODE)` 형태로 붙여 준다.
- 목록의 행은 처음부터 사라진 적이 없으므로 되돌릴 것이 없다. `workspaceRemoval.ts` (스냅샷·복원)는 지운다.
- 부분 실패(터미널은 죽고 마지막 저장만 실패)는 두 번째 문장이 사실대로 알린다 (FR-UIDS-003 AC-3: 무엇이 사라지고 무엇이 남는지).

#### `ConfirmModal` 확장 (새 prop 은 모두 선택, 기존 5곳은 동작이 그대로다)

| prop | 타입 | 기본값 | 효과 |
|---|---|---|---|
| `busy` | `boolean` | `false` | 주 버튼 `aria-disabled="true"` + 클릭 무시 + `BusyLabel` 진행 쪽 표시. 보조 버튼 `disabled`. Esc·바깥 클릭 무시 |
| `busyLabel` | `string` | `'처리하는 중…'` | 진행 중 주 버튼 문구 |
| `error` | `{ message: string; detail?: string } \| null` | `null` | 본문 아래 `.ui-inline-alert` (`role="alert"`) |
| `hideConfirm` | `boolean` | `false` | 주 버튼을 그리지 않는다 (다시 시도가 무의미한 오류) |
| `initialFocus` | `'cancel'` | 없음 | 열릴 때 보조 버튼에 초점을 두고, 창 안에서 Tab 을 가둔다. 없으면 지금 동작 그대로다 |

모든 호출자에게 동작 변화 없이 더하는 것: `.modal-content` 에 `role="alertdialog"`, `aria-modal="true"`, `aria-labelledby={titleId}`, `aria-describedby={messageId}` (`useId`). `.confirm-message` 에 `aria-live="polite"` (처음 내용은 읽지 않고, 바뀔 때만 읽는다).

CSS 추가 (`ConfirmModal.css`):
- `.btn-destructive[aria-disabled='true']` → `cursor: progress`
- `.btn-destructive:hover:not(:disabled)` → `:not(:disabled):not([aria-disabled='true'])` 로 좁힌다

주 버튼에 `disabled` 를 쓰지 않는 이유: 초점이 가 있는 버튼이 `disabled` 가 되면 브라우저가 초점을 `body` 로 떨어뜨린다. 그러면 키보드·스크린리더 사용자가 위치를 잃고, 투명도 0.5 가 "쓸 수 없음"으로 읽힌다.

#### 흐름 모델 (순수 함수, 새 파일 `components/Workspace/workspaceDeleteFlow.ts`)

```ts
export const WORKSPACE_DELETE_MIN_BUSY_MS = 500;
export const WORKSPACE_DELETE_SLOW_AFTER_MS = 10_000;

export type WorkspaceDeletePhase = 'confirm' | 'deleting' | 'error';
export interface WorkspaceDeleteError { message: string; detail?: string; retryable: boolean }
export interface WorkspaceDeleteState {
  phase: WorkspaceDeletePhase;
  workspaceId: string;
  tabCount: number;          // 창을 열 때 잡아 둔다. 진행 중에 목록이 바뀌어도 문구가 흔들리지 않는다
  slow: boolean;
  error: WorkspaceDeleteError | null;
}

openWorkspaceDelete(workspaceId, tabCount): WorkspaceDeleteState            // phase 'confirm'
startWorkspaceDelete(state): WorkspaceDeleteState | null                  // 'deleting' 이면 null (이중 제출)
markWorkspaceDeleteSlow(state): WorkspaceDeleteState                      // 'deleting' 일 때만 slow=true
failWorkspaceDelete(state, err: unknown): WorkspaceDeleteState            // phase 'error'
describeWorkspaceDeleteError(err: unknown): WorkspaceDeleteError & { treatAsDeleted: boolean }
canDismissWorkspaceDelete(state): boolean                                 // phase !== 'deleting'
workspaceDeleteDialogProps(state): { title; message; confirmLabel; cancelLabel; busy; busyLabel; error; hideConfirm }
remainingMinBusyMs(startedAt: number, now: number): number                // max(0, 500 - (now - startedAt))
```

#### `useWorkspaceManager.deleteWorkspace` (낙관적 → 서버 응답 후 반영)

```ts
deleteWorkspace: (id: string, options?: { holdUntil?: Promise<unknown>; onRemoved?: () => void }) => Promise<void>;
```

1. `suppressMosaicLayoutSaveForWorkspace(id)` (지금처럼)
2. `await workspaceApi.delete(id)`. 오류가 `WORKSPACE_NOT_FOUND` 이면 성공으로 보고 계속한다. 그 밖의 오류는 `releaseMosaicLayoutSaveSuppression(id)` 후 **그대로 던진다**. `setError` 는 부르지 않는다 (창이 보여 준다).
3. `await options?.holdUntil`
4. 동기 블록: `removeWorkspaceFromState(id)` + `options?.onRemoved?.()`
   - `removeWorkspaceFromState` 는 WS `'workspace:deleted'` 처리기와 같은 내용이다 (한 함수로 뽑아 둘이 같이 쓴다).
5. `workspaceRemoval.ts` 와 `snapshot/restore*` 호출을 지운다.

#### `App.tsx`

- `pendingDeleteWorkspace: string | null` → `workspaceDelete: WorkspaceDeleteState | null`. `pendingDeleteTabCount` 계산은 지운다 (값은 상태 안에 있다).
- `workspaceDeleteInFlightRef = useRef(false)`: 같은 프레임의 두 번 클릭 대비 (상태가 다시 그려지기 전).

```ts
const handleConfirmDeleteWorkspace = useCallback(async () => {
  const current = workspaceDeleteRef.current;             // 최신 상태 ref
  if (!current || workspaceDeleteInFlightRef.current) return;
  const next = startWorkspaceDelete(current);
  if (!next) return;
  workspaceDeleteInFlightRef.current = true;
  setWorkspaceDelete(next);                               // 클릭 핸들러 안에서 바로 → 1프레임 이내
  const hold = wait(WORKSPACE_DELETE_MIN_BUSY_MS);        // 클릭 시점부터 잰다
  const slow = window.setTimeout(
    () => setWorkspaceDelete(s => (s ? markWorkspaceDeleteSlow(s) : s)),
    WORKSPACE_DELETE_SLOW_AFTER_MS,
  );
  try {
    await wmRef.current.deleteWorkspace(next.workspaceId, {
      holdUntil: hold,
      onRemoved: () => setWorkspaceDelete(null),          // 목록 제거와 같은 동기 블록
    });
  } catch (err) {
    setWorkspaceDelete(s => (s ? failWorkspaceDelete(s, err) : s));
  } finally {
    window.clearTimeout(slow);
    workspaceDeleteInFlightRef.current = false;
  }
}, []);
```

- 터미널 없는 경로(`handleDeleteWorkspace`, 탭 0개): 확인창·로딩 없이 `deleteWorkspace(id)` 를 부른다 (예상 수십–수백 ms, Nielsen 1 s 미만이라 표시하지 않는다). 행은 서버가 답하면 사라진다. 실패하면 `failWorkspaceDelete(openWorkspaceDelete(id, 0), err)` 로 창을 오류 상태로 연다. 같은 in-flight ref 로 중복 호출을 막는다.
- 렌더:

```tsx
{workspaceDelete && (
  <ConfirmModal
    {...workspaceDeleteDialogProps(workspaceDelete)}
    destructive
    initialFocus="cancel"
    onConfirm={() => { void handleConfirmDeleteWorkspace(); }}
    onCancel={() => { if (canDismissWorkspaceDelete(workspaceDelete)) setWorkspaceDelete(null); }}
  />
)}
```

- 선택: 진행 중에 사이드바 `role="listbox"` 에 `aria-busy="true"`. "이 목록이 곧 바뀐다"는 뜻이며 E2E 가 잡을 고리도 된다.

## 5. 접근성

| 항목 | 명세 |
|---|---|
| 역할 | `.modal-content`: `role="alertdialog"`, `aria-modal="true"`, `aria-labelledby`=제목, `aria-describedby`=본문 |
| 초기 초점 | "취소" (APG: 가장 덜 파괴적인 동작). `initialFocus="cancel"` |
| Tab | 창 안의 버튼 사이만 돈다 (Shift+Tab 포함) |
| 진행 시작 | 초점은 주 버튼에 그대로 둔다 (`aria-disabled`, `disabled` 아님). 버튼 이름이 "삭제하는 중…"으로 바뀐다 |
| 상태 알림 | 본문 `<p aria-live="polite">` 가 진행 문구와 느림 문구로 바뀔 때 읽힌다 (WCAG 4.1.3) |
| `aria-busy` | 창에는 **달지 않는다**. `aria-busy` 컨테이너 안의 라이브 영역은 일부 스크린리더가 busy 가 풀릴 때까지 읽지 않는다. 사이드바 목록에만 선택으로 단다 |
| 오류 | `.ui-inline-alert` 에 `role="alert"` (삽입될 때 바로 읽힌다). 다시 시도가 가능하면 초점은 같은 주 버튼("다시 시도")에 남는다. `hideConfirm` 이면 초점을 "닫기"로 옮긴다 |
| 성공 후 초점 | 창과 행이 함께 사라지면 초점은 `body` 로 간다. 사이드바 행은 초점을 받을 수 없어서(`tabIndex` 없음) 옮길 곳이 없다 (§7 위험 7) |
| 키보드로 삭제 | 취소에서 Tab → "모두 삭제" → Enter/Space. Enter 를 누르고 있어 반복 클릭이 와도 가드가 막는다 |
| 대비 | 흰색 on `--danger-fill` 4.6:1 (글자·스피너). 오류 글자 `--danger-text` on `--danger-tint` (chrome 6.0:1 이상). 보조 줄 `--fg-muted` |
| 움직임 | reduced-motion 이면 회전이 2.4 s (기존 규칙). 뜻은 글자가 전한다 |
| 터치 | 모바일 버튼 최소 높이 44px (`globals.css`, NFR-UIDS-001 AC-3) |

| E3 | 이중 제출 (route: 1000 ms 지연 후 `route.continue()`) | 주 버튼 `dblclick()` + Enter 3회 → `page.on('request')` 로 센 DELETE 가 **1개** |
| E4 | 최소 표시 (route: 바로 200 응답) | 진행 상태가 보인 시간 ≥ 450 ms (타이머 오차 고려). 서버에는 Workspace 가 남으므로 정리가 id 로 지운다 |
| E5 | 마지막 Workspace (route: 409 `LAST_WORKSPACE`) | `마지막 Workspace는 삭제할 수 없습니다.`, `다시 시도` 없음, 초점이 `닫기` |
| E6 | 탭 0개 (route: 800 ms 지연 후 `continue()`) | 창이 뜨지 않는다. 지연 동안 행 1개, 응답 뒤 0개 |
| E7 | 움직임 줄이기 (선택) | `page.emulateMedia({ reducedMotion: 'reduce' })` → 스피너의 계산된 `animation-duration` 이 `2.4s` |
| E8 | 모바일 폭 (선택) | 390×844 에서 창이 화면 안에 있고 버튼 높이 ≥ 44px |

스크린샷: 진행 상태 1장, 오류 상태 1장.
