### FR-LOOP-001 — 루프 정의를 검증해 저장한다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | loop-scheduler |
| Status | implemented |
| Priority | high |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | #206 |
| Related Docs | [loop-scheduler.html](../design/loop-scheduler.html) |

#### Requirement

When a user saves a loop, the system shall validate it and keep it in server/data/loops.json so that it survives a server restart.

#### Rationale

Issue #206; design docs/design/loop-scheduler.html §③ and §⑤ 7, 11.

#### Acceptance Criteria

- [x] AC-1: 루프는 이름, 켜짐 여부, 일정, 보낼 곳, 단계 목록을 가지며 서버를 다시 켜도 그대로 남는다. 보낼 곳은 새 세션(셸, 디렉터리, 남겨 둘 탭 수 1~16, 기본 1) 또는 기존 세션(FR-LOOP-008)이다.
- [x] AC-2: 단계는 명령(한 줄) · 프롬프트(여러 줄 가능) · 대기(0 이상 3,600,000 이하의 정수 ms) · 세션 종료 네 가지다. 세션 종료가 마지막이 아닌 곳에 있으면 저장을 거부한다. 세션 종료는 새 세션 루프에만 둘 수 있다(FR-LOOP-008 AC-2).
- [x] AC-3: 단계가 하나도 없거나, 일정에 고른 요일·날짜·시각이 하나도 없거나, 빈 명령·프롬프트가 있으면 저장을 거부한다. 새 세션 루프는 셸과 디렉터리가 없으면 거부하고, 기존 세션 루프는 FR-LOOP-008 AC-2 대로 검사한다.
- [x] AC-4: 특정 날짜 일정의 모든 시각이 이미 지났으면 저장을 거부한다.
- [x] AC-5: REST API 는 GET/POST /api/loops, PUT/DELETE /api/loops/:id, POST /api/loops/:id/run(지금 한 번 실행)을 인증 뒤에 제공한다.

### FR-LOOP-002 — 루프의 다음 실행 시각을 서버 현지 시각으로 계산한다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | loop-scheduler |
| Status | implemented |
| Priority | high |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | #206 |
| Related Docs | [loop-scheduler.html](../design/loop-scheduler.html) |

#### Requirement

While a loop is enabled, the system shall run it at every time its schedule names and at no other time.

#### Rationale

Issue #206; design §⑤ 3, 4, 11.

#### Acceptance Criteria

- [x] AC-1: 요일마다: 고른 요일마다 고른 각 시각에 실행한다.
- [x] AC-2: 매월: 고른 날짜마다 고른 각 시각에 실행한다. 그 달에 없는 날짜(예: 2월 30일)는 건너뛰고, 말일은 그 달의 마지막 날이다. 같은 순간이 두 번 나오면(31일과 말일) 한 번만 실행한다.
- [x] AC-3: 특정 날짜: 그 날짜의 각 시각에 실행하고, 마지막 시각을 실행한 뒤 루프를 끈다.
- [x] AC-4: 간격: 기준 시각부터 간격(1분 이상)마다 실행하며, 날짜를 넘어 이어서 센다.
- [x] AC-5: 시각은 서버 기계의 현지 시간대로 해석한다.
- [x] AC-6: 서버가 꺼져 있던 동안 지나간 시각은 실행하지 않고, 서버가 켜진 뒤의 다음 시각부터 실행한다.

### FR-LOOP-003 — 루프 실행은 단계를 위에서 아래로 차례로 보낸다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | loop-scheduler |
| Status | implemented |
| Priority | high |
| Tags | - |
| Risk | high |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | #206 |
| Related Docs | [loop-scheduler.html](../design/loop-scheduler.html) |

#### Requirement

When a loop runs, the system shall send each step in order: into a new tab opened with the loop's shell in the loop's directory for a new-session loop, or into the saved tab's current session for an existing-session loop (FR-LOOP-008).

#### Rationale

Issue #206; design §③ step kinds, §⑤ 5, 7, 10. The separate Enter reuses FR-MCP-002 AC-7 so the two paths do not drift.

#### Acceptance Criteria

- [x] AC-1: 명령과 프롬프트 단계는 글을 쓰고, 잠시 뒤 Enter 를 따로 쓴다(MCP 와 같은 submitWithSeparateEnter, 같은 대기 설정). 앞 명령이 끝나기를 기다리지 않고 다음 단계로 간다.
- [x] AC-2: 대기 단계는 적힌 ms 만큼 기다린다. 에이전트가 떴는지 감지하지 않는다.
- [x] AC-3: 세션 종료 단계는 셸에 글을 쓰지 않고 서버가 그 탭을 닫는다. 새 세션 루프에만 있다.
- [x] AC-4: 실행 중에 루프를 끄거나 지우거나 그 탭이 닫히면 남은 단계를 보내지 않는다. 탭은 그대로 둔다.
- [x] AC-5: 새 세션 루프에서 셸을 열 수 없거나 디렉터리가 없으면 탭을 만들지 않고 그 실행을 실패로 기록한다. 디렉터리 확인은 세션 생성과 같은 규칙을 쓴다: Windows 서버에서 WSL 경로 /mnt/<드라이브>/… 는 그 Windows 폴더로 바꿔 확인하고, 그 밖의 Linux 경로(/home/…, /tmp 등)는 Windows 에서 확인할 수 없으므로 막지 않는다(이때 세션 생성이 홈 폴더로 대체하는 것은 알려진 한계다). 기존 세션 루프는 디렉터리를 확인하지 않는다(FR-LOOP-008 AC-3).

### FR-LOOP-004 — 루프 탭은 @schedule-{n} 워크스페이스에 연다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | loop-scheduler |
| Status | implemented |
| Priority | high |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | #206 |
| Related Docs | [loop-scheduler.html](../design/loop-scheduler.html) |

#### Requirement

When a new-session loop runs, the system shall place its tab in the lowest-numbered @schedule-{n} workspace with room, and create @schedule-{max+1} (or @schedule-0) when none has room.

#### Rationale

Issue #206; design §④ and §⑤ 1, 2, 6, 8, 9.

#### Acceptance Criteria

- [x] AC-1: @schedule-{n} 워크스페이스는 서버가 만든 id 로 기억한다. 탭 수가 maxTabsPerWorkspace 보다 적은 것 가운데 번호가 가장 작은 곳에 연다.
- [x] AC-2: 모두 가득 찼거나 하나도 없으면 가장 큰 번호 + 1(없으면 0)로 새로 만든다. 사용자가 지운 워크스페이스는 잊는다.
- [x] AC-3: 새 세션 루프의 탭 이름은 「루프 이름 #회차」다. 기존 세션 루프는 탭 이름을 바꾸지 않는다.
- [x] AC-4: 새 세션 루프에서 세션 종료가 없는 실행의 탭이 그 루프의 남겨 둘 탭 수를 넘으면, 그 루프의 가장 오래된 탭부터 닫는다. 기존 세션 루프의 탭은 닫지 않는다.
- [x] AC-5: 모든 @schedule 워크스페이스의 탭 합계가 32 이상이면 새 세션 루프는 탭을 열지 않고 그 실행을 건너뜀으로 기록한다. 기존 세션 루프에는 이 한도를 적용하지 않는다.
- [x] AC-6: 탭이 모두 닫힌 @schedule 워크스페이스는 지우지 않는다.
- [x] AC-7: @schedule 워크스페이스의 탭은 세션 저장·복원(FR-AITUI-007) 대상에서 뺀다.
- [ ] AC-8: 워크스페이스와 탭을 만들고 닫을 때 REST 경로와 같은 WebSocket 이벤트를 보내 열린 브라우저가 따라온다.

### FR-LOOP-005 — 루프는 겹쳐 돌지 않고 실행 기록을 남긴다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | loop-scheduler |
| Status | implemented |
| Priority | medium |
| Tags | - |
| Risk | low |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | #206 |
| Related Docs | [loop-scheduler.html](../design/loop-scheduler.html) |

#### Requirement

When a loop's time comes while its previous run is still sending steps, the system shall skip the new run and record it as skipped.

#### Rationale

Issue #206; design §② history and §⑤ 1, 11.

#### Acceptance Criteria

- [x] AC-1: 「실행 중」은 마지막 단계를 보낼 때까지다. 그 뒤 남아 있는 탭은 실행 중으로 치지 않는다.
- [x] AC-2: 기록 한 건은 시작 시각, 결과(성공 · 실패 · 건너뜀 · 중단), 보낸 단계 수, 워크스페이스와 탭(기존 세션 루프는 보낸 탭), 실패·건너뜀 사유를 담는다. 루프마다 최근 50건만 남긴다.
- [x] AC-3: 같은 순간에 여러 새 세션 루프가 돌면 세션을 하나씩 차례로 만든다. 같은 탭을 고른 기존 세션 루프는 FR-LOOP-008 AC-6 대로 차례로 보낸다.

### FR-LOOP-006 — 도구 메뉴의 루프 창에서 루프를 관리한다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | loop-scheduler |
| Status | implemented |
| Priority | high |
| Tags | - |
| Risk | low |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | #206 |
| Related Docs | [loop-scheduler.html](../design/loop-scheduler.html) |

#### Requirement

When the user chooses Tools > Loop, the system shall show the loop manager, and the loop editor shall build the schedule, target and steps defined in FR-LOOP-001 and FR-LOOP-008.

#### Rationale

Issue #206; design §① §② §③.

#### Acceptance Criteria

- [ ] AC-1: 도구 메뉴 아래쪽에 구분선과 「루프」 항목이 있고, 켜진 루프가 있으면 그 개수를 보여 준다.
- [x] AC-2: 관리 창은 루프마다 켜기/끄기, 이름과 일정 요약, 보낼 곳(새 세션은 셸 · 디렉터리, 기존 세션은 FR-LOOP-008 AC-9), 다음 실행 시각, 마지막 결과를 보이고, 새 루프 · 지금 실행 · 편집 · 삭제와 최근 기록 펼치기를 제공한다.
- [x] AC-3: 편집 창은 반복(요일마다 · 매월 · 특정 날짜 · 간격), 시각, 보낼 곳(「새 세션」은 셸(새 탭과 같은 목록) · 디렉터리 · 남겨 둘 탭, 「기존 세션」은 FR-LOOP-008 AC-8), 단계 목록을 편집한다. 세션 종료 단계가 있으면 단계를 더 추가할 수 없다.
- [x] AC-4: 한 줄 입력 codex delay 2000 "금일 주식 시황 분석하시오" 는 명령 codex, 대기 2000, 프롬프트 세 단계로 풀린다. exit 는 평범한 명령이다.
- [x] AC-5: 화면 문자열은 i18n 카탈로그(en · ko)를 거친다.

#### Requirement

When an MCP client with the loop scopes calls a buildergate.loop.* tool, the system shall list, show history of, create, update, delete or run a loop through the loop service.

#### Rationale

Issue #207. A loop schedules commands to run later, so its write scope is exec-level; the user chose to grant it to session agents as well.

#### Acceptance Criteria

- [x] AC-1: tools/list 에 buildergate.loop.list, history, create, update, delete, run 이 입력 스키마와 함께 나온다.
- [x] AC-2: list 는 루프마다 다음 실행 시각과 마지막 실행을 돌려주고, history 는 한 루프의 최근 실행을 limit(1~50, 기본 10)건 돌려준다.
- [x] AC-3: create 는 FR-LOOP-001 과 같은 정의(보낼 곳 target 포함, target 이 없으면 shell · cwd · keepTabs 의 새 세션)를 받아 같은 검증을 한다. 거부되면 VALIDATION_ERROR 와 fieldErrors.reason 에 거부 사유를 돌려준다.
- [x] AC-4: update 는 준 필드만 바꾸고 나머지는 그대로 둔다. target 을 주면 보낼 곳 전체를 바꾸고, target 없이 shell · cwd · keepTabs 만 주면 새 세션 루프의 그 값만 바꾼다. delete 는 confirm: true 가 없으면 VALIDATION_ERROR 다.
- [x] AC-5: run 은 실행을 시작하자마자 그 실행 기록(running 또는 skipped)을 돌려준다.
- [x] AC-6: 루프는 loopId 또는 loopName 으로 지정한다. 없으면 TARGET_NOT_FOUND, 같은 이름이 여럿이면 AMBIGUOUS_TARGET 과 후보를 돌려준다.
- [x] AC-7: list·history 는 mcp:loops.read, 나머지는 mcp:loops.write 가 필요하다. 고정 접근 키와 세션 에이전트 모두 두 scope 를 가진다(2026-10-30 사용자 결정). scope 가 없으면 INVALID_SCOPE 다.

### FR-LOOP-008 — 루프는 이미 열린 세션 탭에 단계를 보낼 수 있다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | loop-existing-session |
| Status | implemented |
| Priority | high |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [loop-existing-session.html](../design/loop-existing-session.html) |

#### Requirement

When a loop whose target is an existing session runs, the system shall send its steps into the current session of the saved tab without opening a tab.

#### Rationale

Design docs/design/loop-existing-session.html screens 1-7; decisions Q1-Q6 take the recommended answers (2026-11-08).

#### Acceptance Criteria

- [x] AC-1: 루프의 보낼 곳(target)은 새 세션 {kind:'new', shell, cwd, keepTabs} 또는 기존 세션 {kind:'session', tabId, label{workspaceName, tabName}, skipWhenBusy} 이다. skipWhenBusy 의 기본값은 켬이다. target 이 없는 저장 루프와 요청은 최상위 shell·cwd·keepTabs 를 쓰는 새 세션으로 읽는다.
- [x] AC-2: 기존 세션 루프에 세션 종료 단계가 있으면 저장을 거부한다(endNotAllowed). 켜진 기존 세션 루프의 탭이 없으면(sessionMissing) 또는 @schedule 워크스페이스의 탭이면(session) 저장을 거부한다. 저장할 때 표시 이름(label)은 그 탭의 지금 워크스페이스 이름과 탭 이름으로 바꾼다.
- [x] AC-3: 실행은 단계마다 탭 id 로 그 탭의 지금 세션을 다시 찾아 FR-LOOP-003 AC-1·AC-2 대로 보낸다. 그래서 탭을 다시 시작해 세션이 바뀌어도 그 탭을 따라간다. 새 탭 · @schedule 워크스페이스 · 탭 한도 · 남겨 둘 탭 · 디렉터리 확인 · 탭 이름 바꾸기는 하지 않는다.
- [x] AC-4: 실행 시작 때 탭이 지워졌으면 아무것도 보내지 않고 건너뜀(sessionMissing)으로 기록하고 루프를 끈다. 탭은 있으나 살아 있는 세션이 없으면 건너뜀(sessionStopped)으로 기록하고 루프는 켜 둔다. 실행 중에 탭이 닫히면 FR-LOOP-003 AC-4 대로 중단(tabClosed)이다.
- [x] AC-5: skipWhenBusy 가 켜져 있고 실행 시작 때 그 탭의 에이전트가 작업 중(busy · starting · running)이면 아무것도 보내지 않고 건너뜀(agentBusy)으로 기록한다. 첫 판독이 작업 중이 아니면(에이전트가 감지되지 않을 때 포함) 1.5초 동안 두 번 더 보고, 한 번이라도 작업 중이면 건너뛴다(감지 상태가 단계 사이에 잠깐 idle 로 떨어지는 틈 때문). skipWhenBusy 가 꺼져 있으면 기다리지 않고 작업 중이어도 그대로 보낸다.
- [x] AC-6: 같은 탭을 고른 루프가 여럿이면 그 탭에 대한 실행을 한 번에 하나씩 차례로 한다.
- [x] AC-7: GET /api/loops 는 루프마다 targetMissing(기존 세션 루프의 탭이 지금 없는지)을 함께 돌려준다. GET /api/loops/sessions 는 고를 수 있는 탭(@schedule 워크스페이스의 탭 제외)을 워크스페이스 화면 순서와 탭 순서로, 워크스페이스 이름 · 탭 이름 · 폴더 · 셸 · 세션이 살아 있는지 · 에이전트 상태와 함께 돌려준다.
- [x] AC-8: 편집 창 「어디서」에는 「새 세션」/「기존 세션」 탭이 있고 새 루프의 기본은 「새 세션」이다. 「기존 세션」은 워크스페이스별 optgroup 이 있는 네이티브 셀렉트(옵션 글자 「세션 — 상태」, 셸이 끝난 탭은 고를 수 없음), 고른 세션의 폴더 · 셸 · 상태 칩 카드, 「에이전트가 작업 중이면 이번 실행을 건너뜁니다」 체크박스(기본 켬), 같은 탭을 고른 다른 루프가 있을 때의 안내, 입력이 섞일 수 있다는 안내를 보인다. 세션 종료 추가 버튼을 숨기고, 세션 종료 단계가 남아 있으면 안내를 보이고 저장을 막는다. 고를 세션이 하나도 없으면 빈 상태를 보이고 저장을 막는다.
- [x] AC-9: 관리 창 줄은 기존 세션 루프에 「→ 워크스페이스 : 세션」을 보이고, 탭이 없으면 「세션 없음」 표지와 줄 그은 대상을 보인다. 실행 기록은 보낼 곳 열, 탭이 남아 있으면 「탭 열기」 링크, 건너뜀 사유를 보인다.
- [x] AC-10: MCP buildergate.loop.create · update 도 target 을 받아 같은 검증을 한다.
