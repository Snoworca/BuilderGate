## 1. Scope Overview

DocuLight2.0 의 마크다운 편집기를 BuilderGate 로 이식하고, 그 편집기를 담을 모달리스 창 시스템을 세운다. 사용자는 세션의 작업 경로에서 우클릭하여 `CLAUDE.md` · `CLAUDE.local.md` · `AGENTS.md` 를 편집하며, 편집 창은 여러 개를 동시에 띄우고 마우스로 클릭하여 앞뒤 순서를 정한다.

2026-09-26 부터(target `code-editor`) 이 편집기는 마크다운 전용에서 넓어진다. 텍스트로 편집 가능한 소스코드·설정·데이터 파일은 CodeMirror 6 코드 모드로, 이미지 파일은 보기 전용 뷰어로 같은 창의 탭에서 연다. 조사는 `docs/research/2026-09-26.code-and-data-file-editor.md` 에 있다.

설계 근거와 조사 결과는 `docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md` 에 있다. 그 문서는 두 코드베이스를 대조하여 다섯 차례 검증한 결과이며, 이 scope 의 요구사항은 그 위에서 작성된다.

## 2. Scope Boundaries

### In Scope

- 모달리스 창의 배치 상태(최대화 · 자유 배치)와 그와 독립된 감춤 플래그.
- 창 하나가 여러 문서를 탭으로 담는 구조. 탭의 추가 · 선택 · 닫기 규칙.
- 창의 z-order 와 클릭에 의한 순서 변경. 모달 다이얼로그와 분리된 스택.
- 편집기 소스의 이식, 그리고 그 편집기가 강제하는 두 계약(`markdownSource` 가 controlled value 가 아니라는 것, 문서 정체성을 `documentId` 로 준다는 것).
- 서버의 파일 쓰기 경로. 읽기 경로가 쓰는 경로 검증을 그대로 따른다.
- 세션 작업 경로의 우클릭 컨텍스트 메뉴와 파일 부재 시 생성 확인.
- 헤더의 편집기 트레이와 모든 워크스페이스에 걸친 열린 문서 목록.
- 워크스페이스별 문서 목록의 영속화와 복원, 그리고 전역 키에 저장되는 창의 위치와 크기.
- 모바일 레이아웃에서의 창 동작. 창은 화면 전체를 차지하고 끌 수 없다.
- 파일 이름으로 편집 모드(마크다운·코드·이미지·열지 않음)를 정하는 판정표, 코드 모드 편집기, 데이터 파일 구문 검사, 줄바꿈·BOM 보존, UTF-8 이 아닌 파일의 읽기 전용 열기.
- 이미지 파일의 보기 전용 뷰어와 원본 바이트 읽기 경로, SVG 의 소스 편집 전환.

### Out of Scope

- 임의 파일을 고르는 파일 탐색기 UI 자체. 탐색기는 `42.file-explorer.srs.md` 의 범위이며, 이 scope 는 탐색기와 편집기 파일 트리(FR-MDE-012)가 여는 파일을 받는다.
- 이미지 편집(자르기·회전 저장·색 보정), 바이너리 파일 편집, 언어 서버(LSP) 기반 진단·정의 이동.
- 새로고침 이후의 미저장 본문 복원. 세션이 살아 있는 동안의 유지는 In Scope 다.
- 저장 시 외부 변경 충돌 감지. 덮어쓰기가 확정된 결정이다.
- 편집기의 첨부 업로드와 위키링크 기능. 콜백을 주지 않으면 비활성으로 남는다.
- 라이트 테마 대응.

## 3. Assumptions and Constraints

- 파일 접근은 세션 cwd 하위로 한정된다. 서버의 경로 검증이 그 경계를 강제한다.
- **문서는 세션이 아니라 탭에 매인다.** `WorkspaceTab` 이 `id` 와 `sessionId` 를 별개로 갖고 `restartTab` 이 `sessionId` 만 교체하므로, 세션 ID 는 탭의 생애에 걸쳐 안정적이지 않다. 창 하나가 여러 탭의 문서를 담으므로 이 결속은 창이 아니라 문서마다 따로 성립한다.
- 편집기 창의 z-index 는 `3000` 대역을 쓴다. 프로젝트 전체에서 `3000`~`5000` 사이가 비어 있고, 모달(`5000`)·확인 팝업(`9999`)·컨텍스트 메뉴(`10000`)가 모두 그 위에 오기 때문이다.
- `mermaid` 를 `^10.9.5` 에서 `^11.4.1` 로 올려야 한다. 편집기가 요구하는 범위를 현재 버전이 만족하지 않는다.
- 프로젝트는 다크 테마에 고정되어 있다. 편집기의 기본값도 다크이므로 어긋나지 않는다.
- CSS 스코프 격리가 없다. 새 클래스에는 접두사를 둔다.
- 이식 대상 편집기는 MIT 라이선스 벤더링 사본을 포함하므로 `LICENSE` 파일을 함께 유지해야 한다.

#### Requirement

The editor window shall carry exactly one placement state among `stage` and `floating`, and its title bar shall expose four controls in left-to-right order: 저장 / 최대화 / 최소화 / 닫기. The placement controls are injected by `EditorWindow` through the optional `titlebarActions` prop, so `WindowDialog` itself stays unaware of placement states.

Placement semantics:

- `stage` — the whole terminal stage: the container `div{flex:1, position:relative, overflow:hidden}` that `TerminalWorkspaceStage` renders, measured by ref.
- `floating` — where the user placed it, or where the window opened when nothing has been placed yet.

A third state, `docked`, covered the terminal rect of one tab and was the state a window opened in. It is removed. A window holds documents opened from several terminals, so there is no single terminal for it to cover, and nothing left for the placement to be computed against.

Opening placement:

- With no cached geometry, a window opens `floating` at `INITIAL_EDITOR_WINDOW_VIEWPORT_RATIO` (0.7) of the viewport in each axis, centred **inside the stage**. The size comes from the viewport because the window is no longer sized against any one terminal's area; the centring is done in the stage because that is the box the window layer confines a floating window to, and a rect centred in the viewport and then confined to a smaller box is not centred — it is pushed against that box's near edge.
- The floor is `EDITOR_WINDOW_MIN_SIZE` and it wins over both the ratio and the confinement. On a box smaller than the floor part of the window sits outside it, which is the side this rule takes: a window shrunk under its own minimum cannot show its title bar, and a window whose title bar is gone cannot be moved back.

Cached geometry:

- A drag or resize writes the resulting rect to a single key, `buildergate.editor-window.geometry`. It names no workspace and no document: what is asked for is one remembered placement, shared by every window.
- A window with a cached rect opens at it, confined to the viewport and never below the floor.
- That cache is separate from the dialog geometry store, whose read path finishes with `clampDialogRect` — the function that lowers the minimum-size floor to the viewport when the viewport is the smaller of the two. Reading through it would hand back a window too small to show its own title bar. That function is left alone because six other dialogs depend on it.

Control behaviour:

- `최대화` records the current placement and switches to `stage` when the window is not `stage`; when it already is `stage`, it returns to the recorded placement, or to `floating` when no record exists. With two placements the toggle has one destination, and the record is written only on entry to `stage`.
- `최소화` sets the `minimized` flag, which is a separate axis specified by the hiding requirement.
- Drag or resize sets `floating`.

Mobile: the window fills the stage and neither reads nor writes the cached geometry, and it can be neither dragged nor resized. The three answers travel together as one value, because a window that fills the screen cannot be dragged and a window that cannot be dragged produces no rect to cache — and the failure they prevent, a draggable full-screen window writing phone-sized rects into the shared cache, is exactly what three separate judgements could disagree about.

Coordinates: both placement states are computed by `EditorWindow`'s layer and handed to `WindowDialog` as a controlled `rect`, so `clampDialogRect` is not used. `floating` clamping is performed against the stage rect rather than the viewport, and `Rnd`'s `bounds` points at the stage container instead of `"window"`, so a window cannot be dragged over the sidebar, header, or tab bar.

Measured facts the implementer needs:

- Layout constants are hard-coded pixels that do not pass through any CSS variable: sidebar 220px is an inline style in `frontend/src/App.tsx`, header 58px is `Header.css:10`, tab bar 36px is `WorkspaceTabBar.css:7`. The stage container already excludes all three, so `stage` measures that container and does not restate the numbers.
- `WindowDialog` renders its surface through `createPortal(…, document.body)`, so an editor window is a direct child of `document.body` and is never laid out inside the stage.
- The rect registry is a React context owned by `TerminalRuntimeProvider`. The window layer renders inside that provider.
- The target rect must be tracked with `ResizeObserver` plus `window.resize`, following the precedent already in `TerminalHostSlot`.

Pitfalls:

- **`Rnd` reports a drag stop for a press on its handle even when nothing moved, and the title bar is that handle.** Every press of 저장, 최대화 and 최소화 produces one, carrying the rect the window already had. A host that reads an arriving rect as "the user placed this window" therefore sends the placement back to `floating` on every button press — so 최대화 went to `stage` and came back within the same commit, and from the second press onwards the button appeared dead. `WindowDialog` drops a report whose rect equals the one in hand, in `applyRect`, so drag and resize are both covered in one place.
- **The drag boundary must not change with the placement.** It was swapped for the viewport while a window was floating, and `Rnd` read each swap as an interaction it had to settle: it emitted a rect, that rect came back in as a hand-placed one, and the same undo happened. The layer already confines a floating window to the stage, so a constant boundary is also the boundary that was in effect.
- `Rnd`'s `bounds` takes a selector string or an element, and the stage container needs an identifier for that to be possible. `EDITOR_WINDOW_BOUNDS_SELECTOR` is defined once and read by both the dialog and the placement computation, so the box a window is centred in and the box it is confined to cannot drift apart.
- `readDialogGeometry` runs on every mount independently of `persistGeometry`, so `persistGeometry={false}` cannot stop a stored geometry from becoming the initial state. `EditorWindow` supplies the controlled `rect` from the first render so the stored value never reaches the screen.

#### Rationale

`docked` placed the window over the terminal rect of the tab it was bound to, and `터미널 채움` was the control that put it there. Both are gone. A window holds documents opened from several terminals, so there is no single terminal for it to cover — the placement had no target left to be computed against, and the control had no destination to offer.

`stage` is measured from the stage container instead of subtracting sidebar 220px, header 58px, and tab bar 36px, because those three constants live in three different files with no shared variable; duplicating them into the window code means only one copy gets corrected when the layout changes.

The opening size is taken against the viewport while the opening position is centred in the stage, and the two boxes differ on purpose. The size no longer has a terminal to be measured against, so the viewport is what is left. The position has to be centred in the box the window is actually confined to: a rect centred in the viewport and then confined to the stage is not centred any more — it is pushed against the stage's near edge, by the sidebar's width on a desktop layout.

The geometry cache does not go through `readDialogGeometry`, whose last step is `clampDialogRect`. That function lowers the minimum-size floor to the viewport when the viewport is the smaller of the two, which restores a window too small to show its own title bar — and a window whose title bar is gone cannot be dragged or resized back. Six other dialogs depend on that function, so it is left alone and the cache clamps its own way: the size is bounded by the viewport above and by `EDITOR_WINDOW_MIN_SIZE` below, the floor winning where they conflict, and only then is the origin pushed back until the window fits.

A drag report that changes nothing is dropped rather than acted on, because `Rnd` raises one for every press on its handle and the title bar is that handle. Acting on it turned the placement `floating` on every button press, which undid 최대화 within the same commit and made the control appear dead from the second press onwards. The rule is stated as "the rect differs" rather than as a distance, because a one-pixel drag is still the user placing the window and a threshold would be a number nobody chose.

#### Acceptance Criteria

- [ ] AC-1: Given a window whose placement is `floating`, when 최대화 is pressed, then the placement becomes `stage` and `floating` is recorded as the previous placement; when 최대화 is pressed again, then the placement returns to `floating` and the window is drawn at the rect it held before.
- [ ] AC-2: Given a window whose placement is `stage` with no recorded previous placement, when 최대화 is pressed, then the placement becomes `floating`.
- [ ] AC-3: Given a window is open, then its title bar carries exactly four controls — 저장, 최대화, 최소화 and the dialog close button — and no 터미널 채움 control exists.
- [ ] AC-4: Given a window in `stage`, when the user drags or resizes it, then the placement becomes `floating` and the rect at the start of the interaction equals the rect the window had in its previous placement state.
- [ ] AC-5: Given `Rnd` reports a drag or resize whose resulting rect equals the rect the window already holds — which it does for every press of a title bar control, the title bar being the drag handle — then no rect reaches the host and the placement is unchanged.
- [ ] AC-6: Given the stage container measures to rect S, when a window is in `stage`, then its rect equals S; when S subsequently changes through a resize, then the window rect updates to the new S without any sidebar, header, or tab bar pixel constant appearing in the computation.
- [ ] AC-7: Given a `floating` window and a drag whose requested position would place part of the window over the sidebar, header, or tab bar, then the resulting rect is fully contained in the stage rect; and given a drag whose requested position is fully inside the stage rect, then the resulting rect differs from the pre-drag rect by exactly the requested delta.
- [ ] AC-8: Given no cached geometry exists, when a window opens on a desktop layout, then its size is `INITIAL_EDITOR_WINDOW_VIEWPORT_RATIO` of the viewport in each axis, except where that exceeds the stage, which bounds it, or falls below `EDITOR_WINDOW_MIN_SIZE`, which raises it; the test states the viewport it runs at and which of the three decided each axis and its position is centred inside the stage — the box the window is confined to — rather than inside the viewport, and never smaller than `EDITOR_WINDOW_MIN_SIZE`.
- [ ] AC-9: Given the mobile layout is rendered, when a window opens, then its placement is `stage`, the cached geometry is neither read nor written, and the window can be neither dragged nor resized.

#### Implementation Notes

- `WindowDialog` gains six optional props, all of which preserve current behaviour when omitted: `rect` / `onRectChange` (controlled coordinates that also bypass clamping), `boundsElement` (defaults to `"window"`), `movable` (defaults to true; false stops the drag a full-screen window has nowhere to make), `titlebarActions` (placed to the left of the close button that `showCloseButton` renders), and `dirty`.
- `EDITOR_WINDOW_MIN_SIZE` is 320 x 240 and is the floor both the opening rule and the geometry cache clamp against. One definition, so the size a window is placed at and the size it agrees to render at cannot drift.
- The title bar lets the title take the remaining width rather than spacing its children apart. `justify-content: space-between` puts the middle child in the middle, and a bar holding a title, an action group and a close button has three — which left 저장 / 최대화 / 최소화 floating in the centre.
- Rejected alternative: keeping `docked` and choosing one of the open documents' terminals to cover. Nothing picks that terminal: the documents come from several, and a window that covered one of them would be over the wrong terminal for every other tab in it.

#### Requirement

Hiding an editor window shall be expressed as `display: none` on the window surface and shall never unmount the editor. `minimized` is a boolean flag on its own axis, independent of the placement state, so minimizing and restoring leaves the placement state untouched.

A window is visible only when every one of these three terms holds. If any term is false the surface is hidden, and in no case is it unmounted.

1. `minimized` is false.
2. The current screen is the workspace screen.
3. The window's workspace is the current workspace.

Only term 1 is under the user's control through a window button; terms 2 and 3 are decided by the system, so clearing `minimized` alone does not necessarily make a window appear.

Two terms were removed. The terminal tab a window was opened from is no longer one: a window holds documents opened from several terminals, so no single tab could gate it without hiding the others' documents. The usable-terminal-area term went with the `docked` placement it belonged to. Neither is passed to the predicate as an ignored input either — a caller that handed one in would believe it had asked for something.

**Every workspace's window is mounted at once, and all but one are hidden.** The window layer renders the whole collection rather than the active workspace's alone. A layer given only the active window would unmount the others on a workspace switch, and unmounting an editor is how unsaved work is thrown away — the same rule the three terms above exist to serve, applied to the collection instead of to one window.

Why unmounting is forbidden — the two contracts the ported editor enforces:

1. `markdownSource` is not a controlled value. It is read once at mount, and from then on the editor is the source of truth for the document. Feeding the value back on every keystroke is prohibited.
2. Document replacement goes through the `documentId` prop. When it is omitted, the `markdownSource` string itself becomes the document identity, so every save response carrying new body text destroys and recreates the `EditorView` and loses focus and input. The DocuLight commit `f54ee4e fix(web): 저장이 편집기를 갈아 끼우지 않게 한다` is the evidence for this contract.

Canonical source for those two contracts: FR-MDE-005 states them definitively, together with the consequence that `documentId` stays unchanged across a tab restart so the `EditorView` survives it. This requirement restates them only as the premise its hiding rule stands on; when a contract changes, FR-MDE-005 is the requirement to change, and the restatement here follows it.

An unmounted editor loses its unsaved body, and remounting restarts from whatever `markdownSource` was given. Minimizing must hide, not unmount. The same reasoning covers workspace switching and screen switching, and it covers the documents behind inactive tabs of one window — a panel is hidden with `display: none` and stays mounted, which is why several documents can be open at once.

Measured facts the implementer needs:

- The `extensions` array is also captured at mount, so its reference must be pinned with `useMemo`. `readOnly` alone is `Compartment`-based, so toggling it does not remount.
- The window surface is portalled into `document.body`, so hiding must be applied to the surface itself and to `react-rnd`'s positioned root. Hiding only the surface leaves that root at its full rect with `pointer-events: auto` and its resize handles live, so an invisible window still swallows clicks meant for the terminal underneath.

Pitfalls:

- The frontend unit suite cannot mount a React component. `frontend/package.json` declares no `jsdom`, no `happy-dom`, no `@testing-library/*` and no `react-test-renderer`, and no test under `frontend/tests/unit/` renders a component — they are pure module tests and `readFileSync` source-text contract tests. Anything that has to observe a mounted editor therefore belongs in Playwright E2E.
- Clearing `minimized` on its own produces no visible change when another term is false. Any restore path must resolve the terms it can resolve.
- The window renders inside `TerminalRuntimeProvider`, which unmounts together with the active workspace. Deleting the last workspace therefore destroys the windows and their unsaved bodies. This is accepted as a known constraint, because deleting a workspace is an explicit destructive action.

#### Rationale

The editor reads `markdownSource` once at mount and treats itself as the document's source of truth afterwards, so unmounting is equivalent to discarding the unsaved body. Minimize is a display operation from the user's point of view, not a document operation, so it must not have that effect.

Placement and hiding are kept on separate axes because folding minimize into the placement state produces transition combinations in which "the previous state" is undefined — for example minimizing from `stage` and then pressing 최대화. With two axes every combination has a defined destination.

#### Requirement

Pressing anywhere on an editor window shall raise it to the end of the modeless stack, and the modeless stack shall be separate from the modal stack so that a raise can never demote a modal.

Two changes to `dialogStack.ts` deliver it.

1. Split the stack by kind. The single module-global array becomes two stacks, `modal` and `modeless`. A modal's `isTopmost` is decided within the modal stack only.
2. Add a `raise(token)` operation that moves the named entry to the end of its stack and notifies subscribers, plus `raiseDialogById(dialogId, 'modeless')` so a window can be raised by name from outside itself.

The handler is registered on the window's layer element rather than on the surface, in the capture phase, so pressing an element inside the window also raises it. The layer is the outer node: `react-rnd`'s positioned root sits between it and the surface and carries the resize handles, so a listener on the surface alone would miss a press that began on a handle. That handler calls neither `stopPropagation` nor `preventDefault`, so the editor's own input handling, caret placement, and focus are untouched.

What the raise is observable against. There is one editor window per workspace and only the current workspace's window is on screen, so two editor windows never overlap and no press can be seen to move one in front of another. Every workspace's window is nonetheless registered in the modeless stack, because all of them are mounted at once — which is also why `editorWindowDialogId(workspaceId)` keys the registration by workspace: two windows sharing an id would make a raise by name ambiguous. The raise is therefore judged against the stack, which is where its effect lives, rather than against overlapping pixels that cannot be produced.

What the separation is still for. The editor window sits below every modal surface, and a modal's focus containment is decided by its position in the modal stack. One shared array would let a press on the editor window turn a modal's `isTopmost` false, and by the condition at `WindowDialog.tsx:207` that modal's Tab containment and Escape blocking would switch off. That is the failure the split prevents, and it survives unchanged now that editor windows no longer overlap each other.

Stack order is used for the z-index computation only. Mount order stays fixed at creation order and is never reordered to reflect the stack. Moving a DOM node in response to `pointerdown` re-inserts it immediately after the press, which aborts a text selection drag that has just begun. Front-to-back order is therefore expressed purely through z-index.

Measured facts the implementer needs:

- `useDialogStack(dialogId, mode === 'modal')` registered modal dialogs only, so modeless windows were not in the stack at all before this requirement.
- `WindowDialog.tsx:207` gates the focus trap, Tab containment, and Escape blocking on `if (mode !== 'modal' || !stackState.isTopmost) return;`.
- There are six modal call sites, all passing `mode="modal"`: `CommandPresetDialog.tsx:318`, `dialog/MessageBox.tsx:31`, `McpControlDialog.tsx:610`, `RecoveryOptionDialog.tsx:243`, `TerminalShortcutDialog.tsx:342`, `Workspace/WorkspaceMoveDialog.tsx:52`.

Pitfalls:

- The frontend unit suite cannot dispatch DOM events or inspect rendered nodes. `frontend/package.json` declares no `jsdom`, no `happy-dom`, no `@testing-library/*` and no `react-test-renderer`, and no test under `frontend/tests/unit/` renders a component — they are pure module tests and `readFileSync` source-text contract tests. The stack arithmetic is unit-testable and stays there, but every criterion that presses a window, checks the capture phase, watches for `stopPropagation`, reads sibling order, or exercises modal Escape and Tab containment is assigned to Playwright E2E, which already runs a real browser.
- Splitting the stack is not only about `raise`. If modal and modeless entries share one stack, the moment a modeless window is raised above a modal, that modal's `isTopmost` turns false and its Tab containment and Escape blocking switch off entirely.
- Raising by moving the DOM node breaks an in-flight text selection drag. Change z-index, not node position.
- Changing `useDialogStack` is a modification of behaviour that six live modals depend on, so their focus trap and Escape handling need explicit regression coverage.

#### Rationale

Raising through z-index rather than DOM order is chosen because the raise is triggered by the same `pointerdown` that may start a text selection inside the editor, and a node move at that instant cancels the selection the user just began.

The stacks are split rather than shared because the modal's topmost decision and the modeless window's front-most decision are different questions asked of the same array; answering them from one array makes a modeless raise silently disable modal focus containment. That reason is untouched by there being one editor window per workspace: the editor window and the modals above it are still two kinds of surface sharing one screen.

What the one-window-per-workspace structure did change is what a raise can be seen to do. Two editor windows never overlap now, so the criteria read the stack instead of the pixels. Keeping the raise judged against the stack is not a weaker test but a truer one: the stack is what the operation writes to, and the z-index the layer computes from it is what any future overlap would show.

#### Requirement

Whenever a window enters the `docked` placement state, the system shall read the cascade steps already held by windows that are bound to the same `tabId` and whose placement state is `docked`, and give the entering window the lowest step no such window holds. Hidden windows hold their step: a minimized window, and a window on a tab that is not currently active, both still occupy that terminal area. Windows in `stage` or `floating` do not occupy it and are not read. The step is not a count of those windows: after the window at step 1 of 0, 1, 2 closes, a count would hand the next window step 2, where a window already stands, and two windows would coincide exactly — the one outcome this requirement exists to prevent.

Given the target terminal rect `x, y, width, height`, the window at step `k` is placed at `x + 28k`, `y + 28k`, with size `width - 28k`, `height - 28k`. The offset is paid for by shrinking, so the window stays entirely inside the target area.

`k` runs 0, 1, 2, 3 and wraps back to 0 at 4. If the shrunk size would fall below the `minSize` that `EditorWindow` supplies (320 x 240), that window uses `k = 0` instead.

When the target terminal area is itself smaller than `minSize` — narrower than 320 or shorter than 240 — the window is placed at `k = 0` and takes the target area's own width and height. It is not widened or heightened to `minSize`. Containment in the target area outranks `minSize`: a window inflated past the edge of its own tile covers the terminal of the neighbouring tile, which is precisely what docking to a tile is meant to leave alone, and a too-small window is a legible inconvenience while a window over someone else's terminal is a defect.

`k` is recomputed on every entry into `docked` — when a window is first opened, and equally when a window returns from `stage` or `floating` by way of the 터미널 채움 control. It is not stored on the window and it is not persisted; the restore path recomputes it from the same rule, which is why the same arrangement reappears after a reload. The restore path applies the rule to one window at a time so that each window reads the steps the windows before it have already taken; placing them in one pass would let every window read an arrangement in which no step is held yet and take step 0, stacking the whole set on top of each other.

Closing a window in the middle of a cascade does not move the windows that remain. The freed step is taken by the next window that enters `docked`.

Ground truth for the shrink: offsetting the position without shrinking necessarily pushes the window past the edge of the target area, and the rule that pulls an out-of-bounds window back sets the offset to zero again, which makes every window coincide exactly. That defeats the whole purpose of the cascade, which is to leave enough of the window behind visible that its title bar can be pressed to bring it forward.

Pitfalls:

- If each window kept the `k` it was given, then window A leaving to `floating`, window B opening with `k = 0`, and A returning to `docked` would put A and B in exactly the same place. Recomputing on entry is what prevents that.
- Reading the held steps requires reading them from somewhere, and `k` is deliberately not stored on the window. The steps have to be recovered from the placed rects of the sibling windows, which is why the restore path must place one window at a time: a sibling whose rect is not yet assigned holds no step that can be read.
- `WindowDialog` hands `minWidth` and `minHeight` straight to `Rnd` (`WindowDialog.tsx:355-356`), so a controlled rect narrower or shorter than `minSize` does not by itself produce a smaller rendered box: `Rnd` can render the element at the minimum instead, and the window then spills past the target area even though the computation kept it inside. The implementation has to reconcile the two, by lowering the minimum handed to `Rnd` for that window or by an equivalent means. That undersized-target case is the only one where the rendered box can differ from the computed rect, so it is the only criterion judged on measurement — AC-8. Every other containment criterion is judged on the computed rect, which keeps the cascade arithmetic in the unit suite where an error in it surfaces immediately rather than behind a browser.

#### Rationale

Two windows docked on the same terminal must not coincide, because a completely covered window offers no surface to press and the click-to-raise behaviour then has no way to reach it. Offsetting alone is not enough: the window would leave the terminal area, and clamping it back would collapse the offset. Shrinking by the same amount as the offset satisfies both constraints at once.

The count includes hidden and minimized windows because they still hold their place in the cascade; excluding them would hand an occupied step to a new window and make two windows coincide the moment the hidden one reappears.

| Field | Value |
| --- | --- |
| Type | constraint |
| Target | markdown-editor |

| Priority | high |

| GitHub Issue | - |
| Related Docs | docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md |

#### Requirement

Editor windows shall occupy a modeless z-index band whose layer value is `3000 + n * 20`, where `n` is the window's index in the modeless stack, capped at `3980`. The value the window surface itself carries is one greater than the layer value, because `windowDialogModel.ts:68` computes `dialogZ: layerZ + 1` and `WindowDialog.tsx:349` applies `dialogZ` to the `.window-dialog` element. An editor window surface therefore renders at `3001 + n * 20`, capped at `3981`. The two numbers must be kept distinct in every statement about this band: the layer value is what the formula produces, and the surface value is what the DOM receives. The modal band shall not move: `WindowDialog` modals stay in the `5000 + n * 20` layer band, `.command-preset-toast` stays at `5100`, `ConfirmModal` stays at `9999`, and the context menu stays at `10000` with its submenu at `10001`.

Three places carry this, not two. All three are in place; what follows says what each one does and, for the third, why leaving it out would have made the other two look correct while the band meant nothing.

1. The input type of `createWindowDialogBehaviorModel` (`windowDialogModel.ts:50-57`) carries an optional `mode` field. Optional, so a caller that omits it is treated as a modal — which is what AC-2 pins and what keeps the six existing modal call sites working unchanged.
2. The layer value is chosen by band rather than by a single constant: `windowDialogModel.ts:59` reads `Math.min(band.base + input.layerIndex * LAYER_STEP, band.cap)`, where the band is selected by `mode`. Modeless starts at `3000` and modal keeps starting at `5000`, and the cap is what stops a deep stack from climbing into the band above it.
3. `WindowDialog.tsx:85` calls `useDialogStack(dialogId, mode)`, so modeless windows are registered too. Registering only modals would leave `dialogStack.ts:52-55` returning the fixed `{ layerIndex: 0 }` for every editor window, so every one of them would compute the same layer value `3000` and the same surface value `3001`, and the per-window ordering this constraint specifies could never be observed. That is the change that makes the band mean anything, and omitting it fails AC-1 outright while the other two still look correct in isolation.

The call site (`WindowDialog.tsx:87-94`) passes `mode` into the behaviour model, which is the wiring that carries item 2 into the render. `mode` defaults to `'modal'`, so the number of returned fields does not change.

Measured z-index landscape, which is why `3000` is available: the project uses 2 for the terminal itself (`TerminalRuntimeLayer.tsx:60`), 10 and 12 for tile parts, 100 for `SettingsPage.css:7` and `FontSizeToast.css:13`, 998 to 1000 for mobile-only surfaces, 5000 / 5000 / 5001 as the static CSS defaults in `WindowDialog.css:4`, `:18`, `:24`, the inline computed values that override them (`WindowDialog.tsx:338`, `:344`, `:349`, the last of which receives `layerZ + 1`), 5100 for `.command-preset-toast` (`CommandPresetDialog.css:295`), 9999 for `.modal-overlay` (`Modal/RenameModal.css:11`) and the drag ghosts, and 10000 / 10001 for the context menu (`ContextMenu.css:8`, `:17`). There are zero occurrences of any z-index between 3000 and 5000 in the whole project.

The consequences that the band is chosen for: the six existing dialogs keep their exact z-index values; modals, confirmation popups, and context menus all render above editor windows, so a settings dialog is never covered by an editor; and a context menu opened from inside an editor window appears above that window.

Ground truth for lowering the modeless band rather than raising the modal band: `.command-preset-toast` renders as a sibling outside `WindowDialog` and does not use a portal, so raising the modal band to clear the editor windows would push the dialog above 5100 and hide that toast behind it. Lowering the modeless band leaves every existing value untouched and cannot produce that regression.

Pitfalls:

- Splitting the stack by kind, which the click-to-raise requirement specifies, is a precondition for this band and not an independent concern: without the `useDialogStack` change above there is no modeless stack for `n` to index into.
- `frontend/tests/unit/windowDialogContract.test.ts` pins the entire return value of `createWindowDialogBehaviorModel(...)` with `assert.deepEqual`. Adding an input field without adding a returned field keeps it green; if it goes red, the change introduced an unintended return-value difference and that is the signal, not the test.
- The modal `inert` treatment snapshots `document.body.children` at the modal's mount, and an editor window falls inside that snapshot for a structural reason: `WindowDialog` renders every surface through `createPortal(…, document.body)` (`WindowDialog.tsx:333`), so a window is a direct child of `document.body` rather than a descendant of the stage it is placed over. Editor windows that are already open are therefore covered by the snapshot and made `inert` without any additional wiring. The reverse order cannot occur because the UI is locked while a modal is up, so no new editor window can be opened behind it. If the portal target ever moves off `document.body`, this conclusion moves with it and AC-6 has to be re-derived.

Known constraints accepted here rather than fixed: the font-size toast at z-index 100 hides behind an editor window that overlaps that tile, and beyond roughly fifty windows the layer value saturates at `3980` so ordering among those windows falls back to mount order and pressing them no longer changes it.

#### Rationale

The modeless band is lowered instead of the modal band being raised because `.command-preset-toast` at 5100 is a sibling of `WindowDialog` rather than a child and does not go through a portal; any increase to the modal band would place a dialog above it and hide the toast. Choosing 3000 keeps all six existing dialog call sites numerically unchanged, so the change carries no z-index regression at all, and the 3000 to 5000 range is provably free across the project.

The settings screen at z-index 100 is not a conflict because the visibility rule already hides editor windows outside the workspace screen, and the mobile surfaces near 1000 are outside the scope of this feature.

### CON-MDE-002 — Editor documents bind to a tab, not to a session

| Field | Value |
| --- | --- |
| Type | constraint |
| Target | markdown-editor |
| Status | implemented |
| Priority | high |
| Tags | markdown-editor, modeless-window, tab-binding, session-lifecycle |
| Risk | medium |
| Stability | evolving |
| Verification Method | Frontend unit tests for the persisted record shape and for the tab-to-session resolution at call time; Playwright E2E for a tab restart leaving the document alive and saving through the new session, for a closed tab disabling that document's save path while its sibling keeps its own and the window keeps its placement, and for the distinct close prompt in that state. |
| GitHub Issue | - |
| Related Docs | docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md |

#### Requirement

An open editor document shall hold a `tabId` and shall never hold a session ID. The session ID is fetched again from that tab at the moment a file API call is made, and it is not persisted.

The binding belongs to the document, not to the window. One window per workspace holds several documents as tabs, each opened from a terminal tab of its own, so a window has no single tab to be bound to — and a rule written at window level would have had to pick one of its documents' tabs and misdescribe all the others.

The facts that force the tab ID over the session ID. `WorkspaceTab` carries `id` and `sessionId` as separate fields alongside `currentSessionId` and `previousSessionIds` (`frontend/src/types/workspace.ts:14-20`), and the identifier is `id`. `restartTab` keeps `tab.id` and swaps `tab.sessionId` for a new session (`server/src/services/WorkspaceService.ts:780`, `:805`), so a session ID is not stable across the life of a tab. A document bound to a session ID would lose its binding silently after a restart, and the loss would first show as a save going nowhere.

Resolution path: `useWorkspaceManager` exposes `tabs` as a flat array covering every workspace, so the lookup is `wm.tabs.find(t => t.id === tabId)?.sessionId`. That hook is called at exactly one place (`App.tsx:138`) and has no context provider, so the lookup function is passed down from `AppContent` to the window manager as a prop. No new context is introduced for this.

Behaviour when the binding degrades:

- Tab restarted, session replaced — the document stays exactly as it is and its next save goes to the new session.
- Tab alive but session disconnected — the document is left in place and a save is still attempted. Failure is shown as an error in that document's own banner.
- Tab closed — that document loses its save path. While it is the active tab, the window's 저장 control and Ctrl+S are disabled and a 저장 불가 badge appears in the title bar's action group. Selecting a sibling tab whose own tab is alive enables the control again, because the control acts on the active document. Nothing about the window changes: placement and rect belong to the window, which still holds documents whose tabs are alive, so moving or resizing it on account of one closed tab would be acting on the other documents for a reason that has nothing to do with them.
- Closing a document whose tab was closed — the prompt is "저장할 수 없습니다. 그래도 닫으시겠습니까?", a different branch from the ordinary unsaved-changes prompt.
- Restoring persisted state that names a tab that no longer exists — that document is not restored.

`documentId` is the normalized absolute file path, never the session ID. A session ID there would change on tab restart, and by the editor's document-identity contract the `EditorView` would be destroyed and recreated, taking the unsaved body with it.

Canonical sources. This requirement is the canonical source for what happens when the bound tab closes: the disabled save path, the badge, and the separate 저장할 수 없습니다 close prompt. FR-MDE-006 restates those inside its close-branch table and judges on top of them, so a change to any of them is made here first. In the other direction, the document-identity contract — that `documentId` is the normalized absolute path, so a tab restart leaves it unchanged and the `EditorView` alive — is stated definitively in FR-MDE-005, and the statement here follows it.

Pitfall: the document survives a tab restart only if nothing in its identity derives from the session. That includes the persisted record and the `documentId`.

#### Rationale

The session ID is not a stable identifier: `restartTab` replaces it while keeping the tab. Binding a document to it would silently sever the document from its tab after a restart, with no visible failure until a save went to the wrong place or nowhere.

The binding sits on the document rather than on the window because a window holds documents from several tabs at once. A window-level binding would have had to name one of those tabs, and every other document in the same window would then have resolved its session through a tab that is not its own.

The session ID is still required for the file API, so it is resolved at call time rather than stored. That is the only arrangement in which a tab restart is invisible to the user and the next save still reaches the right session.

#### Acceptance Criteria

- [ ] AC-1: Given a document bound to tab T with unsaved edits, when T restarts so that `tab.id` is unchanged and `tab.sessionId` is replaced, then the document is still open with the same editor instance and the same unsaved body, and the next save call carries the new session ID rather than the old one.
- [ ] AC-2: Given any persisted editor document record, then it contains the tab ID and contains no session ID field; and given a stored record produced before a tab restart, then restoring it after the restart still resolves a session ID through the tab.
- [ ] AC-3: Given the session of tab T is disconnected while T itself still exists, then the document bound to T stays open and a save attempt is issued; on failure the document stays dirty and shows the error in its own banner, and the window's placement state is untouched.
- [ ] AC-4: Given a window holding a document bound to tab T and a second document bound to a different tab, when T is closed while its document is the active tab, then the window's 저장 control and Ctrl+S are disabled and a 저장 불가 badge appears in the title bar; and when the second document's tab is then selected, the same 저장 control is enabled again and the badge is gone. The window's placement state and rect are the same values throughout. #### Requirement

The DocuLight2.0 editor package shall be ported into this repository as source under `frontend/src/editor/`, keeping the directory structure of `packages/editor/src`, and the host code that mounts it shall honour the two contracts the editor enforces at mount time.

Port scope and provenance:

- The copied tree is 27 files / 7,333 lines: 25 `.ts`/`.tsx` under `src/` (the 10 files under `__tests__/` are excluded from that count) plus 2 CSS files.
- The editor is CodeMirror 6 based, and `src/vendor/atomic-editor/` is an MIT vendored copy of `kenforthewin/atomic-editor` v0.6.2. `vendor/atomic-editor/LICENSE` is an MIT notice obligation and must be kept in the ported tree.
- The copy source is DocuLight's current state of the vendor directory, not upstream v0.6.2. Since the introduction commit `fc4ded1`, DocuLight changed that directory in 7 commits (5 touching source, 2 test-only). The net increment against the introduction point is `table-widget.ts` +210/-16 and `inline-preview.ts` +22/-1, plus a new test file `__tests__/table-reveal-state.test.ts` (+209 lines, 8 cases).
- The editor package's `"main"` is `./src/index.ts`, so the package publishes source rather than a build artifact. That is why the port is a source copy and not a dependency.

How the port is judged. The counts above are the record, and completeness is verified against them inside this repository: the ported tree's own file count, its line count, the presence of the MIT `LICENSE`, and the entry barrel's exported surface. No criterion reads the DocuLight checkout. That checkout is a developer's local working copy at a path that exists on one machine, so a recursive comparison against it cannot be run in CI or reproduced by anyone else, and a criterion that cannot be run is not a criterion. The DocuLight commit hashes recorded above stay in the text as provenance, which is what they are good for; they are not the pass condition.

Where each contract is verified. The static checks above are unit tests. The two mount-time contracts below are Playwright E2E, because they can only be observed on a mounted editor and this repository's frontend unit suite has no DOM.

The two mount-time contracts:

1. `markdownSource` is not a controlled value. It is read once at mount and from then on the editor is the document's source of truth. The host must not feed the value back on every keystroke.
2. Document replacement goes through the `documentId` prop. When `documentId` is omitted, the `markdownSource` string itself becomes the document's identity, so every save response that returns a new body destroys and recreates the EditorView, losing focus and in-flight input. DocuLight's commit `f54ee4e fix(web): 저장이 편집기를 갈아 끼우지 않게 한다` is the evidence for this contract.

This requirement is the canonical source for both contracts and for their consequence that `documentId` is unchanged across a tab restart so the `EditorView` survives it. FR-MDE-002 and CON-MDE-002 restate them as premises for the hiding rule and the tab binding respectively and judge on top of them; a change to either contract is made here first, and those restatements follow.

The `extensions` array is likewise captured at mount, so its reference shall be pinned with `useMemo`. `readOnly` alone is `Compartment` based and may be toggled without a remount.

`EditorWindow` shall pass the normalized absolute file path as `documentId`. One window corresponds to one file, so that path is the document's identity. Passing the session ID instead would change the value on a tab restart, destroying and recreating the editor and losing the unsaved body.

Dependencies:

- Add `@codemirror/*`, `@lezer/*`, `katex`, `shiki`.
- Raise `mermaid` from `^10.9.5` to `^11.4.1`. The editor requires `^11.4.1` and `^10.9.5` does not satisfy it, so this is a major upgrade. `mermaid` has no use site in this project today, so the blast radius of the upgrade is confined to the editor.

Build tooling stays the host's. The editor's devDependencies are `vite ^8.1.4` and `typescript ^7.0.2` while BuilderGate is on `vite ^7.2.4` and `typescript ~5.9.3`. A source copy does not drag the devDependencies along, but the TypeScript version gap can surface as compile errors, so `tsc` shall be made to pass immediately after the port and before any host wiring is added. The editor package declares no `peerDependencies` and holds React in `dependencies`; because the port copies source, no duplicate React is loaded.

Pitfalls:

- The frontend unit suite cannot mount this editor, so the two contracts above cannot be asserted there. `frontend/package.json` declares no `jsdom`, no `happy-dom`, no `@testing-library/*` and no `react-test-renderer`, and none of the 76 tests under `frontend/tests/unit/` renders a React component — they are pure module tests and `readFileSync` source-text contract tests. AC-2, AC-3, AC-4 and AC-5 are therefore Playwright E2E, which already runs a real browser; only the static verification of the ported artefact — file count, line count, `LICENSE`, barrel exports, declared dependencies, coupling scan — stays in the unit suite. Writing the contract tests as unit tests means introducing a DOM harness first, and that harness is outside this scope.
- The vendored copy carries DocuLight patches, so it cannot be compared against upstream by a plain diff, and `src/vendor/UPSTREAM.md`'s "적용한 패치" table still reads "(아직 없음)" and must not be trusted as the record of what was patched. Commit subjects do not identify the patches either: `be66168` carries a `docs(spec):` prefix while actually changing `table-widget.ts`.
- Saving is not part of the port. The editor package contains no save logic at all; in DocuLight it lives in `packages/web/src/document/` (`DocumentSurface.tsx`, `useAutosave.ts`, `autosave.ts`). This scope supplies its own save path instead.
- The editor's CodeMirror keymap registers no `Ctrl+S` (`Mod-s`), so the host may bind that combination for saving without taking a binding away from the editor.
- Contract 1 is what forces minimize to hide rather than unmount: unmounting drops the edited body, and remounting restarts from whatever `markdownSource` was handed in.

#### Rationale

The port is a source copy rather than a dependency because the package exposes `./src/index.ts` as its `main`, so there is no build artifact to depend on. The copy is taken from DocuLight's current vendor state rather than upstream v0.6.2 because seven DocuLight commits changed that directory and the record of those patches in `UPSTREAM.md` was never updated, so reconstructing them from upstream plus a patch list is not possible.

`documentId` is the normalized absolute path rather than the session ID because a tab restart replaces the session ID while keeping the tab and the file, and the editor treats a changed `documentId` as a different document — the editor would be recreated and the unsaved body lost on every restart.

The two contracts are recorded as requirements rather than left as implementation detail because both fail silently and late: feeding `markdownSource` back on each keystroke produces cursor jumps that look like an input-latency problem, and omitting `documentId` only misbehaves once a save round trip returns a body, which is well after the component appears to work.

### IR-MDE-001 — Session file write endpoint reusing the read path validation

| Field | Value |
| --- | --- |
| Type | interface |
| Target | markdown-editor |
| Status | implemented |
| Priority | high |
| Tags | markdown-editor, file-write, path-validation, api |
| Risk | high |

| Verification Method | Server node:test over the new route and the `FileService` write method covering path escape, blocked path, blocked extension, creation, overwrite, UTF-8 without BOM and newline preservation; frontend unit test over `fileApi.writeFile` asserting the request shape and the rejection on an error response. |
| GitHub Issue | - |
| Related Docs | docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md |

#### Requirement

The server shall expose `POST /api/sessions/:id/files/write` for writing a file inside a session's working directory, and the frontend shall reach it through a new `fileApi.writeFile(sessionId, path, content)`.

The absence this requirement filled, and what stands in its place now:

- There was no write path on the server. `FileService.ts` published `getCwd`, `listDirectory`, `readFile`, `copyFile`, `moveFile`, `deleteFile`, `createDirectory`, `getDiskFreeSpace` and `updateConfig`, and no `writeFile` family existed. `FileService.writeFile(sessionId, filePath, content)` now does, at `FileService.ts:275`, and `FileServiceWrite.test.ts` covers its regression.
- `fileRoutes.ts` registered exactly 7 routes and none of them wrote file content: `GET /:id/cwd`, `GET /:id/files`, `GET /:id/files/read`, `POST /:id/files/copy`, `POST /:id/files/move`, `DELETE /:id/files`, and `POST /:id/files/mkdir`. The write route joins them.
- `fileApi` in `frontend/src/services/api.ts` exposed exactly 7 functions, every one taking `sessionId` as its first argument. `writeFile` at `api.ts:301` keeps that shape, so the call site reads the same as every other file call.

Validation, in the same sequence the read path already uses:

1. `assertSessionExists(sessionId)` rejects a request naming a session that does not exist.
2. `resolveAndValidate(cwd, filePath, blockedPaths)` rejects directory escape and blocked paths.
3. `isBlockedExtension` rejects blocked extensions.

The read path is the precedent: `FileService.ts:225` calls `this.assertSessionExists(sessionId)` as its first statement, `:227` obtains the cwd, `:228` calls `resolveAndValidate`, and `:231` calls `isBlockedExtension`. The write path performs the same three stages in the same order and does not invent a fourth check. The session check is a precondition of the other two rather than an extra: the cwd is obtained from the session, so without it there is no well-defined subtree for `resolveAndValidate` to bound the path against, and a write naming an unknown session would be answered by whatever `getCwd` happened to do.

Request and response:

- Body is `{ path, content }`.
- A file that does not exist is created; a file that exists is overwritten in full.
- Encoding is UTF-8 and no BOM is written.
- Line endings are written exactly as the editor emitted them, with no normalization in either direction.
- Reach is confined to the session's cwd subtree; nothing above it is writable.
- A validation failure is answered with an error response and no bytes are written anywhere.

Pitfalls the implementer will hit:

- `resolveAndValidate` (`server/src/utils/pathValidator.ts:49-75`) performs `validatePath` and `isPathBlocked` but never looks at the extension, so omitting the third stage silently permits every blocked extension on the write path while the read path still blocks it.
- `resolveAndValidate` returns the resolved path unchanged when the target does not exist (ENOENT, `:70-71`). That is what makes it usable for creating a new file, so the implementer must not add an existence precondition in front of it.
- Symbolic links are resolved here on the server (`pathValidator.ts:61-67`) and nowhere on the frontend. The duplicate-document key on the frontend therefore stops at normalization, which is recorded as a known limitation on the context menu requirement.
- Overwriting must truncate. Writing without truncation leaves the tail of a longer previous body behind, which looks like a save that partly failed.
- A rejection test that only asserts an error and an absent file is satisfied by an endpoint that rejects everything, including every legitimate write. Each rejection criterion therefore carries a control in the same test: one legal write that must succeed. Without the control, a route that is broken outright and a route that validates correctly are indistinguishable, and the suite goes green on the broken one.
- The body parser's limit has to follow `maxFileSize`, or the two disagree and the gap between them is a band of files that open and then cannot be saved. `express.json()`'s own default is 100KB while `maxFileSize` defaults to 1MB (`server/src/schemas/config.schema.ts:240`), so every file between those two sizes would have been rejected by the parser before the route ever saw it, and the rejection would have surfaced as a 500 rather than as a size error. `server/src/index.ts:518` therefore mounts `createJsonBodyParser(() => fileService?.maxFileSize ?? fileManagerConfig.maxFileSize)`, which reads the configured size per request (`middleware/requestBodyLimit.ts:64-77`) and turns the parser's `entity.too.large` into a 413 (`:87-92`). The limit is read per request rather than captured once because `updateConfig` can change it while the server runs.

#### Rationale

The write path copies the read path's two-stage validation rather than defining its own because the two stages have different jobs and neither subsumes the other: `resolveAndValidate` bounds the path and `isBlockedExtension` bounds the file type. A write path that validated only the path would be strictly weaker than the read path that already exists, which is the wrong direction for the first endpoint in this codebase that modifies file content.

Conflict detection on save is deliberately absent (design §3): the save overwrites. Detecting an external change would require a confirmation UI and a version token in the read response, which is a scope expansion beyond what was asked. The consequence is that two documents on the same file silently overwrite each other, and that is precisely why the editor layer keys duplicates by resolved absolute path, compared across every workspace, rather than by tab.

`writeFile` takes `sessionId` first because all seven existing `fileApi` functions do; a different argument order in the only mutating call would be the one place a caller could get wrong without a type error, since `sessionId` and `path` are both strings.

#### Acceptance Criteria

- [ ] AC-2: Given content whose text mixes CRLF and LF line endings, when it is written and read back as bytes, then the bytes are identical to the bytes of the submitted content, with no line ending added, removed or converted.

| Field | Value |

| GitHub Issue | - |
| Related Docs | docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md |

#### Requirement

An editor window shall mark unsaved changes with a trailing `*` on its title, shall save through both the title bar save button and `Ctrl+S`, and shall branch its close behaviour on whether the document is dirty and whether saving is still possible.

What the title and the controls act on is the active document of the window. A window holds several documents as tabs and shows one of them, so the `*`, the 저장 button and `Ctrl+S` all name that one; the tab row carries its own `*` per tab, so a dirty document behind another tab is still visible as dirty without being the target of a press aimed at the tab in front. Closing a tab runs the close branches below for that document alone. Closing the window resolves one document per press: the first dirty document is made the active tab and its branch is run, so the user sees which file the question is about before answering it. The remaining documents are closed by the next press, and a window with no dirty document closes outright. A single press that queued several prompts would ask about a file the user cannot see, and a press that closed the window while a prompt was still open would answer its own question.

Source of truth for the body. The body lives in exactly one ref and never in React state as well. Because the editor does not treat `markdownSource` as a controlled value, a second copy would leave no basis for deciding which of the two is current. The editor's change callback updates that ref and sets `dirty` to true. The window hands `WindowDialog` the plain title and the `dirty` flag separately, and `WindowDialog` composes the two through `windowDialogTitleText`. The composition is a pure function living outside the component for a reason: this repository's unit suite has no DOM harness, so a marker assembled inline in JSX could only be judged through E2E, while a function can be judged directly and pinned by a source-text guard at each call site. There is exactly one such function, and the window title, the tab row and the tray list all draw through it; a second place that assembled the marker itself would be the one that silently drifts.

Save. Both entry points call the same save function; there is no second save path. At call time the function re-obtains the session ID from the bound tab rather than using a stored one, because a tab restart replaces `sessionId` while keeping the tab. On success `dirty` becomes false and the `*` disappears. On failure `dirty` stays true and an error banner appears under that window's title bar; the failure is never reported through a modal, so the user can keep editing and retry.

`Ctrl+S` fires only while DOM focus is inside that window. Being topmost in the modeless stack is deliberately not the condition: a window just restored from the tray is frontmost but may hold no focus, and saving on that basis would write a file the user was not looking at while some other window held the text they were editing. The handler calls `preventDefault()` to suppress the browser's own save dialog. The editor's CodeMirror keymap registers no `Ctrl+S` (`Mod-s`), so nothing is taken away from the editor, and while the terminal holds focus the existing xterm handling must be left untouched.

Reading errors. A read failure that happens before any window exists is reported through the existing `MessageBox`, because there is no window in which to draw a banner. Once a window exists, every read and write failure is that window's banner.

Close branches:

- Dirty and saving is possible — ask "저장하시겠습니까?" with save, don't save, and cancel. Save that succeeds closes the window; save that fails leaves the window open with the error shown; don't save closes; cancel leaves the window open with `dirty` intact.
- Dirty and saving is impossible because the bound tab has closed — ask "저장할 수 없습니다. 그래도 닫으시겠습니까?". This is a different prompt from the one above, not the same prompt with a disabled button.
- Not dirty — close with no prompt.

Tab states:

- Tab closed. That document loses its save path: while it is the active tab, the 저장 button and `Ctrl+S` are disabled and a 저장 불가 badge appears in the title bar's action group, to the left of the controls rather than beside the file name — the title bar puts the name on one side and the actions on the other, and the badge belongs with what it disables. The unsaved body stays on screen and cannot be written anywhere. The window itself is untouched, and selecting a sibling document whose tab is alive restores the control, because it acts on the active document.
- Session gone but tab alive (awaiting restart). The document is left alone and a save is still attempted. A failure only produces the banner, and the ordinary unsaved-close confirmation applies.
- Tab restarted. The document survives and the next save goes to the new session.

Canonical source. The tab-closed behaviour — the disabled save path, the badge, and the separate 저장할 수 없습니다 close prompt — is stated definitively in CON-MDE-002. This requirement restates it as one branch of its close table and judges the save flow on top of it; when that behaviour changes, CON-MDE-002 is the requirement to change and this restatement follows it.

Pitfalls:

- Feeding the saved body back into `markdownSource` after a successful save recreates the EditorView and loses focus unless `documentId` is held constant; the port requirement fixes `documentId` to the absolute path for exactly this reason. The save response is not written back into the editor at all.
- Gating `Ctrl+S` on stack order instead of focus produces a bug that only appears after a tray restore, which is late and hard to attribute.
- The confirmation prompt used here is `ConfirmModal`, which applies no `inert`; that is acceptable because the choice is made before anything else can be interacted with, but it means the prompt is not a modal lock and must not be relied upon as one.

#### Rationale

Focus rather than stack position gates `Ctrl+S` because the two disagree exactly in the case the tray creates: the restored window is frontmost while the keyboard still belongs elsewhere. Choosing stack position would save the wrong file with no visible cue that anything unexpected happened, and the file it overwrites is one the user believed they were not touching.

Save failures use an in-window banner rather than a modal because the document is still dirty and still editable; a modal would block the very retry it is announcing. Read failures before a window exists have no banner to live in, so they use the existing `MessageBox` instead of introducing a second error surface.

The close prompt for a closed tab is a separate prompt rather than the ordinary one with the save option greyed out, because the two questions differ: the ordinary one asks whether to save, and this one states that saving is impossible and asks whether to discard.

#### Requirement

Right-clicking the working directory path shown at the bottom of a session shall open a context menu offering `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md`, and choosing one shall open an editor window on that file resolved against the displayed path.

Attachment point. `onContextMenu` is added to `.metadata-cwd-path` in `MetadataRow.tsx` (`:151-176`), and the existing `onClick={handleCopy}` stays. `<MetadataRow>` has two render sites — tab mode at `App.tsx:751-756` and grid mode at `Grid/MosaicTile.tsx:119-123` — so both view modes must get the behaviour. The path value comes from `props.tab.cwd`, which is what the user sees, so what opens matches what is displayed.

File names use the uppercase spelling exactly as written, because those are the names the tools actually read.

Flow when an item is chosen:

- Resolve the file path against the row's `cwd`.
- If a document is already open on the resolved absolute path, do not create a second one: go to the workspace holding it, select its tab, raise its window, and stop.
- Otherwise read the file with `fileApi.readFile(tab.sessionId, path)`.
- On success, add a document bound to that `tabId` as a tab of the current workspace's editor window, and make it the active tab.
- On a 404, ask through the existing `ConfirmModal` whether to create the file; on confirmation write an empty file and then open the window; on cancellation write nothing and open nothing.
- On any other read failure, show `MessageBox` and open no window.

The duplicate key is the normalized absolute path, not the pair of tab ID and path, and it is compared across every workspace rather than within one. Two tabs can share a `cwd`; keyed by the pair, each would open its own `CLAUDE.md` document onto the same file on disk, and since conflict detection is deliberately absent the two would silently overwrite each other's saves. Two workspaces pointed at the same checkout produce the same collision, which is why the key is not scoped to a workspace either. `tab.cwd` is absolute, so joining it with the file name and normalizing yields the key. A document already holding that file is revived even when it is bound to a different tab, so a document stays bound to the tab that first opened it.

This context menu is the only user-facing action that opens a document. Restoring documents after a page reload is a reconstruction of stored state, not a user action, and is specified separately.

Measured facts:

- `ContextMenu.tsx` takes exactly four props — `position`, `items`, `onClose` and `restoreFocusElement?` — and knows nothing about sessions or tabs, so adding items requires no change to it. Multi-level navigation, viewport clamping and mobile behaviour live in separate modules and stay untouched.
- The path element carried `onClick={handleCopy}` and no `onContextMenu` before this requirement; it now carries both, and the copy handler is unchanged.
- Symbolic links are resolved only on the server (`server/src/utils/pathValidator.ts:61-67`), so the frontend key stops at normalization.

Pitfalls:

- Item assembly belongs in a new builder function. Extending the existing `frontend/src/utils/contextMenuBuilder.ts` would entangle this work with the `FR-ARCH-004` through `FR-ARCH-006` contracts, which are `Stability=stable`.
- No submenu is introduced, so `FR-ARCH-001`'s depth limit of 5 is not approached.
- `ConfirmModal` applies no `inert`, which is harmless here only because no editor document for that file exists yet at the moment the question is asked.
- Adding the handler at one render site and not the other leaves the feature missing in whichever view mode the developer was not testing, and both sites render the same component so the omission is invisible in the component itself.

#### Rationale

The duplicate key is the resolved absolute path rather than the tab-and-path pair because the decision not to detect save conflicts makes two windows on one file actively harmful rather than merely redundant: whichever saves last wins and the other's work disappears with no message. Two tabs sharing a `cwd` is ordinary in this product, so the pair key would produce that situation routinely, not rarely.

Reviving a document bound to a different tab, rather than opening a second one bound to the current tab, follows from the same key: there can be only one document per file, so it stays where it was first created. The alternative, rebinding the existing document to the tab the user just right-clicked, would silently move it out from under the tab whose session it had been saving through.

#### Requirement

The header shall carry an editor tray icon that lists every open editor document, regardless of which workspace it belongs to, and choosing a list entry shall make that document visible and frontmost — switching workspaces first when the document belongs to another one.

Placement. The icon goes inside `header-right` (`Header.tsx:131-236`), immediately to the left of the view mode toggle. The stated requirement asks for it "to the left of the hamburger button", but the real `.hamburger-button` is mobile-only and lives in `header-left`; what actually occupies the top right on desktop is the view mode toggle (`☰`/`⊞`), rendered under `onToggleViewMode && !isMobile`. When that toggle is not rendered, the icon takes the first slot of `header-right` instead.

Visibility of the icon. It renders while at least one editor document is open anywhere, which is the same set the list covers, so the icon can never appear above an empty list. That condition belongs to the icon itself.

The badge. The icon carries a count of every open document across every workspace — the same set the list shows. A badge counting only the current workspace would disagree with the list it sits on, and the disagreement would be invisible: the user would see a number and a longer list and have no way to tell which was wrong.

The list. Pressing the icon opens the existing `ContextMenu` with one entry per open document, ordered as the documents are held, and an entry for a document with unsaved changes carries `*`. Each entry reads `워크스페이스 / 탭 | 경로`. The path alone stopped being enough once the list crossed workspaces: the same file name appears under several checkouts, and the two names in front of it say which one this is. A path longer than 56 characters is truncated from the left so the file name survives, because the tail is what distinguishes two entries and the head is what they have in common. A workspace whose name is missing renders `(이름 없음)` and a tab whose name is missing renders `(닫힌 탭)`, so a missing name never collapses the entry into `/ | path`, which would read as a different kind of entry rather than as an incomplete one.

Revival. Choosing an entry resolves every visibility condition that can be resolved and then raises the window: switch to the document's workspace if it is not the current one; clear `minimized`; if the settings screen is showing, return to the workspace screen; and select that document's tab within its window. Clearing `minimized` alone leaves the window blocked by the remaining conditions and nothing changes on screen, which reads as a dead menu item.

The list is not exclusive. The requirement's phrase "선택하여 이것만 출력 가능합니다" is read as reviving the chosen one among several minimized documents, not as hiding every other window. The sentence that immediately follows it in the requirement says multiple editor documents may be up at once, so an exclusive reading contradicts the source.

Pitfalls:

- The frontend unit suite has no DOM environment. `frontend/package.json` declares no `jsdom`, no `happy-dom`, no `@testing-library/*` and no `react-test-renderer`, and no test under `frontend/tests/unit/` renders a component — they are pure module tests and `readFileSync` source-text contract tests. AC-3 asserts a sibling position inside `header-right` and AC-5 crosses a workspace switch in a live application, so both are assigned to Playwright E2E, which already runs a real browser; the icon condition, the badge count, the entry labels and the revival sequence are pure logic and stay in the unit suite.
- The outer condition at `Header.tsx:130` is "at least one callback exists", and `App.tsx:620-636` passes callbacks unconditionally, so that condition is always true. Adding another callback there changes nothing about what is shown or hidden, and an implementer who wires visibility through it will find the icon always present.
- The tray's entries are rebuilt from the workspace and tab lists, and both of those are fresh arrays on every render. A memo that depends on the arrays themselves is therefore recomputed every time, which re-renders the header, replaces its DOM nodes and moves focus out from under whatever had it. The dependency must be the names themselves rather than the arrays that carry them.
- A window revived from the tray is frontmost but does not necessarily hold DOM focus, which is exactly why the save shortcut is gated on focus rather than on stack position.

#### Rationale

The icon's own condition governs its visibility rather than the header's existing callback-presence condition because that condition is always true in production, so routing through it would produce an icon that is permanently visible — including when there is nothing to list.

The list covers every workspace because the tray is the only place that answers "what do I have open". Scoped to the current workspace, it answered a narrower question than the one being asked, and a document left open elsewhere was unreachable until the user happened to return to the workspace holding it. Choosing such an entry does move the user to another workspace, which is why the entry says which workspace it belongs to before it says anything else.

The badge counts the same set the list shows, across every workspace. A badge over a global list that counted only the current workspace would be wrong in a way nobody could see: two numbers, no indication which one to believe.

The entry label leads with the workspace and the tab because the path alone stopped identifying anything once the list crossed workspaces. Several checkouts hold a file of the same name at the same relative path, and their entries were indistinguishable.

Revival resolves all resolvable conditions rather than only `minimized` because the visibility rule is a conjunction: with a hidden tab or the settings screen showing, clearing `minimized` alone produces no visible effect at all, and the user has no way to tell whether the click registered.

#### Requirement

Editor documents shall be persisted per workspace under the key `window_state_<workspaceId>` and reopened after a page reload, and no document body shall ever be written to that store. The window's position and size are the exception and live under one global key; the reason is below.

Structure. `frontend/src/hooks/windowStateStorage.ts` owns the serialization and the per-workspace key, and `useWindowState(workspaceId)` wraps it. That is the same split the project already uses for the mosaic layout: `mosaicLayoutStorage.ts` holds the `mosaic_layout_<workspaceId>` key and `useMosaicLayout.ts` wraps it. `frontend/src/components/editor/editorWindowGeometryCache.ts` owns the global geometry key, and `editorWindowRecord.ts` owns the record shape and the check that a value read back is usable.

What is stored per workspace: one record per open document, carrying the tab ID and the file path.

What is stored globally, once: the window's position and size, under `buildergate.editor-window.geometry`.

The split is asked for rather than chosen. One remembered placement is what the user asked for, and a key named after a workspace cannot be one — every workspace would remember its own. The document records stay per workspace because a record names a tab, and a tab ID means nothing in a workspace that does not hold it.

That geometry key is deliberately not `buildergate.dialog.<id>.geometry`. The dialog store's read path finishes with `clampDialogRect`, which lowers the minimum-size floor to the viewport when the viewport is the smaller of the two — restoring a window too small to show its own title bar, which cannot then be dragged or resized back. Six other dialogs depend on that function, so it is left alone and the editor's cache clamps its own way, in two steps and in this order. First the size is bounded on both sides: never larger than the viewport, never below `EDITOR_WINDOW_MIN_SIZE`, with the floor winning when the two disagree. Then the origin is pushed back until the window fits. Size before position, because a window wider than the viewport has no position at which it fits, so moving it alone would leave it overhanging.

What is deliberately not stored:

- The document body. Reopening re-reads the file from disk. Keeping an unsaved body across a reload would create a conflict question against whatever the file on disk now contains, and detecting that conflict is out of scope.
- The session ID. A tab restart replaces it, so a stored value would be stale; it is re-obtained from the tab whenever an API call needs it.
- The front-to-back order. There is one editor window per workspace, so it has no sibling of its own to be in front of or behind. What the modeless stack still separates is the window from the modals above it, and that is not a stored fact.
- The `stage` rect. It is measured every time from the stage container.

Reopening:

- A stored record whose tab no longer exists is not reopened at all.
- Records come back in the order they were stored, which is the order they become tabs of the window. Nothing re-sorts them: the stored array is the record of the row the user arranged.
- The reopened documents need a window to be tabs of, and it is built by the same function a hand-opened document builds it with: not minimized, positioned and sized from the global geometry key when one is stored, and at the opening placement when none is. The first reopened document becomes the active tab. One builder rather than two — two is how the cache came to be written on every drag and read on none, so a reload returned the window to the stage while the rect it was supposed to remember sat unread.

A record carried four more fields until 2026-09-11: `placement`, `placementBeforeStage`, `minimized` and `floatingRect`. They were written on every change and read by nothing, and `floatingRect` was a second copy of coordinates the global key already owned. They are gone. A stored value that still carries them is read for the two fields it shares with the current record and the rest ignored, so a reload after the change reopens the same documents rather than none.

Workspace switching does not unmount windows; the visibility rule merely hides them, so returning to a workspace finds the unsaved body still there. This store therefore serves only the reconstruction after a page reload. Body preservation while the page lives belongs to runtime memory; this store holds document identity and nothing else.

`persistGeometry={false}` is passed to `WindowDialog` so its own `writeDialogGeometry` path never produces a second copy of the coordinates.

Pitfalls:

- The frontend unit suite has no DOM environment. `frontend/package.json` declares no `jsdom`, no `happy-dom`, no `@testing-library/*` and no `react-test-renderer`, and no test under `frontend/tests/unit/` renders a component — they are pure module tests and `readFileSync` source-text contract tests. The serializer and the cache rules sit there comfortably; anything that asserts a rect reached the screen, or that an editor instance survived a round trip, is assigned to Playwright E2E.
- `persistGeometry={false}` stops the write but not the read: `readDialogGeometry` runs on every mount regardless of that prop, so a value left in `buildergate.dialog.<id>.geometry` by any earlier code path would still become the initial state unless a controlled `rect` is supplied from the first render.
- **A rule that is green as a pure function has not been shown to reach the screen.** The cache's centring and its minimum-size floor are both decided by a function the unit suite exercises, and both were once undone afterwards — the first by a clamp the window layer applied, the second by the dialog store's own read path. The E2E criteria below measure the rendered box for that reason.
- The store is readable and writable by the user, holds values written by older builds, and can be caught half-written. A malformed value reads as nothing rather than throwing, and a storage that refuses reads or writes — as a private browsing mode does — is survived rather than propagated: a window that could not be placed because the store objected would be worse than one placed at its default.

#### Rationale

The body is excluded from the store because storing it converts every reload into a three-way question between the stored body, the file on disk, and what the user remembers writing — and conflict detection is explicitly out of scope. Excluding it makes the reload behaviour simple to state: placement returns, content comes from disk.

The front-to-back order is no longer stored because there is nothing left for it to order. One window per workspace, and only one workspace visible at a time, leaves no pair of editor windows that could be in front of or behind each other. The stored field would have described a relation that no longer exists, and restoring it would have been work whose result nobody could observe.

The document records are scoped per workspace, following the mosaic layout precedent, because a stored record names a tab and a tab ID means nothing in a workspace that does not hold it. The position and size go the other way for a reason that is just as narrow: the user asked for one remembered placement, and a key named after a workspace cannot hold one thing.

The two stores are disjoint: no value lives in both, so neither can contradict the other. They were not always — the per-workspace record carried a `floatingRect` the global key also held, left over from the arrangement before that key existed. Nothing read the per-workspace copy, so the two were never seen to disagree, but that was an accident of the read path rather than a property of the design, and the field was removed rather than left to be found by whoever next went looking for where the rect lives.

The geometry cache is written rather than reusing `readDialogGeometry`, whose last step is `clampDialogRect`. That function lowers the minimum-size floor to the viewport when the viewport is the smaller of the two, and the window it restores is then too small to show its own title bar, which is the handle it would have to be dragged or resized back by. Six other dialogs depend on that function, so it is left alone rather than corrected underneath them.

#### Requirement

One editor window per workspace shall hold every document opened in that workspace as a tab, and the rules for adding, selecting and closing those tabs shall be a pure function of the tab set so that the window layer never decides them for itself.

The tab set is a pair: the ordered list of tabs and the file path of the active one. The active tab is named by path rather than by index. An index is a position in a list that closing a tab renumbers, so a stored index silently comes to mean a different tab; a path is the tab's own identity and survives every change to the list around it.

The three rules:

- Adding. A tab for a path the set already holds is not added twice; the existing one becomes active instead. This is the same duplicate key FR-MDE-007 uses, applied inside the window rather than at the entry point, so a second entry point could not bypass it.
- Selecting. Selecting a path the set does not hold leaves the set unchanged. Nothing is created by selecting.
- Closing. Closing an inactive tab leaves the active one active. Closing the active tab moves the activity to its neighbour — the one that was after it, or, when it was last, the one before it — because a set with tabs remaining and no active tab would render a window with a tab row and nothing under it. Closing the last tab leaves the active path null, and the window then has nothing to show.

Where the rules live. `frontend/src/components/editor/editorWindowTabs.ts` holds all three as pure functions over the pair, and `EditorWindow.tsx` calls them. Kept out of the component because a rule inside a component is only testable through a DOM, and the frontend unit suite has none; kept as one module rather than three because the three rules share the invariant that the active path always names a tab that exists or is null, and an invariant split across three files is an invariant nobody maintains.

Panels. Every open document's panel is mounted at once and all but the active one carry `display: none`. FR-MDE-002 is the canonical statement of why hiding must not unmount; this requirement only says that the rule applies between tabs of one window as well as between windows.

Presentation. The tab row shows each tab's file name with a trailing `*` while that document is dirty, so a dirty document behind another tab is visible as dirty without being selected. Composing that marker with the same function the window title uses keeps one description of what a dirty title looks like.

Pitfalls:

- A rule expressed over the active index instead of the active path passes every test written against a set whose tabs never move, and fails the first time a tab before the active one is closed. The tests must close a tab before the active one for that reason.
- Closing the active tab has three distinct outcomes — a following neighbour, a preceding neighbour, and nothing left — and an implementation that handles only the first two returns a set whose active path names a tab that is gone.

#### Rationale

The active tab is named by path because closing a tab renumbers every index after it, and an index recorded before the close then names a different tab. The defect that produces is silent: the window keeps showing a document, just not the one it was showing, and nothing in the state says anything is wrong.

The rules live in a module of their own because the frontend unit suite has no DOM, so a rule written inside the component could only be judged through Playwright. Three of the seven criteria below distinguish outcomes that differ by which neighbour becomes active, and pinning those through a browser would be slow enough that they would not be written at all.

One window per workspace rather than one window per document follows from what the user asked for and from what the old arrangement cost: several windows on one screen overlapped each other, each carried its own title bar and its own placement, and the placement rules had to answer questions — which terminal does this one cover, how far is it offset from its neighbour — that a single window does not raise.

#### Acceptance Criteria

- [ ] AC-1: Given a tab set holding paths P1 and P2 with P1 active, when a tab for P2 is added, then the set still holds exactly two tabs in the same order and P2 becomes the active path.
- [ ] AC-2: Given a tab set holding P1, when a tab for P3 is added, then the set holds P1 and P3 in that order and P3 is the active path; a newly opened document is the one the user is looking at.
- [ ] AC-3: Given a tab set holding P1, P2 and P3 with P2 active, when P1 is closed, then the remaining tabs are P2 and P3 in that order and P2 is still the active path. The closed tab precedes the active one, so an implementation that tracked the active tab by index would move the activity to P3 here and fail.
- [ ] AC-4: Given a tab set holding P1, P2 and P3 with P2 active, when P2 is closed, then the active path becomes P3; and given instead that P3 was active when it was closed, then the active path becomes P2. Closing the active tab never leaves the set with tabs remaining and no active path.
- [ ] AC-5: Given a tab set holding one tab, when that tab is closed, then the set holds no tabs and the active path is null; and given a selection of a path the set does not hold, then the set is returned unchanged and no tab is created.
- [ ] AC-6: Given a window holding three open documents, then all three panels are mounted and the two inactive ones carry `display: none`; and text typed into one of them before switching away is still present when its tab is selected again.
- [ ] AC-7: Given a document with unsaved changes that is not the active tab, then its entry in the tab row carries a trailing `*` while the active tab's own entry carries none. Saving is deliberately not part of this criterion: the only save controls are the window's 저장 button and `Ctrl+S`, both of which act on the active document, so there is no user action that saves a document behind another tab and no state in which the marker could clear without the tab being selected first.

#### Requirement

The close control in the editor window's title bar shall resolve to the active document and run that document's own close branch, exactly as pressing that tab's own `x` does. It shall never close a document the user is not looking at, and it shall never close more than one document per press. The window is not a thing that can be closed on its own: it exists because documents are open in it, and it disappears when the last one is closed — which is already how closing the last tab behaves.

This supersedes the window-wide close of FR-MDE-006. That requirement resolved the press against the *first dirty* document rather than the active one and, when nothing was dirty, discarded every document in the workspace in a single call. The second half is what the user hit: a window carrying many tabs was emptied by one press, and reopening the editor showed none of them. There was no confirmation because there was nothing dirty to confirm, so the loss was silent and total.

The bulk path is removed rather than left unreachable. A function that discards every document of a workspace has exactly one correct number of callers, and leaving it in place with none of them is an invitation — the next person wiring a close control finds it and it does what its name says.

Where a document is dirty, nothing about the prompts changes: FR-MDE-006's close-branch table still decides, and CON-MDE-002 still owns the tab-closed branch. What changes is only which document the press is about and how many documents a press can affect.

#### Rationale

Acting on the active document rather than the first dirty one is what makes a press answerable. Under the superseded behaviour the window jumped to a tab the user had not selected and asked about a file they had not been looking at; under this one the question is always about the document on screen.

Closing one per press is not slower in the case that matters. A window with one document closes in one press, which is the common case. A window with many documents is precisely the case where wiping them all on one press is wrong, and where the user who wants the window out of the way has the minimize control instead.

#### Acceptance Criteria

- [ ] AC-1: Given a window holding three documents with the second active and none dirty, when the title bar close control is pressed once, then exactly one document is closed and it is the active one; the other two remain open and the window remains.
- [ ] AC-2: Given a window holding one document that is not dirty, when the title bar close control is pressed, then that document is closed and the window disappears with it.
- [ ] AC-3: Given a window whose active document is dirty, when the title bar close control is pressed, then that document's close branch from FR-MDE-006 runs for that document; a dirty document behind another tab is neither prompted for nor closed by that press.
- [ ] AC-4: Given a window holding documents, then the title bar close control and the active tab's own close control reach the same close path for the same document, so a document has exactly one way of closing.
- [ ] AC-5: Given the shipped frontend source, then no function closes every document of a workspace in one call, and the editor window has no prop through which such a call could be reached. This is the control for AC-1: asserting that one press closes one document proves nothing if a second, bulk path still exists beside it.
- [ ] AC-6: Given a tab set that holds documents but whose active path names none of them, when the title bar close control is pressed, then one document is still closed rather than the press doing nothing; a control that silently does nothing is indistinguishable from a broken one.

#### Requirement

시스템은 편집기 창 본문 왼쪽에 파일 트리 패널을 호스팅하여, 컨텍스트 메뉴로 열고 패널 상단의 닫기 버튼으로 닫으며, 경계를 끌어 폭을 조절하되 창 폭의 50% 를 넘지 않게 해야 한다.

#### Rationale

탭 막대를 트리 위가 아니라 트리 오른쪽에 두는 것은 탭이 문서 영역에 속하고 트리는 창 전체에 속하기 때문이다. 제목 표시줄에 토글을 넣지 않는 것은 그 줄에 저장·최대화·최소화가 이미 있어 네 번째 버튼이 창이 좁아질 때 가장 먼저 뭉개지는 자리가 되기 때문이다. 앞선 설계의 '탐색 전용' 은 승계한다 — 근거였던 Delete 사고는 단축키를 가두는 범위를 창 표면에서 트리 패널 표면으로 좁혀 막는다.

#### Acceptance Criteria

- [x] AC-1: 패널은 창 본문 왼쪽에 놓이고 탭 막대와 문서 영역이 그 오른쪽에 세로로 쌓인다
- [x] AC-2: 여는 길은 둘이다 — 문서 도구줄의 파일 트리 토글 버튼(FR-MDE-020)과, 탭 막대·제목 표시줄의 빈 곳에 붙는 창 컨텍스트 메뉴. 터치에서는 같은 빈 곳을 길게 눌러 메뉴를 연다(iOS 는 길게 누르기 contextmenu 가 없다). 패널을 열 수 없으면(문서의 터미널에 세션·cwd 가 없음) 토글은 비활성이고 이유를 툴팁으로 보인다
- [x] AC-3: 닫는 길은 패널 상단의 X 버튼, 문서 도구줄의 파일 트리 토글, 창 메뉴 항목이다 — 토글은 패널이 열려 있는지를 눌림 상태로 보이며 메뉴의 체크와 같은 상태를 읽는다

- [x] AC-6: 패널은 항상 트리 모드이고 목록 모드를 지원하지 않는다
- [x] AC-7: 패널에도 상위로 가는 '..' 를 둔다
- [x] AC-8: 패널에서도 컨텍스트 메뉴와 단축키로 파일 조작을 할 수 있고 '새 탭에서 열기' 만 빠진다
- [x] AC-9: 단축키는 트리 패널 표면에 포커스가 있을 때만 가로채고 문서 영역에서 누른 Delete 는 글자를 지운다 — 이 규칙의 canonical source 는 FR-FEX-005 AC-7 이며, 여기서는 이 패널이 서는 전제로만 다시 적는다. 규칙이 바뀌면 FR-FEX-005 를 먼저 고친다
- [x] AC-10: 경계를 끌어 폭을 조절하며 최소 160px, 최대 창 폭의 50%, 더블클릭은 기본값으로 되돌린다

#### Requirement

시스템은 파일 이름 하나로 마크다운·코드·이미지·열지 않음 중 하나의 모드를 정하는 단일 판정표를 두고, 편집기 열기와 탐색기의 열 수 있음 표시와 파일 아이콘이 모두 이 표를 읽어야 한다.

#### Rationale

지금 열기 판정(viewableExtensions.ts)과 아이콘 표(fileListView.ts)가 따로 있어 한쪽만 고쳐진다. 또 .ts·.py·.yaml 이 허용 목록에 있어 마크다운 편집기로 열리며 # 주석이 제목으로 렌더링된다. 판정을 한 표로 모으면 목록이 갈라지지 않는다.

#### Acceptance Criteria

#### Acceptance Criteria

### FR-MDE-020 — 편집기 문서 도구줄: 경로 표시·복사, 주간/야간 토글, 줄바꿈 아이콘, 코드 모드 전체 폭

| Field | Value |
| --- | --- |
| Type | functional |
| Target | code-editor |
| Status | implemented |
| Priority | medium |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | - |

#### Requirement

편집기 창의 각 문서 위에는 한 줄 도구줄이 있어 왼쪽에 문서 파일의 절대 경로를, 오른쪽에 주간/야간 토글과(코드 모드일 때만) 줄바꿈 토글을 아이콘으로 보여 주어야 하며, 마크다운이 아닌 코드 모드 문서는 가운데 정렬된 읽기 열이 아니라 편집 영역 전체 폭을 써야 한다.

#### Rationale

사용자 요청(2026-09-26): 코드 파일은 화면 폭 전체를 보고 싶고, 도구줄 왼쪽이 비어 어색하며, 편집기 테마를 주간/야간으로 고르고 싶다. 야간 테마는 벤더 편집기의 기본(다크) 팔레트를 쓰므로 새 색 값을 만들지 않는다. 주간 테마의 본문 검은색 규칙은 주간일 때만 적용된다

#### Acceptance Criteria

- [x] AC-1: 마크다운이 아닌 코드 모드 문서(SVG 소스 편집 포함)는 본문을 가운데 정렬 열로 제한하지 않고 편집 영역의 전체 폭과 높이를 쓴다. 마크다운 문서의 읽기 열 폭과 가운데 정렬은 바뀌지 않는다
- [x] AC-2: 코드 모드의 줄바꿈 토글은 글자 버튼이 아니라 SVG 아이콘 토글 버튼이며, 켜짐 상태는 aria-pressed 와 눌림 모양으로 구별된다. FR-MDE-014 AC-3 의 전역 선호 저장은 그대로다
- [x] AC-3: 도구줄 오른쪽 끝에는 줄바꿈 토글(있을 때), 그 왼쪽에 파일 트리 토글, 그 왼쪽에 주간/야간 토글이 놓인다. 주간일 때는 달 모양, 야간일 때는 해 모양 SVG 아이콘을 보이며 누르면 편집기 테마가 바뀐다
- [x] AC-4: 주간/야간 선택은 브라우저 localStorage 의 전역 사용자 선호로 저장되어 새로고침과 재시작 뒤에도 적용되고, 열린 모든 편집기 문서가 함께 바뀐다. 저장소를 쓸 수 없으면 주간으로 연다
- [x] AC-5: 마크다운 문서의 도구줄에는 주간/야간 토글만 있고 줄바꿈 토글은 없다
- [x] AC-6: 도구줄 왼쪽에 문서 파일의 절대 경로가 표시된다. 경로 전체가 들어가지 않으면 ...\{파일이름} 형태(경로의 구분자를 따름)로 줄여 표시하고, 전체 경로는 툴팁으로 볼 수 있다
- [x] AC-7: 경로를 클릭하면 전체 절대 경로가 클립보드에 복사되고, 경로 자리의 글자가 세션 하단 경로와 같은 방식으로 잠시 '✓ Copied' 로 바뀌었다가 다시 경로로 돌아온다

### CON-MDE-003 — Math fonts are served as files, not inlined past the CSP

| Field | Value |

| Priority | medium |

#### Requirement

The production build shall emit every font asset as a file served from the application origin rather than inlining it as a data: URI, so that the server's font-src 'self' policy does not refuse a font the editor's math rendering depends on.

#### Rationale

The server sends Content-Security-Policy font-src 'self' (server/src/middleware/securityHeaders.ts:43). Vite inlines any asset under its 4KB default threshold, and KaTeX_Size3-Regular.woff2 fell under it, so the browser refused the one face the markdown preview uses for large math delimiters and silently fell back for every viewer.

#### Acceptance Criteria

- [x] AC-1: AC-1: The production build shall emit .woff2, .woff, .ttf, .otf and .eot assets as files. No built CSS or JS shall reference a font through a data: URI.
- [x] AC-2: AC-2: Non-font assets shall keep Vite's default inlining behaviour, so the change costs no extra request outside fonts.
- [x] AC-3: AC-3: A logged-in page load against a live server shall report no Content-Security-Policy font violation in the browser console.
