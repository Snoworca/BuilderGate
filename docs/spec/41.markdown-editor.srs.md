## 1. Scope Overview

DocuLight2.0 의 마크다운 편집기를 BuilderGate 로 이식하고, 그 편집기를 담을 모달리스 창 시스템을 세운다. 사용자는 세션의 작업 경로에서 우클릭하여 `CLAUDE.md` · `CLAUDE.local.md` · `AGENTS.md` 를 편집하며, 편집 창은 여러 개를 동시에 띄우고 마우스로 클릭하여 앞뒤 순서를 정한다.

설계 근거와 조사 결과는 `docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md` 에 있다. 그 문서는 두 코드베이스를 대조하여 다섯 차례 검증한 결과이며, 이 scope 의 요구사항은 그 위에서 작성된다.

## 2. Scope Boundaries

### In Scope

- 모달리스 창의 배치 상태(터미널 채움 · 최대화 · 자유 배치)와 그와 독립된 감춤 플래그.
- 창의 z-order 와 클릭에 의한 순서 변경. 모달 다이얼로그와 분리된 스택.
- 편집기 소스의 이식, 그리고 그 편집기가 강제하는 두 계약(`markdownSource` 가 controlled value 가 아니라는 것, 문서 정체성을 `documentId` 로 준다는 것).
- 서버의 파일 쓰기 경로. 읽기 경로가 쓰는 경로 검증을 그대로 따른다.
- 세션 작업 경로의 우클릭 컨텍스트 메뉴와 파일 부재 시 생성 확인.
- 헤더의 편집기 트레이와 열린 문서 목록.
- 워크스페이스별 창 배치의 영속화와 복원.

### Out of Scope

- 임의 파일을 고르는 파일 탐색기 UI. 내부 API 는 임의 경로를 받도록 만들되 UI 진입점은 세 파일로 제한한다.
- 새로고침 이후의 미저장 본문 복원. 세션이 살아 있는 동안의 유지는 In Scope 다.
- 저장 시 외부 변경 충돌 감지. 덮어쓰기가 확정된 결정이다.
- 편집기의 첨부 업로드와 위키링크 기능. 콜백을 주지 않으면 비활성으로 남는다.
- 모바일 레이아웃에서의 창 동작.
- 라이트 테마 대응.

## 3. Assumptions and Constraints

- 파일 접근은 세션 cwd 하위로 한정된다. 서버의 경로 검증이 그 경계를 강제한다.
- **창은 세션이 아니라 탭에 매인다.** `WorkspaceTab` 이 `id` 와 `sessionId` 를 별개로 갖고 `restartTab` 이 `sessionId` 만 교체하므로, 세션 ID 는 탭의 생애에 걸쳐 안정적이지 않다. 터미널 rect 레지스트리도 탭 ID 를 키로 쓴다.
- 편집기 창의 z-index 는 `3000` 대역을 쓴다. 프로젝트 전체에서 `3000`~`5000` 사이가 비어 있고, 모달(`5000`)·확인 팝업(`9999`)·컨텍스트 메뉴(`10000`)가 모두 그 위에 오기 때문이다.
- `mermaid` 를 `^10.9.5` 에서 `^11.4.1` 로 올려야 한다. 편집기가 요구하는 범위를 현재 버전이 만족하지 않는다.
- 프로젝트는 다크 테마에 고정되어 있다. 편집기의 기본값도 다크이므로 어긋나지 않는다.
- CSS 스코프 격리가 없다. 새 클래스에는 접두사를 둔다.
- 이식 대상 편집기는 MIT 라이선스 벤더링 사본을 포함하므로 `LICENSE` 파일을 함께 유지해야 한다.

#### Requirement

The editor window shall carry exactly one placement state among `docked`, `stage`, and `floating`, and its title bar shall expose five controls in left-to-right order: 저장 / 터미널 채움 / 최대화 / 최소화 / 닫기. The placement controls are injected by `EditorWindow` through the new optional `titlebarActions` prop, so `WindowDialog` itself stays unaware of placement states.

Placement semantics:

- `docked` (the state a window opens in) — the window covers the terminal rect of the tab it is bound to. That rect is read from the existing registry that `TerminalHostSlot` fills with `upsertHost(tabId, hostId, rect, isVisible, extras)` and that `TerminalRuntimeLayer` reads through `hosts.get(tab.id)`; no new measurement code is added. The registered coordinates are relative to the `position:absolute; inset:0` overlay div that `TerminalRuntimeLayer` renders inside the stage, so the overlay's `getBoundingClientRect()` is added to convert them to viewport coordinates. Because the target is the terminal rect and not the whole tab area, the 28px path bar (`MetadataRow` root, fixed `height: '28px'`) is never covered.
- `stage` — the whole terminal stage: the container `div{flex:1, position:relative, overflow:hidden}` that `TerminalWorkspaceStage` renders, measured by ref.
- `floating` — where the user placed it. Entering `floating` from `docked` or `stage` inherits that rect unchanged.

Control behaviour:

- `터미널 채움` sets `docked`, and renders disabled while the window is already `docked`.
- `최대화` records the current placement and switches to `stage` when the window is not `stage`; when it already is `stage`, it returns to the recorded placement, or to `docked` when no record exists. The record is written only on entry to `stage`, so every transition among the three placement states has a defined destination.
- `최소화` sets the `minimized` flag, which is a separate axis specified by the hiding requirement.
- Drag or resize sets `floating`.

Coordinates: all three placement states are computed by `EditorWindow` and handed to `WindowDialog` as a controlled `rect`, so `clampDialogRect` is not used. `floating` clamping is performed by `EditorWindow` against the stage rect rather than the viewport, and `Rnd`'s `bounds` points at the stage container instead of `"window"`, so a window cannot be dragged over the sidebar, header, or tab bar. The stated requirement only demands that maximizing not cover them, but restricting only maximize while permitting drag would make the rule inconsistent, so one boundary applies to every movement.

Measured facts the implementer needs:

- Layout constants are hard-coded pixels that do not pass through any CSS variable: sidebar 220px is an inline style at `frontend/src/App.tsx:592`, header 58px is `Header.css:10`, tab bar 36px is `WorkspaceTabBar.css:7`, and the tab bar renders only under the condition at `App.tsx:609`. The stage container (`App.tsx:103`, rendered by `TerminalWorkspaceStage` defined at `App.tsx:72`) already excludes all three, so `stage` measures that container and does not restate the numbers.
- `WindowDialog` already implements the modeless branch — background click-through via `pointer-events: none`, no backdrop, no sibling `inert`, no focus trap — and `DialogMode='modeless'` has zero call sites in production or tests today, so changing that path carries no existing-behaviour regression.
- `WindowDialog` renders its surface through `createPortal(…, document.body)` (`WindowDialog.tsx:203`), so an editor window is a direct child of `document.body` and is never laid out inside the stage. That portal is the reason the `docked` rect has to be converted at all: the registry hands out stage-relative coordinates, while a portalled surface positioned absolutely resolves against the viewport, so the overlay's viewport origin must be added before the rect is applied. Leaving the coordinates in stage-relative form would place every `docked` window off by the stage's own offset.
- The terminal-area registry is keyed by tab ID (`TerminalHostSlot.tsx:42-59`) and read at `TerminalRuntimeLayer.tsx:188`; the overlay is at `TerminalRuntimeLayer.tsx:182`; `MetadataRow.tsx:84` holds the 28px height.
- `upsertHost` carries visibility as a dedicated fourth argument that is separate from the rect: its signature is `upsertHost(tabId, hostId, rect, isVisible, extras)` (`TerminalRuntimeContext.tsx:43-49`). Visibility is therefore a registered fact, not something to be inferred from coordinates.

Pitfalls:

- `Rnd`'s `bounds` takes a selector string or an element, and the stage container it must point at has neither to offer: `App.tsx:103` is an anonymous `div` carrying inline styles only, with no class and no id. Giving that container an identifier, or threading a ref from it out to the window layer, is therefore a prerequisite of the bounds restriction rather than a detail of it — until one exists there is no way to name the bounds target, and `bounds` falls back to `"window"`, which is exactly the boundary this requirement replaces.
- `readDialogGeometry` (`WindowDialog.tsx:37-39`) runs on every mount independently of `persistGeometry`, so `persistGeometry={false}` cannot stop a stored geometry from becoming the initial state. `EditorWindow` must supply the controlled `rect` from the first render so the stored value never reaches the screen. `persistGeometry` also defaults to `true` (`windowDialogModel.ts:26`), so it must be passed explicitly as `false` to stop `writeDialogGeometry` from creating a second source of truth for coordinates.
- A hidden tab must be recognised through the registry entry and its `isVisible` field, never through a `{0,0,0,0}` rect literal. The judgement is the one `TerminalRuntimeLayer.tsx:51` already makes: `Boolean(host?.isVisible && host.rect.width > 0 && host.rect.height > 0)`. Two measured facts make a rect-literal comparison wrong. First, the registered coordinates are stage-relative — `hostRect.left - rootRect.left` at `TerminalHostSlot.tsx:46-47` — so a hidden slot, whose own `getBoundingClientRect()` returns zeros, reports a `left` that is negative by the stage's left offset (the sidebar width in the desktop layout) rather than zero; only `width` and `height` fall to zero. Second, when a slot unmounts, `removeHost` deletes the entry outright with `next.delete(tabId)` (`TerminalRuntimeContext.tsx:123`), so the lookup returns `undefined` and there is no rect left to compare. A `{0,0,0,0}` condition therefore never becomes true in production: only a test that writes that literal by hand would exercise it, so such a check is vacuous exactly where it is meant to protect. While the judgement is false the window is not placed and stays hidden.
- The rect registry is a React context owned by `TerminalRuntimeProvider`, which exists only inside `App.tsx:623`-`:716` and only while `wm.activeWorkspace` is set (`App.tsx:606`, `:718`). Window components must render inside that provider to read it.
- The target rect must be tracked with `ResizeObserver` plus `window.resize`, following the precedent already in `TerminalHostSlot`.

#### Rationale

`docked` targets the terminal rect rather than the whole tab area for three reasons. The stated requirement is that the window covers the terminal. Leaving the 28px path bar visible keeps the right-click entry point reachable while a window is open, so a second file can still be opened. And it guarantees that `docked` and `stage` always differ by at least those 28px, so `터미널 채움` and `최대화` never produce the same result and never look like duplicate buttons.

`stage` is measured from the stage container instead of subtracting sidebar 220px, header 58px, and tab bar 36px, because those three constants live in three different files with no shared variable; duplicating them into the window code means only one copy gets corrected when the layout changes. Measuring also removes the need to branch on view mode: in grid mode the terminal area inside a tile and in tab mode the stage minus the path bar both come out of the same registry.

#### Acceptance Criteria

- [ ] AC-1: Given a window whose placement is `docked`, when 최대화 is pressed, then the placement becomes `stage` and `docked` is recorded as the previous placement; when 최대화 is pressed again, then the placement returns to `docked`.
- [ ] AC-2: Given a window whose placement is `stage` with no recorded previous placement, when 최대화 is pressed, then the placement becomes `docked`.
- [ ] AC-3: Given a window whose placement is `docked`, then the 터미널 채움 control renders disabled; given a window in `stage` or `floating`, then that control is enabled and pressing it sets the placement to `docked`.
- [ ] AC-4: Given a window in `docked` or in `stage`, when the user drags or resizes it, then the placement becomes `floating` and the rect at the start of the interaction equals the rect the window had in its previous placement state.
- [ ] AC-5: Given tab T has terminal rect R registered through `upsertHost(T, hostId, R, true, extras)` and the runtime overlay's viewport origin is O, when a window bound to T is laid out in `docked`, then its rect equals R translated by O, and its bottom edge is at or above the top edge of the 28px path bar of that tab.
- [ ] AC-6: Given the stage container measures to rect S, when a window is in `stage`, then its rect equals S; when S subsequently changes through a resize, then the window rect updates to the new S without any sidebar, header, or tab bar pixel constant appearing in the computation.
- [ ] AC-7: Given a `floating` window and a drag whose requested position would place part of the window over the sidebar, header, or tab bar, then the resulting rect is fully contained in the stage rect; and given a drag whose requested position is fully inside the stage rect, then the resulting rect differs from the pre-drag rect by exactly the requested delta.
- [ ] AC-8: Given a stored geometry exists under `buildergate.dialog.<id>.geometry` for an editor window, when that window mounts, then the rect actually rendered is the computed placement rect and not the stored one, and closing the window writes no value to that key.
- [ ] AC-9: Given a tab T that is rendered while hidden because it is not the active tab, when the registry entry actually produced at runtime for T is read, then its `isVisible` is false and its rect reports `width` 0 and `height` 0 while `left` is negative rather than 0, so the entry does not equal `{0,0,0,0}`; and given tab T's slot has unmounted, then the lookup for T returns `undefined` and carries no rect at all. In both cases a window bound to T is withheld from `docked` placement by the `host?.isVisible && host.rect.width > 0 && host.rect.height > 0` judgement, and the placement code contains no comparison of a registered rect against a `{0,0,0,0}` literal.

### FR-MDE-002 — Editor window hiding must preserve the editor instance

| Field | Value |
| --- | --- |
| Type | functional |
| Target | markdown-editor |
| Status | planned |
| Priority | high |
| Tags | markdown-editor, modeless-window, visibility, editor-lifecycle |
| Risk | high |
| Stability | evolving |
| Verification Method | Frontend unit tests (`frontend/tests/unit/`, node:test) for AC-3 (placement preserved across minimize and restore), AC-4 (the five-term visibility conjunction, each term individually false) and AC-5 (term 5 applied to `docked` only) — all pure predicate logic. Playwright E2E for AC-1, AC-2, AC-6 and AC-7, which each require a mounted editor: same instance and unsaved body intact across minimize and restore, `display: none` without unmount, the same EditorView across a tab restart, and `markdownSource` staying at its mount value; plus leaving and returning to a tab or workspace with unsaved edits intact. The frontend unit suite has no DOM environment, so every mount-observing assertion is E2E. |
| GitHub Issue | - |
| Related Docs | docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md |

#### Requirement

Hiding an editor window shall be expressed as `display: none` on the window surface and shall never unmount the editor. `minimized` is a boolean flag on its own axis, independent of the placement state, so minimizing and restoring leaves the placement state untouched.

A window is visible only when every one of these five terms holds. If any term is false the surface is hidden, and in no case is it unmounted.

1. `minimized` is false.
2. The current screen is the workspace screen.
3. The window's workspace is the current workspace.
4. The view mode is grid, or the active tab ID equals the window's tab ID.
5. The placement state is not `docked`, or the registry entry for the window's tab reports a usable terminal area, which is the judgement `host?.isVisible && host.rect.width > 0 && host.rect.height > 0`.

Term 5 applies to `docked` only, because `stage` and `floating` do not read the terminal rect. Only term 1 is under the user's control through a window button; terms 2 to 5 are decided by the system, so clearing `minimized` alone does not necessarily make a window appear.

Why unmounting is forbidden — the two contracts the ported editor enforces:

1. `markdownSource` is not a controlled value. It is read once at mount, and from then on the editor is the source of truth for the document. Feeding the value back on every keystroke is prohibited.
2. Document replacement goes through the `documentId` prop. When it is omitted, the `markdownSource` string itself becomes the document identity, so every save response carrying new body text destroys and recreates the `EditorView` and loses focus and input. The DocuLight commit `f54ee4e fix(web): 저장이 편집기를 갈아 끼우지 않게 한다` is the evidence for this contract.

Canonical source for those two contracts: FR-MDE-005 states them definitively, together with the consequence that `documentId` stays unchanged across a tab restart so the `EditorView` survives it. This requirement restates them only as the premise its hiding rule stands on and judges on top of that premise; when a contract changes, FR-MDE-005 is the requirement to change, and the restatement here follows it.

An unmounted editor therefore loses its unsaved body, and remounting restarts from whatever `markdownSource` was given. Minimizing must hide, not unmount. The same reasoning covers workspace switching, screen switching, and tab switching, all of which go through the five terms above.

Measured facts the implementer needs:

- The `extensions` array is also captured at mount, so its reference must be pinned with `useMemo`. `readOnly` alone is `Compartment`-based, so toggling it does not remount.
- The wrapper of an inactive tab already carries `display: none` at `frontend/src/App.tsx:672`, and the decision that drives it is `const isVisible = isActiveWs && isActiveTab;` at `App.tsx:665`, which conjoins the workspace condition `tab.workspaceId === wm.activeWorkspaceId` (`:663`) with the tab condition `ws?.activeTabId === tab.id` (`:664`). Terms 3 and 4 together mirror that combined judgement rather than introducing a second one: term 3 is its workspace half, and term 4 is its tab half widened by the grid-mode escape. Term 4 alone is not that judgement, so quoting only the tab half would understate what the code actually decides.
- `upsertHost` registers visibility as a dedicated fourth argument that is separate from the rect: `upsertHost(tabId, hostId, rect, isVisible, extras)` (`TerminalRuntimeContext.tsx:43-49`). Term 5 reads that field; it does not infer visibility from coordinates.

Pitfalls:

- The frontend unit suite cannot mount a React component. `frontend/package.json` declares no `jsdom`, no `happy-dom`, no `@testing-library/*` and no `react-test-renderer`, and none of the 76 tests under `frontend/tests/unit/` renders a component — they are pure module tests and `readFileSync` source-text contract tests. Anything that has to observe a mounted editor therefore belongs in Playwright E2E, which already runs a real browser; AC-1, AC-2, AC-6 and AC-7 are assigned there for that reason. Writing them as unit tests means building a DOM harness first, and that harness is outside this scope.
- A hidden tab must never be detected by comparing the registered rect against `{0,0,0,0}`. Term 5 is the judgement `TerminalRuntimeLayer.tsx:51` already makes, `Boolean(host?.isVisible && host.rect.width > 0 && host.rect.height > 0)`, and two measured facts are why. First, the registered coordinates are stage-relative — `hostRect.left - rootRect.left` at `TerminalHostSlot.tsx:46-47` — so a hidden slot, whose own `getBoundingClientRect()` returns zeros, reports a `left` that is negative by the stage's left offset (the sidebar width in the desktop layout); only `width` and `height` fall to zero. Second, when a slot unmounts, `removeHost` deletes the entry with `next.delete(tabId)` (`TerminalRuntimeContext.tsx:123`), so the lookup returns `undefined` and there is no rect left to compare. A `{0,0,0,0}` condition therefore never becomes true in production, and only a test that writes that literal into the registry by hand would exercise it — the check would be vacuous exactly where it is meant to protect. Placing a window on a zero-sized area would give the window zero size, which is what term 5 prevents.
- Clearing `minimized` on its own produces no visible change when another term is false. Any restore path must resolve the terms it can resolve.
- The window renders inside `TerminalRuntimeProvider`, which unmounts together with the active workspace. Deleting the last workspace therefore destroys the windows and their unsaved bodies. This is accepted as a known constraint, because deleting a workspace is an explicit destructive action.

#### Rationale

The editor reads `markdownSource` once at mount and treats itself as the document's source of truth afterwards, so unmounting is equivalent to discarding the unsaved body. Minimize is a display operation from the user's point of view, not a document operation, so it must not have that effect.

Placement and hiding are kept on separate axes because folding minimize into the placement state produces transition combinations in which "the previous state" is undefined — for example minimizing from `stage` and then pressing 터미널 채움. With two axes every combination has a defined destination.

#### Acceptance Criteria

#### Requirement

Pressing anywhere on an editor window shall bring that window in front of every other editor window. This is the core behaviour of the feature and no part of it exists in the code today.

Two changes to `dialogStack.ts` deliver it.

1. Split the stack by kind. The single module-global array becomes two stacks, `modal` and `modeless`. A modal's `isTopmost` is decided within the modal stack only.
2. Add a `raise(token)` operation that moves the named entry to the end of its stack and notifies subscribers.

The window surface calls `raise` from a `pointerdown` handler registered in the capture phase, so pressing an element inside the window also raises it. That handler calls neither `stopPropagation` nor `preventDefault`, so the editor's own input handling, caret placement, and focus are untouched.

Stack order is used for the z-index computation only. Mount order stays fixed at creation order and is never reordered to reflect the stack. Moving a DOM node in response to `pointerdown` re-inserts it immediately after the press, which aborts a text selection drag that has just begun. Front-to-back order is therefore expressed purely through z-index.

Measured facts the implementer needs:

- `dialogStack.ts` today keeps one module-global array and only appends to it with `entries.push`; there is no API that reorders an entry.
- `useDialogStack(dialogId, mode === 'modal')` registers modal dialogs only, so modeless windows are not in the stack at all yet.
- `WindowDialog.tsx:100` gates the focus trap, Tab containment, and Escape blocking on `if (mode !== 'modal' || !stackState.isTopmost) return;`.
- There are six modal call sites, all passing `mode="modal"`: `CommandPresetDialog.tsx:315`, `dialog/MessageBox.tsx:28`, `McpControlDialog.tsx:607`, `RecoveryOptionDialog.tsx:240`, `TerminalShortcutDialog.tsx:339`, `Workspace/WorkspaceMoveDialog.tsx:49`.

Pitfalls:

- The frontend unit suite cannot dispatch DOM events or inspect rendered nodes. `frontend/package.json` declares no `jsdom`, no `happy-dom`, no `@testing-library/*` and no `react-test-renderer`, and none of the 76 tests under `frontend/tests/unit/` renders a component — they are pure module tests and `readFileSync` source-text contract tests. The stack arithmetic is unit-testable and stays there, but every criterion that presses a window, checks the capture phase, watches for `stopPropagation`, reads sibling order, or exercises modal Escape and Tab containment is assigned to Playwright E2E, which already runs a real browser. Attempting those as unit tests means building a DOM harness first, and that harness is outside this scope.
- Splitting the stack is not only about `raise`. If modal and modeless entries share one stack, the moment a modeless window is raised above a modal, that modal's `isTopmost` turns false and, by the condition at `WindowDialog.tsx:100`, its Tab containment and Escape blocking switch off entirely.
- Raising by moving the DOM node breaks an in-flight text selection drag. Change z-index, not node position.
- Changing `useDialogStack` is a modification of behaviour that six live modals depend on, so their focus trap and Escape handling need explicit regression coverage.

#### Rationale

Without a reorder operation two overlapping windows can never change places, and "click to decide front and back" — the behaviour the user asked for — cannot exist. Raising through z-index rather than DOM order is chosen because the raise is triggered by the same `pointerdown` that may start a text selection inside the editor, and a node move at that instant cancels the selection the user just began.

The stacks are split rather than shared because the modal's topmost decision and the modeless window's front-most decision are different questions asked of the same array; answering them from one array makes a modeless raise silently disable modal focus containment.

- [ ] AC-1: Given editor windows A and B where B was opened after A and therefore sits in front, when a `pointerdown` occurs on A's title bar, then A's computed z-index becomes strictly greater than B's.
- [ ] AC-2: Given the same two windows, when a `pointerdown` occurs on an element nested inside A's editor content rather than on the window surface itself, then A is still raised in front of B, showing the handler runs in the capture phase.
- [ ] AC-3: Given a `pointerdown` on an editor window, then the raise handler calls neither `stopPropagation` nor `preventDefault`: a listener attached to the pressed descendant still receives the event and the default caret placement or focus change still occurs.

### FR-MDE-004 — Cascade offset must keep every docked window inside its target area

| Field | Value |
| --- | --- |
| Type | functional |
| Target | markdown-editor |
| Status | planned |
| Priority | medium |
| Tags | markdown-editor, modeless-window, cascade, placement |
| Risk | medium |
| Stability | evolving |
| Verification Method | Frontend unit tests (`frontend/tests/unit/`, node:test) for AC-1 to AC-7, all of which judge the cascade computation itself: containment of the computed rect inside the target rect, the exact 28px step, the wrap at `k = 4`, the `minSize` fallback, inclusion of hidden and minimized windows in the count, exclusion of `stage` and `floating` windows, and recomputation on re-entry into `docked`. Playwright E2E for AC-8, which is judged on the box actually rendered rather than on the rect that was computed: a target area narrower than 320 or shorter than 240 must not be widened or heightened by the minimum `WindowDialog` hands to `Rnd`, and no part of the window may extend over a neighbouring tile. That measurement needs a real browser, which the frontend unit suite does not provide. |
| GitHub Issue | - |
| Related Docs | docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md |

#### Requirement

Whenever a window enters the `docked` placement state, the system shall count the windows that are bound to the same `tabId` and whose placement state is `docked`, and use that count as the cascade step `k`. Hidden windows count: a minimized window, and a window on a tab that is not currently active, both still occupy that terminal area. Windows in `stage` or `floating` do not occupy it and are not counted.

Given the target terminal rect `x, y, width, height`, the window at step `k` is placed at `x + 28k`, `y + 28k`, with size `width - 28k`, `height - 28k`. The offset is paid for by shrinking, so the window stays entirely inside the target area.

`k` runs 0, 1, 2, 3 and wraps back to 0 at 4. If the shrunk size would fall below the `minSize` that `EditorWindow` supplies (320 x 240), that window uses `k = 0` instead.

When the target terminal area is itself smaller than `minSize` — narrower than 320 or shorter than 240 — the window is placed at `k = 0` and takes the target area's own width and height. It is not widened or heightened to `minSize`. Containment in the target area outranks `minSize`: a window inflated past the edge of its own tile covers the terminal of the neighbouring tile, which is precisely what docking to a tile is meant to leave alone, and a too-small window is a legible inconvenience while a window over someone else's terminal is a defect.

`k` is recomputed on every entry into `docked` — when a window is first opened, and equally when a window returns from `stage` or `floating` by way of the 터미널 채움 control. It is not stored on the window and it is not persisted; the restore path recomputes it from the same rule, which is why the same arrangement reappears after a reload.

Closing a window in the middle of a cascade does not move the windows that remain. The freed step is taken by the next window that enters `docked`.

Ground truth for the shrink: offsetting the position without shrinking necessarily pushes the window past the edge of the target area, and the rule that pulls an out-of-bounds window back sets the offset to zero again, which makes every window coincide exactly. That defeats the whole purpose of the cascade, which is to leave enough of the window behind visible that its title bar can be pressed to bring it forward.

Pitfalls:

- If each window kept the `k` it was given, then window A leaving to `floating`, window B opening with `k = 0`, and A returning to `docked` would put A and B in exactly the same place. Recomputing on entry is what prevents that.
- `WindowDialog` hands `minWidth` and `minHeight` straight to `Rnd` (`WindowDialog.tsx:224-225`), so a controlled rect narrower or shorter than `minSize` does not by itself produce a smaller rendered box: `Rnd` can render the element at the minimum instead, and the window then spills past the target area even though the computation kept it inside. The implementation has to reconcile the two, by lowering the minimum handed to `Rnd` for that window or by an equivalent means. That undersized-target case is the only one where the rendered box can differ from the computed rect, so it is the only criterion judged on measurement — AC-8. Every other containment criterion is judged on the computed rect, which keeps the cascade arithmetic in the unit suite where an error in it surfaces immediately rather than behind a browser.

#### Rationale

Two windows docked on the same terminal must not coincide, because a completely covered window offers no surface to press and the click-to-raise behaviour then has no way to reach it. Offsetting alone is not enough: the window would leave the terminal area, and clamping it back would collapse the offset. Shrinking by the same amount as the offset satisfies both constraints at once.

The count includes hidden and minimized windows because they still hold their place in the cascade; excluding them would hand an occupied step to a new window and make two windows coincide the moment the hidden one reappears.

#### Acceptance Criteria

- [ ] AC-1: Given tab T with target rect (x, y, w, h) and n windows already docked to T where n is 0, 1, 2, or 3, when a further window enters `docked` on T, then its rect is exactly (x + 28n, y + 28n, w - 28n, h - 28n) and that rect is fully contained in (x, y, w, h).
- [ ] AC-2: Given one window already docked to tab T, when a second window is docked to T, then the two rects are not equal: they differ by exactly 28 in x and by exactly 28 in y, and the second is 28 smaller in both width and height.
- [ ] AC-3: Given four windows already docked to tab T, when a fifth is docked to T, then `k` wraps to 0 and the fifth window's rect equals the first window's rect exactly.
- [ ] AC-4: Given a target rect whose own width is at least 320 and whose own height is at least 240, but for which (w - 28k) is below 320 or (h - 28k) is below 240 for the step k that the count would assign, when the window enters `docked`, then it is placed with k = 0 and its rect equals the full target rect.
- [ ] AC-5: Given one minimized window docked to tab T and one window docked to T whose tab is not the active tab, when a new window enters `docked` on T, then it receives k = 2; and given instead one `floating` window and one `stage` window bound to T, then a new window entering `docked` receives k = 0.
- [ ] AC-6: Given window A is docked to T with k = 0, when A moves to `floating`, then B is docked to T and receives k = 0, and then A returns to `docked` through the 터미널 채움 control, then A's recomputed rect differs from B's rect.
- [ ] AC-7: Given three windows docked to T at steps 0, 1, and 2, when the window at step 1 is closed, then the rects of the remaining two windows are unchanged, and the next window to enter `docked` on T is placed at step 1.
- [ ] AC-8: Given a target terminal area whose own width is below 320 or whose own height is below 240, when a window enters `docked` on it, then k is 0 and the window's width and height equal the target area's own width and height. The box actually rendered for that window, measured rather than computed, is not widened to 320 and not heightened to 240, and is fully contained in the target area, so no part of it extends over a neighbouring tile.

### CON-MDE-001 — Editor windows occupy the 3000 z-index band below every modal surface

| Field | Value |
| --- | --- |
| Type | constraint |
| Target | markdown-editor |
| Status | planned |
| Priority | high |
| Tags | markdown-editor, modeless-window, z-index, layering |
| Risk | medium |
| Stability | evolving |
| Verification Method | Frontend unit tests on the z-index formula for both modes, covering the layer cap at `3980` and the surface cap at `3981` as distinct values, and the unchanged modal values, plus the existing `windowDialogContract.test.ts` as a regression pin; Playwright E2E for a `WindowDialog` modal opening above an editor window and rendering the editor non-interactive, and for the command preset toast staying visible above its dialog. |
| GitHub Issue | - |

#### Requirement

Editor windows shall occupy a modeless z-index band whose layer value is `3000 + n * 20`, where `n` is the window's index in the modeless stack, capped at `3980`. The value the window surface itself carries is one greater than the layer value, because `windowDialogModel.ts:29` computes `dialogZ: layerZ + 1` and `WindowDialog.tsx:219` applies `dialogZ` to the `.window-dialog` element. An editor window surface therefore renders at `3001 + n * 20`, capped at `3981`. The two numbers must be kept distinct in every statement about this band: the layer value is what the formula produces, and the surface value is what the DOM receives. The modal band shall not move: `WindowDialog` modals stay in the `5000 + n * 20` layer band, `.command-preset-toast` stays at `5100`, `ConfirmModal` stays at `9999`, and the context menu stays at `10000` with its submenu at `10001`.

Three places change, not two.

1. The input type of `createWindowDialogBehaviorModel` (`windowDialogModel.ts:13-19`) has no `mode` field.
2. The single formula at `windowDialogModel.ts:20`, `const layerZ = 5000 + input.layerIndex * 20;`, gains a branch on `mode` so that modeless starts at `3000` and modal keeps starting at `5000`.
3. `WindowDialog.tsx:40` calls `useDialogStack(dialogId, mode === 'modal')`, which registers modal dialogs only. A modeless window is therefore not in any stack today, and `dialogStack.ts:61` returns the fixed `{ layerIndex: 0 }` whenever the hook is inactive. Left unchanged, every editor window would receive `layerIndex` 0, so every one of them would compute the same layer value `3000` and the same surface value `3001`, and the per-window ordering this constraint specifies could never be observed. That is the single change that makes the band mean anything, and omitting it fails AC-1 outright while the other two changes still look correct in isolation.

The call site (`WindowDialog.tsx:41-47`) also has to pass `mode` into the behaviour model, which is the wiring that carries change 2 into the render. `mode` defaults to `'modal'`, so the number of returned fields does not change.

Measured z-index landscape, which is why `3000` is available: the project uses 2 for the terminal itself (`TerminalRuntimeLayer.tsx:60`), 10 and 12 for tile parts, 100 for `SettingsPage.css:7` and `FontSizeToast.css:13`, 998 to 1000 for mobile-only surfaces, 5000 / 5000 / 5001 as the static CSS defaults in `WindowDialog.css:4`, `:18`, `:24`, the inline computed values that override them (`WindowDialog.tsx:208`, `:214`, `:219`, the last of which receives `layerZ + 1`), 5100 for `.command-preset-toast` (`CommandPresetDialog.css:295`), 9999 for `.modal-overlay` (`Modal/RenameModal.css:11`) and the drag ghosts, and 10000 / 10001 for the context menu (`ContextMenu.css:8`, `:17`). There are zero occurrences of any z-index between 3000 and 5000 in the whole project.

The consequences that the band is chosen for: the six existing dialogs keep their exact z-index values; modals, confirmation popups, and context menus all render above editor windows, so a settings dialog is never covered by an editor; and a context menu opened from inside an editor window appears above that window.

Ground truth for lowering the modeless band rather than raising the modal band: `.command-preset-toast` renders as a sibling outside `WindowDialog` and does not use a portal, so raising the modal band to clear the editor windows would push the dialog above 5100 and hide that toast behind it. Lowering the modeless band leaves every existing value untouched and cannot produce that regression.

Pitfalls:

- Splitting the stack by kind, which the click-to-raise requirement specifies, is a precondition for this band and not an independent concern: without the `useDialogStack` change above there is no modeless stack for `n` to index into.
- `frontend/tests/unit/windowDialogContract.test.ts` pins the entire return value of `createWindowDialogBehaviorModel(...)` with `assert.deepEqual`. Adding an input field without adding a returned field keeps it green; if it goes red, the change introduced an unintended return-value difference and that is the signal, not the test.
- The modal `inert` treatment snapshots `document.body.children` at the modal's mount, and an editor window falls inside that snapshot for a structural reason: `WindowDialog` renders every surface through `createPortal(…, document.body)` (`WindowDialog.tsx:203`), so a window is a direct child of `document.body` rather than a descendant of the stage it is placed over. Editor windows that are already open are therefore covered by the snapshot and made `inert` without any additional wiring. The reverse order cannot occur because the UI is locked while a modal is up, so no new editor window can be opened behind it. If the portal target ever moves off `document.body`, this conclusion moves with it and AC-6 has to be re-derived.

Known constraints accepted here rather than fixed: the font-size toast at z-index 100 hides behind a `docked` editor window covering that tile, and beyond roughly fifty windows the layer value saturates at `3980` so ordering among those windows falls back to mount order and pressing them no longer changes it.

#### Rationale

The modeless band is lowered instead of the modal band being raised because `.command-preset-toast` at 5100 is a sibling of `WindowDialog` rather than a child and does not go through a portal; any increase to the modal band would place a dialog above it and hide the toast. Choosing 3000 keeps all six existing dialog call sites numerically unchanged, so the change carries no z-index regression at all, and the 3000 to 5000 range is provably free across the project.

The settings screen at z-index 100 is not a conflict because the visibility rule already hides editor windows outside the workspace screen, and the mobile surfaces near 1000 are outside the scope of this feature.

### CON-MDE-002 — Editor windows bind to a tab, not to a session

| Field | Value |
| --- | --- |
| Type | constraint |
| Target | markdown-editor |
| Status | planned |
| Priority | high |
| Tags | markdown-editor, modeless-window, tab-binding, session-lifecycle |
| Risk | medium |
| Stability | evolving |
| Verification Method | Frontend unit tests for the persisted record shape and for the tab-to-session resolution at call time; Playwright E2E for a tab restart leaving the window alive and saving through the new session, for a closed tab dropping its window to `floating` with saving disabled, and for the distinct close prompt in that state. |
| GitHub Issue | - |
| Related Docs | docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md |

#### Requirement

An editor window shall hold a `tabId` and shall never hold a session ID. The session ID is fetched again from that tab at the moment a file API call is made, and it is not persisted.

The facts that force this. `WorkspaceTab` carries `id` and `sessionId` as separate fields alongside `currentSessionId` and `previousSessionIds` (`frontend/src/types/workspace.ts:14-20`), and the identifier is `id`. `restartTab` keeps `tab.id` and swaps `tab.sessionId` for a new session (`server/src/services/WorkspaceService.ts:759`, `:778`), so a session ID is not stable across the life of a tab. Beyond that, the registry that supplies the `docked` rect is keyed by tab ID through `upsertHost(tabId, hostId, rect, isVisible, extras)` (`TerminalHostSlot.tsx:42-59`), and the visibility decision for a tab wrapper is `const isVisible = isActiveWs && isActiveTab;` at `App.tsx:665`, which conjoins `tab.workspaceId === wm.activeWorkspaceId` (`:663`) with `ws?.activeTabId === tab.id` (`:664`). A window bound to a session ID could not look its rect up at all, and its binding would break silently after a tab restart.

Resolution path: `useWorkspaceManager` exposes `tabs` as a flat array covering every workspace, so the lookup is `wm.tabs.find(t => t.id === tabId)?.sessionId`. That hook is called at exactly one place (`App.tsx:128`) and has no context provider, so the lookup function is passed down from `AppContent` to the window manager as a prop. No new context is introduced for this.

Behaviour when the binding degrades:

- Tab restarted, session replaced — the window stays exactly as it is and the next save goes to the new session.
- Tab alive but session disconnected — the window is left in place and a save is still attempted. Failure is shown as an error; the window is not dropped to `floating`. Closing it uses the ordinary unsaved-changes prompt.
- Tab closed — the window drops to `floating` and loses its save path. Its rect starts from the viewport rectangle it occupied immediately before the close, because the target terminal area is gone and there is nothing left to recompute `docked` from, and the `floating` clamping rule specified by FR-MDE-001 is then applied to that inherited rect. Where the inherited rect and the clamp disagree, the clamp wins. A badge next to the file name in the title bar states the condition, and the save button and Ctrl+S are disabled.
- Closing a window whose tab was closed — the prompt is "저장할 수 없습니다. 그래도 닫으시겠습니까?", a different branch from the ordinary unsaved-changes prompt.
- Restoring persisted state that names a tab that no longer exists — that window is not restored.

Why the clamp beats the inherited coordinates. Closing a tab can change the stage boundary itself: closing the last tab removes the tab bar, so the stage the clamp measures against is not the stage that was in force when the rect was captured. An inherited rect honoured literally can therefore land partly or wholly outside the stage, and a window whose title bar is off screen offers no surface to press and no way to be dragged back. Requiring the exact pre-close rect and requiring containment in the stage are two rules that can disagree, and this requirement resolves that disagreement in favour of containment.

`documentId` is the normalized absolute file path, never the session ID. A session ID there would change on tab restart, and by the editor's document-identity contract the `EditorView` would be destroyed and recreated, taking the unsaved body with it.

Canonical sources. This requirement is the canonical source for what happens when the bound tab closes: the drop to `floating`, the clamped inherited rect, the disabled save path, and the separate 저장할 수 없습니다 close prompt. FR-MDE-006 restates those inside its close-branch table and judges on top of them, so a change to any of them is made here first. In the other direction, the document-identity contract — that `documentId` is the normalized absolute path, so a tab restart leaves it unchanged and the `EditorView` alive — is stated definitively in FR-MDE-005, and the statement here follows it.

Pitfall: the window survives a tab restart only if nothing in its identity derives from the session. That includes the persisted record, the `documentId`, and the `docked` rect lookup key.

#### Rationale

The session ID is not a stable identifier: `restartTab` replaces it while keeping the tab. Binding a window to it would break the rect lookup, which is keyed by tab ID, and would silently sever the window from its tab after a restart, with no visible failure until a save went to the wrong place or nowhere.

The session ID is still required for the file API, so it is resolved at call time rather than stored. That is the only arrangement in which a tab restart is invisible to the user and the next save still reaches the right session.

#### Acceptance Criteria

- [ ] AC-1: Given a window bound to tab T with unsaved edits, when T restarts so that `tab.id` is unchanged and `tab.sessionId` is replaced, then the window is still open with the same editor instance and the same unsaved body, and the next save call carries the new session ID rather than the old one.
- [ ] AC-2: Given any persisted editor window record, then it contains the tab ID and contains no session ID field; and given a stored record produced before a tab restart, then restoring it after the restart still resolves a session ID through the tab.
- [ ] AC-3: Given the session of tab T is disconnected while T itself still exists, then a window bound to T keeps its current placement state rather than dropping to `floating`, and a save attempt is issued; on failure the window stays dirty and shows the error in its own banner.
- [ ] AC-4: Given a window docked to tab T, when T is closed, then the window's placement state becomes `floating` and both the save control and Ctrl+S are disabled; and its rect is the viewport rectangle it occupied immediately before the close with the `floating` clamping rule applied to it. Given that inherited rectangle already lies fully inside the stage as measured after the close, then the resulting rect equals the inherited one exactly. Given instead that T was the last tab, so closing it removed the tab bar and the inherited rectangle would now extend outside the stage, then the resulting rect is fully contained in the post-close stage and differs from the inherited one: the clamp wins over the inherited coordinates.
- [ ] AC-5: Given a window with unsaved content whose tab has been closed, when the user closes the window, then the prompt shown is the 저장할 수 없습니다 branch and not the ordinary save prompt, and choosing to close discards the body without attempting a write.
- [ ] AC-6: Given persisted state containing two windows, one naming a tab that exists at restore time and one naming a tab that does not, then only the first is restored and the second is dropped.
- [ ] AC-7: Given a window bound to tab T, then its `documentId` equals the normalized absolute file path; and when T restarts, then `documentId` is unchanged and the `EditorView` instance is the same object as before the restart. The canonical statement of this obligation is FR-MDE-005; this criterion judges the tab binding on top of it.

#### Requirement

The DocuLight2.0 editor package shall be ported into this repository as source under `frontend/src/editor/`, keeping the directory structure of `packages/editor/src`, and the host code that mounts it shall honour the two contracts the editor enforces at mount time.

Port scope and provenance:

- The copied tree is 27 files / 7,333 lines: 25 `.ts`/`.tsx` under `src/` (the 10 files under `__tests__/` are excluded from that count) plus 2 CSS files.
- The editor is CodeMirror 6 based, and `src/vendor/atomic-editor/` is an MIT vendored copy of `kenforthewin/atomic-editor` v0.6.2. `vendor/atomic-editor/LICENSE` is an MIT notice obligation and must be kept in the ported tree.
- The copy source is DocuLight's current state of the vendor directory, not upstream v0.6.2. Since the introduction commit `fc4ded1`, DocuLight changed that directory in 7 commits (5 touching source, 2 test-only). The net increment against the introduction point is `table-widget.ts` +210/-16 and `inline-preview.ts` +22/-1, plus a new test file `__tests__/table-reveal-state.test.ts` (+209 lines, 8 cases).
- The editor package's `"main"` is `./src/index.ts`, so the package publishes source rather than a build artifact. That is why the port is a source copy and not a dependency.

How the port is judged. The counts above are the record, and completeness is verified against them inside this repository: the ported tree's own file count, its line count, the presence of the MIT `LICENSE`, and the entry barrel's exported surface. No criterion reads the DocuLight checkout. That checkout is a developer's local working copy at a path that exists on one machine, so a recursive comparison against it cannot be run in CI or reproduced by anyone else, and a criterion that cannot be run is not a criterion. The DocuLight commit hashes recorded above stay in the text as provenance, which is what they are good for; they are not the pass condition.

Where each contract is verified. The static checks above are unit tests. The two mount-time contracts below are Playwright E2E, because they can only be observed on a mounted editor and this repository's frontend unit suite has no DOM.

The two mount-time contracts:

1. `markdownSource` is not a controlled value. It is read once at mount and from then on the editor is the document's source of truth. The host must not feed the value back on every keystroke.
2. Document replacement goes through the `documentId` prop. When `documentId` is omitted, the `markdownSource` string itself becomes the document's identity, so every save response that returns a new body destroys and recreates the EditorView, losing focus and in-flight input. DocuLight's commit `f54ee4e fix(web): 저장이 편집기를 갈아 끼우지 않게 한다` is the evidence for this contract.

This requirement is the canonical source for both contracts and for their consequence that `documentId` is unchanged across a tab restart so the `EditorView` survives it. FR-MDE-002 and CON-MDE-002 restate them as premises for the hiding rule and the tab binding respectively and judge on top of them; a change to either contract is made here first, and those restatements follow.

The `extensions` array is likewise captured at mount, so its reference shall be pinned with `useMemo`. `readOnly` alone is `Compartment` based and may be toggled without a remount.

`EditorWindow` shall pass the normalized absolute file path as `documentId`. One window corresponds to one file, so that path is the document's identity. Passing the session ID instead would change the value on a tab restart, destroying and recreating the editor and losing the unsaved body.

- Add `@codemirror/*`, `@lezer/*`, `katex`, `shiki`.
- Raise `mermaid` from `^10.9.5` to `^11.4.1`. The editor requires `^11.4.1` and `^10.9.5` does not satisfy it, so this is a major upgrade. `mermaid` has no use site in this project today, so the blast radius of the upgrade is confined to the editor.

Build tooling stays the host's. The editor's devDependencies are `vite ^8.1.4` and `typescript ^7.0.2` while BuilderGate is on `vite ^7.2.4` and `typescript ~5.9.3`. A source copy does not drag the devDependencies along, but the TypeScript version gap can surface as compile errors, so `tsc` shall be made to pass immediately after the port and before any host wiring is added. The editor package declares no `peerDependencies` and holds React in `dependencies`; because the port copies source, no duplicate React is loaded.

- Coupling is zero: searching `packages/editor/src` for `fetch(`, `/api/`, `useContext`, `localStorage` and `react-router` returns 0 hits, and the standalone demo at `packages/editor/demo/` proves the editor runs with no surrounding application. The whole external surface is the 5 optional callbacks of `doculightExtensions`: `onTagClick`, `onAttach`, `suggestWikiLinks`, `onOpenWikiLink`, `resolveWikiLink`. Leaving them unpassed leaves attachment upload and wiki links inert, which is the intended state for this scope.

Pitfalls:

- The frontend unit suite cannot mount this editor, so the two contracts above cannot be asserted there. `frontend/package.json` declares no `jsdom`, no `happy-dom`, no `@testing-library/*` and no `react-test-renderer`, and none of the 76 tests under `frontend/tests/unit/` renders a React component — they are pure module tests and `readFileSync` source-text contract tests. Writing the contract tests as unit tests means introducing a DOM harness first, and that harness is outside this scope.

Commit subjects do not identify the patches either: `be66168` carries a `docs(spec):` prefix while actually changing `table-widget.ts`.
- Saving is not part of the port. The editor package contains no save logic at all; in DocuLight it lives in `packages/web/src/document/` (`DocumentSurface.tsx`, `useAutosave.ts`, `autosave.ts`). This scope supplies its own save path instead.
- The editor's CodeMirror keymap registers no `Ctrl+S` (`Mod-s`), so the host may bind that combination for saving without taking a binding away from the editor.
- Contract 1 is what forces minimize to hide rather than unmount: unmounting drops the edited body, and remounting restarts from whatever `markdownSource` was handed in.

#### Rationale

The port is a source copy rather than a dependency because the package exposes `./src/index.ts` as its `main`, so there is no build artifact to depend on. The copy is taken from DocuLight's current vendor state rather than upstream v0.6.2 because seven DocuLight commits changed that directory and the record of those patches in `UPSTREAM.md` was never updated, so reconstructing them from upstream plus a patch list is not possible.

`documentId` is the normalized absolute path rather than the session ID because a tab restart replaces the session ID while keeping the tab and the file, and the editor treats a changed `documentId` as a different document — the editor would be recreated and the unsaved body lost on every restart.

The two contracts are recorded as requirements rather than left as implementation detail because both fail silently and late: feeding `markdownSource` back on each keystroke produces cursor jumps that look like an input-latency problem, and omitting `documentId` only misbehaves once a save round trip returns a body, which is well after the component appears to work.

| Field | Value |
| --- | --- |
| Type | interface |

| GitHub Issue | - |
| Related Docs | docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md |

#### Requirement

The server shall expose `POST /api/sessions/:id/files/write` for writing a file inside a session's working directory, and the frontend shall reach it through a new `fileApi.writeFile(sessionId, path, content)`.

Measured absence this requirement fills:

- The server has no write path at all today. `FileService.ts` publishes `getCwd`, `listDirectory`, `readFile`, `copyFile`, `moveFile`, `deleteFile`, `createDirectory`, `getDiskFreeSpace` and `updateConfig`, and no `writeFile` family exists.
- `fileRoutes.ts` registers exactly 7 routes and none of them writes file content: `GET /:id/cwd`, `GET /:id/files`, `GET /:id/files/read`, `POST /:id/files/copy`, `POST /:id/files/move`, `DELETE /:id/files`, and `POST /:id/files/mkdir`.
- `fileApi` in `frontend/src/services/api.ts` exposes exactly 7 functions and every one of them takes `sessionId` as its first argument: `getCwd`, `listDirectory`, `readFile`, `copyFile`, `moveFile`, `deleteFile`, `createDirectory`. The new `writeFile` keeps that shape so the call site reads the same as every other file call.

Validation, in the same sequence the read path already uses:

1. `assertSessionExists(sessionId)` rejects a request naming a session that does not exist.
2. `resolveAndValidate(cwd, filePath, blockedPaths)` rejects directory escape and blocked paths.
3. `isBlockedExtension` rejects blocked extensions.

The read path is the precedent: `FileService.ts:213` calls `this.assertSessionExists(sessionId)` as its first statement, `:215` obtains the cwd, `:216` calls `resolveAndValidate`, and `:219` calls `isBlockedExtension`. The write path performs the same three stages in the same order and does not invent a fourth check. The session check is a precondition of the other two rather than an extra: the cwd is obtained from the session, so without it there is no well-defined subtree for `resolveAndValidate` to bound the path against, and a write naming an unknown session would be answered by whatever `getCwd` happened to do.

Request and response:

- Body is `{ path, content }`.
- A file that does not exist is created; a file that exists is overwritten in full.
- Encoding is UTF-8 and no BOM is written.
- Line endings are written exactly as the editor emitted them, with no normalization in either direction.
- Reach is confined to the session's cwd subtree; nothing above it is writable.
- A validation failure is answered with an error response and no bytes are written anywhere.

Pitfalls the implementer will hit:

- `resolveAndValidate` (`server/src/utils/pathValidator.ts:49-75`) performs `validatePath` and `isPathBlocked` but never looks at the extension, so omitting the third stage silently permits every blocked extension on the write path while the read path still blocks it.
- `resolveAndValidate` returns the resolved path unchanged when the target does not exist (ENOENT, `:70-71`). That is what makes it usable for creating a new file, so the implementer must not add an existence precondition in front of it.
- Symbolic links are resolved here on the server (`pathValidator.ts:61-67`) and nowhere on the frontend. The duplicate-window key on the frontend therefore stops at normalization, which is recorded as a known limitation on the context menu requirement.
- Overwriting must truncate. Writing without truncation leaves the tail of a longer previous body behind, which looks like a save that partly failed.
- A rejection test that only asserts an error and an absent file is satisfied by an endpoint that rejects everything, including every legitimate write. Each rejection criterion therefore carries a control in the same test: one legal write that must succeed. Without the control, a route that is broken outright and a route that validates correctly are indistinguishable, and the suite goes green on the broken one.

#### Rationale

The write path copies the read path's two-stage validation rather than defining its own because the two stages have different jobs and neither subsumes the other: `resolveAndValidate` bounds the path and `isBlockedExtension` bounds the file type. A write path that validated only the path would be strictly weaker than the read path that already exists, which is the wrong direction for the first endpoint in this codebase that modifies file content.

Conflict detection on save is deliberately absent (design §3): the save overwrites. Detecting an external change would require a confirmation UI and a version token in the read response, which is a scope expansion beyond what was asked. The consequence is that two windows on the same file silently overwrite each other, and that is precisely why the window layer keys duplicates by resolved absolute path rather than by tab.

`writeFile` takes `sessionId` first because all seven existing `fileApi` functions do; a different argument order in the only mutating call would be the one place a caller could get wrong without a type error, since `sessionId` and `path` are both strings.

#### Acceptance Criteria

- [ ] AC-1: Given a session whose cwd is C, when a write is requested for a relative path inside C with content S, then the response is a success, the file's bytes decode from UTF-8 to exactly S, and the first three bytes are not the UTF-8 BOM.
- [ ] AC-2: Given content whose text mixes CRLF and LF line endings, when it is written and read back as bytes, then the bytes are identical to the bytes of the submitted content, with no line ending added, removed or converted.
- [ ] AC-3: Given a path that escapes the session cwd (for example a parent-directory traversal, or an absolute path outside C), when a write is requested, then the response is an error, no file is created at the escaped location, and a control write to a legal path inside C in the same test succeeds.
- [ ] AC-4: Given a path whose extension is in the blocked extension list, when a write is requested, then the response is an error and no file is created; and in the same test the identical content written to a `.md` path inside C succeeds.

### FR-MDE-006 — Unsaved changes marker and save through both Ctrl+S and the title bar button

| Field | Value |
| --- | --- |
| Type | functional |
| Target | markdown-editor |
| Status | planned |
| Priority | high |
| Tags | markdown-editor, save, dirty, keyboard, close-confirmation |
| Risk | high |
| Stability | evolving |
| Verification Method | Frontend unit tests (`frontend/tests/unit/`, node:test) for the dirty transitions, the focus-scoped `Ctrl+S` gate and the close branch table; Playwright E2E for typing marking the title with `*`, `Ctrl+S` and the title bar button each clearing it, and the save error banner appearing inside the window. |
| GitHub Issue | - |
| Related Docs | docs/plan/2026-09-01.markdown-editor-modeless-windows.design.md |

#### Requirement

An editor window shall mark unsaved changes with a leading `*` on its title, shall save through both the title bar save button and `Ctrl+S`, and shall branch its close behaviour on whether the document is dirty and whether saving is still possible.

Source of truth for the body. The body lives in exactly one ref and never in React state as well. Because the editor does not treat `markdownSource` as a controlled value, a second copy would leave no basis for deciding which of the two is current. The editor's change callback updates that ref and sets `dirty` to true; the `*` reaches the title through the optional `dirty` prop added to `WindowDialog`.

Save. Both entry points call the same save function; there is no second save path. At call time the function re-obtains the session ID from the bound tab rather than using a stored one, because a tab restart replaces `sessionId` while keeping the tab. On success `dirty` becomes false and the `*` disappears. On failure `dirty` stays true and an error banner appears under that window's title bar; the failure is never reported through a modal, so the user can keep editing and retry.

`Ctrl+S` fires only while DOM focus is inside that window. Being topmost in the modeless stack is deliberately not the condition: a window just restored from the tray is frontmost but may hold no focus, and saving on that basis would write a file the user was not looking at while some other window held the text they were editing. The handler calls `preventDefault()` to suppress the browser's own save dialog. The editor's CodeMirror keymap registers no `Ctrl+S` (`Mod-s`), so nothing is taken away from the editor, and while the terminal holds focus the existing xterm handling must be left untouched.

Reading errors. A read failure that happens before any window exists is reported through the existing `MessageBox`, because there is no window in which to draw a banner. Once a window exists, every read and write failure is that window's banner.

Close branches:

- Dirty and saving is possible — ask "저장하시겠습니까?" with save, don't save, and cancel. Save that succeeds closes the window; save that fails leaves the window open with the error shown; don't save closes; cancel leaves the window open with `dirty` intact.
- Dirty and saving is impossible because the bound tab has closed — ask "저장할 수 없습니다. 그래도 닫으시겠습니까?". This is a different prompt from the one above, not the same prompt with a disabled button.
- Not dirty — close with no prompt.

Tab states:

- Tab closed. The window drops to `floating` and loses its save path. Its rect starts from the viewport rect it occupied at that moment and then has the `floating` clamping rule of FR-MDE-001 applied to it; where the inherited rect and the clamp disagree, the clamp wins, because closing the last tab removes the tab bar and moves the stage boundary, and a window pushed outside the stage has no title bar left to press and no way back. The save button and `Ctrl+S` are disabled and a badge beside the file name in the title bar says so. The unsaved body stays on screen and cannot be written anywhere.
- Session gone but tab alive (awaiting restart). The window is left alone and a save is still attempted. A failure only produces the banner; the window is not dropped to `floating` and the ordinary unsaved-close confirmation applies.
- Tab restarted. The window survives and the next save goes to the new session.

Canonical source. The tab-closed behaviour — the drop to `floating`, the clamped inherited rect, the disabled save path, and the separate 저장할 수 없습니다 close prompt — is stated definitively in CON-MDE-002. This requirement restates it as one branch of its close table and judges the save flow on top of it; when that behaviour changes, CON-MDE-002 is the requirement to change and this restatement follows it.

Pitfalls:

- Feeding the saved body back into `markdownSource` after a successful save recreates the EditorView and loses focus unless `documentId` is held constant; the port requirement fixes `documentId` to the absolute path for exactly this reason. The save response is not written back into the editor at all.
- Gating `Ctrl+S` on stack order instead of focus produces a bug that only appears after a tray restore, which is late and hard to attribute.
- The confirmation prompt used here is `ConfirmModal`, which applies no `inert`; that is acceptable because the choice is made before anything else can be interacted with, but it means the prompt is not a modal lock and must not be relied upon as one.

#### Rationale

Focus rather than stack position gates `Ctrl+S` because the two disagree exactly in the case the tray creates: the restored window is frontmost while the keyboard still belongs elsewhere. Choosing stack position would save the wrong file with no visible cue that anything unexpected happened, and the file it overwrites is one the user believed they were not touching.

Save failures use an in-window banner rather than a modal because the document is still dirty and still editable; a modal would block the very retry it is announcing. Read failures before a window exists have no banner to live in, so they use the existing `MessageBox` instead of introducing a second error surface.

The close prompt for a closed tab is a separate prompt rather than the ordinary one with the save option greyed out, because the two questions differ: the ordinary one asks whether to save, and this one states that saving is impossible and asks whether to discard.

- [ ] AC-1: Given a window whose document has just been read from disk, then its title carries no `*`; when the user types into the editor, then the title carries a leading `*` and the body ref holds the typed text.
- [ ] AC-2: Given window A holds DOM focus and window B is dirty and frontmost in the modeless stack, when `Ctrl+S` is pressed, then exactly one write is issued and its path is A's file; no write is issued for B's file.
- [ ] AC-3: Given DOM focus is outside every editor window, when `Ctrl+S` is pressed, then no write is issued; and in the same test, when focus is then moved inside a window and `Ctrl+S` is pressed again, then exactly one write is issued.
- [ ] AC-4: Given DOM focus is inside an editor window, when `Ctrl+S` is pressed, then `preventDefault()` is called on that keyboard event.

#### Requirement

Right-clicking the working directory path shown at the bottom of a session shall open a context menu offering `CLAUDE.md`, `CLAUDE.local.md` and `AGENTS.md`, and choosing one shall open an editor window on that file resolved against the displayed path.

Attachment point. `onContextMenu` is added to `.metadata-cwd-path` in `MetadataRow.tsx` (`:151-176`), and the existing `onClick={handleCopy}` stays. `<MetadataRow>` has two render sites — tab mode at `App.tsx:701-704` and grid mode at `Grid/MosaicTile.tsx:116-119` — so both view modes must get the behaviour. The path value comes from `props.tab.cwd`, which is what the user sees, so what opens matches what is displayed.

File names use the uppercase spelling exactly as written, because those are the names the tools actually read.

Flow when an item is chosen:

- Resolve the file path against the row's `cwd`.
- If a window is already open on the resolved absolute path, do not create a second one: revive that window and raise it, and stop.
- Otherwise read the file with `fileApi.readFile(tab.sessionId, path)`.
- On success, open a window bound to that `tabId` in `docked`.
- On a 404, ask through the existing `ConfirmModal` whether to create the file; on confirmation write an empty file and then open the window; on cancellation write nothing and open nothing.
- On any other read failure, show `MessageBox` and open no window.

The duplicate key is the normalized absolute path, not the pair of tab ID and path. Two tabs can share a `cwd`; keyed by the pair, each would open its own `CLAUDE.md` window onto the same file on disk, and since conflict detection is deliberately absent the two windows would silently overwrite each other's saves. `tab.cwd` is absolute, so joining it with the file name and normalizing yields the key. A window already holding that file is revived even when it is bound to a different tab, so a window stays bound to the tab that first opened it.

This context menu is the only user-facing action that creates a window. Restoring windows after a page reload is a reconstruction of stored state, not a user action, and is specified separately.

Measured facts:

- `ContextMenu.tsx` takes exactly four props — `position`, `items`, `onClose` and `restoreFocusElement?` — and knows nothing about sessions or tabs, so adding items requires no change to it. Multi-level navigation, viewport clamping and mobile behaviour live in separate modules and stay untouched.
- The path element currently carries `onClick={handleCopy}` and no `onContextMenu` at all.
- Symbolic links are resolved only on the server (`server/src/utils/pathValidator.ts:61-67`), so the frontend key stops at normalization.

Pitfalls:

- Item assembly belongs in a new builder function. Extending the existing `frontend/src/utils/contextMenuBuilder.ts` would entangle this work with the `FR-ARCH-004` through `FR-ARCH-006` contracts, which are `Stability=stable`.
- No submenu is introduced, so `FR-ARCH-001`'s depth limit of 5 is not approached.
- `ConfirmModal` applies no `inert`, which is harmless here only because no editor window for that file exists yet at the moment the question is asked.
- Adding the handler at one render site and not the other leaves the feature missing in whichever view mode the developer was not testing, and both sites render the same component so the omission is invisible in the component itself.

#### Rationale

The duplicate key is the resolved absolute path rather than the tab-and-path pair because the decision not to detect save conflicts makes two windows on one file actively harmful rather than merely redundant: whichever saves last wins and the other's work disappears with no message. Two tabs sharing a `cwd` is ordinary in this product, so the pair key would produce that situation routinely, not rarely.

Reviving a window bound to a different tab, rather than opening a new one bound to the current tab, follows from the same key: there can be only one window per file, so it stays where it was first created. The alternative — rebinding the existing window to the tab the user just right-clicked — would silently move the window out from under whatever tab it was docked to.

A separate builder function is used instead of extending `contextMenuBuilder.ts` because that module is covered by stable architecture requirements; keeping the new items out of it means this work cannot regress those contracts and does not need to be reviewed against them.

#### Requirement

The header shall carry an editor tray icon that lists every editor window belonging to the current workspace, and choosing a list entry shall make that window visible and bring it to the front.

Placement. The icon goes inside `header-right` (`Header.tsx:110-182`), immediately to the left of the view mode toggle. The stated requirement asks for it "to the left of the hamburger button", but the real `.hamburger-button` is mobile-only and lives in `header-left`; what actually occupies the top right on desktop is the view mode toggle (`☰`/`⊞`), rendered under `onToggleViewMode && !isMobile`. When that toggle is not rendered, the icon takes the first slot of `header-right` instead.

Visibility of the icon. It renders only while the current workspace holds at least one editor window, which is the same scope the list uses, so the icon can never appear above an empty list. That condition belongs to the icon itself.

The list. Pressing the icon opens the existing `ContextMenu` with one entry per window of the current workspace, regardless of whether the window is minimized, and an entry for a document with unsaved changes carries `*`. Windows belonging to other workspaces are not listed.

Revival. Choosing an entry resolves every visibility condition that can be resolved and then raises the window: clear `minimized`; if the settings screen is showing, return to the workspace screen; and in tab mode, if the window's bound tab is not the active tab, switch to it. Clearing `minimized` alone leaves the window blocked by the remaining conditions and nothing changes on screen, which reads as a dead menu item.

After a tab switch, the `docked` rect must not be applied until the registry actually reports a usable terminal area for that tab, which is the judgement `host?.isVisible && host.rect.width > 0 && host.rect.height > 0` that `TerminalRuntimeLayer.tsx:51` already makes. Until that judgement turns true the window stays hidden and no rect is applied, because laying a window out on an area of zero size would give the window zero size.

Canonical source: the deferred `docked` measurement is stated definitively in FR-MDE-009, which owns restoration and the deferral rule. This requirement restates it only as the tail of the tray revival sequence and judges on top of it; when the deferral rule changes, FR-MDE-009 is the requirement to change and this restatement follows it.

The list is not exclusive. The requirement's phrase "선택하여 이것만 출력 가능합니다" is read as reviving the chosen one among several minimized documents, not as hiding every other window. The sentence that immediately follows it in the requirement says multiple editor windows may be up at once, so an exclusive reading contradicts the source.

Pitfalls:

- The frontend unit suite has no DOM environment. `frontend/package.json` declares no `jsdom`, no `happy-dom`, no `@testing-library/*` and no `react-test-renderer`, and none of the 76 tests under `frontend/tests/unit/` renders a component — they are pure module tests and `readFileSync` source-text contract tests. AC-3 asserts a sibling position inside `header-right` and AC-8 reads the registry entry a tab actually produces at runtime, so both are assigned to Playwright E2E, which already runs a real browser; the icon condition, the workspace scoping and the revival sequence are pure logic and stay in the unit suite. Writing the DOM ones as unit tests means building a harness first, and that harness is outside this scope.
- `Header.tsx:110`'s outer condition is "at least one callback exists", and `App.tsx:584-587` passes callbacks unconditionally, so that condition is always true. Adding another callback there changes nothing about what is shown or hidden, and an implementer who wires visibility through it will find the icon always present.
- The deferral must never be written as a comparison of the registered rect against `{0,0,0,0}`. Two measured facts make that literal unreachable in production. First, the registered coordinates are stage-relative — `hostRect.left - rootRect.left` at `TerminalHostSlot.tsx:46-47` — so a hidden slot, whose own `getBoundingClientRect()` returns zeros, reports a `left` that is negative by the stage's left offset (the sidebar width in the desktop layout); only `width` and `height` fall to zero. Second, when a slot unmounts, `removeHost` deletes the entry with `next.delete(tabId)` (`TerminalRuntimeContext.tsx:123`), so the lookup returns `undefined` and there is no rect left to compare. A `{0,0,0,0}` condition would therefore never be true at runtime, and only a test that wrote that literal into the registry by hand would pass — a green that says nothing about the tray. Read `isVisible`, which `upsertHost(tabId, hostId, rect, isVisible, extras)` registers as a dedicated fourth argument (`TerminalRuntimeContext.tsx:43-49`), together with the two positive size checks.
- The tray shows windows of the current workspace only. A tray entry that also switched workspaces would move the user somewhere they did not ask to go, so a window in another workspace simply is not offered.
- A window revived from the tray is frontmost but does not necessarily hold DOM focus, which is exactly why the save shortcut is gated on focus rather than on stack position.

#### Rationale

The icon's own condition governs its visibility rather than the header's existing callback-presence condition because that condition is always true in production, so routing through it would produce an icon that is permanently visible — including when there is nothing to list.

The list is scoped to the current workspace because the alternative is a tray entry whose effect is a workspace switch. Making an entry visible would require moving the user out of the workspace they are looking at, and nothing in the tray's appearance suggests that.

Revival resolves all resolvable conditions rather than only `minimized` because the visibility rule is a conjunction: with a hidden tab or the settings screen showing, clearing `minimized` alone produces no visible effect at all, and the user has no way to tell whether the click registered.

#### Requirement

Editor window placement shall be persisted per workspace under the key `window_state_<workspaceId>` and restored after a page reload, and no document body shall ever be written to that store.

Structure. `frontend/src/hooks/windowStateStorage.ts` owns the serialization and the storage key, and `useWindowState(workspaceId)` wraps it. That is the same split the project already uses for the mosaic layout: `mosaicLayoutStorage.ts` holds the `mosaic_layout_<workspaceId>` key and `useMosaicLayout.ts` wraps it.

What is stored, per window: the tab ID, the file path, the placement state, the placement recorded before entering `stage`, the `minimized` flag, the `floating` rect, and the stack order.

What is deliberately not stored:

- The document body. Restoration re-reads the file from disk. Keeping an unsaved body across a reload would create a conflict question against whatever the file on disk now contains, and detecting that conflict is out of scope.
- The cascade step. Restoring windows in stack order lets the `docked` entry rule recompute it, which reproduces the same layout without a second copy of the number that could disagree with the rule.
- The session ID. A tab restart replaces it, so a stored value would be stale; it is re-obtained from the tab whenever an API call needs it.
- The `docked` and `stage` rects. Both are measured every time from the terminal rect registry and the stage container.

Restoration:

- A stored window whose tab no longer exists is not restored at all.
- A `docked` window's rect measurement is deferred until the registry reports a usable terminal area for its tab. That judgement is the one `TerminalRuntimeLayer.tsx:51` already makes, `Boolean(host?.isVisible && host.rect.width > 0 && host.rect.height > 0)`, where `isVisible` is the dedicated fourth argument of `upsertHost(tabId, hostId, rect, isVisible, extras)` (`TerminalRuntimeContext.tsx:43-49`) and is carried separately from the rect. Until it turns true the window stays hidden and no rect is applied, because laying the window out on an area of zero size would give the window zero size. This requirement is the canonical statement of that deferral rule; FR-MDE-008 restates it for the tray revival path and judges on top of it.
- Stack order is restored only among the windows of the current workspace. The stack itself is global while the store is per workspace, so restored windows take the stored order relative to one another and windows of other workspaces keep the positions they already hold.

Workspace switching does not unmount windows; the visibility rule merely hides them, so returning to a workspace finds the unsaved body still there. This store therefore serves only the reconstruction after a page reload. Body preservation while the page lives belongs to runtime memory; this store holds placement and nothing else.

`floating` coordinates have exactly one source of truth, which is this store. `persistGeometry={false}` is passed to `WindowDialog` so its own `writeDialogGeometry` path never produces a second copy.

Pitfalls:

- The frontend unit suite has no DOM environment. `frontend/package.json` declares no `jsdom`, no `happy-dom`, no `@testing-library/*` and no `react-test-renderer`, and none of the 76 tests under `frontend/tests/unit/` renders a component — they are pure module tests and `readFileSync` source-text contract tests. The serializer criteria sit there comfortably, but AC-4 needs the registry state an inactive tab actually produces at runtime and AC-6 asserts that the editor instance is the same object after a workspace round trip, so both are assigned to Playwright E2E, which already runs a real browser. Writing them as unit tests means building a DOM harness first, and that harness is outside this scope.
- The deferral must never be expressed as a comparison of the registered rect against `{0,0,0,0}`, and two measured facts are why that literal is unreachable. First, the registered coordinates are stage-relative — `hostRect.left - rootRect.left` at `TerminalHostSlot.tsx:46-47` — so an inactive tab's slot, whose own `getBoundingClientRect()` returns zeros, reports a `left` that is negative by the stage's left offset (the sidebar width in the desktop layout); only `width` and `height` fall to zero. Second, when a slot unmounts, `removeHost` deletes the entry with `next.delete(tabId)` (`TerminalRuntimeContext.tsx:123`), so the lookup returns `undefined` and there is no rect left to compare at all. A `{0,0,0,0}` condition therefore never becomes true in production, and the only thing that would satisfy it is a test writing that literal into the registry by hand — a green that proves nothing about restoration.
- `persistGeometry={false}` stops the write but not the read: `readDialogGeometry` runs on every mount regardless of that prop, so a value left in `buildergate.dialog.<id>.geometry` by any earlier code path would still become the initial state unless a controlled `rect` is supplied from the first render.
- Persisting the cascade step and then restoring it would defeat the recomputation rule, so two windows that were staggered before the reload could come back exactly on top of each other once one of them had moved.
- Restoring windows out of stack order changes which one the cascade rule counts first, so the restored layout would differ from the one that was saved even though every stored field was honoured.

#### Rationale

The body is excluded from the store because storing it converts every reload into a three-way question between the stored body, the file on disk, and what the user remembers writing — and conflict detection is explicitly out of scope. Excluding it makes the reload behaviour simple to state: placement returns, content comes from disk.

The cascade step is excluded rather than stored because it is derivable, and a stored derivable value is a second source of truth that only ever disagrees with the rule. The rule already recomputes the step on every entry into `docked`, so restoring in stack order reproduces the layout for free.

The store is scoped per workspace, following the mosaic layout precedent, because window placement is meaningful only against a workspace's tabs; a global store would carry entries whose tab IDs mean nothing in the workspace being restored.

#### Acceptance Criteria

- [ ] AC-1: Given a workspace holding two windows whose editors contain the unsaved text U1 and U2, when the state is serialized, then the value written under `window_state_<workspaceId>` contains exactly two window entries, each carrying a tab ID, a file path, a placement state, a `minimized` flag and a stack position, and neither U1 nor U2 appears anywhere in the serialized value.
- [ ] AC-2: Given the same serialized value, then it contains no session ID and no cascade step field; and when it is restored, then the resulting `docked` rects equal the rects produced by recomputing the cascade rule in stack order.
- [ ] AC-3: Given a stored value naming windows for tabs T1 and T2 where only T1 exists in the workspace, when restoration runs, then a window is created for T1 and no window is created for T2.
- [ ] AC-4: Given a restored `docked` window bound to an inactive tab, then while the registry entry that tab actually produces at runtime reports `isVisible` false, or `width` 0, or `height` 0, or is absent so the lookup returns `undefined`, the window is hidden and its rect is not applied; and once that tab registers an entry with `isVisible` true and both `width` and `height` above 0, the window becomes visible with a rect derived from it. The runtime entry of the inactive tab is read directly and shown to carry a negative `left` rather than 0, so it does not equal `{0,0,0,0}`, and the deferral contains no comparison against that literal.
- [ ] AC-5: Given a stored stack order W1, W2, W3 for workspace A and an existing stack already holding window X from workspace B, when workspace A is restored, then W1, W2 and W3 appear in that relative order in the stack and X's position relative to the other pre-existing entries is unchanged.
- [ ] AC-6: Given a window with unsaved text, when the workspace is switched away and back, then the editor instance is the same object, the unsaved text is still present, and no read of `window_state_<workspaceId>` occurred during the round trip.
- [ ] AC-7: Given a `floating` window that the user drags to a new rect, then that rect is written under `window_state_<workspaceId>`; and no value is written to `buildergate.dialog.<id>.geometry` at any point, including when the window is closed.
- [ ] AC-8: Given a `docked` window and a `stage` window, when the state is serialized, then each entry carries its placement state and neither carries a stored rect, while a `floating` entry in the same value does carry one.
- [ ] AC-9: Given no stored value under `window_state_<workspaceId>`, or a stored value that fails to parse, when restoration runs, then no window is created and no error is surfaced to the user.
