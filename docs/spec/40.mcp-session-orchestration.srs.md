# MCP Session Orchestration

| Field | Value |
|---|---|
| Document Type | scope_srs |
| Scope | MCP |
| Scope Name | MCP Session Orchestration |

## 1. Scope Overview

This scope specifies the BuilderGate MCP control-plane for exposing terminal sessions, agent orchestration, webhook-triggered assignments, alias management, and safe cross-session input delivery to MCP-connected coding agents.

## 2. Scope Boundaries

### In Scope

- Streamable HTTP MCP listener configuration, security guards, tool discovery, tool calls, and listener rebind behavior.
- Session identity, stable session addressing, alias list/search, status update, message delivery, reply, and close workflows for terminal sessions.
- Agent command profiles, MCP-launched follower sessions, launch-time capability binding, kickoff prompt delivery, and launch compensation.
- Webhook invocation through random query keys or header keys, assignment creation, source session `"0"`, prompt limits, and redaction.
- Header Tools menu dialog surfaces for MCP server, security, agent profiles, webhooks, and live sessions.
- Audit logging, token/key separation, scope checks, observable rejection errors, and regression/E2E verification for MCP control-plane behavior.

### Out of Scope

- Replacing the terminal rendering engine, xterm.js, or existing workspace grid layout mechanics.
- Making split WebSocket the default socket topology.
- Changing the MCP control-plane message encoding, which remains JSON. The negotiated binary terminal data plane specified in the BuilderGate Stability scope is not restricted by this exclusion.
- Using browser JWTs as MCP or webhook actor credentials.
- Treating runtime `sessionId` as a permission credential.
- Broad OS process termination such as killing all `node.exe` processes during validation or cleanup.
- Guaranteeing automatic MCP client configuration for every external coding agent when that agent only supports manual configuration.

## 3. Assumptions and Constraints

- The active target is `0.5.5-buildergate-stability`.
- The default MCP HTTP endpoint is loopback-only.
- External MCP access requires explicit whitelist mode plus direct TLS or a trusted TLS reverse proxy.
- MCP input, WebSocket input, and restore input must converge on a shared input policy before MCP message delivery becomes available.
- MCP tool calls, webhook payloads, and MCP-delivered session input remain JSON regardless of the terminal data plane wire format.
- Existing `WorkspaceTab.name` with `nameSource='user'` is the primary user alias source.
- `SessionManager` continues to own PTY spawn/write/terminate/finalization, and `WorkspaceService` continues to own tab lifecycle.
- Playwright/manual validation must target `https://localhost:2222`; `http://localhost:2221` is health/redirect only.

#### Requirement

The system shall run the BuilderGate MCP Streamable HTTP endpoint on an independent MCP listener that is loopback-only by default, permits external access only through explicit IP or CIDR whitelist mode with direct TLS or a trusted TLS reverse proxy, validates effective client IP, Origin, authentication, and actor scope before every MCP or webhook request, and rebinds MCP host or port by swapping only the MCP listener with rollback on failure instead of restarting the BuilderGate app process.

#### Rationale

The research identifies the MCP endpoint as a remote control surface for terminal input, session creation, and session termination. Keeping the listener independent, closed by default, and guarded by explicit TLS, whitelist, Origin, and scoped capability checks prevents accidental external exposure and keeps port changes from destabilizing the main app server.

#### Acceptance Criteria

- [ ] AC-1: Given MCP is enabled with default configuration, when the listener starts, then it binds to 127.0.0.1 and rejects non-loopback remote addresses before MCP tool dispatch.
- [x] AC-2: Given whitelist mode with transportSecurity none, direct TLS or trusted TLS proxy, when the config is validated, then it is accepted; MCP is then reachable over plain HTTP from the listed addresses (the listener serves HTTPS only for direct TLS). A trusted TLS proxy still requires at least one trusted proxy.
- [ ] AC-3: Given trusted TLS proxy mode is enabled, when a request arrives, then forwarded client IP headers are trusted only if the immediate remote address is in trustedProxies and the forwarded protocol is HTTPS; otherwise the request is rejected before whitelist matching.
- [ ] AC-4: Given an MCP or webhook request has a remote address, effective client IP, Origin, or token that fails policy, then the response contains an observable error code and audit id without disclosing token, key, or raw prompt material.
- [ ] AC-5: Given the MCP port or bind host changes, when rebind succeeds, then a candidate listener is health-probed, swapped active, and the old listener is drained without restarting the app HTTPS server or redirect server.
- [ ] AC-6: Given MCP rebind fails during validation, candidate bind, health probe, or persistence, then the previous listener and persisted config remain active and the failure is visible through MCP control status and audit.
- [x] AC-7: Given externalWhitelist contains '*', then any client address (IPv4 or IPv6) passes the whitelist. '*' is accepted only in externalWhitelist, never in trustedProxies, and 0.0.0.0/0 stays rejected with MCP_WHITELIST_DENIED so '*' is the one way to open to every address.
- [x] AC-8: Given the MCP settings dialog, when MCP is on in whitelist mode combined with transportSecurity none, or with externalWhitelist containing '*', then a warning stays visible under that field naming the risk (the key travels unencrypted; any address can try the key), and Save asks once for confirmation before saving; cancelling saves nothing. A save that turns MCP off is neither warned about nor confirmed.
- [x] AC-9: Given the MCP settings dialog, then the transport options read HTTP (unencrypted), HTTPS (direct TLS) and HTTPS (trusted proxy), the external bind mode reads as external access by IP list, and choosing that mode while the host is a loopback address changes the host to 0.0.0.0 (and choosing loopback mode while the host is 0.0.0.0 changes it back to 127.0.0.1).
- [x] AC-10: Given a save that turns MCP off (and may switch to loopback mode with a loopback host), then the saved host and port are the ones in that save, not the stopped listener's previous ones, so turning external access off and back to loopback succeeds in one save.

#### Requirement

The system shall expose BuilderGate session orchestration through MCP tool discovery and tool calls using stable ASCII tool names for session identity, claim, list, search, message delivery, alias update, agent launch, close, self-close, reply-to-leader, and status update, while keeping Korean session aliases and prompts as input or output data rather than tool names.

#### Rationale

The research separates natural-language agent intent from the MCP tool surface. Stable tool names and explicit schemas let Codex, Claude Code, and other clients perform the same search, send, launch, reply, and close workflows without relying on localized command names.

#### Acceptance Criteria

- [ ] AC-1: Given an MCP client calls tools/list, then the response includes buildergate.session.whoami, buildergate.session.claim, buildergate.session.list, buildergate.session.search, buildergate.message.send, buildergate.session.set_alias, buildergate.session.open_agent, buildergate.session.close, buildergate.session.close_self, buildergate.message.reply_to_leader, and buildergate.session.update_status with JSON input schemas.
- [ ] AC-2: Given a session-bound actor calls buildergate.session.whoami, then the result includes sessionId, sessionKey, workspaceId, tabId, alias, agentKind, leaderSessionKey, bindingLifecycle, and agentStatus.
- [ ] AC-3: Given a legacy or manually configured session lacks a session-bound token, when Streamable HTTP initialization presents a valid one-time claim code as its Bearer bootstrap credential and that transport session calls buildergate.session.claim with the same code, then the code must be unexpired, bound to an existing live session, atomically consumed once, and exchanged for a registered session-bound actor token. Claim codes expire after five minutes, their server-side collection is pruned and limited to 256 records, and reuse, expiration, or a non-live binding is rejected with a stable denial code. Every subsequent POST carrying mcp-session-id must also present the exact Bearer used at initialization; the claim bootstrap transport continues presenting its original claim code after binding while the server authorizes through the internally minted actor token. Missing, mismatched, or browser-JWT credentials are rejected, an unbound bootstrap session may discover or call only the claim flow plus protocol initialization and ping operations, and every session capability is revalidated against its current live binding on each request. Once an authorized close begins, all registered actor tokens for that session are revoked even if later tab or process cleanup reports failure.
- [ ] AC-4: Given a tool call fails validation or policy, then the MCP response maps the failure to a stable observable error code rather than silently falling back to a different tool or target.
- [ ] AC-5: Given the MCP implementation exchanges JSON-RPC messages over Streamable HTTP, then request and response bodies are UTF-8 JSON and tool names remain ASCII even when aliases such as 빌더 게이트 or 클로드 are used in arguments.

### FR-MCP-001 — Stable session identity, alias listing, search, and alias updates

#### Requirement

The system shall maintain an MCP session registry that maps each stable sessionKey to the current runtime UUID sessionId, workspaceId, tabId, generation, alias, leaderSessionKey, bindingLifecycle, MCP connection state, and agentStatus, and shall use that registry to implement whoami, session list, session search, stale sessionId rejection, and alias updates based on WorkspaceTab.name with nameSource set to user.

#### Rationale

The current runtime sessionId changes on restart and orphan recovery. The research therefore requires a stable sessionKey and generation guard so long-running assignments, search results, and leader or follower relationships do not silently target stale sessions. Reusing WorkspaceTab.name preserves the user-visible alias source instead of introducing a second naming model.

#### Acceptance Criteria

- [ ] AC-1: Given a runtime terminal session is created, when the MCP registry binds it, then sessionId is a UUID generated by SessionManager and sessionKey remains stable for the tab across restart and orphan recovery.
- [ ] AC-2: Given a tab restart or orphan recovery replaces WorkspaceTab.sessionId, when registry reconciliation runs, then currentSessionId and generation are updated while the previous sessionId becomes stale for MCP targeting.
- [ ] AC-3: Given a tool call targets a sessionId that does not match the current binding generation, then the call fails with STALE_SESSION_ID and returns enough non-secret binding context for the caller to re-search or retarget.
- [ ] AC-4: Given buildergate.session.list is called with includeSelf true or false, then it returns live bindings with sessionId, sessionKey, alias, nameSource, workspaceId, tabId, agentKind, agentStatus, mcpConnected, and leaderSessionKey according to the includeSelf option.
- [ ] AC-5: Given the user renames the lower status-bar session name or tab name, when WorkspaceTab.name is saved with nameSource user, then MCP list and exact alias search use that value as the primary alias.
- [ ] AC-6: Given buildergate.session.set_alias succeeds, then it updates the same WorkspaceTab.name and nameSource user path used by UI rename and broadcasts tab:updated to connected clients.
- [ ] AC-7: Given buildergate.session.search receives a query such as 빌더 게이트, then exact user alias match is ranked before terminal-title names, tab prefixes, agent aliases, cwd, or recovery-command matches; zero matches, ambiguous equal-rank matches, stopped bindings, and unauthorized targets fail with explicit candidate or reason data.

### FR-MCP-002 — Shared input gateway for MCP messages and leader replies

| Field | Value |
| --- | --- |
| Type | functional |
| Target | 0.5.5-buildergate-stability |
| Status | planned |
| Priority | critical |
| Tags | mcp, input-gateway, message-send, reply, replay-safety, feasibility:high |
| Risk | high |
| Stability | evolving |
| Verification Method | Gateway unit tests, WebSocket input regression tests, restore input regression tests, message.send and reply_to_leader MCP integration tests, and AI TUI idle invariant tests. |
| GitHub Issue | - |
| Related Docs | docs/research/mcp/01.requirements-and-domain-model.md, docs/research/mcp/02.current-architecture-inventory.md, docs/research/mcp/04.session-orchestration-and-input-safety.md, docs/research/mcp/06.security-ops-test-plan.md |

#### Requirement

The system shall route WebSocket user input, restore input, MCP message delivery, agent-command injection, kickoff prompt injection, webhook delivery, and reply-to-leader delivery through a shared SessionInputGateway that enforces byte limits, live-session checks, replay and repair policy, hidden-terminal policy, paste-only versus submit policy, audit hooks, and the AI TUI idle invariant before calling the low-level PTY write path.

#### Rationale

The research identifies direct SessionManager.writeInput calls from multiple ingress paths as the main safety risk. MCP and webhook input must not bypass replay queues, newline policy, hidden-session policy, or the existing AI TUI status invariant.

#### Acceptance Criteria

- [ ] AC-1: Given WebSocket user input, restore input, buildergate.message.send, buildergate.message.reply_to_leader, open_agent command injection, kickoff, or webhook delivery is submitted, when input is accepted, then the final PTY write occurs through SessionInputGateway rather than each caller directly invoking SessionManager.writeInput.
- [ ] AC-2: Given replay or screen-repair state is pending for a target session, when MCP or webhook input is submitted, then the gateway queues or rejects according to the configured replayPolicy and returns INPUT_REJECTED_REPLAY_PENDING or equivalent observable status when rejected.
- [ ] AC-3: Given a message uses paste-only delivery, then the gateway writes text without synthetic Enter submission and rejects carriage return, line feed, or submit semantics unless the actor has mcp:message.submit scope and the request explicitly sets submit true.
- [ ] AC-4: Given a hidden, closed, retired, stale-generation, or non-live target is selected, then the gateway rejects the delivery with a stable error code and does not call the PTY write path.
- [ ] AC-5: Given an AI TUI session receives user typing, local echo, prompt redraw, cursor movement, ticker output, or waiting-input repaint, then the shared input path preserves the existing invariant that those events do not transition the session to running.
- [ ] AC-6: Given a follower calls buildergate.message.reply_to_leader, then the gateway resolves the leaderSessionKey to a live binding and reuses message delivery; if the leader is unavailable, the follower remains open and the error is returned.
- [ ] AC-7: Given an MCP or agent-lifecycle delivery uses submit (buildergate.message.send, buildergate.message.reply_to_leader, buildergate.terminal.exec, open_agent command injection or kickoff), when it is accepted, then the text without its trailing carriage return or line feed is written first, and after a short delay that grows with the text length a single carriage return is written as a separate PTY write, so an AI TUI cannot read the Enter inside the same paste-sized input chunk as the text; if the text write is rejected no Enter is written, and if the Enter write is rejected its failure code is returned instead of a delivered status.
- [ ] AC-8: Given the MCP settings of the Tools dialog, then the AC-7 wait is base wait plus per-KB wait for each started 1024 characters of text, capped at 10000 ms; base wait (default 1000, 0 to 5000 ms) and per-KB wait (default 50, 0 to 1000 ms) are set there, rejected with VALIDATION_ERROR outside those integer ranges, persisted in mcp-control-config.json, and applied to the next delivery without rebinding the MCP listener.
- [ ] AC-9: Given an MCP client runs initialize or server/discover, then the server instructions say the tools can orchestrate other sessions (open terminals, start coding agents, send them prompts and read their screens) and that a submit through buildergate.terminal.exec or buildergate.message.send with deliveryMode submit already presses Enter, so no separate message is needed just to submit.

#### Requirement

The system shall make MCP-launched session lifecycle operations transactional and observable by compensating failed open_agent attempts, closing target sessions through the single WorkspaceService.deleteTab path, and allowing buildergate.session.close_self only for follower sessions that have a leaderSessionKey with deferred execution after the MCP response is flushed.

#### Rationale

MCP tools can create and close PTY-backed sessions, so lifecycle errors can leak tabs, tokens, generated config files, or processes. The research also found that self-close can terminate its own response channel unless close is deferred after the tool response.

#### Acceptance Criteria

- [ ] AC-1: Given open_agent fails before tab or PTY creation, then no workspace tab or runtime session is left behind, minted capability tokens are revoked, generated config files are deleted, and the launch attempt is recorded as cancelled or failed with an observable error code.
- [ ] AC-2: Given open_agent creates a tab or PTY and then binding finalization or command injection fails, then the compensation path calls WorkspaceService.deleteTab once, revokes tokens, deletes generated files, marks the launch attempt failed, and records cleanup success or failure.
- [ ] AC-3: Given agent command injection succeeds but readiness times out, then the session remains open, agentStatus remains unknown or starting, kickoffPending is true, and no automatic close or unsafe kickoff paste occurs.
- [ ] AC-4: Given buildergate.session.close is authorized for another session, then tab and PTY cleanup go through WorkspaceService.deleteTab and MCP code does not call SessionManager.terminateSession a second time for the same tab-close operation.
- [ ] AC-5: Given buildergate.session.close_self is called without leaderSessionKey, then it fails with SELF_CLOSE_DENIED_NO_LEADER and does not close the user-created session.
- [ ] AC-6: Given buildergate.session.close_self is called by a follower with a live leaderSessionKey, then the tool returns an accepted close job before scheduling tab and PTY cleanup 250 to 1000 milliseconds after response flush.
- [ ] AC-7: Given any close path completes or fails, then registry bindingLifecycle, tab removal broadcast, process-tree cleanup evidence, and audit result remain consistent and traceable.

#### Requirement

The system shall enforce a scoped capability model for MCP session actors and webhook actors, rejecting browser JWTs as MCP or webhook credentials, applying explicit Origin and whitelist edge-case policy, generating webhook keys and an administrator-managed fixed MCP access key with at least 32 bytes of CSPRNG entropy, binding webhook keys to allowed targets, profiles, modes, and scopes, supporting token and key rotation, and returning stable MCP error codes for every policy denial.

#### Rationale

The first SRS pass captured security principles but did not make capability scopes, auth boundary edge cases, webhook entropy, webhook binding, empty whitelist behavior, or stable error-code mapping sufficiently testable. These are remote-control security contracts and must be explicit before implementation.

#### Acceptance Criteria

- [ ] AC-1: Given an MCP session token is minted, then it carries audience buildergate-mcp, scope, expiration, jti, and sessionKey when session-bound; the raw token is not persisted and replayed, expired, wrong-audience, or wrong-session tokens are rejected.
- [ ] AC-2: Given a default session-bound actor is created, then its default scopes are exactly mcp:self.read, mcp:sessions.list, mcp:message.paste, and mcp:status.write; mcp:message.submit, mcp:session.open, mcp:sessions.alias.write, mcp:session.close, and mcp:session.close_self require explicit additional grants.
- [ ] AC-3: Given a leader creates a follower, then the follower token may receive mcp:session.close_self only when the binding has a leaderSessionKey; closing another session requires mcp:session.close and cannot be inferred from sessionId knowledge.
- [ ] AC-4: Given a browser JWT is presented to the MCP endpoint or webhook endpoint as the only credential, then the request is rejected before tool or webhook dispatch and the audit reason identifies a credential-boundary violation without logging the JWT.
- [ ] AC-5: Given an Origin header is present, then it must match allowedOrigins; when Origin is absent, the request is accepted only if the non-browser request still passes loopback or whitelist transport policy and presents a valid MCP capability token, fixed MCP access key, webhook key, or one-time claim code restricted to the claim bootstrap flow. Browser JWTs and uncredentialed MCP initialization are rejected before dispatch.
- [ ] AC-6: Given whitelist bind mode is requested with an empty externalWhitelist, then the config is rejected rather than opening a broader listener or silently falling back to external access.
- [ ] AC-7: Given a webhook key is created or rotated, then the secret material is generated with a CSPRNG and at least 32 bytes of entropy, only keyHash and metadata are persisted, and the full key is returned only in the creation or rotation response.
- [ ] AC-8: Given a webhook key is created, then allowed target, default agent profile, allowed mode such as send-only or open-or-send, and mcp:webhook.invoke scope are stored with the key; a request that overrides those bindings beyond its grant is rejected before assignment side effects.
- [ ] AC-9: Given a policy denial occurs, then the response uses one of the stable contract codes UNBOUND_ACTOR, INVALID_SCOPE, TARGET_NOT_FOUND, AMBIGUOUS_TARGET, STALE_SESSION_ID, TARGET_NOT_LIVE, INPUT_REJECTED_REPLAY_PENDING, INPUT_REJECTED_ENTER_POLICY, SELF_CLOSE_DENIED_NO_LEADER, MCP_PORT_REBIND_FAILED, WEBHOOK_KEY_INVALID, or a documented successor code.
- [ ] AC-10: Given an authenticated UI administrator generates or regenerates the fixed MCP access key, then the server creates at least 32 bytes of CSPRNG secret material, serializes concurrent config writes, persists only its SHA-256 hash, invalidates the previous key immediately including already initialized MCP transport sessions, and returns the new plaintext key only in that generation response. A valid fixed key authenticates a non-session-bound MCP actor with exactly mcp:sessions.list, mcp:sessions.search, mcp:message.paste, and mcp:message.submit scopes; it grants no session creation, close, alias, status, or self identity privilege.

### SEC-MCP-003 — Terminal sessions do not inherit the host process's coding-agent identity

| Field | Value |
| --- | --- |
| Type | security |
| Target | 0.5.5-buildergate-stability |
| Status | implemented |
| Priority | high |
| Tags | mcp, security, session-env, agent-identity, pty |
| Risk | high |
| Stability | evolving |
| Verification Method | Server unit tests over the environment a session is spawned with: the prefixed variables absent, every other variable present with its value unchanged, the BASH_ENV injection surviving, an envPatch entry in the filtered namespace surviving, and a name that merely contains the prefix left alone. The environment is read from the value handed to the spawn rather than from a description of it, so a filter that ran somewhere else would not satisfy these. |
| GitHub Issue | https://github.com/Snoworca/BuilderGate/issues/47 |
| Related Docs | - |

#### Requirement

A terminal session shall not inherit the host process's coding-agent session identity. Every environment variable that names that identity shall be removed from the environment a PTY session is spawned with, unless the caller named it explicitly in that session's `envPatch`.

Which names those are, measured on a real host on 2026-09-11 rather than assumed: every variable beginning with `CLAUDE`, and `AI_AGENT`. Twelve were present, and they do not share one namespace — `CLAUDECODE` has no underscore, `CLAUDE_PID` and `CLAUDE_EFFORT` and `CLAUDE_PLUGIN_DATA` sit outside `CLAUDE_CODE_` entirely, and `AI_AGENT` shares no prefix with any of them.

The fact that forces this. `SessionManager.buildShellEnv()` copied the server process's whole environment into the PTY. Nothing filtered it. So when the BuilderGate server is started from a shell that is itself a Claude Code session — which is how it is started during development and during agent-driven work — every terminal the server creates carried that session's identity, and every agent run in those terminals believed it was a child of the host session.

What that costs, measured rather than supposed:

- `CLAUDE_CODE_CHILD_SESSION` turns transcript saving off. The agent prints one warning line and then keeps no record of the session. The line scrolls away, so the absence is usually discovered long after the work it would have recorded.
- `CLAUDECODE` is the presence marker a tool reads to answer "am I running inside Claude Code", and `CLAUDE_PID` and `AI_AGENT` name the host process and its build. A terminal carrying them describes itself as the host rather than as itself.
- `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` name the host session and the channel it listens on. Whether a spawned agent can reach that channel through them has not been tested and is not claimed here; they are removed on the same principle as the rest, which is that a session BuilderGate creates is not a continuation of whatever session created BuilderGate.

A prefix, not a list. A list is a second place that has to learn every variable the tool adds, and the entry nobody remembers to add is the one that leaks. `AI_AGENT` is the exception and is named individually because it shares a prefix with nothing; the prefix rule is what keeps that exception from having to grow.

`CLAUDE` rather than `CLAUDE_CODE_` costs one thing: a user's own `CLAUDE`-named variable goes too. That is the right way round. A terminal that lost a setting shows it immediately and `envPatch` puts it back by name; a terminal that kept the host's identity shows nothing until somebody goes looking for a transcript that was never written. The `ANTHROPIC_` keys a user needs in order to run an agent of their own are outside the rule and are carried through.

`envPatch` wins over the rule. A caller that names `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE` — or any other variable the rule would take — is stating an intent about this session, and a rule that overrode it would leave the caller with no way to say what they meant. The rule exists to drop what was inherited by accident, not to forbid what was asked for. It is a create-time property: `envPatch` is not persisted on the tab, so a tab restart re-creates the session without it.

Nothing outside the rule is touched. `PATH`, `HOME`, `USERPROFILE` and the `BASH_ENV` injection the OSC 133 integration depends on all pass through unchanged, and the criteria below assert that rather than leave it to be assumed.

Pitfall: the server also spawns a probe PTY through a generated script that passes `env: process.env` directly (`SessionManager.ts:4887`). That path runs `powershell -Command exit`, reaches no user and returns nothing to a terminal, so it is outside this requirement; it is named here so a reader who greps for `process.env` does not take it for a hole in the rule.

#### Rationale

BuilderGate exists to run coding agents in parallel. An agent in a terminal that carries the identity of whoever started the server is not an independent agent: it keeps no record of its own session, and it names a messaging channel that belongs to something else.

The filter is by prefix rather than by a list of names because a list is a second place that must learn every variable the tool adds, and the entry nobody remembers to add is the one that leaks. The prefix is the vendor's namespace, so anything added to it is covered on the day it appears.

envPatch wins over the filter because the two say different things. An inherited variable is an accident of how the server was started; a variable the caller named is a statement about this session, and overriding it would leave no way to ask for the behaviour it selects.

#### Acceptance Criteria

- [ ] AC-1: Given the server process environment carries `CLAUDE_CODE_CHILD_SESSION`, when a session is created, then that variable is absent from the environment the PTY is spawned with, and the same test asserts the variable really was set on the server process so the absence is not vacuous.
- [ ] AC-2: Given the server process environment carries the twelve variables a Claude Code session exports — `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`, `CLAUDECODE`, `CLAUDE_PID`, `CLAUDE_EFFORT`, `CLAUDE_PLUGIN_DATA` and `AI_AGENT` — when a session is created, then none of the twelve is present in the spawned environment. The five that carry no `CLAUDE_CODE_` prefix are named individually, because a rule written against that prefix alone passes the first seven and fails these.
- [ ] AC-3: Given a variable named `CLAUDE_ANYTHING_ADDED_LATER` that no version of the tool ships today, then it is removed as well: the rule is a prefix rule and not a list of known names, so a variable added to the namespace next year is covered without anyone editing it.
- [ ] AC-4: Given the server process environment carries `PATH`, `HOME`, `USERPROFILE` and other variables outside the rule, when a session is created, then every one of them is present in the spawned environment with its value unchanged, and the number of variables removed equals the number the process carried that the rule names. Without the count, a rule that removed everything would satisfy the absences above.
- [ ] AC-5: Given a bash session whose OSC 133 integration sets `BASH_ENV`, when that session is created, then `BASH_ENV` is present with the integration script path. This is judged as the presence of a variable the rule never names rather than as an ordering guard: no ordering of a rule over these names can remove `BASH_ENV`, and the ordering that is actually pinned — the rule before the `envPatch` merge — is AC-6's.
- [ ] AC-6: Given a session created with an `envPatch` naming `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE`, then that variable is present in the spawned environment with the value the caller gave, even though the rule would otherwise take it; and the inherited variables are still gone, so the patch does not turn the rule off wholesale. This pins that the patch is merged over the filtered base rather than under it.
- [ ] AC-7: Given a variable whose name merely mentions the namespace without beginning with it, such as `MY_CLAUDE_SETTING` or `NOT_AI_AGENT`, and given `ANTHROPIC_API_KEY`, when a session is created, then all three are present in the spawned environment. The rule is a prefix rule plus one exact name, and a substring match would take variables that belong to the user rather than to the host.
- [ ] AC-8: Given an environment entry whose value is `undefined`, when it is filtered, then the key is absent from the result rather than carried with the literal string `undefined`. A spread would have carried it.
