## 1. Scope Overview

서버에서 파일을 복사·이동·삭제하는 작업 모델. 진행률과 취소와 중간 질문이 붙으므로 단순한 비동기 함수가 아니라 **답을 기다리며 멈출 수 있는 상태 기계**다.

화면과 독립적으로 검증한다. 복사가 취소를 어떻게 처리하는지, 이름이 겹칠 때 무엇을 만드는지는 브라우저 없이 서버 테스트로 판정할 수 있고 그렇게 판정해야 한다. 그것이 이 스코프를 `FEX` 에서 떼어 놓은 이유다.

## 2. Scope Boundaries

### In Scope

- 작업 상태 기계와 결정 대기
- scanning · transferring 두 단계와 진행률 산출
- REST 진입점 (`/api/file-jobs` 계열)
- WebSocket 진행 보고와 결정 요청 메시지
- 세션 결속과 새로고침 복구, 응답 대기 시간 제한
- 이름 충돌 규칙과 "더 이상 묻지 않기" 의 유효 범위
- 취소 의미론
- 경로 검증 정책의 적용

### Out of Scope

- 작업을 일으키고 진행을 보여 주는 화면 — `FEX` 스코프
- 파일 시스템 변경 감시
- 여러 작업의 순서 조정과 일시 정지
- 휴지통 또는 삭제 취소

## 3. Assumptions and Constraints

- 기존 파일 API(`fileRoutes.ts`)의 경로 검증을 그대로 쓴다. 새 경계 규칙을 만들지 않는다.
- `fs.cp({recursive:true})` 는 더 이상 쓸 수 없다. 전부 끝난 뒤에야 돌아오고 중간 진행을 알려 주지 않으므로, 디렉터리를 직접 걸어 다니며 파일을 하나씩 옮긴다.
- 진행 보고는 터미널 출력이 이미 쓰고 있는 WebSocket 연결을 함께 쓴다. 새 연결을 만들지 않는다.
- `ws-protocol.ts` 에는 메시지 목록을 원본 텍스트로 읽어 대조하는 테스트(`wsProtocolParityAck.test.ts`)가 붙어 있으므로 형식을 추가할 때 함께 갱신해야 한다.
- 응답 대기 10분은 짐작으로 정한 값이며 실제 사용에서 조정한다.

#### Requirement

시스템은 복사·이동·삭제를 queued → running → (awaiting-decision → running)* → completed 상태 기계로 수행하여, 실행 도중 사용자에게 묻고 답을 받은 뒤 이어서 진행해야 한다.

#### Rationale

요구사항 9번과 10번이 실행 중의 질문을 요구한다. 미리 훑어 충돌을 모두 모은 뒤 한꺼번에 묻는 방식은 훑는 동안 파일이 바뀌어 그때 없던 충돌이 실행 중에 생기므로, 실행 중에 묻는 경로를 어차피 만들어야 한다. 같은 일을 하는 경로가 둘이 되면 한쪽만 고쳐진다.

#### Acceptance Criteria

- [x] AC-1: 작업은 queued·running·awaiting-decision·completed·cancelled·failed 상태를 가진다
- [x] AC-2: awaiting-decision 에서 답을 받으면 running 으로 돌아가 남은 항목을 이어서 처리한다
- [x] AC-3: 한 작업 안에서 awaiting-decision 으로 여러 번 들어갈 수 있다
- [x] AC-4: 취소는 running 과 awaiting-decision 두 상태 모두에서 받는다
- [x] AC-5: 실행 전 일괄 스캔으로 충돌을 모으는 별도 경로를 두지 않는다
- [x] AC-6: 파일 하나의 fs 오류(EBUSY·EPERM·EACCES·ENOSPC 등)는 작업 전체를 실패시키지 않고 kind=error 결정(retry·skip, detail 은 errno 코드)으로 묻는다 — 스캔 단계의 폴더 읽기 실패도 같으며, 건너뛴 폴더는 복사·이동·삭제하지 않는다
- [x] AC-7: 디렉터리를 자기 자신이나 그 하위로 복사·이동하면 아무것도 만들기 전에 EINVAL 로 실패한다 — 입력 문자열과 실제 경로 양쪽으로 비교한다
- [x] AC-8: 세션 cwd 가 링크(junction·symlink)거나 8.3 짧은 이름이어도 세션 루트를 복사하는 작업은 완료된다

### FR-FOP-002 — 작업은 scanning 과 transferring 두 단계로 진행한다

| Target | file-explorer |

#### Requirement

시스템은 파일 조작을 대상을 세는 scanning 단계와 실제로 옮기는 transferring 단계로 나누어 수행하고, 각 단계에 맞는 진행률을 보고해야 한다.

#### Rationale

전체 크기를 먼저 세지 않으면 막대의 길이를 정할 수 없다. 큰 트리에서는 세는 일 자체가 오래 걸리므로 그동안은 막대가 아니라 회전 프로그레스를 보여야 한다.

#### Acceptance Criteria

- [x] AC-1: scanning 단계는 파일 수와 전체 바이트를 세고 그동안 막대 진행률을 보고하지 않는다
- [x] AC-2: transferring 단계는 누적 바이트를 보고한다
- [x] AC-3: 복사는 스트림으로 수행하여 파일 하나가 아주 클 때도 중간 진행률이 나온다
- [x] AC-4: 삭제는 바이트가 아니라 처리한 항목 수로 진행률을 낸다
- [x] AC-5: 진행 보고에는 바이트와 항목 수를 함께 실어 화면이 작업 종류에 따라 고른다
- [x] AC-6: 삭제·이동(REST FileService 와 파일 작업 모두)은 세션 폴더 자신을 거부한다 — cwd 문자열로 쓰든 실제 경로로 쓰든 같고, 세션 안에서 루트를 가리키는 링크는 링크만 지울 수 있다

| Status | implemented |

#### Requirement

시스템은 POST /api/file-jobs, POST /api/file-jobs/:jobId/decision, DELETE /api/file-jobs/:jobId, GET /api/file-jobs 를 제공해야 한다.

#### Rationale

출발지와 목적지의 세션을 따로 받는 것은 요구사항 12번 때문이다. resolveAndValidate 가 세션의 작업 디렉터리를 기준으로 경로를 검사하므로, 탭 사이 이동은 두 세션 기준으로 각각 검사해야 한다. 하나의 세션만 받는 현재 API 로는 표현할 수 없다.

#### Acceptance Criteria

- [x] AC-1: POST /api/file-jobs 는 operation, sourceSessionId, sources 를 받고 jobId 를 돌려준다
- [x] AC-2: POST /api/file-jobs 는 destSessionId 와 destPath 를 sourceSessionId 와 별개로 받는다
- [x] AC-3: 출발지 경로는 출발지 세션 기준으로, 목적지 경로는 목적지 세션 기준으로 각각 검증한다
- [x] AC-4: POST /api/file-jobs/:jobId/decision 은 decisionId, choice, applyToAll 을 받는다
- [x] AC-5: DELETE /api/file-jobs/:jobId 는 작업을 취소한다
- [x] AC-6: GET /api/file-jobs 는 살아 있는 작업 목록을 돌려주어 새로고침 후 복구에 쓰인다
- [x] AC-7: 결정 엔드포인트의 오류는 JOB_NOT_FOUND 404, JOB_NOT_AWAITING·DECISION_MISMATCH 409, INVALID_CHOICE 400, MANAGER_DISPOSED 503 으로 매핑되고, INVALID_CHOICE 는 질문을 열어 둔다
- [x] AC-8: 출발지와 destPath 는 절대 경로여야 하며 아니면 400 INVALID_INPUT — win32 는 드라이브 문자+구분자와 서버·공유 이름이 있는 UNC 만 받고 `C:foo`·`\foo`·장치 경로(`\\?\`, `\\.\`)는 거부한다. 러너는 검증된 경로(출발지는 entry, 목적지는 실제 경로)로만 작업한다
- [x] AC-9: 세션 루트는 작업을 받을 때 실제 경로로 고정하고, blockedPaths 는 검사마다 새로 읽는다 — 작업 중 터미널에서 cd 해도 작업은 끝까지 간다
- [x] AC-10: win32 서버에서 세션 cwd 가 서버·공유 이름이 있는 UNC(WSL 세션의 \\wsl.localhost\<배포판>\…)이면, 슬래시 하나로 시작하는 리눅스 경로(/home/…)는 그 cwd 의 공유 루트 아래 경로로 풀어 받는다. /mnt/<드라이브>/… 는 그 드라이브 경로로 바꾼다. 세션 cwd 가 드라이브 경로이면 그 밖의 /… 와 \foo 는 AC-8 대로 거부한다. 완료 이벤트의 affectedDirectories 는 클라이언트가 보낸 모양을 유지한다

#### Requirement

시스템은 file-job:progress, file-job:decision-required, file-job:done 메시지를 기존 WebSocket 연결로 보내야 하며, 진행 보고는 작업마다 초당 10회로 제한해야 한다.

#### Rationale

초당 여러 번 갱신되는 값을 REST 요청·응답으로 받으면 요청 수가 그대로 늘어난다. 터미널 출력이 이미 같은 연결을 쓰고 있어 새 연결도 필요 없다. 작은 파일이 수천 개인 디렉터리에서 파일마다 메시지를 보내면 화면 갱신 비용이 복사 자체보다 커진다.

#### Acceptance Criteria

- [x] AC-1: ServerWsMessage 에 file-job:progress, file-job:decision-required, file-job:done 을 추가한다
- [x] AC-2: file-job:progress 는 jobId, phase, processedBytes, totalBytes, processedEntries, totalEntries, currentPath 를 싣는다 — phase 는 scanning|transferring 이고, 메시지는 sessionId 를 함께 싣는다(WsRouter.sendSessionEvent 가 감싼다)
- [x] AC-3: file-job:decision-required 는 jobId, decisionId, kind(conflict|error), path, detail, choices 를 싣는다 — FR-FOP-004 의 충돌 선택지와 FR-FEX-007 의 모달이 이 필드로 그려진다 — choices 는 overwrite|rename|skip|retry 리터럴이며 경로(path·progress.currentPath)는 클라이언트가 보낸 접두사로 되돌려 보낸다
- [x] AC-4: file-job:done 은 jobId, outcome(completed|cancelled|failed), processedEntries, affectedDirectories 를 싣는다 — FR-FOP-005 AC-4 의 항목 수 보고와 FR-FEX-001 AC-6 의 영향 디렉터리 재조회가 이 필드에 의존한다 — affectedDirectories 는 copy=[목적지], move=목적지+출발지들의 부모, delete=출발지들의 부모이며 중복이 없다 — 실패로 끝난 작업만 경로·메시지 없는 errorCode(errno·정책 코드, 아니면 UNKNOWN)를 싣는다
- [x] AC-5: 진행 보고는 작업마다 초당 10회를 넘지 않는다
- [x] AC-6: REST 폴링 경로를 두지 않는다
- [x] AC-7: 서버 server/src/types/ws-protocol.ts 와 프런트엔드 frontend/src/types/ws-protocol.ts 두 사본이 file-job 메시지 세 종을 같은 type 문자열과 같은 필드 이름으로 선언한다 — 한쪽만 바뀌면 빨개지는 테스트가 그것을 지킨다

#### Acceptance Criteria

- [x] AC-1: 이름 바꾸기는 '이름 (2).확장자' 를 만들고 그 이름도 있으면 숫자를 하나씩 올린다
- [x] AC-2: 디렉터리는 확장자가 없으므로 '이름 (2)' 가 된다
- [x] AC-3: 더 이상 묻지 않기는 그 작업이 끝날 때까지만 적용된다 — 이 판정에는 FR-FOP-001 의 awaiting-decision 루프와 IR-FOP-001 AC-4 의 applyToAll 이 먼저 서 있어야 한다
- [x] AC-4: 작업이 끝나면 그 선택을 기억하지 않는다
- [x] AC-5: 파일을 그 파일이 있던 폴더에 붙여넣으면(복사 출발지 === 목적지) 실패가 아니라 rename·skip 두 선택지의 충돌이 되고, overwrite 는 INVALID_CHOICE 로 거부된다 — rename 은 '이름 (2).확장자' 를 만든다
- [x] AC-6: 파일을 원래 있던 폴더로 이동하면 아무것도 묻지 않고 그대로 둔 채 처리 항목으로 세어 완료한다

#### Requirement

시스템은 작업이 취소되면 이미 마친 파일을 그대로 두고 취소한 순간 쓰고 있던 파일 하나만 지워야 하며, 무엇이 실제로 끝났는지 숫자로 보고해야 한다.

#### Rationale

반쯤 쓰이다 만 파일을 남기면 사용자가 그것을 온전한 파일로 착각한다. 전부 되돌리는 방식은 되돌리는 일 자체가 또 하나의 긴 작업이고, 그 도중에 실패하면 되돌리다 만 상태가 되는데 그것을 설명할 방법이 없다.

#### Acceptance Criteria

- [x] AC-1: 취소해도 이미 복사를 마친 파일은 지우지 않는다
- [x] AC-2: 취소한 순간 쓰고 있던 파일 하나는 지운다
- [x] AC-3: 전체 롤백 경로를 두지 않는다
- [x] AC-4: 작업 종료 보고에 실제로 끝난 항목 수가 들어간다 (예: 23개 복사 후 취소됨)
- [x] AC-5: 같은 장치 안의 이동은 fs.rename 으로 원자적으로 끝나 취소를 받을 중간 상태가 아예 없다 — 작업이 그 사실을 밝히고, 이미 끝난 작업에 온 취소 요청을 실패가 아니라 무시로 처리한다
- [x] AC-6: 장치를 건너는 이동(EXDEV)은 전체 복사 후 전체 삭제로 하지 않는다 — 현재 moveFile:381-384 가 copyFile + deleteFile 을 통째로 부르는데, 그러면 취소 시점에 원본과 사본이 모두 온전히 남거나 모두 사라지는 두 상태뿐이라 AC-1·AC-2 를 지킬 수 없다

- [x] AC-8: 끝난 작업은 끝난 시점부터 5분 동안 보존되어 그동안 온 취소는 not-found 가 아니라 ignored 가 된다
- [x] AC-9: 새 파일도 같은 디렉터리의 임시 이름(.bg-part-<16hex>)에 다 쓴 뒤 놓는다 — 하드 링크로 덮어쓰지 않고 놓으며(이미 있으면 EEXIST 결정), 하드 링크가 안 되는 볼륨은 lstat+rename 으로 되돌아간다. 임시 이름은 디렉터리 목록에 보이지 않는다

### SEC-FOP-001 — 파일 조작 경로 검증은 서버의 blocked path 정책을 그대로 따른다

| Field | Value |
| --- | --- |
| Type | security |
| Target | file-explorer |
| Status | verified |
| Priority | medium |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |

#### Requirement

시스템은 파일 조작 작업의 모든 경로를 기존 파일 API 가 쓰는 path traversal 및 blocked path 정책(레거시 SRS `docs/srs/buildergate.srs.md` §4.7 의 `NFR-SEC-004`, 구현은 `FileService` 의 `resolveAndValidate` 와 `config.blockedPaths`)으로 검증해야 하며, 클라이언트가 별도의 경계 규칙을 갖지 않아야 한다.

#### Rationale

세션 작업 디렉터리로 막는 것은 클라이언트에만 있는 제한이라 서버가 강제하지 않는다. 보안이 아니라 장식이고, 같은 정책을 두 군데 두면 어긋난다. 저장소 밖 파일을 끌어오는 것은 여러 프로젝트를 동시에 운용할 때 실제로 쓰이는 동작이다.

#### Acceptance Criteria

- [x] AC-1: 출발지와 목적지 경로 모두 blocked path 정책으로 검증한다
- [x] AC-2: 작업 도중 만들어지는 중간 경로도 같은 검증을 거친다
- [x] AC-3: 클라이언트는 경계 규칙의 사본을 갖지 않는다
- [x] AC-4: '↑' 활성 여부는 서버 listDirectory 응답의 '..' 유무로 판정하되, 그 신호는 '드라이브 루트가 아님' 만 뜻한다 (FileService.ts:171 의 조건이 parsed.root !== dirPath 다)
- [x] AC-5: 부모가 blocked path 라 나열이 거부되면 그 오류를 사용자에게 보이고 뿌리를 바꾸지 않는다 — '↑' 가 활성이라는 것이 나열 가능을 보장하지 않는다
- [x] AC-6: 실제 대상이 세션 cwd 안인 링크는 따라가 내용을 복사하고, cwd 밖이거나 차단된 대상의 링크는 kind=error 결정으로 거부하며 그 아래는 만들지 않는다 — 검증은 링크 너머의 실제 위치로 한다
- [x] AC-7: 스캔 중 만난 blocked 자손(표시 경로나 실제 읽기 경로)은 skip 만 있는 kind=error 결정이 되고, 읽거나 만들거나 지우거나 옮기지 않는다 — 그것을 품은 디렉터리를 rename 한 번으로 통째로 옮기지 않는다

The system shall extract .zip, .tar, .tar.gz and .tgz archives as a server file job that streams each entry to a hidden temporary file and renames it into place, refuses entries that would leave the target folder or that the file API blocks, and refuses archives that exceed configured size, entry count or compression ratio limits before writing anything.

#### Rationale

An archive is untrusted input: its entry names, links and sizes are chosen by whoever made it.

#### Acceptance Criteria

- [x] AC-1: AC-1: The file job API accepts operation extract with the archive path and the mode smart or here; the archive and the target folder resolve with the file API rules (session root, blocked paths) and the job reports progress, decisions, errors and completion like copy and move jobs.
- [x] AC-2: AC-2: An entry whose normalized path contains .., is absolute, has a drive letter, a NUL character, a Windows reserved name or a segment ending in a dot or space, or would resolve outside the target folder, is not written and is reported as skipped; nothing is created outside the target folder.
- [x] AC-3: AC-3: Symbolic link, hard link, device and FIFO entries are not created and are reported as skipped; an entry under a blocked path or with a blocked extension is not written and is reported as skipped.
- [x] AC-4: AC-4: Before writing, a pre-count of entries and unpacked bytes runs; an archive over fileManager.maxExtractBytes (default 10 GiB), over fileManager.maxExtractEntries (default 100,000), or whose unpacked size exceeds 64 MiB with an unpacked to packed ratio above 1000 is refused with ARCHIVE_TOO_LARGE and writes nothing; during extraction an entry that produces more bytes than its declared size is cut off, its temporary file removed and the job fails with ARCHIVE_TOO_LARGE.
- [x] AC-5: AC-5: An encrypted ZIP entry or a split or multi-disk ZIP is refused with ARCHIVE_UNSUPPORTED (with the reason) and writes nothing; a corrupt archive or a gzip or tar read error fails the job with ARCHIVE_CORRUPT after removing the entry being written.
- [x] AC-6: AC-6: ZIP entry names without the UTF-8 flag that are not valid UTF-8 are decoded as CP949 so Korean names extract correctly; tar entries with pax or GNU long names keep their full names.
- [x] AC-7: AC-7: Each file entry is written to a hidden temporary file in its destination folder and renamed into place only when complete; cancelling stops after the current entry, deletes only the half-written temporary file, and keeps the entries already completed (FR-FOP-005); directory entries and file modification times are restored.

### SEC-FOP-002 — 세션 폴더와 같은 git 저장소의 worktree 파일은 읽기 전용으로 열 수 있다

| Field | Value |
| --- | --- |
| Type | security |
| Target | worktree-read-open |
| Status | verified |
| Priority | medium |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | #150 |
| Related Docs | [FR-ARCH-012 터미널 경로 열기](./10.product-architecture.srs.md) |

#### Requirement

시스템은 세션 폴더가 git 저장소의 worktree 안에 있을 때, 그 저장소에 등록된 다른 worktree 안의 파일을 경로 확인(stat), 텍스트 읽기, 이미지 읽기, HTML 보기, MCP 편집기 도구의 기존 파일 열기 범위에서만 허용해야 하며, 쓰기와 그 밖의 파일 조작은 세션 폴더 안으로 유지해야 한다.

#### Rationale

코딩 에이전트는 메인 worktree 옆에 형제 폴더(d-1, d-23 등)로 worktree를 만들어 작업한다. 에이전트가 출력한 시안 파일 경로는 전부 세션 폴더 밖이라서 터미널 경로 열기(FR-ARCH-012)와 편집기가 열지 못했다. 로그인한 사용자는 이미 터미널에서 같은 파일을 읽을 수 있으므로, 같은 저장소의 worktree를 읽기 전용으로 허용해도 새로 드러나는 것은 없다. 쓰기, MCP 도구, HTML 뷰 자원 범위는 넓히지 않아 실수와 페이지 스크립트의 접근 범위는 그대로 둔다. 이슈 #150 원안은 localhostNoAuth 모드에서 넓히지 않기로 했으나, 그 모드는 같은 PC의 프로그램에 셸 세션을 이미 내주므로 읽기 전용 허용이 더하는 위험이 없고, 운영 설치본이 그 모드를 켜고 있어 원안대로면 기능이 동작하지 않는다. 그래서 그 예외는 두지 않는다.

#### Acceptance Criteria

- [x] AC-1: 세션 폴더에서 위로 올라가며 찾은 .git(폴더 또는 gitdir 파일)로 git common dir 을 정하고, <common dir>/worktrees/*/gitdir 가 가리키는 폴더와 주 worktree(common dir 의 부모)를 같은 저장소의 worktree 로 인정한다. 이 목록은 git 프로세스를 실행하지 않고 파일을 읽어 만든다. 세션 폴더가 git 저장소 밖이면 목록은 비어 있다
- [x] AC-2: 세션 폴더 밖이지만 같은 저장소의 worktree 안에 있는 경로에 대해 GET files/stat, GET files/read, GET files/read-image 는 그 worktree 를 경계로 삼아 허용한다. 어느 worktree 에도 속하지 않는 경로는 지금처럼 PATH_TRAVERSAL 로 거부한다
- [x] AC-3: worktree 경로에 대한 쓰기(files/write, create, mkdir), 복사·이동·삭제, 업로드, 압축 풀기, 디렉터리 나열, 검색, 다운로드, MCP 편집기 도구의 본문 저장(html·content 인자)과 그 밖의 MCP 에이전트 도구는 지금처럼 세션 폴더 경계로 검사한다
- [x] AC-4: worktree 경로에도 링크를 따라간 실제 위치 검사, blockedPaths, blockedExtensions 를 그대로 적용한다. worktree 안의 링크가 그 worktree 밖을 가리키면 거부한다
- [x] AC-5: 다른 worktree 의 파일에 대한 stat 과 read 응답은 worktree 필드(루트 경로와 폴더 이름)를 담는다. 세션 폴더 안의 파일 응답에는 이 필드가 없다
- [x] AC-6: 편집기는 worktree 필드가 있는 문서를 읽기 전용으로 열고, 문서 위 안내 줄에 worktree 이름과 읽기 전용인 이유를 표시한다. 그 문서에는 저장이 동작하지 않는다
