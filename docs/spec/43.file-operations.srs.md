## 1. Scope Overview

서버에서 파일을 복사·이동·삭제하는 작업 모델. 진행률과 취소와 중간 질문이 붙으므로 단순한 비동기 함수가 아니라 **답을 기다리며 멈출 수 있는 상태 기계**다.

화면과 독립적으로 검증한다. 복사가 취소를 어떻게 처리하는지, 이름이 겹칠 때 무엇을 만드는지는 브라우저 없이 서버 테스트로 판정할 수 있고 그렇게 판정해야 한다. 그것이 이 스코프를 `FEX` 에서 떼어 놓은 이유다.

## 2. Scope Boundaries

### In Scope

- 작업 상태 기계와 결정 대기
- scanning · transferring 두 단계와 진행률 산출
- REST 진입점 (`/api/file-jobs` 계열)
- WebSocket 진행 보고와 결정 요청 메시지
- 세션 결속과 새로고침 복구, 응답 대기 시간 제한
- 이름 충돌 규칙과 "더 이상 묻지 않기" 의 유효 범위
- 취소 의미론
- 경로 검증 정책의 적용

### Out of Scope

- 작업을 일으키고 진행을 보여 주는 화면 — `FEX` 스코프
- 파일 시스템 변경 감시
- 여러 작업의 순서 조정과 일시 정지
- 휴지통 또는 삭제 취소

## 3. Assumptions and Constraints

- 기존 파일 API(`fileRoutes.ts`)의 경로 검증을 그대로 쓴다. 새 경계 규칙을 만들지 않는다.
- `fs.cp({recursive:true})` 는 더 이상 쓸 수 없다. 전부 끝난 뒤에야 돌아오고 중간 진행을 알려 주지 않으므로, 디렉터리를 직접 걸어 다니며 파일을 하나씩 옮긴다.
- 진행 보고는 터미널 출력이 이미 쓰고 있는 WebSocket 연결을 함께 쓴다. 새 연결을 만들지 않는다.
- `ws-protocol.ts` 에는 메시지 목록을 원본 텍스트로 읽어 대조하는 테스트(`wsProtocolParityAck.test.ts`)가 붙어 있으므로 형식을 추가할 때 함께 갱신해야 한다.
- 응답 대기 10분은 짐작으로 정한 값이며 실제 사용에서 조정한다.

### FR-FOP-001 — 파일 조작 작업은 답을 기다리며 멈출 수 있는 상태 기계다

#### Requirement

시스템은 복사·이동·삭제를 queued → running → (awaiting-decision → running)* → completed 상태 기계로 수행하여, 실행 도중 사용자에게 묻고 답을 받은 뒤 이어서 진행해야 한다.

#### Rationale

요구사항 9번과 10번이 실행 중의 질문을 요구한다. 미리 훑어 충돌을 모두 모은 뒤 한꺼번에 묻는 방식은 훑는 동안 파일이 바뀌어 그때 없던 충돌이 실행 중에 생기므로, 실행 중에 묻는 경로를 어차피 만들어야 한다. 같은 일을 하는 경로가 둘이 되면 한쪽만 고쳐진다.

#### Acceptance Criteria

- [ ] AC-1: 작업은 queued·running·awaiting-decision·completed·cancelled·failed 상태를 가진다
- [ ] AC-2: awaiting-decision 에서 답을 받으면 running 으로 돌아가 남은 항목을 이어서 처리한다
- [ ] AC-3: 한 작업 안에서 awaiting-decision 으로 여러 번 들어갈 수 있다
- [ ] AC-4: 취소는 running 과 awaiting-decision 두 상태 모두에서 받는다
- [ ] AC-5: 실행 전 일괄 스캔으로 충돌을 모으는 별도 경로를 두지 않는다

### FR-FOP-002 — 작업은 scanning 과 transferring 두 단계로 진행한다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | file-explorer |
| Status | planned |
| Priority | medium |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [파일 탐색기 설계](../plan/2026-09-12.file-explorer.design.md) |

#### Requirement

시스템은 파일 조작을 대상을 세는 scanning 단계와 실제로 옮기는 transferring 단계로 나누어 수행하고, 각 단계에 맞는 진행률을 보고해야 한다.

#### Rationale

전체 크기를 먼저 세지 않으면 막대의 길이를 정할 수 없다. 큰 트리에서는 세는 일 자체가 오래 걸리므로 그동안은 막대가 아니라 회전 프로그레스를 보여야 한다.

#### Acceptance Criteria

- [ ] AC-1: scanning 단계는 파일 수와 전체 바이트를 세고 그동안 막대 진행률을 보고하지 않는다
- [ ] AC-2: transferring 단계는 누적 바이트를 보고한다
- [ ] AC-3: 복사는 스트림으로 수행하여 파일 하나가 아주 클 때도 중간 진행률이 나온다
- [ ] AC-4: 삭제는 바이트가 아니라 처리한 항목 수로 진행률을 낸다
- [ ] AC-5: 진행 보고에는 바이트와 항목 수를 함께 실어 화면이 작업 종류에 따라 고른다

### IR-FOP-001 — 파일 조작 작업의 REST 진입점

| Field | Value |
| --- | --- |
| Type | interface |
| Target | file-explorer |
| Status | planned |
| Priority | medium |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [파일 탐색기 설계](../plan/2026-09-12.file-explorer.design.md) |

#### Requirement

시스템은 POST /api/file-jobs, POST /api/file-jobs/:jobId/decision, DELETE /api/file-jobs/:jobId, GET /api/file-jobs 를 제공해야 한다.

#### Rationale

출발지와 목적지의 세션을 따로 받는 것은 요구사항 12번 때문이다. resolveAndValidate 가 세션의 작업 디렉터리를 기준으로 경로를 검사하므로, 탭 사이 이동은 두 세션 기준으로 각각 검사해야 한다. 하나의 세션만 받는 현재 API 로는 표현할 수 없다.

#### Acceptance Criteria

- [ ] AC-1: POST /api/file-jobs 는 operation, sourceSessionId, sources 를 받고 jobId 를 돌려준다
- [ ] AC-2: POST /api/file-jobs 는 destSessionId 와 destPath 를 sourceSessionId 와 별개로 받는다
- [ ] AC-3: 출발지 경로는 출발지 세션 기준으로, 목적지 경로는 목적지 세션 기준으로 각각 검증한다
- [ ] AC-4: POST /api/file-jobs/:jobId/decision 은 decisionId, choice, applyToAll 을 받는다
- [ ] AC-5: DELETE /api/file-jobs/:jobId 는 작업을 취소한다
- [ ] AC-6: GET /api/file-jobs 는 살아 있는 작업 목록을 돌려주어 새로고침 후 복구에 쓰인다

### IR-FOP-002 — 진행 보고와 결정 요청은 WebSocket 으로 보낸다

| Field | Value |
| --- | --- |
| Type | interface |
| Target | file-explorer |
| Status | planned |
| Priority | medium |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [파일 탐색기 설계](../plan/2026-09-12.file-explorer.design.md) |

#### Requirement

시스템은 file-job:progress, file-job:decision-required, file-job:done 메시지를 기존 WebSocket 연결로 보내야 하며, 진행 보고는 작업마다 초당 10회로 제한해야 한다.

#### Rationale

초당 여러 번 갱신되는 값을 REST 요청·응답으로 받으면 요청 수가 그대로 늘어난다. 터미널 출력이 이미 같은 연결을 쓰고 있어 새 연결도 필요 없다. 작은 파일이 수천 개인 디렉터리에서 파일마다 메시지를 보내면 화면 갱신 비용이 복사 자체보다 커진다.

#### Acceptance Criteria

- [ ] AC-1: ServerWsMessage 에 file-job:progress, file-job:decision-required, file-job:done 을 추가한다
- [ ] AC-2: file-job:progress 는 jobId, phase, processedBytes, totalBytes, processedEntries, totalEntries, currentPath 를 싣는다
- [ ] AC-3: 진행 보고는 작업마다 초당 10회를 넘지 않는다
- [ ] AC-4: REST 폴링 경로를 두지 않는다
- [ ] AC-5: wsProtocolParityAck.test.ts 의 메시지 대조 목록을 함께 갱신한다

### FR-FOP-003 — 작업은 연결이 아니라 세션에 매이고 새로고침을 견딘다

| --- | --- |

| Risk | medium |

| Verification Method | test |
| GitHub Issue | - |

#### Requirement

시스템은 파일 조작 작업을 브라우저 연결이 아니라 세션에 매어, 사용자가 새로고침해도 진행 중이던 작업이 중단되지 않게 해야 한다. 멈춰 있는 시간의 총합이 10분을 넘으면 작업을 자동으로 취소해야 한다.

#### Rationale

답이 오지 않는 상태가 무한히 이어지면 작업이 자원을 붙든 채 남는다. 10분은 짐작으로 정한 값이며 실제 사용에서 조정한다.

#### Acceptance Criteria

- [ ] AC-1: 새로고침해도 진행 중이던 작업이 중단되지 않는다
- [ ] AC-2: 다시 접속한 클라이언트는 GET /api/file-jobs 로 살아 있는 작업을 다시 받는다
- [ ] AC-3: 답을 기다리던 작업이 있으면 서버가 decision-required 를 다시 보낸다
- [ ] AC-4: 멈춰 있는 시간의 총합이 10분을 넘으면 작업을 자동 취소한다
- [ ] AC-5: 자동 취소는 사용자가 취소했을 때와 같은 규칙을 따른다

### FR-FOP-004 — 이름이 겹칠 때의 규칙과 묻지 않기의 범위

| Field | Value |
| --- | --- |
| Type | functional |
| Target | file-explorer |
| Status | planned |
| Priority | medium |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [파일 탐색기 설계](../plan/2026-09-12.file-explorer.design.md) |

#### Requirement

시스템은 이름 바꾸기를 '이름 (2).확장자' 형태로 만들고 이미 있으면 숫자를 올려야 하며, '더 이상 묻지 않기' 선택은 그 작업이 끝날 때까지만 적용해야 한다.

#### Rationale

숫자를 2부터 시작하는 것은 원본이 첫 번째이기 때문이다. 선택을 작업 너머로 기억해 두면 한참 뒤의 다른 작업에서 사용자가 모르는 사이에 파일을 덮어쓰게 된다. 덮어쓰기는 되돌릴 수 없으므로 그 위험을 기본값으로 둘 수 없다.

#### Acceptance Criteria

- [ ] AC-1: 이름 바꾸기는 '이름 (2).확장자' 를 만들고 그 이름도 있으면 숫자를 하나씩 올린다
- [ ] AC-2: 디렉터리는 확장자가 없으므로 '이름 (2)' 가 된다
- [ ] AC-3: 더 이상 묻지 않기는 그 작업이 끝날 때까지만 적용된다
- [ ] AC-4: 작업이 끝나면 그 선택을 기억하지 않는다

### FR-FOP-005 — 취소는 되돌리지 않고 쓰다 만 파일 하나만 지운다

| Field | Value |
| --- | --- |
| Type | functional |
| Target | file-explorer |
| Status | planned |
| Priority | medium |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [파일 탐색기 설계](../plan/2026-09-12.file-explorer.design.md) |

#### Requirement

시스템은 작업이 취소되면 이미 마친 파일을 그대로 두고 취소한 순간 쓰고 있던 파일 하나만 지워야 하며, 무엇이 실제로 끝났는지 숫자로 보고해야 한다.

#### Rationale

반쯤 쓰이다 만 파일을 남기면 사용자가 그것을 온전한 파일로 착각한다. 전부 되돌리는 방식은 되돌리는 일 자체가 또 하나의 긴 작업이고, 그 도중에 실패하면 되돌리다 만 상태가 되는데 그것을 설명할 방법이 없다.

#### Acceptance Criteria

- [ ] AC-1: 취소해도 이미 복사를 마친 파일은 지우지 않는다
- [ ] AC-2: 취소한 순간 쓰고 있던 파일 하나는 지운다
- [ ] AC-3: 전체 롤백 경로를 두지 않는다
- [ ] AC-4: 작업 종료 보고에 실제로 끝난 항목 수가 들어간다 (예: 23개 복사 후 취소됨)

### SEC-FOP-001 — 파일 조작 경로 검증은 서버의 blocked path 정책을 그대로 따른다

| Field | Value |
| --- | --- |
| Type | security |
| Target | file-explorer |
| Status | planned |
| Priority | medium |
| Tags | - |
| Risk | medium |
| Stability | evolving |
| Verification Method | test |
| GitHub Issue | - |
| Related Docs | [파일 탐색기 설계](../plan/2026-09-12.file-explorer.design.md) |

#### Requirement

시스템은 파일 조작 작업의 모든 경로를 기존 NFR-SEC-004 의 path traversal 및 blocked path 정책으로 검증해야 하며, 클라이언트가 별도의 경계 규칙을 갖지 않아야 한다.

#### Rationale

세션 작업 디렉터리로 막는 것은 클라이언트에만 있는 제한이라 서버가 강제하지 않는다. 보안이 아니라 장식이고, 같은 정책을 두 군데 두면 어긋난다. 저장소 밖 파일을 끌어오는 것은 여러 프로젝트를 동시에 운용할 때 실제로 쓰이는 동작이다.

#### Acceptance Criteria

- [ ] AC-1: 출발지와 목적지 경로 모두 blocked path 정책으로 검증한다
- [ ] AC-2: 작업 도중 만들어지는 중간 경로도 같은 검증을 거친다
- [ ] AC-3: 클라이언트는 경계 규칙의 사본을 갖지 않는다
- [ ] AC-4: 상위로 갈 수 있는지는 서버 listDirectory 응답의 '..' 유무로만 판정한다
