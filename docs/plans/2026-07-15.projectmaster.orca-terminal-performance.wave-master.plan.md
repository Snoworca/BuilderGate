## 실행 원칙

1. Epic의 명시적 Wave 0~4 구조를 `wave-1`~`wave-5`에 1:1로 매핑한다.
2. 각 wave는 전용 milestone target을 사용한다. 기존 `0.5.5-buildergate-stability` 요구사항을 이동하거나 복제하지 않고, 새 wave envelope Requirement가 기존 Requirement를 `depends_on` 회귀 계약으로 참조한다.
3. 기존 stable Requirement의 의미 변경·supersede, scope boundary 변경, `Stability=stable` 승격, G1 branch 결정은 critical gate로 취급한다. `--auto`로 우회하지 않는다.
4. 모든 동작 변경은 Requirement ID를 먼저 확보하고 failing regression test부터 TDD로 진행한다.
5. 각 구현 Phase는 자동 검증과 까칠한 reviewer의 `No findings` 재검토를 통과해야 완료한다.
6. `confirmed-bug-only`이면 G1이 선택한 국소 fix와 회귀 evidence를 `wave-1` 안에서 완료하고 종료한다. `wave-2`~`wave-5`는 pending/inactive로 남긴다.
7. `architectural migration`일 때만 `wave-2`~`wave-5`를 순차 활성화한다.
8. Wave 5의 two-release soak와 물리 삭제는 외부 시간·Tier 3 gate를 만족할 때까지 완료 처리하지 않는다.

## 검증과 안전 정지

- SpecKiwi MCP가 정상 target-scoped mutation의 유일한 경로다.
- `REL-BGSTAB-005`는 현재 작업과 무관한 draft blocker이므로 어느 wave에도 포함하지 않는다.
- 외부 Orca 저장소는 read-only 참고 대상이며 변경하지 않는다.
- 테스트 서비스는 `2222`만 사용하고 `node.exe` 또는 TCP `2001`/`2002` 프로세스를 중단하지 않는다.
- 하위 pipeline이 `NEEDS_USER`, `FAILED` 또는 critical gate를 반환하면 `--auto`를 중단하고 해당 wave를 complete로 기록하지 않는다.
